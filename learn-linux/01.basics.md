# Part 1: The Linux Kernel - The Restaurant Manager

## 1.1 What IS the Kernel? (The Restaurant Manager Analogy)

Imagine you're in a **restaurant**. You want to eat, but you don't go into the kitchen and cook. Instead:

```
YOU (Customer) → WAITER → KITCHEN (Chefs, Equipment)
```

Now let's map this to Linux:

```
┌─────────────────────────────────────────────────────────────┐
│                 THE RESTAURANT (Your Computer)              │
│                                                             │
│  ┌───────────────────────────────────────────────────────┐ │
│  │  YOU (the customer)                                   │ │
│  │  ┌─────────────────────────────────────────────────┐ │ │
│  │  │  YOUR PROGRAMS (Firefox, Terminal, Games)       │ │ │
│  │  │  "I want to open a file"                        │ │ │
│  │  └─────────────────────┬───────────────────────────┘ │ │
│  │                        │                              │ │
│  │                        ▼                              │ │
│  │  ┌─────────────────────────────────────────────────┐ │ │
│  │  │  THE WAITER (System Call Interface)             │ │ │
│  │  │  "Customer wants to open a file"                │ │ │
│  │  └─────────────────────┬───────────────────────────┘ │ │
│  └────────────────────────┼──────────────────────────────┘ │
│                           │                                │
│  ┌────────────────────────▼──────────────────────────────┐ │
│  │              THE KITCHEN (Kernel Space)               │ │
│  │                                                        │ │
│  │  ┌────────────────────────────────────────────────┐  │ │
│  │  │ HEAD CHEF (Process Scheduler)                  │  │ │
│  │  │ "Which order should I cook first?"             │  │ │
│  │  └────────────────────────────────────────────────┘  │ │
│  │                                                        │ │
│  │  ┌────────────────────────────────────────────────┐  │ │
│  │  │ PANTRY MANAGER (Memory Manager)                │  │ │
│  │  │ "Where should I store these ingredients?"      │  │ │
│  │  └────────────────────────────────────────────────┘  │ │
│  │                                                        │ │
│  │  ┌────────────────────────────────────────────────┐  │ │
│  │  │ FILE CABINET (Filesystem)                      │  │ │
│  │  │ "Where did we put yesterday's receipts?"       │  │ │
│  │  └────────────────────────────────────────────────┘  │ │
│  │                                                        │ │
│  │  ┌────────────────────────────────────────────────┐  │ │
│  │  │ EQUIPMENT SPECIALISTS (Device Drivers)         │  │ │
│  │  │ "How do I use the oven?" "How does the stove work?"│ │
│  │  └────────────────────────────────────────────────┘  │ │
│  │                                                        │ │
│  │  ┌────────────────────────────────────────────────┐  │ │
│  │  │ DELIVERY SYSTEM (Network Stack)                │  │ │
│  │  │ "How do I get ingredients from other restaurants?"│ │
│  │  └────────────────────────────────────────────────┘  │ │
│  └────────────────────────────────────────────────────────┘ │
│                           │                                │
│  ┌────────────────────────▼────────────────────────────────┐│
│  │           THE KITCHEN EQUIPMENT (Hardware)             ││
│  │  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐     ││
│  │  │  Stove  │ │ Fridge  │ │  Oven   │ │  Phone  │     ││
│  │  │  (CPU)  │ │  (RAM)  │ │ (Disk)  │ │(Network)│     ││
│  │  └─────────┘ └─────────┘ └─────────┘ └─────────┘     ││
│  └────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────┘
```

**Key Insight:** Your programs NEVER touch the hardware directly. Just like you never walk into the kitchen and start cooking, your programs always ask the kernel (the kitchen staff) to do things for them.

## 1.3 System Calls: How Programs Order from the Kitchen

When your program needs something, it places an **order** through the waiter. These orders are called **system calls**.

Think of it like ordering food:

| Your Order          | System Call | What the Kitchen Does         |
| ------------------- | ----------- | ----------------------------- |
| "I want a steak"    | `open()`    | Get the steak from the fridge |
| "Take a bite"       | `read()`    | Cut a piece and bring it      |
| "Save my leftovers" | `write()`   | Put it back in the fridge     |
| "Cook a new dish"   | `fork()`    | Start cooking a new meal      |
| "Throw it away"     | `close()`   | Clear the plate               |

Let's watch this happen:

```bash
# Watch everything that happens when you run a simple command
strace ls

# You'll see lines like:
# openat(AT_FDCWD, "/etc/passwd", O_RDONLY) = 3
# Translation: "Waiter! Open the password file! I want to read it!"
# The kitchen returns a ticket number (3)

# read(3, "root:x:0:0:root:/root:/bin/bash", 4096) = 50
# Translation: "I have ticket 3, give me some of that file"
# Kitchen gives 50 characters

# close(3)
# Translation: "I'm done with ticket 3"
```

**Your turn:**

```bash
# See what system calls the 'date' command makes
strace date 2>&1 | head -20

# See only file-related calls
strace -e trace=file ls
```

# Part 2: The Linux Filesystem - A Giant Filing Cabinet

## 2.1 The Filesystem as an Office Building

| Directory  | One-sentence job                         | What it actually does                                                                                                                                 |
| ---------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **/bin**   | "Essential user commands for everyone"   | Contains basic programs like `ls`, `cp`, `mv`, and `bash` that are needed to boot the system and work in single-user mode.                            |
| **/boot**  | "The startup essentials"                 | Holds the Linux kernel (`vmlinuz`), initial RAM disk (`initramfs`), and bootloader configs (GRUB) — without this, the PC won't start.                 |
| **/dev**   | "Hardware as files"                      | Provides special file representations of every device: hard disks (`/dev/sda`), terminals (`/dev/tty`), random number generators, etc.                |
| **/etc**   | "The system's control panel"             | Stores all system-wide configuration files: user accounts (`passwd`), disk mounts (`fstab`), network settings, and program configs.                   |
| **/home**  | "Each user's private desk"               | Contains personal folders for normal users (`/home/alice/Documents/`), with permissions keeping everyone's files separate.                            |
| **/lib**   | "Shared code library for /bin and /sbin" | Holds essential shared libraries (like `libc.so`) that programs in `/bin` and `/sbin` need to run — similar to `.dll` files on Windows.               |
| **/media** | "Auto-mounted removable drives"          | Serves as the default mount point for USB sticks, external hard drives, CDs, and DVDs when you plug them in.                                          |
| **/mnt**   | "Manual temporary mounting spot"         | Used by administrators to temporarily mount filesystems (like checking another hard drive or a network share) by hand.                                |
| **/opt**   | "Third-party add-on software"            | Houses optional, self-contained applications that aren't part of the base OS, like Google Chrome or VirtualBox.                                       |
| **/proc**  | "Live kernel and process snapshot"       | Virtual filesystem showing real-time system info: CPU (`cpuinfo`), memory (`meminfo`), and every running process as a numbered directory.             |
| **/root**  | "The admin's private home"               | Home directory for the root (superuser) user — kept separate from `/home` so the system can still log in even if `/home` is broken.                   |
| **/run**   | "Temporary runtime data since boot"      | Stores volatile runtime information like process IDs, socket files, and logged-in user sessions — cleared completely on every reboot.                 |
| **/sbin**  | "System administration binaries"         | Contains essential admin programs for root users: `fdisk` (partitioning), `mkfs` (formatting), `reboot`, and `shutdown`.                              |
| **/srv**   | "Service-specific data storage"          | Holds data for system services like web servers (`/srv/www/` for websites) and FTP servers (`/srv/ftp/`).                                             |
| **/sys**   | "Kernel and device tuning interface"     | Virtual filesystem exposing kernel internals, devices, and drivers — allows changing system behavior by writing to files.                             |
| **/tmp**   | "Scratch space for temporary files"      | World-writable directory for short-lived files that programs create and delete; often cleared on reboot and sometimes stored in RAM.                  |
| **/usr**   | "User-installed programs and data"       | Contains the majority of user commands (`/usr/bin/`), libraries (`/usr/lib/`), documentation, icons, and shared resources — not critical for booting. |
| **/var**   | "Frequently changing data storage"       | Holds variable data that grows over time: system logs (`/var/log/`), package caches (`/var/cache/`), print queues, and mail spools.                   |

---

And here are the **special/virtual filesystems** (also part of the hierarchy but not physical directories):

| Directory | One-sentence job                                       | What it actually does                                                             |
| --------- | ------------------------------------------------------ | --------------------------------------------------------------------------------- |
| **/proc** | (already covered above — virtual process/kernel info)  | Virtual filesystem in RAM showing kernel and process state in real time.          |
| **/sys**  | (already covered above — virtual device/kernel tuning) | Virtual filesystem exposing kernel objects, devices, and driver parameters.       |
| **/dev**  | (already covered above — virtual device files)         | Virtual filesystem dynamically populated by the kernel with all hardware devices. |
| **/run**  | (already covered above — virtual runtime data)         | `tmpfs` (RAM-based) filesystem for temporary runtime data since last boot.        |

---

This table covers **all 18 main directories** defined in the Linux Filesystem Hierarchy Standard (FHS) — not a single one missing.

Now let's explore each room:

### The Emergency Tools Closet (`/bin`)

```bash
# These are basic tools that MUST work even if nothing else is working
ls /bin
# You'll see: ls, cp, mv, rm, bash, cat, etc.
# These are like a hammer and screwdriver - always available
```

### The Startup Room (`/boot`)

```bash
ls /boot
# You'll see:
# vmlinuz-5.15.0-91-generic  ← The kernel (the chef)
# initrd.img-5.15.0-91-generic ← The startup instructions
# grub/                      ← The door lock mechanism
```

**Critical:** If this room gets full, the building can't open. Never let `/boot` get 100% full!

### The Equipment Interface Room (`/dev`)

This is the coolest room. It doesn't contain actual files - it contains **doorways to hardware**:

```bash
ls -la /dev
# Look for:
# /dev/sda  ← Your first hard drive (like the main kitchen fridge)
# /dev/null ← A trash chute that anything disappears into
# /dev/random ← A random number generator (like rolling dice)
```

**Try this:**

```bash
# Send "hello" into the trash chute
echo "hello" > /dev/null
# Nothing happens - it's gone forever!

# Get random numbers
head -c 10 /dev/random | xxd
# Shows random bytes (like rolling dice)
```

### The Building Rules Office (`/etc`)

This is where ALL configuration lives. Back this up or lose everything!

```bash
ls /etc
# Important files:
# /etc/passwd  ← List of employees (users)
# /etc/fstab   ← Where things are mounted (furniture placement)
# /etc/ssh/    ← Security guard rules for remote entry
```

### Employee Offices (`/home`)

Each person gets their own office. They can arrange it however they want:

```bash
# Your office
cd ~
ls -la
# Hidden files (.bashrc, .profile) are like your personal preferences
# - Desk arrangement (terminal prompt)
# - Coffee maker settings (aliases)
# - Personal notes (your files)
```

### The Virtual Rooms (`/proc` and `/sys`)

These are **magic rooms**. They don't physically exist - they're windows into what's happening right now:

```bash
# /proc - The "Currently Happening" window
cat /proc/cpuinfo
# Shows: What's happening with the CPU right now

cat /proc/meminfo
# Shows: How much memory is in use

# /proc/PID/ - Window into a specific employee's office
ps aux | grep bash  # Find your shell's PID
# Then look at that process's window:
ls /proc/1234/  # (replace 1234 with actual PID)
```

## 2.3 Permissions: The Building Security System

Every file has a security system. Let's use an **office analogy**:

```
-rwxr-xr--
│││││││││
││││││││└─── Visitor: Can read (look) but NOT write (touch)
│││││││└──── Visitor: Cannot write
││││││└───── Visitor: Cannot execute (can't use equipment)
│││││└────── Coworkers: Can read
││││└─────── Coworkers: Cannot write
│││└──────── Coworkers: Can execute (can use equipment)
││└───────── Owner: Can read
│└────────── Owner: Can write
└─────────── Owner: Can execute
```

**Three groups of people:**

| Group      | Office Analogy                   |
| ---------- | -------------------------------- |
| **Owner**  | The employee who has this office |
| **Group**  | People in the same department    |
| **Others** | Anyone else in the building      |

**Permission levels:**

| Permission      | File (Document)         | Directory (Room)                        |
| --------------- | ----------------------- | --------------------------------------- |
| **Read (r)**    | Can read the document   | Can see what's in the room (list files) |
| **Write (w)**   | Can change the document | Can add/remove things from the room     |
| **Execute (x)** | Can run the program     | Can enter the room (cd into it)         |

┌─────────────────────────────────────────────────────────────────┐
│ LINUX PERMISSIONS IN A NUTSHELL │
├─────────────────────────────────────────────────────────────────┤
│ │
│ r = 4 w = 2 x = 1 - = 0 │
│ │
│ ┌──────┬───────┬───────┬───────┬─────────────────────┐ │
│ │ Mode │ Owner │ Group │ Other │ Use case │ │
│ ├──────┼───────┼───────┼───────┼─────────────────────┤ │
│ │ 600 │ rw- │ --- │ --- │ Private files │ │
│ │ 644 │ rw- │ r-- │ r-- │ Normal files │ │
│ │ 700 │ rwx │ --- │ --- │ Private scripts │ │
│ │ 750 │ rwx │ r-x │ --- │ Team scripts │ │
│ │ 755 │ rwx │ r-x │ r-x │ Public scripts │ │
│ │ 660 │ rw- │ rw- │ --- │ Team files │ │
│ │ 664 │ rw- │ rw- │ r-- │ Shared files │ │
│ │ 777 │ rwx │ rwx │ rwx │ DANGER - never use! │ │
│ └──────┴───────┴───────┴───────┴─────────────────────┘ │
│ │
│ Command format: chmod XYZ filename │
│ Where: X=Owner, Y=Group, Z=Others │
│ │
│ View: ls -l filename │
│ Change owner: chown user:group filename │
│ │
└─────────────────────────────────────────────────────────────────┘
**Let's practice security settings:**

```bash
# Create a private document (only I can see it)
echo "My secret" > secret.txt
chmod 600 secret.txt
ls -l secret.txt
# Shows: -rw------- (like a locked drawer only I can open)

# Create a shared folder (everyone can enter, but only I can change)
mkdir shared
chmod 755 shared
ls -ld shared
# Shows: drwxr-xr-x (like a conference room anyone can enter)

# Create a public trash folder (anyone can throw things away)
mkdir trash
chmod 1777 trash  # The 1 at the front adds the sticky bit
ls -ld trash
# Shows: drwxrwxrwt (like a public trash can)
```

**The Sticky Bit (t):** In a public trash can, you can only throw away YOUR trash, not someone else's. That's what the sticky bit does on folders.

# Part 3: Processes - People Working in the Building

## 3.1 What's a Process? (Workers in the Building)

Every time you run a program, it becomes a **process** - like hiring a worker to do a task.

```
Process Attributes:

PID: 1234        ← Employee ID number
PPID: 567        ← Who hired them (their manager)
User: alice      ← Which department they work for
State: Running   ← Are they working or sleeping?
Memory: 2.1%     ← How much desk space they're using
```

Let's see all the workers:

```bash
# See all workers (processes)
ps aux
# Shows: Every employee, what they're doing, how much resources they use

# See just your workers
ps u

# Watch workers in real-time (like a security camera)
top
# Press 'q' to quit
# Press '1' to see each CPU core (like seeing each department)
# Press 'm' to sort by memory usage (who's using the most desk space)
```

---

## 3.2 Process States: What Workers Are Doing

| State                   | What it means           | Office Analogy                                       |
| ----------------------- | ----------------------- | ---------------------------------------------------- |
| **R (Running)**         | Actively working        | Typing on keyboard                                   |
| **S (Sleeping)**        | Waiting for something   | Waiting for an email                                 |
| **D (Uninterruptible)** | Waiting for hardware    | Waiting for printer - can't interrupt                |
| **Z (Zombie)**          | Dead but not cleaned up | Terminated employee whose office hasn't been cleared |
| **T (Stopped)**         | Suspended               | Coffee break                                         |

```bash
# See process states
ps aux | head -10
# Look at the STAT column: R, S, D, Z, T

# Create a sleeping process
sleep 300 &
# Now it's sleeping (waiting to wake up)

# See its state
ps aux | grep sleep
# STAT column shows 'S' (sleeping)
```

---

## 3.3 Managing Processes: HR for Workers

```bash
# Run a worker in the background (like sending them to work in another room)
sleep 500 &
# The & means "send to background"

# See background workers
jobs
# Shows: [1]+  Running  sleep 500 &

# Bring a worker to the foreground (talk to them directly)
fg
# Or: fg %1

# Stop a worker (Ctrl+Z)
# Then send them back to background:
bg

# Fire a worker (kill the process)
kill 1234  # Graceful firing - "Please finish up and leave"
kill -9 1234  # Immediate firing - security escorts them out

# Fire all workers with a certain name
pkill sleep
killall sleep
```

**Analogy for signals:**

| Signal  | Number | Office Analogy                                                          |
| ------- | ------ | ----------------------------------------------------------------------- |
| SIGTERM | 15     | "Please wrap up your work and leave"                                    |
| SIGKILL | 9      | Security drags them out immediately                                     |
| SIGHUP  | 1      | "Reload your configuration" (like asking them to reorganize their desk) |

---

## 3.4 Process Priorities: Who Gets CPU First?

The "nice" value determines how **nice** a process is to others:

- **-20 (Not nice at all)** - "I go first! I'm the most important!"
- **0 (Neutral)** - Normal politeness
- **19 (Very nice)** - "You go ahead, I'll wait"

```bash
# Start a very nice worker (low priority)
nice -n 19 ./long_job &

# Start an important worker (high priority - needs root)
sudo nice -n -10 ./important_job &

# Change priority of existing worker
renice -n 5 -p 1234  # Make process 1234 nicer
```

# Part 4: Systemd - The Building Manager

## 4.1 What's a Service? (Permanent Employees)

Some workers are **always there** - they're permanent employees of the building:

- **Security Guard (SSH)** - Always watches the door
- **Mail Room (Postfix)** - Delivers messages
- **Web Receptionist (Nginx)** - Greets website visitors

Systemd is the **Building Manager** who manages all these permanent employees.

```bash
# See all permanent employees (services)
systemctl list-units --type=service

# Check on a specific employee
systemctl status ssh
# Shows: Are they working? What are they doing? Any problems?
```

---

## 4.2 Managing Services: HR for Permanent Employees

```bash
# Tell the security guard to start working
sudo systemctl start ssh

# Tell them to stop
sudo systemctl stop ssh

# Ask them to restart (if they're confused)
sudo systemctl restart ssh

# Ask them to reload their rules (without stopping)
sudo systemctl reload ssh
# Like: "Security guard, here are new entry rules, please use them"

# Set them to start automatically when building opens
sudo systemctl enable ssh

# Set them NOT to start automatically
sudo systemctl disable ssh
```

**Important distinction:**

| Command            | What it does     | Office Analogy                      |
| ------------------ | ---------------- | ----------------------------------- |
| `start`/`stop`     | Controls NOW     | "Clock in"/"Clock out"              |
| `enable`/`disable` | Controls on boot | "On the schedule"/"Not on schedule" |

---

## 4.3 Viewing Logs: The Building's Security Camera

Every employee writes things down. These notes are stored in the **Building Log**.

```bash
# View all building logs
sudo journalctl

# View just the security guard's notes
sudo journalctl -u ssh

# Watch logs in real-time (like watching security cameras)
sudo journalctl -u ssh -f

# See what happened in the last hour
sudo journalctl --since "1 hour ago"

# See everything that went wrong
sudo journalctl -p 3  # Priority 3 = errors
```

# Part 5: Putting It All Together - Your First Admin Task

## Scenario: "The Office Is Running Slow!"

You're the building manager. People complain that work is slow. Let's investigate:

```bash
# 1. How long has the building been open? Are there too many people?
uptime
# Output: 10:30 up 5 days, load average: 2.5, 1.8, 1.2
# Load average: 1.0 = fully busy. 2.5 = OVERLOADED!

# 2. Who's working the hardest?
top -bn1 | head -20
# Shows: Top workers by CPU usage

# 3. Who's taking up the most desk space (memory)?
ps aux --sort=-%mem | head -10

# 4. Is the storage room full?
df -h
# Check if any disk is >90% full

# 5. Check the building logs for errors
sudo journalctl -p 3 -xb --since "1 hour ago"

# 6. Create a report for the building owner
{
    echo "=== BUILDING STATUS REPORT ==="
    echo "Time: $(date)"
    echo ""
    echo "Building open for: $(uptime)"
    echo ""
    echo "Memory available: $(free -h | grep Mem)"
    echo ""
    echo "Top 5 busiest workers:"
    ps aux --sort=-%cpu | head -6
} > ~/building_report.txt
```
