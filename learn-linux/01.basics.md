# Part 1: The Linux Kernel - The Heart of Your System

## 1.1 What Actually IS the Kernel?

The kernel is the **bridge** between software and hardware. When you run a program, it doesn't talk directly to your CPU, RAM, or disk. It asks the kernel to do it.

Let me give you a more detailed analogy:

## 1.2 Let's See the Kernel in Action

Let's actually look at your kernel:

```bash
# Check your kernel version
uname -r
# Output example: 5.15.0-91-generic
# 5.15 = version, 91 = patch level, generic = type

# Get ALL kernel information
uname -a
# Shows: kernel name, hostname, version, build date, architecture

# See kernel parameters (how it was configured)
cat /proc/cmdline
# Shows boot parameters passed to kernel

# See what kernel modules are loaded (drivers)
lsmod | head -20
# Shows currently loaded kernel modules/drivers

# See kernel messages (what happened during boot)
dmesg | head -50
# Shows kernel ring buffer - what kernel "said" during boot
```

## 1.3 The System Call Interface - How Programs Talk to Kernel

When your program needs to do something (open a file, create a process), it makes a **system call**. Let's see them:

```bash
# Trace system calls of a simple command
strace ls
# This shows EVERY system call ls makes!
# You'll see things like:
# openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY) = 3
# This is ls asking kernel to open a file

# To see just the file-related system calls:
strace -e trace=file ls

# See system calls of a running process
sudo strace -p PID

# List all system calls available on your system
man syscalls
# Or see the list:
ls /usr/include/x86_64-linux-gnu/asm/unistd_64.h | head -20
```

**Common system calls you should know:**

| System Call | What it does              | Example                   |
| ----------- | ------------------------- | ------------------------- |
| `open()`    | Open a file               | Opening a document        |
| `read()`    | Read from a file          | Reading that document     |
| `write()`   | Write to a file           | Saving changes            |
| `fork()`    | Create a new process      | Starting a new program    |
| `exec()`    | Run a new program         | Replacing current program |
| `kill()`    | Send signal to process    | Terminating a program     |
| `socket()`  | Create network connection | Opening a website         |

# Part 2: The Linux Filesystem - Complete Deep Dive

## 2.1 The Complete Filesystem Hierarchy Standard (FHS)

Every directory has a specific purpose. Let me explain each one in detail:

```
/ (Root Directory)
│
├── /bin - Essential User Binaries
│   ├── What goes here: Commands needed in single-user mode
│   ├── Examples: ls, cp, mv, rm, bash
│   └── Admin note: Even if nothing else is mounted, /bin must be available
│
├── /boot - Boot Files
│   ├── What goes here: Files needed to start Linux
│   ├── Examples: vmlinuz (kernel), initrd.img (initial ramdisk), grub/
│   └── Admin note: Often a separate partition, DO NOT delete anything here
│
├── /dev - Device Files
│   ├── What goes here: Files representing hardware devices
│   ├── Examples:
│   │   /dev/sda - First hard disk
│   │   /dev/sda1 - First partition on first disk
│   │   /dev/null - Black hole (discard data)
│   │   /dev/random - Random number generator
│   │   /dev/tty - Terminal devices
│   └── Admin note: These are NOT regular files - they're interfaces to hardware
│
├── /etc - System Configuration
│   ├── What goes here: All system-wide configuration
│   ├── Important subdirectories:
│   │   /etc/apt/ - Package manager config (Ubuntu/Debian)
│   │   /etc/yum.repos.d/ - Package manager config (RHEL)
│   │   /etc/ssh/ - SSH server configuration
│   │   /etc/nginx/ - Web server configuration
│   │   /etc/systemd/ - Systemd configuration
│   │   /etc/passwd - User account information
│   │   /etc/fstab - Filesystem mount points
│   └── Admin note: BACK THIS UP. This is where ALL configuration lives
│
├── /home - User Home Directories
│   ├── What goes here: Personal files for regular users
│   ├── Examples: /home/alice/, /home/bob/
│   └── Admin note: Often a separate partition for easier backup/reinstall
│
├── /lib - Essential Shared Libraries
│   ├── What goes here: Libraries needed by /bin and /sbin
│   ├── Examples: libc.so (C library), libssl.so (SSL)
│   └── Admin note: Don't mess with these unless you know what you're doing
│
├── /lib64 - 64-bit Libraries (on 64-bit systems)
│   └── Same as /lib but for 64-bit libraries
│
├── /media - Removable Media
│   ├── What goes here: Automatically mounted USB drives, CDs
│   ├── Examples: /media/usb/, /media/cdrom/
│   └── Admin note: Modern systems auto-mount here
│
├── /mnt - Temporary Mount Points
│   ├── What goes here: Manually mounted filesystems
│   ├── Examples: Mounting a network share temporarily
│   └── Admin note: Used for temporary mounts, not permanent
│
├── /opt - Optional Applications
│   ├── What goes here: Third-party software not managed by package manager
│   ├── Examples: /opt/google/chrome, /opt/teamviewer
│   └── Admin note: Each app gets its own subdirectory
│
├── /proc - Process Information (Virtual Filesystem)
│   ├── What goes here: Kernel and process information (in memory)
│   ├── Examples:
│   │   /proc/cpuinfo - CPU information
│   │   /proc/meminfo - Memory information
│   │   /proc/PID/ - Information about process with that PID
│   │   /proc/self/ - Current process
│   └── Admin note: NOT real files. Changes as system runs. DON'T write here
│
├── /root - Root User's Home
│   ├── What goes here: Home directory for root user
│   └── Admin note: Only root can access this
│
├── /run - Runtime Data
│   ├── What goes here: System information since last boot
│   ├── Examples: PID files, sockets, systemd data
│   └── Admin note: Cleared on reboot, don't put permanent files here
│
├── /sbin - System Binaries
│   ├── What goes here: System administration commands
│   ├── Examples: fdisk, ifconfig, iptables, reboot
│   └── Admin note: Only root typically runs these
│
├── /srv - Service Data
│   ├── What goes here: Data for services provided by the system
│   ├── Examples: /srv/www/ (website files), /srv/ftp/ (FTP files)
│   └── Admin note: Often used for web server document roots
│
├── /sys - System Information (Virtual Filesystem)
│   ├── What goes here: Kernel objects, hardware information
│   ├── Examples: /sys/class/net/ (network interfaces)
│   └── Admin note: Like /proc, this is virtual. DON'T write here
│
├── /tmp - Temporary Files
│   ├── What goes here: Temporary files, cleared on reboot
│   ├── Permissions: Usually sticky bit (1777)
│   └── Admin note: Monitor disk space - full /tmp causes issues
│
├── /usr - User Programs and Data (Secondary Hierarchy)
│   ├── /usr/bin/ - User binaries (non-essential)
│   ├── /usr/lib/ - Libraries for /usr/bin
│   ├── /usr/local/ - Locally compiled software
│   │   ├── /usr/local/bin/ - Locally installed programs
│   │   ├── /usr/local/lib/ - Libraries for local programs
│   │   └── /usr/local/src/ - Source code
│   ├── /usr/share/ - Architecture-independent data
│   │   ├── /usr/share/man/ - Manual pages
│   │   ├── /usr/share/doc/ - Documentation
│   │   └── /usr/share/icons/ - Icons
│   └── /usr/src/ - Kernel source code
│
└── /var - Variable Data
    ├── /var/log/ - Log files (CRITICAL for admins)
    │   ├── syslog - System log
    │   ├── auth.log - Authentication attempts
    │   ├── dmesg - Kernel messages
    │   └── apt/ - Package manager logs
    ├── /var/mail/ - User mail
    ├── /var/spool/ - Print queues, mail queues
    ├── /var/tmp/ - Persistent temporary files
    └── /var/www/ - Web server files (on some systems)
```

## 2.2 Virtual Filesystems: /proc and /sys Explained

These are SPECIAL. They don't exist on disk - they're created by the kernel in memory.

```bash
# Let's explore /proc - process information
ls /proc
# You'll see numbered directories (PIDs of running processes)
# And special files

# Check your CPU
cat /proc/cpuinfo | head -20

# Check your memory
cat /proc/meminfo

# See mounted filesystems
cat /proc/mounts

# See kernel parameters
cat /proc/sys/net/ipv4/ip_forward
# 0 means IP forwarding is off, 1 means on

# Change kernel parameter (temporarily)
echo 1 | sudo tee /proc/sys/net/ipv4/ip_forward
# This enables IP forwarding without reboot

# See what processes are using what
ls -la /proc/self/fd/
# Shows file descriptors for the current process

# Explore /sys - hardware information
ls /sys/class/net/
# Shows network interfaces
cat /sys/class/net/eth0/operstate
# Shows if network is up

ls /sys/class/block/
# Shows block devices (disks)
```

## 2.3 Device Files in /dev

These are how your programs talk to hardware:

```bash
# See all device files
ls -la /dev

# Types of device files:
# c = character device (stream of bytes) - keyboards, terminals
# b = block device (random access) - disks, partitions

# Disk devices
ls -la /dev/sd*
# sda, sda1, sdb, etc.
# sda = first SCSI/SATA disk
# sda1 = first partition on that disk

# Terminal devices
ls -la /dev/tty*

# Random number generators
ls -la /dev/random /dev/urandom

# Special devices
# /dev/null - discards anything written to it
# /dev/zero - produces zeros
# /dev/full - always says "disk full"

# Create a device file (advanced, just so you understand)
sudo mknod /tmp/testdev c 100 0
# Creates a character device with major=100, minor=0
ls -l /tmp/testdev
# Shows: crw-r--r-- 1 root root 100, 0 date /tmp/testdev
```

# Part 3: Filesystem Types - What's Under the Hood

## 3.1 Different Filesystem Types

Not all filesystems are the same. Each has different features:

```bash
# Check what filesystems you have
df -T
# Shows: Filesystem Type Size Used Avail Use% Mounted on
# /dev/sda1    ext4  100G  20G   75G  21% /

# Common filesystem types:
# ext4 - Standard Linux filesystem
# xfs - High performance, good for large files
# btrfs - Modern with snapshots, compression
# zfs - Advanced features (on some systems)
# tmpfs - In-memory filesystem
# nfs - Network filesystem
# vfat - FAT32 (for USB drives)

# See what filesystem a file is on
df -T /home

# Get filesystem statistics
sudo tune2fs -l /dev/sda1 | head -20  # For ext4
sudo xfs_info /dev/sda1  # For XFS
```

## 3.2 Mounting Filesystems

Attaching a filesystem to your directory tree:

```bash
# See what's mounted
mount
# Or
findmnt

# Mount a device manually
sudo mount /dev/sdb1 /mnt/usb

# Mount with specific options
sudo mount -o ro /dev/sdb1 /mnt/usb  # Read-only
sudo mount -o noexec /dev/sdb1 /mnt/usb  # No executing programs

# Unmount
sudo umount /mnt/usb
# If it says "target is busy", find what's using it:
lsof /mnt/usb
# Or
fuser -v /mnt/usb

# Permanent mounts go in /etc/fstab
cat /etc/fstab
# Format:
# device    mountpoint  filesystem  options  dump  pass
# /dev/sda1 /           ext4        defaults 0     1

# Add a permanent mount (BE CAREFUL)
echo "/dev/sdb1 /data ext4 defaults 0 0" | sudo tee -a /etc/fstab

# Test fstab without rebooting
sudo mount -a
```

## 3.3 Disk Space Management

```bash
# Check disk usage
df -h
# -h = human readable (GB, MB)

# Check disk usage of directories
du -sh /home
du -sh /var/log

# Find large directories
sudo du -sh /* 2>/dev/null | sort -h
# Shows size of top-level directories

# Find large files
find / -type f -size +100M -exec ls -lh {} \; 2>/dev/null
# Finds all files larger than 100MB

# Check inode usage (files, not space)
df -i
# If inodes are full, you can't create new files even with free space
```

# Part 4: Putting It All Together - Deep Understanding

## 4.1 How Reading a File Actually Works

Let's trace what happens when you open a file:

```bash
# Create a test file
echo "Hello World" > /tmp/test.txt

# Trace what happens when you read it
strace -e trace=open,read,close cat /tmp/test.txt
```

**What's happening behind the scenes:**

1. You type `cat /tmp/test.txt`
2. Shell finds `cat` in `/usr/bin`
3. Shell calls `fork()` to create a new process
4. Shell calls `exec()` to run `cat`
5. `cat` calls `open("/tmp/test.txt", O_RDONLY)`
   - Kernel checks permissions
   - Kernel looks up file in filesystem
   - Kernel returns file descriptor (a number)
6. `cat` calls `read(fd, buffer, size)`
   - Kernel reads from disk into kernel memory
   - Kernel copies data to `cat`'s memory
7. `cat` writes to stdout
8. `cat` calls `close(fd)`

## 4.2 Understanding the Boot Process Completely

Let's walk through exactly what happens when you turn on a Linux computer:

```
1. BIOS/UEFI
   │
   ├── Power is applied
   ├── CPU starts executing BIOS/UEFI code
   ├── POST (Power-On Self Test) runs
   ├── BIOS/UEFI looks for boot devices
   └── Loads bootloader from MBR or EFI partition

2. Bootloader (GRUB)
   │
   ├── GRUB stage 1 loaded from MBR
   ├── GRUB stage 1.5 loads filesystem driver
   ├── GRUB stage 2 loads from /boot/grub
   ├── You see GRUB menu (if configured)
   └── Loads kernel and initramfs into memory

3. Kernel Initialization
   │
   ├── Kernel decompresses itself
   ├── CPU detection and setup
   ├── Memory management initialization
   ├── Interrupt handlers set up
   ├── Device detection begins
   └── Mounts initramfs

4. initramfs (Initial RAM Filesystem)
   │
   ├── Loads necessary drivers (RAID, LVM, encryption)
   ├── Discovers root filesystem
   ├── Mounts root filesystem
   └── Transfers control to /sbin/init (systemd)

5. systemd (PID 1)
   │
   ├── Reads /etc/systemd/system/default.target
   ├── Starts all required services
   ├── Runs getty for login terminals
   └── System is now running
```

Let's examine each step:

```bash
# 1. See bootloader configuration
cat /boot/grub/grub.cfg | head -50

# 2. See kernel boot parameters
cat /proc/cmdline

# 3. See boot messages
dmesg | head -100

# 4. See initramfs contents
lsinitramfs /boot/initrd.img-$(uname -r) | head -20

# 5. See systemd boot performance
systemd-analyze
systemd-analyze blame
systemd-analyze critical-chain
```

# 🎯 Advanced Questions (Test Your Deep Understanding)

1. **Why does `/proc` and `/sys` exist? Why can't we just use regular files?**

   _Answer: They provide a uniform interface to kernel data structures. Regular files would require disk I/O and wouldn't reflect real-time changes._

2. **What happens if `/boot` is full? Can the system still boot?**

   _Answer: No - kernel updates require space. GRUB needs to read from /boot to load the kernel._

3. **Why can you delete a file that's currently being used?**

   _Answer: The kernel keeps the file open via inode. The directory entry is removed, but the file data remains until all processes close it._

4. **What's the difference between `/tmp` and `/var/tmp`?**

   _Answer: /tmp is cleared on reboot (often tmpfs, in memory). /var/tmp persists across reboots._

5. **Why can't you `cd` into `/proc/1234` if process 1234 doesn't exist?**

   _Answer: /proc is created on the fly. The kernel creates the directory only when you try to access it and the PID exists._
