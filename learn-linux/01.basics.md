## Module 1: Linux Architecture & System Fundamentals

### 1.1 The Linux Operating System Structure

Before you type a single command, you need to understand what you're working with. Linux is not like Windows or macOS—it's built on a philosophy of modular components.

```
┌─────────────────────────────────────────┐
│           USER SPACE                    │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐   │
│  │  Shell  │ │  Apps   │ │  GUI    │   │
│  │ (bash)  │ │(nginx)  │ │ (X11)   │   │
│  └─────────┘ └─────────┘ └─────────┘   │
├─────────────────────────────────────────┤
│      SYSTEM CALL INTERFACE              │
├─────────────────────────────────────────┤
│           KERNEL SPACE                  │
│  ┌─────────────────────────────────┐   │
│  │ Process Scheduler               │   │
│  │ Memory Manager                  │   │
│  │ File System                     │   │
│  │ Device Drivers                  │   │
│  │ Network Stack                   │   │
│  └─────────────────────────────────┘   │
├─────────────────────────────────────────┤
│           HARDWARE                      │
│  (CPU, RAM, Disks, Network Card)       │
└─────────────────────────────────────────┘
```

**Key Concepts to Understand:**

| Component      | Role                                            | Admin Responsibility                         |
| -------------- | ----------------------------------------------- | -------------------------------------------- |
| **Kernel**     | Core of OS, manages hardware, memory, processes | Choosing kernel parameters, modules, updates |
| **Shell**      | Command interpreter (bash, zsh, etc.)           | User environment, scripting                  |
| **Filesystem** | Organizes data on disk                          | Mount points, permissions, quotas            |
| **Processes**  | Running programs                                | Monitoring, killing, prioritizing            |
| **Systemd**    | Init system and service manager                 | Service management, boot process             |

### 1.2 The Filesystem Hierarchy Standard (FHS)

Linux organizes files differently than Windows. Every Linux admin MUST know where things go.

```bash
/                   # Root - everything starts here
├── bin/            # Essential user binaries (ls, cp, mv)
├── boot/           # Boot loader files (kernel, initrd)
├── dev/            # Device files (hardware interfaces)
├── etc/            # System configuration files
├── home/           # User home directories
├── lib/            # Essential shared libraries
├── media/          # Removable media mount points
├── mnt/            # Temporary mount points
├── opt/            # Optional application software
├── proc/           # Virtual filesystem (process info)
├── root/           # Root user's home directory
├── run/            # Runtime data (PID files, sockets)
├── sbin/           # System binaries (admin commands)
├── srv/            # Service data (web, FTP)
├── sys/            # Virtual filesystem (kernel info)
├── tmp/            # Temporary files
├── usr/            # User programs and data
│   ├── bin/        # Non-essential user binaries
│   ├── lib/        # Non-essential libraries
│   ├── local/      # Locally installed software
│   └── share/      # Architecture-independent data
└── var/            # Variable data (logs, mail, spool)
    ├── log/        # Log files
    ├── mail/       # User mail
    └── www/        # Web server content
```

**📝 Hands-On Practice:**

```bash
# Navigate to root and explore
cd /
ls -la

# Check what each directory contains
ls -la /bin
ls -la /etc
ls -la /var/log

# Check disk usage per directory
sudo du -sh /* 2>/dev/null | sort -h

# Find where a command is located
which ls
which systemctl

# Understand PATH
echo $PATH
```

**🔴 Critical Admin Knowledge:**

- `/etc` contains configuration—back this up regularly
- `/var/log` contains logs—monitor disk space here
- `/tmp` is often cleared on reboot
- Never touch `/proc` or `/sys` unless you know exactly what you're doing

### 1.3 The Boot Process (What Happens When You Power On)

Understanding boot helps you troubleshoot system startup issues.

```
1. BIOS/UEFI
   ↓ (Loads boot device)
2. Boot Loader (GRUB2)
   ↓ (Loads kernel & initramfs)
3. Kernel Initialization
   ↓ (Mounts root filesystem)
4. initramfs (Initial RAM Filesystem)
   ↓ (Loads necessary drivers)
5. systemd (PID 1)
   ↓ (Starts services)
6. Target/Runlevel
   ↓
7. Login Prompt
```

**📝 Hands-On Practice:**

```bash
# View kernel version and boot parameters
uname -a
cat /proc/cmdline

# Check boot logs
sudo dmesg | head -50
sudo journalctl -b | head -50

# View systemd targets
systemctl get-default
systemctl list-units --type=target

# Check which services start at boot
systemctl list-unit-files --type=service --state=enabled
```

**🔴 RHEL Note:** Boot process is identical. Red Hat uses the same GRUB2, systemd, and boot sequence.

### 1.4 The Linux Shell Environment

The shell is your primary interface as a Linux admin. Let's understand it deeply.

**Types of Shells:**

- **bash** (Bourne Again Shell) - Most common, default on most distros
- **sh** (Bourne Shell) - Original, POSIX standard
- **zsh** (Z Shell) - Advanced features
- **dash** (Debian Almquist Shell) - Lightweight, used for scripts

**Shell Startup Files:**

```
Login Shell:
/etc/profile → /etc/profile.d/* → ~/.bash_profile → ~/.profile

Interactive Non-Login Shell:
/etc/bash.bashrc → ~/.bashrc
```

**📝 Hands-On Practice:**

```bash
# View your current shell
echo $SHELL
echo $0

# View all available shells
cat /etc/shells

# Change your default shell
chsh -s /bin/bash
# Logout and back in to apply

# Explore environment variables
env
echo $HOME
echo $PATH
echo $PS1  # Prompt format

# Create a custom alias (add to ~/.bashrc)
alias ll='ls -la'
alias ..='cd ..'
alias c='clear'

# View your command history
history
!!  # Run last command
!100  # Run command number 100
```

### 1.5 File Types and Permissions (Deep Dive)

This is where many admins make mistakes. Let's understand it completely.

**File Types in Linux:**

```bash
ls -la
# Output: -rwxr-xr-x 1 user group 1234 Jan 1 10:00 file
#         ^
#         |
#    First character indicates type:
#    - = regular file
#    d = directory
#    l = symbolic link
#    c = character device (e.g., /dev/tty)
#    b = block device (e.g., /dev/sda)
#    p = named pipe
#    s = socket
```

**Permission Structure:**

```
-rwxr-xr-x
│││││││││
││││││││└─── Others: Execute
│││││││└──── Others: Write
││││││└───── Others: Read
│││││└────── Group: Execute
││││└─────── Group: Write
│││└──────── Group: Read
││└───────── Owner: Execute
│└────────── Owner: Write
└─────────── Owner: Read

rwx = 7 (4+2+1)
rw- = 6 (4+2+0)
r-x = 5 (4+0+1)
r-- = 4 (4+0+0)
```

**📝 Comprehensive Practice:**

```bash
# Create test environment
mkdir -p ~/permissions_test
cd ~/permissions_test

# Create various file types
touch regular_file.txt
ln -s regular_file.txt symlink_file
sudo mknod char_device c 100 0
mkfifo named_pipe

# View them
ls -la

# Permission exercises
echo "Hello" > test.txt
ls -l test.txt

# Change owner
sudo useradd testuser
sudo chown testuser test.txt
ls -l test.txt

# Change group
sudo chgrp testuser test.txt

# Change permissions numerically
chmod 755 test.txt
ls -l test.txt

# Change permissions symbolically
chmod u+x,g-w,o-r test.txt
ls -l test.txt

# Special permissions - SUID (Set User ID)
chmod u+s test.txt
ls -l test.txt  # Shows -rwsr-xr-x

# Special permissions - SGID (Set Group ID)
chmod g+s test.txt

# Special permissions - Sticky Bit (on directories)
mkdir shared_dir
chmod 1777 shared_dir
ls -ld shared_dir  # Shows drwxrwxrwt

# Understanding umask
umask  # Shows current value (e.g., 0022)
# Default permissions: 666 for files, 777 for directories
# New file permissions = 666 - umask
touch newfile.txt
ls -l newfile.txt
```

**🔴 RHEL Note:** Permissions work identically. RHEL adds SELinux context which you'll see with `ls -Z`.

### 1.6 Process Management Deep Dive

Processes are running programs. As an admin, you need to control them.

**Process States:**

- **R (Running)** - Currently executing
- **S (Sleeping)** - Waiting for an event
- **D (Uninterruptible sleep)** - Waiting for I/O
- **Z (Zombie)** - Terminated but not reaped by parent
- **T (Stopped)** - Suspended

**Process Attributes:**

- **PID** - Process ID
- **PPID** - Parent Process ID
- **UID/EUID** - User ID / Effective User ID
- **Nice value** - Priority (-20 to 19, lower = higher priority)

**📝 Comprehensive Practice:**

```bash
# View processes
ps aux
ps -ef
ps -e --forest  # Tree view

# Real-time monitoring
top
# In top:
# Press '1' to see each CPU core
# Press 'm' to sort by memory
# Press 'k' to kill a process
# Press 'q' to quit

# Better alternative
htop  # Install if needed: sudo apt install htop

# Find a specific process
ps aux | grep nginx
pgrep nginx
pidof nginx

# Process tree
pstree -p
pstree -u

# Change process priority
nice -n 10 ./long_running_script &
renice -n 5 -p PID

# Send signals to processes
kill -l  # List all signals
kill -15 PID  # SIGTERM (graceful termination)
kill -9 PID   # SIGKILL (force kill)
killall nginx
pkill -u username

# Background and foreground
sleep 100 &  # Run in background
jobs         # List background jobs
fg %1        # Bring job 1 to foreground
bg %1        # Resume in background
```

### 1.7 Systemd Service Management

Modern Linux distributions use systemd as the init system. This is your primary tool for managing services.

**Systemd Unit Types:**

- `.service` - System services
- `.socket` - Socket activation
- `.timer` - Timers (cron replacement)
- `.target` - Groups of units (runlevels)
- `.mount` - Mount points

**📝 Comprehensive Practice:**

```bash
# Understanding systemd hierarchy
systemd-cgls  # View control group tree
systemd-analyze  # Boot performance
systemd-analyze blame  # Slow services
systemd-analyze critical-chain  # Boot dependency chain

# Service management
systemctl list-units --type=service
systemctl list-unit-files --type=service

# Start/stop services
sudo systemctl start nginx
sudo systemctl stop nginx
sudo systemctl restart nginx
sudo systemctl reload nginx  # Graceful reload

# Enable/disable at boot
sudo systemctl enable nginx
sudo systemctl disable nginx
sudo systemctl is-enabled nginx

# Check service status
systemctl status nginx
systemctl show nginx  # All properties

# Create a custom service
sudo cat > /etc/systemd/system/myscript.service << 'EOF'
[Unit]
Description=My Custom Script
After=network.target

[Service]
Type=simple
User=ubuntu
ExecStart=/home/ubuntu/labs/myscript.sh
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
EOF

# Create the script
cat > ~/labs/myscript.sh << 'EOF'
#!/bin/bash
while true; do
    echo "$(date): Script running" >> /home/ubuntu/myscript.log
    sleep 60
done
EOF

chmod +x ~/labs/myscript.sh

# Reload systemd, enable, and start
sudo systemctl daemon-reload
sudo systemctl enable myscript
sudo systemctl start myscript
sudo systemctl status myscript

# View logs
sudo journalctl -u myscript -f
```

**🔴 RHEL Note:** systemd works identically on RHEL. This is one area where Ubuntu and RHEL are fully compatible.

## 🎯 Your First Admin Task

Now that you understand the fundamentals, here's a real-world scenario:

**Scenario:** A developer reports their web application is slow. You need to investigate.

```bash
# 1. Check system load
uptime
top -bn1 | head -5

# 2. Check memory usage
free -h
vmstat 1 5

# 3. Check disk I/O
iostat -x 1 5  # Install sysstat if needed: sudo apt install sysstat

# 4. Find memory-hungry processes
ps aux --sort=-%mem | head -10

# 5. Find CPU-hungry processes
ps aux --sort=-%cpu | head -10

# 6. Check web server logs
sudo tail -100 /var/log/nginx/error.log
sudo tail -100 /var/log/nginx/access.log

# 7. Check system logs
sudo journalctl -xe --since "1 hour ago"

# 8. Check open connections
ss -tulpn
netstat -tulpn

# 9. Create a report
{
    echo "=== System Report ==="
    echo "Uptime: $(uptime)"
    echo "Memory: $(free -h)"
    echo "Top 5 CPU Processes:"
    ps aux --sort=-%cpu | head -6
    echo "Top 5 Memory Processes:"
    ps aux --sort=-%mem | head -6
} > ~/system_report_$(date +%Y%m%d).txt
```
