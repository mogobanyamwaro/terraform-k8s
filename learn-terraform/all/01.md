## **Module 1: Terraform Basics & Setup**

### **1.1 What is Terraform?**

**Concept:** Terraform is an Infrastructure as Code (IaC) tool that lets you define and provision infrastructure using a declarative configuration language.

**Key Exam Points:**

- Created by HashiCorp
- Written in Go
- Uses HCL (HashiCorp Configuration Language)
- **Declarative** (you declare the end state, not the steps)
- **Idempotent** (running multiple times produces same result)

**📝 Exam Question:**

> Q: What does it mean that Terraform is "declarative"?
>
> A: You define the desired end state of your infrastructure, and Terraform determines the steps to reach that state.

### **1.4 Understanding Providers**

**Concept:** Providers are plugins that Terraform uses to interact with APIs (AWS, Azure, GCP, etc.)

**File: `providers.tf`**

```hcl
terraform {
  required_version = ">= 1.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 4.0"
    }
    random = {
      source  = "hashicorp/random"
      version = ">= 3.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
  # AWS credentials from environment variables or ~/.aws/credentials
}

provider "random" {
  # No configuration needed
}
```

**Key Exam Points:**

- **Source**: Where to find the provider (registry.terraform.io/hashicorp/aws)
- **Version**: Provider version constraint
- **Provider configuration**: Region, credentials, etc.

**Version Constraints:**
| Syntax | Meaning | Example |
|--------|---------|---------|
| `= 1.2.3` | Exact version | `version = "= 1.2.3"` |
| `~> 1.2` | Patch updates only | `version = "~> 1.2"` (allows 1.2.x but not 1.3) |
| `>= 1.2` | Minimum version | `version = ">= 1.2"` |
| `<= 1.2` | Maximum version | `version = "<= 1.2"` |
| `1.2` | Same as >= 1.2, < 2.0 | `version = "1.2"` |

**📝 Exam Questions:**

> Q: What does the provider block do in Terraform?
>
> A: It configures a specific provider (like AWS) with authentication details and region settings.

> Q: What does the version constraint `~> 2.3.0` mean?
>
> A: It allows any 2.3.x version but not 2.4.0 or higher (only patch updates).

## **Module 2: Resources & State**

### **2.1 Resources Deep Dive**

**Concept:** Resources are the most important element - they represent infrastructure components.

**File: `ec2.tf`**

```hcl
# Create an EC2 instance
resource "aws_instance" "web_server" {
  # Arguments
  ami           = "ami-0c55b159cbfafe1f0"  # Amazon Linux 2
  instance_type = "t2.micro"

  # Tags (metadata)
  tags = {
    Name = "Web Server"
    Environment = "Development"
    Owner = "Team Alpha"
  }

  # User data script (runs at boot)
  user_data = <<-EOF
    #!/bin/bash
    yum update -y
    yum install -y httpd
    systemctl start httpd
    systemctl enable httpd
    echo "<h1>Hello from Terraform</h1>" > /var/www/html/index.html
  EOF
}

# Create an S3 bucket with versioning
resource "aws_s3_bucket" "data" {
  bucket = "my-company-data-bucket-${random_id.suffix.hex}"

  # Force destroy even if not empty (for non-prod)
  force_destroy = true
}

# Random ID for unique bucket name
resource "random_id" "suffix" {
  byte_length = 4
}
```

**Resource Behavior:**
| Action | When It Happens |
|--------|-----------------|
| **Create** | Resource doesn't exist in state or real world |
| **Update** | Resource exists, arguments changed |
| **Destroy** | Resource removed from config or recreated |
| **Replace** | Resource must be recreated (e.g., changing immutable field) |

**📝 Exam Questions:**

> Q: What happens when you change the `ami` of an EC2 instance?
>
> A: The instance will be **replaced** (destroyed and recreated) because AMI is an immutable attribute.

> Q: What is `force_destroy` in an S3 bucket?
>
> A: It allows Terraform to delete the bucket even if it contains objects (dangerous for production!).

### **2.2 Understanding State**

**Concept:** Terraform tracks the state of your infrastructure in a state file.

**File: `terraform.tfstate`** (automatically created)

```json
{
  "version": 4,
  "terraform_version": "1.6.0",
  "resources": [
    {
      "mode": "managed",
      "type": "aws_instance",
      "name": "web_server",
      "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
      "instances": [
        {
          "attributes": {
            "id": "i-1234567890abcdef0",
            "ami": "ami-0c55b159cbfafe1f0",
            "instance_type": "t2.micro"
          }
        }
      ]
    }
  ]
}
```

**State Management Commands:**

```bash
# List all resources in state
terraform state list

# Show details of a specific resource
terraform state show aws_instance.web_server

# Move a resource in state
terraform state mv aws_instance.web_server aws_instance.web

# Remove a resource from state
terraform state rm aws_instance.web_server

# Pull remote state to local
terraform state pull

# Push local state to remote
terraform state push
```

**Key Exam Points:**

- **State file format**: JSON
- **Contains**: Resource IDs, attributes, dependencies
- **Sensitive**: Can contain passwords, keys (use `sensitive = true`)
- **Backends**: Where state is stored (local, S3, Terraform Cloud)

**📝 Exam Questions:**

> Q: Why does Terraform need a state file?
>
> A: To map configuration to real-world resources, track metadata, and improve performance.

> Q: Is it safe to edit terraform.tfstate manually?
>
> A: No - always use `terraform state` commands instead of manual editing.

> Q: What sensitive information might be in a state file?
>
> A: Database passwords, API keys, private keys, any resource attributes marked as sensitive.

### **2.3 Remote State**

**Concept:** Store state remotely for team collaboration.

**File: `backend.tf`**

```hcl
terraform {
  backend "s3" {
    bucket         = "my-terraform-state-bucket"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-state-lock"  # For state locking
  }
}

# Create the DynamoDB table for locking (run separately)
resource "aws_dynamodb_table" "terraform_lock" {
  name         = "terraform-state-lock"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    type = "S"
  }
}
```

**State Locking:**

- Prevents concurrent operations
- Requires backend that supports locking (S3 + DynamoDB)
- Automatic during `plan` and `apply`

**📝 Exam Questions:**

> Q: Why use remote state?
>
> A: For team collaboration, backup, and sharing outputs between configurations.

> Q: How does Terraform prevent two people from applying at the same time?
>
> A: State locking - with S3 backend, it uses DynamoDB for locking.

> Q: What happens if state locking fails?
>
> A: Terraform exits with an error and won't proceed until the lock is released.

## **Module 3: Variables & Outputs**

### **3.1 Input Variables**

**Concept:** Variables make configurations dynamic and reusable.

**File: `variables.tf`**

```hcl
# Simple variable with default
variable "region" {
  description = "AWS region"
  type        = string
  default     = "us-east-1"
}

# Variable with validation
variable "instance_type" {
  description = "EC2 instance type"
  type        = string

  validation {
    condition     = contains(["t2.micro", "t2.small", "t2.medium"], var.instance_type)
    error_message = "Instance type must be t2.micro, t2.small, or t2.medium."
  }
}

# Required variable (no default)
variable "environment" {
  description = "Environment name"
  type        = string
}

# List variable
variable "availability_zones" {
  description = "List of availability zones"
  type        = list(string)
  default     = ["us-east-1a", "us-east-1b"]
}

# Map variable
variable "amis" {
  description = "Map of AMIs by region"
  type        = map(string)
  default = {
    us-east-1 = "ami-0c55b159cbfafe1f0"
    us-west-2 = "ami-0a36eb8fadc9768d1"
  }
}

# Object variable (complex)
variable "network_config" {
  description = "Network configuration"
  type = object({
    vpc_cidr     = string
    subnet_count = number
    public       = bool
  })
  default = {
    vpc_cidr     = "10.0.0.0/16"
    subnet_count = 3
    public       = true
  }
}
```

**File: `main.tf`** (using variables)

```hcl
provider "aws" {
  region = var.region
}

resource "aws_instance" "web" {
  ami           = var.amis[var.region]
  instance_type = var.instance_type

  # Use list variable
  availability_zone = var.availability_zones[0]

  tags = {
    Name        = "Web Server"
    Environment = var.environment
  }
}

# Using object variable
resource "aws_vpc" "main" {
  cidr_block = var.network_config.vpc_cidr

  tags = {
    Name = "main-vpc"
  }
}
```

**Variable Definition Priority (highest to lowest):**

1. **Command line**: `terraform apply -var="instance_type=t2.small"`
2. **Variable files**: `terraform.tfvars` or `*.auto.tfvars`
3. **Environment variables**: `TF_VAR_instance_type`
4. **Defaults**: in variable block
5. **Interactive prompt**: if no value found

**File: `terraform.tfvars`**

```hcl
region         = "us-west-2"
instance_type  = "t2.small"
environment    = "development"
availability_zones = ["us-west-2a", "us-west-2b", "us-west-2c"]
```

**📝 Exam Questions:**

> Q: What are the three ways to set variable values?
>
> A: 1) `terraform.tfvars` file, 2) Command line `-var`, 3) Environment variable `TF_VAR_`

> Q: What happens if you don't set a required variable?
>
> A: Terraform will prompt you interactively for the value.

> Q: Can you validate variable values in Terraform?
>
> A: Yes, using the `validation` block (Terraform 0.13+).

### **3.3 Local Values**

**Concept:** Locals assign names to expressions for reuse within a module.

**File: `locals.tf`**

```hcl
locals {
  # Simple computed value
  environment_prefix = var.environment == "prod" ? "prd" : "dev"

  # Common tags reused everywhere
  common_tags = {
    Environment = var.environment
    ManagedBy   = "Terraform"
    Project     = "Web Application"
    CostCenter  = "IT-${upper(var.environment)}"
  }

  # Computed name
  instance_name = "${local.environment_prefix}-web-server-${random_id.suffix.hex}"

  # Filtered list
  public_subnets = [for s in aws_subnet.main : s.id if s.map_public_ip_on_launch]

  # Transformed map
  tags_with_name = merge(local.common_tags, {
    Name = local.instance_name
  })
}

resource "random_id" "suffix" {
  byte_length = 2
}
```

**File: `main.tf`** (using locals)

```hcl
resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = var.instance_type

  # Using local values
  tags = local.tags_with_name

  # Count based on environment
  count = var.environment == "prod" ? 3 : 1
}

# Using computed local
resource "aws_s3_bucket" "logs" {
  bucket = "${local.environment_prefix}-application-logs-${random_id.suffix.hex}"

  tags = local.common_tags
}
```

**📝 Exam Questions:**

> Q: What's the difference between variables and locals?
>
> A: Variables are set by users; locals are computed from variables and resources within the module.

> Q: Can locals reference resources?
>
> A: Yes, locals can reference any attribute from resources, data sources, variables, or other locals.

## **Module 4: Resource Meta-Arguments**

### **4.1 depends_on**

**Concept:** Explicitly declare dependencies between resources.

**File: `dependencies.tf`**

```hcl
# S3 bucket
resource "aws_s3_bucket" "data" {
  bucket = "application-data"
}

# IAM role that depends on bucket (implicit dependency via reference)
resource "aws_iam_role" "app_role" {
  name = "application-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Action = "sts:AssumeRole"
        Effect = "Allow"
        Principal = {
          Service = "ec2.amazonaws.com"
        }
      }
    ]
  })
}

# IAM policy that depends on both (explicit dependency)
resource "aws_iam_policy" "s3_access" {
  name        = "s3-access-policy"
  description = "Access to application bucket"

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Action = [
          "s3:GetObject",
          "s3:PutObject"
        ]
        Effect   = "Allow"
        Resource = "${aws_s3_bucket.data.arn}/*"
      }
    ]
  })

  depends_on = [
    aws_s3_bucket.data,
    aws_iam_role.app_role
  ]
}

# EC2 instance with explicit dependency on policy
resource "aws_instance" "app" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  iam_instance_profile = aws_iam_instance_profile.app.name

  depends_on = [
    aws_iam_policy.s3_access  # Wait for policy to be created
  ]
}
```

**📝 Exam Questions:**

> Q: When do you need `depends_on`?
>
> A: When Terraform can't automatically infer a dependency (e.g., when one resource affects another through side effects, not direct references).

> Q: What's the difference between implicit and explicit dependencies?
>
> A: Implicit dependencies come from resource references; explicit dependencies use `depends_on`.

### **4.2 count**

**Concept:** Create multiple instances of a resource.

**File: `count-example.tf`**

```hcl
variable "subnet_cidrs" {
  description = "CIDR blocks for subnets"
  type        = list(string)
  default     = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
}

variable "instance_names" {
  description = "Names for EC2 instances"
  type        = list(string)
  default     = ["web-01", "web-02", "web-03"]
}

# Create multiple subnets with count
resource "aws_subnet" "public" {
  count = length(var.subnet_cidrs)

  vpc_id                  = aws_vpc.main.id
  cidr_block              = var.subnet_cidrs[count.index]
  availability_zone       = data.aws_availability_zones.available.names[count.index]
  map_public_ip_on_launch = true

  tags = {
    Name = "public-subnet-${count.index + 1}"
    Zone = count.index % 2 == 0 ? "even" : "odd"
  }
}

# Create EC2 instances with count (conditional)
resource "aws_instance" "web" {
  count = var.environment == "prod" ? 3 : 1

  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
  subnet_id     = aws_subnet.public[count.index % length(aws_subnet.public)].id

  tags = {
    Name = var.instance_names[count.index]
    Index = count.index
  }
}

# Access count-created resources
output "instance_ids" {
  value = aws_instance.web[*].id  # All instances
}

output "first_instance_ip" {
  value = aws_instance.web[0].public_ip  # First instance
}
```

**Key Points:**

- `count.index` gives current index (0-based)
- Resources created with count become a **list**
- Access: `resource.name[INDEX].attribute`
- All instances created from same configuration

**📝 Exam Questions:**

> Q: What happens if you remove an item from the middle of a list when using `count`?
>
> A: Terraform will destroy and recreate subsequent resources because indexes shift.

> Q: How do you access the first resource created with count?
>
> A: `aws_instance.web[0]`

### **4.3 for_each**

**Concept:** Create multiple instances from a map or set of strings.

**File: `for-each-example.tf`**

```hcl
# Using for_each with a map
variable "instances" {
  description = "Map of instances to create"
  type = map(object({
    instance_type = string
    subnet_id     = string
    environment   = string
  }))
  default = {
    "web-01" = {
      instance_type = "t2.micro"
      subnet_id     = "subnet-12345"
      environment   = "dev"
    }
    "web-02" = {
      instance_type = "t2.small"
      subnet_id     = "subnet-67890"
      environment   = "dev"
    }
    "db-01" = {
      instance_type = "t3.medium"
      subnet_id     = "subnet-54321"
      environment   = "prod"
    }
  }
}

# Create instances from map
resource "aws_instance" "servers" {
  for_each = var.instances

  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = each.value.instance_type
  subnet_id     = each.value.subnet_id

  tags = {
    Name        = each.key
    Environment = each.value.environment
    ManagedBy   = "Terraform"
  }
}

# Using for_each with a set
resource "aws_iam_user" "developers" {
  for_each = toset(["alice", "bob", "charlie"])

  name = each.key
}

# Security group rules with for_each
locals {
  ingress_rules = {
    "ssh" = {
      from_port   = 22
      to_port     = 22
      protocol    = "tcp"
      cidr_blocks = ["10.0.0.0/8"]
    }
    "http" = {
      from_port   = 80
      to_port     = 80
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
    "https" = {
      from_port   = 443
      to_port     = 443
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}

resource "aws_security_group_rule" "ingress" {
  for_each = local.ingress_rules

  type              = "ingress"
  from_port         = each.value.from_port
  to_port           = each.value.to_port
  protocol          = each.value.protocol
  cidr_blocks       = each.value.cidr_blocks
  security_group_id = aws_security_group.web.id
}

# Access for_each resources
output "instance_details" {
  value = {
    for name, instance in aws_instance.servers :
    name => {
      id   = instance.id
      ip   = instance.public_ip
      type = instance.instance_type
    }
  }
}
```

**count vs for_each Comparison:**

| Aspect    | count                             | for_each                         |
| --------- | --------------------------------- | -------------------------------- |
| Input     | List                              | Map or set of strings            |
| Access    | Index-based (`[0]`)               | Key-based (`["web-01"]`)         |
| Stability | Shifts on removal                 | Stable keys                      |
| Use case  | Simple lists, identical resources | Named resources, complex configs |

**📝 Exam Questions:**

> Q: When would you prefer `for_each` over `count`?
>
> A: When resources have stable identifiers (names) and you want to avoid recreation when items are added/removed.

> Q: What's `each.key` and `each.value` in a for_each block?
>
> A: `each.key` is the map key or set element; `each.value` is the map value (for maps).

> Q: Can you use `for_each` with a list?
>
> A: Yes, but you must convert it to a set with `toset()` first.

## **Module 5: Data Sources**

### **5.1 Using Data Sources**

**Concept:** Data sources fetch information from providers without creating resources.

**File: `data-sources.tf`**

```hcl
# Get latest Amazon Linux 2 AMI
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["amzn2-ami-hvm-*-x86_64-gp2"]
  }

  filter {
    name   = "virtualization-type"
    values = ["hvm"]
  }
}

# Get current AWS caller identity
data "aws_caller_identity" "current" {}

# Get current region
data "aws_region" "current" {}

# Get availability zones
data "aws_availability_zones" "available" {
  state = "available"
}

# Get existing VPC by tag
data "aws_vpc" "selected" {
  tags = {
    Name = "production-vpc"
  }
}

# Get existing subnets in VPC
data "aws_subnets" "private" {
  filter {
    name   = "vpc-id"
    values = [data.aws_vpc.selected.id]
  }

  filter {
    name   = "tag:Type"
    values = ["private"]
  }
}

# Get S3 bucket
data "aws_s3_bucket" "logs" {
  bucket = "existing-logs-bucket"
}

# Use data sources in resources
resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t2.micro"

  availability_zone = data.aws_availability_zones.available.names[0]

  tags = {
    Name        = "Web Server"
    AccountID   = data.aws_caller_identity.current.account_id
    Region      = data.aws_region.current.name
    Environment = "Production"
  }
}
```

**Key Points:**

- Data sources are **read-only**
- Syntax: `data "<provider>_<type>" "<name>"`
- Use in resources: `data.<type>.<name>.<attribute>`
- Can use filters to find specific resources

**📝 Exam Questions:**

> Q: What's the difference between a resource and a data source?
>
> A: Resources create/manage infrastructure; data sources query existing infrastructure.

> Q: When would you use a data source?
>
> A: To fetch existing AMI IDs, VPC IDs, or any information about already-created resources.

> Q: Can data sources depend on resources?
>
> A: Yes, data sources can have dependencies and will wait for resources to be created.

## **Module 6: Modules**

### **6.1 Creating and Using Modules**

**Concept:** Modules are containers for multiple resources that are used together.

**Directory Structure:**

```
modules/
├── networking/
│   ├── main.tf
│   ├── variables.tf
│   └── outputs.tf
├── compute/
│   ├── main.tf
│   ├── variables.tf
│   └── outputs.tf
└── database/
    ├── main.tf
    ├── variables.tf
    └── outputs.tf
```

**File: `modules/networking/main.tf`**

```hcl
resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_hostnames = true
  enable_dns_support   = true

  tags = merge(var.tags, {
    Name = "${var.environment}-vpc"
  })
}

resource "aws_subnet" "public" {
  count = length(var.public_subnet_cidrs)

  vpc_id                  = aws_vpc.main.id
  cidr_block              = var.public_subnet_cidrs[count.index]
  availability_zone       = var.availability_zones[count.index]
  map_public_ip_on_launch = true

  tags = merge(var.tags, {
    Name = "${var.environment}-public-${count.index + 1}"
    Type = "Public"
  })
}

resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id

  tags = merge(var.tags, {
    Name = "${var.environment}-igw"
  })
}
```

**File: `modules/networking/variables.tf`**

```hcl
variable "environment" {
  description = "Environment name"
  type        = string
}

variable "vpc_cidr" {
  description = "CIDR block for VPC"
  type        = string
}

variable "public_subnet_cidrs" {
  description = "CIDR blocks for public subnets"
  type        = list(string)
}

variable "availability_zones" {
  description = "List of availability zones"
  type        = list(string)
}

variable "tags" {
  description = "Common tags for all resources"
  type        = map(string)
  default     = {}
}
```

**File: `modules/networking/outputs.tf`**

```hcl
output "vpc_id" {
  description = "ID of the VPC"
  value       = aws_vpc.main.id
}

output "public_subnet_ids" {
  description = "IDs of public subnets"
  value       = aws_subnet.public[*].id
}

output "internet_gateway_id" {
  description = "ID of the internet gateway"
  value       = aws_internet_gateway.main.id
}
```

**File: `main.tf`** (root module using networking module)

```hcl
module "networking" {
  source = "./modules/networking"

  environment           = var.environment
  vpc_cidr             = "10.0.0.0/16"
  public_subnet_cidrs   = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  availability_zones    = ["us-east-1a", "us-east-1b", "us-east-1c"]

  tags = {
    ManagedBy = "Terraform"
    Project   = "WebApp"
  }
}

module "compute" {
  source = "./modules/compute"

  environment      = var.environment
  vpc_id          = module.networking.vpc_id
  subnet_ids      = module.networking.public_subnet_ids
  instance_type   = var.instance_type
  instance_count  = var.instance_count

  tags = {
    ManagedBy = "Terraform"
    Project   = "WebApp"
  }
}

# Using module outputs
output "vpc_info" {
  value = {
    vpc_id            = module.networking.vpc_id
    public_subnet_ids = module.networking.public_subnet_ids
  }
}
```

**Module Sources:**
| Source | Example |
|--------|---------|
| Local path | `source = "./modules/networking"` |
| Terraform Registry | `source = "terraform-aws-modules/vpc/aws"` |
| GitHub | `source = "github.com/terraform-aws-modules/terraform-aws-vpc"` |
| S3 | `source = "s3::https://s3.amazonaws.com/bucket/module.zip"` |
| HTTP | `source = "https://example.com/module.zip"` |

**Module Versioning:**

```hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.0.0"  # For registry modules

  # ... configuration
}
```

**📝 Exam Questions:**

> Q: What are the benefits of using modules?
>
> A: Reusability, organization, abstraction, consistency, and versioning.

> Q: How do you pass information from a child module back to the root?
>
> A: Using `output` blocks in the child module.

> Q: Can you use modules from the Terraform Registry?
>
> A: Yes, by specifying the source as `namespace/name/provider` and optionally a version.

> Q: What's the difference between root module and child modules?
>
> A: The root module is the main directory where you run Terraform; child modules are called from the root.

## **Module 7: Terraform Workflow & Commands**

### **7.1 Complete Workflow Example**

Let's build a complete project demonstrating the full workflow.

**Step 1: Write Configuration**

```hcl
# File: main.tf
terraform {
  required_version = ">= 1.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.region
}

resource "aws_s3_bucket" "example" {
  bucket = "terraform-workflow-demo-${random_string.suffix.result}"

  tags = {
    Name        = "Workflow Demo"
    Environment = var.environment
  }
}

resource "random_string" "suffix" {
  length  = 8
  special = false
  upper   = false
}
```

**File: `variables.tf`**

```hcl
variable "region" {
  description = "AWS region"
  type        = string
  default     = "us-east-1"
}

variable "environment" {
  description = "Environment"
  type        = string
  default     = "dev"
}
```

**File: `outputs.tf`**

```hcl
output "bucket_name" {
  description = "Name of created bucket"
  value       = aws_s3_bucket.example.bucket
}

output "bucket_arn" {
  description = "ARN of created bucket"
  value       = aws_s3_bucket.example.arn
}
```

**Step 2: Initialize**

```bash
# Initialize the working directory
terraform init

# Output:
# Initializing modules...
# Initializing provider plugins...
# - Finding hashicorp/aws versions...
# - Finding hashicorp/random versions...
# - Installing hashicorp/aws v5.0.0...
# - Installing hashicorp/random v3.5.0...
# Terraform has been successfully initialized!
```

**Step 3: Format & Validate**

```bash
# Format code
terraform fmt

# Validate configuration
terraform validate
# Success! The configuration is valid.
```

**Step 4: Plan**

```bash
# Create a plan
terraform plan -out=plan.tfplan

# Output shows what will be created
# Plan: 2 to add, 0 to change, 0 to destroy.
```

**Step 5: Apply**

```bash
# Apply the saved plan
terraform apply plan.tfplan

# Or directly apply (with prompt)
terraform apply

# Apply without prompt (automation)
terraform apply -auto-approve
```

**Step 6: Inspect State**

```bash
# List resources
terraform state list
# random_string.suffix
# aws_s3_bucket.example

# Show specific resource
terraform state show aws_s3_bucket.example

# Refresh state
terraform refresh

# Output values
terraform output
```

**Step 7: Modify & Reapply**

```hcl
# Add a tag to the bucket
resource "aws_s3_bucket" "example" {
  bucket = "terraform-workflow-demo-${random_string.suffix.result}"

  tags = {
    Name        = "Workflow Demo"
    Environment = var.environment
    ManagedBy   = "Terraform"  # New tag
  }
}
```

```bash
# Plan shows the change
terraform plan
# ~ update in-place

# Apply the change
terraform apply
```

**Step 8: Destroy**

```bash
# Preview destruction
terraform plan -destroy

# Destroy everything
terraform destroy

# Destroy specific resource
terraform destroy -target=aws_s3_bucket.example
```

**Step 9: Workspaces (Environments)**

```bash
# List workspaces
terraform workspace list
# * default

# Create new workspace
terraform workspace new dev
terraform workspace new prod

# Switch workspace
terraform workspace select prod

# Current workspace
terraform workspace show
# prod

# Apply in prod workspace
terraform apply -var="environment=prod"
```

**📝 Exam Questions:**

> Q: What's the correct order of Terraform commands for a new project?
>
> A: `terraform init` → `terraform fmt` → `terraform validate` → `terraform plan` → `terraform apply`

> Q: What's the difference between `terraform plan` and `terraform apply`?
>
> A: `plan` shows what will happen without making changes; `apply` executes the changes.

> Q: What is `terraform refresh` used for?
>
> A: To update the state file with real-world infrastructure without making changes.

> Q: What are workspaces used for?
>
> A: To manage multiple environments (dev/staging/prod) with the same configuration.

resource "aws_instance" "lifecycle_example" {

### **8.3 Provisioners (Last Resort!)**

```hcl
resource "aws_instance" "provisioner_example" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  # File provisioner
  provisioner "file" {
    source      = "script.sh"
    destination = "/tmp/script.sh"

    connection {
      type        = "ssh"
      user        = "ec2-user"
      private_key = file("~/.ssh/id_rsa")
      host        = self.public_ip
    }
  }

  # Remote-exec provisioner
  provisioner "remote-exec" {
    inline = [
      "chmod +x /tmp/script.sh",
      "/tmp/script.sh"
    ]

    connection {
      type        = "ssh"
      user        = "ec2-user"
      private_key = file("~/.ssh/id_rsa")
      host        = self.public_ip
    }
  }

  # Local-exec provisioner
  provisioner "local-exec" {
    command = "echo ${self.public_ip} >> ips.txt"
  }

  # Provisioner failure behavior
  provisioner "local-exec" {
    command    = "echo 'This might fail'"
    on_failure = continue  # or fail (default)
  }
}
```

**📝 Exam Questions:**

> Q: Why are provisioners considered a last resort?
>
> A: Because they make configurations non-idempotent and can fail in ways that leave infrastructure in an unknown state.

> Q: What's the difference between `remote-exec` and `local-exec`?
>
> A: `remote-exec` runs on the created resource; `local-exec` runs on the machine running Terraform.

### **9.2 Scenario-Based Questions**

**Q9:** You have a configuration that creates 3 EC2 instances using `count`. You need to remove the second instance from the middle. What happens?

**✅ Answer:** Terraform will destroy instance 2 and then modify instances 3 to become the new 2, potentially causing downtime. This is why `for_each` is better for stable identifiers.

---

**Q10:** Your team of 5 developers is all working on the same Terraform configuration. How do you prevent conflicts?

**✅ Answer:** Use remote state with locking (S3 backend + DynamoDB table for locking). This ensures only one person can apply changes at a time.

---

**Q11:** You need to reference the VPC ID from another Terraform configuration. How?

**✅ Answer:** Use `terraform_remote_state` data source:

```hcl
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "my-state-bucket"
    key    = "network/terraform.tfstate"
    region = "us-east-1"
  }
}

resource "aws_instance" "web" {
  vpc_id = data.terraform_remote_state.network.outputs.vpc_id
}
```

---

**Q12:** You accidentally deleted a resource from your Terraform configuration. What happens on the next `apply`?

**✅ Answer:** Terraform will destroy that resource because it exists in state but not in configuration.
