## Question 2: Expose an Application via Service

### Scenario

You have an existing pod running nginx in the `web` namespace. However, the development team cannot access it because no service exists. Additionally, there are strict network policies that need to be verified.

### Tasks

1. Create a namespace called `web`
2. Run an nginx pod named `web-server` in the `web` namespace
3. Expose the nginx pod as a **ClusterIP** service named `web-service` on port 80
4. Verify the service is accessible from within the cluster by running a temporary busybox pod
5. **Bonus:** Change the service to `NodePort` and verify external access (if your Multipass setup allows)

## Let's Set Up the Environment First

Run this to create the initial setup:

```bash
# Create the namespace
kubectl create namespace web

# Create the nginx pod
kubectl run web-server --image=nginx --namespace=web --labels="app=web,env=production"

# Verify the pod is running
kubectl get pods -n web
```

## Now, Your Tasks

### Task 1: Expose the Pod as a Service

**Try to figure this out yourself first.** Here are hints:

- Use `kubectl expose` command
- Service type should be `ClusterIP` (default)
- Target port 80, service port 80
- Name the service `web-service`

<details>
<summary>Click here for the solution when you're ready</summary>

```bash
# Expose the deployment as a service
kubectl expose pod web-server --name=web-service --port=80 --target-port=80 --namespace=web

# Or using the service command
kubectl create service clusterip web-service --tcp=80:80 --namespace=web
```

</details>

### Task 2: Verify the Service

Check that the service was created:

```bash
# List services in web namespace
kubectl get svc -n web

# Get detailed service info
kubectl describe svc web-service -n web
```

### Task 3: Test Access from Within the Cluster

Run a temporary busybox pod to test accessing the service:

```bash
# Run busybox and try to curl the service
kubectl run test-pod --image=busybox -it --rm --restart=Never -n web -- sh

# Inside the busybox container, run:
curl web-service:80
# or
wget -O- web-service:80

# Exit with 'exit' command
```

**Question:** Did you get the nginx welcome page? If not, why?

### Task 4: Check Service Endpoints

Services route traffic to pods with matching labels. Verify the endpoint is connected:

```bash
# Check endpoints
kubectl get endpoints -n web

# View service as YAML
kubectl get svc web-service -n web -o yaml
```

## Common Issues & Solutions

**Issue 1:** Service created but no endpoints

```bash
# Check if pod has correct labels
kubectl get pods -n web --show-labels

# Service selector must match pod labels
kubectl describe svc web-service -n web | grep Selector
```

**Issue 2:** Can't curl from test pod

```bash
# Check DNS resolution
nslookup web-service

# Check if service has IP
kubectl get svc -n web
```

## Bonus: Convert to NodePort

If your Multipass setup allows external access, try this:

```bash
# Edit the service to change type to NodePort
kubectl edit svc web-service -n web

# Change 'type: ClusterIP' to 'type: NodePort' and save

# Get the NodePort
kubectl get svc web-service -n web

# You should see a PORT(S) column like: 80:31234/TCP
```

## CKA Exam Tips for This Question

- **Service types matter:** ClusterIP (internal), NodePort (external access), LoadBalancer (cloud)
- **Label matching is critical:** Services route based on selectors matching pod labels
- **Endpoints show if service is working:** No endpoints = no matching pods
- **DNS format:** `service-name.namespace.svc.cluster.local` or just `service-name` within same namespace

