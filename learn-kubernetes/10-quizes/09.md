## Question 9: Security Context and ServiceAccounts

### Scenario

You have an application that needs:

1. A non-root user to run containers (security best practice)
2. A ServiceAccount with specific permissions to read pods
3. A pod that cannot run as root or escalate privileges
4. A pod that needs read-only filesystem
5. Testing that pods cannot access Kubernetes API without proper authorization

### Tasks

1. Create a ServiceAccount named `pod-reader`
2. Create a Role and RoleBinding that allows the ServiceAccount to `list` pods
3. Create a pod that uses this ServiceAccount and test API access
4. Create a pod with SecurityContext that:
   - Runs as non-root user (UID 1000)
   - Prevents privilege escalation
   - Uses read-only root filesystem
5. Test what happens when a pod tries to run as root

## Let's Build This Step by Step

### Step 1: Create a ServiceAccount

```bash
# Create a ServiceAccount
kubectl create serviceaccount pod-reader-sa

# Verify
kubectl get serviceaccounts

# View details
kubectl describe serviceaccount pod-reader-sa
```

### Step 2: Create RBAC for the ServiceAccount

Create `rbac-for-sa.yaml`:

```yaml
# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader-role
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
---
# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
subjects:
  - kind: ServiceAccount
    name: pod-reader-sa
roleRef:
  kind: Role
  name: pod-reader-role
  apiGroup: rbac.authorization.k8s.io
```

Apply:

```bash
kubectl apply -f rbac-for-sa.yaml

# Verify
kubectl get role,rolebinding
```

### Step 3: Pod Using ServiceAccount with API Access

Create `sa-pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: sa-test-pod
spec:
  serviceAccountName: pod-reader-sa
  containers:
    - name: api-client
      image: bitnami/kubectl:latest
      command: ["/bin/sh", "-c"]
      args:
        - |
          echo "Testing API access with ServiceAccount"
          # Try to list pods (should work)
          kubectl get pods --token=/var/run/secrets/kubernetes.io/serviceaccount/token
          echo "---"
          # Try to list secrets (should fail - no permission)
          kubectl get secrets --token=/var/run/secrets/kubernetes.io/serviceaccount/token
          sleep 3600
```

Apply and test:

```bash
kubectl apply -f sa-pod.yaml

# Wait for pod to run
kubectl wait --for=condition=ready pod/sa-test-pod --timeout=30s

# Check pod logs to see API access results
kubectl logs sa-test-pod

# Also test exec into pod
kubectl exec -it sa-test-pod -- /bin/sh
# Inside pod, run:
kubectl auth can-i list pods
kubectl auth can-i list secrets
exit
```

### Step 4: Create Pod with SecurityContext (Non-root)

Create `secure-pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
  containers:
    - name: secure-app
      image: busybox
      command: ["/bin/sh", "-c"]
      args:
        - |
          echo "Running as user: $(id)"
          echo "Creating file in writable location"
          echo "test data" > /tmp/test.txt
          cat /tmp/test.txt

          # Try to write to root filesystem (should fail if read-only)
          echo "trying to write to /" > /test.txt || echo "Cannot write to / - good!"

          sleep 3600
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop:
            - ALL
```

Apply and test:

```bash
kubectl apply -f secure-pod.yaml

# Check user running the container
kubectl exec secure-pod -- id

# Verify cannot run as root
kubectl exec secure-pod -- whoami

# Check security context
kubectl describe pod secure-pod | grep -A10 "Security Context"
```

### Step 5: Pod with Read-Only Root Filesystem

Create `readonly-pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: readonly-pod
spec:
  containers:
    - name: readonly-app
      image: nginx:alpine
      securityContext:
        readOnlyRootFilesystem: true
        runAsNonRoot: true
        runAsUser: 101
      volumeMounts:
        - name: tmp-vol
          mountPath: /tmp
        - name: cache-vol
          mountPath: /var/cache/nginx
        - name: run-vol
          mountPath: /var/run
  volumes:
    - name: tmp-vol
      emptyDir: {}
    - name: cache-vol
      emptyDir: {}
    - name: run-vol
      emptyDir: {}
```

Apply and test:

```bash
kubectl apply -f readonly-pod.yaml

# Wait for pod to start
kubectl wait --for=condition=ready pod/readonly-pod --timeout=30s

# Test that writing to root fails
kubectl exec readonly-pod -- touch /test.txt 2>&1 | grep -i "read-only"

# Test writing to mounted volumes (should work)
kubectl exec readonly-pod -- touch /tmp/test.txt && echo "Can write to /tmp - good!"

# Check security context
kubectl get pod readonly-pod -o yaml | grep -A8 "securityContext"
```

### Step 6: Test Pod Running as Root (Should be prevented)

Create `root-pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: root-pod
spec:
  securityContext:
    runAsNonRoot: true # This will prevent root
  containers:
    - name: root-container
```

### Step 7: Pod Security Standards (Pod Security Admission)

Create a namespace with restricted Pod Security Standard:

```bash
# Create namespace with restricted policy
kubectl create namespace restricted

# Label namespace to enforce restricted policy
kubectl label namespace restricted pod-security.kubernetes.io/enforce=restricted
kubectl label namespace restricted pod-security.kubernetes.io/audit=restricted
kubectl label namespace restricted pod-security.kubernetes.io/warn=restricted

# Try to create a privileged pod in restricted namespace
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: privileged-pod
  namespace: restricted
spec:
  containers:
  - name: privileged
    image: nginx
    securityContext:
      privileged: true
EOF

# Check warnings (should show policy violations)
kubectl get pods -n restricted

# Create a compliant pod
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: compliant-pod
  namespace: restricted
spec:
  containers:
  - name: compliant
    image: nginx
    securityContext:
      runAsNonRoot: true
      runAsUser: 1000
      capabilities:
        drop: ["ALL"]
EOF

# Verify it runs
kubectl get pods -n restricted
```

### Scenario B: Pod SecurityContext at Container Level

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: granular-security
spec:
  securityContext:
    runAsUser: 1000 # Pod-level default
  containers:
    - name: container1
      image: nginx
      securityContext:
        runAsUser: 2000 # Override for this container
    - name: container2
      image: busybox
      command: ["sleep", "3600"]
      # Inherits pod-level runAsUser: 1000
```

### Scenario C: Adding Capabilities (Dropping all, adding specific)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: capability-pod
spec:
  containers:
    - name: app
      image: nginx
      securityContext:
        capabilities:
          drop:
            - ALL
          add:
            - NET_ADMIN
            - NET_RAW
      command: ["/bin/sh", "-c"]
      args:
        - |
          # Check capabilities
          cat /proc/self/status | grep Cap
          # Try privileged operations
          ip link set lo up
          sleep 3600
```

## Common Issues & Solutions

**Issue 1:** Pod fails with "runAsNonRoot forbids root user"

```bash
# Check container user
kubectl exec <pod> -- id

# Verify image doesn't force root
# Some images run as root by default - use alpine or distroless images
```

**Issue 2:** ServiceAccount token not mounted

```bash
# Check automount setting
kubectl get pod <pod> -o yaml | grep automountServiceAccountToken

# Verify token exists
kubectl exec <pod> -- ls -la /var/run/secrets/kubernetes.io/serviceaccount/
```

**Issue 3:** Cannot write to filesystem with read-only root

```bash
# Solution: Mount writable volumes
volumes:
- name: tmp
  emptyDir: {}
volumeMounts:
- name: tmp
  mountPath: /tmp
```

## Security Context Parameters

| Parameter                  | Purpose                | Example                           |
| -------------------------- | ---------------------- | --------------------------------- |
| `runAsUser`                | Specific UID           | `runAsUser: 1000`                 |
| `runAsNonRoot`             | Prevent root           | `runAsNonRoot: true`              |
| `runAsGroup`               | Primary GID            | `runAsGroup: 3000`                |
| `fsGroup`                  | Volume ownership       | `fsGroup: 2000`                   |
| `readOnlyRootFilesystem`   | Prevent writes to root | `readOnlyRootFilesystem: true`    |
| `allowPrivilegeEscalation` | Prevent setuid         | `allowPrivilegeEscalation: false` |
| `capabilities`             | Linux capabilities     | `drop: ["ALL"]`                   |
| `privileged`               | Full host access       | `privileged: false`               |

## CKA Exam Tips

- **Always use runAsNonRoot** for production pods
- **Drop all capabilities** and add only what's needed
- **ServiceAccounts are namespace-scoped** (unlike Users)
- **Default ServiceAccount has limited permissions** (cannot list pods)
- **Pod Security Standards** replace PodSecurityPolicies (deprecated)
- **Read-only root + writable volumes** is best practice
- **Never run containers as root** in production
