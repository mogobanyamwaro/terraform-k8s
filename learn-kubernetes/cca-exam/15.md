# 15. Hubble Observability Capabilities

**Domain:** Network Observability (10%)

## Concept Refresher

**Hubble** is Cilium’s observability layer. It does not scrape `/metrics` from your app. It **exports what eBPF already saw**: who talked to whom, ports, verdicts, optionally L7.

```text
eBPF datapath  ->  Hubble observer (in agent)
                        |
                        v
                 Hubble Relay (optional, cluster-wide)
                        |
            +-----------+-----------+
            v                       v
     hubble CLI              Hubble UI / metrics
```

### What you can see

- Source/destination **identity**, pod, namespace
- IP, port, protocol
- **FORWARDED** vs **DROPPED** (policy, CT, etc.)
- Direction
- With L7: HTTP method, path, status; DNS query; Kafka

### What Hubble is not

- Not a log aggregator for stdout
- Not distributed tracing like Jaeger (though it can correlate in a limited way)
- Not Prometheus itself — it can **expose metrics** Prometheus scrapes (`hubble_flows_processed_total`, drop reasons, …)

### Enable

Hubble is often enabled with Cilium. Relay + UI are extra flags (`hubble.relay.enabled`, `hubble.ui.enabled`).

## Hands-on

```bash
cilium hubble port-forward &
hubble status
hubble observe --since 2m -n shop
```

Generate curl traffic first.

## Exam tips

- **Hubble = eBPF flows.** Relay = cluster aggregator. UI = pretty Relay client.
- Drops + identity is the policy debugging story.
