# 02. Architecture and Component Roles

**Domain:** Architecture (20%)

## Concept Refresher

```text
                    Kubernetes API
                          |
          +---------------+----------------+
          |                                |
   cilium-operator                  cilium-agent (DaemonSet)
   (Deployment, HA)                 one pod per node
          |                                |
     IPAM pools                      eBPF programs + maps
     identity GC                     CNI ADD/DEL
     Cluster Mesh bits               policy, LB, Hubble export
     LB-IPAM / BGP helpers           talks to local kernel
```

### cilium-agent

- Runs on **every node** (DaemonSet, typically `kube-system`)
- Attaches eBPF programs to NICs / cgroup / XDP as configured
- Implements the **CNI** operations with `cilium-cni`
- Watches Endpoints, Services, NetworkPolicies, Cilium CRDs
- Allocates **identities** locally (synced cluster-wide)
- Exposes Hubble observer on the node
- Health checks (`cilium-health`)

If the agent is down on a node, **new pods on that node fail to network**; existing eBPF programs often keep forwarding until maps/programs are removed.

### cilium-operator

- **Cluster-scoped** Deployment (not per node)
- **IPAM** for `cluster-pool` (and cloud IPAM coordination)
- Garbage-collects unused identities and leftovers
- Cluster Mesh API server management, some Hubble/HA logic depending on version
- LoadBalancer IPAM, BGP control-plane support pieces

Operator down: **existing datapath keeps working**. New IP allocations and some GC/Cluster Mesh operations stall.

### Other components

| Component | Role |
| --- | --- |
| `cilium-cni` | Binary kubelet calls on pod add/del |
| `cilium-envoy` | Optional per-node L7 proxy (service mesh / L7 policy) |
| Hubble Relay | Aggregates per-node Hubble to one gRPC API |
| Hubble UI | Visual service map / flows |
| clustermesh-apiserver | Exports identities/services to remote clusters |
| `cilium-dbg` / `cilium` inside agent | Debug CLI in the agent pod |

### Control plane vs data plane

- **Data plane:** eBPF in the kernel (and optional Envoy)
- **Control plane:** agent + operator + Kubernetes API + CRDs

istiod is *not* a Cilium component. Do not mix Istio names into Cilium architecture questions.

## Exam tips

- **Agent = node = packets.** **Operator = cluster = IPs/GC/mesh helpers.**
- Operator death ≠ instant blackhole. Agent death on a node ≠ cluster-wide failure.
- Hubble UI is optional; Hubble/observer can exist without the UI.
