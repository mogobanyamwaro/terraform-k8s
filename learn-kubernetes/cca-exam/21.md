# 21. Role of eBPF and Key Benefits

**Domain:** eBPF (10%)

## Concept Refresher

**eBPF** (extended Berkeley Packet Filter) runs **sandboxed programs in the Linux kernel** at hook points: TC, XDP, sockets, cgroups, tracing.

Cilium **compiles/loads** BPF programs that:

- Redirect/forward packets
- Enforce identity policy
- Do Service LB (kube-proxy replacement)
- Export Hubble events
- Optionally encrypt (with kernel WG/IPsec)

### Why eBPF (exam list)

| Benefit | Meaning |
| --- | --- |
| Performance | Map lookups O(1), XDP before iptables |
| Safety | Verifier rejects unsafe programs; no kernel module crash-the-box (in theory) |
| Visibility | Same hooks Hubble uses |
| Flexibility | Update programs without reboot (vs custom kernel modules) |
| No sidecar required | Logic at host kernel, not userspace per pod |

### Programs + maps

- **Program:** bytecode attached to a hook
- **Map:** key/value in kernel (identities, CT, LB backends, policy)

Agent updates **maps** as pods come and go; programs stay attached.

### Verifier

Kernel **verifier** ensures programs terminate, no arbitrary kernel memory write. That is why eBPF is preferred over out-of-tree kernel modules for this use case.
