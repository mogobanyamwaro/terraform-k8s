# 11. Sidecarless Service Mesh Use Cases

**Domain:** Service Mesh (16%)

## Concept Refresher

A **service mesh** gives you traffic management, mTLS/encryption, L7 policy, and telemetry **without changing application code**.

### Sidecar-based (Istio classic, Linkerd)

Every pod gets a **proxy container**. Traffic redirected to the sidecar. Cost: RAM/CPU per pod, extra hops, injection complexity.

### Sidecarless (Cilium Service Mesh)

- **L3/L4** in **eBPF** on the node
- **L7** in a **per-node Envoy** (`cilium-envoy`), not per pod
- Apps stay **1/1** containers
- Identity still from Cilium (labels), encryption can be **WireGuard/IPsec** node-to-node rather than per-connection sidecar mTLS

Cilium mesh use cases:

- L7 NetworkPolicy (HTTP path, Kafka)
- Ingress / Gateway API
- Transparent encryption
- Hubble L7 traces
- Canary-ish L7 routing via Gateway API / Envoy (less “VirtualService weights” than Istio; know the idea)

Cilium does **not** try to be a full Istio clone (no destination subset CRDs of that shape). Exam: **benefits of sidecarless** and **when you still might use Istio**.

## Exam tips

- **Sidecarless = Cilium. Sidecar = Istio/Linkerd classic.**
- Envoy still exists — **one per node**, not per pod.
- Mesh domain is 16%: encryption + Gateway API + this comparison.
