# 01. Role of Cilium in Kubernetes

**Domain:** Architecture (20%)

## Concept Refresher

Cilium is the CNCF-graduated project that provides **networking, security, and observability** for Kubernetes using **eBPF** in the Linux kernel.

It typically replaces:

| Traditional piece | Cilium equivalent |
| --- | --- |
| CNI plugin (Flannel, Calico data path, etc.) | Cilium CNI + eBPF datapath |
| kube-proxy (iptables/IPVS) | Optional **kube-proxy replacement** |
| NetworkPolicy engine | Kubernetes NetworkPolicy **and** CiliumNetworkPolicy |
| Sidecar mesh for L7 (optional) | Sidecarless mesh (eBPF + node Envoy) |
| Flow logs (poor man's tcpdump) | **Hubble** |

Cilium is **not** a Kubernetes distro, not a CSI driver (by default), and not an ingress-only product. It **can** run an Ingress controller and Gateway API implementation as extra features.

### Why platforms pick it

- Identity-based policy (labels → eBPF identity) instead of IP-only firewalling
- High performance (maps, XDP) versus iptables chains
- Built-in Hubble observability
- Cluster Mesh for multi-cluster Services
- Optional encryption (WireGuard / IPsec)
- Optional BGP to the physical network

### What it is not responsible for

- Scheduling pods (kube-scheduler)
- Storing cluster state (etcd)
- Application metrics inside the process (that is Prometheus from the app)
- Replacing CoreDNS (Cilium can do DNS policy and a DNS proxy for FQDN; it is not your cluster DNS server by default)

## Question

**Q1.** Cilium’s primary data plane technology in the kernel is:

- A. iptables only
- B. Open vSwitch
- C. eBPF
- D. IPVS exclusively

**Q2.** Which job is *least* associated with Cilium’s role in a Kubernetes cluster?

- A. Allocating pod IPs (IPAM)
- B. Enforcing NetworkPolicy
- C. Running the Kubernetes API server
- D. Observing network flows with Hubble

**Q3.** Replacing kube-proxy with Cilium means:

- A. Services and NodePorts are implemented in eBPF instead of iptables/IPVS
- B. Services no longer exist; you must use Ingress
- C. etcd is no longer required
- D. CoreDNS is removed

**Q4.** A team already has Flannel as CNI. To use Cilium as CNI they must:

- A. Run both CNIs on every node permanently
- B. Remove or disable the other CNI; only one CNI datapath should own pod networking
- C. Install Cilium only as Hubble, leaving Flannel for IPs
- D. Convert Flannel VXLAN to Cilium automatically in-place with no downtime guaranteed

**Q5.** Cilium security policy is based primarily on:

- A. Source IP addresses only
- B. MAC addresses
- C. Security identities derived from labels
- D. Kubernetes UID of the kubelet process

**Q6.** Which statement is true?

- A. Cilium can only do L3/L4; L7 always requires Istio
- B. Cilium can enforce L7 (HTTP/gRPC/Kafka/DNS) using its proxy without a per-pod sidecar mesh
- C. Cilium cannot implement Kubernetes NetworkPolicy
- D. Cilium replaces kubelet

**Q7.** Hubble is:

- A. Cilium’s observability layer built on eBPF flow data
- B. A replacement for Prometheus
- C. The Cilium IPAM operator
- D. A BGP daemon

**Q8.** Which use case is a *classic* reason to adopt Cilium?

- A. Compiling the Linux kernel from source on each node
- B. High-performance, identity-aware networking and policy on Kubernetes
- C. Replacing containerd
- D. Storing persistent volumes

**Q9.** Cluster Mesh is about:

- A. Joining worker nodes to a single control plane
- B. Multi-cluster connectivity and global Services between Cilium clusters
- C. etcd clustering only
- D. Connecting laptops to Wi-Fi

**Q10.** Which OSI layers does Cilium commonly operate at?

- A. L1 only
- B. L3/L4 always, L7 when visibility or L7 policy is enabled
- C. L7 only, never L3
- D. L8 application business logic

## Answers

**Q1.** C. iptables is what Cilium *avoids* in the fast path when kube-proxy replacement is on. OVS is a different datapath. IPVS is an old kube-proxy mode.

**Q2.** C. API server is Kubernetes control plane.

**Q3.** A. ClusterIP/NodePort/LoadBalancer handling moves into eBPF.

**Q4.** B. One CNI. Hubble-only without being CNI is not the usual CCA model.

**Q5.** C. Identities from labels. IPs are ephemeral.

**Q6.** B. Node-level Envoy (or DNS proxy) for L7; no required app sidecar.

**Q7.** A.

**Q8.** B.

**Q9.** B.

**Q10.** B.

## Hands-on

```bash
cilium status
kubectl -n kube-system get ds,deploy | grep -E 'cilium|hubble|operator'
```

List what Cilium replaced on your cluster: is kube-proxy still there?

```bash
kubectl -n kube-system get ds kube-proxy || echo "no kube-proxy (replacement likely on)"
```

## Exam tips

- Three words: **connect, secure, observe**.
- eBPF is the *how*. Hubble / policy / CNI are the *what*.
- kube-proxy replacement is **optional** but a headline feature.
