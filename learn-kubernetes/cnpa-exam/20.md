# 20. IDPs, Catalogs, and Developer Portals

**Domain:** IDPs and Developer Experience (8%)

## Concept Refresher

**IDP (Internal Developer Platform / Portal — exam uses both flavours):** the **product UX** over platform capabilities.

**CNCF:** the *platform* is the product (APIs, paths). A **developer portal** (often **Backstage**) is the **shop window**: catalog, docs, templates, search, scorecards.

| Piece | Job |
| --- | --- |
| **Software catalog** | Inventory of services, owners, APIs, docs (metadata) |
| **Software templates** | Golden-path scaffolding (`cookiecutter` / Backstage Scaffolder) |
| **API-driven catalogs** | Same data via API, not only UI (Backstage catalog API, CRDs, Service Catalog-style) |
| **Docs / TechDocs** | Docs-like-code next to the service |
| **Plugins** | CI status, Kubernetes, cost, on-call — **if** APIs exist |

**Simplified access:** one place to **discover and request** capabilities (create service, get a namespace, see SLOs). The portal **must not** be the only API — CLI/Git should work.

Empty portal with no templates = failed DX. Templates with no portal can still be an IDP.

**Service catalog** historically (K8s / Open Service Broker) = **provision APIs**. On CNPA, “API-driven service catalogs” = requestable platform services, not only a website.

## Exam tips

- **Portal ≠ platform.** Portal **surfaces** APIs/templates.
- Catalog = **ownership + discovery**. Templates = **golden path start**.
- Measure **adoption**, not plugin count.
