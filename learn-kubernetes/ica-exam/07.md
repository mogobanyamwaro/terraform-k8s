# 07. Upgrading Istio: Canary Revisions, Tags, and In-Place

## Concept Refresher

Istio supports two upgrade strategies, and the exam objective names both explicitly.

| | In-place | Canary (revision-based) |
| --- | --- | --- |
| Control planes running | One, replaced | **Two, side by side** |
| Command | `istioctl upgrade` or `istioctl install` with a new version | `istioctl install --revision <rev>` |
| Data plane migration | All at once, on restart | **Per namespace, gradually** |
| Rollback | Reinstall the old version | Relabel the namespace and restart |
| Risk | Higher, all-or-nothing | Lower, incremental |
| Resource cost | Low | Two control planes |

**Canary is the recommended production approach and the more likely exam subject**, because it exercises revisions, tags, and namespace labels together.

### The revision model

A revision is a named control plane instance. Installing with `--revision 1-26-0` creates:

```text
Deployment:                       istiod-1-26-0
Service:                          istiod-1-26-0
MutatingWebhookConfiguration:     istio-sidecar-injector-1-26-0
Label on everything:              istio.io/rev=1-26-0
```

The default (unrevisioned) install has revision `default` and its objects are simply `istiod`, `istio-sidecar-injector`.

Workloads choose a revision through the namespace label:

```bash
kubectl label namespace demo istio.io/rev=1-26-0 --overwrite
kubectl label namespace demo istio-injection-        # must remove this
kubectl -n demo rollout restart deployment           # must restart
```

All three steps are required. **Missing any one of them means the namespace did not migrate**, and the failure is silent.

### Revision tags

A tag is an alias for a revision. It exists so that you can move many namespaces between revisions **without relabelling any of them**.

```text
Without tags:                      With tags:

namespace A: istio.io/rev=1-26-0   namespace A: istio.io/rev=prod
namespace B: istio.io/rev=1-26-0   namespace B: istio.io/rev=prod
namespace C: istio.io/rev=1-26-0   namespace C: istio.io/rev=prod

To upgrade: relabel all three     tag "prod" -> 1-26-1
            namespaces             then just restart the workloads
```

```bash
istioctl tag set prod --revision 1-26-1 --overwrite
```

The namespaces keep saying `istio.io/rev=prod`; the tag now points at the new control plane. Restart a namespace's workloads and they move. This is the cleanest answer to "upgrade many namespaces with minimal label churn", and it is very examinable.

A special case worth knowing: the tag named `default` makes a revisioned control plane serve the plain `istio-injection=enabled` label.

```bash
istioctl tag set default --revision 1-26-1 --overwrite
```

### The label precedence trap

```text
Namespace has istio-injection=enabled  AND  istio.io/rev=1-26-1
                          |
                          v
        istio-injection=enabled WINS. The revision label is IGNORED.
```

So a canary migration that only *adds* the revision label does nothing. You must remove `istio-injection`:

```bash
kubectl label namespace demo istio-injection- istio.io/rev=1-26-1 --overwrite
```

The trailing hyphen deletes the label. Doing both in one command is the safe idiom.

## Tasks

Start from a working 1.26.0 install.

1. Install a second control plane as revision `1-26-1` without disturbing the existing one. Verify both are running.
2. Migrate namespace `demo` from the default control plane to revision `1-26-1`, and prove the proxies moved.
3. Roll `demo` back to the original control plane.
4. Create a revision tag `stable` pointing at `1-26-1`, and attach namespace `shop` to the tag rather than the revision.
5. Move the `stable` tag to a different revision and migrate `shop` with no namespace relabelling.
6. Make a revisioned control plane serve namespaces that use the plain `istio-injection=enabled` label.
7. Upgrade the ingress gateway to the new revision.
8. Remove the old control plane once every namespace has migrated, and verify nothing is left behind.
9. Perform an in-place upgrade instead, and state what makes it riskier.
10. Determine which revision each proxy in the mesh is currently using, and find any that are stale.
11. A namespace was labelled with the new revision but the proxies are still on the old one. Diagnose it.
12. Verify an upgrade is safe to perform before doing it.

## Solutions

### 1. Install a second control plane

```bash
istioctl install --set profile=default --set revision=1-26-1 -y
```

In practice you would also point at the new version's binaries. Using a matching `istioctl` is cleanest:

```bash
# with the 1.26.1 istioctl on PATH
istioctl install --set profile=default --set revision=1-26-1 -y
```

Verify both control planes:

```bash
kubectl -n istio-system get pods -l app=istiod
```

```text
NAME                             READY   STATUS
istiod-7d8f9c5b4-x2klm           1/1     Running
istiod-1-26-1-6c9d8f7a5-mn3pq    1/1     Running
```

```bash
kubectl -n istio-system get deploy -l app=istiod
kubectl -n istio-system get svc -l app=istiod
istioctl tag list
```

```text
TAG        REVISION   NAMESPACES
default    default    demo,bookinfo
```

Two injection webhooks now exist:

```bash
kubectl get mutatingwebhookconfiguration | grep sidecar
```

```text
istio-sidecar-injector
istio-sidecar-injector-1-26-1
```

Crucially, **nothing has changed for existing workloads.** The new control plane is running but no namespace points at it, so no proxy is talking to it:

```bash
istioctl proxy-status
# every row still shows the old istiod
```

That is the whole point of canary: install first, migrate later.

### 2. Migrate a namespace

```bash
# The two-label operation, in one command
kubectl label namespace demo istio-injection- istio.io/rev=1-26-1 --overwrite

kubectl get ns demo --show-labels
```

```text
demo   Active   1h   istio.io/rev=1-26-1, kubernetes.io/metadata.name=demo
```

`istio-injection` is gone. Now restart:

```bash
kubectl -n demo rollout restart deployment
kubectl -n demo rollout status deployment httpbin
kubectl -n demo rollout status deployment sleep
```

Prove the proxies moved:

```bash
istioctl proxy-status | grep demo
```

```text
NAME                    ...  ISTIOD                            VERSION
httpbin-...demo         ...  istiod-1-26-1-6c9d8f7a5-mn3pq     1.26.1
sleep-...demo           ...  istiod-1-26-1-6c9d8f7a5-mn3pq     1.26.1
```

The `ISTIOD` column names the new control plane. That column is how you verify a canary migration; do not rely on the namespace label alone.

Also check the proxy image tag:

```bash
kubectl -n demo get pod -l app=httpbin \
  -o jsonpath='{.items[0].spec.containers[?(@.name=="istio-proxy")].image}{"\n"}'
# docker.io/istio/proxyv2:1.26.1
```

And confirm traffic never broke:

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{http_code}\n" http://httpbin:8000/get
kubectl -n bookinfo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "cross-revision: %{http_code}\n" http://httpbin.demo:8000/get 2>/dev/null
```

Workloads on different revisions interoperate normally. They share the same root CA and the same service registry, which is what makes gradual migration viable.

### 3. Roll back

```bash
kubectl label namespace demo istio.io/rev- istio-injection=enabled --overwrite
kubectl -n demo rollout restart deployment
kubectl -n demo rollout status deployment httpbin

istioctl proxy-status | grep demo
```

Back on the old control plane. Rollback is symmetric with migration, which is exactly why canary is the low-risk strategy: the escape hatch is two commands and it does not involve reinstalling anything.

### 4. A revision tag

```bash
istioctl tag set stable --revision 1-26-1
istioctl tag list
```

```text
TAG      REVISION   NAMESPACES
default  default    bookinfo,demo
stable   1-26-1
```

The tag creates its own webhook:

```bash
kubectl get mutatingwebhookconfiguration | grep sidecar
```

```text
istio-sidecar-injector
istio-sidecar-injector-1-26-1
istio-sidecar-injector-stable
```

Attach a namespace to the tag, not the revision:

```bash
kubectl create namespace shop 2>/dev/null
kubectl label namespace shop istio-injection- istio.io/rev=stable --overwrite

kubectl -n shop apply -f ~/istio-1.26.0/samples/httpbin/httpbin.yaml
kubectl -n shop wait --for=condition=ready pod -l app=httpbin --timeout=120s

istioctl proxy-status | grep shop
istioctl tag list
```

```text
TAG      REVISION   NAMESPACES
default  default    bookinfo,demo
stable   1-26-1     shop
```

The namespace label says `stable`, and the proxy is served by `istiod-1-26-1`. The indirection is now in place.

### 5. Move the tag

Install a third revision, then repoint the tag:

```bash
istioctl install --set profile=default --set revision=1-26-2 -y

istioctl tag set stable --revision 1-26-2 --overwrite
istioctl tag list
```

```text
TAG      REVISION   NAMESPACES
default  default    bookinfo,demo
stable   1-26-2     shop
```

**The namespace was not touched.** Its label is still `istio.io/rev=stable`. Confirm:

```bash
kubectl get ns shop --show-labels
```

Now just restart the workloads:

```bash
kubectl -n shop rollout restart deployment
kubectl -n shop rollout status deployment httpbin

istioctl proxy-status | grep shop
```

```text
httpbin-...shop   ...   istiod-1-26-2-...   1.26.2
```

With fifty namespaces on the `stable` tag, this is one `istioctl tag set` plus fifty restarts, instead of fifty relabel-plus-restart pairs. If a task mentions many namespaces, or minimising configuration churn, tags are the intended answer.

`--overwrite` is required when the tag already exists. Without it you get an error rather than a silent no-op, which is at least honest.

### 6. Make a revision serve the plain label

```bash
istioctl tag set default --revision 1-26-2 --overwrite
istioctl tag list
```

```text
TAG      REVISION   NAMESPACES
default  1-26-2     bookinfo,demo
stable   1-26-2     shop
```

Now namespaces with `istio-injection=enabled` are served by `istiod-1-26-2`:

```bash
kubectl get ns bookinfo --show-labels    # still istio-injection=enabled
kubectl -n bookinfo rollout restart deployment
kubectl -n bookinfo rollout status deployment productpage-v1

istioctl proxy-status | grep bookinfo
```

This is how you finish a canary upgrade without ever relabelling the namespaces that use the legacy label. It is also the mechanism that lets you delete the original unrevisioned control plane while keeping `istio-injection=enabled` working.

Note the collision rule: you cannot have both an unrevisioned `istiod` install and a `default` tag pointing elsewhere, because both would claim the same webhook. Remove the old install first, or accept that the tag takes over the webhook.

### 7. Upgrade the gateway

Gateways are ordinary workloads, so they need moving too. They are easy to forget, and a gateway left on a control plane you then delete is a real outage.

For a gateway installed with `istioctl` in `istio-system`:

```bash
istioctl install --set profile=default --set revision=1-26-2 -y
kubectl -n istio-system rollout restart deploy/istio-ingressgateway
kubectl -n istio-system rollout status deploy/istio-ingressgateway

istioctl proxy-status | grep ingressgateway
```

For a gateway installed with the Helm `gateway` chart in its own namespace, relabel the namespace and restart:

```bash
kubectl label namespace gateways istio-injection- istio.io/rev=1-26-2 --overwrite
kubectl -n gateways rollout restart deployment
istioctl proxy-status | grep -i gateway
```

A revisioned gateway can also be created explicitly, so that both old and new gateways run and you can shift DNS or the Service selector between them:

```bash
istioctl install --set profile=empty \
  --set revision=1-26-2 \
  --set components.ingressGateways[0].name=istio-ingressgateway-1-26-2 \
  --set components.ingressGateways[0].enabled=true \
  -y
```

That is the zero-downtime gateway upgrade. Verify continuously while it happens:

```bash
while true; do curl -s -o /dev/null -w "%{http_code} " http://localhost/productpage; sleep 1; done
```

### 8. Remove the old control plane

First confirm nothing still uses it.

```bash
# Which proxies point at which istiod?
istioctl proxy-status

# Any namespace still on the old revision or the plain label?
kubectl get ns -L istio-injection -L istio.io/rev

# Explicitly, anything still on "default"
istioctl proxy-status | awk 'NR>1 {print $NF, $(NF-1)}' | sort | uniq -c
```

Only when nothing references it:

```bash
istioctl uninstall --revision default -y
```

Or if the old one was revisioned:

```bash
istioctl uninstall --revision 1-26-0 -y
```

Verify:

```bash
kubectl -n istio-system get pods -l app=istiod
kubectl -n istio-system get deploy -l app=istiod
kubectl get mutatingwebhookconfiguration | grep sidecar
istioctl tag list
```

**Do not use `--purge` here.** `--purge` removes CRDs and cluster-wide resources shared by *all* revisions, which takes down the revision you just upgraded to. `--revision <name>` is the surgical form. Confusing the two mid-upgrade destroys the mesh, and it is the kind of decision an exam task can hinge on.

Sanity check afterwards:

```bash
istioctl proxy-status         # everything SYNCED to the surviving istiod
istioctl analyze -A
curl -s -o /dev/null -w "%{http_code}\n" http://localhost/productpage
```

### 9. In-place upgrade

```bash
# With the new istioctl binary on PATH
istioctl upgrade -y

# Equivalent, and more explicit about preserving settings
istioctl install -f iop.yaml -y
```

Then restart the data plane, because sidecars keep running the old proxy image until their pods are recreated:

```bash
kubectl -n demo rollout restart deployment
kubectl -n bookinfo rollout restart deployment
kubectl -n istio-system rollout restart deploy/istio-ingressgateway
```

Verify:

```bash
istioctl version
istioctl proxy-status
```

Why it is riskier, and worth being able to articulate:

- **There is no second control plane to fall back to.** Rollback means reinstalling the previous version, during which the mesh has no working control plane.
- **The whole data plane moves together**, so a regression hits every namespace at once instead of one.
- **Version skew is temporary but unavoidable**: until every pod restarts, old proxies talk to the new istiod. Istio supports skew of one minor version, so a jump from 1.24 to 1.26 in place is unsupported and can break the data plane.
- Immediately after the control plane swap, **existing proxies reconnect to the new istiod**, so a config-generation bug is felt instantly, not gradually.

The one thing in-place has going for it is that it needs only one control plane's worth of resources, which matters on small clusters.

**Never skip a minor version.** 1.24 to 1.25 to 1.26, not 1.24 to 1.26. This applies to both strategies and is a likely factual question.

### 10. Which revision is each proxy on

```bash
istioctl proxy-status
```

The `ISTIOD` and `VERSION` columns answer it. A compact summary:

```bash
istioctl proxy-status | awk 'NR>1 {print $(NF)}' | sort | uniq -c
```

```text
     12 1.26.2
      2 1.26.0
```

Two proxies are stale. Find them:

```bash
istioctl proxy-status | awk 'NR==1 || $NF=="1.26.0"'
```

From the Kubernetes side, by image:

```bash
kubectl get pods -A -o json | jq -r '
  .items[]
  | select(.spec.containers[]?.name == "istio-proxy")
  | "\(.metadata.namespace)/\(.metadata.name)\t\(
      [.spec.containers[] | select(.name=="istio-proxy") | .image] | join(""))"' \
  | sort -k2 | column -t
```

By revision label on the pod, which Istio stamps at injection:

```bash
kubectl get pods -A -L istio.io/rev
```

And the summary view:

```bash
istioctl version -o json | jq -r '.dataPlaneVersion[] | .IstioVersion' | sort | uniq -c
```

Any pod whose proxy version differs from the control plane version needs a restart. `istioctl analyze` flags this too:

```bash
istioctl analyze -A
```

```text
Info [IST0105] (Pod httpbin-... demo) The image of the Istio proxy running on the pod does not match the image defined in the injection configuration
```

`IST0105` is precisely the "you forgot to restart after an upgrade" finding. Recognising the code is useful.

### 11. Namespace relabelled but proxies did not move

The diagnostic order.

```bash
# 1. The precedence trap. Is istio-injection still present?
kubectl get ns shop --show-labels
```

If you see both `istio-injection=enabled` and `istio.io/rev=1-26-2`, that is the answer. `istio-injection` wins.

```bash
kubectl label namespace shop istio-injection- --overwrite
kubectl -n shop rollout restart deployment
```

```bash
# 2. Were the pods restarted at all? Compare ages.
kubectl -n shop get pods
kubectl get ns shop -o jsonpath='{.metadata.labels}' | jq
```

A pod older than the relabel has not been recreated, so it still holds the old sidecar.

```bash
# 3. Does the target revision exist?
istioctl tag list
kubectl -n istio-system get deploy -l app=istiod
kubectl get mutatingwebhookconfiguration | grep sidecar
```

A label naming a revision that does not exist means **no webhook matches, so no sidecar is injected at all**. New pods come up `1/1`. That is a nastier failure than staying on the old revision, and it is a good sabotage scenario.

```bash
# 4. Is the tag pointing where you think?
istioctl tag list
# a namespace on istio.io/rev=stable follows wherever "stable" points
```

```bash
# 5. Is the revision's webhook actually selecting this namespace?
kubectl get mutatingwebhookconfiguration istio-sidecar-injector-1-26-2 \
  -o jsonpath='{range .webhooks[*]}{.name}{": "}{.namespaceSelector}{"\n"}{end}'
```

```bash
# 6. Typos. The value must match the revision name exactly.
kubectl get ns -L istio.io/rev
istioctl tag list
```

`istio.io/rev=1.26.2` with dots does not match a revision named `1-26-2`. Revisions must be DNS labels.

```bash
# 7. The umbrella check
istioctl analyze -n shop
```

### 12. Pre-upgrade verification

```bash
# Current state is healthy before you change anything
istioctl proxy-status            # all SYNCED
istioctl analyze -A              # no errors
kubectl -n istio-system get pods

# What version am I on, and what am I going to?
istioctl version

# Check for deprecated or incompatible config
istioctl analyze -A --failure-threshold Info

# Back up all Istio configuration
mkdir -p ~/istio-backup && cd ~/istio-backup
for k in virtualservices destinationrules gateways serviceentries sidecars \
         workloadentries workloadgroups envoyfilters telemetries \
         peerauthentications requestauthentications authorizationpolicies; do
  kubectl get "$k" -A -o yaml > "$k.yaml"
done
kubectl -n istio-system get cm istio -o yaml > meshconfig.yaml
kubectl get istiooperator -A -o yaml > istiooperator.yaml 2>/dev/null

# Preview what the new version would change
istioctl manifest diff \
  <(istioctl manifest generate -f iop.yaml) \
  <(istioctl manifest generate -f iop.yaml --set revision=1-26-2)

# Confirm the version skew is legal (one minor at most)
```

`istioctl x precheck` is the purpose-built command and is worth reaching for first:

```bash
istioctl x precheck
```

```text
✔ No issues found when checking the cluster. Istio is safe to install or upgrade!
```

It checks Kubernetes version compatibility, CRD state, existing install health, and known incompatibilities. If a task asks you to verify readiness before upgrading, this is the intended answer.

## Verify

```bash
# Control planes present
kubectl -n istio-system get deploy -l app=istiod

# Tags and their namespaces
istioctl tag list

# Which revision serves each namespace
kubectl get ns -L istio-injection -L istio.io/rev

# Which control plane each proxy uses, and its version
istioctl proxy-status

# No stale proxies
istioctl analyze -A | grep -i IST0105 || echo "no stale proxies"

# Traffic still flows
curl -s -o /dev/null -w "ingress: %{http_code}\n" http://localhost/productpage
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "east-west: %{http_code}\n" http://httpbin:8000/get
```

## Exam Tips

**Canary migration is three steps, and all three are graded.** Remove `istio-injection`, add `istio.io/rev`, restart the workloads. One command for the labels:

```bash
kubectl label ns <ns> istio-injection- istio.io/rev=<rev> --overwrite
```

Then `kubectl rollout restart deployment -n <ns>`. Leaving out the restart is the most common way to lose the point on an otherwise correct answer.

**`istio-injection=enabled` beats `istio.io/rev`.** If both are on a namespace, the revision label does nothing. Whenever a migration "didn't work", check the labels first.

**`istioctl proxy-status` is how you prove a migration.** The `ISTIOD` column names the serving control plane. Namespace labels state intent; `proxy-status` states reality.

**Tags are the answer whenever the task involves many namespaces or minimising relabelling.** `istioctl tag set <tag> --revision <rev> --overwrite`, then restart. The namespaces never change.

**`istioctl tag set default --revision <rev>` lets a revisioned control plane serve `istio-injection=enabled`.** That is the trick for finishing an upgrade without touching legacy namespace labels.

**Uninstall by revision, never with `--purge`, when other revisions must survive.** `istioctl uninstall --revision <old> -y` is surgical. `--purge` removes shared CRDs and cluster resources and takes the new revision down with it.

**Do not forget the gateways.** They are workloads on a revision like anything else. A gateway still attached to a control plane you delete stops receiving config, and ingress dies while everything else looks fine.

**Never skip a minor version.** One minor at a time, in both strategies. Also remember Istio supports at most one minor version of skew between control plane and data plane, which is why the restart cannot be deferred indefinitely.

**`istioctl x precheck` before, `istioctl analyze -A` after.** The first tells you whether it is safe to start; the second catches `IST0105` stale proxies, which is the residue of an incomplete upgrade.

**Revision names must be valid DNS labels.** `1-26-2`, never `1.26.2`. A dotted name is rejected, and a mismatched label silently prevents injection entirely, producing `1/1` pods rather than an error.
