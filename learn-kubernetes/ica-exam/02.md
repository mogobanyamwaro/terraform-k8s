# 02. Installing Istio with istioctl and Profiles

## Concept Refresher

`istioctl install` is the fastest install path and the one the exam is most likely to test. It reads an **IstioOperator** specification, renders the manifests, and applies them. You can supply that spec three ways:

1. `--set` flags for one-off values.
2. `-f overlay.yaml` for a file.
3. `--set profile=<name>` to start from a named preset, then override.

### Profiles

A profile is a bundle of defaults. Knowing the differences between them is directly examinable, because a task like "install Istio with an egress gateway" is solved instantly if you know `demo` includes one.

| Profile | istiod | Ingress GW | Egress GW | ztunnel | CNI | Typical use |
| --- | :---: | :---: | :---: | :---: | :---: | --- |
| `default` | yes | yes | no | no | no | Production baseline |
| `demo` | yes | yes | **yes** | no | no | Learning, high telemetry |
| `minimal` | yes | no | no | no | no | Control plane only |
| `ambient` | yes | yes | no | **yes** | **yes** | Ambient data plane |
| `empty` | no | no | no | no | no | Base for fully custom builds |
| `preview` | yes | yes | no | no | no | Experimental features |
| `remote` | no | no | no | no | no | Multi-cluster remote, uses external istiod |

```bash
istioctl profile list
istioctl profile dump demo
istioctl profile dump --config-path components demo
istioctl profile diff default demo
```

`istioctl profile diff` is the fast way to answer "what does this profile actually change", and it is far quicker than reading the docs.

The important practical differences:

- **`demo` sets 100% trace sampling and full access logs.** Great for a lab, wasteful in production. It also sets lower resource requests so it fits on small clusters.
- **`default` has no egress gateway.** If a task needs one, you either use `demo` or explicitly enable the component.
- **`minimal` gives you istiod only.** Useful when gateways are managed separately, for instance as Gateway API `Gateway` resources.
- **`ambient` enables ztunnel and the CNI**, both of which are mandatory for ambient mode.

### The IstioOperator spec shape

Even when you never write one, this is the schema `--set` paths address, so learning the tree makes `--set` predictable.

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  name: my-istio
  namespace: istio-system
spec:
  profile: default            # base to start from
  revision: ""                # for canary installs, see 07.md
  hub: docker.io/istio        # image registry
  tag: 1.26.0                 # image tag

  meshConfig:                 # becomes the istio ConfigMap
    accessLogFile: /dev/stdout
    enableTracing: true
    defaultConfig:
      holdApplicationUntilProxyStarts: true

  components:                 # what to install
    pilot:
      enabled: true
      k8s:
        resources:
          requests:
            cpu: 500m
            memory: 2048Mi
        hpaSpec:
          minReplicas: 2
    ingressGateways:
      - name: istio-ingressgateway
        enabled: true
        k8s:
          service:
            type: LoadBalancer
            ports:
              - name: http2
                port: 80
                targetPort: 8080
    egressGateways:
      - name: istio-egressgateway
        enabled: false
    cni:
      enabled: false
    ztunnel:
      enabled: false

  values:                     # passthrough to the underlying Helm charts
    global:
      proxy:
        privileged: false
      logAsJson: true
    pilot:
      env:
        PILOT_ENABLE_ALPHA_GATEWAY_API: "true"
```

Two branches, two purposes, and mixing them up is a common mistake:

- **`spec.components`** controls *whether and how* a Kubernetes object exists: replicas, resources, Service type, ports, node selectors.
- **`spec.values`** is a raw passthrough to the Helm chart values, used for settings that have no first-class `components` field, such as `pilot.env` variables.
- **`spec.meshConfig`** configures *mesh behaviour*, and lands in the `istio` ConfigMap.

### `--set` path syntax

`--set` addresses the same tree with dots, and list elements with `[n]`:

```bash
istioctl install \
  --set profile=default \
  --set meshConfig.accessLogFile=/dev/stdout \
  --set components.egressGateways[0].enabled=true \
  --set components.egressGateways[0].name=istio-egressgateway \
  --set values.global.logAsJson=true \
  --set components.pilot.k8s.resources.requests.cpu=1000m \
  -y
```

`-y` is `--skip-confirmation`. Use it in the exam; the prompt wastes time.

### Preview before applying

```bash
# Render manifests without applying them
istioctl manifest generate --set profile=demo > /tmp/istio-demo.yaml

# What would change relative to what is installed?
istioctl manifest diff <(istioctl manifest generate --set profile=default) \
                       <(istioctl manifest generate --set profile=demo)

# Verify after install
istioctl verify-install
istioctl verify-install -f my-iop.yaml
```

`istioctl manifest generate` is also the answer to "install Istio without cluster admin rights": generate the YAML, hand it to someone who has the rights.

## Tasks

Use a **throwaway cluster** for these. Several tasks uninstall and reinstall.

1. List all available profiles and show exactly what the `demo` profile changes relative to `default`.
2. Install Istio using the `default` profile, into a control plane namespace of `istio-system`, without an interactive prompt.
3. Without reinstalling from scratch, add an egress gateway to the existing install.
4. Install Istio so that access logs are written to stdout for every proxy, and prove it took effect on a running workload.
5. Install with the ingress gateway exposed as a `NodePort` service on `30080` for HTTP, instead of a `LoadBalancer`.
6. Set istiod to request 1 CPU and 2Gi of memory, and to run a minimum of 2 replicas.
7. Generate the manifest for the `minimal` profile to a file, without touching the cluster. Count how many Kubernetes objects it would create.
8. Install Istio with the trust domain set to `mycompany.internal` and verify a workload certificate reflects it.
9. Install with `holdApplicationUntilProxyStarts` enabled mesh-wide, and explain what it fixes.
10. Uninstall Istio completely, including CRDs, and confirm nothing is left.
11. Install Istio from an `IstioOperator` file that enables the egress gateway, sets JSON logging, and disables tracing.
12. Verify an installation matches its intended spec.

## Solutions

### 1. Profiles and the demo/default difference

```bash
istioctl profile list
```

```text
Istio configuration profiles:
    ambient
    default
    demo
    empty
    minimal
    openshift
    openshift-ambient
    preview
    remote
    stable
```

```bash
istioctl profile diff default demo
```

The meaningful hunks:

```yaml
# demo enables the egress gateway
 egressGateways:
 - enabled: false        ->  - enabled: true
   name: istio-egressgateway

# demo turns on full access logging
 meshConfig:
+  accessLogFile: /dev/stdout

# demo samples every trace
   defaultConfig:
     tracing:
-      sampling: 1
+      sampling: 100

# demo asks for far fewer resources
   pilot:
     k8s:
       resources:
         requests:
-          cpu: 500m
-          memory: 2048Mi
+          cpu: 10m
+          memory: 100Mi
```

Dump one profile in full:

```bash
istioctl profile dump demo
istioctl profile dump --config-path components.egressGateways demo
istioctl profile dump --config-path meshConfig demo
```

### 2. Basic install, no prompt

```bash
istioctl install --set profile=default -y
```

The namespace defaults to `istio-system` and is created if missing. To be explicit:

```bash
istioctl install --set profile=default \
  --set values.global.istioNamespace=istio-system \
  -y
```

Verify:

```bash
kubectl -n istio-system get pods
istioctl verify-install
```

```text
✔ Istio is installed and verified successfully
```

### 3. Add an egress gateway to a running install

`istioctl install` is declarative and idempotent, so you re-run it with the extra component. **You must repeat the original settings**, because anything you omit reverts to the profile default. This is the single biggest gotcha with `istioctl install`.

```bash
istioctl install --set profile=default \
  --set components.egressGateways[0].name=istio-egressgateway \
  --set components.egressGateways[0].enabled=true \
  -y
```

Verify:

```bash
kubectl -n istio-system get deploy istio-egressgateway
kubectl -n istio-system get svc istio-egressgateway
```

The safer habit, and what you would do in production, is to keep an `IstioOperator` file under version control and always apply the whole file:

```bash
cat <<'EOF' > iop.yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: default
  components:
    egressGateways:
      - name: istio-egressgateway
        enabled: true
EOF

istioctl install -f iop.yaml -y
```

Now a later change never silently drops an earlier one.

### 4. Access logs to stdout

```bash
istioctl install --set profile=default \
  --set meshConfig.accessLogFile=/dev/stdout \
  -y
```

This edits the `istio` ConfigMap, and **existing proxies pick it up dynamically**; no pod restart is needed, because `accessLogFile` is delivered over xDS.

Verify the ConfigMap:

```bash
kubectl -n istio-system get cm istio -o jsonpath='{.data.mesh}' | grep accessLogFile
```

Then prove it end to end:

```bash
kubectl -n demo exec deploy/sleep -c sleep -- curl -sS -o /dev/null http://httpbin:8000/get
kubectl -n demo logs deploy/httpbin -c istio-proxy --tail=5
```

```text
[2026-08-19T12:00:00.123Z] "GET /get HTTP/1.1" 200 - via_upstream - "-" 0 429 3 2 "-" "curl/8.5.0" "abc-123" "httpbin:8000" "10.244.1.7:80" inbound|8000|| 127.0.0.6:39481 10.244.1.7:80 10.244.2.9:44238 outbound_.8000_._.httpbin.demo.svc.cluster.local default
```

Decoding that line is `33.md`. For now, note that its presence proves the setting is live.

To set a custom format, which is a plausible exam variation:

```bash
istioctl install --set profile=default \
  --set meshConfig.accessLogFile=/dev/stdout \
  --set meshConfig.accessLogEncoding=JSON \
  -y
```

### 5. NodePort ingress gateway

```bash
istioctl install --set profile=default \
  --set components.ingressGateways[0].name=istio-ingressgateway \
  --set components.ingressGateways[0].enabled=true \
  --set components.ingressGateways[0].k8s.service.type=NodePort \
  --set components.ingressGateways[0].k8s.service.ports[0].name=http2 \
  --set components.ingressGateways[0].k8s.service.ports[0].port=80 \
  --set components.ingressGateways[0].k8s.service.ports[0].targetPort=8080 \
  --set components.ingressGateways[0].k8s.service.ports[0].nodePort=30080 \
  -y
```

That is unwieldy. The file form is much better and less error-prone under time pressure:

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: default
  components:
    ingressGateways:
      - name: istio-ingressgateway
        enabled: true
        k8s:
          service:
            type: NodePort
            ports:
              - name: status-port
                port: 15021
                targetPort: 15021
                nodePort: 30021
              - name: http2
                port: 80
                targetPort: 8080
                nodePort: 30080
              - name: https
                port: 443
                targetPort: 8443
                nodePort: 30443
```

```bash
istioctl install -f ingress-nodeport.yaml -y
kubectl -n istio-system get svc istio-ingressgateway
```

**When you specify `ports`, you replace the whole list.** Omitting `status-port` (15021) breaks the gateway's readiness probe and the pod never becomes ready. Always include it.

### 6. istiod resources and replica floor

```bash
istioctl install --set profile=default \
  --set components.pilot.k8s.resources.requests.cpu=1000m \
  --set components.pilot.k8s.resources.requests.memory=2048Mi \
  --set components.pilot.k8s.hpaSpec.minReplicas=2 \
  -y
```

Verify:

```bash
kubectl -n istio-system get deploy istiod \
  -o jsonpath='{.spec.template.spec.containers[0].resources}'
kubectl -n istio-system get hpa istiod
```

```text
NAME     REFERENCE           TARGETS   MINPODS   MAXPODS   REPLICAS
istiod   Deployment/istiod   12%/80%   2         5         2
```

istiod ships with an HPA by default, so setting `replicaCount` alone gets overridden by the autoscaler. Set `hpaSpec.minReplicas` instead. That distinction is worth remembering.

```bash
istioctl manifest generate --set profile=minimal > /tmp/minimal.yaml
wc -l /tmp/minimal.yaml

grep '^kind:' /tmp/minimal.yaml | sort | uniq -c | sort -rn
```

### 8. Custom trust domain

```bash
istioctl install --set profile=demo \
  --set meshConfig.trustDomain=mycompany.internal \
  -y
```

Verify the mesh config:

```bash
kubectl -n istio-system get cm istio -o jsonpath='{.data.mesh}' | grep trustDomain
```

Restart a workload so it gets a fresh cert, then read the SAN:

```bash
kubectl -n demo rollout restart deploy/httpbin
kubectl -n demo rollout status deploy/httpbin

istioctl proxy-config secret deploy/httpbin.demo -o json \
  | jq -r '.dynamicActiveSecrets[] | select(.name=="default")
           | .secret.tlsCertificate.certificateChain.inlineBytes' \
  | base64 -d | openssl x509 -noout -text | grep 'URI:'
```

```text
URI:spiffe://mycompany.internal/ns/demo/sa/httpbin
```

Every `AuthorizationPolicy` `principals` value must now use the new trust domain:

```yaml
principals: ["mycompany.internal/ns/demo/sa/sleep"]
```

Note that `principals` omits the `spiffe://` scheme. Include it and the policy silently never matches. Istio does maintain `trustDomainAliases` to ease migration, but do not rely on it in an exam answer.

### 9. holdApplicationUntilProxyStarts

```bash
istioctl install --set profile=demo \
  --set meshConfig.defaultConfig.holdApplicationUntilProxyStarts=true \
  -y
```

What it fixes: without it, the app container and the sidecar start in parallel. An app that makes an outbound call immediately on boot can fire it before Envoy is ready, and that request fails with a connection error. Startup crash loops in short-lived jobs and in apps that connect to a database on init are the classic symptom.

With it enabled, Istio marks the sidecar as a container that must reach ready before the app container starts.

Verify on a new pod:

```bash
kubectl -n demo rollout restart deploy/httpbin
kubectl -n demo get pod -l app=httpbin -o jsonpath='{.items[0].spec.containers[?(@.name=="istio-proxy")].lifecycle}'
```

Per-workload instead of mesh-wide, which is often better practice:

```yaml
# On the pod template
metadata:
  annotations:
    proxy.istio.io/config: |
      holdApplicationUntilProxyStarts: true
```

The mirror-image problem at shutdown is `EXIT_ON_ZERO_ACTIVE_CONNECTIONS`, where the sidecar dies before in-flight requests drain:

```bash
--set meshConfig.defaultConfig.proxyMetadata.EXIT_ON_ZERO_ACTIVE_CONNECTIONS=true
```

### 10. Complete uninstall

```bash
# Remove the Istio install, keeping CRDs
istioctl uninstall --purge -y

# --purge removes everything including CRDs and the cluster-scoped resources
```

Then clean the namespace, which `uninstall` leaves behind on purpose:

```bash
kubectl delete namespace istio-system
```

Confirm nothing remains:

```bash
kubectl get crd | grep istio.io
kubectl get mutatingwebhookconfiguration | grep istio
kubectl get validatingwebhookconfiguration | grep istio
kubectl get clusterrole,clusterrolebinding | grep istio
kubectl get ns istio-system
```

All should be empty or `NotFound`.

Variants worth knowing:

```bash
# Remove only a specific revision (leaves other revisions running)
istioctl uninstall --revision 1-26-0 -y

# Remove what a given spec file describes
istioctl uninstall -f iop.yaml -y

# Preview what would go
istioctl uninstall --purge --dry-run
```

**`--purge` deletes CRDs, and deleting a CRD deletes every custom resource of that kind.** All your VirtualServices and AuthorizationPolicies go with it, irreversibly. In a real cluster you back those up first:

```bash
for k in virtualservices destinationrules gateways serviceentries \
         peerauthentications requestauthentications authorizationpolicies; do
  kubectl get "$k" -A -o yaml > "backup-$k.yaml"
done
```

### 11. Install from an IstioOperator file

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
metadata:
  name: exam-install
  namespace: istio-system
spec:
  profile: default
  meshConfig:
    enableTracing: false
    accessLogFile: /dev/stdout
    accessLogEncoding: JSON
  components:
    egressGateways:
      - name: istio-egressgateway
        enabled: true
  values:
    global:
      logAsJson: true
```

```bash
istioctl install -f iop.yaml -y
```

Verify each of the three requirements independently:

```bash
# Egress gateway exists
kubectl -n istio-system get deploy istio-egressgateway

# JSON access logs, tracing off
kubectl -n istio-system get cm istio -o jsonpath='{.data.mesh}' \
  | grep -E 'accessLogEncoding|enableTracing'

# istiod logs as JSON
kubectl -n istio-system logs deploy/istiod --tail=3
```

Note the distinction the task is really testing: `values.global.logAsJson` changes the format of **Istio component logs** (istiod's own output), while `meshConfig.accessLogEncoding` changes the format of **Envoy access logs**. Two different things with similar names.

```bash
# Generic health check
istioctl verify-install

# Check against the spec you intended
istioctl verify-install -f iop.yaml
```

## Exam Tips

**`istioctl install` is declarative, so re-running it with only new flags silently reverts the old ones.** This is the number one install mistake. If a task says "add X to the existing installation", either restate the full original configuration or work from a saved `IstioOperator` file. Recover the current spec if you did not save it:

```bash
kubectl -n istio-system get istiooperator -o yaml
```

**Always pass `-y`.** The confirmation prompt costs seconds you will want back later.

**`demo` for anything needing an egress gateway or visible access logs.** `default` for anything else. `minimal` when the task says control plane only. Recognising the right profile immediately is worth several minutes.

**`--set` list syntax is `[0]`, not a plain key.** `components.egressGateways[0].enabled=true` works; `components.egressGateways.enabled=true` does not, and fails in a confusing way.

**Know which branch a setting lives in.** Mesh behaviour goes in `meshConfig`. Kubernetes object shape goes in `components.<x>.k8s`. Anything else is `values`. If a `--set` path is rejected, you almost certainly picked the wrong branch.

**`meshConfig` changes are picked up live; sidecar template changes need a restart.** Access logging, tracing, and `outboundTrafficPolicy` take effect immediately. Anything that alters the injected pod spec, such as resource limits on the proxy or `holdApplicationUntilProxyStarts`, requires `kubectl rollout restart`. Knowing which is which stops you from restarting the world unnecessarily, and stops you from wondering why a change did nothing.

**If you override gateway `ports`, include `status-port` on 15021.** Otherwise the readiness probe fails and the gateway never comes up, and the cause is not obvious from the pod events.

**`istioctl manifest generate` is the answer to any "without applying" or "no cluster admin" phrasing.**

**`istioctl uninstall --purge` destroys your CRs along with the CRDs.** If a task asks you to reinstall, do not reach for `--purge` unless it explicitly says to remove everything.
