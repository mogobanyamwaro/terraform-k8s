# 23. PeerAuthentication and mTLS Modes

## Concept Refresher

**PeerAuthentication** is what a workload **accepts**. **DestinationRule `tls.mode`** is what a client **sends**. Both must agree or you get `503` with flags like `UH` / `UF` / connection reset.

```yaml
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: demo
spec:
  mtls:
    mode: STRICT
```

### Modes

| Mode | Inbound |
| --- | --- |
| `UNSET` | Inherit parent (namespace inherits mesh, workload inherits namespace) |
| `PERMISSIVE` | Accept both plaintext and mTLS. **Mesh default** |
| `STRICT` | Accept **only** mTLS. Plaintext dropped |
| `DISABLE` | Accept only plaintext. mTLS clients fail |

`PERMISSIVE` is why "I turned on Istio" does not by itself prove mTLS. Traffic still works from non-meshed clients. **STRICT** is the exam's "enforce mTLS" answer.

### Scope

```text
Mesh-wide     PeerAuthentication default in root namespace (istio-system)
Namespace     PeerAuthentication in that namespace, no selector
Workload      spec.selector.matchLabels
Port          spec.portLevelMtls.<port>.mode
```

More specific wins for the selected workload/port. A workload STRICT port can coexist with PERMISSIVE on other ports.

```yaml
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: httpbin
  namespace: demo
spec:
  selector:
    matchLabels:
      app: httpbin
  mtls:
    mode: STRICT
  portLevelMtls:
    8080:
      mode: DISABLE
```

`portLevelMtls` keys are **container ports**, the pod port, not the Service port if they differ. Confirm with `kubectl get pod -o yaml`.

### Auto mTLS (clients)

For destinations **inside** the mesh, Istio auto-sets client TLS to `ISTIO_MUTUAL` when the destination has a sidecar/ztunnel. You rarely need a DestinationRule for ordinary east-west mTLS.

You **do** need a DestinationRule when:

- Dest is outside the mesh (`DISABLE` or `SIMPLE`).
- You must force `ISTIO_MUTUAL` explicitly.
- You use an egress gateway hop.

### Ambient

Ambient ztunnel provides L4 mTLS as soon as the namespace is enrolled. PeerAuthentication still applies. STRICT in ambient rejects plaintext to those workloads.

## Tasks

`demo` is meshed. `nomesh` has a sleep **without** a sidecar (`Lab-Setup.md`).

1. Mesh-wide stay PERMISSIVE. Set namespace `demo` to **STRICT**.
2. Show `nomesh/sleep` can no longer `curl httpbin.demo:8000`, while `demo/sleep` still can.
3. Make **only** `httpbin` STRICT; rest of `demo` PERMISSIVE.
4. Disable mTLS on `httpbin` port **8000** only, keep STRICT on other ports.
5. Restore the default (delete the policies) and confirm nomesh works again.

## Solutions

### 1. Namespace STRICT

```bash
kubectl apply -f - <<'EOF'
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: demo
spec:
  mtls:
    mode: STRICT
EOF
```

### 2. Cross-mesh test

```bash
# Meshed client: success
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "mesh %{http_code}\n" http://httpbin:8000/get

# Unmeshed client: fail under STRICT
kubectl -n nomesh exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "nomesh %{http_code}\n" --max-time 5 http://httpbin.demo:8000/get || true
```

### 3. Workload selector

Delete the namespace policy first or it still applies to everything in `demo`.

```yaml
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: httpbin
  namespace: demo
spec:
  selector:
    matchLabels:
      app: httpbin
  mtls:
    mode: STRICT
```

### 4. Port exception

```yaml
spec:
  selector:
    matchLabels:
      app: httpbin
  mtls:
    mode: STRICT
  portLevelMtls:
    8000:
      mode: DISABLE
```

If httpbin's container port is 80 and Service maps 8000->80, the key is **80**, not 8000. Check:

```bash
kubectl -n demo get pod -l app=httpbin -o jsonpath='{.items[0].spec.containers[*].ports}' ; echo
```

### 5. Cleanup

```bash
kubectl -n demo delete peerauthentication --all
```

## Verify

```bash
kubectl get peerauthentication -A
istioctl x describe pod -n demo $(kubectl -n demo get pod -l app=httpbin -o jsonpath='{.items[0].metadata.name}')

# Client cluster TLS
istioctl proxy-config cluster deploy/sleep.demo --fqdn httpbin.demo.svc.cluster.local -o json \
  | jq '.[0].transportSocket.name // .[0].transportSocketMatches'
```

Kiali or `istioctl experimental authz check` can also show mTLS. Access logs with `upstream_cluster` and TLS handshake failures on STRICT+plaintext.

## Exam Tips

- **PERMISSIVE is the default.** A task that says "require mTLS" wants `STRICT`, not a DestinationRule alone.
- PeerAuthentication does not encrypt outbound to **external** sites. That is DestinationRule `SIMPLE` / egress TLS origination.
- `security.istio.io/v1` is current; older answers use `v1beta1`. Both work; prefer `v1`.
- Docs: [Mutual TLS migration](https://istio.io/docs/tasks/security/authentication/mtls-migration/) and PeerAuthentication reference.
