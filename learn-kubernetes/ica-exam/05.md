# 05. Ambient Mode, ztunnel, and Waypoints

## Concept Refresher

Ambient mode removes the per-pod sidecar. It reached GA in Istio 1.24 and is explicitly named in the ICA objectives, so expect at least one task on it.

The design splits the data plane into two independent layers, and **the layers are opt-in separately**. That separation is the single most important thing to understand.

```text
                    Ambient data plane
    +-----------------------------------------------+
    |  L4 layer: ztunnel                            |
    |  - one DaemonSet, one pod per node            |
    |  - mTLS, L4 authorization, TCP telemetry      |
    |  - enabled by labelling a namespace or pod    |
    +-----------------------------------------------+
    |  L7 layer: waypoint proxy  (OPTIONAL)         |
    |  - a Deployment, per namespace or per service |
    |  - HTTP routing, retries, timeouts,           |
    |    L7 authorization, fault injection          |
    |  - enabled by creating a waypoint Gateway     |
    +-----------------------------------------------+
```

**Enrol a namespace in ambient and you get mTLS and L4 policy. You get no L7 features at all until you add a waypoint.** This is the defining ambient gotcha: you apply a VirtualService with a timeout, nothing happens, and there is no error message. The VirtualService is valid, it is accepted, and there is simply no L7 proxy in the path to enforce it.

### Sidecar versus ambient

| | Sidecar | Ambient |
| --- | --- | --- |
| Proxy placement | One Envoy per pod | ztunnel per node, waypoint per namespace/service |
| Pod restart to enrol | **Yes** | **No** |
| Resource overhead | Per pod | Shared per node |
| L4 mTLS | Yes | Yes (ztunnel) |
| L7 features | Yes, always | Only with a waypoint |
| Transport | mTLS | **HBONE** (HTTP/2 CONNECT over mTLS, port 15008) |
| Requires CNI | Optional | **Mandatory** |
| `istioctl proxy-config` | Works | Use `istioctl ztunnel-config` for ztunnel |

The "no pod restart" difference is the practical headline: labelling a namespace for ambient meshes the running pods immediately, which is the opposite of sidecar mode and a very likely exam contrast question.

### HBONE

Ambient tunnels traffic inside **HBONE**: an HTTP/2 `CONNECT` stream over mTLS, on port **15008**. It preserves the original destination and the source identity while carrying arbitrary TCP. When you see port 15008 in output or in a NetworkPolicy question, that is ambient's transport.

### Waypoints

A waypoint is an Envoy deployment created through the **Kubernetes Gateway API**, with `gatewayClassName: istio-waypoint`. Which traffic it handles is controlled by labels.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: waypoint
  namespace: shop
  labels:
    istio.io/waypoint-for: service     # service | workload | all | none
spec:
  gatewayClassName: istio-waypoint
  listeners:
    - name: mesh
      port: 15008
      protocol: HBONE
```

The listener must be named `mesh` on port `15008` with protocol `HBONE`. `istioctl waypoint` generates this for you and is far faster under time pressure.

| `istio.io/waypoint-for` | Intercepts |
| --- | --- |
| `service` (default) | Traffic addressed to Services |
| `workload` | Traffic addressed directly to pod IPs |
| `all` | Both |
| `none` | Nothing, used to disable |

Attaching a waypoint to things:

```bash
# whole namespace
kubectl label namespace shop istio.io/use-waypoint=waypoint

# one service
kubectl -n shop label service httpbin istio.io/use-waypoint=waypoint

# one workload
kubectl -n shop label deployment httpbin istio.io/use-waypoint=waypoint
```

More specific beats less specific: a service label overrides the namespace label.

### The labels that matter

| Label | On | Meaning |
| --- | --- | --- |
| `istio.io/dataplane-mode=ambient` | Namespace or Pod | Enrol in ambient (ztunnel, L4) |
| `istio.io/dataplane-mode=none` | Pod | Opt this pod out of ambient |
| `istio.io/use-waypoint=<name>` | Namespace, Service, or Pod | Route L7 through that waypoint |
| `istio.io/use-waypoint-namespace=<ns>` | Namespace/Service | Waypoint lives in another namespace |
| `istio.io/waypoint-for=<scope>` | The waypoint Gateway | What the waypoint captures |
| `istio.io/ingress-use-waypoint=true` | Service | Send ingress-gateway traffic via the waypoint too |

## Tasks

Use a separate cluster for this. `Lab-Setup.md` has an `ambient-lab` recipe.

1. Install Istio in ambient mode and verify both the CNI and ztunnel are running.
2. Create namespace `shop`, deploy `httpbin` and `sleep`, and enrol the namespace in ambient **without restarting any pods**. Prove the pods have no sidecar.
3. Prove that traffic between `sleep` and `httpbin` is now mTLS-encrypted.
4. Apply an L4 `AuthorizationPolicy` that allows only `sleep` to reach `httpbin`, and verify a third workload is denied.
5. Apply a VirtualService that adds a 5 second delay to `httpbin`. Observe that it has no effect, and explain why.
6. Deploy a waypoint for the `shop` namespace and make the previous VirtualService take effect.
7. Scope a waypoint to a single service instead of the whole namespace.
8. Apply an L7 `AuthorizationPolicy` that only permits `GET` to `/get`, and verify `POST` is denied.
9. Inspect ztunnel's view of workloads and certificates.
10. Opt a single pod out of ambient while leaving the namespace enrolled.
11. Run an ambient namespace and a sidecar namespace in the same cluster, and get traffic flowing between them.
12. A waypoint exists but L7 policy is not applying. Diagnose it.

## Solutions

### 1. Install ambient

```bash
# Gateway API CRDs are required for waypoints
kubectl get crd gateways.gateway.networking.k8s.io >/dev/null 2>&1 || \
  kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.2.1/standard-install.yaml

istioctl install --set profile=ambient --skip-confirmation
```

Verify all four pieces:

```bash
kubectl -n istio-system get pods
```

```text
NAME                                   READY   STATUS
istio-cni-node-4x8kp                   1/1     Running
istio-cni-node-9mv2t                   1/1     Running
istiod-6b7c8d9f5-lm3np                 1/1     Running
ztunnel-7k2pl                          1/1     Running
ztunnel-x9nfm                          1/1     Running
```

```bash
kubectl -n istio-system get daemonset
```

```text
NAME             DESIRED   CURRENT   READY
istio-cni-node   2         2         2
ztunnel          2         2         2
```

Two DaemonSets, one pod each per node. `istio-cni-node` sets up the traffic redirection; `ztunnel` is the L4 proxy. **Both are mandatory for ambient.** If `istio-cni-node` is missing, nothing is redirected and ambient silently does nothing.

The Helm equivalent:

```bash
helm install istio-base istio/base -n istio-system --create-namespace --version 1.26.0 --wait
helm install istiod istio/istiod -n istio-system --set profile=ambient --version 1.26.0 --wait
helm install istio-cni istio/cni -n istio-system --set profile=ambient --version 1.26.0 --wait
helm install ztunnel istio/ztunnel -n istio-system --version 1.26.0 --wait
```

Note the order: `cni` before `ztunnel`.

### 2. Enrol a namespace with no restart

```bash
kubectl create namespace shop
kubectl -n shop apply -f ~/istio-1.26.0/samples/httpbin/httpbin.yaml
kubectl -n shop apply -f ~/istio-1.26.0/samples/sleep/sleep.yaml
kubectl -n shop wait --for=condition=ready pod --all --timeout=120s

# Note the pod names and ages now
kubectl -n shop get pods
```

Enrol:

```bash
kubectl label namespace shop istio.io/dataplane-mode=ambient
```

```bash
kubectl -n shop get pods
```

```text
NAME                      READY   STATUS    RESTARTS   AGE
httpbin-8b9c5d6f7-k2nml   1/1     Running   0          2m
sleep-9f8d7c6b5-x3mlp     1/1     Running   0          2m
```

**Same pod names, same ages, still `1/1`.** Nothing restarted, and there is no sidecar. This is the headline ambient behaviour.

Confirm they are genuinely in the mesh, using the ztunnel view rather than pod inspection:

```bash
istioctl ztunnel-config workload --namespace shop
```

```text
NAMESPACE  POD NAME                  ADDRESS      NODE              WAYPOINT  PROTOCOL
shop       httpbin-8b9c5d6f7-k2nml   10.244.1.8   ambient-worker    None      HBONE
shop       sleep-9f8d7c6b5-x3mlp     10.244.2.5   ambient-worker2   None      HBONE
```

`PROTOCOL: HBONE` means enrolled. A workload showing `TCP` is not in the mesh. `WAYPOINT: None` confirms there is no L7 layer yet, which sets up task 5.

Traffic still works:

```bash
kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{http_code}\n" http://httpbin:8000/get
```

### 3. Prove mTLS

Read ztunnel's own logs, which record the identity on both ends:

```bash
ZPOD=$(kubectl -n istio-system get pod -l app=ztunnel \
  -o jsonpath='{.items[0].metadata.name}')

kubectl -n istio-system logs "$ZPOD" --tail=0 -f &

kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null http://httpbin:8000/get

# then stop the follow
kill %1
```

```text
INFO access connection complete src.addr=10.244.2.5:41234
  src.workload="sleep" src.namespace="shop"
  src.identity="spiffe://cluster.local/ns/shop/sa/sleep"
  dst.addr=10.244.1.8:15008
  dst.workload="httpbin" dst.namespace="shop"
  dst.identity="spiffe://cluster.local/ns/shop/sa/httpbin"
  protocol=HBONE ...
```

Two things prove encryption: `dst.addr` is port **15008** (the HBONE port, not the app's 8000), and both `src.identity` and `dst.identity` are populated SPIFFE URIs, which only happens after a successful mTLS handshake.

Check the certificates ztunnel holds:

```bash
istioctl ztunnel-config certificate --namespace shop
```

```text
CERTIFICATE NAME                                  TYPE     STATUS  VALID CERT  SERIAL  NOT AFTER
spiffe://cluster.local/ns/shop/sa/httpbin         Leaf     Available  true     abc123  2026-08-20T...
spiffe://cluster.local/ns/shop/sa/httpbin         Root     Available  true     def456  2036-08-17T...
spiffe://cluster.local/ns/shop/sa/sleep           Leaf     Available  true     ghi789  2026-08-20T...
```

ztunnel holds a leaf certificate **per identity on its node**, not one shared cert. That is how a shared node proxy can still assert per-workload identity, and it is a good conceptual question.

An out-of-mesh caller confirms the mesh boundary:

```bash
kubectl create namespace outside
kubectl -n outside apply -f ~/istio-1.26.0/samples/sleep/sleep.yaml
kubectl -n outside wait --for=condition=ready pod --all --timeout=120s

kubectl -n outside exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{http_code}\n" http://httpbin.shop:8000/get
# 200 - allowed, but plaintext, because no policy requires mTLS yet
```

### 4. L4 authorization

```bash
kubectl apply -f - <<'EOF'
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: httpbin-l4
  namespace: shop
spec:
  selector:
    matchLabels:
      app: httpbin
  action: ALLOW
  rules:
    - from:
        - source:
            principals:
              - cluster.local/ns/shop/sa/sleep
EOF
```

Verify allowed and denied:

```bash
# In-mesh sleep, has the right identity
kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "in-mesh sleep: %{http_code}\n" http://httpbin:8000/get
# 200

# Out-of-mesh caller, no identity
kubectl -n outside exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "outside: %{http_code}\n" --max-time 5 http://httpbin.shop:8000/get
# connection reset / empty reply
```

The denial mode is the interesting part. **ztunnel enforces at L4, so it closes the TCP connection.** You get a reset or an empty reply, not an HTTP `403`. In sidecar mode, or in ambient with a waypoint, an L7 denial returns `403 RBAC: access denied`.

That difference is a strong exam discriminator:

| Enforcement point | Denial looks like |
| --- | --- |
| ztunnel (L4, ambient, no waypoint) | TCP reset, connection refused, empty reply |
| Waypoint or sidecar (L7) | HTTP `403` with body `RBAC: access denied` |

Confirm ztunnel received the policy:

```bash
istioctl ztunnel-config policy --namespace shop
```

Clean up before the next task:

```bash
kubectl -n shop delete authorizationpolicy httpbin-l4
```

### 5. An L7 rule that does nothing

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin-delay
  namespace: shop
spec:
  hosts:
    - httpbin
  http:
    - fault:
        delay:
          percentage:
            value: 100
          fixedDelay: 5s
      route:
        - destination:
            host: httpbin
EOF
```

```bash
kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "time: %{time_total}s  code: %{http_code}\n" http://httpbin:8000/get
```

```text
time: 0.008s  code: 200
```

**No delay.** The resource was accepted, `kubectl get virtualservice` shows it, and `istioctl analyze` reports no error. It simply has no effect.

Why: fault injection is an L7 feature. In ambient mode without a waypoint, the only proxy in the path is ztunnel, which operates at L4. It moves bytes over HBONE and enforces L4 policy; it does not parse HTTP, so it cannot delay a request, retry it, or route on a header.

Confirm the absence of an L7 hop:

```bash
istioctl ztunnel-config workload --namespace shop
# WAYPOINT column says None
```

This is the ambient trap. Whenever an L7 configuration in ambient mode "does nothing", the answer is almost always a missing waypoint.

### 6. Add a waypoint

The fast way:

```bash
istioctl waypoint apply -n shop --enroll-namespace --wait
```

That does two things: creates the waypoint `Gateway`, and labels the namespace with `istio.io/use-waypoint`. Verify both:

```bash
istioctl waypoint list -n shop
kubectl -n shop get gateway
kubectl -n shop get pods
kubectl get ns shop --show-labels
```

```text
NAME       CLASS            ADDRESS        PROGRAMMED
waypoint   istio-waypoint   10.96.12.34    True
```

```text
NAME                        READY   STATUS
httpbin-8b9c5d6f7-k2nml     1/1     Running
sleep-9f8d7c6b5-x3mlp       1/1     Running
waypoint-6f7d8c9b5-mn2pl    1/1     Running
```

The waypoint is a separate pod, shared by the namespace. The application pods are untouched and still `1/1`.

Now the same VirtualService works:

```bash
kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "time: %{time_total}s  code: %{http_code}\n" http://httpbin:8000/get
```

```text
time: 5.012s  code: 200
```

Nothing about the VirtualService changed. Adding the L7 proxy is what made it real.

Confirm the routing path now includes the waypoint:

```bash
istioctl ztunnel-config workload --namespace shop
```

```text
NAMESPACE  POD NAME                 ADDRESS      WAYPOINT   PROTOCOL
shop       httpbin-8b9c5d6f7-k2nml  10.244.1.8   waypoint   HBONE
```

The declarative form, for a task that wants YAML:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: waypoint
  namespace: shop
  labels:
    istio.io/waypoint-for: service
spec:
  gatewayClassName: istio-waypoint
  listeners:
    - name: mesh
      port: 15008
      protocol: HBONE
```

```bash
kubectl apply -f waypoint.yaml
kubectl label namespace shop istio.io/use-waypoint=waypoint
```

The waypoint is a real Envoy, so the familiar tooling works on it:

```bash
istioctl proxy-config route deploy/waypoint.shop
istioctl proxy-config cluster deploy/waypoint.shop
istioctl proxy-status | grep waypoint
```

### 7. Scope a waypoint to one service

Remove the namespace-wide attachment and attach per service:

```bash
kubectl label namespace shop istio.io/use-waypoint-
kubectl -n shop label service httpbin istio.io/use-waypoint=waypoint
```

```bash
istioctl ztunnel-config workload --namespace shop
```

Now `httpbin` routes through the waypoint and `sleep` does not. Verify:

```bash
# httpbin as a destination gets L7 treatment (the 5s delay applies)
kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{time_total}s\n" http://httpbin:8000/get
# ~5s
```

Per-service scoping is the recommended production pattern: only pay for L7 processing where you need L7 features.

A dedicated waypoint for one service:

```bash
istioctl waypoint apply -n shop --name httpbin-waypoint
kubectl -n shop label service httpbin istio.io/use-waypoint=httpbin-waypoint --overwrite
```

A waypoint in a different namespace:

```bash
kubectl -n shop label service httpbin \
  istio.io/use-waypoint=shared-waypoint \
  istio.io/use-waypoint-namespace=infra --overwrite
```

### 8. L7 authorization through the waypoint

Restore the namespace waypoint first:

```bash
kubectl -n shop delete virtualservice httpbin-delay
kubectl label namespace shop istio.io/use-waypoint=waypoint --overwrite
```

```bash
kubectl apply -f - <<'EOF'
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: httpbin-l7
  namespace: shop
spec:
  targetRefs:
    - kind: Service
      group: ""
      name: httpbin
  action: ALLOW
  rules:
    - from:
        - source:
            principals:
              - cluster.local/ns/shop/sa/sleep
      to:
        - operation:
            methods: ["GET"]
            paths: ["/get"]
EOF
```

Verify:

```bash
kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "GET /get:  %{http_code}\n" http://httpbin:8000/get
# 200

kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "POST /post: %{http_code}\n" -X POST http://httpbin:8000/post
# 403

kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -w "\nGET /headers: %{http_code}\n" http://httpbin:8000/headers
# RBAC: access denied
# 403
```

Now the denial is a proper HTTP `403` with `RBAC: access denied`, because a waypoint is enforcing it at L7. Compare that against the TCP reset from task 4.

Note `targetRefs` rather than `selector`. For waypoint-enforced policy, **`targetRefs` pointing at the Service is the correct attachment**, because the waypoint is service-scoped. Using `selector` targets the workload, which is the pattern for sidecars and for ztunnel L4 policy. Getting this wrong produces a policy that exists and does nothing.

| Attachment | Use for |
| --- | --- |
| `selector` | Sidecars, ztunnel L4 policy |
| `targetRefs` with `kind: Service` | Waypoint L7 policy |
| `targetRefs` with `kind: Gateway` | Policy on a gateway |

Confirm the waypoint received it:

```bash
istioctl proxy-config all deploy/waypoint.shop -o json | jq '.. | .rbac? // empty' | head -40
istioctl proxy-config log deploy/waypoint.shop --level rbac:debug
kubectl -n shop logs deploy/waypoint --tail=20
```

### 9. Inspect ztunnel

```bash
# Workloads ztunnel knows about
istioctl ztunnel-config workload
istioctl ztunnel-config workload --namespace shop -o json

# Services
istioctl ztunnel-config service

# Certificates per identity
istioctl ztunnel-config certificate

# Policies pushed to ztunnel
istioctl ztunnel-config policy

# ztunnel's own logs
istioctl ztunnel-config log
istioctl ztunnel-config log --level debug

# Everything
istioctl ztunnel-config all -o json > /tmp/ztunnel.json
```

Raw ztunnel logs, which are the primary L4 debugging tool in ambient:

```bash
kubectl -n istio-system logs -l app=ztunnel --tail=50
kubectl -n istio-system logs -l app=ztunnel -f | grep -i shop
```

To target the ztunnel on the same node as a specific pod:

```bash
NODE=$(kubectl -n shop get pod -l app=httpbin -o jsonpath='{.items[0].spec.nodeName}')
kubectl -n istio-system get pod -l app=ztunnel \
  -o jsonpath="{range .items[?(@.spec.nodeName=='$NODE')]}{.metadata.name}{'\n'}{end}"
```

That matters because ztunnel is per node: the logs for a given connection are on the source pod's node.

### 10. Opt one pod out of ambient

```bash
kubectl -n shop patch deployment sleep -p '{
  "spec":{"template":{"metadata":{"labels":{
    "istio.io/dataplane-mode":"none"
  }}}}}'
kubectl -n shop rollout status deployment sleep
```

```bash
istioctl ztunnel-config workload --namespace shop
```

The `sleep` pod now shows `PROTOCOL: TCP` instead of `HBONE`, meaning it is out of the mesh. Note that although enrolling needs no restart, changing a **pod label** does require the pod to be recreated, because labels are part of the pod template.

Verify the consequence:

```bash
kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{http_code}\n" http://httpbin:8000/get
```

It still gets a `200` unless a policy requires mTLS, but the traffic is now plaintext from the client side and has no identity. Reapply the L4 policy from task 4 and it will be denied.

Undo:

```bash
kubectl -n shop patch deployment sleep --type json \
  -p '[{"op":"remove","path":"/spec/template/metadata/labels/istio.io~1dataplane-mode"}]'
```

Note `~1` is the JSON Pointer escape for `/` in a key name. Worth knowing for any label containing a slash.

### 11. Ambient and sidecar together

```bash
kubectl create namespace legacy
kubectl label namespace legacy istio-injection=enabled
kubectl -n legacy apply -f ~/istio-1.26.0/samples/sleep/sleep.yaml
kubectl -n legacy wait --for=condition=ready pod --all --timeout=120s

kubectl -n legacy get pods   # 2/2, sidecar
kubectl -n shop   get pods   # 1/1, ambient
```

Traffic in both directions:

```bash
# sidecar -> ambient
kubectl -n legacy exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "sidecar->ambient: %{http_code}\n" http://httpbin.shop:8000/get

# ambient -> sidecar (needs a service in legacy; add httpbin there)
kubectl -n legacy apply -f ~/istio-1.26.0/samples/httpbin/httpbin.yaml
kubectl -n legacy wait --for=condition=ready pod -l app=httpbin --timeout=120s
kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "ambient->sidecar: %{http_code}\n" http://httpbin.legacy:8000/get
```

Both work, and both are mTLS. Sidecars and ztunnel share the same identity system and the same root CA, and sidecars understand HBONE, so interoperation is transparent. That is a deliberate design goal, because it is what makes incremental migration possible.

The migration path an exam might ask you to describe:

```bash
# 1. Ensure the CNI and ztunnel are installed
# 2. Remove the sidecar label, add the ambient label
kubectl label namespace legacy istio-injection- --overwrite
kubectl label namespace legacy istio.io/dataplane-mode=ambient --overwrite
# 3. Restart to shed the now-unwanted sidecars
kubectl -n legacy rollout restart deployment
# 4. Add a waypoint if any L7 config existed
istioctl waypoint apply -n legacy --enroll-namespace --wait
```

Step 4 is the one that gets forgotten, and it is where all the existing VirtualService behaviour silently disappears.

### 12. Waypoint exists but L7 policy is not applying

Walk this list.

```bash
# 1. Is the waypoint running and programmed?
istioctl waypoint list -n shop
kubectl -n shop get gateway waypoint -o jsonpath='{.status.conditions}' | jq
kubectl -n shop get pods -l gateway.networking.k8s.io/gateway-name=waypoint
```

`PROGRAMMED: True` is required. `False` usually means the Gateway API CRDs are missing or the `gatewayClassName` is wrong.

```bash
# 2. Is anything actually pointed at it?
kubectl get ns shop --show-labels | grep use-waypoint
kubectl -n shop get svc httpbin --show-labels
kubectl -n shop get svc -o custom-columns='NAME:.metadata.name,WAYPOINT:.metadata.labels.istio\.io/use-waypoint'
```

A waypoint with nothing labelled to use it is inert. This is the most common cause.

```bash
# 3. Does ztunnel agree that traffic should go via the waypoint?
istioctl ztunnel-config workload --namespace shop
# the WAYPOINT column must name your waypoint, not None
```

```bash
# 4. Is the namespace actually in ambient at all?
kubectl get ns shop --show-labels | grep dataplane-mode
```

A waypoint without ambient enrolment does nothing, because ztunnel is what redirects traffic to it.

```bash
# 5. Is the waypoint scope right for the traffic?
kubectl -n shop get gateway waypoint -o jsonpath='{.metadata.labels}' | jq
# istio.io/waypoint-for=service will not capture direct pod-IP traffic
```

```bash
# 6. Does the policy use the right attachment?
kubectl -n shop get authorizationpolicy httpbin-l7 -o yaml | grep -A5 -E 'targetRefs|selector'
```

For waypoint enforcement it must be `targetRefs` to the Service. A `selector` here is the classic silent failure.

```bash
# 7. What config does the waypoint actually have?
istioctl proxy-config route deploy/waypoint.shop
istioctl proxy-config listener deploy/waypoint.shop
istioctl proxy-status | grep waypoint
```

```bash
# 8. The catch-all
istioctl analyze -n shop
kubectl -n shop logs deploy/waypoint --tail=50
```

```bash
# Ambient infrastructure
kubectl -n istio-system get daemonset ztunnel istio-cni-node

# Namespace enrolment
kubectl get ns -L istio.io/dataplane-mode -L istio.io/use-waypoint

# Workloads seen by ztunnel, with waypoint assignment
istioctl ztunnel-config workload

# Waypoints
istioctl waypoint list -A

# No sidecars where you expect none
kubectl -n shop get pods   # 1/1

# Traffic works
kubectl -n shop exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{http_code}\n" http://httpbin:8000/get

istioctl analyze -A
```

## Exam Tips

**Ambient gives you L4 for free and L7 never, until you add a waypoint.** If any task involves an HTTP-level feature (routing on headers, timeouts, retries, fault injection, L7 authorization, HTTP telemetry) in an ambient namespace, a waypoint is part of the answer. This is the single highest-value fact in this file.

**`istioctl waypoint apply -n <ns> --enroll-namespace --wait` is the fast path.** It creates the Gateway and applies the `use-waypoint` label in one command. Writing the Gateway YAML by hand is correct but slower, and the listener block (`name: mesh`, `port: 15008`, `protocol: HBONE`) is easy to get wrong from memory.

**Ambient needs no pod restart to enrol; sidecar mode always does.** Expect to be asked to contrast them. The reason is that ambient redirection happens at the node via the CNI, so it applies to running pods immediately.

**Changing a pod label still needs a restart.** Enrolling a namespace does not, but opting an individual pod out via `istio.io/dataplane-mode=none` modifies the pod template, so the pod is recreated. Do not state "ambient never needs restarts" without that qualifier.

**L4 denials look like TCP resets; L7 denials look like HTTP 403.** If a task shows a connection reset and asks where the policy is enforced, the answer is ztunnel. If it shows `RBAC: access denied`, a waypoint or sidecar is enforcing.

**Waypoint policy attaches with `targetRefs`, not `selector`.** `targetRefs` to `kind: Service` for a waypoint. `selector` for sidecars and ztunnel. Wrong choice means the policy exists, validates, and does nothing.

**`istioctl ztunnel-config workload` is the ambient equivalent of `istioctl proxy-status`.** The `PROTOCOL` column tells you whether a workload is enrolled (`HBONE`) or not (`TCP`), and the `WAYPOINT` column tells you whether L7 is in the path. Two questions answered by one command.

**Port 15008 is HBONE.** If a NetworkPolicy or firewall question involves ambient, 15008 must be open between nodes.

**The CNI is not optional in ambient.** `istio-cni-node` missing means no redirection at all, and the symptom is that everything looks installed but no workload is ever enrolled.

**Waypoints are ordinary Envoys.** `istioctl proxy-config route deploy/waypoint.<ns>` works on them, as does `proxy-config log --level rbac:debug`. Do not forget your sidecar debugging toolkit just because the mode changed.
