# Istio Certified Associate (ICA) Practice

This folder mirrors the flat `learn-kubernetes/exam` (CKA), `learn-kubernetes/cks-exam` (CKS), and `learn-kubernetes/pca-exam` (PCA) layout, but targets the ICA exam.

Outline checked against the Linux Foundation ICA certification page and the ICA Program Changes page on 2026-08-19. The curriculum below is the **post-August 12, 2025** version. If you find older study material listing "Resilience and Fault Injection" or "Advanced Scenarios" as separate domains, it is out of date.

## Exam Facts

### How ICA compares to the other exams in this repo

| | CKA / CKS | PCA | **ICA** |
| --- | --- | --- | --- |
| Format | Hands-on | Multiple choice | **Hands-on** |
| Duration | 2 hours | 90 min | **2 hours** |
| Passing | 66% / 67% | 75% | **68%** |
| Docs | Yes | No, closed book | **Yes** |
| Questions | 15-20 | 60 | **15-20** |

ICA is the closest sibling to **CKA**, not PCA. If you have already done CKA, the exam mechanics will feel familiar: a live terminal, a task list, cluster context switching, and partial credit per task.

**The old ICA mixed a few multiple-choice items and used a 75% cut score. That mix is gone.** Current important instructions describe **15–20 performance-based tasks**, 120 minutes, passing score **68%**. Some catalog pages still say "performance-based and multiple-choice"; trust the [ICA important instructions](https://docs.linuxfoundation.org/tc-docs/certification/important-instructions-ica) and [FAQ](https://docs.linuxfoundation.org/tc-docs/certification/frequently-asked-questions-ica) on exam day.

**Exam desktop:** SSH from hostname `base` to a per-task host. Nested SSH is not supported. Preinstalled: `kubectl` (`k`), `istioctl`, `yq`, `curl`, `wget`, bash completion. Do not reboot `base`.

- Configuring Ingress and Egress Traffic
- Configuring Routing within a Service Mesh
- Defining Traffic Policies with Destination Rules

- Using Fault Injection

**Securing Workloads (25%)**

- Configuring Authorization

- Securing Edge Traffic with TLS

**Troubleshooting (20%)**

- Troubleshooting Configuration
- Troubleshooting the Mesh Control Plane
- Troubleshooting the Mesh Data Plane

## How Each Numbered File Is Structured

- **Concept refresher** - the mental model, kept short.
- **Tasks** - exam-style, terse, no hand-holding. Try these before reading on.
- **Solutions** - the YAML and commands, with the reasoning.
- **Verify** - how to prove it works, because the grader only sees the result.
- **Exam tips** - the traps and the speed tricks.

Attempt the tasks first. Reading Istio YAML is not the same as writing it under a clock.

## Universal ICA Reasoning Flow

When a task looks unfamiliar, walk this order.

```text
1. Is the traffic north-south (entering/leaving) or east-west (service to service)?
   north-south in  -> Gateway + VirtualService (or Gateway API Gateway + HTTPRoute)
   north-south out -> ServiceEntry, maybe egress Gateway
   east-west       -> VirtualService + DestinationRule, no Gateway resource

2. Which resource owns the behaviour I need?
   WHERE does traffic go        -> VirtualService (routes, match, weight, mirror,
                                   timeout, retries, fault injection, rewrite, redirect)
   HOW do we talk to it         -> DestinationRule (subsets, load balancing, TLS,
                                   connection pool, outlier detection)
   WHAT exists outside the mesh -> ServiceEntry
   WHO may call it              -> AuthorizationPolicy
   HOW do we prove identity     -> PeerAuthentication (mTLS) / RequestAuthentication (JWT)
   WHAT config reaches a proxy  -> Sidecar

3. Did I bind the VirtualService correctly?
   mesh-internal  -> no gateways field (defaults to "mesh")
   through ingress-> gateways: [<gateway-name>] and hosts must match the Gateway hosts
   both           -> gateways: [mesh, <gateway-name>]

4. Do subsets exist?
   VirtualService referencing subset "v1" with NO DestinationRule defining it
   = 503 NR / no healthy upstream. This is the single most common self-inflicted failure.

5. Verify like the grader would.
   istioctl analyze
   istioctl proxy-config route/cluster/endpoint
   actual curl through the real path
```

## The Ten Istio Truths To Remember

- **Envoy does the work.** istiod only computes and pushes config over xDS. If traffic behaves oddly, ask what config Envoy actually has, not what YAML you wrote.
- **VirtualService decides where. DestinationRule decides how.** Almost every "which resource?" question resolves with this sentence.
- **A `subset` is only real if a DestinationRule defines it.** Referencing an undefined subset produces `503`, not a validation error.
- **Route rules are evaluated in order, first match wins.** Put specific matches above catch-alls. An unconditional route at the top makes everything below it dead code.
- **`hosts` in a VirtualService must match the Gateway's `hosts`** for gateway-bound traffic, or the route never attaches.
- **mTLS is `PERMISSIVE` by default**, which is why "I enabled mTLS" often changes nothing observable until you set `STRICT`.
- **AuthorizationPolicy is deny-by-default only once a policy selects the workload.** No policy means allow all. An `ALLOW` policy on a workload denies everything not explicitly allowed.
- **`RequestAuthentication` does not authorize.** It only validates tokens. Without an `AuthorizationPolicy`, a request with no token at all still passes.
- **Ambient has no sidecar.** L4 is ztunnel; L7 needs a waypoint. If an L7 policy does nothing in ambient mode, you are probably missing the waypoint.
- **Always `istioctl analyze` before you call a task done.** It catches missing subsets, bad host references, and conflicting policies in one shot.

## Time Strategy For 120 Minutes

| Phase | Minutes | What |
| --- | ---: | --- |
| Setup | 2 | Aliases, completion, survey the cluster |
| First pass | 85 | Do every task you recognise immediately. Flag the rest |
| Second pass | 25 | The flagged ones, using docs |
| Final sweep | 8 | Re-verify every answer, run `istioctl analyze -A` |

At roughly **6-7 minutes per task**, anything that has eaten 10 minutes is a trap. Flag it and move. Partial credit is real, so a half-finished task beats an untouched one.

One habit that pays for itself: **check the namespace and cluster context in every single task.** ICA tasks, like CKA tasks, name a specific namespace, and applying perfect YAML to the wrong namespace scores zero.
