# 12. Traffic Shifting and Weighted Canary Release

## Concept Refresher

Traffic shifting is how Istio does canaries and A/B tests: send a percentage of requests to a new subset, keep the rest on the stable subset, then move the weights until the new version owns 100%.

The resource is still a VirtualService. The only new field is `weight` on each `route` destination. Subsets must already exist in a DestinationRule, or you get `503 NR`.

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
  namespace: bookinfo
spec:
  hosts:
    - reviews
  http:
    - route:
        - destination:
            host: reviews
            subset: v1
          weight: 90
        - destination:
            host: reviews
            subset: v2
          weight: 10
```

### Rules that bite

- Weights are **relative**. `90` and `10` is 90/10. `9` and `1` is the same split. They do not have to sum to 100, but summing to 100 is the exam convention and the grader-friendly choice.
- A single destination with no `weight` is 100%. Adding a second destination without weights is invalid; Envoy needs the split.
- Header-based routing and weighted routing are different jobs. Header routing is *who* gets the new version. Weights are *how many* get it. Combine them: match `end-user: jason` to v2 at 100%, everyone else 90/10.
- The split happens at the **source proxy**. Clients of `reviews` (productpage, sleep, the ingress gateway) enforce it. The reviews pods themselves do not.
- Changing weights is a live config push. No pod restart. `istioctl proxy-status` should stay `SYNCED`.

### Canary vs A/B vs blue/green in Istio terms

| Pattern | How you do it |
| --- | --- |
| Canary | Weighted split, slowly raise the new subset |
| A/B | Match on a header/cookie/query to pin a user to a subset |
| Blue/green | Two subsets, flip weight from 100/0 to 0/100 in one apply |

## Tasks

Assume Bookinfo is running in `bookinfo` with DestinationRules that define `reviews` subsets `v1`, `v2`, `v3` (`samples/bookinfo/networking/destination-rule-all.yaml`).

1. Send **all** reviews traffic to `v1`.
2. Shift **20%** of reviews traffic to `v2`, keep **80%** on `v1`.
3. Pin user `jason` (header `end-user: jason`) to `v2`, everyone else stays 80/20 on v1/v2.
4. Finish the canary: send **100%** to `v2`.
5. Shift `ratings` 50/50 between `v1` and `v2` **only for traffic that entered through the ingress gateway**. Mesh-internal traffic to ratings must stay on `v1`.

Attempt these before reading the solutions.

## Solutions

### 1. Pin reviews to v1

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
  namespace: bookinfo
spec:
  hosts:
    - reviews
  http:
    - route:
        - destination:
            host: reviews
            subset: v1
EOF
```

No `weight` needed for a single destination.

### 2. 80/20 canary

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
  namespace: bookinfo
spec:
  hosts:
    - reviews
  http:
    - route:
        - destination:
            host: reviews
            subset: v1
          weight: 80
        - destination:
            host: reviews
            subset: v2
          weight: 20
EOF
```

### 3. Header pin plus weighted default

```yaml
spec:
  hosts:
    - reviews
  http:
    - match:
        - headers:
            end-user:
              exact: jason
      route:
        - destination:
            host: reviews
            subset: v2
    - route:
        - destination:
            host: reviews
            subset: v1
          weight: 80
        - destination:
            host: reviews
            subset: v2
          weight: 20
```

Specific match **above** the weighted catch-all. Reverse that order and jason is just another 80/20 request.

### 4. Cut over

Change both weights to `0` / `100`, or delete the v1 destination. Cleaner cutover:

```yaml
    - route:
        - destination:
            host: reviews
            subset: v2
```

Leave the DestinationRule subsets in place. You will need them if you roll back.

### 5. Gateway-only split

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: ratings
  namespace: bookinfo
spec:
  hosts:
    - ratings
  gateways:
    - bookinfo-gateway
    - mesh
  http:
    - match:
        - gateways:
            - bookinfo-gateway
      route:
        - destination:
            host: ratings
            subset: v1
          weight: 50
        - destination:
            host: ratings
            subset: v2
          weight: 50
    - route:
        - destination:
            host: ratings
            subset: v1
```

`match.gateways` scopes a rule to one listener. The catch-all with no match handles `mesh`. You must list both gateways on `spec.gateways` or the unmatched source never sees this VirtualService.

## Verify

```bash
# Subsets exist?
kubectl -n bookinfo get destinationrule reviews -o yaml | grep -A2 'name: v'

# Routes pushed?
istioctl proxy-config route deploy/productpage-v1.bookinfo --name 9080 -o json \
  | jq '.[] | .virtualHosts[] | select(.name|test("reviews")) | .routes[].route.weightedClusters'

# Generate traffic and count versions. v1 has no stars, v2 has black stars, v3 has red stars.
for i in $(seq 1 100); do
  curl -s http://localhost/productpage | grep -o 'reviews-v[123]' || true
done | sort | uniq -c
```

From inside the mesh:

```bash
kubectl -n bookinfo exec deploy/productpage-v1 -c productpage -- \
  sh -c 'for i in $(seq 1 50); do curl -s http://reviews:9080/reviews/0 | grep -o "reviews-v[123]"; done' \
  | sort | uniq -c
```

Expect roughly 40 v1 and 10 v2 on a 80/20 split. Small samples wander. If you see 100% one version, the VirtualService is not attached (wrong host, wrong namespace, missing subset).

```bash
istioctl analyze -n bookinfo
istioctl proxy-status | grep productpage
```

## Exam Tips

- **DestinationRule first, VirtualService second.** Apply order does not matter to the API, but if you apply the VS first and test immediately you will see 503s until the DR exists. On the exam, apply both, then curl.
- **`host` on the destination is the Kubernetes Service name**, not the subset name. `subset` is a separate field.
- Cross-namespace: fully qualify `host: reviews.bookinfo.svc.cluster.local` and put the DR in the service's namespace. A DR in another namespace for the same host is ignored unless `exportTo` allows it.
- To roll back a canary, revert the weights. Do not delete the new Deployment until traffic is off it.
- `mirror` is not shifting. Mirroring copies traffic; shifting moves it. See `13.md`.
- Docs shortcut: [Traffic Shifting](https://istio.io/docs/tasks/traffic-management/traffic-shifting/) and the VirtualService reference, `http[].route[].weight`.
