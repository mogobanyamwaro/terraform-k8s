# 06. Customizing the Installation: MeshConfig and Overrides

## Concept Refresher

"Customizing your Istio Installation" is its own listed competency. In practice it means knowing **which of four places** a setting belongs in, because putting a valid setting in the wrong place is the failure mode.

```text
+--------------------------------------------------------------+
| 1. meshConfig            -> the "istio" ConfigMap            |
|    Mesh-wide behaviour. Access logs, tracing, trust domain,   |
|    outboundTrafficPolicy, default providers.                  |
|    MOSTLY LIVE: no pod restart needed.                        |
+--------------------------------------------------------------+
| 2. meshConfig.defaultConfig -> default ProxyConfig            |
|    Per-proxy defaults. Concurrency, tracing sampling,         |
|    holdApplicationUntilProxyStarts, proxyMetadata.            |
|    NEEDS A RESTART for anything in the injected pod spec.      |
+--------------------------------------------------------------+
| 3. components.<x>.k8s    -> Kubernetes object shape           |
|    Replicas, resources, HPA, Service type, ports,             |
|    nodeSelector, tolerations, affinity, env, podAnnotations.   |
+--------------------------------------------------------------+
| 4. values.*              -> raw Helm chart passthrough        |
|    Anything with no first-class field. pilot.env,             |
|    global.proxy.*, global.logAsJson, global.imagePullPolicy.   |
+--------------------------------------------------------------+
```

Then there are **per-workload overrides**, which beat all of the above for a single workload:

- Pod annotations, such as `sidecar.istio.io/proxyCPU`.
- The `proxy.istio.io/config` annotation, carrying arbitrary ProxyConfig YAML.
- A `ProxyConfig` resource, which applies to a selected set of workloads.

### Precedence

```text
Pod annotation  >  ProxyConfig resource  >  meshConfig.defaultConfig  >  built-in default
```

### The MeshConfig fields worth memorising

| Field | Purpose | Live? |
| --- | --- | --- |
| `accessLogFile` | Where Envoy writes access logs. `/dev/stdout` | Yes |
| `accessLogFormat` | Custom access log line | Yes |
| `accessLogEncoding` | `TEXT` or `JSON` | Yes |
| `enableTracing` | Turn tracing on or off | Yes |
| `trustDomain` | SPIFFE trust domain | Restart |
| `trustDomainAliases` | Accept other trust domains | Yes |
| `outboundTrafficPolicy.mode` | `ALLOW_ANY` or `REGISTRY_ONLY` | Yes |
| `rootNamespace` | Where mesh-wide policy lives | Restart |
| `defaultProviders` | Default telemetry providers | Yes |
| `extensionProviders` | Named providers for Telemetry API | Yes |
| `ingressSelector` | Which gateway handles Ingress resources | Yes |
| `enablePrometheusMerge` | Merge app and Envoy metrics on 15020 | Yes |
| `defaultConfig.concurrency` | Envoy worker threads | Restart |
| `defaultConfig.holdApplicationUntilProxyStarts` | Startup ordering | Restart |
| `defaultConfig.tracing.sampling` | Trace sample percentage | Restart |
| `defaultHttpRetryPolicy` | Mesh-wide default retries | Yes |
| `discoverySelectors` | Which namespaces istiod watches | Yes |

`outboundTrafficPolicy` and `discoverySelectors` are the two most likely to appear in a task, so know them well.

## Tasks

1. Turn on access logging mesh-wide with a custom format that includes the request ID and the upstream cluster.
2. Change the mesh to block all traffic to external services not declared by a `ServiceEntry`, then verify it.
3. Restrict istiod to watching only the namespaces `shop` and `bookinfo`.
4. Set Envoy's worker thread count to 2 mesh-wide, then override it to 4 for one workload only.
5. Set a mesh-wide default retry policy of 3 attempts with a 2 second per-try timeout.
6. Configure the sidecar to hold the application until the proxy is ready, but only for workloads labelled `needs-ordering=true`.
7. Add a Zipkin tracing provider and set sampling to 10%.
8. Give the ingress gateway a node selector, a toleration, and 3 replicas.
9. Set the proxy image to come from a private registry `registry.internal/istio`.
10. Change the default sidecar resource requests mesh-wide to 100m CPU and 128Mi memory.
11. Enable the DNS proxy so that in-mesh workloads resolve `ServiceEntry` hosts without Kubernetes DNS.
12. Inspect the effective proxy configuration for one workload and prove which layer a value came from.

## Solutions

### 1. Custom access log format

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: default
  meshConfig:
    accessLogFile: /dev/stdout
    accessLogEncoding: TEXT
    accessLogFormat: |
      [%START_TIME%] "%REQ(:METHOD)% %REQ(X-ENVOY-ORIGINAL-PATH?:PATH)% %PROTOCOL%" %RESPONSE_CODE% %RESPONSE_FLAGS% %DURATION% reqid=%REQ(X-REQUEST-ID)% upstream=%UPSTREAM_CLUSTER% host=%UPSTREAM_HOST%
```

```bash
istioctl install -f iop.yaml -y
```

Or directly on the ConfigMap, which takes effect within seconds and is the faster exam answer if the task says "configure the mesh" rather than "install":

```bash
kubectl -n istio-system get cm istio -o yaml > /tmp/istio-cm.yaml
kubectl -n istio-system edit cm istio
```

Verify:

```bash
kubectl -n istio-system get cm istio -o jsonpath='{.data.mesh}' | grep -A3 accessLogFormat

kubectl -n demo exec deploy/sleep -c sleep -- curl -sS -o /dev/null http://httpbin:8000/get
kubectl -n demo logs deploy/httpbin -c istio-proxy --tail=1
```

```text
[2026-08-19T12:00:00.123Z] "GET /get HTTP/1.1" 200 - 3 reqid=9f2a-... upstream=inbound|8000|| host=10.244.1.7:80
```

**No pod restart needed.** Access log configuration goes over xDS.

JSON form, which is what you would want in production:

```yaml
  meshConfig:
    accessLogFile: /dev/stdout
    accessLogEncoding: JSON
    accessLogFormat: |
      {
        "start_time": "%START_TIME%",
        "method": "%REQ(:METHOD)%",
        "path": "%REQ(X-ENVOY-ORIGINAL-PATH?:PATH)%",
        "response_code": "%RESPONSE_CODE%",
        "response_flags": "%RESPONSE_FLAGS%",
        "duration": "%DURATION%",
        "request_id": "%REQ(X-REQUEST-ID)%",
        "upstream_cluster": "%UPSTREAM_CLUSTER%",
        "upstream_host": "%UPSTREAM_HOST%",
        "downstream_remote_address": "%DOWNSTREAM_REMOTE_ADDRESS%"
      }
```

The operators worth knowing, because `33.md` depends on reading them:

| Operator | Meaning |
| --- | --- |
| `%RESPONSE_CODE%` | HTTP status |
| `%RESPONSE_FLAGS%` | Envoy's short failure codes: `UF`, `NR`, `UO`, `URX`, `DC` |
| `%UPSTREAM_CLUSTER%` | Which Envoy cluster was chosen |
| `%UPSTREAM_HOST%` | The actual pod IP and port |
| `%DURATION%` | Total ms |
| `%REQ(X-REQUEST-ID)%` | Correlation ID across hops |
| `%DOWNSTREAM_PEER_URI_SAN%` | The caller's SPIFFE identity |

### 2. Block undeclared external traffic

```bash
# Baseline: external calls succeed
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "before: %{http_code}\n" https://example.com
# 200
```

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: default
  meshConfig:
    outboundTrafficPolicy:
      mode: REGISTRY_ONLY
```

```bash
istioctl install -f iop.yaml -y
```

Or patch the ConfigMap for speed:

```bash
kubectl -n istio-system patch cm istio --type merge -p '{"data":{"mesh":"outboundTrafficPolicy:\n  mode: REGISTRY_ONLY\n"}}'
```

That patch replaces the whole `mesh` key, which destroys the rest of the config. **Do not do that.** Edit it properly instead:

```bash
kubectl -n istio-system edit cm istio
# add under the top level:
#   outboundTrafficPolicy:
#     mode: REGISTRY_ONLY
```

Verify:

```bash
kubectl -n istio-system get cm istio -o jsonpath='{.data.mesh}' | grep -A2 outboundTrafficPolicy

kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "after: %{http_code}\n" --max-time 5 https://example.com
# 502, or a connection failure
```

Now allow one host back with a `ServiceEntry`:

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: ServiceEntry
metadata:
  name: example-com
  namespace: demo
spec:
  hosts:
    - example.com
  ports:
    - number: 443
      name: https
      protocol: TLS
  resolution: DNS
  location: MESH_EXTERNAL
EOF

kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "with SE: %{http_code}\n" https://example.com
# 200
```

The two modes:

| Mode | Behaviour |
| --- | --- |
| `ALLOW_ANY` (default) | Unknown destinations are passed through unproxied |
| `REGISTRY_ONLY` | Only destinations in the mesh registry are reachable |

`REGISTRY_ONLY` is the security-hardening answer and is very likely to appear in a task phrased as "prevent workloads from reaching arbitrary external endpoints".

### 3. Restrict istiod to specific namespaces

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: default
  meshConfig:
    discoverySelectors:
      - matchLabels:
          istio-discovery: enabled
```

```bash
istioctl install -f iop.yaml -y

kubectl label namespace shop istio-discovery=enabled
kubectl label namespace bookinfo istio-discovery=enabled
```

Verify by checking what a proxy now knows about:

```bash
istioctl proxy-config cluster deploy/httpbin.shop | grep -c .
istioctl proxy-config cluster deploy/httpbin.shop | grep -E 'shop|bookinfo|istio-system'
# no clusters for unlabelled namespaces
```

Why it matters: istiod normally computes config for every Service in the cluster and pushes it to every proxy. On a large cluster that is a lot of wasted config and a lot of memory. `discoverySelectors` scopes it down. It is the coarse, control-plane-side tool; the `Sidecar` resource in `16.md` is the fine, per-workload tool.

Two important consequences to be able to state:

- Services in unselected namespaces become unreachable from the mesh, because no cluster exists for them.
- `istio-system` should generally stay selected, or gateway and telemetry config breaks.

### 4. Envoy concurrency, mesh-wide then overridden

Mesh-wide:

```yaml
  meshConfig:
    defaultConfig:
      concurrency: 2
```

```bash
istioctl install -f iop.yaml -y
kubectl -n demo rollout restart deploy/httpbin   # concurrency needs a restart
```

Verify:

```bash
kubectl -n demo get pod -l app=httpbin -o json \
  | jq -r '.items[0].spec.containers[] | select(.name=="istio-proxy") | .args'
```

Per-workload override with the annotation:

```bash
kubectl -n demo patch deployment httpbin -p '{
  "spec":{"template":{"metadata":{"annotations":{
    "proxy.istio.io/config":"{\"concurrency\": 4}"
  }}}}}'
kubectl -n demo rollout status deploy/httpbin
```

Or with a `ProxyConfig` resource, which is the cleaner mechanism when you want it to apply to a label selector rather than a single template:

```yaml
apiVersion: networking.istio.io/v1beta1
kind: ProxyConfig
metadata:
  name: httpbin-concurrency
  namespace: demo
spec:
  selector:
    matchLabels:
      app: httpbin
  concurrency: 4
```

```bash
kubectl apply -f proxyconfig.yaml
kubectl -n demo rollout restart deploy/httpbin
```

Check the effective value:

```bash
istioctl proxy-config bootstrap deploy/httpbin.demo -o json \
  | jq '.bootstrap.node.metadata.PROXY_CONFIG'
```

`concurrency: 0` means "use all available cores", which on a large node produces a surprisingly heavy sidecar. Setting it explicitly is a standard tuning step.

### 5. Mesh-wide default retry policy

```yaml
  meshConfig:
    defaultHttpRetryPolicy:
      attempts: 3
      perTryTimeout: 2s
      retryOn: connect-failure,refused-stream,unavailable,cancelled,retriable-status-codes
```

```bash
istioctl install -f iop.yaml -y
```

Verify on a route:

```bash
istioctl proxy-config route deploy/sleep.demo \
  --name 8000 -o json | jq '.[].virtualHosts[].routes[].route.retryPolicy'
```

Istio's built-in default is **2 attempts** with no per-try timeout. `defaultHttpRetryPolicy` changes that baseline for the whole mesh. A per-route `retries` block in a VirtualService still wins.

To disable retries mesh-wide, which is sometimes the right answer for a service that is not idempotent:

```yaml
  meshConfig:
    defaultHttpRetryPolicy:
      attempts: 0
```

### 6. holdApplicationUntilProxyStarts for selected workloads only

`meshConfig.defaultConfig` is mesh-wide, so to scope it use a `ProxyConfig`:

```yaml
apiVersion: networking.istio.io/v1beta1
kind: ProxyConfig
metadata:
  name: ordered-startup
  namespace: demo
spec:
  selector:
    matchLabels:
      needs-ordering: "true"
  environmentVariables: {}
```

`holdApplicationUntilProxyStarts` is not a `ProxyConfig` field, so the correct mechanism here is the pod annotation:

```bash
kubectl -n demo patch deployment httpbin -p '{
  "spec":{"template":{"metadata":{
    "labels":{"needs-ordering":"true"},
    "annotations":{"proxy.istio.io/config":"{\"holdApplicationUntilProxyStarts\": true}"}
  }}}}'
kubectl -n demo rollout status deploy/httpbin
```

Verify:

```bash
kubectl -n demo get pod -l app=httpbin -o json \
  | jq '.items[0].spec.containers[] | select(.name=="istio-proxy") | .lifecycle'
```

The point of the task is recognising the distinction: some settings are only expressible mesh-wide or per-pod, not per-selector. When a task says "only for workloads matching X" and the setting has no `ProxyConfig` field, the pod annotation on those workloads' templates is the answer.

### 7. Zipkin provider with 10% sampling

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: default
  meshConfig:
    enableTracing: true
    defaultConfig:
      tracing:
        sampling: 10.0
    extensionProviders:
      - name: zipkin-provider
        zipkin:
          service: zipkin.istio-system.svc.cluster.local
          port: 9411
    defaultProviders:
      tracing:
        - zipkin-provider
```

```bash
istioctl install -f iop.yaml -y
kubectl -n demo rollout restart deployment    # sampling is in defaultConfig, needs restart
```

Verify:

```bash
kubectl -n istio-system get cm istio -o jsonpath='{.data.mesh}' \
  | grep -A6 -E 'extensionProviders|sampling'
```

The modern per-namespace way, using the Telemetry API rather than mesh config:

```yaml
apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata:
  name: mesh-tracing
  namespace: istio-system     # rootNamespace => mesh-wide
spec:
  tracing:
    - providers:
        - name: zipkin-provider
      randomSamplingPercentage: 10.0
```

The Telemetry API is preferred now because it can be scoped per namespace or per workload and it takes effect without a restart. Know both, and prefer `Telemetry` when a task says "for namespace X only".

### 8. Gateway placement and scale

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: default
  components:
    ingressGateways:
      - name: istio-ingressgateway
        enabled: true
        k8s:
          replicaCount: 3
          nodeSelector:
            node-role: edge
          tolerations:
            - key: dedicated
              operator: Equal
              value: edge
              effect: NoSchedule
          affinity:
            podAntiAffinity:
              preferredDuringSchedulingIgnoredDuringExecution:
                - weight: 100
                  podAffinityTerm:
                    topologyKey: kubernetes.io/hostname
                    labelSelector:
                      matchLabels:
                        istio: ingressgateway
          resources:
            requests:
              cpu: 200m
              memory: 256Mi
            limits:
              cpu: "2"
              memory: 1Gi
          podAnnotations:
            prometheus.io/scrape: "true"
```

```bash
istioctl install -f iop.yaml -y
```

Verify:

```bash
kubectl -n istio-system get deploy istio-ingressgateway \
  -o jsonpath='{.spec.replicas}{"\n"}{.spec.template.spec.nodeSelector}{"\n"}{.spec.template.spec.tolerations}{"\n"}'
kubectl -n istio-system get pods -l istio=ingressgateway -o wide
```

If an HPA exists it overrides `replicaCount`, exactly as with istiod. Check and disable if the task wants a fixed count:

```bash
kubectl -n istio-system get hpa
```

```yaml
        k8s:
          hpaSpec:
            minReplicas: 3
            maxReplicas: 3
```

### 9. Private registry

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  profile: default
  hub: registry.internal/istio
  tag: 1.26.0
  values:
    global:
      imagePullPolicy: IfNotPresent
      imagePullSecrets:
        - my-registry-creds
```

```bash
istioctl install -f iop.yaml -y
```

Verify:

```bash
kubectl -n istio-system get deploy istiod \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
# registry.internal/istio/pilot:1.26.0

kubectl -n demo get pod -l app=httpbin \
  -o jsonpath='{.items[0].spec.containers[?(@.name=="istio-proxy")].image}{"\n"}'
# registry.internal/istio/proxyv2:1.26.0
```

`hub` and `tag` are top-level `spec` fields, not under `values`, which is easy to get wrong. To override the proxy image alone:

```yaml
  values:
    global:
      proxy:
        image: proxyv2
```

The pull secret must exist in **every namespace that runs injected workloads**, not just `istio-system`, because the sidecar image is pulled in the workload's namespace. That detail is a realistic troubleshooting scenario: istiod comes up fine, application pods sit in `ImagePullBackOff` on the sidecar.

```yaml
            cpu: "2"
```

```bash
istioctl install -f iop.yaml -y

```

```bash
kubectl -n demo get pod -l app=httpbin -o json \
```

### 11. DNS proxying

```yaml
  meshConfig:
    defaultConfig:
      proxyMetadata:
        ISTIO_META_DNS_CAPTURE: "true"
        ISTIO_META_DNS_AUTO_ALLOCATE: "true"
```

```bash
istioctl install -f iop.yaml -y
kubectl -n demo rollout restart deployment
```

Verify:

```bash
kubectl -n demo get pod -l app=sleep -o json \
  | jq '.items[0].spec.containers[] | select(.name=="istio-proxy") | .env[] | select(.name|startswith("ISTIO_META_DNS"))'
```

Then prove that a `ServiceEntry` host resolves even though it has no Kubernetes DNS record:

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: ServiceEntry
metadata:
  name: fake-external
  namespace: demo
spec:
  hosts:
    - my.fake.service.internal
  ports:
    - number: 80
      name: http
      protocol: HTTP
  resolution: DNS
  location: MESH_EXTERNAL
EOF

kubectl -n demo exec deploy/sleep -c sleep -- getent hosts my.fake.service.internal
```

Without DNS capture that returns nothing, because CoreDNS has no such record. With capture and auto-allocation, Envoy answers with a synthetic address from `240.240.0.0/16` and routes accordingly.

What this solves: TCP `ServiceEntry` hosts, and external services reached by name where the mesh needs to apply policy per hostname rather than per IP. Also removes a round trip to CoreDNS for in-mesh names, which reduces DNS load meaningfully on large clusters.

### 12. Trace an effective value to its source

Take `concurrency` as the example.

```bash
# Layer 4: what the pod's container args and env say
kubectl -n demo get pod -l app=httpbin -o json \
  | jq '.items[0].spec.containers[] | select(.name=="istio-proxy")
        | {args, env: [.env[] | select(.name|test("PROXY_CONFIG|ISTIO_META"))]}'

# Layer 3: pod annotation override
kubectl -n demo get pod -l app=httpbin \
  -o jsonpath='{.items[0].metadata.annotations.proxy\.istio\.io/config}{"\n"}'

# Layer 2: ProxyConfig resources selecting this workload
kubectl -n demo get proxyconfig -o yaml

# Layer 1: mesh default
kubectl -n istio-system get cm istio -o jsonpath='{.data.mesh}' | grep -A10 defaultConfig

# The merged result Envoy actually booted with
istioctl proxy-config bootstrap deploy/httpbin.demo -o json \
  | jq '.bootstrap.node.metadata.PROXY_CONFIG'
```

The last command is the authoritative one: it shows the fully merged `ProxyConfig` after all layers were applied. When a setting is "not working", compare what you wrote with what appears there. If it is absent from the bootstrap, the layer you edited is not the layer that wins, or the pod predates your change.

For mesh config specifically:

```bash
# The rendered ConfigMap
kubectl -n istio-system get cm istio -o jsonpath='{.data.mesh}'

# What istiod has loaded, including defaults you never set
kubectl -n istio-system exec deploy/istiod -- \
  curl -sS localhost:15014/debug/mesh 2>/dev/null | head -60
```

## Exam Tips

**Ask "is this mesh behaviour or object shape?" before you write anything.** Mesh behaviour goes in `meshConfig`. Kubernetes object shape goes in `components.<x>.k8s`. Everything else is `values`. That one question resolves most "where does this setting go" problems in a few seconds.

**`meshConfig` top level is mostly live. `meshConfig.defaultConfig` mostly needs a restart.** Access logging, tracing on/off, and `outboundTrafficPolicy` apply immediately. Concurrency, sampling, and startup ordering are baked into the pod, so `kubectl rollout restart` is part of the answer. Stating the restart requirement, and doing it, is often where the point is.

**For "configure the mesh to do X" you can edit the `istio` ConfigMap directly.** It is faster than a full `istioctl install`, and it is legitimate. But never `kubectl patch` the `mesh` key with a merge patch, because the whole key is a single string and you will wipe everything else. Use `kubectl edit`.

**`REGISTRY_ONLY` is the answer to any "block undeclared external traffic" task.** Remember the follow-up: each allowed destination then needs a `ServiceEntry`. Setting the mode without adding the ServiceEntry for a host the task still needs is a half-finished answer.

**`hub` and `tag` are top-level, not under `values`.** And image pull secrets have to exist in every workload namespace, not just `istio-system`.

**An HPA beats `replicaCount`.** For istiod and for gateways, use `hpaSpec.minReplicas` when a task specifies a replica count, or you will set a value that the autoscaler immediately overrides.

**`istioctl proxy-config bootstrap ... | jq '.bootstrap.node.metadata.PROXY_CONFIG'` settles every "is my setting applied" argument.** It shows the merged result, so if your value is not in there, you edited the wrong layer or you forgot to restart.

**Prefer the `Telemetry` API over `meshConfig` tracing when the task scopes to a namespace or workload.** Mesh config is mesh-wide by definition; `Telemetry` is scopeable and needs no restart.

**`discoverySelectors` scopes the control plane; `Sidecar` scopes one workload.** Both reduce config size. If a task says "reduce what istiod computes" that is `discoverySelectors`; "reduce what this proxy receives" is a `Sidecar`, covered in `16.md`.
