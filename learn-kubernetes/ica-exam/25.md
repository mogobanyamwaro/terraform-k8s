# 25. AuthorizationPolicy Fundamentals

## Concept Refresher

AuthorizationPolicy is Istio's L3/L7 ACL. It is evaluated by Envoy (or ztunnel at L4) on **inbound** traffic to the selected workload.

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: httpbin
  namespace: demo
spec:
  selector:
    matchLabels:
      app: httpbin
  action: ALLOW
  rules:
    - from:
        - source:
            principals:
              - cluster.local/ns/demo/sa/sleep
      to:
        - operation:
            methods: ["GET"]
            paths: ["/get"]
```

### The default-allow trap

```text
No AuthorizationPolicy selecting the workload  -> ALLOW everything
One ALLOW policy selecting it                  -> DENY everything not matched by an ALLOW rule
DENY policy                                    -> those matches are denied, everything else still allowed
ALLOW + DENY                                   -> DENY first, then ALLOW
```

Installing a single ALLOW that matches `GET /get` **breaks** `POST /post` and every other client. That is intended. Exam tasks that say "only sleep can call httpbin" want ALLOW + source principal, and they **accept** that everyone else is locked out.

### Actions

| Action | Meaning |
| --- | --- |
| `ALLOW` | Allow if a rule matches (and no DENY matched). Default action if omitted |
| `DENY` | Deny if a rule matches. Evaluated first |
| `AUDIT` | Log a match, do not enforce |
| `CUSTOM` | External authorizer (out of typical ICA scope) |

### Rule structure

A rule matches if **from AND to AND when** all match. Empty `from` = any source. Empty `to` = any operation. Empty `rules: []` or missing rules on ALLOW = match **nothing** (deny all, for ALLOW). Empty rules on DENY = match **nothing** (deny nothing). A DENY with no rules is a no-op. An ALLOW with no rules is **deny all**.

`from` list is OR. Inside one source, fields are AND.

### Source and operation fields

**source:** `principals`, `notPrincipals`, `requestPrincipals`, `namespaces`, `ipBlocks`, `remoteIpBlocks`, `serviceAccounts` (ns/sa form in recent Istio)

**operation:** `hosts`, `methods`, `ports`, `paths`, and `not*` inverses. Paths are exact or suffix wildcards like `/api/*`. Prefix in older docs; check the reference for `*` rules.

**when:** `key` + `values` / `notValues`. Keys like `request.headers[x-token]`, `source.ip`, `destination.port`, `request.auth.claims[iss]`.

### Selector

- Namespace policy, no selector: all workloads in that namespace (including the ingress gateway if the policy is in `istio-system` — be careful).
- `selector.matchLabels`: workload pods.
- `targetRef` to Gateway / Service: Gateway API / waypoint style.

## Tasks

1. Deny all traffic to `httpbin` (break the service on purpose).
2. Allow only `GET` to `httpbin` from any source.
3. Allow only the `sleep` ServiceAccount in `demo` to call `httpbin`.
4. Allow `GET` and `HEAD` on paths `/get` and `/status/*`, nothing else.
5. Namespace `demo`: allow intra-namespace traffic, deny everyone else. Do not brick istiod health.

## Solutions

### 1. Deny all

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: httpbin-deny-all
  namespace: demo
spec:
  selector:
    matchLabels:
      app: httpbin
  action: ALLOW
  # no rules => match nothing => deny all
```

### 2. GET only

```yaml
spec:
  selector:
    matchLabels:
      app: httpbin
  action: ALLOW
  rules:
    - to:
        - operation:
            methods: ["GET"]
```

### 3. SA allowlist

```yaml
  rules:
    - from:
        - source:
            principals:
              - cluster.local/ns/demo/sa/sleep
```

Confirm SA name: `kubectl -n demo get deploy sleep -o jsonpath='{.spec.template.spec.serviceAccountName}'`.

Shorthand in recent Istio:

```yaml
            namespaces: ["demo"]
```

that allows every SA in `demo`, which is broader than the task.

### 4. Methods and paths

```yaml
  rules:
    - to:
        - operation:
            methods: ["GET", "HEAD"]
            paths: ["/get", "/status/*"]
```

### 5. Namespace isolation

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-demo
  namespace: demo
spec:
  action: ALLOW
  rules:
    - from:
        - source:
            namespaces: ["demo"]
```

No selector: applies to every workload in `demo`. Mesh-internal mTLS is required for `namespaces` to populate. Gateways in other namespaces cannot call in unless you add them.

Do **not** apply this in `istio-system` without extra rules for kubelet probes and Prometheus, or the control plane goes NotReady.

## Verify

```bash
kubectl -n demo exec deploy/sleep -c sleep -- curl -sS -o /dev/null -w "%{http_code}\n" http://httpbin:8000/get
kubectl -n demo exec deploy/sleep -c sleep -- curl -sS -o /dev/null -w "%{http_code}\n" -X POST http://httpbin:8000/post

istioctl experimental authz check \
  $(kubectl -n demo get pod -l app=httpbin -o jsonpath='{.items[0].metadata.name}').demo
```

Expect `200` vs `403`. Authorization denials are **403**, JWT failures are **401**.

## Exam Tips

- First ALLOW policy is a **default deny** for that workload. Add every method/path the app needs, or probes fail (`15021` is Istio's own; app probes on app ports can 403).
- Kubernetes HTTP probes come from kubelet, **not** a mesh identity. If STRICT mTLS + ALLOW principals only, **probes fail**. Fix with `portLevelMtls` DISABLE on the probe port, or `ipBlocks` for node IPs, or a separate port. Exam often uses `/healthz` allowed from anywhere:

```yaml
    - to:
        - operation:
            paths: ["/healthz", "/ready"]
```
