# 16. The Sidecar Resource and Scoping Config

## Concept Refresher

Every sidecar (or waypoint) is given configuration for **every service in the mesh** by default. That is simple, and it does not scale: 500 services means 500 clusters on every Envoy.

The **Sidecar** resource limits what a proxy is programmed with: which hosts it can call (`egress`), which ports it listens on (`ingress`), and whether unknown destinations are allowed.

```yaml
apiVersion: networking.istio.io/v1
kind: Sidecar
metadata:
  name: default
  namespace: shop
spec:
  workloadSelector:
    labels:
      app: frontend
  egress:
    - hosts:
        - "shop/*"
        - "istio-system/*"
  outboundTrafficPolicy:
    mode: REGISTRY_ONLY
```

### How Istio picks a Sidecar

```text
1. Sidecar in the workload's namespace with a matching workloadSelector
2. Sidecar named "default" in that namespace (no selector)
3. Sidecar named "default" in the mesh root namespace (istio-system, usually)
4. Built-in default: egress to "*/*" (everything), ALLOW_ANY
```

There is **no merge**. A more specific Sidecar **replaces** the default entirely. If `default` in `shop` allows `shop/*` and `istio-system/*`, and you add a selected Sidecar that only lists `shop/*`, that workload **loses** istiod and will fail certificate refresh and xDS. Always include `istio-system/*` unless you know you do not need it.

### `egress.hosts` syntax

| Host | Meaning |
| --- | --- |
| `*/*` | Every namespace, every service |
| `shop/*` | All services in `shop` |
| `shop/reviews.shop.svc.cluster.local` | One service |
| `istio-system/*` | istiod, gateways, etc. **Keep this** |
| `~/*` | Nothing. Trims outbound to zero |

The first label is a **namespace**, not a wildcard domain. `"*.example.com"` does not belong here; that is ServiceEntry/VirtualService territory.

### `ingress`

Override the captured inbound ports. Rare on ICA, used when the app listens on unexpected ports or you need a custom Envoy filter chain.

```yaml
spec:
  ingress:
    - port:
        number: 9080
        protocol: HTTP
        name: http
      defaultEndpoint: 127.0.0.1:9080
```

### Sidecar vs ServiceEntry `exportTo` vs `exportTo` on VS/DR

They compose:

- **exportTo** on a Service/VS/DR/SE: "is this object visible to namespace X?"
- **Sidecar egress hosts**: "of the things visible, which ones should this proxy be programmed with?"

Both must allow a destination or the cluster will not appear in `proxy-config cluster`.

## Tasks

Namespace `shop` has `frontend` and `backend`. Namespace `other` has `httpbin`. All meshed.

1. Make every proxy in `shop` only see services in `shop` and `istio-system`.
2. Tighten **only** `frontend` so it can call `backend` and istiod, nothing in `other`.
3. Put `shop` in `REGISTRY_ONLY` so `frontend` cannot hit arbitrary IPs.
4. Show that `other/httpbin` disappears from frontend's cluster list, then restore it surgically (one host, not `*/*`).

## Solutions

### 1. Namespace default Sidecar

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: Sidecar
metadata:
  name: default
  namespace: shop
spec:
  egress:
    - hosts:
        - "./*"
        - "istio-system/*"
EOF
```

`"."` means **this namespace**. Do not put a space in `"./*"`.

### 2. Workload-selected Sidecar

```yaml
apiVersion: networking.istio.io/v1
kind: Sidecar
metadata:
  name: frontend
  namespace: shop
spec:
  workloadSelector:
    labels:
      app: frontend
  egress:
    - hosts:
        - "shop/backend.shop.svc.cluster.local"
        - "istio-system/*"
        - "shop/frontend.shop.svc.cluster.local"
```

Including the workload's own service avoids obscure inbound issues. Always keep `istio-system/*`.

### 3. REGISTRY_ONLY on that Sidecar

```yaml
  outboundTrafficPolicy:
    mode: REGISTRY_ONLY
```

### 4. Surgical allow of other/httpbin

Add to the frontend Sidecar hosts:

```yaml
        - "other/httpbin.other.svc.cluster.local"
```

If `httpbin`'s Sidecar/exportTo hides it from `shop`, this is not enough. Check:

```bash
kubectl -n other get svc httpbin -o yaml | grep -A2 exportTo || true
```

Istio also honours `spec.exportTo` on the Kubernetes Service via the `networking.istio.io/exportTo` annotation.

## Verify

```bash
# Before/after cluster counts
istioctl proxy-config cluster deploy/frontend.shop | wc -l
istioctl proxy-config cluster deploy/frontend.shop | grep httpbin || echo "httpbin gone (expected)"
istioctl proxy-config cluster deploy/frontend.shop | grep backend

# xDS still working? If you forgot istio-system, this goes STALE
istioctl proxy-status | grep frontend

kubectl -n shop exec deploy/frontend -c istio-proxy -- \
  curl -sS http://127.0.0.1:15000/clusters | grep outbound | wc -l
```

Traffic test:

```bash
kubectl -n shop exec deploy/frontend -c <app> -- curl -sS -o /dev/null -w "%{http_code}\n" http://backend:80
kubectl -n shop exec deploy/frontend -c <app> -- curl -sS -o /dev/null -w "%{http_code}\n" http://httpbin.other:8000
```

Second curl should fail after tightening.

## Exam Tips

- Forgetting `istio-system/*` is the classic Sidecar footgun. Proxies go `STALE`, new pods never become Ready (`15021` fails eventually as certs expire).
- `metadata.name: default` in a namespace is special. Any other name **without** a `workloadSelector` is ignored.
- Sidecar is **not** how you enable sidecar injection. Injection is the namespace label `istio-injection=enabled` (`04.md`). This CRD only scopes config.
- Ambient: a Sidecar resource does not configure ztunnel. Waypoints use Gateway API. Do not apply Sidecar to fix ambient L7.
- Docs: [Sidecar](https://istio.io/docs/reference/config/networking/sidecar/).
