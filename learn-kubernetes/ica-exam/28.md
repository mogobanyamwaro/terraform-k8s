# 28. Certificate Management and Custom CA

## Concept Refresher

Istio's default install creates a self-signed root in Secret **`istio-ca-secret`** (`ca-cert.pem`, `ca-key.pem`, `cert-chain.pem`, `root-cert.pem`) in `istio-system`. Workload certs chain to that root.

Custom CA on ICA means one of:

1. Plug a root/intermediate into istiod via Secret **`cacerts`**.
2. Use cert-manager / `istio-csr` (know that it exists; full installer is heavy for 6 minutes).
3. Rotate or inspect workload certs and the mesh trust domain.

### Installing with cacerts

Before or as you install, in `istio-system`:

```text
ca-cert.pem      intermediate (or root if no intermediate)
ca-key.pem       matching key
root-cert.pem    trusted root
cert-chain.pem   ca-cert + any intermediates up to but not always including root
```

```bash
kubectl -n istio-system create secret generic cacerts \
  --from-file=ca-cert.pem \
  --from-file=ca-key.pem \
  --from-file=root-cert.pem \
  --from-file=cert-chain.pem
```

If `cacerts` exists, istiod **ignores** `istio-ca-secret` for signing. Wrong files = workloads fail SDS, pods never Ready.

### Intermediate CA

Production meshes use an org root and give Istio an intermediate. `root-cert.pem` is the org root (what you distribute to non-mesh clients). `ca-cert.pem` + `ca-key.pem` are the intermediate istiod uses to sign workload certs. `cert-chain.pem` is intermediate (+ extras) presented to peers.

### Trust domain

```yaml
# MeshConfig / IstioOperator
spec:
  values:
    global:
      trustDomain: example.com
```

Principals become `spiffe://example.com/ns/demo/sa/sleep`. **Existing AuthorizationPolicies that hardcode `cluster.local` break** after this change. Recreate workloads to get new certs.

### TTL and rotation

| Cert | Default |
| --- | --- |
| Workload | 24h, rotated by agent at ~12h |
| Root (self-signed) | 10 years |

MeshConfig:

```yaml
meshConfig:
  defaultConfig:
    proxyMetadata: {}
  # istiod env
```

`externalCa` / `PILOT_CERT_PROVIDER` are advanced. For ICA, `istioctl proxy-config secret` + openssl dates is enough to prove rotation is active.

### Gateway certs vs mesh certs

| | Mesh mTLS | Edge SIMPLE/MUTUAL |
| --- | --- | --- |
| Issued by | istiod | You (`credentialName` Secret) or cert-manager |
| Identity | SPIFFE SAN | DNS SAN for the hostname |
| Resource | automatic | Gateway `tls.credentialName` |

Do not put the mesh `istio-ca-secret` on a public Gateway unless you understand you are presenting an internal CA to the internet.

## Tasks

1. Extract and print the root subject and expiry of the mesh CA.
2. Print a workload cert's SPIFFE URI and `NotAfter`.
3. Create a `cacerts` secret from a self-signed root (lab only) and restart istiod so it uses it. Verify new workload certs chain to that root.
4. Set trust domain to `exam.local` on a **fresh** install (or explain why changing it on a running mesh needs a coordinated rollout).

## Solutions

### 1. Mesh root

```bash
kubectl -n istio-system get secret istio-ca-secret -o jsonpath='{.data.ca-cert\.pem}' \
  | base64 -d | openssl x509 -noout -subject -dates

kubectl -n istio-system get secret istio-ca-secret -o jsonpath='{.data.root-cert\.pem}' \
  | base64 -d | openssl x509 -noout -subject -dates
```

If `cacerts` exists, use that instead.

### 2. Workload cert

Same `istioctl proxy-config secret` pipeline as `22.md`.

```bash
istioctl proxy-config secret deploy/httpbin.demo -o json \
  | jq -r '.dynamicActiveSecrets[] | select(.name=="default")
      | .secret.tlsCertificate.certificateChain.inlineBytes' \
  | base64 -d | openssl x509 -noout -dates -ext subjectAltName
```

### 3. Custom cacerts (lab)

```bash
mkdir -p /tmp/certs && cd /tmp/certs
openssl req -x509 -newkey rsa:2048 -keyout ca-key.pem -out root-cert.pem -days 365 -nodes \
  -subj "/CN=Exam Root"
cp root-cert.pem ca-cert.pem
cp ca-cert.pem cert-chain.pem
# For a real intermediate you would sign a second cert. This lab uses root=ca.

kubectl create ns istio-system 2>/dev/null || true
kubectl -n istio-system create secret generic cacerts \
  --from-file=ca-cert.pem \
  --from-file=ca-key.pem \
  --from-file=root-cert.pem \
  --from-file=cert-chain.pem \
  --dry-run=client -o yaml | kubectl apply -f -

kubectl -n istio-system rollout restart deploy/istiod
kubectl -n demo rollout restart deploy/httpbin
```

Then re-run the openssl SAN dump. Issuer should match `Exam Root`.

If istiod was already running with `istio-ca-secret`, adding `cacerts` still requires the restart. New pods get the new CA; old pods keep old certs until restart. **Two CAs in one mesh = mTLS failures** until everything rolls.

### 4. Trust domain

On install:

```bash
istioctl install -y --set values.global.trustDomain=exam.local
```

On an existing mesh this is a breaking change: every AuthorizationPolicy principal, every cert, every ztunnel identity. ICA will more likely ask you to **read** the trust domain:

```bash
kubectl -n istio-system get cm istio -o yaml | grep trustDomain
istioctl proxy-config secret deploy/httpbin.demo -o json | jq -r '... SAN ...'
```

## Verify

```bash
kubectl -n istio-system get secret istio-ca-secret cacerts 2>/dev/null
kubectl -n istio-system logs deploy/istiod --tail=50 | grep -i 'ca\|cert' | head
istioctl proxy-status
```

Pods stuck 1/2 or 0/1 with SDS errors mean the CA secret is malformed.

## Exam Tips

- **`cacerts` vs `istio-ca-secret`:** custom CA uses `cacerts`. Do not mix keys into the wrong secret.
- Rolling a new root without keeping the old root in `root-cert.pem` (bundle) splits the mesh.
- Gateway `credentialName` is unrelated to `cacerts`. Edge certs are ordinary TLS secrets.
- Docs: [Plugin CA certificates](https://istio.io/docs/tasks/security/cert-management/plugin-ca-cert/) and [Cert management](https://istio.io/docs/concepts/security/#pki).
