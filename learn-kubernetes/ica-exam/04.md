# 04. Sidecar Mode and Sidecar Injection

## Concept Refresher

In sidecar mode every meshed pod gets its own Envoy container. Injection is done by a **MutatingAdmissionWebhook** that rewrites the pod spec at creation time.

The single most important consequence: **injection happens at pod creation, and only at pod creation.** Labelling a namespace does nothing to pods that already exist. You must recreate them. This is examined constantly, and forgetting it is the most common reason a candidate's otherwise-correct work scores zero.

```bash
kubectl label namespace demo istio-injection=enabled
kubectl -n demo rollout restart deployment    # <-- without this, nothing changes
```

### What gets injected

```text
Before:                          After:
  containers:                      initContainers:
    - app                            - istio-init      (iptables rules)
                                   containers:
                                     - istio-proxy     (Envoy + pilot-agent)
                                     - app
                                   volumes:
                                     - istio-envoy      (config, emptyDir memory)
                                     - istio-data
                                     - istio-podinfo
                                     - istio-token      (SA token for CA auth)
                                     - istiod-ca-cert
```

With `istio-cni` installed there is **no `istio-init` container**, because the CNI plugin writes the iptables rules from the node instead. That removes the need for `NET_ADMIN` on application pods, which is why the CNI is preferred in restricted environments. Recognising a pod with a sidecar but no init container as "CNI mode" rather than "broken" is worth knowing.

In recent Kubernetes versions, `istio-proxy` is injected as a **native sidecar** (an `initContainer` with `restartPolicy: Always`) when the feature is enabled. That fixes the old problems with Jobs never completing and with startup ordering.

### The decision order for whether a pod gets a sidecar

This precedence chain is prime exam material. Later entries override earlier ones.

```text
1. Namespace label
     istio-injection=enabled          -> inject (default revision)
     istio.io/rev=<rev>               -> inject (that revision)
     istio-injection=disabled         -> do not inject
     neither                          -> do not inject  (with default webhook config)

2. Pod label / annotation  (OVERRIDES the namespace)
     sidecar.istio.io/inject: "true"  -> inject even in an unlabelled namespace*
     sidecar.istio.io/inject: "false" -> do not inject, even in an enabled namespace

3. Pod is on the host network (hostNetwork: true)  -> never injected

* only if the webhook's namespaceSelector allows the namespace to be considered
```

Two hard rules that catch people out:

- **`istio-injection=enabled` beats `istio.io/rev`.** If a namespace has both, the revision label is ignored and you get the default revision. During a canary upgrade this means your "migrated" namespace never actually moved.
- **`istio-injection=disabled` is not the same as no label.** Both prevent injection, but `disabled` is explicit and survives someone else adding the enabled label carelessly.
- The pod-level key works as **either a label or an annotation**. The label form is now preferred.

### Manual injection

For the case where you cannot use the webhook, for example generating manifests to commit to git:

```bash
istioctl kube-inject -f deployment.yaml > deployment-injected.yaml
kubectl apply -f deployment-injected.yaml
```

This bakes the sidecar into the YAML. The downside is that the injected config is frozen at generation time and does not follow control plane upgrades, so it is a fallback rather than a default choice.

## Solutions

### 1. New namespace with injection

```bash
kubectl create namespace shop
kubectl label namespace shop istio-injection=enabled

kubectl -n shop apply -f ~/istio-1.26.0/samples/httpbin/httpbin.yaml
kubectl -n shop wait --for=condition=ready pod -l app=httpbin --timeout=120s

kubectl -n shop get pods
```

```text
NAME                      READY   STATUS    RESTARTS   AGE
httpbin-8b9c5d6f7-k2nml   2/2     Running   0          25s
```

`2/2` is the proof. Confirm which containers:

```bash
kubectl -n shop get pod -l app=httpbin \
  -o jsonpath='{.items[0].spec.containers[*].name}{"\n"}'
```

```text
httpbin istio-proxy
```

And the init container, if not using CNI:

```bash
kubectl -n shop get pod -l app=httpbin \
  -o jsonpath='{.items[0].spec.initContainers[*].name}{"\n"}'
```

### 2. Mesh an existing workload

```bash
# Set up the scenario
kubectl create namespace legacy
kubectl -n legacy apply -f ~/istio-1.26.0/samples/httpbin/httpbin.yaml
kubectl -n legacy get pods     # 1/1, no sidecar
```

The fix is two steps, and **the second step is the one people forget**:

```bash
kubectl label namespace legacy istio-injection=enabled

kubectl -n legacy rollout restart deployment httpbin
kubectl -n legacy rollout status deployment httpbin
```

```bash
kubectl -n legacy get pods     # now 2/2
```

For every workload in the namespace at once:

```bash
kubectl -n legacy rollout restart deployment,statefulset,daemonset
```

If a workload is a bare pod with no controller, a restart is not possible; it must be deleted and recreated:

```bash
kubectl -n legacy delete pod standalone-pod
kubectl -n legacy apply -f standalone-pod.yaml
```

`rollout restart` is a rolling operation so it is safe for a Deployment with more than one replica. Note it works by stamping `kubectl.kubernetes.io/restartedAt` on the pod template, which is why it triggers a normal rolling update.

### 3. Opt one pod out

Add the label to the **pod template**, not the Deployment metadata. This is a distinction that costs people points.

```bash
kubectl -n shop apply -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nosidecar
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nosidecar
  template:
    metadata:
      labels:
        app: nosidecar
        sidecar.istio.io/inject: "false"
    spec:
      containers:
        - name: app
          image: curlimages/curl
          command: ["sleep", "3600"]
EOF

kubectl -n shop get pods -l app=nosidecar
```

```text
NAME                        READY   STATUS    RESTARTS   AGE
nosidecar-6f8d9c5b4-x2klm   1/1     Running   0          15s
```

For an existing Deployment, patch the template:

```bash
kubectl -n shop patch deployment nosidecar -p \
  '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"false"}}}}}'
```

The annotation form still works and appears in older docs:

```yaml
template:
  metadata:
    annotations:
      sidecar.istio.io/inject: "false"
```

**The value must be the quoted string `"false"`.** Unquoted `false` is a YAML boolean, and Kubernetes rejects boolean label values outright with a type error. Under time pressure this produces a baffling failure.

### 4. Opt one pod in, namespace unlabelled

```bash
kubectl create namespace special
# deliberately no namespace label

kubectl -n special apply -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: wants-mesh
spec:
  replicas: 1
  selector:
    matchLabels:
      app: wants-mesh
  template:
    metadata:
      labels:
        app: wants-mesh
        sidecar.istio.io/inject: "true"
    spec:
      containers:
        - name: app
          image: curlimages/curl
          command: ["sleep", "3600"]
EOF

kubectl -n special get pods
```

Whether this works depends on the webhook's `namespaceSelector`. The default Istio webhook is configured so that pod-level opt-in works in namespaces that are not explicitly disabled:

```bash
kubectl get mutatingwebhookconfiguration istio-sidecar-injector \
  -o jsonpath='{range .webhooks[*]}{"\n=== "}{.name}{"\n"}{.namespaceSelector}{"\n"}{.objectSelector}{"\n"}{end}'
```

You will see four webhook entries, covering the four combinations of namespace-level and object-level selection. The `object-selector` entries are the ones that make per-pod opt-in work.

If the pod does not get a sidecar, label the namespace explicitly to allow consideration while defaulting to off:

```bash
kubectl label namespace special istio-injection=disabled
# then pod-level "true" is honoured for pods that ask for it
```

In practice, labelling the namespace and opting individual pods out is the cleaner and far more common pattern. Prefer it unless a task specifically forbids touching the namespace.

### 5. Audit sidecars across the cluster

Pods **without** a sidecar:

```bash
kubectl get pods -A -o json | jq -r '
  .items[]
  | select([.spec.containers[].name] | index("istio-proxy") | not)
  | "\(.metadata.namespace)\t\(.metadata.name)"' \
  | column -t
```

Pods **with** one:

```bash
kubectl get pods -A -o json | jq -r '
  .items[]
  | select([.spec.containers[].name] | index("istio-proxy"))
  | "\(.metadata.namespace)\t\(.metadata.name)"' \
  | column -t
```

A count per namespace, which is the most useful summary:

```bash
kubectl get pods -A -o json | jq -r '
  .items[]
  | "\(.metadata.namespace) \(if ([.spec.containers[].name] | index("istio-proxy")) then "meshed" else "bare" end)"' \
  | sort | uniq -c
```

Without `jq`, the crude version works fine:

```bash
kubectl get pods -A -o wide | awk 'NR==1 || $3 !~ /\// || $3 ~ /^1\/1$/'
```

The authoritative view from Istio's side, which also tells you which revision each proxy is on:

```bash
istioctl proxy-status
```

Any workload you expect to see there but do not is unmeshed. Cross-check namespace intent against reality:

```bash
istioctl analyze -A
```

`analyze` reports `IST0102` for a namespace that is enabled but contains pods without sidecars, which is exactly the "you forgot to restart" case.

### 6. Offline injection

```bash
kubectl create deployment offline --image=nginx --dry-run=client -o yaml > /tmp/offline.yaml

istioctl kube-inject -f /tmp/offline.yaml > /tmp/offline-injected.yaml

grep -A2 'name: istio-proxy' /tmp/offline-injected.yaml | head -20

# Container list
grep -E '^\s+- name:' /tmp/offline-injected.yaml
```

Apply and confirm:

```bash
kubectl -n special apply -f /tmp/offline-injected.yaml
kubectl -n special get pods -l app=offline
```

If istiod is unreachable, supply the config from local files:

```bash
kubectl -n istio-system get cm istio-sidecar-injector -o jsonpath='{.data.config}' > /tmp/inject-config.yaml
kubectl -n istio-system get cm istio -o jsonpath='{.data.mesh}' > /tmp/mesh-config.yaml
kubectl -n istio-system get cm istio-sidecar-injector -o jsonpath='{.data.values}' > /tmp/inject-values.yaml

istioctl kube-inject \
  --injectConfigFile /tmp/inject-config.yaml \
  --meshConfigFile /tmp/mesh-config.yaml \
  --valuesFile /tmp/inject-values.yaml \
  -f /tmp/offline.yaml
```

That fully-offline form is the reason `kube-inject` still exists.

### 7. Per-workload sidecar resources

Annotations on the pod template:

```bash
kubectl -n shop patch deployment httpbin -p '{
  "spec": {"template": {"metadata": {"annotations": {
    "sidecar.istio.io/proxyCPU": "50m",
    "sidecar.istio.io/proxyMemory": "64Mi",
    "sidecar.istio.io/proxyCPULimit": "500m",
    "sidecar.istio.io/proxyMemoryLimit": "256Mi"
  }}}}}'

kubectl -n shop rollout status deployment httpbin

kubectl -n shop get pod -l app=httpbin -o jsonpath='{.items[0].spec.containers[?(@.name=="istio-proxy")].resources}' | jq
```

```json
{
  "limits": {"cpu": "500m", "memory": "256Mi"},
  "requests": {"cpu": "50m", "memory": "64Mi"}
}
```

The full annotation set worth remembering:

| Annotation | Effect |
| --- | --- |
| `sidecar.istio.io/proxyCPU` | Proxy CPU request |
| `sidecar.istio.io/proxyMemory` | Proxy memory request |
| `sidecar.istio.io/proxyCPULimit` | Proxy CPU limit |
| `sidecar.istio.io/proxyMemoryLimit` | Proxy memory limit |
| `sidecar.istio.io/inject` | Inject or not |
| `sidecar.istio.io/logLevel` | Envoy log level |
| `sidecar.istio.io/componentLogLevel` | Per-Envoy-component log level |
| `sidecar.istio.io/statsInclusionPrefixes` | Extra stats to emit |
| `sidecar.istio.io/rewriteAppHTTPProbers` | Rewrite HTTP probes through the proxy |
| `traffic.sidecar.istio.io/includeOutboundIPRanges` | Which outbound CIDRs to capture |
| `traffic.sidecar.istio.io/excludeOutboundIPRanges` | Which outbound CIDRs to bypass |
| `traffic.sidecar.istio.io/excludeInboundPorts` | Inbound ports to bypass |
| `traffic.sidecar.istio.io/excludeOutboundPorts` | Outbound ports to bypass |
| `proxy.istio.io/config` | Arbitrary ProxyConfig overrides as YAML |

Mesh-wide equivalents live in `values.global.proxy.resources` at install time.

### 8. Sidecar log level

Baked in at injection time:

```bash
kubectl -n shop patch deployment httpbin -p '{
  "spec": {"template": {"metadata": {"annotations": {
    "sidecar.istio.io/logLevel": "debug"
  }}}}}'
kubectl -n shop rollout status deployment httpbin
kubectl -n shop logs deploy/httpbin -c istio-proxy --tail=20
```

Changed live, with no restart, which is what you actually want while debugging:

```bash
istioctl proxy-config log deploy/httpbin.shop --level debug

# Watch, then put it back
kubectl -n shop logs deploy/httpbin -c istio-proxy -f
istioctl proxy-config log deploy/httpbin.shop --level info
```

Per-component, to avoid drowning in output:

```bash
istioctl proxy-config log deploy/httpbin.shop --level router:debug,connection:debug
istioctl proxy-config log deploy/httpbin.shop --level rbac:debug   # authorization decisions
```

Levels are `trace`, `debug`, `info`, `warning`, `error`, `critical`, `off`. `rbac:debug` is the one that tells you why an `AuthorizationPolicy` denied a request, and it is invaluable in `25.md` and `26.md`.

Read the current levels:

```bash
istioctl proxy-config log deploy/httpbin.shop
```

### 9. Exclude a CIDR from interception

```bash
kubectl -n shop patch deployment httpbin -p '{
  "spec": {"template": {"metadata": {"annotations": {
    "traffic.sidecar.istio.io/excludeOutboundIPRanges": "10.96.0.0/12"
  }}}}}'
kubectl -n shop rollout status deployment httpbin
```

Verify by reading the iptables setup recorded on the pod:

```bash
kubectl -n shop get pod -l app=httpbin \
  -o jsonpath='{.items[0].metadata.annotations}' | jq
```

Traffic to that range now leaves the pod directly, bypassing Envoy entirely. Consequences you should be able to state: no mTLS, no telemetry, no routing rules, and no authorization for that traffic. It is a legitimate tool for things like a cloud metadata endpoint or a database that must not be proxied, but it is a hole in the mesh.

The inverse, capture only these ranges and let everything else out directly:

```yaml
annotations:
  traffic.sidecar.istio.io/includeOutboundIPRanges: "10.244.0.0/16"
```

Port-based versions:

```yaml
annotations:
  traffic.sidecar.istio.io/excludeInboundPorts: "9000,9001"
  traffic.sidecar.istio.io/excludeOutboundPorts: "3306"
```

Excluding inbound port 3306 for a database sidecar is a common real-world example.

### 10. Sidecar stuck, pod at 1/2

Work through it methodically.

```bash
kubectl -n shop get pods
kubectl -n shop describe pod <pod>
kubectl -n shop logs <pod> -c istio-proxy
```

The realistic causes, in rough order of likelihood:

**Cannot reach istiod.** The log shows connection failures to `istiod.istio-system.svc:15012`.

```bash
kubectl -n shop logs <pod> -c istio-proxy | grep -iE 'connect|xds|warn|error'
kubectl -n istio-system get pods -l app=istiod
kubectl -n istio-system get svc istiod
# Is a NetworkPolicy blocking 15012?
kubectl get networkpolicy -A
```

**Readiness probe failing.** The proxy readiness endpoint is port `15021`, path `/healthz/ready`.

```bash
kubectl -n shop exec <pod> -c istio-proxy -- \
  curl -sS -o /dev/null -w "%{http_code}\n" localhost:15021/healthz/ready
```

`200` means ready. Anything else, read the body:

```bash
kubectl -n shop exec <pod> -c istio-proxy -- curl -sS localhost:15021/healthz/ready
```

**Certificate problem.** The proxy cannot get an identity, usually a ServiceAccount token issue.

```bash
istioctl proxy-config secret <pod>.shop
kubectl -n shop logs <pod> -c istio-proxy | grep -i -E 'cert|ca|sds'
```

**Version skew.** The proxy image is from a different Istio version than istiod.

```bash
kubectl -n shop get pod <pod> -o jsonpath='{.spec.containers[?(@.name=="istio-proxy")].image}{"\n"}'
istioctl version
```

**Wrong revision label, pointing at a control plane that does not exist.**

```bash
kubectl get ns shop --show-labels
istioctl tag list
```

The umbrella command that checks several of these at once:

```bash
istioctl x describe pod <pod> -n shop
istioctl analyze -n shop
```

### 11. Namespace labelled but pods still 1/1

The diagnostic order that finds it fastest:

```bash
# 1. Is the label exactly right? Typos are common.
kubectl get ns shop --show-labels
# want istio-injection=enabled, not istio-injected, not istio-injection=true
```

`istio-injection=true` is **wrong**; the value must be `enabled`. That typo is a favourite exam sabotage because the label looks plausible.

```bash
# 2. Does the webhook exist and is it healthy?
kubectl get mutatingwebhookconfiguration istio-sidecar-injector
kubectl -n istio-system get pods -l app=istiod

# 3. Is a pod-level override defeating it?
kubectl -n shop get pod <pod> -o jsonpath='{.metadata.labels}' | jq
kubectl -n shop get deploy <name> -o jsonpath='{.spec.template.metadata}' | jq

# 4. Is the webhook's namespaceSelector actually matching?
kubectl get mutatingwebhookconfiguration istio-sidecar-injector \
  -o jsonpath='{range .webhooks[*]}{.name}{": "}{.namespaceSelector}{"\n"}{end}'

# 5. Revisioned install, and the namespace uses the wrong label?
kubectl get ns shop --show-labels
istioctl tag list
kubectl get mutatingwebhookconfiguration | grep sidecar

# 6. Were the pods created before the label was applied?
kubectl -n shop get pods -o custom-columns='NAME:.metadata.name,AGE:.metadata.creationTimestamp'
kubectl get ns shop -o jsonpath='{.metadata.managedFields[*].time}{"\n"}'
```

Cause 6 is by far the most common, and the fix is `kubectl rollout restart`.

Two more that appear in practice:

```bash
# hostNetwork pods are never injected
kubectl -n shop get pod <pod> -o jsonpath='{.spec.hostNetwork}{"\n"}'

# istiod rejected the request; the reason is in istiod's log
kubectl -n istio-system logs deploy/istiod | grep -i inject
```

And `analyze` will just tell you:

```bash
istioctl analyze -n shop
```

```text
Info [IST0102] (Namespace shop) The namespace is not enabled for Istio injection...
```

### 12. A Job that can complete

The classic problem: with a traditional sidecar, the app container finishes but Envoy keeps running, so the pod never reaches `Completed` and the Job hangs forever.

Modern answer, native sidecars. On Kubernetes 1.29+ with Istio 1.26, `istio-proxy` is injected as an init container with `restartPolicy: Always`, and the kubelet terminates it once the main containers exit. Jobs then work with no special handling.

```bash
kubectl -n shop apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: fetch
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: fetch
          image: curlimages/curl
          command: ["curl", "-sS", "-o", "/dev/null", "-w", "%{http_code}\n",
                    "http://httpbin.shop:8000/get"]
EOF

kubectl -n shop wait --for=condition=complete job/fetch --timeout=120s
kubectl -n shop get job fetch
kubectl -n shop logs job/fetch -c fetch
```

Confirm the native sidecar shape:

```bash
kubectl -n shop get pod -l job-name=fetch \
  -o jsonpath='{.items[0].spec.initContainers[*].name}{"\n"}'
kubectl -n shop get pod -l job-name=fetch -o json \
  | jq '.items[0].spec.initContainers[] | select(.name=="istio-proxy") | .restartPolicy'
```

```text
"Always"
```

If native sidecars are unavailable, the fallbacks, in descending order of preference:

```yaml
# a. Keep the Job out of the mesh entirely
template:
  metadata:
    labels:
      sidecar.istio.io/inject: "false"
```

```bash
# b. Have the app tell Envoy to quit when it is done
curl -sS -X POST http://localhost:15020/quitquitquit
```

```yaml
# c. Wait for the proxy before starting, so short jobs do not race it
metadata:
  annotations:
    proxy.istio.io/config: |
      holdApplicationUntilProxyStarts: true
```

Option (a) is usually the right answer in an exam if the Job needs no mesh features. If the Job must call a meshed service under mTLS, it needs to be in the mesh, and then native sidecars or `/quitquitquit` is the answer.

## Exam Tips

**Label, then restart. Always both.** If a task says "add this namespace to the mesh", it is not done until existing pods are `2/2`. `kubectl rollout restart deployment -n <ns>` is the second half of the answer and it is where the points are.

**The label value is `enabled`, not `true`.** `istio-injection=true` silently does nothing. Check with `kubectl get ns --show-labels` whenever injection "isn't working".

**Pod-level settings go on `spec.template.metadata`, not on the Deployment's own metadata.** Annotating the Deployment object itself has no effect on the pods it creates. This is an easy point to lose and easy to check.

**Quote boolean-looking label values.** `sidecar.istio.io/inject: "false"`. Unquoted, YAML makes it a boolean and Kubernetes rejects it.

**`istio-injection=enabled` overrides `istio.io/rev`.** During a revisioned upgrade, remove the plain label when you add the revision label:

```bash
kubectl label ns demo istio-injection- istio.io/rev=1-26-0 --overwrite
```

The trailing hyphen deletes a label. Know that syntax; it is faster than editing YAML.

**`2/2` is your success signal, and `istioctl proxy-status` is your authority.** A pod that appears in `proxy-status` is genuinely in the mesh and talking to istiod. A pod with two containers that does not appear there has a proxy that cannot reach the control plane.

**For a proxy that will not become ready, check `localhost:15021/healthz/ready` first.** It usually names the problem directly, and it is much faster than reading the whole proxy log.

**`istioctl proxy-config log --level rbac:debug` when authorization is mysteriously denying requests.** It changes live, needs no restart, and prints the matched policy. Remember to set it back to `info`.

**Jobs and sidecars:** if a Job hangs at `1/2` after the work is done, either exclude it from the mesh or rely on native sidecars. Knowing that this is a known category of problem, and naming `restartPolicy: Always` init containers as the modern fix, is what the exam is testing.
