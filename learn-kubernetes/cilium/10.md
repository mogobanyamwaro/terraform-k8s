# 10. Kubernetes NetworkPolicy vs CiliumNetworkPolicy

**Domain:** Network Policy (18%)

## Concept Refresher

Cilium **implements** `networking.k8s.io/v1` **NetworkPolicy**. You can keep stock YAML.

**CiliumNetworkPolicy** / **CiliumClusterwideNetworkPolicy** add what Kubernetes NP cannot:

| Feature | NetworkPolicy | CNP / CCNP |
| --- | --- | --- |
| Pod selector + ns selector + L4 ports | Yes | Yes |
| L7 HTTP/gRPC/Kafka | No | Yes |
| DNS / FQDN egress | No | Yes |
| Entities (world, host, remote-node) | No (CIDRs instead) | Yes |
| Node selectors / host firewall | No | Yes (CCNP) |
| Cluster-wide single object | No (per ns) | **CCNP** |
| Explicit deny | No (only allow-lists) | Yes (`ingressDeny`) |
| Service selectors `toServices` | No | Yes |
| CIDR | Yes (`ipBlock`) | Yes (`fromCIDR`) |

Kubernetes NP is **allow-list only**. There is no deny rule. Cilium deny rules can override allows.

### Intent interpretation

Exam questions show a YAML snippet and ask “what is allowed?”. Walk:

1. Who is selected?
2. Which direction?
3. Default deny now?
4. Which peers/ports/L7?

### Mixing

A pod can be selected by both NP and CNP. Cilium **intersects** (most restrictive combination). Do not assume NP is ignored.

## Hands-on

Apply a standard NP isolating httpbin, then a CNP allowing GET only. Observe Hubble drops for POST.

## Exam tips

- Cilium **understands** NetworkPolicy. Extra power = **CNP/CCNP**.
- NP = L3/L4 allow lists. Anything L7/DNS/entity/node/deny/clusterwide → Cilium CRD.
- Combined policies = more deny, not “CNP wins and ignores NP.”
