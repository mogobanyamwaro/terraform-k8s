# 19. Cluster Mesh Benefits

**Domain:** Cluster Mesh (10%)

## Concept Refresher

**Cluster Mesh** connects **two or more Cilium clusters** so that:

- Identities and endpoints are known across clusters
- **Global Services** load-balance to backends in multiple clusters
- Hubble can show cross-cluster flows (with Relay)
- NetworkPolicy can use **cluster** label / remote identities

This is **not** Kubernetes Federation, not kube-federation, not simply running `kubectl` with two contexts. Control planes stay **separate**. Cilium syncs network state via **clustermesh-apiserver** / KVStore.

### Why platforms want it

- HA across regions: if cluster A dies, Service still has endpoints in B
- Isolation: blast radius per cluster, shared services
- Migration: drain A while B serves
- Locality: prefer local backends, fail over remote

### Requirements (preview of `20.md`)

- Unique **cluster-name** and **cluster-id** (1–255)
- **Non-overlapping Pod CIDRs**
- IP connectivity between nodes (or tunnels) as designed
- Same Cilium major compatibility
- Trust (certificates) between clustermesh APIs

## Hands-on

Single-cluster lab cannot fully mesh. Read `cilium clustermesh --help` and the Cluster Mesh docs headings so the verbs look familiar.

```bash
cilium clustermesh --help
```

## Exam tips

- **Two clusters, two API servers, one Cilium network fabric.**
- **cluster-id unique, CIDRs disjoint.**
- Global Services are the load-balancing payoff (`20.md`).
