# Cilium Certified Associate (CCA) Practice

This folder mirrors the flat `learn-kubernetes/kubernetes` (CKA), `kubernetes-security`, `prometheus`, and `istio` layout, but targets the **CCA** exam.

Outline checked against the Linux Foundation CCA certification page and the CNCF CCA page on 2026-08-19.

## Important: CCA Is Not Like CKA or ICA

| | CKA / CKS / ICA | PCA / **CCA** |
| --- | --- | --- |
| Format | Performance-based, live terminal | **Multiple choice**, online proctored |
| Questions | 15–20 tasks | **60 questions** |
| Duration | 2 hours | **90 minutes** |
| Passing score | 66% / 67% / 68% | **75%** (45 of 60) |
| Docs allowed | Yes | **No. Closed book** |
| Validity | 2 years | 2 years |
| Cost | Varies | 250 USD, one free retake |
| Scheduling window | 12 months | 12 months |
| Results | 24 hours | 24 hours |
| Proctor platform | PSI | PSI |

CCA is the closest sibling to **PCA** and **KCNA**, not CKA. You cannot open `docs.cilium.io` during the exam. Every file here has an **Exam tips / Memorise** section for that reason.

Budget roughly **90 seconds per question**. Flag anything that takes longer and come back.

Official MC exam instructions: 60 questions, 90 minutes, 75% pass. See [Multiple Choice Important Instructions](https://docs.linuxfoundation.org/tc-docs/certification/important-instructions-mc) and [FAQ](https://docs.linuxfoundation.org/tc-docs/certification/faq-mc).

## Numbers And Defaults You Must Know Cold

| Thing | Default / Value |
| --- | --- |
| Default datapath (typical install) | **VXLAN tunnel** overlay |
| Alternate tunnel | Geneve |
| Default IPAM (self-managed) | **cluster-pool** |
| kube-proxy replacement | Off unless you enable it |
| Encryption options | **WireGuard** or **IPsec** (not both) |
| Default policy | Allow all until a policy **selects** the endpoint |
| After a policy selects an endpoint | Default **deny** for that direction |
| Cluster Mesh `cluster-id` | Integer **1–255**, unique per cluster |
| Global service annotation | `service.cilium.io/global: "true"` |
| Hubble CLI | `hubble observe` |
| Connectivity test | `cilium connectivity test` |
| Status | `cilium status` / `cilium status --wait` |
| Agent | DaemonSet, one per node |
| Operator | Deployment, HA |
| Reserved identity `world` | Outside the cluster |
| Reserved identity `host` | The local node |
| Reserved identity `remote-node` | Other cluster nodes |
| Cilium namespace (typical) | `kube-system` |

## Universal CCA Reasoning Flow

```text
1. Is this about the kernel datapath or the control plane?
   eBPF / identity / Hubble flow  -> agent + maps
   IPAM pool, Cluster Mesh API, identity GC -> operator

2. Is this Kubernetes NetworkPolicy or CiliumNetworkPolicy?
   labels + ingress/egress ports only -> both can do it
   L7, DNS, entities, FQDN, clusterwide, deny, node selector
     -> Cilium CRDs only

3. Overlay or native?
   pods on an overlay UDP port (VXLAN 8472 / Geneve 6081) -> tunnel
   pod CIDR routed on the underlay / BGP -> native

4. Sidecar or not?
   Cilium mesh is sidecarless: eBPF on the node + optional node Envoy
   Istio default is per-pod sidecar

5. Hubble L3/L4 vs L7
   L3/L4 flows always (if Hubble enabled)
   HTTP methods/paths need L7 visibility (proxy or policy)
```

## Cilium Truths To Remember

- Cilium is a **CNI**, a **NetworkPolicy** implementation, a **kube-proxy replacement**, an **observability** platform (Hubble), and a **sidecarless service mesh**. Exam questions often ask which of those hats is in play.
- **Identities**, not IPs, are the security unit. IPs change; labels become numeric identities in eBPF maps.
- The **agent** programs the kernel. The **operator** does cluster-wide jobs (IPAM, GC, Cluster Mesh pieces).
- **No policy selecting you = allow.** First selecting policy = default deny for that traffic direction. Same idea as Istio AuthorizationPolicy, different product.
- Hubble sees what eBPF sees. If L7 fields are empty, you have not enabled L7 visibility.
- Cluster Mesh needs **unique cluster-id**, **non-overlapping Pod CIDRs**, and connectivity between nodes/API.
- eBPF beats iptables because it is **O(1) map lookups**, not a growing linear chain of rules.
