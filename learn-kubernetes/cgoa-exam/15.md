# 15. Architecture: Reconcilers and State Store Management

**Domain:** GitOps Patterns (20%)

## Concept Refresher

**In-cluster reconciler:** Argo CD, Flux, operators running **inside** the target cluster (or a management cluster that applies to many). They use in-cluster credentials, pull Git, apply.

**External reconciler:** process **outside** the cluster (SaaS GitOps, a central management cluster, a pipeline runner). Can still be GitOps **if it pulls** declarations and reconciles continuously. If it only pushes on events, it is not.

**Management cluster:** one cluster hosts Argo/Flux that deploys to **many** workload clusters (Argo CD application in `destination` cluster). Agents still pull Git; kubeconfig/secrets live in the management cluster.

**State store management:**

- Protect `main` / `prod` with branch protection, CODEOWNERS, required reviews, signed commits (optional)
- Separate **app source** repos from **desired-state/config** repos (common)
- Environments as directories/overlays, not unreviewed hotfixes
- Break-glass: documented, audited, then **Git updated** so the store wins again

**Repo patterns:** monorepo vs polyrepo; App-of-Apps / root Kustomization; environment overlays.

## Hands-on

`kubectl scale` a lab app, then commit the same replica count to Git (or revert Git). Break-glass without the commit is what self-heal fights.

## Exam tips

- **In-cluster vs external** = *where the agent runs*, not push vs pull.
- Management cluster is still pull GitOps.
- After break-glass, **commit**.
