# 39. Troubleshooting The Alerting Pipeline

**Domain:** Alerting and Dashboarding

## Concept Refresher

"The alert did not fire" and "the alert fired but nobody got paged" are different problems with different diagnostic paths. Learn the pipeline as a checklist and you can answer any scenario question in this domain.

```text
┌──────────────────────────────────────────────────────────────────────┐
│ 1. Is the DATA there?                                                │
│    /targets up==1, series exists, query returns a value              │
├──────────────────────────────────────────────────────────────────────┤
│ 2. Is the RULE loaded?                                               │
│    /rules shows it, health=ok, rule_files glob matched               │
├──────────────────────────────────────────────────────────────────────┤
│ 3. Is the EXPRESSION true?                                           │
│    Run it in the expression browser. Does it return series?          │
├──────────────────────────────────────────────────────────────────────┤
│ 4. Has `for` elapsed?                                                │
│    ALERTS{alertstate="pending"} vs "firing"                          │
├──────────────────────────────────────────────────────────────────────┤
│ 5. Did Prometheus SEND it?                                           │
│    /api/v1/alerts, prometheus_notifications_* metrics                │
├──────────────────────────────────────────────────────────────────────┤
│ 6. Did Alertmanager RECEIVE it?                                      │
│    /api/v2/alerts, alertmanager_alerts_received_total                 │
├──────────────────────────────────────────────────────────────────────┤
│ 7. Is it SUPPRESSED?                                                 │
│    status.state == suppressed, silencedBy, inhibitedBy, mute windows │
├──────────────────────────────────────────────────────────────────────┤
│ 8. Did it ROUTE correctly?                                           │
│    amtool config routes test <labels>                                │
├──────────────────────────────────────────────────────────────────────┤
│ 9. Are we WAITING on a timer?                                        │
│    group_wait / group_interval / repeat_interval                     │
├──────────────────────────────────────────────────────────────────────┤
│10. Did the NOTIFICATION deliver?                                     │
│    alertmanager_notifications_failed_total, AM logs                  │
└──────────────────────────────────────────────────────────────────────┘
```

### Layer 1: is the data there?

```bash
curl -s http://localhost:9090/api/v1/targets | jq -r '.data.activeTargets[] | select(.health!="up") | "\(.scrapePool) \(.scrapeUrl) \(.health) \(.lastError)"'
```

```promql
up == 0
absent(up{job="myapp"})
myapp_http_requests_total
scrape_samples_scraped == 0
```

Common causes: target never discovered (check `/service-discovery`), relabeling dropped it, wrong `metrics_path`, wrong port, TLS failure, `sample_limit` exceeded, or scrape timeout.

```promql
scrape_duration_seconds > 5
prometheus_target_scrapes_exceeded_sample_limit_total
prometheus_target_scrapes_sample_duplicate_timestamp_total
```

### Layer 2: is the rule loaded?

```bash
curl -s http://localhost:9090/api/v1/rules | jq -r '.data.groups[] | "\(.file) :: \(.name)", (.rules[] | "   \(.name) health=\(.health) err=\(.lastError // "-")")'
```

Failure modes:

| Symptom | Cause |
| --- | --- |
| Rule not listed at all | `rule_files` glob does not match the file, or Prometheus was not reloaded |
| `health: err` | The expression failed, e.g. a type error or exceeded `limit` |
| `health: unknown` | Not yet evaluated |
| Config reload silently ignored | Reload failed; check `prometheus_config_last_reload_successful` |

```promql
prometheus_config_last_reload_successful
prometheus_config_last_reload_success_timestamp_seconds
```

A reload that fails leaves the **old** config running. That is why the metric matters: Prometheus keeps working, so nothing looks broken.

### Layer 3: is the expression true?

Run it verbatim in `/graph`. The most common reasons a correct-looking expression returns nothing:

| Cause | Example |
| --- | --- |
| Label mismatch in a binary op | Two vectors with different label sets produce an empty result |
| `rate()` window shorter than 2 scrape intervals | `rate(x[15s])` with a 15s interval |
| The series does not exist | Metric renamed, job renamed, relabeled away |
| Comparison filtered everything | `up == 0` when everything is up, which is correct but confusing |
| A typo in a label value | `code=~"5.."` versus `status=~"5.."` |
| Regex not anchored as expected | `job=~"api"` matches only exactly `api` |
| Staleness | The series went stale more than 5m ago |

Diagnose binary-op label mismatches by inspecting both sides:

```promql
count(left_side)
count(right_side)
count(left_side) - count(right_side)
left_side unless right_side          # what is on the left but not the right
right_side unless left_side
```

### Layer 4: has `for` elapsed?

```promql
ALERTS
ALERTS{alertname="MyAlert"}
ALERTS{alertname="MyAlert", alertstate="pending"}
time() - ALERTS_FOR_STATE{alertname="MyAlert"}
```

If it is stuck in `pending`, the expression is flapping. Prove it:

```promql
changes(     ( (up == 0) or vector(0) )[1h:1m] )
count_over_time(ALERTS{alertname="MyAlert", alertstate="pending"}[1h])
count_over_time(ALERTS{alertname="MyAlert", alertstate="firing"}[1h])
```

Remember: **the `for` timer resets** on any evaluation where the expression stops matching.

### Layer 5: did Prometheus send it?

```bash
curl -s http://localhost:9090/api/v1/alerts | jq -r '.data.alerts[] | "\(.labels.alertname) \(.state) \(.activeAt)"'
```

```promql
prometheus_notifications_alertmanagers_discovered
rate(prometheus_notifications_sent_total[5m])
rate(prometheus_notifications_errors_total[5m])
rate(prometheus_notifications_dropped_total[5m])
prometheus_notifications_queue_length
prometheus_notifications_queue_capacity
prometheus_notifications_queue_length / prometheus_notifications_queue_capacity
```

| Metric non-zero | Meaning |
| --- | --- |
| `alertmanagers_discovered == 0` | Prometheus has no Alertmanager. Check the `alerting:` block and DNS/SD |
| `notifications_errors_total` | Prometheus reached Alertmanager but the POST failed |
| `notifications_dropped_total` | The queue overflowed. Too many alerts, or Alertmanager too slow |
| `queue_length` near capacity | Backpressure building |

### Layer 6: did Alertmanager receive it?

```bash
curl -s http://localhost:9093/api/v2/alerts | jq -r '.[] | "\(.labels.alertname) state=\(.status.state)"'
```

```promql
rate(alertmanager_alerts_received_total[5m])
alertmanager_alerts_invalid_total
alertmanager_alerts
```

`alertmanager_alerts_invalid_total` rising means malformed alerts, usually a labelling problem from a non-Prometheus source.

### Layer 7: is it suppressed?

This is the single most common "the alert fired but nobody was paged" cause.

```bash
curl -s http://localhost:9093/api/v2/alerts \
  | jq -r '.[] | "\(.labels.alertname) state=\(.status.state) silencedBy=\(.status.silencedBy) inhibitedBy=\(.status.inhibitedBy)"'
```

```bash
amtool silence query
amtool silence query --expired
```

```promql
alertmanager_alerts{state="suppressed"}
alertmanager_silences{state="active"}
```

Three suppression sources to check in order:

1. **A silence** somebody forgot to expire. `silencedBy` will be populated.
2. **An inhibition rule**, often one missing `equal` and therefore suppressing far more than intended. `inhibitedBy` will be populated.
3. **A mute time interval**, which does **not** show as `suppressed`; the alert looks active but no notification goes out. Check `mute_time_intervals` on the matched route.

That third case is nasty precisely because the API shows the alert as active.

### Layer 8: did it route correctly?

```bash
amtool config routes show
amtool config routes test severity=critical team=database
amtool config routes test --verify.receivers=pager severity=critical
```

Routing mistakes to look for:

| Mistake | Effect |
| --- | --- |
| A broad route earlier in the list | Swallows alerts before a specific route is reached |
| Missing `continue: true` | An alert reaches only the first matching receiver |
| Typo in a matcher value | Alert falls through to the root receiver |
| Regex not anchored as expected | `severity=~"crit"` matches nothing |
| Route to an empty receiver | Alert intentionally dropped, easy to forget |
| Child route inherits an unexpected `receiver` | A child without its own `receiver` uses the parent's |

Remember sibling order matters and **the first match wins**, then matching descends into children.

### Layer 9: are we waiting on a timer?

```text
new group           -> wait group_wait (30s default)
group changed       -> wait until the next group_interval (5m default)
group unchanged     -> next notification at repeat_interval (4h default)
```

Symptoms and causes:

| Symptom | Cause |
| --- | --- |
| First notification took 30 seconds | `group_wait`. Normal |
| A new instance joining an existing group did not notify for minutes | `group_interval`. Normal, and surprising |
| Reminder notifications every 4 hours | `repeat_interval`. Normal |
| Notifications every 30 seconds for one incident | `group_by` is too granular, or `group_by: ['...']` |
| One notification for 200 unrelated alerts | `group_by: []` or too coarse |

```bash
curl -s http://localhost:9093/api/v2/alerts/groups \
  | jq -r '.[] | "receiver=\(.receiver.name) labels=\(.labels) count=\(.alerts|length)"'
```

### Layer 10: did the notification deliver?

```promql
sum by (integration) (rate(alertmanager_notifications_total[5m]))
sum by (integration) (rate(alertmanager_notifications_failed_total[5m]))
histogram_quantile(0.99, sum by (le, integration) (rate(alertmanager_notification_latency_seconds_bucket[5m])))
```

```bash
docker logs alertmanager --tail 50 | grep -i 'error\|failed\|notify'
```

Delivery failures are otherwise **completely silent** to the user. If you take one operational lesson from this domain, it is to alert on `alertmanager_notifications_failed_total`.

### The HA-specific failure modes

| Symptom | Cause |
| --- | --- |
| Duplicate notifications | Alertmanagers not clustered (`--cluster.peer` missing), so they cannot share the nflog |
| Duplicate notifications with different content | Cluster members have **different configs**. Check `alertmanager_config_hash` |
| Duplicate alerts with different labels | Prometheus HA pair not dropping the `replica` label in `alert_relabel_configs` |
| Alerts stop when one AM dies | Prometheus configured with only one Alertmanager, or a load balancer in front |
| Silences not applying | Cluster not gossiping; check `alertmanager_cluster_members` and `alertmanager_cluster_health_score` |

```promql
alertmanager_cluster_members
alertmanager_cluster_health_score            # 0 is healthy
alertmanager_cluster_failed_peers
count by (job) (count by (job, hash) (alertmanager_config_hash))    # > 1 means divergence
```

### Symptom-to-cause quick table

Memorise this. It is the fastest way to answer a scenario question.

| Symptom | Most likely cause | First check |
| --- | --- | --- |
| Alert never appears in Prometheus | Rule not loaded, or expression returns nothing | `/rules`, then run the expression |
| Alert stuck `pending` | Expression flapping, so `for` keeps resetting | `count_over_time(ALERTS{...}[1h])` |
| Alert firing in Prometheus, absent in Alertmanager | Connectivity, or no Alertmanager configured | `prometheus_notifications_*` |
| Alert in Alertmanager, no notification | Silence, inhibition, or mute interval | `status.state`, `silencedBy`, `inhibitedBy` |
| Alert routes to the wrong receiver | Sibling order, or a matcher typo | `amtool config routes test` |
| Notification is late by ~30s | `group_wait` | Normal |
| Notification is late by minutes | `group_interval` | Normal |
| Repeated identical notifications every 4h | `repeat_interval` | Normal |
| Duplicate notifications | AMs not clustered, or `replica` label not dropped | `alertmanager_cluster_members` |
| Notification never arrives at all | Receiver delivery failure | `alertmanager_notifications_failed_total`, AM logs |
| Alert never resolves | Expression still matching, or `keep_firing_for` | Run the expression |
| Alert resolved but should still fire | Series went stale or target vanished | `absent()`, `/targets` |
| Everything fires after a restart | Pending state not restored | `--rules.alert.for-outage-tolerance` |
| No alerts at all, and no errors | Prometheus down. Nothing can fire | The Watchdog |

**Q4: B.** Evaluation failure.

**Q6: B.** Counting pending samples over a window.

**Q7: B.** The notification path metrics.

**Q8: B.** Queue overflow.

**Q9: B.** An active silence.

**Q10: C.** Mute time intervals suppress the notification without marking the alert suppressed.

**Q11: B.** It looks perfectly healthy in the API.

**Q12: B.** Missing `equal`.

**Q13: B.** `amtool config routes test`.

**Q14: B.** A matcher typo means no child matches, so the root receiver is used.

**Q15: B.** `continue: true`.

**Q16: B.** First match wins among siblings.

**Q17: B.** `group_interval`.

**Q18: B.** `repeat_interval`, default 4h.

**Q19: B.** Not clustered, so no shared nflog.

**Q20: B.** Config divergence. Counting distinct hashes per job detects it.

**Q21: B.** Drop `replica` so both servers emit identical alerts.

**Q22: B.** `alertmanager_notifications_failed_total`. Delivery failure is otherwise invisible.

## Hands-on

Break the pipeline deliberately, one layer at a time, and diagnose each break using only the checklist. This is the most valuable exercise in the folder.

Start with a known-good baseline:

```bash
curl -s http://localhost:9090/-/healthy && echo " prometheus ok"
curl -s http://localhost:9093/-/healthy && echo " alertmanager ok"
python3 ~/pca-lab/sink.py &
docker stop demo-b && sleep 90
curl -s http://localhost:9093/api/v2/alerts | jq -r '.[] | "\(.labels.alertname) \(.status.state)"'
```

### Break 1: rule file not matched by the glob

```bash
mv ~/pca-lab/rules/alerts.yml ~/pca-lab/rules/alerts.yaml     # .yaml, not .yml
curl -X POST http://localhost:9090/-/reload
```

Diagnose using layer 2:

```bash
curl -s http://localhost:9090/api/v1/rules | jq -r '.data.groups[].name'
```

The groups are gone. The rules are not loaded at all. Note that `promtool check rules` on the file would pass, because the file is fine; the **glob** is wrong.

```bash
curl -s http://localhost:9090/api/v1/status/config | jq -r '.data.yaml' | grep -A3 rule_files
mv ~/pca-lab/rules/alerts.yaml ~/pca-lab/rules/alerts.yml
curl -X POST http://localhost:9090/-/reload
```

### Break 2: a failed reload leaves the old config running

```bash
cp ~/pca-lab/prometheus/prometheus.yml /tmp/prom.bak
echo "this: is: not: valid: yaml:" >> ~/pca-lab/prometheus/prometheus.yml
curl -X POST http://localhost:9090/-/reload
```

Note the reload returns an error, but Prometheus **keeps working**:

```promql
prometheus_config_last_reload_successful
time() - prometheus_config_last_reload_success_timestamp_seconds
up
```

`prometheus_config_last_reload_successful` is 0, yet everything still scrapes and alerts. **This is why you must alert on that metric.** Anyone checking "is Prometheus up?" would see a healthy system running a stale config.

```bash
cp /tmp/prom.bak ~/pca-lab/prometheus/prometheus.yml
promtool check config ~/pca-lab/prometheus/prometheus.yml
curl -X POST http://localhost:9090/-/reload
```

```promql
prometheus_config_last_reload_successful
```

### Break 3: an expression that silently returns nothing

Add a rule with a deliberate label typo:

```yaml
      - alert: TypoAlert
        expr: |
          sum by (job) (rate(myapp_http_requests_total{status=~"5.."}[5m]))
            / sum by (job) (rate(myapp_http_requests_total[5m])) > 0.05
        for: 1m
        labels:
          severity: critical
```

The label is `code`, not `status`.

```bash
curl -X POST http://localhost:9090/-/reload
curl -s http://localhost:9090/api/v1/rules | jq -r '.data.groups[].rules[] | select(.name=="TypoAlert") | "health=\(.health) state=\(.state) alerts=\(.alerts|length)"'
```

Health is `ok` and state is `inactive`. **Nothing indicates a problem.** Diagnose by decomposing:

```promql
sum by (job) (rate(myapp_http_requests_total{status=~"5.."}[5m]))
count(myapp_http_requests_total{status=~"5.."})
count(myapp_http_requests_total)
```

The numerator is empty. Find the real label name:

```bash
curl -s -G http://localhost:9090/api/v1/series \
  --data-urlencode 'match[]=myapp_http_requests_total' | jq -r '.data[0] | keys[]'
```

Or:

```promql
count by (code) (myapp_http_requests_total)
```

This is the most common real-world alerting bug: an expression that is syntactically valid, evaluates cleanly, and always returns nothing.

### Break 4: a rate window shorter than two scrape intervals

```promql
rate(myapp_http_requests_total[5s])
rate(myapp_http_requests_total[10s])
rate(myapp_http_requests_total[15s])
rate(myapp_http_requests_total[1m])
```

With a 5s scrape interval on the `myapp` job, `[5s]` returns nothing or is unreliable. Confirm the sample count per window:

```promql
count_over_time(myapp_http_requests_total[5s])
count_over_time(myapp_http_requests_total[15s])
count_over_time(myapp_http_requests_total[1m])
```

`rate()` needs at least 2. That is the mechanism behind blank Grafana graphs and dead alerts.

### Break 5: a label mismatch in a binary operation

```promql
# Deliberately mismatched: one side has a route label, the other does not
sum by (job, route) (rate(myapp_http_requests_total{code=~"5.."}[5m]))
  / sum by (job) (rate(myapp_http_requests_total[5m]))
```

Empty. Diagnose:

```promql
count(sum by (job, route) (rate(myapp_http_requests_total{code=~"5.."}[5m])))
count(sum by (job) (rate(myapp_http_requests_total[5m])))

sum by (job, route) (rate(myapp_http_requests_total{code=~"5.."}[5m]))
  unless sum by (job) (rate(myapp_http_requests_total[5m]))
```

Everything is unpaired. Fix with matching label sets, or `on()`/`group_left`:

```promql
sum by (job, route) (rate(myapp_http_requests_total{code=~"5.."}[5m]))
  / on (job) group_left
sum by (job) (rate(myapp_http_requests_total[5m]))
```

### Break 6: Prometheus cannot reach Alertmanager

```promql
prometheus_notifications_queue_length
```

Note `alertmanagers_discovered` may stay at 1 (it is still configured) while `errors_total` climbs. In Prometheus, alerts are still firing:


The alert exists; nobody is told. That is layer 5 failing.


### Break 7: a forgotten silence

```bash
AM="docker exec alertmanager amtool --alertmanager.url=http://localhost:9093"
$AM silence add alertname=InstanceDown --duration=24h --comment="forgot to remove this" --author=someone
```

Now the classic scenario: the alert is firing in Prometheus, nobody is paged.

```promql
ALERTS{alertname="InstanceDown", alertstate="firing"}
```

Firing. But:

```bash
curl -s http://localhost:9093/api/v2/alerts \
  | jq -r '.[] | "\(.labels.alertname) state=\(.status.state) silencedBy=\(.status.silencedBy)"'
```

`suppressed`, with `silencedBy` populated. Find the culprit:

```bash
$AM silence query
curl -s http://localhost:9093/api/v2/silences | jq -r '.[] | select(.status.state=="active") | "\(.id) by=\(.createdBy) comment=\(.comment) until=\(.endsAt)"'
```

```promql
alertmanager_alerts{state="suppressed"}
alertmanager_silences{state="active"}
```

Remove it:

```bash
for s in $($AM silence query -q); do $AM silence expire "$s"; done
```

### Break 8: an over-broad inhibition rule

```yaml
inhibit_rules:
  - source_matchers:
      - severity = "critical"
    target_matchers:
      - severity = "warning"
    # equal deliberately omitted
```

```bash
curl -X POST http://localhost:9093/-/reload
curl -s -XPOST http://localhost:9093/api/v2/alerts -H 'Content-Type: application/json' -d '[{
  "labels": {"alertname":"CompletelyUnrelated","severity":"warning","cluster":"elsewhere","instance":"other-host"},
  "startsAt": "'$(date -u +%Y-%m-%dT%H:%M:%SZ)'"
}]'
sleep 5
curl -s http://localhost:9093/api/v2/alerts \
  | jq -r '.[] | "\(.labels.alertname) sev=\(.labels.severity) state=\(.status.state) inhibitedBy=\(.status.inhibitedBy)"'
```

`CompletelyUnrelated` is suppressed by an alert on a different host in a different cluster. `inhibitedBy` names the culprit fingerprint. Trace it back:

```bash
FP=$(curl -s http://localhost:9093/api/v2/alerts | jq -r '.[] | select(.labels.alertname=="CompletelyUnrelated") | .status.inhibitedBy[0]')
curl -s http://localhost:9093/api/v2/alerts | jq -r --arg fp "$FP" '.[] | select(.fingerprint==$fp) | .labels'
```

Restore `equal: ['instance']` and reload.

### Break 9: a mute time interval, the invisible suppression

```yaml
time_intervals:
  - name: always
    time_intervals:
      - times:
          - start_time: '00:00'
            end_time: '24:00'

route:
  routes:
    - receiver: pager
      matchers:
        - severity = "critical"
      mute_time_intervals: ['always']
```

```bash
curl -X POST http://localhost:9093/-/reload
docker stop demo-b ; sleep 90
curl -s http://localhost:9093/api/v2/alerts \
  | jq -r '.[] | "\(.labels.alertname) state=\(.status.state) silencedBy=\(.status.silencedBy) inhibitedBy=\(.status.inhibitedBy)"'
```

The alert shows **`active`**, with no `silencedBy` and no `inhibitedBy`. Nothing in the API suggests suppression. Yet the sink receives nothing.

```promql
alertmanager_alerts{state="suppressed"}
rate(alertmanager_notifications_total[5m])
```

`suppressed` is 0 and no notifications are being sent. The only way to find this is to inspect the route:

```bash
$AM config routes show
$AM config routes test severity=critical
```

Remove the mute interval and reload. Notifications resume. **Remember this scenario**; it is the hardest one on the list.

### Break 10: a routing order mistake

```yaml
route:
  receiver: default
  routes:
    # This broad route is FIRST, so it swallows everything
    - receiver: tickets
      matchers:
        - alertname =~ ".+"

    # Never reached
    - receiver: pager
      matchers:
        - severity = "critical"
```

```bash
curl -X POST http://localhost:9093/-/reload
$AM config routes test severity=critical
$AM config routes show
```

Every alert goes to `tickets`. Critical alerts never page. Fix by ordering specific routes first, or by adding `continue: true` to the broad one.

```bash

#!/usr/bin/env bash
P=http://localhost:9090

q() { curl -s -G "$P/api/v1/query" --data-urlencode "query=$1" | jq -r '.data.result[] | "\(.metric) \(.value[1])"'; }

echo "=== 5. RULE GROUPS OVERRUNNING"
```

## Exam tips

- Walk the pipeline in order: **data → rule loaded → expression true → `for` elapsed → sent → received → suppressed? → routed → timers → delivered.**
- A **failed reload leaves the old config running.** `prometheus_config_last_reload_successful == 0` is the only signal. Same for `alertmanager_config_last_reload_successful`.
- A rule missing from `/rules` means the **glob did not match** or there was **no reload**, not that the expression is wrong.
- `health: err` on a rule means **evaluation failure**, including an exceeded group `limit`.
- Stuck in **`pending`** means the expression is **flapping** and the `for` timer keeps resetting.
- A valid expression that always returns nothing is the most common real bug. Decompose it and check **label names** with `count by (label) (metric)`.
- `rate()` needs **at least two samples**; verify with `count_over_time(metric[window])`.
- Diagnose binary-op emptiness with **`unless`** and by counting each side.
- Firing in Prometheus but missing from Alertmanager: check **`prometheus_notifications_alertmanagers_discovered`**, `notifications_errors_total`, `notifications_dropped_total`, and the queue length.
- In Alertmanager but no notification: check **`status.state`**, **`silencedBy`**, **`inhibitedBy`**, then **mute time intervals**.
- **A mute time interval does not mark the alert `suppressed`.** The alert looks active and nothing is sent. Only the route reveals it.
- An over-broad inhibition rule almost always means a **missing `equal`**.
- Wrong receiver: check **sibling order (first match wins)**, matcher typos, and missing `continue: true`.
- ~30 second delay = `group_wait`. Minutes for an added instance = `group_interval`. Every 4 hours = `repeat_interval`.
- **Duplicate notifications = Alertmanagers not clustered.** Duplicates with different content = **divergent configs** (`alertmanager_config_hash`). Duplicate alerts with different labels = **`replica` not dropped**.
- Delivery failure is **silent**. Always alert on **`alertmanager_notifications_failed_total`**.
- An alert that resolves while the problem persists usually means the **series went stale or the target vanished**. Use `absent()`.
- No alerts and no errors at all: the **Watchdog** is the only thing that catches it.
- Tools: `promtool check config`, `promtool check rules`, `promtool test rules`, `amtool check-config`, `amtool config routes show`, **`amtool config routes test`**, `amtool silence query`.
