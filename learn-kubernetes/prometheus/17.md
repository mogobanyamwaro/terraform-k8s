# 17. Rates And Derivatives

**Domain:** PromQL

## Concept Refresher

This is the highest-value topic in the entire exam. Counters are useless raw; the rate functions are how you extract meaning.

### rate()

```promql
rate(http_requests_total[5m])
```

- Input: a **range vector** of a **counter**.
- Output: an **instant vector** of **per-second** average rate over the window.
- **Handles counter resets** automatically: if a value drops, the drop is treated as a reset and the counter is assumed to have continued from 0.
- **Extrapolates** to the window boundaries. If the window edges do not align with samples, Prometheus extrapolates, which is why results can be slightly non-integer.
- Needs **at least two samples** in the window. With fewer, the series is dropped from the result.
- Loses the `_total` suffix meaning; the result is a rate, so always label your graphs "per second".

The extrapolation detail: since Prometheus 2.x, if the first or last sample is close to the window boundary (within 110% of the average sample interval), Prometheus extrapolates to the boundary. Otherwise it extrapolates only halfway to the boundary. This is why `increase()` can return `1.0000000001` or `9.6` instead of a clean integer.

### irate()

```promql
irate(http_requests_total[5m])
```

- Uses **only the last two samples** in the window.
- Very responsive, shows spikes.
- **Do not use in alerting rules or slow-moving graphs.** Between samples it produces jagged, aliasing output, and it can miss activity entirely.
- The window here only bounds how far back to look for those two samples.

Rule of thumb: **`rate()` for alerts and dashboards, `irate()` only for short-range zoomed-in debugging of fast-moving counters.**

### increase()

```promql
increase(http_requests_total[1h])
```

- Exactly equivalent to `rate(x[1h]) * 3600`.
- Output is a **count over the window**, not per second.
- Same reset handling and extrapolation as `rate()`, so results may be non-integer.

### The range selection rule

**Always choose a range of at least 4 times the scrape interval.**

| Scrape interval | Minimum sane range | Typical choice |
| --- | --- | --- |
| 15s | 1m | 5m |
| 30s | 2m | 5m |
| 1m | 4m | 5m to 10m |

Why: you need at least two samples, and you want tolerance for a missed scrape. With a range of exactly two intervals, one failed scrape empties the result.

Symptom of too short a range: the graph shows gaps or the series disappears entirely.

### delta()

```promql
delta(cpu_temp_celsius[2h])
```

- For **gauges**. Difference between the first and last value in the window.
- **Does not** correct for resets, because gauges legitimately go down.
- Extrapolated, like `rate()`.
- Can be negative.

### idelta()

```promql
idelta(cpu_temp_celsius[5m])
```

- Difference between the **last two** samples only. The gauge analogue of `irate()`.

### deriv()

```promql
deriv(node_filesystem_avail_bytes[1h])
```

- For **gauges**. Per-second derivative computed by **simple linear regression** over all samples in the window.
- Much smoother and more robust than `delta()/window`, because it uses every sample.
- Units are "per second".

### predict_linear()

```promql
predict_linear(node_filesystem_avail_bytes[6h], 4 * 3600)
```

- Fits a linear regression over the range vector and **extrapolates `t` seconds into the future**.
- Second argument is in **seconds**.
- The canonical disk-full alert:

```promql
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4 * 3600) < 0
```

Read as: "based on the last 6 hours of trend, will this filesystem be empty within 4 hours?"

Best practice: combine with a current-usage guard to avoid alerting on tiny, noisy filesystems:

```promql
predict_linear(node_filesystem_avail_bytes{fstype!~"tmpfs"}[6h], 4*3600) < 0
  and
node_filesystem_avail_bytes / node_filesystem_size_bytes < 0.4
```

### resets() and changes()

```promql
resets(http_requests_total[1h])     # how many times a COUNTER reset (decreased)
changes(node_boot_time_seconds[1h]) # how many times a GAUGE's value changed
```

- `resets()` is for counters. A restarted process shows up here.
- `changes()` is for gauges. `changes(up[1h]) > 5` detects a flapping target.

### double_exponential_smoothing (formerly holt_winters)

```promql
double_exponential_smoothing(node_load1[10m], 0.3, 0.3)
```

- Smooths a gauge series. `sf` is the smoothing factor, `tf` the trend factor, both in `(0,1)`.
- Experimental. Renamed from `holt_winters` in Prometheus 3.0.
- Rarely examined, but recognise the name.

### The cardinal rate mistakes

**Mistake 1: sum before rate**

```promql
rate(sum(http_requests_total)[5m:])    # WRONG
sum(rate(http_requests_total[5m]))     # RIGHT
```

Summing raw counters merges series whose resets happen at different times. The sum then appears to drop, and the reset correction cannot recover the truth. **Always `rate()` first, then aggregate.**

**Mistake 2: avg of rate vs rate of avg**

```promql
avg(rate(x[5m]))            # average of per-series rates
rate(avg(x)[5m:])           # rate of an averaged counter. Almost always wrong
```

**Mistake 3: irate in an alert**

```promql
irate(errors_total[5m]) > 0    # WRONG: flaps, misses events
rate(errors_total[5m]) > 0     # RIGHT
```

**Mistake 4: range too short**

```promql
rate(x[15s])   # with a 15s scrape interval this yields at most one sample. Empty result
rate(x[1m])    # minimum viable
rate(x[5m])    # safe
```

**Mistake 5: rate on a gauge**

```promql
rate(node_memory_MemAvailable_bytes[5m])   # meaningless, no error raised
deriv(node_memory_MemAvailable_bytes[5m])  # correct if you want a slope
delta(node_memory_MemAvailable_bytes[5m])  # correct if you want the change
```

### Function selection table

| You have | You want | Use |
| --- | --- | --- |
| Counter | Per-second rate | `rate(x[5m])` |
| Counter | Total over window | `increase(x[1h])` |
| Counter | Instantaneous spike, debugging only | `irate(x[1m])` |
| Counter | How many restarts | `resets(x[1h])` |
| Gauge | Change over window | `delta(x[1h])` |
| Gauge | Per-second slope, smoothed | `deriv(x[1h])` |
| Gauge | Change between last two samples | `idelta(x[5m])` |
| Gauge | Future value | `predict_linear(x[6h], 3600)` |
| Gauge | How many times it changed | `changes(x[1h])` |
| Histogram bucket (counter) | Quantile | `histogram_quantile(0.9, rate(x_bucket[5m]))` |

## Answers

**Q1: B.** Per-second average rate over the window.

**Q2: B.** Reset detection is automatic. A decrease is interpreted as a restart, and the counter is assumed to have resumed from zero.

**Q3: B.** Two. With one sample the series is dropped from the output.

**Q4: B.** `increase(x[t])` is `rate(x[t]) * t_in_seconds`.

**Q5: B.** Extrapolation to the window boundaries. This is expected behaviour, documented, and the reason `increase()` output is a float.

**Q6: B.** Only the final two samples.

**Q7: B.** `irate()` is deliberately spiky. For alerting you want the smoothed average that `rate()` gives, otherwise alerts flap and short bursts between the last two samples are invisible.

**Q8: C.** At least 4x the scrape interval, so `2m`. `1m` gives only two samples with no tolerance for a missed scrape.

**Q9: B.** `rate()` first, then `sum()`.

**Q10: B.** Different instances reset at different times. The sum of raw counters shows a drop that reset correction cannot untangle, because it can no longer tell which component reset.

**Q11: B.** `deriv()` uses simple linear regression across every sample in the window.

**Q12: C.** `delta()`. `rate()` and `increase()` apply reset correction, which is wrong for a gauge that legitimately decreases.

**Q13: B.** Fit on the last 6 hours, extrapolate 4 hours forward.

**Q14: B.** Seconds. Hence the idiomatic `4 * 3600`.

**Q15: B.** `predict_linear` compared against zero. Option A only fires once the disk is already full, which is too late.

**Q16: B.** Counter decreases.

**Q17: B.** `changes()` on `up` counts transitions, which is the flapping-target idiom.

**Q18: B.** No error. Types are not enforced, so you get a silently wrong number. This is why the exam emphasises type discipline.

**Q19: C.** `idelta()`.

**Q20: B.** `double_exponential_smoothing`.

**Q21: B.** Too short a range. Widen it to at least 4x the scrape interval.

**Q22: B.** `increase()` over 24h. `rate()` would give per-second, and the raw counter is cumulative since start.

## Hands-on

Start with the fundamental comparison. Graph all three over 1 hour:

```promql
node_cpu_seconds_total{mode="idle", cpu="0"}
rate(node_cpu_seconds_total{mode="idle", cpu="0"}[5m])
irate(node_cpu_seconds_total{mode="idle", cpu="0"}[5m])
```

The raw counter is a straight ramp. `rate()` is smooth. `irate()` is jagged. Look at all three on one graph to make the point stick.

Prove `increase` is `rate * seconds`:

```promql
increase(node_cpu_seconds_total{mode="idle", cpu="0"}[1h])
rate(node_cpu_seconds_total{mode="idle", cpu="0"}[1h]) * 3600

# The difference should be zero (or floating-point noise)
increase(node_cpu_seconds_total{mode="idle", cpu="0"}[1h])
  - rate(node_cpu_seconds_total{mode="idle", cpu="0"}[1h]) * 3600
```

See extrapolation produce a non-integer:

```promql
increase(demo_api_request_duration_seconds_count[1m])
```

Rarely a clean integer.

Demonstrate the range-too-short failure:

```promql
# Demo job scrapes every 5s, so this works
rate(demo_api_request_duration_seconds_count[15s])

# Node job scrapes every 15s, so this often returns nothing
rate(node_cpu_seconds_total[15s])

# Safe
rate(node_cpu_seconds_total[1m])
```

Force a counter reset and watch each function respond:

```bash
docker restart demo-a
```

Immediately query:

```promql
demo_api_request_duration_seconds_count{instance="demo-a:8080"}
rate(demo_api_request_duration_seconds_count{instance="demo-a:8080"}[5m])
resets(demo_api_request_duration_seconds_count{instance="demo-a:8080"}[1h])
irate(demo_api_request_duration_seconds_count{instance="demo-a:8080"}[5m])
```

Raw drops to near zero. `rate()` stays sane. `resets()` reports 1.

Now prove why sum-before-rate is wrong. Restart one instance:

```bash
docker restart demo-b
```

```promql
# Correct: rate first
sum(rate(demo_api_request_duration_seconds_count[5m]))

# Wrong: sum first (via subquery)
rate(sum(demo_api_request_duration_seconds_count)[5m:15s])
```

The second dips or goes negative-adjacent around the restart. The first does not.

Gauge functions:

```promql
node_load1
delta(node_load1[10m])
idelta(node_load1[1m])
deriv(node_load1[10m])
changes(node_load1[10m])

# Compare delta/window against deriv
delta(node_load1[10m]) / 600
deriv(node_load1[10m])
```

`deriv()` is smoother because it uses every sample.

Disk prediction:

```promql
node_filesystem_avail_bytes{mountpoint="/host"}

# Seconds until full at the current trend
node_filesystem_avail_bytes{mountpoint="/host"} / -deriv(node_filesystem_avail_bytes{mountpoint="/host"}[1h])

# Predicted free bytes in 4 hours
predict_linear(node_filesystem_avail_bytes{mountpoint="/host"}[1h], 4 * 3600)

# The alert condition
predict_linear(node_filesystem_avail_bytes{mountpoint="/host"}[6h], 4 * 3600) < 0
```

Fill a disk in a container to see the prediction turn negative:

```bash
docker exec node-exporter sh -c 'dd if=/dev/zero of=/tmp/fill bs=1M count=500 2>/dev/null'
sleep 120
```

```promql
deriv(node_filesystem_avail_bytes{mountpoint="/host"}[10m])
predict_linear(node_filesystem_avail_bytes{mountpoint="/host"}[10m], 3600)
```

```bash
docker exec node-exporter rm -f /tmp/fill
```

Detect a flapping target:

```bash
for i in 1 2 3; do docker stop demo-c; sleep 20; docker start demo-c; sleep 20; done
```

```promql
changes(up{instance="demo-c:8080"}[30m])
avg_over_time(up{instance="demo-c:8080"}[30m])
```

Prove the type-safety gap:

```promql
# No error, meaningless result
rate(node_memory_MemAvailable_bytes[5m])

# Correct intent
deriv(node_memory_MemAvailable_bytes[5m])
```

Build the classic dashboards:

```promql
# Requests per second by status
sum by (status) (rate(demo_api_request_duration_seconds_count[5m]))

# Error ratio
sum(rate(demo_api_request_duration_seconds_count{status=~"5.."}[5m]))
  / sum(rate(demo_api_request_duration_seconds_count[5m]))

# CPU utilisation per instance
1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))

# Network throughput
sum by (device) (rate(node_network_receive_bytes_total[5m]))

# Disk IO
sum by (device) (rate(node_disk_read_bytes_total[5m]) + rate(node_disk_written_bytes_total[5m]))
```

## Exam tips

- `rate()` = per-second average over the window, **handles resets**, **extrapolates**, needs **≥2 samples**.
- `increase(x[t])` = `rate(x[t]) * t_seconds`. Non-integer results are normal and expected.
- `irate()` = last two samples only. **Never in alerts.** Debugging zoom only.
- **Range ≥ 4x scrape interval.** Gaps in a rate graph almost always mean the range is too short.
- **Always `rate()` before aggregating.** `sum(rate(x[5m]))`, never `rate(sum(x)[5m:])`.
- Gauges: `delta()` for change, `deriv()` for smoothed per-second slope, `idelta()` for last-two-sample change, `predict_linear()` for forecasting.
- `predict_linear(x[6h], 4*3600)` second argument is **seconds**.
- Disk-full alert = `predict_linear(...) < 0`.
- `resets()` counts **counter** decreases. `changes()` counts **gauge** value changes, and `changes(up[...])` finds flapping targets.
- `rate()` on a gauge returns a silent wrong answer. No error.
- `holt_winters` is now `double_exponential_smoothing`.
