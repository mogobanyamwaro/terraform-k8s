# 03. Tracing And Spans

**Domain:** Observability Concepts

## Concept Refresher

A **distributed trace** records the path of a single request as it moves through multiple services. It is a tree (technically a DAG) of **spans**.

```text
Trace  (trace_id = abc123)
│
├── Span: frontend HTTP GET /checkout          [0ms ────────────── 420ms]  root span
│   ├── Span: auth-service ValidateToken       [5ms ── 18ms]
│   ├── Span: cart-service GetCart             [20ms ──── 65ms]
│   │   └── Span: redis GET cart:42            [22ms ─ 30ms]
│   └── Span: payment-service Charge           [70ms ─────────── 415ms]  <-- the latency lives here
│       └── Span: postgres INSERT payments     [90ms ──── 210ms]
```

### Span anatomy

| Field | Meaning |
| --- | --- |
| `trace_id` | Identifies the whole request, shared by every span |
| `span_id` | Identifies this span |
| `parent_span_id` | Links to the caller. Empty for the root span |
| Name / operation | What this unit of work is, e.g. `GET /checkout` |
| Start time, end time | Gives duration |
| Attributes / tags | Key-value context, e.g. `http.status_code=500` |
| Events / logs | Timestamped notes inside the span |
| Status | Ok, Error, Unset |
| Span kind | Server, Client, Producer, Consumer, Internal |

### Context propagation

Trace context travels between services in HTTP headers. The W3C standard:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^  ^                                ^                ^
             |  trace-id (16 bytes hex)          parent span-id   flags (01 = sampled)
             version
tracestate: vendor1=value,vendor2=value
```

Older / vendor formats: B3 (`X-B3-TraceId`, `X-B3-SpanId`, `X-B3-Sampled`), Jaeger (`uber-trace-id`).

If propagation breaks, you get **orphaned traces**: many small disconnected traces instead of one.

### Sampling

Traces are voluminous, so they are usually sampled.

| Strategy | How it works | Trade-off |
| --- | --- | --- |
| Head-based (upfront) | Decide at the root, e.g. keep 1% | Cheap, but you may miss the rare error |
| Tail-based | Buffer all spans, decide after seeing the whole trace | Keeps all errors and slow traces, needs memory |
| Probabilistic | Fixed ratio | Simple |
| Rate limiting | N traces per second | Predictable cost |

### Tracing vs metrics

| Question | Right signal |
| --- | --- |
| "Is p99 latency above SLO?" | Metrics (histogram) |
| "Which downstream service is causing the p99?" | Traces |
| "How many requests failed in the last hour?" | Metrics (counter) |
| "What was the exact call path of this failed request?" | Traces |

The usual workflow: **metrics alert you, traces localise the problem, logs explain it.**

### Tooling landscape

- **OpenTelemetry (OTel)**: the CNCF standard for instrumentation. Covers traces, metrics, and logs. The OTel Collector can receive OTLP and export to Prometheus.
- **Jaeger**: CNCF tracing backend, originally Uber.
- **Zipkin**: older tracing backend, Twitter origin.
- **Grafana Tempo**: trace backend that indexes only trace IDs, similar economics to Loki.
- **OpenTracing + OpenCensus**: both merged into OpenTelemetry. Historical.

### Exemplars: the bridge between metrics and traces

An **exemplar** attaches a trace ID to a specific histogram bucket observation in the exposition format:

```text
http_request_duration_seconds_bucket{le="0.5"} 4823 # {trace_id="4bf92f3577b34da6a3ce929d0e0e4736"} 0.427 1687000000.000
```

Rules:

- Exemplars require the **OpenMetrics** exposition format.
- Prometheus needs `--enable-feature=exemplar-storage` to store them.
- Exemplars are stored in a fixed-size circular buffer, not the TSDB proper.
- Grafana renders them as clickable dots on a graph that jump straight to the trace.

This is the exam-relevant answer to "how do you go from a latency spike on a dashboard to the trace that caused it".

## Answers

**Q1: B.** The `trace_id` is shared by all spans of a request. `span_id` is per-span, `parent_span_id` links to the caller.

**Q2: C.** The root span is the entry point and has no parent. Duration and completion order are irrelevant.

**Q3: C.** `traceparent`, with the optional companion `tracestate`. `X-B3-*` is Zipkin's B3 format, `uber-trace-id` is Jaeger's, `X-Request-ID` is an unrelated correlation convention.

**Q4: B.** Tail-based sampling buffers spans and decides once the trace is complete, so it can keep 100% of error and slow traces. The cost is memory in the collector. The name refers to the tail of the trace lifecycle, not tail latency.

**Q5: B.** Traces show per-dependency time attribution. Metrics tell you p99 is bad, traces tell you where the time went.

**Q6: B.** Exemplars link a metric observation, typically a histogram bucket, to a trace ID so you can jump from a graph to a trace.

**Q7: B.** OpenMetrics. The classic Prometheus text format has no exemplar syntax. Prometheus also needs `--enable-feature=exemplar-storage`.

**Q8: B.** OpenTracing (API standard) and OpenCensus (Google libraries) merged into OpenTelemetry.

**Q9: C.** Broken context propagation produces orphaned root spans. Each service starts a new trace because it never received a `traceparent`.

**Q10: B.** Metrics detect, traces localise, logs explain. Metrics are the correct alerting signal because they are cheap, complete, and unsampled.

**Q11: C.** Attributes, called tags in older systems, carry key-value context such as HTTP status.

**Q12: B.** Tempo indexes only trace IDs and keeps blocks in object storage, the same "cheap index, scan on read" philosophy as Loki.

## Hands-on

You do not need a full tracing stack for PCA, but seeing exemplars is worth it.

Enable exemplar storage:

```bash
# Add to the Prometheus command in docker-compose.yml
--enable-feature=exemplar-storage
```

Then restart and query the exemplar API:

```bash
curl -sG http://localhost:9090/api/v1/query_exemplars \
  --data-urlencode 'query=http_request_duration_seconds_bucket' \
  --data-urlencode "start=$(date -d '-1 hour' +%s)" \
  --data-urlencode "end=$(date +%s)" | jq
```

Hand-craft an exposition payload with an exemplar to see the syntax:

```bash
cat <<'EOF' > /tmp/exemplar.txt
# HELP demo_latency_seconds Request latency
# TYPE demo_latency_seconds histogram
demo_latency_seconds_bucket{le="0.1"} 1
demo_latency_seconds_bucket{le="0.5"} 3 # {trace_id="4bf92f3577b34da6a3ce929d0e0e4736"} 0.42 1687000000
demo_latency_seconds_bucket{le="+Inf"} 4
demo_latency_seconds_sum 1.2
demo_latency_seconds_count 4
# EOF
EOF
promtool check metrics < /tmp/exemplar.txt
```

Run Jaeger all-in-one if you want to see a real trace tree:

```bash
docker run -d --name jaeger -p 16686:16686 -p 4317:4317 -p 4318:4318 \
  jaegertracing/all-in-one:1.62.0
# UI at http://localhost:16686
```

Inspect a W3C header shape:

```bash
python3 -c "
import secrets
print('traceparent: 00-%s-%s-01' % (secrets.token_hex(16), secrets.token_hex(8)))
"
```

## Exam tips

- `trace_id` groups a request. `span_id` identifies a unit of work. `parent_span_id` builds the tree.
- Root span = no parent.
- W3C header is `traceparent` (plus `tracestate`). B3 is Zipkin. `uber-trace-id` is Jaeger.
- Head sampling decides early and cheaply. Tail sampling decides late and keeps the interesting traces.
- Exemplars connect metrics to traces. They need OpenMetrics format and `--enable-feature=exemplar-storage`.
- OpenTracing + OpenCensus = OpenTelemetry.
- Metrics alert, traces localise, logs explain. Do not alert on sampled traces.
- Tempo and Loki share the "tiny index, cheap object storage" model.
