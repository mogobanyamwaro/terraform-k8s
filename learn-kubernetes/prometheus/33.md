# 33. Recording Rules

**Domain:** Alerting and Dashboarding

## Concept Refresher

A **recording rule** precomputes a PromQL expression on a schedule and stores the result as a new time series. Use them for expensive queries, dashboard speed, and to give SLO math a stable name.

```yaml
groups:
  - name: example
    interval: 30s
    limit: 0
    rules:
      - record: job:http_requests:rate5m
        expr: sum by (job) (rate(http_requests_total[5m]))
        labels:
          team: platform
```

Rule files are loaded via `rule_files` in `prometheus.yml`:

```yaml
rule_files:
  - /etc/prometheus/rules/*.yml
  - /etc/prometheus/rules/alerts/*.yml
```

Globs are expanded at load time. Adding a **new file** that matches an existing glob is picked up on reload; you do not need to edit `prometheus.yml`.

### Group semantics

| Field | Meaning |
| --- | --- |
| `name` | Group name. Must be unique **within a file** |
| `interval` | Evaluation interval for this group. Defaults to global `evaluation_interval` (`1m`) |
| `limit` | Max series a rule in this group may produce. `0` = unlimited. Exceeding it fails the rule |
| `query_offset` | Delay evaluation by this much, to let late samples arrive |
| `rules` | Ordered list of rules |

Critical facts:

- **Rules within a group run sequentially, in order.** So a later rule can use an earlier rule's output from the same evaluation cycle.
- **Different groups run in parallel** and independently. A rule in group B cannot rely on a rule in group A having run this cycle.
- Therefore, chained rules must be **in the same group, in dependency order**.

```yaml
groups:
  - name: slo_chain
    interval: 30s
    rules:
      # 1. runs first
      - record: job:requests:rate5m
        expr: sum by (job) (rate(http_requests_total[5m]))
      # 2. can safely use the output of rule 1
      - record: job:errors:rate5m
        expr: sum by (job) (rate(http_requests_total{code=~"5.."}[5m]))
      # 3. uses both
      - record: job:error_ratio:rate5m
        expr: job:errors:rate5m / job:requests:rate5m
```

### The naming convention

This is heavily tested. The official convention is:

```text
level:metric:operations
```

| Part | Meaning |
| --- | --- |
| `level` | The aggregation level, i.e. the labels the result is aggregated **to** |
| `metric` | The metric name, without the `_total` suffix removed by rate |
| `operations` | The operations applied, most recent first |

Examples:

```text
instance:node_cpu:rate5m
job:http_requests:rate5m
job_route:http_request_duration_seconds:p99
cluster_namespace_job:request_latency_seconds:histogram_quantile99
code:prometheus_http_requests:rate5m
```

Rules:

- Colons are **reserved for recording rules**. Never use a colon in a directly instrumented metric name.
- Colons are **allowed** in metric names in PromQL and are not affected by relabeling.
- The `level` should list the `by` labels joined with `_`.
- Keep the unit in the metric part if the source had one.

### When to use recording rules

| Use | Reason |
| --- | --- |
| Expensive aggregations used by many dashboards | Compute once, read many |
| Subqueries | Replacing a subquery with a recorded series is the standard optimisation |
| SLO error ratios over long windows | `rate(...[30d])` is brutally expensive; record short windows and combine |
| Alert expressions reused across rules | One source of truth |
| Federation | Federate only recorded aggregates, not raw series |
| Long-window histogram quantiles | Record the bucket rates, quantile at query time |

### When NOT to use recording rules

- Do **not** record something you query once.
- Do **not** record a value you could compute as cheaply at query time.
- Do **not** record `histogram_quantile()` results if you will ever need to re-aggregate. Record the **bucket rates** instead, keeping `le`:

```yaml
      # Right: keeps le, so quantiles stay flexible and aggregatable
      - record: job_le:http_request_duration_seconds_bucket:rate5m
        expr: sum by (job, le) (rate(http_request_duration_seconds_bucket[5m]))
```

```promql
histogram_quantile(0.99, job_le:http_request_duration_seconds_bucket:rate5m)
```

### Backfilling

Recording rules only produce data **from the moment they are created forward**. Historical data is not retroactively computed. To fill in history:

```bash
promtool tsdb create-blocks-from rules \
  --start 2026-08-01T00:00:00Z \
  --end 2026-08-10T00:00:00Z \
  --url http://localhost:9090 \
  --output-dir ./backfill \
  rules/slo.yml

# then move the blocks into the TSDB directory and reload
```

That this requires an explicit backfill step is a common exam point.

### Validation and reload

```bash
promtool check rules rules/*.yml
promtool check config prometheus.yml       # also checks referenced rule files

# Reload
kill -HUP $(pidof prometheus)
curl -X POST http://localhost:9090/-/reload     # needs --web.enable-lifecycle
```

Unit-test rules with `promtool test rules`:

```yaml
# tests/slo_test.yml
rule_files:
  - ../rules/slo.yml

evaluation_interval: 1m

tests:
  - interval: 1m
    input_series:
      - series: 'http_requests_total{job="api", code="200"}'
        values: '0+10x10'
      - series: 'http_requests_total{job="api", code="500"}'
        values: '0+1x10'
    promql_expr_test:
      - expr: job:error_ratio:rate5m
        eval_time: 10m
        exp_samples:
          - labels: 'job:error_ratio:rate5m{job="api"}'
            value: 0.09090909090909091
```

```bash
promtool test rules tests/slo_test.yml
```

Series notation: `0+10x10` means start at 0, add 10, ten times. `1x5` means the value 1 repeated. `_` means a gap (no sample). `stale` inserts a staleness marker.

### Rule health metrics

| Metric | Meaning |
| --- | --- |
| `prometheus_rule_evaluation_duration_seconds` | How long rule evaluation takes |
| `prometheus_rule_group_duration_seconds` | Per-group duration |
| `prometheus_rule_group_last_duration_seconds` | Last run duration |
| `prometheus_rule_group_interval_seconds` | Configured interval |
| `prometheus_rule_evaluation_failures_total` | Failed evaluations |
| `prometheus_rule_group_iterations_missed_total` | **Skipped iterations because evaluation overran the interval** |

The classic health check:

```promql
prometheus_rule_group_last_duration_seconds
  > prometheus_rule_group_interval_seconds
```

If a group takes longer to evaluate than its interval, iterations get skipped and you silently lose data.

The rules API:

```bash
curl -s http://localhost:9090/api/v1/rules | jq .
curl -s 'http://localhost:9090/api/v1/rules?type=record' | jq .
```

## Answers

**Q1: B.** Precompute and store.

**Q2: B.** `level:metric:operations`.

**Q3: B.** Aggregation level, metric, operations, separated by colons.

**Q4: B.** Reserved for recording rules by convention, precisely so a colon signals "this is derived".

**Q5: B.** Sequentially in order, which is what makes chaining safe.

**Q6: B.** In parallel, so cross-group dependencies are unsafe.

**Q7: B.** Same group, dependency order.

**Q8: C.** Global `evaluation_interval`, default `1m`.

**Q9: B.** A per-rule series cap; the rule fails rather than silently truncating.

**Q10: B.** Forward only, plus explicit backfill.

**Q11: B.** `promtool check rules`.

**Q12: B.** `promtool test rules` with `input_series` and `exp_samples`.

**Q13: B.** `start+increment x count`.

**Q14: B.** A gap. `stale` is the staleness marker.

**Q15: B.** `prometheus_rule_group_iterations_missed_total`.

**Q16: B.** Compare last duration against the configured interval.

**Q17: B.** Record the bucket rates with `le` preserved, and apply `histogram_quantile()` at query time.

**Q18: B.** Quantiles are not aggregatable, so you cannot slice differently later.

**Q19: B.** Recording rules are the canonical subquery optimisation.

**Q20: B.** Reload; globs are re-expanded.

**Q21: B.** The `labels` block, which overrides same-named result labels.

**Q22: B.** Late sample tolerance.

**Q23: B.** Volume. Federating raw series does not scale and is an anti-pattern.

**Q24: B.** Unique within a file.

**Q25: B.** `?type=record`. Use `?type=alert` for alerting rules.

## Hands-on

Build a real rule chain. `~/pca-lab/rules/recording.yml`:

```yaml
groups:
  # Ordered chain: these MUST be in one group
  - name: request_slo_chain
    interval: 15s
    rules:
      - record: job:myapp_requests:rate5m
        expr: sum by (job) (rate(myapp_http_requests_total[5m]))

      - record: job:myapp_request_errors:rate5m
        expr: sum by (job) (rate(myapp_http_requests_total{code=~"5.."}[5m]))

      - record: job:myapp_request_error_ratio:rate5m
        expr: |
          job:myapp_request_errors:rate5m
            /
          job:myapp_requests:rate5m

      - record: job:myapp_request_availability:ratio5m
        expr: 1 - job:myapp_request_error_ratio:rate5m

  # Bucket rates with le preserved: the RIGHT way to record latency
  - name: latency
    interval: 15s
    rules:
      - record: job_le:myapp_request_duration_seconds_bucket:rate5m
        expr: sum by (job, le) (rate(myapp_http_request_duration_seconds_bucket[5m]))

      - record: job_route_le:myapp_request_duration_seconds_bucket:rate5m
        expr: sum by (job, route, le) (rate(myapp_http_request_duration_seconds_bucket[5m]))

      - record: job:myapp_request_duration_seconds:mean5m
        expr: |
          sum by (job) (rate(myapp_http_request_duration_seconds_sum[5m]))
            /
          sum by (job) (rate(myapp_http_request_duration_seconds_count[5m]))

  - name: node
    interval: 30s
    rules:
      - record: instance:node_cpu_utilisation:rate5m
        expr: 1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))

      - record: instance:node_memory_utilisation:ratio
        expr: 1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)

      - record: instance_device:node_filesystem_utilisation:ratio
        expr: |
          1 - (
            node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"}
              /
            node_filesystem_size_bytes{fstype!~"tmpfs|overlay|squashfs"}
          )

      - record: instance:node_network_receive_bytes:rate5m
        expr: sum by (instance) (rate(node_network_receive_bytes_total{device!="lo"}[5m]))
```

Validate before reloading. Always.

```bash
promtool check rules ~/pca-lab/rules/recording.yml
curl -X POST http://localhost:9090/-/reload
```

Confirm the rules registered:

```bash
curl -s 'http://localhost:9090/api/v1/rules?type=record' \
  | jq -r '.data.groups[] | "\(.name) [\(.interval)s]", (.rules[] | "  \(.name)  health=\(.health)  lastEval=\(.evaluationTime)s")'
```

Query the recorded series:

```promql
job:myapp_requests:rate5m
job:myapp_request_error_ratio:rate5m
job:myapp_request_availability:ratio5m
instance:node_cpu_utilisation:rate5m
```

Prove the recorded value matches the raw expression:

```promql
job:myapp_request_error_ratio:rate5m
  -
(
  sum by (job) (rate(myapp_http_requests_total{code=~"5.."}[5m]))
    /
  sum by (job) (rate(myapp_http_requests_total[5m]))
)
```

Near zero. Any difference is just evaluation-time skew between the rule cycle and your query timestamp.

Now prove the histogram point. Apply the quantile at query time to the recorded buckets:

```promql
histogram_quantile(0.50, job_le:myapp_request_duration_seconds_bucket:rate5m)
histogram_quantile(0.95, job_le:myapp_request_duration_seconds_bucket:rate5m)
histogram_quantile(0.99, job_le:myapp_request_duration_seconds_bucket:rate5m)
```

One recorded series set, any quantile you like. And you can still re-aggregate the per-route version:

```promql
histogram_quantile(0.95, job_route_le:myapp_request_duration_seconds_bucket:rate5m)
histogram_quantile(0.95, sum by (job, le) (job_route_le:myapp_request_duration_seconds_bucket:rate5m))
```

That second query re-aggregates route-level buckets up to job level. **You could not do that if you had recorded the quantile.**

Now demonstrate **why cross-group chaining is unsafe**. Split the chain deliberately:

```yaml
groups:
  - name: chain_a
    interval: 1m
    rules:
      - record: test:numerator
        expr: sum(rate(myapp_http_requests_total{code=~"5.."}[5m]))

  - name: chain_b
    interval: 5s
    rules:
      - record: test:ratio_bad
        expr: test:numerator / sum(rate(myapp_http_requests_total[5m]))
```

```bash
promtool check rules ~/pca-lab/rules/bad-chain.yml
curl -X POST http://localhost:9090/-/reload
```

```promql
test:ratio_bad
```

`chain_b` evaluates every 5s but `test:numerator` only updates every 60s, so the numerator is stale relative to the denominator for most evaluations. In the worst case, if group B runs before group A has ever run, the rule produces **no result at all**. Watch it right after a reload:

```promql
test:ratio_bad
count(test:ratio_bad)
```

Delete that file when done:

```bash
rm ~/pca-lab/rules/bad-chain.yml && curl -X POST http://localhost:9090/-/reload
```

Now write a **rule unit test**, which is the part most people skip.

```bash
mkdir -p ~/pca-lab/tests
cat > ~/pca-lab/tests/recording_test.yml <<'EOF'
rule_files:
  - ../rules/unit.yml

evaluation_interval: 1m

tests:
  - interval: 1m
    input_series:
      - series: 'http_requests_total{job="api", code="200"}'
        values: '0+90x10'
      - series: 'http_requests_total{job="api", code="500"}'
        values: '0+10x10'

    promql_expr_test:
      - expr: job:requests:rate5m
        eval_time: 10m
        exp_samples:
          - labels: 'job:requests:rate5m{job="api"}'
            value: 1.6666666666666667

      - expr: job:error_ratio:rate5m
        eval_time: 10m
        exp_samples:
          - labels: 'job:error_ratio:rate5m{job="api"}'
            value: 0.1
EOF

cat > ~/pca-lab/rules/unit.yml <<'EOF'
groups:
  - name: unit
    rules:
      - record: job:requests:rate5m
        expr: sum by (job) (rate(http_requests_total[5m]))
      - record: job:errors:rate5m
        expr: sum by (job) (rate(http_requests_total{code=~"5.."}[5m]))
      - record: job:error_ratio:rate5m
        expr: job:errors:rate5m / job:requests:rate5m
EOF

promtool test rules ~/pca-lab/tests/recording_test.yml
```

Work out the expected numbers by hand: 100 requests per minute total, so `rate` over 5m of 1-minute samples = 100/60 = 1.6667/s. Errors are 10 per minute = 0.1667/s. Ratio = 0.1. Break one expected value deliberately and rerun to see the failure output; it prints the actual value, which makes it a great learning tool.

Add a rule health alert:

```yaml
  - name: meta
    rules:
      - alert: RuleGroupOverrunning
        expr: |
          prometheus_rule_group_last_duration_seconds
            > prometheus_rule_group_interval_seconds
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Rule group {{ $labels.rule_group }} takes {{ $value }}s, longer than its interval"

      - alert: RuleEvaluationFailing
        expr: increase(prometheus_rule_evaluation_failures_total[5m]) > 0
        for: 0m
        labels:
          severity: warning
        annotations:
          summary: "Rule evaluation failures on {{ $labels.instance }}"
```

Finally, test the `limit` field. Add a deliberately explosive rule:

```yaml
  - name: limited
    limit: 3
    rules:
      - record: test:exploded
        expr: node_cpu_seconds_total
```

```bash
curl -X POST http://localhost:9090/-/reload
curl -s http://localhost:9090/api/v1/rules | jq -r '.data.groups[] | select(.name=="limited") | .rules[] | "\(.name) health=\(.health) error=\(.lastError)"'
```

The rule health becomes `err` with an exceeded-limit error, and no series are written. That is the protection `limit` gives you against a rule accidentally producing millions of series.

## Exam tips

- Recording rules **precompute and store**. Naming convention is **`level:metric:operations`**.
- **Colons are reserved for recording rules.** Never in instrumented names.
- **Within a group: sequential, in order. Across groups: parallel.** Chain dependent rules in one group.
- Group `interval` defaults to the global **`evaluation_interval` (`1m`)**.
- `limit` caps series per rule; exceeding it makes the rule **fail**, writing nothing.
- Rules are **forward-only**. Backfill with `promtool tsdb create-blocks-from rules`.
- **Record bucket rates keeping `le`**, not `histogram_quantile()` results, so quantiles and aggregation levels stay flexible.
- Recording rules are the standard **subquery optimisation** and the standard way to make long-window SLO math affordable.
- Validate with `promtool check rules`; unit-test with `promtool test rules`.
- Test series notation: `a+bxn` = start `a`, add `b`, `n` times. `_` = gap. `stale` = staleness marker.
- Health: `prometheus_rule_group_last_duration_seconds > prometheus_rule_group_interval_seconds` and `prometheus_rule_group_iterations_missed_total`.
- Group names must be unique **within a file**.
- `/api/v1/rules?type=record` and `?type=alert` filter the rules API.
- Federate **recorded aggregates**, never raw series.
