# OpenTelemetry Certified Associate (OTCA) Practice

This folder mirrors `pca-exam`, `cba-exam`, and `capa-exam`: **closed-book multiple choice**, not a live cluster like CKA or CNPE.

Outline checked against the Linux Foundation [OTCA page](https://training.linuxfoundation.org/certification/opentelemetry-certified-associate-otca/), [CNCF OTCA](https://www.cncf.io/training/certification/otca/), and [opentelemetry.io](https://opentelemetry.io/docs/) on 2026-08-19.

OTCA is **the OpenTelemetry product exam**: signals, API vs SDK, Collector pipelines, and how to keep those pipelines healthy. It is not PCA (Prometheus/PromQL) and not “generic observability theory” without OTel names.

A minimally qualified candidate can instrument an app (or attach an agent), export **OTLP**, and read a Collector YAML (receivers → processors → exporters).

## OTCA vs PCA

| | **OTCA** | PCA |
| --- | --- | --- |
| Vendor-neutral telemetry | **The syllabus** | Metrics only |
| PromQL | Out | **Largest domain** |
| Collector YAML | **In scope** | Out |
| OTLP / traces / logs | **In scope** | Concept only |
| Pull scrape / exporters | Secondary | **Core** |

Study PCA if you live in Prometheus. Study OTCA if you live in **instrumentation + pipelines**.

## Universal OTCA Reasoning Flow

```text
1. Is it a *signal* question (trace/metric/log)?
     Yes -> data model, instruments, semantic conventions
2. Is it *in the application*?
     Yes -> API vs SDK, OTEL_* env, sampler, propagator, agent
     API is no-op until an SDK is registered
3. Is it *in the pipeline after the app*?
     Yes -> Collector: receiver -> processor -> exporter
     Agent (next to app) vs gateway (central)
4. Is it *broken / sampled away / missing a parent*?
     Yes -> context headers, debug exporter, zpages, schema URL
```
