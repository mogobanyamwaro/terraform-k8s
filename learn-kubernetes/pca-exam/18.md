# 18. Aggregating Over Dimensions

**Domain:** PromQL

## Concept Refresher

Aggregation operators collapse an instant vector across **label dimensions**, producing fewer series.

```text
INPUT (instant vector, 5 series)              sum by (job) (...)         OUTPUT (2 series)

up{job="demo", instance="a"} 1                                            {job="demo"} 3
up{job="demo", instance="b"} 1        ──────────────────────────►         {job="node"} 2
up{job="demo", instance="c"} 1
up{job="node", instance="n1"} 1
up{job="node", instance="n2"} 1
```

### Syntax, both forms

```promql
sum by (job, status) (rate(http_requests_total[5m]))
sum (rate(http_requests_total[5m])) by (job, status)
```

Both are valid. The `by`-first form is preferred and is what you will see in the docs.

### by vs without

```promql
sum by (job) (x)          # KEEP only the job label. Everything else is dropped
sum without (instance) (x) # DROP the instance label. Keep everything else
sum(x)                     # drop ALL labels, one result series
```

`without` is often the better choice because it survives new labels being added later.

**Important:** `by` and `without` are mutually exclusive; you cannot use both.

### All aggregation operators

| Operator | Result |
| --- | --- |
| `sum` | Sum of values |
| `min` | Smallest value |
| `max` | Largest value |
| `avg` | Arithmetic mean |
| `group` | All result values are `1`. Useful for set operations |
| `stddev` | Population standard deviation |
| `stdvar` | Population standard variance |
| `count` | Number of series in the group |
| `count_values` | Count series by their **value**, requires a label name parameter |
| `bottomk` | Smallest `k` series, **preserves labels** |
| `topk` | Largest `k` series, **preserves labels** |
| `quantile` | φ-quantile (0 ≤ φ ≤ 1) across the **dimension** |
| `limitk` | First `k` series (experimental) |
| `limit_ratio` | A deterministic ratio sample of series (experimental) |

### Operators that take a parameter

Four aggregators require a first parameter, placed **inside** the parentheses before the vector:

```promql
topk(5, rate(http_requests_total[5m]))
bottomk(3, node_filesystem_avail_bytes)
quantile(0.95, node_cpu_utilisation)
count_values("version", go_info)
```

Common mistake:

```promql
topk(rate(x[5m]), 5)     # WRONG, argument order reversed
topk(5, rate(x[5m]))     # RIGHT
```

### topk and bottomk behaviour

Unlike other aggregators, `topk` and `bottomk`:

- **Preserve all original labels** of the selected series.
- Return `k` series **per group**, if you use `by`.

```promql
topk(3, node_load1)              # the 3 highest series overall
topk by (job) (1, node_load1)    # the single highest series WITHIN each job
```

The grouping modifier works exactly as it does for any other aggregator, and the numeric parameter still comes first inside the parentheses. Both forms return the selected series with **all their original labels intact**, which is the point of `topk`: you want to know *which* instance is the outlier, not just the value.

`topk` caveat in graphs: it is recomputed at every step, so the series set flickers. Pin it:

```promql
topk(5, sum by (instance) (rate(x[5m] @ end())))
```

### count vs count_values

```promql
count(up)                        # how many up series exist
count by (job) (up)              # how many series per job
count_values("value", up)        # how many series have each distinct VALUE
```

`count_values` creates a **new label** whose value is the original sample value:

```promql
count_values("version", go_info)
# => {version="go1.22.3"} 12
#    {version="go1.21.9"} 3
```

### The count-of-count idiom

To find how many distinct values a label has:

```promql
count(count by (mode) (node_cpu_seconds_total))
count(count by (instance) (up))
count(group by (job) (up))          # equivalent using group
```

Inner `count by (l)` gives one series per distinct `l`. Outer `count` counts those series.

### quantile as an aggregator

`quantile()` computes a quantile **across series in a dimension**, which is different from `histogram_quantile()`.

```promql
# The 95th percentile CPU utilisation ACROSS INSTANCES
quantile(0.95, instance:node_cpu_utilisation:rate5m)

# The 95th percentile REQUEST LATENCY from a histogram
histogram_quantile(0.95, sum by (le) (rate(request_duration_seconds_bucket[5m])))
```

Both say "95th percentile" but they answer completely different questions. Confusing them is a classic exam trap.

| Function | Percentile across |
| --- | --- |
| `quantile(0.95, v)` | The set of **series** in the group |
| `histogram_quantile(0.95, v)` | The **observation distribution** inside a histogram |

### avg vs sum/count

```promql
avg by (job) (x)
sum by (job) (x) / count by (job) (x)      # identical
```

But averaging averages is not the same as a true average:

```promql
avg(avg by (instance) (x))          # NOT the true global average unless groups are equal size
sum(x) / count(x)                   # true global average
```

### Aggregating histograms correctly

```promql
# WRONG: averages per-instance p99s
avg(histogram_quantile(0.99, rate(x_bucket[5m])))

# RIGHT: sum the buckets first, then compute the quantile once
histogram_quantile(0.99, sum by (le) (rate(x_bucket[5m])))
```

The `le` label **must** be preserved in the aggregation. Dropping it makes `histogram_quantile` fail or return nonsense.

### Aggregation with group_left context

Aggregation drops labels. If you need a label back for display, join it in with an info metric:

```promql
sum by (instance) (rate(x[5m]))
  * on(instance) group_left(version) node_exporter_build_info
```

### Common patterns

```promql
# Total request rate across the fleet
sum(rate(http_requests_total[5m]))

# Per-status breakdown
sum by (status) (rate(http_requests_total[5m]))

# Per-service error ratio
sum by (service) (rate(http_requests_total{status=~"5.."}[5m]))
  / sum by (service) (rate(http_requests_total[5m]))

# Number of running instances per job
count by (job) (up == 1)

# Number of down instances per job
count by (job) (up == 0) or count by (job) (up) * 0

# Fleet-wide CPU utilisation
1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m]))

# Per-instance CPU utilisation
1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))

# Top 5 memory consumers
topk(5, node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes)

# Least free disk
bottomk(3, node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"})

# How many distinct Go versions are running
count_values("go_version", go_info)

# Standard deviation of load across instances
stddev(node_load1)

# 90th percentile of per-instance load
quantile(0.9, node_load1)
```

## Answers

**Q1: B.** One series per distinct `job`. All non-grouping labels are discarded.

**Q2: B.** `by` is a whitelist of labels to keep. `without` is a blacklist of labels to remove.

**Q3: B.** The parameter comes first, inside the parentheses.

**Q4: B.** `topk`, `bottomk`, `quantile`, and `count_values` all take a leading parameter. (`limitk` and `limit_ratio` do too, but they are experimental.)

**Q5: B.** They select whole series and return them with labels intact, which is why you can see *which* instance is the top consumer.

**Q6: B.** It buckets series by sample value and materialises that value into the named label.

**Q7: B.** The count-of-count idiom. Option C returns one series per instance rather than a single number.

**Q8: B.** As an aggregator, `quantile` works across the **series dimension**, not across time and not inside a histogram.

**Q9: B.** Aggregate the buckets with `by (le)` first, then apply `histogram_quantile` once.

**Q10: B.** `histogram_quantile` needs the `le` label to know the bucket boundaries. A bare `sum()` removes it.

**Q11: B.** `group` sets every result value to 1. It is used for existence checks and set operations where the value is irrelevant.

**Q12: B.** That is the definition of the mean.

**Q13: B.** Mutually exclusive.

**Q14: B.** `up == 0` filters to the down series, then `count by (job)` counts them. Note the subtlety: if no target is down, the result is empty rather than zero, which matters for dashboards.

**Q15: B.** `bottomk` selects the smallest values and preserves labels so you can see which instances they are.

**Q16: B.** `@ end()` pins the evaluation timestamp, fixing the series set for the whole graph.

**Q17: D.** Both `sum(x)` and `sum by () (x)` produce a single label-less series.

**Q18: B.** Averaging averages gives each group equal weight regardless of size. `sum/count` is the true weighted mean.

**Q19: B.** Standard deviation across the series within each job group.

**Q20: B.** `avg` across the per-core idle rates, because `rate(...{mode="idle"})` gives roughly 1 per idle core. Summing would yield the core count, not a fraction.

## Hands-on

Basic aggregation:

```promql
up
sum(up)
count(up)
sum by (job) (up)
count by (job) (up)
sum without (instance) (up)
avg by (job) (up)
min by (job) (up)
max by (job) (up)
```

Compare `by` and `without`:

```promql
node_cpu_seconds_total{mode="idle"}
sum by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))
sum without (cpu, mode) (rate(node_cpu_seconds_total{mode="idle"}[5m]))
```

Both give one series per instance, but `without` also keeps `job`.

Parameterised aggregators:

```promql
topk(3, node_load1)
bottomk(3, node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"})
quantile(0.5, node_load1)
quantile(0.95, node_load1)
count_values("load_value", node_load1)
count_values("go_version", go_info)
```

Try the wrong order and read the error:

```bash
curl -sG http://localhost:9090/api/v1/query --data-urlencode 'query=topk(node_load1, 3)' | jq -r '.error'
```

Prove `topk` preserves labels:

```promql
topk(2, rate(node_cpu_seconds_total[5m]))
```

Note that `cpu` and `mode` are still there, unlike with `sum`.

Grouped topk:

```promql
topk by (job) (1, up)
```

Count-of-count idiom:

```promql
count(count by (instance) (up))
count(count by (job) (up))
count(count by (mode) (node_cpu_seconds_total))
count(count by (cpu) (node_cpu_seconds_total))
count(group by (job) (up))
```

Verify the cardinality multiplication:

```promql
count(node_cpu_seconds_total)
count(count by (cpu) (node_cpu_seconds_total)) * count(count by (mode) (node_cpu_seconds_total))
```

`group`:

```promql
group by (job) (up)
group(up)
```

All values are 1.

Histogram aggregation, right and wrong:

```promql
# Wrong: averaging per-instance quantiles
avg(histogram_quantile(0.99, rate(demo_api_request_duration_seconds_bucket[5m])))

# Right: aggregate buckets, then compute
histogram_quantile(0.99, sum by (le) (rate(demo_api_request_duration_seconds_bucket[5m])))

# Right, per path
histogram_quantile(0.99, sum by (le, path) (rate(demo_api_request_duration_seconds_bucket[5m])))

# Broken: le dropped
histogram_quantile(0.99, sum(rate(demo_api_request_duration_seconds_bucket[5m])))
```

Compare the numbers from the first two. They will differ, sometimes substantially.

Prove averaging averages is not the true mean. Create unequal groups by looking at CPU counts, or use this simpler demonstration:

```promql
avg(avg by (instance) (rate(node_cpu_seconds_total[5m])))
sum(rate(node_cpu_seconds_total[5m])) / count(rate(node_cpu_seconds_total[5m]))
```

Statistics across the fleet:

```promql
stddev(node_load1)
stdvar(node_load1)
stddev by (job) (node_load1)
max(node_load1) - min(node_load1)
```

Real dashboard queries:

```promql
# Total request rate
sum(rate(demo_api_request_duration_seconds_count[5m]))

# By status
sum by (status) (rate(demo_api_request_duration_seconds_count[5m]))

# By path and method
sum by (path, method) (rate(demo_api_request_duration_seconds_count[5m]))

# Error ratio per instance
sum by (instance) (rate(demo_api_request_duration_seconds_count{status=~"5.."}[5m]))
  / sum by (instance) (rate(demo_api_request_duration_seconds_count[5m]))

# Healthy target count
count by (job) (up == 1)

# CPU utilisation, per instance and fleet-wide
1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))
1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m]))

# CPU by mode
avg by (mode) (rate(node_cpu_seconds_total[5m]))

# Memory used ratio
1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)

# Top 5 by network receive
topk(5, sum by (instance, device) (rate(node_network_receive_bytes_total[5m])))
```

Join a label back after aggregation:

```promql
sum by (instance) (rate(node_cpu_seconds_total[5m]))
  * on(instance) group_left(version) node_exporter_build_info
```

## Exam tips

- `by (labels)` **keeps** those labels. `without (labels)` **removes** them. Mutually exclusive.
- `sum(x)` drops all labels and returns one series.
- Parameterised aggregators: **`topk`, `bottomk`, `quantile`, `count_values`**. Parameter goes **first**: `topk(5, x)`.
- `topk` and `bottomk` **preserve all labels**. Every other aggregator drops non-grouping labels.
- `topk` in a graph flickers. Pin with `@ end()`.
- `count_values("label", x)` groups by **sample value** and puts it in a new label.
- Distinct label values = `count(count by (label) (metric))`.
- `quantile(0.95, v)` = percentile **across series**. `histogram_quantile(0.95, v)` = percentile **within a histogram**. Never confuse them.
- Aggregating histograms: `histogram_quantile(φ, sum by (le) (rate(x_bucket[5m])))`. **Keep `le`.**
- `group` returns 1 for every group. Handy for existence tests.
- `avg by (l) (x)` = `sum by (l) (x) / count by (l) (x)`.
- Averaging averages weights groups equally, which is usually wrong. Use `sum/count`.
- Multi-core CPU utilisation uses `avg by (instance)`, not `sum`.
- `count by (job) (up == 0)` returns **nothing** when all targets are healthy, not zero.
