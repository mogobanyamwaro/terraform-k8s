# 15. Storage, Limitations, And Scaling

**Domain:** Prometheus Fundamentals

## Concept Refresher

### TSDB on-disk layout

```text
data/
├── 01HQ8X9Y2K3M4N5P6Q7R8S9T0V/      ← a BLOCK (ULID name), immutable
│   ├── chunks/
│   │   └── 000001                    ← compressed sample chunks (max 512MB per file)
│   ├── index                         ← inverted index: label pairs -> series
│   ├── meta.json                     ← time range, series count, compaction level
│   └── tombstones                    ← deletion markers from the admin API
├── 01HQ8XABCDEFGHJKMNPQRSTVWX/
│   └── ...
├── chunks_head/                      ← memory-mapped head chunks
│   ├── 000001
│   └── 000002
├── wal/                              ← write-ahead log for the head block
│   ├── 00000000
│   ├── 00000001
│   └── checkpoint.00000000/
└── lock
```

### The write path

```text
scrape → head block (in memory) → WAL (on disk, for crash recovery)
                ↓ every 2 hours
         head is cut into a persistent BLOCK on disk
                ↓ background compaction
         small blocks merged into larger blocks (up to 10% of retention)
                ↓ retention
         blocks older than retention.time are deleted whole
```

Key numbers:

| Aspect | Value |
| --- | --- |
| Head block duration / min block duration | **2 hours** |
| Max block duration | 10% of retention time, capped at 31 days |
| WAL segment size | 128MB |
| WAL truncation / checkpoint | Every 3 head compactions |
| Compression | Gorilla-style XOR delta-of-delta for values, varint for timestamps |
| Bytes per sample (typical) | **1 to 2 bytes**, commonly quoted as ~1.7 |
| Retention default | `15d` |
| Chunk | Up to 120 samples per chunk |

### Capacity planning formula

```text
disk = retention_seconds x ingested_samples_per_second x bytes_per_sample
```

`ingested_samples_per_second` = total series / average scrape interval.

Worked example:

```text
1,000,000 series, 15s scrape interval, 15 days retention, 1.7 bytes/sample

samples/sec = 1,000,000 / 15               = 66,667
seconds     = 15 x 86,400                  = 1,296,000
bytes       = 66,667 x 1,296,000 x 1.7     ≈ 147 GB
```

Memory rule of thumb: roughly **2 to 4 KB of RAM per active series**, so 1M series needs somewhere around 2 to 4 GB just for the head, plus query working memory. Head memory is the dominant constraint, not disk.

### Retention

```bash
--storage.tsdb.retention.time=30d      # time based, default 15d
--storage.tsdb.retention.size=100GB    # size based, default 0 = disabled
```

If both are set, **whichever triggers first wins**. Size-based retention deletes the oldest blocks. Retention deletes **whole blocks**, so actual retention can exceed the setting by up to one block duration.

Retention is a **command line flag, never a YAML key.** Expect to be tested on this.

### Documented Prometheus limitations

This is an explicit exam competency. Learn the list.

| Limitation | Detail | Mitigation |
| --- | --- | --- |
| **Not for 100% accurate accounting** | Scrapes can be missed, rates are extrapolated, samples are lossy-compressed. Unsuitable for per-request billing | Use a log/event pipeline for billing |
| **No event logging** | Cannot store per-event detail or strings | Use Loki, ELK |
| **Local storage is not durable or clustered** | Single node, no replication. Node loss = data loss | remote_write to Thanos/Mimir/Cortex; run HA pairs |
| **Single-node scaling ceiling** | Bounded by one machine's RAM and CPU | Functional sharding by job, `hashmod` sharding, federation, or Mimir/Cortex |
| **High cardinality is the main failure mode** | Series count drives memory | Drop labels, avoid unbounded values |
| **Long-term storage needs external systems** | Local TSDB is designed for weeks, not years | Thanos, Mimir, VictoriaMetrics |
| **No downsampling** | All samples stored at full resolution | Thanos Compactor downsamples |
| **No built-in cross-cluster global view** | Each server sees its own data | Thanos Querier, Mimir |
| **No built-in authentication or authorization historically** | Since 2.24 a `--web.config.file` provides TLS and basic auth for the web endpoint, but there is no multi-tenancy or per-query authz | Reverse proxy, Mimir tenants |
| **Not a general-purpose push ingest endpoint** | Pushgateway is only for batch jobs | Agent mode, OTel Collector |
| **PromQL has no joins across time or subqueries over unbounded ranges** | It is not SQL | Recording rules |
| **Alertmanager notification delivery is not guaranteed** | Best effort. Notifications can be lost | Monitor Prometheus and Alertmanager themselves, dead man's switch |

### Federation

Hierarchical federation lets a global Prometheus scrape aggregated data from lower-level servers.

```yaml
scrape_configs:
  - job_name: federate
    scrape_interval: 60s
    honor_labels: true             # MANDATORY, keeps the source job/instance labels
    metrics_path: /federate
    params:
      match[]:
        - '{__name__=~"job:.*"}'   # only pre-aggregated recording rules
        - '{__name__=~"instance:.*"}'
        - 'up'
    static_configs:
      - targets:
          - prometheus-eu:9090
          - prometheus-us:9090
```

Rules:

- `honor_labels: true` is **required** so the federated `job` and `instance` labels survive.
- `match[]` is **required**. Without it you get nothing. It accepts multiple selectors, OR'd together.
- The `/federate` endpoint attaches the source's `external_labels`.
- Federate **only aggregated recording rules**, never raw series. Federating everything recreates the cardinality problem on the parent and is a well-known anti-pattern.
- Federation is for **cross-server aggregation views**, not for long-term storage or reliable replication.

### remote_write and remote_read

```yaml
remote_write:
  - url: https://mimir.example.com/api/v1/push
    write_relabel_configs:
      - source_labels: [__name__]
        regex: "go_.*"
        action: drop
    queue_config:
      capacity: 10000
      max_shards: 200
      max_samples_per_send: 2000
      batch_send_deadline: 5s

remote_read:
  - url: https://mimir.example.com/api/v1/read
    read_recent: false
```

- `remote_write` streams from the **WAL**, so it survives restarts and buffers during outages.
- `external_labels` are added to remote_write data.
- `remote_read` merges remote data into local query results. It is slower than local queries and is often replaced by Thanos Querier or Mimir's own query path.
- Monitor with `prometheus_remote_storage_samples_pending`, `prometheus_remote_storage_samples_failed_total`, `prometheus_remote_storage_highest_timestamp_in_seconds`.

### Scaling strategies, in order of preference

```text
1. Reduce cardinality.                       Cheapest, always do this first
2. Functional sharding.                      One Prometheus per team/region/concern
3. hashmod sharding within a job.             Split a huge job across N servers
4. Hierarchical federation of aggregates.     Global dashboards only
5. remote_write to Thanos / Mimir / Cortex.   Long-term, global, HA
```

### Thanos components

| Component | Role |
| --- | --- |
| **Sidecar** | Runs beside Prometheus, uploads blocks to object storage, serves recent data via StoreAPI |
| **Store Gateway** | Serves historical blocks from object storage |
| **Querier** | Fans out PromQL to Sidecars and Store Gateways, deduplicates HA replicas |
| **Compactor** | Compacts and **downsamples** blocks in object storage (5m and 1h resolutions) |
| **Ruler** | Evaluates recording and alerting rules against the global view |
| **Receive** | Accepts `remote_write` for push-based ingestion |

### Admin API

Requires `--web.enable-admin-api`.

```bash
# Delete series matching a selector
curl -X POST -g 'http://localhost:9090/api/v1/admin/tsdb/delete_series?match[]=bad_metric'

# Free the disk space
curl -X POST http://localhost:9090/api/v1/admin/tsdb/clean_tombstones

# Snapshot for backup
curl -X POST http://localhost:9090/api/v1/admin/tsdb/snapshot
# writes to <storage.tsdb.path>/snapshots/<timestamp>-<hash>
```

Backup of Prometheus data = take a snapshot and copy the directory. There is no logical dump format.

### Inspecting the TSDB offline

```bash
promtool tsdb list data/
promtool tsdb analyze data/
promtool tsdb analyze data/ <block-ulid>
promtool tsdb dump --match='{__name__="up"}' data/
promtool tsdb stats data/
```

`promtool tsdb analyze` gives you the highest-cardinality label pairs and metric names in a block. It is the offline equivalent of `/api/v1/status/tsdb`.

## Answers

**Q1: B.** The `--storage.tsdb.retention.time` flag. There is no YAML key.

**Q2: B.** `15d`.

**Q3: C.** 2 hours.

**Q4: B.** The write-ahead log lets Prometheus replay head samples after an unclean shutdown, so in-memory data is not lost.

**Q5: B.** Roughly 1 to 2 bytes per sample thanks to delta-of-delta timestamp encoding and XOR value compression. The figure usually quoted is about 1.7.

**Q6: B.** samples/sec = 500,000 / 30 = 16,667. Seconds = 15 x 86,400 = 1,296,000. 16,667 x 1,296,000 x 1.7 ≈ 36.7 GB.

**Q7: B.** Head-block memory scales with active series. This is why cardinality control is the primary scaling lever.

**Q8: C.** Either limit can trigger deletion, whichever comes first.

**Q9: B.** Prometheus's own documentation states it is not suitable where 100% accuracy is required, such as per-request billing.

**Q10: B.** `remote_write` to a purpose-built long-term store. Simply raising retention does not give you durability, replication, or downsampling.

**Q11: B.** `honor_labels: true`, otherwise Prometheus overwrites the federated `job` and `instance` labels with the federation job's own.

**Q12: B.** `match[]` is a required series selector. An empty `match[]` returns nothing.

**Q13: B.** Only aggregates. Federating raw series moves the cardinality problem upstream, which is a documented anti-pattern.

**Q14: C.** The Compactor compacts and downsamples to 5 minute and 1 hour resolutions.

**Q15: B.** The Querier deduplicates replicas using the replica label.

**Q16: B.** `remote_write` reads from the WAL and maintains a dynamically sharded retry queue, so it buffers through outages up to the WAL's retention.

**Q17: B.** `--web.enable-admin-api`.

**Q18: B.** Snapshot via `POST /api/v1/admin/tsdb/snapshot` and copy the resulting directory. There is no logical export format.

**Q19: B.** `promtool tsdb analyze`.

**Q20: B.** Cut cardinality first. It is free and addresses the root cause. Adding RAM only postpones the problem.

**Q21: C.** Whole blocks. This is why actual retention can slightly exceed the configured value.

**Q22: C.** No replication. Run duplicate independent servers and let Alertmanager dedupe alerts, and Thanos or Mimir dedupe queries.

## Exam tips

- **Retention is a CLI flag**, `--storage.tsdb.retention.time`, default **15d**. Never a YAML key.
- Head block / min block duration = **2 hours**. Max block = 10% of retention.
- WAL exists for **crash recovery** of head samples.
- Bytes per sample ≈ **1 to 2** (quote 1.7). Disk = retention_sec x samples/sec x bytes/sample.
- Memory ≈ **2 to 4 KB per active series**. Memory, not disk, is the ceiling.
- Retention deletes **whole blocks**, so effective retention can overshoot.
- Both time and size retention: **first to trigger wins**.
- Limitations to recite: no 100% accuracy/billing, no event logging, local storage not durable or clustered, single-node scaling ceiling, cardinality is the failure mode, no downsampling, no global view, no real multi-tenancy.
- Federation: `honor_labels: true` **mandatory**, `match[]` **mandatory**, federate **aggregates only**.
- Federation is not backup and not long-term storage.
- `remote_write` streams from the **WAL** and buffers through outages.
- Thanos: Sidecar uploads, Store Gateway serves history, Querier fans out and dedupes, Compactor compacts and **downsamples**, Ruler evaluates globally, Receive accepts remote_write.
- Admin API needs `--web.enable-admin-api`. Backup = snapshot + copy directory.
- `promtool tsdb analyze` is the offline cardinality report.
- Scaling order: cut cardinality, then functional sharding, then hashmod, then federate aggregates, then remote_write to a scalable store.
- **No replication, no clustering.** HA = duplicate servers + Alertmanager dedup.
