# 37. Dashboarding Basics

**Domain:** Alerting and Dashboarding

## Concept Refresher

The PCA curriculum lists "Dashboarding basics". In practice that means three things: the Prometheus expression browser, Grafana, and knowing that Prometheus console templates exist.

### What Prometheus's own UI can and cannot do

The built-in web UI at `:9090` gives you:

| Page | Purpose |
| --- | --- |
| `/graph` | Expression browser: table and graph views, one expression at a time |
| `/alerts` | Alerting rules with their state and active instances |
| `/rules` | All rules, health, and last evaluation time |
| `/targets` | Every target, its labels, health, last scrape, and error |
| `/service-discovery` | Discovered targets with `__meta_*` labels **before and after** relabeling |
| `/config` | The loaded configuration as Prometheus sees it |
| `/status` | Build info, runtime info, storage stats, flags |
| `/tsdb-status` | Cardinality statistics: top label names, values, series counts |
| `/flags` | Command-line flags in effect |

Prometheus is explicit in its documentation that it is **not** a dashboarding solution. There is no way to save a dashboard, arrange panels, or template variables in the expression browser. **Grafana is the recommended dashboarding tool.**

### Grafana fundamentals

Add Prometheus as a data source:

```yaml
# provisioning/datasources/prometheus.yml
apiVersion: 1
datasources:
  - name: Prometheus
    type: prometheus
    access: proxy
    url: http://prometheus:9090
    isDefault: true
    jsonData:
      httpMethod: POST
      timeInterval: 15s        # tell Grafana your scrape_interval
      queryTimeout: 60s
```

`timeInterval` should equal your `scrape_interval`. It sets what `$__interval` resolves to at minimum, which matters for `rate()` windows.

| Concept | Meaning |
| --- | --- |
| **Data source** | Connection to Prometheus |
| **Dashboard** | A collection of panels, saved as JSON |
| **Panel** | One visualisation, with one or more queries |
| **Query** | A PromQL expression plus a legend format |
| **Row** | Collapsible grouping of panels |
| **Variable** | A templated value, often populated from a `label_values()` query |
| **Annotation** | Event markers on the time axis, can come from a PromQL query |
| **Time range** | Global, per-dashboard, overridable per panel |
| **Transformation** | Post-query reshaping of the data |

### Panel types you should recognise

| Panel | Use |
| --- | --- |
| **Time series** | The default. Rates, utilisation, latency over time |
| **Stat** | A single big number, current value or aggregate |
| **Gauge** | A single value against a range, good for utilisation percentages |
| **Bar gauge** | Compare a value across many series, good with `topk()` |
| **Table** | Instant query results, good for target lists and `topk` tables |
| **Heatmap** | **Histogram bucket data over time.** The canonical use of `_bucket` series |
| **State timeline** | Discrete state over time, good for `up` |
| **Logs** | Loki, not Prometheus |

The heatmap point matters: a heatmap is how you visualise a Prometheus histogram's full distribution rather than a single quantile. Set the panel's format to **Heatmap** and query the `_bucket` series with `rate()`.

### Grafana query options

| Option | Meaning |
| --- | --- |
| **Legend** | `{{instance}}` interpolates a label into the series name |
| **Format** | `Time series`, `Table`, or `Heatmap` |
| **Type** | `Range` (uses `query_range`) or `Instant` (uses `query`, returns latest value only) |
| **Min step / Interval** | Lower bound on the step Grafana requests |
| **Resolution** | Divides the number of data points requested |
| **Exemplars** | Show trace exemplars on the graph |

### The interval variables

These are the most commonly misunderstood part of Grafana with Prometheus.

| Variable | Meaning |
| --- | --- |
| `$__interval` | Grafana's computed step: time range divided by panel width in pixels, floored to the data source `timeInterval` |
| `$__rate_interval` | `max($__interval + scrape_interval, 4 * scrape_interval)`. **Designed specifically for `rate()`** |
| `$__range` | The full selected time range, e.g. `6h` |
| `$__interval_ms` | `$__interval` in milliseconds |

Use **`$__rate_interval`** in `rate()`, not `$__interval`:

```promql
rate(http_requests_total[$__rate_interval])
```

Why: `rate()` needs **at least two samples** in its window. If `$__interval` resolves to something at or below the scrape interval (which happens on wide panels with short ranges), `rate()` returns nothing and the graph goes blank. `$__rate_interval` guarantees at least four scrape intervals of window.

This is the standard answer to "my Grafana graph is empty at short time ranges but fine at long ones".

### Dashboard variables

```text
Query variable:   label_values(node_cpu_seconds_total, instance)
                  label_values(up{job="$job"}, instance)
                  query_result(topk(10, sum by (route) (rate(requests_total[5m]))))
                  metrics(node_)
Custom variable:  prod,staging,dev
Interval variable: 1m,5m,10m,1h
Constant, Textbox, Datasource, Ad hoc filters
```

Used in queries as `$job`, or `${job}`, and with multi-value selection as a regex:

```promql
sum by (instance) (rate(node_cpu_seconds_total{instance=~"$instance"}[$__rate_interval]))
```

Note the `=~` when the variable is multi-value, because Grafana interpolates it as `(a|b|c)`.

| Grafana function | Returns |
| --- | --- |
| `label_values(metric, label)` | All values of a label, optionally filtered by a selector |
| `label_names()` | All label names |
| `metrics(regex)` | Metric names matching a regex |
| `query_result(promql)` | Full series results, needs regex extraction |

`label_values()` maps to `/api/v1/label/<name>/values`, and with a selector to `/api/v1/series`.

### Building a useful dashboard

The standard structure for a service dashboard, based on the golden signals:

```text
Row: Overview
  Stat:      current request rate
  Stat:      current error ratio
  Stat:      p99 latency
  Stat:      SLO error budget remaining
  Timeline:  up per instance

Row: Traffic (Rate)
  Time series: sum by (route) (rate(requests_total[$__rate_interval]))

Row: Errors
  Time series: error ratio by route
  Bar gauge:   topk(10, rate of 5xx by route)

Row: Latency (Duration)
  Time series: p50, p90, p99 from histogram_quantile
  Heatmap:     rate(duration_bucket[$__rate_interval])

Row: Saturation
  Time series: CPU, memory, connection pool, queue depth
```

Panel queries for that dashboard:

```promql
# Rate
sum(rate(myapp_http_requests_total[$__rate_interval]))
sum by (route) (rate(myapp_http_requests_total[$__rate_interval]))

# Errors
sum(rate(myapp_http_requests_total{code=~"5.."}[$__rate_interval]))
  / sum(rate(myapp_http_requests_total[$__rate_interval]))

# Duration: three quantiles in one panel, three queries
histogram_quantile(0.50, sum by (le) (rate(myapp_http_request_duration_seconds_bucket[$__rate_interval])))
histogram_quantile(0.90, sum by (le) (rate(myapp_http_request_duration_seconds_bucket[$__rate_interval])))
histogram_quantile(0.99, sum by (le) (rate(myapp_http_request_duration_seconds_bucket[$__rate_interval])))

# Heatmap: format = Heatmap, legend = {{le}}
sum by (le) (rate(myapp_http_request_duration_seconds_bucket[$__rate_interval]))

# Saturation
1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[$__rate_interval]))
1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes

# Availability, as a stat with a percent unit
1 - (
  sum(increase(myapp_http_requests_total{code=~"5.."}[$__range]))
  / sum(increase(myapp_http_requests_total[$__range]))
)
```

### Dashboarding rules of thumb

- **One dashboard per service**, aligned with the golden signals. Do not build one giant dashboard.
- Put the **most important panel top-left**. People read that first during an incident.
- Use **units**. Seconds, bytes, percent (0-1) versus percent (0-100) is a common misconfiguration.
- `humanize`-style formatting is Grafana's job via units, not PromQL's.
- Keep panel counts low. Every panel is a query; a 40-panel dashboard on a 30-day range can overload Prometheus.
- Use **recording rules** for anything a dashboard queries repeatedly over long ranges.
- Prefer **`sum by (...)`** over raw per-series graphs; a graph with 500 lines tells you nothing.
- Use `topk()` when you must show many series.
- Set the dashboard **refresh interval** no faster than the scrape interval.

### Console templates

Prometheus supports Go-templated HTML consoles served from `--web.console.templates` and `--web.console.libraries`.

```bash
prometheus \
  --web.console.templates=/etc/prometheus/consoles \
  --web.console.libraries=/etc/prometheus/console_libraries
```

```html
{{ template "head" . }}
{{ template "prom_content_head" . }}

<h1>Node Overview</h1>

<h2>CPU</h2>
<div id="cpu"></div>
<script>
new PromConsole.Graph({
  node: document.querySelector("#cpu"),
  expr: "1 - avg by (instance) (rate(node_cpu_seconds_total{mode='idle'}[5m]))",
  name: "[[ instance ]]",
  yAxis: { labelFormatter: PromConsole.NumberFormatter.humanizeNoSmallPrefix },
  yTitle: "CPU utilisation"
})
</script>

<h2>Up</h2>
{{ template "prom_query_drilldown" (args "sum(up)") }}

{{ template "prom_content_tail" . }}
{{ template "tail" }}
```

What you need to know for the exam:

- Console templates are **built into Prometheus**, version-controllable, and Go-templated.
- They are useful for auto-generated, drill-down consoles, historically the Prometheus-native dashboarding approach.
- They are **not** the recommended general dashboarding solution. **Grafana is.**
- Available template functions include `query`, `first`, `label`, `value`, `sortByLabel`, `humanize`, `humanize1024`, `humanizeDuration`, `humanizePercentage`, `printf`, `args`, `match`, `reReplaceAll`, `safeHtml`.

```html
{{ range query "up == 0" }}
  <li>{{ .Labels.instance }} is down</li>
{{ end }}

{{ with query "sum(rate(http_requests_total[5m]))" }}
  {{ . | first | value | humanize }} req/s
{{ end }}
```

### Grafana alerting versus Prometheus alerting

Grafana has its own alerting engine. For PCA, the important distinction:

| | Prometheus alerting | Grafana alerting |
| --- | --- | --- |
| Evaluated by | Prometheus rule manager | Grafana |
| Config | Rule files in YAML, version controlled | Grafana database / provisioning |
| Routing | Alertmanager | Grafana's built-in Alertmanager or an external one |
| Works if Grafana is down | **Yes** | No |

The Prometheus-native answer is **rule files plus Alertmanager**. Grafana alerting is an alternative, not the Prometheus way.

Now the important experiment: **prove the `$__interval` versus `$__rate_interval` problem yourself.**

Create a time series panel with two queries:

```promql
# Query A
sum(rate(myapp_http_requests_total[$__interval]))
# Query B
sum(rate(myapp_http_requests_total[$__rate_interval]))
```

Set the dashboard time range to **last 15 minutes** on a wide panel. Query A goes blank or spiky; Query B is smooth. Now set the range to **last 6 hours**. Both work.

Check what Grafana actually requested. Use the panel's Query Inspector, or reproduce it by hand:

```bash
# Wide panel, short range: step is small, so $__interval is small
curl -s -G http://localhost:9090/api/v1/query_range \
  --data-urlencode 'query=rate(myapp_http_requests_total[15s])' \
  --data-urlencode "start=$(date -d '-15 min' +%s)" \
  --data-urlencode "end=$(date +%s)" \
  --data-urlencode 'step=15s' | jq '.data.result | length'

# rate() over one scrape interval: not enough samples
curl -s -G http://localhost:9090/api/v1/query \
  --data-urlencode 'query=rate(myapp_http_requests_total[5s])' | jq '.data.result | length'
```

The second returns `0` results. That is the blank-graph bug, reproduced without Grafana.

## Exam tips

- Prometheus's UI is **not** a dashboarding solution. **Grafana is the recommended tool.** The expression browser is for ad-hoc queries and debugging.
- Know the UI pages: **`/targets`** for health, **`/service-discovery`** for `__meta_*` and relabeling, **`/tsdb-status`** for cardinality, **`/config`** for the loaded config, **`/rules`** and **`/alerts`** for rules.
- **Use `$__rate_interval` inside `rate()`**, never `$__interval`. `$__rate_interval` = `max($__interval + scrape_interval, 4 * scrape_interval)`.
- A blank Grafana rate graph at short time ranges means the window had **fewer than two samples**.
- Set the data source **`timeInterval` to your `scrape_interval`**.
- **`$__range`** is the full selected range, used for availability over the picker window.
- **Heatmap panel + `rate()` of `_bucket` series + `{{le}}` legend** is how you visualise a histogram distribution.
- `label_values(metric, label)` populates variables and maps to `/api/v1/label/<name>/values`. Multi-value variables interpolate as `(a|b|c)`, so use **`=~`**.
- Legends use **`{{label}}`**.
- Stat for one number, Gauge for one value against a range, Bar gauge with `topk()` for comparison, Table for instant results, State timeline for `up`.
- Aggregate with **`sum by (...)`** and use `topk()`. Do not graph hundreds of raw series.
- Use **recording rules** behind slow dashboards. Do not refresh faster than the scrape interval.
- **Console templates** are built-in, Go-templated HTML enabled with `--web.console.templates` and `--web.console.libraries`. Functions include `query`, `first`, `value`, `humanize`, `humanizePercentage`. They are historical, **not** the recommended solution.
- **Prometheus rule files plus Alertmanager keep alerting if Grafana is down.** That is the Prometheus-native answer.
