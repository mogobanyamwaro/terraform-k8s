# 35. Alertmanager Routing And Grouping

**Domain:** Alerting and Dashboarding

## Concept Refresher

Alertmanager takes firing alerts and decides **who gets notified, when, and how many notifications**.

```text
alerts in (HTTP POST /api/v2/alerts)
   │
   ├─► alert_relabel? (no, that is Prometheus-side)
   │
   ├─► INHIBITION   drop alerts suppressed by a more severe alert
   │
   ├─► SILENCES     drop alerts matching an active silence
   │
   ├─► ROUTING TREE match to exactly one leaf receiver (unless continue: true)
   │
   ├─► GROUPING     bucket by group_by labels
   │
   ├─► group_wait / group_interval / repeat_interval timers
   │
   └─► NOTIFY       receiver integrations, with templating
```

Order matters: **inhibition and silencing happen before notification**, and grouping happens per route.

### The routing tree

Matching rules you must know:

1. The **root route** matches everything and must have a `receiver`. It cannot have `matchers`.
2. Alertmanager walks child routes **in order** and takes the **first match**.
3. Matching then **descends** into that route's children. If no child matches, the current route's receiver is used.
4. `continue: false` (the default) stops sibling evaluation once a route matches.
5. `continue: true` lets evaluation continue to later siblings, so an alert can reach **multiple** receivers.
6. Child routes **inherit** `receiver`, `group_by`, `group_wait`, `group_interval`, `repeat_interval`, `matchers` are **not** inherited.

That inheritance rule is a common question. A child that omits `group_wait` uses its parent's value, recursively up to the root.

### Matchers

Modern syntax (Alertmanager 0.22+, and the only syntax you should write now):

```yaml
      matchers:
        - severity = "critical"
        - team != "database"
        - alertname =~ "High.*"
        - env !~ "dev|staging"
```

| Operator | Meaning |
| --- | --- |
| `=` | Equal |
| `!=` | Not equal |
| `=~` | Regex match, **fully anchored** |
| `!~` | Regex not match, fully anchored |

Deprecated forms you may still see in questions:

```yaml
      match:
        severity: critical
      match_re:
        alertname: High.*
```

`match` / `match_re` still work but are deprecated in favour of `matchers`.

Note: unlike PromQL, an Alertmanager matcher on a **missing** label with `!=` or `!~` **does** match, because a missing label is treated as the empty string. `severity != "critical"` matches an alert with no `severity` label at all.

### Grouping

`group_by` collapses many alerts into one notification.

```yaml
  group_by: ['alertname', 'cluster']
```

- 50 instances firing `InstanceDown` in cluster `prod` become **one** notification listing 50 alerts.
- `group_by: ['...']` (literally three dots) means **do not group at all**: every alert gets its own notification. Use sparingly.
- `group_by: []` groups **everything** in that route into a single group.
- Labels not in `group_by` are still present on the individual alerts inside the group; they just do not split it.

### The three timers

This is the most commonly tested part of Alertmanager.

| Timer | Default | Meaning |
| --- | --- | --- |
| `group_wait` | `30s` | How long to wait after the **first** alert in a **new** group arrives, so related alerts can join the same notification |
| `group_interval` | `5m` | Minimum time before sending an updated notification for an **existing** group when its contents **change** (new alerts added, or alerts resolved) |
| `repeat_interval` | `4h` | How long before re-sending a notification for a group that has **not changed** |

```text
t=0     first alert of a new group arrives
t=30s   group_wait elapses -> NOTIFY #1
t=45s   another alert joins the group
t=5m30s group_interval elapses -> NOTIFY #2 (contains both)
        ... nothing changes ...
t=4h30s repeat_interval elapses -> NOTIFY #3 (same content, reminder)
```

Key nuances:

- `group_wait` applies **only to a brand-new group**.
- `group_interval` throttles **change-driven** notifications. A new alert joining a group does not notify immediately; it waits for the next `group_interval` boundary.
- `repeat_interval` should be **greater than** `group_interval`. Alertmanager warns otherwise.
- Small `group_wait` = faster paging, more notifications. Large `group_wait` = better batching, slower paging. `10s` for critical, `30s`-`5m` for warnings is typical.

### `resolve_timeout`

```yaml
global:
  resolve_timeout: 5m
```

If an alert has no `EndsAt` and Prometheus stops re-sending it, Alertmanager marks it resolved after `resolve_timeout`. Prometheus actually sets `EndsAt` itself, so this mainly matters for alerts pushed by other sources.

### `send_resolved`

Each receiver integration has `send_resolved`, controlling whether resolution notifications go out.

| Integration | `send_resolved` default |
| --- | --- |
| `webhook_configs` | `true` |
| `pagerduty_configs` | `true` |
| `slack_configs` | `false` |
| `email_configs` | `false` |
| `opsgenie_configs` | `true` |

Do not memorise all of them, but do remember that **webhook and PagerDuty default to true while email and Slack default to false**.

### Receivers

Built-in integrations:

```text
email_configs        pagerduty_configs   slack_configs        webhook_configs
opsgenie_configs     victorops_configs   pushover_configs     wechat_configs
telegram_configs     discord_configs     webex_configs        msteams_configs
sns_configs          jira_configs        rocketchat_configs
```

A receiver may have **multiple** integrations and **multiple entries** of the same integration, all of which fire.

```yaml
  - name: multi
    slack_configs:
      - channel: '#alerts'
      - channel: '#ops'
    email_configs:
      - to: 'a@example.com'
    webhook_configs:
      - url: 'http://audit:8080/'
```

An empty receiver is the standard "drop these alerts" idiom:

```yaml
  - name: 'dev-null'
```

### Time-based muting

```yaml
time_intervals:
  - name: out_of_hours
    time_intervals:
      - weekdays: ['saturday', 'sunday']
      - times:
          - start_time: '00:00'
            end_time: '09:00'
        location: 'Europe/London'

route:
  routes:
    - receiver: tickets
      matchers:
        - severity = "warning"
      mute_time_intervals: ['out_of_hours']

    - receiver: pager
      matchers:
        - severity = "critical"
      active_time_intervals: ['out_of_hours']
```

| Field | Effect |
| --- | --- |
| `mute_time_intervals` | Suppress notifications **during** the interval |
| `active_time_intervals` | Only notify **during** the interval |

The older key `mute_time_intervals` referencing `mute_time_intervals:` top-level block is now `time_intervals:`. Both names exist; `time_intervals` is current.

### Alertmanager HA clustering

```bash
alertmanager \
  --config.file=/etc/alertmanager/alertmanager.yml \
  --storage.path=/alertmanager \
  --cluster.listen-address=0.0.0.0:9094 \
  --cluster.peer=am1:9094 \
  --cluster.peer=am2:9094
```

- Uses a **gossip** protocol (memberlist) on port **9094**.
- Every Prometheus sends **every alert to every Alertmanager**.
- The cluster gossips **notification logs (nflog)** and **silences**, so a notification is sent once, not once per node.
- Deduplication is **eventual**, driven by a per-position wait: each node waits `peer_timeout` multiplied by its index in the sorted peer list before sending, and skips if it sees the notification already logged.
- Silences created on any node propagate to all nodes.

Cluster health metrics:

```promql
alertmanager_cluster_members
alertmanager_cluster_health_score          # 0 is healthy
alertmanager_cluster_failed_peers
alertmanager_cluster_peers_joined_total
```

| Metric | Meaning |
| --- | --- |
| `alertmanager_alerts{state}` | Alerts by state: `active`, `suppressed` |

| `alertmanager_alerts_invalid_total` | Rejected alerts |
| `alertmanager_notifications_total{integration}` | Notifications sent |
| `alertmanager_notifications_failed_total{integration}` | Failures |
| `alertmanager_notification_latency_seconds` | Delivery latency |

| `alertmanager_config_last_reload_successful` | 1 if the last reload worked |

## Hands-on

Set up a webhook sink so you can actually see notifications. This is essential; without it you are guessing.

```bash
cat > ~/pca-lab/sink.py <<'PY'
import json, datetime
from http.server import BaseHTTPRequestHandler, HTTPServer

class H(BaseHTTPRequestHandler):
    def do_POST(self):
        n = int(self.headers.get("Content-Length", 0))
        body = json.loads(self.rfile.read(n) or b"{}")
        ts = datetime.datetime.now().strftime("%H:%M:%S")
        print(f"\n=== {ts}  {self.path}")
        print(f"  status      : {body.get('status')}")
        print(f"  receiver    : {body.get('receiver')}")
        print(f"  groupLabels : {body.get('groupLabels')}")
        print(f"  commonLabels: {body.get('commonLabels')}")
        print(f"  alerts      : {len(body.get('alerts', []))}")
        for a in body.get("alerts", []):
            print(f"    - {a['status']:8} {a['labels'].get('alertname')} "
                  f"{a['labels'].get('instance','')} sev={a['labels'].get('severity')}")
        self.send_response(200); self.end_headers(); self.wfile.write(b"ok")
    def log_message(self, *a): pass

HTTPServer(("0.0.0.0", 5001), H).serve_forever()
PY
python3 ~/pca-lab/sink.py &
```

Now write a routing tree that exercises everything. `~/pca-lab/alertmanager/alertmanager.yml`:

```yaml
global:
  resolve_timeout: 5m

route:
  receiver: default
  group_by: ['alertname', 'cluster']
  group_wait: 10s
  group_interval: 30s
  repeat_interval: 5m

  routes:
    # 1. Drop the watchdog and anything explicitly severity=none
    - receiver: dev-null
      matchers:
        - severity = "none"

    # 2. Critical goes fast, with a per-team child route
    - receiver: pager
      matchers:
        - severity = "critical"
      group_wait: 5s
      group_interval: 30s
      repeat_interval: 2m
      routes:
        - receiver: pager-database
          matchers:
            - team = "database"

      matchers:
        - severity = "warning"
      group_by: ['alertname']
      group_wait: 30s
      group_interval: 1m
      repeat_interval: 10m

    # 4. Audit sees EVERYTHING because continue: true
    - receiver: audit
      matchers:
        - alertname =~ ".+"
      continue: true

inhibit_rules:
  - source_matchers:
      - severity = "critical"
    target_matchers:
      - severity = "warning"
    equal: ['alertname', 'cluster']

receivers:
  - name: default
    webhook_configs:

  - name: dev-null

  - name: pager

  - name: pager-database
    webhook_configs:
```

Then test specific label sets against it. Do each of these and predict the answer first:

```bash
AM="docker exec alertmanager amtool --alertmanager.url=http://localhost:9093"

$AM config routes test severity=critical
```

Note that `severity=critical team=database` reaches `pager-database`, not `pager`. Matching **descends** into children. And `severity=info` falls through to `default`, because no route matches it except the catch-all audit route with `continue: true`, which does not stop the walk.

Now inject alerts by hand, which lets you test routing without waiting for real conditions:

```bash
send() {
  curl -s -XPOST http://localhost:9093/api/v2/alerts -H 'Content-Type: application/json' -d "$1" > /dev/null
}

# One critical alert
send '[{
  "labels": {"alertname":"DiskFull","severity":"critical","cluster":"pca-lab","instance":"node1","team":"platform"},
  "annotations": {"summary":"Disk full on node1"},
  "startsAt": "'$(date -u +%Y-%m-%dT%H:%M:%SZ)'"
}]'
```

Watch the sink output. You should see it arrive at `/pager` after about 5 seconds (`group_wait: 5s`) **and** at `/audit` because of `continue: true`.

Now demonstrate **grouping**. Send five alerts with the same `alertname` and `cluster`:

```bash
for i in 1 2 3 4 5; do
send '[{
  "labels": {"alertname":"InstanceDown","severity":"critical","cluster":"pca-lab","instance":"node'$i'"},
  "annotations": {"summary":"node'$i' down"},
  "startsAt": "'$(date -u +%Y-%m-%dT%H:%M:%SZ)'"
}]'
done
```

One notification arrives at `/pager` containing **five alerts**, because they share `alertname` and `cluster`. That is grouping working.

Now show that a **different** `cluster` makes a **different** group:

```bash
send '[{
  "labels": {"alertname":"InstanceDown","severity":"critical","cluster":"other","instance":"node9"},
  "startsAt": "'$(date -u +%Y-%m-%dT%H:%M:%SZ)'"
}]'
```

A separate notification, with its own `group_wait`.

Now demonstrate **`group_interval`**. While the first group is still firing, add a sixth instance:

```bash
send '[{
  "labels": {"alertname":"InstanceDown","severity":"critical","cluster":"pca-lab","instance":"node6"},
  "startsAt": "'$(date -u +%Y-%m-%dT%H:%M:%SZ)'"

```

Note the timestamp. The notification does **not** arrive immediately; it waits until the next `group_interval` (30s) boundary, then arrives containing all six. That delay is the thing people get wrong.

Now demonstrate **`repeat_interval`**. Do nothing for two minutes and keep re-sending the same alerts so they stay active:

```bash

  for i in 1 2 3 4 5 6; do
    send '[{"labels":{"alertname":"InstanceDown","severity":"critical","cluster":"pca-lab","instance":"node'$i'"},"startsAt":"'$(date -u +%Y-%m-%dT%H:%M:%SZ)'"}]'
  done
  sleep 20
done &
REPEATER=$!
```

Every 2 minutes (`repeat_interval: 2m`) an identical notification arrives. That is the reminder behaviour. Kill it when you have seen it twice:

```bash

```

## Exam tips

- **Ports: Alertmanager 9093, cluster gossip 9094.**
- Routing: **first matching sibling wins, then descend into children.** `continue: true` allows multiple receivers.
- Children **inherit** `receiver`, `group_by`, and the timers. They do **not** inherit `matchers`.
- The **root route matches everything** and cannot have matchers.
- **`group_wait` 30s** = new-group batching. **`group_interval` 5m** = throttle for changed groups. **`repeat_interval` 4h** = reminder for unchanged groups. Memorise all three names, meanings, and defaults.
- A new alert joining an existing group waits for the next **`group_interval`**, not `group_wait`.
- `repeat_interval` must be **greater than** `group_interval`.
- **`group_by: ['...']` disables grouping entirely. `group_by: []` puts everything in one group.**
- Use `matchers:` with `=`, `!=`, `=~`, `!~`. Regexes are **fully anchored**. `match`/`match_re` are deprecated.
- A **missing label** is treated as the **empty string** in Alertmanager matchers, so `!=` and `!~` match it.
- Drop alerts by routing to an **empty receiver**.
- `send_resolved` defaults **true for webhook and PagerDuty**, **false for email and Slack**.
- `mute_time_intervals` suppresses **during**; `active_time_intervals` notifies **only during**.
- HA: Prometheus sends **every alert to every Alertmanager**; the cluster gossips **nflog and silences** to deduplicate. `alertmanager_cluster_health_score` of **0** is healthy.
- `amtool config routes show` and **`amtool config routes test`** answer "where does this alert go". `amtool check-config` validates.
- `resolve_timeout` default **5m**.
