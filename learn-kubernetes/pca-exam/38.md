# 38. Alerting Basics: When, What, And Why

**Domain:** Alerting and Dashboarding

## Concept Refresher

The curriculum item is literally "Alerting basics (when, what, and why)". This is the judgement half of the domain, and it is examinable as multiple choice because the guidance is opinionated and well documented.

### The core principle

> Alert on **symptoms**, not causes.

A symptom is something a user can perceive: errors, slowness, unavailability, wrong results. A cause is an internal condition: high CPU, a full disk, a restarted pod, a saturated thread pool.

```text
CAUSE                              SYMPTOM
disk 90% full                 ->   writes are failing
CPU saturated                 ->   requests are slow
one replica of five down      ->   (no symptom, capacity absorbed it)
cache hit ratio dropped       ->   latency increased
certificate expired           ->   TLS handshakes failing
```

The middle example is the point. A single replica down produces **no user-visible impact**, so it must not page anyone. A cause-based alert would have paged.

### The three questions for every alert

| Question | If the answer is no |
| --- | --- |
| **Is a human needed right now?** | It is not a page. Make it a ticket or a dashboard |
| **Is it actionable?** | Delete it, or write the runbook that makes it actionable |
| **Would a user notice?** | It is probably a cause. Consider a warning or ticket instead |

The canonical formulation: **every page must be urgent, actionable, and about real, ongoing or imminent user impact.**

### Severity levels

There is no enforced standard, but the conventional set is:

| Severity | Meaning | Destination |
| --- | --- | --- |
| `critical` | User impact now. Wake someone up | Pager |
| `warning` | Will become user impact if ignored. Handle in hours | Ticket, chat |
| `info` | Context only. Never notifies | Dashboard, log |
| `none` | Watchdog and pipeline canaries | Special handling |

The `severity` label is the primary routing key, which is why it belongs in `labels`, not `annotations`.

### What to alert on: the four questions of the golden signals

For any user-facing service, the minimum useful alert set is:

```yaml
# 1. Availability: are we serving errors?
      - alert: HighErrorRate
        expr: |
          sum by (job) (rate(http_requests_total{code=~"5.."}[5m]))
            / sum by (job) (rate(http_requests_total[5m])) > 0.02
        for: 10m
        labels: {severity: critical}

# 2. Latency: are we slow?
      - alert: HighLatency
        expr: |
          histogram_quantile(0.99,
            sum by (job, le) (rate(http_request_duration_seconds_bucket[5m]))) > 1
        for: 10m
        labels: {severity: critical}

# 3. Traffic: has traffic vanished (or exploded)?
      - alert: NoTraffic
        expr: sum by (job) (rate(http_requests_total[10m])) == 0
        for: 10m
        labels: {severity: critical}

# 4. Saturation: are we about to run out of something?
      - alert: DiskWillFillIn4Hours
        expr: |
          predict_linear(node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}[6h], 4*3600) < 0
            and on (instance, mountpoint)
          node_filesystem_avail_bytes / node_filesystem_size_bytes < 0.2
        for: 30m
        labels: {severity: warning}
```

Note that saturation is a **cause**, so it is a `warning`, and it is only useful when it is **predictive**. "Disk is 85% full" is noise. "Disk will be full in four hours at the current rate" is actionable.

### When to alert: choosing `for`

| Situation | `for` |
| --- | --- |
| Hard, unambiguous failure (target down, cert expired) | `5m` typical, `1m` if truly critical |
| Ratio or rate crossing a threshold | `5m`-`15m`, long enough to survive a blip |
| Something predictive (disk filling) | `30m`-`1h`, because the trend must be real |
| Watchdog / canary | `0` |
| Anything that flaps | Add `for` **and** `keep_firing_for` |

A rough rule: `for` should be long enough that the alert would not have fired during a single bad scrape or a deploy, and short enough that the burn is not over before you are told.

### Thresholds versus SLO burn rates

Static thresholds have two failure modes:

- **Too sensitive**: a 1% error rate for 30 seconds pages you, even though the monthly budget is untouched.
- **Too insensitive**: a 0.5% error rate that persists for a week silently eats the entire budget without ever crossing 2%.

Burn-rate alerting fixes both by measuring error rate **relative to the error budget**.

```text
SLO           = 99.9% availability over 30 days
Error budget  = 0.1% of requests
Burn rate     = observed error ratio / (1 - SLO)

burn rate 1   = budget exactly exhausted at the end of the 30 days
burn rate 14.4= budget exhausted in ~2 days   (2% of 30d)
burn rate 6   = budget exhausted in ~5 days
burn rate 1   = budget exhausted in 30 days
```

### Multi-window multi-burn-rate alerting

The standard pattern from the Google SRE Workbook, and the reference answer for "how should you alert on an SLO".

| Severity | Burn rate | Long window | Short window | Budget consumed to trigger | Detection time |
| --- | ---: | --- | --- | ---: | --- |
| Page | 14.4 | 1h | 5m | 2% | fast |
| Page | 6 | 6h | 30m | 5% | medium |
| Ticket | 3 | 1d | 2h | 10% | slow |
| Ticket | 1 | 3d | 6h | 10% | very slow |

The **short window** is an `and` guard requiring the problem to still be happening right now, which makes the alert **resolve quickly** once the burn stops.

```yaml
groups:
  - name: slo_burn
    rules:
      # Record short and long window error ratios once
      - record: job:slo_errors:ratio_rate5m
        expr: |
          sum by (job) (rate(http_requests_total{code=~"5.."}[5m]))
            / sum by (job) (rate(http_requests_total[5m]))
      - record: job:slo_errors:ratio_rate30m
        expr: |
          sum by (job) (rate(http_requests_total{code=~"5.."}[30m]))
            / sum by (job) (rate(http_requests_total[30m]))
      - record: job:slo_errors:ratio_rate1h
        expr: |
          sum by (job) (rate(http_requests_total{code=~"5.."}[1h]))
            / sum by (job) (rate(http_requests_total[1h]))
      - record: job:slo_errors:ratio_rate6h
        expr: |
          sum by (job) (rate(http_requests_total{code=~"5.."}[6h]))
            / sum by (job) (rate(http_requests_total[6h]))

      - alert: ErrorBudgetBurnFast
        expr: |
          job:slo_errors:ratio_rate1h  > (14.4 * 0.001)
            and
          job:slo_errors:ratio_rate5m  > (14.4 * 0.001)
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Burning 30d error budget 14.4x too fast on {{ $labels.job }}"

      - alert: ErrorBudgetBurnSlow
        expr: |
          job:slo_errors:ratio_rate6h  > (6 * 0.001)
            and
          job:slo_errors:ratio_rate30m > (6 * 0.001)
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "Burning 30d error budget 6x too fast on {{ $labels.job }}"
```

`0.001` is `1 - 0.999`, the error budget for a 99.9% SLO. Multiply it by the burn rate to get the threshold.

Note the use of **recording rules** here. `rate(...[6h])` in an alert evaluated every 15 seconds is expensive; recording it once per interval is the standard optimisation.

Error budget remaining, for a dashboard:

```promql
1 - (
  sum(increase(http_requests_total{code=~"5.."}[30d]))
    /
  (0.001 * sum(increase(http_requests_total[30d])))
)
```

That returns 1 when the budget is untouched and 0 when exhausted, going negative when overspent.

### Alert fatigue and how it kills you

Signs your alerting is broken:

- Alerts routinely auto-resolve before anyone looks.
- On-call has standing silences for alerts nobody intends to fix.
- The runbook says "usually resolves itself".
- More than a handful of pages per on-call shift.
- Anyone says "just ignore that one".

The fix is always to **delete or downgrade the alert**, or fix the underlying instrumentation. Adding a longer `for` or a silence is a workaround, not a fix.

### What NOT to alert on

| Do not page on | Why | What to do instead |
| --- | --- | --- |
| CPU utilisation being high | High CPU with acceptable latency is efficiency, not a problem | Alert on latency; dashboard the CPU |
| A single replica down in a healthy pool | No user impact | Alert on `count(up == 1) < N` or on the symptom |
| Memory usage being high | Caches and JVMs use available memory by design | Alert on OOM kills, or on latency |
| Every restart | Some restarts are normal | Alert on **repeated** restarts: `changes(process_start_time_seconds[15m]) > 3` |
| Disk 80% full | Not urgent, and often static | Alert on `predict_linear()` with an absolute guard |
| Individual slow requests | Tails are normal | Alert on a quantile or on the SLO burn rate |
| Absolute error counts | Meaningless without traffic context | Alert on the **ratio** |

That last row is worth internalising: `rate(errors_total[5m]) > 10` means something completely different at 100 rps and at 100,000 rps. **Always alert on ratios for error conditions.**

### Alerting on the monitoring itself

If Prometheus is down, no alert can fire. That is the fundamental gap, and there are two standard answers.

1. **A Watchdog / DeadMansSwitch alert** that always fires, routed to something external that pages when the heartbeat **stops**.

```yaml
      - alert: Watchdog
        expr: vector(1)
        labels:
          severity: none
        annotations:
          summary: "Always firing. Page if this stops arriving."
```

2. **Meta-monitoring**: a second Prometheus that scrapes the first.

```yaml
      - alert: PrometheusDown
        expr: up{job="prometheus"} == 0
        for: 5m

      - alert: PrometheusNotIngesting
        expr: rate(prometheus_tsdb_head_samples_appended_total[5m]) == 0
        for: 10m

      - alert: PrometheusTooManyRestarts
        expr: changes(process_start_time_seconds{job="prometheus"}[15m]) > 2

      - alert: PrometheusConfigReloadFailed
        expr: prometheus_config_last_reload_successful == 0
        for: 5m

      - alert: PrometheusTargetsMissing
        expr: prometheus_sd_discovered_targets == 0
        for: 10m

      - alert: AlertmanagerConfigInconsistent
        expr: count by (job) (count by (job, hash) (alertmanager_config_hash)) > 1
        for: 10m
```

That last one is a nice pattern: if cluster members disagree on the config hash, they will route differently.

### Alert quality checklist

Before shipping an alert:

```text
[ ] Is it symptom-based, or a justified predictive cause?
[ ] Is the threshold derived from an SLO, not guessed?
[ ] Does it use a ratio, not an absolute count, for error conditions?
[ ] Does `for` survive a single bad scrape and a deploy?
[ ] Does it use rate() not irate() ?
[ ] Is the severity right, and does it route to the right place?
[ ] Do the annotations say what is wrong, where, and how bad ($value)?
[ ] Is there a runbook_url?
[ ] Will it resolve on its own when the condition clears?
[ ] Is it inhibited by more severe alerts that imply it?
[ ] Have you tested it with promtool test rules ?
```

The `irate()` line is worth calling out: **never use `irate()` in an alerting rule.** It uses only the last two samples, so it is extremely spiky and will both flap and miss. `rate()` is the alerting function.

## Hands-on

Build a complete SLO burn-rate alerting setup, which is the most valuable thing in this file.

Define the SLO: **99.9% of `myapp` requests succeed, measured over 30 days.** Error budget ratio is `0.001`.

`~/pca-lab/rules/slo.yml`:

```yaml
groups:
  # Record the windows once. Cheap for alerts to read.
  - name: slo_windows
    interval: 30s
    rules:
      - record: job:slo_requests:rate5m
        expr: sum by (job) (rate(myapp_http_requests_total[5m]))
      - record: job:slo_errors:rate5m
        expr: sum by (job) (rate(myapp_http_requests_total{code=~"5.."}[5m]))

      - record: job:slo_errors:ratio_rate5m
        expr: |
          sum by (job) (rate(myapp_http_requests_total{code=~"5.."}[5m]))
            /
          sum by (job) (rate(myapp_http_requests_total[5m]))

      - record: job:slo_errors:ratio_rate30m
        expr: |
          sum by (job) (rate(myapp_http_requests_total{code=~"5.."}[30m]))
            /
          sum by (job) (rate(myapp_http_requests_total[30m]))

      - record: job:slo_errors:ratio_rate1h
        expr: |
          sum by (job) (rate(myapp_http_requests_total{code=~"5.."}[1h]))
            /
          sum by (job) (rate(myapp_http_requests_total[1h]))

      - record: job:slo_errors:ratio_rate2h
        expr: |
          sum by (job) (rate(myapp_http_requests_total{code=~"5.."}[2h]))
            /
          sum by (job) (rate(myapp_http_requests_total[2h]))

      - record: job:slo_errors:ratio_rate6h
        expr: |
          sum by (job) (rate(myapp_http_requests_total{code=~"5.."}[6h]))
            /
          sum by (job) (rate(myapp_http_requests_total[6h]))

      # Burn rate expressed directly, for dashboards
      - record: job:slo_burnrate1h:ratio
        expr: job:slo_errors:ratio_rate1h / 0.001
      - record: job:slo_burnrate6h:ratio
        expr: job:slo_errors:ratio_rate6h / 0.001

  - name: slo_burn_alerts
    rules:
      # 14.4x over 1h, guarded by 5m. Consumes 2% of budget. PAGE.
      - alert: SLOErrorBudgetBurnVeryFast
        expr: |
          job:slo_errors:ratio_rate1h > (14.4 * 0.001)
            and
          job:slo_errors:ratio_rate5m > (14.4 * 0.001)
        for: 2m
        labels:
          severity: critical
          slo: myapp_availability
        annotations:
          summary: "{{ $labels.job }} is burning the 30d error budget 14.4x too fast"
          description: "1h error ratio is {{ $value | humanizePercentage }}. At this rate 2% of the budget is gone every hour."
          runbook_url: "https://runbooks.example.com/SLOBurn"

      # 6x over 6h, guarded by 30m. Consumes 5% of budget. PAGE.
      - alert: SLOErrorBudgetBurnFast
        expr: |
          job:slo_errors:ratio_rate6h > (6 * 0.001)
            and
          job:slo_errors:ratio_rate30m > (6 * 0.001)
        for: 15m
        labels:
          severity: critical
          slo: myapp_availability
        annotations:
          summary: "{{ $labels.job }} is burning the 30d error budget 6x too fast"

      # 3x over 1d, guarded by 2h. TICKET.
      - alert: SLOErrorBudgetBurnSlow
        expr: |
          job:slo_errors:ratio_rate1h > (3 * 0.001)
            and
          job:slo_errors:ratio_rate2h > (3 * 0.001)
        for: 1h
        labels:
          severity: warning
          slo: myapp_availability
        annotations:
          summary: "{{ $labels.job }} is slowly burning the error budget (3x)"

  - name: symptom_alerts
    rules:
      - alert: NoTraffic
        expr: sum by (job) (rate(myapp_http_requests_total[10m])) == 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.job }} is receiving no traffic at all"

      - alert: LatencySLOBreach
        expr: |
          (
            sum(rate(myapp_http_request_duration_seconds_bucket{le="0.3"}[5m]))
              /
            sum(rate(myapp_http_request_duration_seconds_count[5m]))
          ) < 0.95
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: "Only {{ $value | humanizePercentage }} of requests are under 300ms (SLO: 95%)"
```

Note the latency alert. Because the histogram has a bucket at exactly `0.3`, this is an **exact** ratio, not an interpolated quantile. That is the right way to alert on a latency SLO.

Now demonstrate why the **short-window guard** matters. Stop the error source by pointing the recording rules at a clean metric, or simpler, watch what happens when errors stop. Reduce the app's error rate:

## Exam tips

- **Alert on symptoms, not causes.** Every page must be **urgent, actionable, and about real user impact**.
- A single replica down in a healthy pool is **not** an alert. High CPU with good latency is **not** an alert.
- **Always alert on ratios for error conditions**, never absolute counts. `> 10 errors/sec` is meaningless without traffic context.
- **Never use `irate()` in an alerting rule.** Use `rate()`.
- `severity` belongs in **`labels`** because it drives routing. Conventional set: `critical` pages, `warning` tickets, `info` never notifies, `none` for canaries.
- **Error budget = `1 - SLO`.** For 99.9%, that is **0.001**.
- **Burn rate = observed error ratio / (1 - SLO).** Burn rate 1 exhausts the budget exactly at the window's end.
- Memorise the standard table: **14.4x over 1h guarded by 5m (2% of budget, page)**, **6x over 6h guarded by 30m (5%, page)**, **3x over 1d guarded by 2h (10%, ticket)**.
- Threshold = **burn rate x budget ratio**. For 14.4x on 99.9%, that is `> 0.0144`.
- The **short window is an `and` guard** that makes the alert resolve quickly once the burn stops.
- Use **recording rules** for long-window rates in burn-rate alerts.
- Static thresholds miss **slow burns** below the threshold and fire on **brief spikes** that cost no budget. That is why burn rates exist.
- Predictive saturation alerts (`predict_linear()`) are legitimate cause-based alerts, usually **`warning`**, and need an **absolute-usage guard**.
- **Watchdog / DeadMansSwitch** = `vector(1)`, always firing, escalate when it **stops**. Necessary because a dead Prometheus fires nothing.
- Meta-monitor with `up{job="prometheus"}`, `rate(prometheus_tsdb_head_samples_appended_total[5m]) == 0`, `prometheus_config_last_reload_successful == 0`, `prometheus_notifications_alertmanagers_discovered < 1`, and divergent `alertmanager_config_hash`.
- Alert on **repeated** restarts with `changes(process_start_time_seconds[15m]) > N`, not on any restart.
- A permanent silence means the alert is wrong. **Delete or downgrade it.**
- Absence of traffic (`rate(requests_total[10m]) == 0`) is a strong outage symptom.
