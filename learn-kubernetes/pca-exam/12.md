# 12. Metric Types In Depth

**Domain:** Prometheus Fundamentals

## Concept Refresher

Four core types. Choosing the wrong one is the most common instrumentation mistake, and the exam tests the distinction repeatedly.

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ COUNTER    monotonically increasing, resets to 0 on process restart      │
│            "how many times has X happened since start"                    │
│            Suffix: _total          Never use the raw value                │
│            Always wrap in rate() / irate() / increase()                   │
│            Examples: requests, errors, bytes sent, jobs completed         │
├──────────────────────────────────────────────────────────────────────────┤
│ GAUGE      goes up and down, snapshot of a current value                  │
│            "what is X right now"                                          │
│            Use the raw value directly                                     │
│            Examples: temperature, queue depth, in-flight requests,        │
│                      memory bytes, replicas desired                       │
├──────────────────────────────────────────────────────────────────────────┤
│ HISTOGRAM  samples observations into CUMULATIVE buckets                   │
│            Server-side quantiles, aggregatable across instances           │
│            Series: _bucket{le="..."}  _sum  _count                        │
│            Examples: request duration, response size                      │
├──────────────────────────────────────────────────────────────────────────┤
│ SUMMARY    client-side pre-computed quantiles                             │
│            CANNOT be aggregated across instances                          │
│            Series: name{quantile="..."}  _sum  _count                     │
│            Use only when you need an exact quantile per instance          │
└──────────────────────────────────────────────────────────────────────────┘
```

### Counter

```text
# HELP http_requests_total Total HTTP requests.
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 48291
```

Rules:

- Only ever goes up, or resets to 0 on restart.
- Suffix `_total` by convention (mandatory in OpenMetrics).
- The **absolute value is meaningless**. `http_requests_total` tells you nothing useful; `rate(http_requests_total[5m])` tells you requests per second.
- `rate()` and `increase()` automatically **detect and correct for counter resets**.
- Counters can be float. `increase()` may return a non-integer because of extrapolation.

Wrong and right:

```promql
http_requests_total                       # meaningless in a dashboard
rate(http_requests_total[5m])             # per-second rate. Correct
increase(http_requests_total[1h])         # count over the hour. Correct
```

### Gauge

```text
# HELP node_memory_MemAvailable_bytes Available memory in bytes.
# TYPE node_memory_MemAvailable_bytes gauge
node_memory_MemAvailable_bytes 8.32405504e+09
```

Rules:

- Use the value directly.
- `rate()` on a gauge is a bug. Use `deriv()` if you genuinely want a slope, or `delta()` for the change.
- Aggregate over time with `avg_over_time`, `max_over_time`, `min_over_time`.
- A "gauge that only goes up" (like a timestamp) is still a gauge, not a counter. `*_timestamp_seconds` metrics are gauges.

### Histogram

```text
# HELP http_request_duration_seconds Request duration.
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.05"} 120
http_request_duration_seconds_bucket{le="0.1"}  180
http_request_duration_seconds_bucket{le="0.5"}  240
http_request_duration_seconds_bucket{le="1"}    250
http_request_duration_seconds_bucket{le="+Inf"} 255
http_request_duration_seconds_sum   43.2
http_request_duration_seconds_count 255
```

Critical facts:

- Buckets are **cumulative**. `le="0.5"` counts every observation ≤ 0.5 seconds, including those already counted in `le="0.1"`.
- The `+Inf` bucket is **mandatory** and always equals `_count`.
- Each `_bucket` series is a **counter**, so you need `rate()` before `histogram_quantile()`.
- Bucket boundaries are **chosen at instrumentation time** and are fixed. Choose them to bracket your SLO thresholds.
- Quantiles are **estimated** by linear interpolation within the matched bucket.
- Histograms **can** be aggregated across instances: `sum by (le) (rate(..._bucket[5m]))`.
- Average from a histogram: `rate(_sum[5m]) / rate(_count[5m])`.
- Cardinality cost: `number of buckets + 2` series per label combination.

### Summary

```text
# HELP rpc_duration_seconds RPC latency.
# TYPE rpc_duration_seconds summary
rpc_duration_seconds{quantile="0.5"}  0.032
rpc_duration_seconds{quantile="0.9"}  0.11
rpc_duration_seconds{quantile="0.99"} 0.44
rpc_duration_seconds_sum   4823.1
rpc_duration_seconds_count 92183
```

Critical facts:

- Quantiles are computed **in the client**, over a sliding time window.
- **You cannot aggregate quantiles.** Averaging p99 across ten instances does not give you the fleet p99. There is no mathematically valid way to combine pre-computed quantiles.
- The `quantile` label values are fixed at instrumentation time. You cannot ask for p95 later if only p50/p90/p99 were configured.
- `_sum` and `_count` **can** be aggregated, so `rate(_sum[5m]) / rate(_count[5m])` gives a valid average.
- Cheaper on the server, more expensive on the client (maintaining the sliding window costs CPU).
- Some client libraries expose a summary with only `_sum` and `_count`, no quantiles. That is fine and cheap.

### Histogram vs Summary decision table

| Need | Choose |
| --- | --- |
| Aggregate latency across instances | **Histogram** |
| Arbitrary quantile computed at query time | **Histogram** |
| Exact quantile, no interpolation error | **Summary** |
| Minimal client CPU | **Histogram** |
| Minimal server cardinality | **Summary** |
| SLO-driven "fraction under threshold" | **Histogram** |
| You do not know good bucket boundaries in advance | **Native histogram**, or a summary |

Default answer for the exam: **histogram**, because aggregation is almost always required.

### Native histograms

Prometheus 2.40+ (experimental, enable with `--enable-feature=native-histograms`) supports **native histograms**:

- Buckets are generated automatically with exponential boundaries controlled by a `schema` number.
- Stored as a **single** sample per series, not `N` bucket series. Massive cardinality reduction.
- Resolution can be reduced at query time.
- Require the **protobuf** exposition format (classic text format cannot carry them; OpenMetrics 2.0 adds support).
- `histogram_quantile()` works on them directly, without `rate()` on `_bucket`, though you still use `rate()` on the histogram itself.
- Companion functions: `histogram_count`, `histogram_sum`, `histogram_avg`, `histogram_fraction`, `histogram_stddev`, `histogram_stdvar`.

### OpenMetrics extra types

| Type | Use |
| --- | --- |
| `info` | Static metadata. Series named `*_info`, value always 1, all the information in labels. Example: `version_info{version="1.2.3", commit="abc"} 1` |
| `stateset` | One series per possible state, exactly one is 1. Example: `node_state{state="ready"} 1` |
| `gaugehistogram` | Histogram whose buckets are gauges, can decrease. Example: queue latency distributions |
| `unknown` / `untyped` | No semantics declared |

The **info pattern** matters: rather than putting a version label on every metric (multiplying cardinality), expose one `*_info` metric and join it at query time with `group_left`.

### Choosing the right type: worked examples

| Measurement | Type | Why |
| --- | --- | --- |
| Total HTTP requests served | Counter | Monotonic event count |
| Requests currently in flight | Gauge | Goes up and down |
| Total bytes written to disk | Counter | Monotonic |
| Free disk bytes | Gauge | Fluctuates |
| Request latency | Histogram | Need distribution and aggregation |
| Queue length | Gauge | Snapshot |
| Number of restarts | Counter | Monotonic |
| Last successful backup time | Gauge | It is a timestamp, not a count |
| CPU seconds consumed | Counter | Monotonic accumulation |
| Temperature | Gauge | Can fall |
| Cache hit ratio | Two counters (hits and total), ratio computed in PromQL | Never expose a pre-computed ratio |
| Build version | Info (`*_info` gauge = 1) | Metadata in labels |

Rule: **never expose a pre-computed ratio, average, or percentage.** Expose the numerator and denominator as counters and let PromQL do the arithmetic. Otherwise you cannot re-aggregate.

## Answers

**Q1: B.** Counter. Monotonically increasing event count.

**Q2: B.** Gauge. Connections open and close, so the value falls as well as rises.

**Q3: B.** `_total`. It is a convention in the Prometheus text format and mandatory in OpenMetrics.

**Q4: B.** A counter is cumulative since process start. Its absolute value depends on how long the process has been up, which is not what you want to know. Its **rate** is the signal.

**Q5: B.** `_bucket{le}`, `_sum`, `_count`. Option A describes a summary.

**Q6: B.** Cumulative, less-than-or-equal semantics. This is why `histogram_quantile` can interpolate and why buckets are monotonically non-decreasing across `le`.

**Q7: C.** `le="+Inf"` is required.

**Q8: B.** `_count`, because every observation is ≤ infinity.

**Q9: B.** There is no valid mathematics for combining pre-computed quantiles from separate populations. You would need the underlying distribution, which the summary discarded.

**Q10: B.** Histogram. `histogram_quantile(0.99, sum by (le) (rate(x_bucket[5m])))` aggregates buckets first, then estimates the quantile.

**Q11: B.** `rate(_sum) / rate(_count)`. This works for both histograms and summaries.

**Q12: B.** Exact per-instance quantiles with known targets ahead of time. Summaries cost more client CPU, not less, so D is wrong.

**Q13: C.** 14. The formula is **bucket series + 2**: twelve `_bucket` series plus `_sum` plus `_count`. Always count `+Inf` as one of the bucket series, and never forget the `_sum` and `_count` pair.

**Q14: B.** One sample carries the entire distribution with exponential buckets defined by a schema. This is the headline benefit: cardinality collapses.

**Q15: B.** `*_info` metrics always have value 1 and carry metadata in labels, to be joined at query time with `group_left` instead of polluting every metric.

**Q16: B.** Expose the parts, compute the ratio at query time. A pre-computed ratio cannot be summed or averaged correctly across instances.

**Q17: B.** No enforcement. Types are metadata only. `rate()` on a gauge is a silent bug.

**Q18: B.** Gauge. It is a timestamp value, not an accumulating count. All `*_timestamp_seconds` metrics are gauges.

**Q19: B.** Put boundaries around your SLO threshold so you can compute the fraction under it exactly, with no interpolation.

**Q20: B.** Protobuf exposition (and OpenMetrics 2.0). The classic text format has no native histogram syntax.

## Hands-on

Inspect each type in the raw exposition:

```bash
# Counter
curl -s http://localhost:9100/metrics | grep -A2 '^# TYPE node_cpu_seconds_total'

# Gauge
curl -s http://localhost:9100/metrics | grep -A2 '^# TYPE node_memory_MemAvailable_bytes'

# Histogram
curl -s http://localhost:8080/metrics | grep -E 'demo_api_request_duration_seconds(_bucket|_sum|_count)' | head -20

# Prometheus' own summary
curl -s http://localhost:9090/metrics | grep -E 'prometheus_target_interval_length_seconds' | head
```

Prove buckets are cumulative:

```promql
demo_api_request_duration_seconds_bucket{instance="demo-a:8080"}
```

Values must be non-decreasing as `le` increases, and the `+Inf` value must equal:

```promql
demo_api_request_duration_seconds_count{instance="demo-a:8080"}
```

Verify that equality explicitly:

```promql
demo_api_request_duration_seconds_bucket{le="+Inf"}
  == on(instance, job, method, path, status)
demo_api_request_duration_seconds_count
```

Compute the average from a histogram:

```promql
rate(demo_api_request_duration_seconds_sum[5m])
  / rate(demo_api_request_duration_seconds_count[5m])
```

Aggregate a histogram properly, then compute p99:

```promql
histogram_quantile(0.99, sum by (le) (rate(demo_api_request_duration_seconds_bucket[5m])))
```

Compare with the wrong approach (averaging quantiles per instance):

```promql
avg(histogram_quantile(0.99, rate(demo_api_request_duration_seconds_bucket[5m])))
```

Note the numbers differ. The first is correct.

Demonstrate why the raw counter is useless:

```promql
node_cpu_seconds_total{mode="idle", cpu="0"}
rate(node_cpu_seconds_total{mode="idle", cpu="0"}[5m])
```

Graph both. The first is a ramp whose slope is the real signal.

Demonstrate a counter reset:

```bash
docker restart demo-a
```

```promql
demo_api_request_duration_seconds_count{instance="demo-a:8080"}
rate(demo_api_request_duration_seconds_count{instance="demo-a:8080"}[5m])
resets(demo_api_request_duration_seconds_count{instance="demo-a:8080"}[1h])
```

The raw series drops to near zero. The `rate()` stays sane because it corrects for the reset. `resets()` counts how many resets happened.

Push each type by hand and inspect what promtool says:

```bash
cat > /tmp/types.txt <<'EOF'
# HELP demo_requests_total Total requests.
# TYPE demo_requests_total counter
demo_requests_total 100
# HELP demo_queue_depth Current queue depth.
# TYPE demo_queue_depth gauge
demo_queue_depth 7
# HELP demo_latency_seconds Latency.
# TYPE demo_latency_seconds histogram
demo_latency_seconds_bucket{le="0.1"} 5
demo_latency_seconds_bucket{le="0.5"} 12
demo_latency_seconds_bucket{le="+Inf"} 15
demo_latency_seconds_sum 3.4
demo_latency_seconds_count 15
# HELP demo_build_info Build metadata.
# TYPE demo_build_info gauge
demo_build_info{version="1.4.2",commit="deadbeef"} 1
EOF

promtool check metrics < /tmp/types.txt
curl --data-binary @/tmp/types.txt http://localhost:9091/metrics/job/typedemo
```

Now practise the info-metric join pattern:

```promql
demo_requests_total * on(job) group_left(version) demo_build_info
```

Break the histogram to see validation fire:

```bash
cat > /tmp/badhist.txt <<'EOF'
# TYPE bad_latency_seconds histogram
bad_latency_seconds_bucket{le="0.5"} 12
bad_latency_seconds_bucket{le="0.1"} 20
bad_latency_seconds_bucket{le="+Inf"} 15
bad_latency_seconds_sum 3.4
bad_latency_seconds_count 15
EOF
promtool check metrics < /tmp/badhist.txt
```

Buckets that decrease as `le` grows are invalid, and `+Inf` not matching `_count` is invalid.

## Exam tips

- Counter = monotonic, suffix `_total`, **always** wrap in `rate`/`increase`. Raw value is meaningless.
- Gauge = up and down, use directly, aggregate with `*_over_time`.
- Histogram = **cumulative** `_bucket{le}` + `_sum` + `_count`. `+Inf` is mandatory and equals `_count`. Aggregatable. Quantiles estimated at query time.
- Summary = client-computed `{quantile}` + `_sum` + `_count`. **Quantiles cannot be aggregated.** Exact per instance.
- Need fleet-wide percentiles? **Histogram.** This is the single most common question in the domain.
- Average latency from either type: `rate(_sum[5m]) / rate(_count[5m])`.
- Series per histogram = **bucket series + 2**.
- Native histograms: one sample, exponential auto-buckets, protobuf exposition, feature-flagged.
- `*_info` metrics are value-1 metadata carriers, joined with `group_left`.
- Never expose pre-computed ratios, averages, or percentages. Expose numerator and denominator.
- The server does **not** enforce types. Wrong function on wrong type = silent nonsense.
- `*_timestamp_seconds` is a **gauge**, not a counter.
