# 20. Binary Operators And Vector Matching

**Domain:** PromQL

## Concept Refresher

### The three operator families

```text
ARITHMETIC   + - * / % ^
COMPARISON   == != > < >= <=
LOGICAL/SET  and  or  unless
```

### Arithmetic operators

| Operator | Meaning |
| --- | --- |
| `+` | Addition |
| `-` | Subtraction |
| `*` | Multiplication |
| `/` | Division |
| `%` | Modulo |
| `^` | Exponentiation (right associative) |

Operator precedence, highest to lowest:

```text
^
* / % atan2
+ -
== != <= < >= >
and unless
or
```

`^` is **right associative**: `2 ^ 3 ^ 2` is `2 ^ 9` = 512, not `64`.

### Comparison operators

Comparisons between a vector and a scalar act as a **filter** by default:

```promql
up == 0                     # returns only the series where up is 0
node_load1 > 2              # returns only series above 2, with original values
```

Add the `bool` modifier to get 0/1 instead of filtering:

```promql
up == bool 0                # every series, valued 1 where up==0 and 0 otherwise
node_load1 > bool 2         # 1 or 0 for every series
```

This distinction is heavily examined. **Without `bool`, comparison filters. With `bool`, it maps to 0/1 and keeps every series.**

Between two vectors, comparison also filters by default, returning the left-hand side's values for matching pairs where the comparison holds.

### Logical / set operators

These only work **vector to vector**, never with scalars.

| Operator | Result |
| --- | --- |
| `a and b` | Series from `a` that have a matching label set in `b`. Values come from `a` |
| `a or b` | All series from `a`, plus series from `b` that have no match in `a` |
| `a unless b` | Series from `a` that have **no** matching label set in `b` |

Set operators match on the **full label set** by default, and `on`/`ignoring` can narrow it.

Patterns:

```promql
# Only alert if BOTH conditions hold
node_filesystem_avail_bytes / node_filesystem_size_bytes < 0.1
  and
predict_linear(node_filesystem_avail_bytes[6h], 4*3600) < 0

# Exclude a subset
up == 0 unless on(instance) node_maintenance_mode == 1

# Provide a fallback of zero when a series is missing
sum(rate(errors_total[5m])) or vector(0)
```

### Vector matching: one-to-one

By default, a binary operation between two instant vectors matches series with **identical label sets**, after dropping the metric name.

```promql
method_code:http_errors:rate5m / method:http_requests:rate5m
```

Series with no partner on the other side are simply **absent from the result**. This silent dropping is the most common cause of "my query returns nothing".

Restrict or ignore labels during matching:

```promql
# Match using ONLY these labels
a / on(instance) b

# Match using ALL labels EXCEPT these
a / ignoring(cpu, mode) b
```

`on` and `ignoring` are mutually exclusive.

### Vector matching: many-to-one and one-to-many

When one side has more series than the other, you must declare which side is "many" using `group_left` or `group_right`.

```text
group_left   the LEFT side is the "many" side
group_right  the RIGHT side is the "many" side
```

The arrow points at the **many** side. Memorise it that way: `group_left` means "many on the left".

```promql
# Many error-rate series, one request-rate series per method
method_code:http_errors:rate5m / ignoring(code) group_left method:http_requests:rate5m
```

Optionally copy labels from the **one** side into the result:

```promql
a * on(instance) group_left(version, os) b
```

The labels listed in the parentheses are pulled from the "one" side onto the result.

### The info-metric join pattern

This is the single most useful `group_left` idiom, and the standard answer to "how do I add metadata without cardinality cost".

```promql
# node_exporter_build_info{instance="...", version="1.9.1", ...} = 1
node_load1 * on(instance) group_left(version) node_exporter_build_info
```

Multiplying by 1 preserves the value and attaches the `version` label.

Kubernetes example, joining pod metrics with the owning deployment:

```promql
sum by (pod) (rate(container_cpu_usage_seconds_total[5m]))
  * on(pod) group_left(owner_name)
  kube_pod_owner{owner_kind="ReplicaSet"}
```

### The metric name is dropped

Any binary operator between two vectors **drops `__name__`** from the result:

```promql
node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
# result has no __name__
```

Exception: a **vector-scalar** arithmetic operation also drops the name:

```promql
node_load1 * 2      # no __name__ in the result
```

But comparison filters (without `bool`) **keep** the name, because they return the original series:

```promql
node_load1 > 2      # __name__ is still node_load1
```

To give the result a name, use a recording rule.

### Scalar operands

```promql
node_load1 * 2                 # vector * scalar, element-wise
2 * node_load1                 # same
1 - avg(rate(x[5m]))           # scalar - vector
node_memory_MemTotal_bytes / 1024 / 1024    # bytes to MiB
```

`scalar()` converts a single-element vector to a scalar. If the vector has zero or more than one element, it returns `NaN`.

```promql
scalar(sum(up))
node_load1 > scalar(quantile(0.9, node_load1))
```

### Special values

```text
0 / 0    = NaN
1 / 0    = +Inf
-1 / 0   = -Inf
NaN in any comparison  = false
```

`NaN != NaN`. To detect NaN, there is no `is_nan()`; use `x != x` conceptually, though in practice you filter with `absent()` or guard your denominators.

Guard against division by zero:

```promql
sum(rate(errors_total[5m]))
  / clamp_min(sum(rate(requests_total[5m])), 1)
```

Or use `> 0` on the denominator:

```promql
(sum(rate(errors_total[5m])) / sum(rate(requests_total[5m])))
  and sum(rate(requests_total[5m])) > 0
```

### Diagnosing "my query returns nothing"

Checklist, in order:

```text
1. Run each side of the operator alone. Do both return series?
2. Compare the label sets. Are they identical?
   Use: count by (__name__) (a)   and inspect the Table view
3. If label sets differ, add on() or ignoring()
4. If the cardinality differs, add group_left or group_right
5. Check for a stray label like `le` or `cpu` on one side only
6. Remember the metric name is dropped, so it never needs to match
```

### Full worked examples

```promql
# Memory used ratio
1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)

# Disk used percentage
100 * (1 - node_filesystem_avail_bytes / node_filesystem_size_bytes)

# Error ratio, safe against zero traffic
sum by (job) (rate(http_requests_total{status=~"5.."}[5m]))
  / sum by (job) (rate(http_requests_total[5m]))

# Cache hit ratio from two counters
rate(cache_hits_total[5m]) / rate(cache_requests_total[5m])

# Requests per CPU core
sum by (instance) (rate(http_requests_total[5m]))
  / on(instance) count by (instance) (count by (instance, cpu) (node_cpu_seconds_total))

# Down targets excluding those in maintenance
up == 0 unless on(instance) instance_maintenance == 1

# Pods over their memory request
container_memory_working_set_bytes
  / on(pod, container) group_left
  kube_pod_container_resource_requests{resource="memory"} > 1.5

# Add version metadata
sum by (instance) (rate(node_cpu_seconds_total[5m]))
  * on(instance) group_left(version) node_exporter_build_info

# Boolean map for a scoreboard panel
up == bool 1

# Count how many are above a threshold
count(node_load1 > 2)

# Sum of a boolean, i.e. how many satisfy the condition
sum(node_load1 > bool 2)
```

## Answers

**Q1: B.** Without `bool`, comparison is a filter. Only matching series are returned, keeping their original values (and their metric name).

**Q2: B.** `bool` converts the comparison into 0/1 for **every** series, filtering nothing.

**Q3: B.** Identical label sets, with the metric name excluded from the comparison.

**Q4: B.** Silently omitted. This is by far the most common reason a query "returns nothing".

**Q5: B.** `on()`. Note `by()` is for aggregation, not matching. Confusing the two is a classic mistake.

**Q6: B.** `ignoring()`.

**Q7: B.** `group_left` means the left side is the many side. The arrow points at "many".

**Q8: B.** It declares left-many cardinality and lifts the named labels from the one side into the result.

**Q9: B.** Multiply by the info metric with `group_left(version)`.

**Q10: A.** `*_info` metrics always have the value 1, so multiplication is value-preserving while the join brings the labels across.

**Q11: B.** Set difference.

**Q12: B.** Set intersection, taking values from the left.

**Q13: B.** Set union, with the left side winning on conflicts.

**Q14: B.** `or vector(0)`. `vector(0)` creates a label-less series with value 0, which has no match on the left, so `or` includes it when the left is empty.

**Q15: B.** Set operators are vector-only.

**Q16: B.** Dropped. Any binary operation between vectors, and any vector-scalar arithmetic, removes the metric name.

**Q17: B.** Filtering comparisons return the original series unchanged, name included.

**Q18: B.** `+Inf`.

**Q19: C.** `NaN`.

**Q20: B.** Highest precedence and right associative.

**Q21: B.** Right associative, so `2 ^ (3 ^ 2)` = `2 ^ 9` = 512.

**Q22: C.** `NaN`. `scalar()` requires exactly one element.

**Q23: B.** Label set mismatch. Diagnose by inspecting both sides in the Table view and looking for extra labels such as `cpu`, `mode`, or `le`.

**Q24: B.** Filter with `> 2`, then `count()`.

**Q25: B.** `> bool 2` yields 1/0 for every series, so `sum()` counts the satisfying ones. Note that `sum(node_load1 > 2)` sums the **load values** of the matching series, which is a different and usually unintended result.

## Hands-on

Arithmetic and unit conversion:

```promql
node_memory_MemTotal_bytes
node_memory_MemTotal_bytes / 1024 / 1024 / 1024
node_load1 * 100
node_load1 % 1
2 ^ 10
2 ^ 3 ^ 2
```

Comparison as a filter versus `bool`:

```promql
up
up == 0
up == 1
up == bool 0
up == bool 1

# Count them the two ways
count(up == 1)
sum(up == bool 1)

node_load1
node_load1 > 0.1
node_load1 > bool 0.1
```

Compare the row counts in the Table tab. `> 0.1` returns a subset. `> bool 0.1` returns everything.

The critical distinction, demonstrated:

```promql
# Sums the LOAD VALUES of instances above 0.1
sum(node_load1 > 0.1)

# Counts HOW MANY instances are above 0.1
sum(node_load1 > bool 0.1)
count(node_load1 > 0.1)
```

Ratios with matching label sets:

```promql
node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)
100 * (1 - node_filesystem_avail_bytes / node_filesystem_size_bytes)
```

Note the result has no `__name__`.

Now break matching on purpose:

```promql
# Extra labels on the left (cpu, mode) prevent matching
rate(node_cpu_seconds_total{mode="idle"}[5m]) / node_load1

# Fix with on()
rate(node_cpu_seconds_total{mode="idle"}[5m]) / on(instance) node_load1

# Or with ignoring()
rate(node_cpu_seconds_total{mode="idle"}[5m]) / ignoring(cpu, mode, job) node_load1
```

The first returns nothing. Read that as the diagnostic signature of a label mismatch.

Many-to-one with `group_left`:

```promql
# Many cpu/mode series on the left, one load series per instance on the right
rate(node_cpu_seconds_total[5m]) / on(instance) group_left node_load1
```

The info-metric join:

```promql
node_exporter_build_info
node_load1
node_load1 * on(instance) group_left(version) node_exporter_build_info
node_load1 * on(instance) group_left(version, goversion) node_exporter_build_info
```

Confirm the value is unchanged and the labels are richer.

Do the same with Prometheus' own build info:

```promql
prometheus_build_info
prometheus_tsdb_head_series * on(instance) group_left(version) prometheus_build_info
```

Set operators:

```promql
# Intersection
up == 1 and node_load1 > 0

# Difference
up == 1 unless node_load1 > 100

# Union
up{job="demo"} or up{job="node"}

# Fallback to zero
sum(rate(nonexistent_metric_total[5m])) or vector(0)
sum(rate(demo_api_request_duration_seconds_count[5m])) or vector(0)
```

The compound alert condition pattern:

```promql
# Both must hold
(node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes < 0.5)
  and
(predict_linear(node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}[1h], 24*3600) < 0)
```

Exclusion pattern. Mark an instance as under maintenance and exclude it:

```bash
echo 'instance_maintenance{instance="demo-c:8080"} 1' \
  | curl --data-binary @- http://localhost:9091/metrics/job/maintenance
```

```bash
docker stop demo-c
sleep 30
```

```promql
up == 0
up == 0 unless on(instance) instance_maintenance == 1
```

The second excludes the maintained instance. Clean up:

```bash
docker start demo-c
curl -X DELETE http://localhost:9091/metrics/job/maintenance
```

Special values:

```promql
vector(1) / vector(0)
vector(0) / vector(0)
vector(-1) / vector(0)

# NaN never satisfies a comparison
(vector(0) / vector(0)) > 0
(vector(0) / vector(0)) < 0
(vector(0) / vector(0)) == 0
```

Guard a division:

```promql
# Unsafe when there is no traffic
sum(rate(demo_api_request_duration_seconds_count{status=~"5.."}[5m]))
  / sum(rate(demo_api_request_duration_seconds_count[5m]))

# Safe with clamp_min
sum(rate(demo_api_request_duration_seconds_count{status=~"5.."}[5m]))
  / clamp_min(sum(rate(demo_api_request_duration_seconds_count[5m])), 1)

# Safe with an and guard
(
  sum(rate(demo_api_request_duration_seconds_count{status=~"5.."}[5m]))
    / sum(rate(demo_api_request_duration_seconds_count[5m]))
) and sum(rate(demo_api_request_duration_seconds_count[5m])) > 0
```

`scalar()`:

```promql
scalar(sum(up))
scalar(up)                              # NaN, more than one element
node_load1 > scalar(quantile(0.9, node_load1))
node_load1 / scalar(max(node_load1))
```

Precedence experiments:

```promql
1 + 2 * 3
(1 + 2) * 3
2 ^ 3 ^ 2
(2 ^ 3) ^ 2
up == 1 and node_load1 > 0 or vector(99)
```

## Exam tips

- Comparison **without `bool` filters**. Comparison **with `bool` maps to 1/0 and keeps every series.** Know this cold.
- `sum(x > 2)` sums the **values** of qualifying series. `sum(x > bool 2)` **counts** them.
- Default vector matching is on **identical label sets, metric name excluded**. Unmatched series are **silently dropped**.
- `on(labels)` matches using only those. `ignoring(labels)` matches using everything else. Mutually exclusive.
- `by`/`without` are for **aggregation**. `on`/`ignoring` are for **matching**. Do not swap them.
- `group_left` = **many on the left**. `group_right` = many on the right. The arrow points at "many".
- `group_left(a, b)` copies labels `a` and `b` from the **one** side into the result.
- Info-metric join: `metric * on(instance) group_left(version) something_build_info`. Works because info metrics are always 1.
- `and` = intersection, `or` = union (left wins), `unless` = difference. **Vectors only, no scalars.**
- `or vector(0)` is the standard "default to zero" idiom.
- Binary operations between vectors **drop `__name__`**. Filtering comparisons **keep** it.
- `1/0 = +Inf`, `0/0 = NaN`. `NaN` fails every comparison.
- `^` is highest precedence and **right associative**: `2^3^2 = 512`.
- `scalar()` on a vector with anything other than exactly one element gives `NaN`.
- Empty result from a binary op? Run each side alone and compare label sets. That is the fix 90% of the time.
