# 21. Histograms And Quantiles

**Domain:** PromQL

## Concept Refresher

This is the most technically demanding PromQL topic and it appears reliably on the exam.

### What a classic histogram looks like on the wire

```text
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.05"}  120     ← ≤ 50ms
http_request_duration_seconds_bucket{le="0.1"}   180     ← ≤ 100ms (includes the 120)
http_request_duration_seconds_bucket{le="0.25"}  220
http_request_duration_seconds_bucket{le="0.5"}   240
http_request_duration_seconds_bucket{le="1"}     250
http_request_duration_seconds_bucket{le="+Inf"}  255     ← equals _count
http_request_duration_seconds_sum    43.2                ← total of all observed values
http_request_duration_seconds_count  255                 ← number of observations
```

**Cumulative** means `le="0.1"` includes everything in `le="0.05"`. Values are non-decreasing as `le` grows.

To get the count **in** a single bucket you subtract:

```text
observations between 50ms and 100ms = bucket(le=0.1) - bucket(le=0.05) = 60
```

Every `_bucket` series, plus `_sum` and `_count`, is a **counter**.

### histogram_quantile

```promql
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))
```

Signature:

```text
histogram_quantile(φ, bucket_instant_vector)
                   ^   ^
                   |   must have an `le` label
                   0 ≤ φ ≤ 1
```

Rules, all of them exam-relevant:

1. The **quantile comes first**. `histogram_quantile(rate(...), 0.95)` is wrong.
2. φ is a **fraction between 0 and 1**, not a percentage. p95 is `0.95`, not `95`.
3. The input **must** carry the `le` label. Aggregations must use `by (le)`.
4. You almost always need `rate()` first, because buckets are counters.
5. The result is an **estimate** by linear interpolation within the matched bucket.
6. Only aggregate buckets with `sum`, never `avg`.

### The canonical forms, memorise these

```promql
# p95 per series, as exposed
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))

# p95 across the whole fleet
histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# p95 per job
histogram_quantile(0.95, sum by (job, le) (rate(http_request_duration_seconds_bucket[5m])))

# p95 per path and method
histogram_quantile(0.95, sum by (path, method, le) (rate(http_request_duration_seconds_bucket[5m])))

# Median
histogram_quantile(0.5, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# Average (NOT a quantile)
rate(http_request_duration_seconds_sum[5m]) / rate(http_request_duration_seconds_count[5m])
```

### The four classic mistakes

**1. Forgetting `by (le)`**

```promql
histogram_quantile(0.95, sum(rate(x_bucket[5m])))              # BROKEN
histogram_quantile(0.95, sum by (le) (rate(x_bucket[5m])))     # correct
```

Without `le`, `histogram_quantile` has no bucket boundaries and returns `NaN` or nonsense.

**2. Averaging quantiles instead of aggregating buckets**

```promql
avg(histogram_quantile(0.95, rate(x_bucket[5m])))              # WRONG
histogram_quantile(0.95, sum by (le) (rate(x_bucket[5m])))     # correct
```

The mean of per-instance p95s is not the fleet p95.

**3. Using a percentage instead of a fraction**

```promql
histogram_quantile(95, ...)      # WRONG, returns +Inf
histogram_quantile(0.95, ...)    # correct
```

φ > 1 returns `+Inf`, and φ < 0 returns `-Inf`.

**4. Forgetting `rate()`**

```promql
histogram_quantile(0.95, x_bucket)                    # quantile over ALL TIME since start
histogram_quantile(0.95, rate(x_bucket[5m]))          # quantile over the last 5 minutes
```

The first is not an error, but it answers a question nobody asked.

### Interpolation and its limits

`histogram_quantile` assumes observations are **uniformly distributed within each bucket**. Consequences:

- The result can never exceed the second-highest bucket boundary unless the quantile falls in `+Inf`, in which case the **highest finite boundary** is returned.
- If your highest finite bucket is `le="1"` and real latencies are 8 seconds, p99 reports `1`. Your histogram is blind above its top bucket.
- Coarse buckets give coarse estimates. `le="0.1"` then `le="10"` cannot distinguish 200ms from 9s.
- Accuracy depends entirely on bucket placement, so **place boundaries around your SLO thresholds**.

Prometheus emits a warning ("Quantile value is not in a bucket range") in some versions when the result is unreliable.

### Bucket selection guidance

Default `prometheus.DefBuckets` in the Go client:

```text
.005 .01 .025 .05 .1 .25 .5 1 2.5 5 10
```

Helper generators:

```go
prometheus.LinearBuckets(start, width, count)      // 0.1, 0.2, 0.3, ...
prometheus.ExponentialBuckets(start, factor, count) // 0.001, 0.002, 0.004, ...
prometheus.ExponentialBucketsRange(min, max, count)
```

Design rules:

- Cover the full realistic range, including a boundary above your worst acceptable latency.
- Put a boundary **exactly at** each SLO threshold, so the SLI needs no interpolation.
- 10 to 15 buckets is normal. Each one is a series, so 30 buckets x 100 instances x 5 paths = 15,000+ series.

### The SLI query: fraction under a threshold

This needs **no interpolation** and is therefore exact:

```promql
sum(rate(http_request_duration_seconds_bucket{le="0.3"}[5m]))
  / sum(rate(http_request_duration_seconds_count[5m]))
```

Read as: "what proportion of requests completed within 300ms". This is the preferred SLI form and is superior to a percentile for SLO purposes. It only works if `le="0.3"` is an actual bucket boundary.

Equivalent using the `+Inf` bucket as the denominator:

```promql
sum(rate(http_request_duration_seconds_bucket{le="0.3"}[5m]))
  / sum(rate(http_request_duration_seconds_bucket{le="+Inf"}[5m]))
```

### Requests in a specific bucket range

```promql
sum(rate(x_bucket{le="1"}[5m])) - sum(rate(x_bucket{le="0.5"}[5m]))
```

Requests taking between 500ms and 1s.

### Summaries: the contrast

```text
# TYPE rpc_duration_seconds summary
rpc_duration_seconds{quantile="0.5"}  0.032
rpc_duration_seconds{quantile="0.9"}  0.11
rpc_duration_seconds{quantile="0.99"} 0.44
rpc_duration_seconds_sum   4823.1
rpc_duration_seconds_count 92183
```

- Query the quantile directly: `rpc_duration_seconds{quantile="0.99"}`.
- **Never** aggregate it: `avg(rpc_duration_seconds{quantile="0.99"})` is mathematically meaningless.
- You cannot ask for p95 if only 0.5, 0.9, and 0.99 were configured.
- `_sum` and `_count` **are** aggregatable: `rate(_sum[5m]) / rate(_count[5m])` gives a valid average.
- Do **not** apply `histogram_quantile` to a summary. It has no `le` label.

### Native histograms

With `--enable-feature=native-histograms`:

```promql
# The whole distribution is one sample, so histogram_quantile takes the series directly
histogram_quantile(0.95, rate(http_request_duration_seconds[5m]))

# Companion functions
histogram_count(rate(http_request_duration_seconds[5m]))
histogram_sum(rate(http_request_duration_seconds[5m]))
histogram_avg(rate(http_request_duration_seconds[5m]))
histogram_stddev(rate(http_request_duration_seconds[5m]))
histogram_stdvar(rate(http_request_duration_seconds[5m]))

# Fraction of observations between two values, the native SLI form
histogram_fraction(0, 0.3, rate(http_request_duration_seconds[5m]))
```

Note the absence of `_bucket` and `by (le)`. Native histograms need protobuf exposition.

`histogram_fraction(lower, upper, v)` is the native equivalent of the bucket-ratio SLI and is exact for the schema resolution.

## Answers

**Q1: B.** Quantile first, bucket vector second.

**Q2: B.** A fraction from 0 to 1.

**Q3: B.** φ > 1 yields `+Inf`. φ < 0 yields `-Inf`. No error is raised, which makes this a silent bug.

**Q4: B.** `le`.

**Q5: B.** `le` carries the bucket boundaries. Dropping it destroys the histogram structure.

**Q6: B.** Less than or equal to the boundary. Cumulative.

**Q7: B.** Subtract the lower cumulative bucket from the higher one.

**Q8: B.** Sum the bucket rates keeping `le`, then take the quantile once.

**Q9: B.** Quantiles are not linear, so their mean is not the population quantile.

**Q10: B.** `rate(_sum) / rate(_count)`.

**Q11: B.** The estimate saturates at the highest finite boundary. Your histogram is blind above its top bucket, and the reported p99 is misleadingly good.

**Q12: B.** Bucket boundaries are fixed at instrumentation time. Fixing this requires a code change and redeploy, which is exactly why bucket design matters up front.

**Q13: B.** The bucket-ratio form.

**Q14: B.** It is exact (no interpolation) and it is a ratio of good to valid events, which is what an error budget needs.

**Q15: B.** The threshold must coincide with a real bucket boundary. Otherwise you are back to interpolating.

**Q16: B.** Summaries have no `le` label, so `histogram_quantile` cannot work on them.

**Q17: B.** Select the pre-computed quantile series directly.

**Q18: B.** The quantiles are baked in at instrumentation time. What was not computed does not exist.

**Q19: B.** `_sum` and `_count` are ordinary counters and aggregate normally. The `quantile` series never do.

**Q20: B.** No `by (le)` and no `_bucket`. The distribution lives in one sample.

**Q21: B.** `histogram_fraction(lower, upper, v)`.

**Q22: B.** `DefBuckets` is `.005 .01 .025 .05 .1 .25 .5 1 2.5 5 10`.

**Q23: C.** 11 finite boundaries plus `+Inf` gives 12 bucket series, and `_sum` and `_count` bring it to 14 per instance. 14 x 50 = 700. Option B (600) is the trap: it counts only the bucket series and forgets `_sum` and `_count`.

**Q24: B.** Uniform distribution within the bucket, hence linear interpolation.

**Q25: B.** You must keep both the grouping label and `le`.

## Exam tips

- **`histogram_quantile(φ, buckets)`.** Quantile **first**. φ is a **fraction** (0.95, not 95).
- φ > 1 returns `+Inf`. No error. Silent bug.
- The input must have `le`. Always aggregate with **`sum by (le)`** (adding any other grouping labels you need).
- Buckets are **cumulative** and are **counters**, so `rate()` first.
- Bucket range count = `bucket{le="hi"} - bucket{le="lo"}`.
- **Aggregate buckets, then take the quantile.** Never average quantiles.
- Average = `rate(_sum[5m]) / rate(_count[5m])`, for both histograms and summaries.
- The estimate saturates at the **highest finite boundary**. Bad top bucket = falsely good p99.
- Bucket boundaries are fixed at instrumentation time. Place one **exactly at each SLO threshold**.
- Preferred SLI: `sum(rate(x_bucket{le="T"}[5m])) / sum(rate(x_count[5m]))`. Exact, no interpolation.
- Summaries: read `{quantile="0.99"}` directly, **never aggregate it**, `histogram_quantile` does not apply. `_sum` and `_count` aggregate fine.
- Series per histogram = **bucket series + 2**.
- Native histograms: one series, no `_bucket`, no `by (le)`, needs protobuf. Companions: `histogram_count`, `histogram_sum`, `histogram_avg`, `histogram_fraction`, `histogram_stddev`.
- Default Go buckets: `.005 .01 .025 .05 .1 .25 .5 1 2.5 5 10`.
