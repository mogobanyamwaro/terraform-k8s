# 02. Logs And Events

**Domain:** Observability Concepts

## Concept Refresher

A **log** is a timestamped record of a discrete occurrence. An **event** is the same idea at a higher level, often structured and meaningful to the business or platform (a deploy, a Kubernetes pod eviction, a config change).

### Log types

| Type | Example | Machine parseable |
| --- | --- | --- |
| Unstructured / plaintext | `2026-08-18 10:00:01 ERROR failed to connect to db` | Painful. Regex required |
| Structured (JSON, logfmt) | `{"ts":"...","level":"error","msg":"db connect failed","db":"orders"}` | Yes |
| Binary | systemd journal, some audit formats | Needs a tool |

### Why logs are not metrics

| | Logs | Metrics |
| --- | --- | --- |
| Volume | Grows with traffic linearly | Constant per series |
| Retention cost | High | Low |
| Query latency | Slow full-text scans | Fast, indexed by label |
| Alerting | Possible but expensive and noisy | Purpose-built |
| Detail level | Full context per event | Aggregated only |

### Turning logs into metrics

You often want the volume, not the content. Tools that do this:

- `mtail` (Google) tails logs and exports Prometheus metrics
- `grok_exporter` uses grok patterns
- Promtail / Loki with `metrics` stage in the pipeline
- Vector, Fluent Bit with Prometheus output
- Loki ruler evaluating LogQL to produce alerts

Pattern: `log line matched -> increment a counter -> alert on the counter's rate`.

### Loki compared to Prometheus

Loki is intentionally Prometheus-shaped:

| Aspect | Prometheus | Loki |
| --- | --- | --- |
| Data | Metrics | Log lines |
| Query language | PromQL | LogQL (PromQL-like) |
| Indexed | All labels | **Labels only**, not log content |
| Selector | `{job="api"}` | `{job="api"} \|= "error"` |
| Storage of body | N/A | Compressed chunks, unindexed |

Loki indexes labels only. That is what keeps it cheap, and it is why you must not put high-cardinality data in Loki labels either.

### Kubernetes Events

Kubernetes `Event` objects are a distinct thing from both logs and metrics:

```bash
kubectl get events --sort-by=.lastTimestamp
kubectl get events --field-selector type=Warning
```

They are stored in etcd with a short TTL (default 1 hour). To get them into Prometheus, use `kube-event-exporter` or `event-exporter`. `kube-state-metrics` exposes object **state**, not events.

## Question

**Q1.** Which characteristic of logs makes them expensive compared to metrics?

- A. Logs need more CPU to compress
- B. Log volume grows with request volume, while metric storage is roughly constant per series
- C. Logs must be replicated three times by definition
- D. Logs cannot be sampled

**Q2.** What does Loki index?

- A. The full text of every log line
- B. Only the labels attached to log streams
- C. Nothing, it scans everything at query time
- D. Labels plus the first 256 bytes of each line

**Q3.** You need to alert when the string `OutOfMemoryError` appears in application logs. What is the cleanest Prometheus-native approach?

- A. Store the log lines as a Prometheus metric with the message as a label
- B. Use a log-to-metric exporter such as mtail to increment a counter, then alert on that counter
- C. Query Prometheus for the log text with a regex matcher
- D. Configure Alertmanager to tail the log file

**Q4.** Which statement about Kubernetes Events is correct?

- A. They are retained indefinitely in etcd
- B. They are exposed on the kubelet `/metrics` endpoint by default
- C. They have a limited TTL and need an exporter to become Prometheus metrics
- D. `kube-state-metrics` exports them as counters automatically

**Q5.** Which of these is the strongest reason to use structured logging?

- A. It reduces the total number of bytes written
- B. It makes fields machine-queryable without brittle regex parsing
- C. It removes the need for log retention policies
- D. It allows logs to be stored in a TSDB

**Q6.** A single request produces one log line and increments three counters. Traffic increases 100x. What happens?

- A. Both log and metric storage grow 100x
- B. Log storage grows roughly 100x, metric storage stays roughly the same
- C. Metric storage grows 100x, log storage stays the same
- D. Neither grows because both are aggregated

**Q7.** Which is a legitimate reason to keep logs even when you have good metrics?

- A. Logs are needed to compute rates
- B. Logs provide per-event context for root cause analysis that aggregates cannot
- C. Logs are cheaper for long retention
- D. Prometheus requires logs to build its index

**Q8.** In LogQL, what does `{app="api"} |= "timeout"` do?

- A. Selects the metric `app` and filters values containing `timeout`
- B. Selects log streams labelled `app=api` and keeps lines containing `timeout`
- C. Creates a counter of timeout occurrences
- D. Drops lines containing `timeout`

**Q9.** Which practice creates the same cardinality danger in Loki as it does in Prometheus?

- A. Long log lines
- B. Putting request IDs or trace IDs into stream labels
- C. Using JSON format
- D. Retaining logs for 90 days

**Q10.** Your on-call wants a dashboard panel showing error log volume per service over time. What is the most efficient architecture?

- A. Query the log store directly for every dashboard refresh at full text scan
- B. Pre-aggregate log matches into Prometheus counters, then graph `rate()` of them
- C. Store each log line as a Prometheus sample
- D. Use Alertmanager as the data source

## Answers

**Q1: B.** Log cost scales with event volume. Metric cost scales with the number of series, which is independent of traffic. This is the fundamental economic difference.

**Q2: B.** Loki indexes labels only. The log body is stored compressed and scanned at query time. That design keeps the index tiny.

**Q3: B.** Convert the log occurrence into a counter with a log-to-metric tool, then alert on the counter. Option A is a cardinality disaster and Prometheus cannot store strings as values. Option C is impossible, Prometheus holds no log text.

**Q4: C.** Kubernetes Events default to a 1 hour TTL in etcd and are not Prometheus metrics. You need an event exporter. `kube-state-metrics` exposes object state such as `kube_pod_status_phase`, not events.

**Q5: B.** Structured logs give you queryable fields without regex fragility. It usually increases byte count slightly, not decreases it.

**Q6: B.** Logs scale with traffic. The three counters remain three series regardless of how many requests hit them, so metric storage barely moves.

**Q7: B.** Logs give per-event context. Aggregates deliberately throw that away. Logs are not cheaper for long retention and are not required by Prometheus.

**Q8: B.** `{app="api"}` is the stream selector, `|=` is the line filter keeping lines that contain the string. `!=` would exclude them.

**Q9: B.** High-cardinality stream labels blow up Loki's index exactly as they blow up Prometheus. Put IDs in the log **body**, not in labels.

**Q10: B.** Pre-aggregate into counters, graph with `rate()`. Full text scans on every refresh are slow and expensive.

## Hands-on

Look at Kubernetes events and their short life:

```bash
kubectl get events -A --sort-by=.lastTimestamp
kubectl get events -A --field-selector type=Warning
```

Simulate log-to-metric conversion with a tiny counter. Push a value each time a pattern appears:

```bash
COUNT=$(journalctl --since "1 hour ago" 2>/dev/null | grep -ci error || echo 0)
echo "log_error_lines_total ${COUNT}" | \
  curl --data-binary @- http://localhost:9091/metrics/job/logscan/instance/localhost
```

Query it:

```promql
log_error_lines_total
```

See what Prometheus itself logs while you scrape:

```bash
docker logs prometheus --tail 30
```

Compare storage shapes. Metrics:

```bash
curl -s http://localhost:9090/api/v1/status/tsdb | jq '.data.numSeries'
```

## Exam tips

- Loki indexes **labels only**. Prometheus indexes **all labels** and stores numbers only.
- Metric cost tracks series count. Log cost tracks event volume.
- To alert on log content, convert to a metric first. mtail, grok_exporter, Promtail metrics stage, Loki ruler.
- Kubernetes Events are short-lived etcd objects, not metrics. `kube-state-metrics` gives object state, not events.
- Never put unbounded IDs into labels, in Prometheus or in Loki.
- Prometheus cannot store strings as sample values. Any answer suggesting it can is wrong.
