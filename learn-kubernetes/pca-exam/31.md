# 31. Pushgateway And Batch Jobs

**Domain:** Instrumentation and Exporters

## Concept Refresher

The Pushgateway exists for exactly one problem: **service-level batch jobs that do not live long enough to be scraped**.

```text
┌───────────────┐   HTTP PUT/POST    ┌──────────────┐   scrape    ┌────────────┐
│ short-lived   │───────────────────►│ Pushgateway  │◄────────────│ Prometheus │
│ batch job     │   /metrics/job/... │    :9091     │  /metrics   │            │
│ (exits)       │                    │  (in memory) │             │            │
└───────────────┘                    └──────────────┘             └────────────┘
```

The Pushgateway is a **cache**, not a proxy and not a push gateway into Prometheus. Prometheus still pulls from it.

### The API

```text
PUT  /metrics/job/<JOB>{/<LABEL>/<VALUE>}   Replace ALL metrics in this group
POST /metrics/job/<JOB>{/<LABEL>/<VALUE>}   Replace only the metrics named in the body
DELETE /metrics/job/<JOB>{/<LABEL>/<VALUE>} Delete this group
```

Path label values that contain `/` must be base64url encoded, using the `@base64` suffix:

```text
/metrics/job@base64/<base64>/instance@base64/<base64>
```

An empty label value is encoded as `=`.

The **grouping key** is the job plus all the label/value pairs in the URL path. Everything pushed under the same grouping key is one group, and PUT/DELETE operate on whole groups.

| Method | Effect |
| --- | --- |
| `PUT` | Replaces the entire group. Metrics previously in the group that are absent from this body are **removed** |
| `POST` | Only replaces metrics with names present in the body. Others in the group survive |
| `DELETE` | Removes the group entirely |

### Pushing

```bash
# Single metric
echo "some_metric 3.14" | curl --data-binary @- \
  http://localhost:9091/metrics/job/some_job

# Multiple metrics with HELP and TYPE
cat <<'EOF' | curl --data-binary @- http://localhost:9091/metrics/job/backup/instance/db1
# HELP backup_duration_seconds Duration of the backup.
# TYPE backup_duration_seconds gauge
backup_duration_seconds 184.2
# HELP backup_records_processed Records processed.
# TYPE backup_records_processed gauge
backup_records_processed 918273
# HELP backup_success Whether the backup succeeded.
# TYPE backup_success gauge
backup_success 1
EOF

# Delete the group
curl -X DELETE http://localhost:9091/metrics/job/backup/instance/db1
```

Note: the body must end with a newline. `curl --data-binary @-` with a heredoc handles that.

### honor_labels: the critical detail

Normally Prometheus **overwrites** any label on a scraped sample that collides with a target label, renaming the original to `exported_<label>`. That would destroy the `job` and `instance` labels the batch job pushed.

So the Pushgateway scrape job must set `honor_labels: true`:

```yaml
scrape_configs:
  - job_name: pushgateway
    honor_labels: true
    static_configs:
      - targets: ["pushgateway:9091"]
```

| `honor_labels` | Collision behaviour |
| --- | --- |
| `false` (default) | Target labels win. The scraped label becomes `exported_job`, `exported_instance`, etc. |
| `true` | **Scraped labels win.** Target labels are only applied when absent |

Without `honor_labels: true` on a Pushgateway job, every pushed metric ends up with `job="pushgateway"` and `exported_job="backup"`, which breaks every query and dashboard you write.

This is one of the most reliably tested Pushgateway facts.

### Pushgateway's own metrics

| Metric | Meaning |
| --- | --- |
| `push_time_seconds{job,instance}` | Unix time of the last successful push for that group |
| `push_failure_time_seconds{job,instance}` | Unix time of the last failed push |
| `pushgateway_build_info` | Version info |
| `pushgateway_http_push_duration_seconds` | Push handling latency |

`push_time_seconds` is how you alert on a batch job that stopped running:

```promql
time() - push_time_seconds{job="nightly_backup"} > 86400 * 1.5
```

This works because the Pushgateway keeps serving the group even after the job is gone, which is the whole point and also the main hazard.

### The caveats you must know

The Prometheus docs list explicit reasons **not** to use the Pushgateway.

1. **It becomes a single point of failure** and a shared bottleneck for many jobs.
2. **You lose `up`** as a health signal. Prometheus's `up` reflects the Pushgateway, not your job. A dead job looks identical to a job that has not run yet.
3. **Metrics persist forever** until explicitly deleted or the Pushgateway restarts. A decommissioned job's last values keep being exported, looking live.
4. **The Pushgateway never forgets by itself.** There is no TTL. (`--persistence.file` even makes it survive restarts.)
5. It is **not** for converting Prometheus from pull to push. If you are tempted to push from long-running services, you want either normal scraping or **agent mode / remote write**.

The correct mental rule:

```text
Long-running service        -> scrape it directly
Machine-level cron job      -> node_exporter textfile collector
Service-level batch job     -> Pushgateway
Ephemeral/serverless at scale-> Pushgateway is a poor fit; consider remote write or an aggregator
```

### Deletion discipline

Because there is no TTL, you need a strategy:

```bash
# Delete the group when the job is decommissioned
curl -X DELETE http://localhost:9091/metrics/job/old_job/instance/host1

# Wipe everything (admin API must be enabled)
curl -X PUT http://localhost:9091/api/v1/admin/wipe
```

`--web.enable-admin-api` is required for the wipe endpoint.

### What a batch job should push

```text
<job>_last_success_timestamp_seconds   gauge   Unix time of last success
<job>_duration_seconds                 gauge   How long the run took
<job>_records_processed                gauge   Work volume
<job>_success                          gauge   1 or 0
<job>_last_start_timestamp_seconds     gauge   When it started
```

Note these are **gauges**, not counters, because each push replaces the value rather than accumulating. If you want cumulative totals across runs you must read the current value and add to it, which the client libraries' `push_to_gateway` helpers do not do for you.

Client library helpers:

```python
from prometheus_client import CollectorRegistry, Gauge, push_to_gateway

registry = CollectorRegistry()
g = Gauge("batch_job_duration_seconds", "Duration.", registry=registry)
g.set(184.2)
push_to_gateway("localhost:9091", job="batchA", registry=registry)
# also: pushadd_to_gateway (POST), delete_from_gateway (DELETE)
```

Use a **separate registry**, not the default one, so you do not push `python_*` and `process_*` metrics from a process that is about to exit.

| Python helper | HTTP method |
| --- | --- |
| `push_to_gateway` | PUT (replace group) |
| `pushadd_to_gateway` | POST (add or replace named metrics) |
| `delete_from_gateway` | DELETE |

### Prometheus agent mode: the other "push" answer

Agent mode is often the correct answer when a question describes wanting to push data centrally.

```bash
prometheus --agent \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.agent.path=/var/lib/prometheus-agent
```

In agent mode Prometheus:

- Scrapes and relabels as normal.
- **Forwards everything via remote write.**
- Keeps only a WAL, no blocks, no long-term local storage.
- **Disables** querying, alerting, and recording rules locally.

Use it for edge/spoke collection into a central store. It is not a replacement for the Pushgateway; it still pulls.

Demonstrate PUT versus POST. Push two metrics:

```bash

# TYPE metric_a gauge

# TYPE metric_b gauge
metric_b 2
```

Now `POST` only `metric_a`:

```bash

curl -s http://localhost:9091/metrics | grep -E '^metric_'
```

`metric_a` is 99 and `metric_b` **survives**.

Now `PUT` only `metric_a`:

```bash

curl -s http://localhost:9091/metrics | grep -E '^metric_'
```

`metric_b` is **gone**. PUT replaced the entire group.

Demonstrate the persistence hazard. Delete nothing, and just watch the metric keep being served:

```promql
backup_success
time() - push_time_seconds{job="nightly_backup"}
```

The `backup_success 1` value stays at 1 forever, even though the job may never run again. That is why you alert on push age:

Add to `rules/lab.yml`:

```yaml
  - name: batch
    rules:
      - alert: BatchJobStale
        expr: time() - push_time_seconds > 300
        for: 1m
        labels:
          severity: warning
        annotations:
          summary: "Batch job {{ $labels.job }} on {{ $labels.instance }} has not pushed in {{ $value | humanizeDuration }}"

      - alert: BatchJobFailed
        expr: backup_success == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Backup on {{ $labels.instance }} reported failure"

      - alert: BatchJobMissing
        expr: absent(backup_success{job="nightly_backup"})
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "No backup metrics have ever been pushed"
```

```bash
curl -X POST http://localhost:9090/-/reload
```

Use the Python client properly:

```bash
cat > ~/pca-lab/batch.py <<'PY'
import random, time
from prometheus_client import CollectorRegistry, Gauge, push_to_gateway

# Dedicated registry: do NOT ship process_* / python_* from a dying process
registry = CollectorRegistry()

duration = Gauge("etl_duration_seconds", "ETL duration.", registry=registry)
records = Gauge("etl_records_processed", "Records processed.", registry=registry)
success = Gauge("etl_success", "1 if the run succeeded.", registry=registry)
last_ok = Gauge("etl_last_success_timestamp_seconds", "Last success.", registry=registry)

start = time.time()
try:
    time.sleep(random.uniform(0.5, 2.0))
    n = random.randint(1000, 50000)
    if random.random() < 0.25:
        raise RuntimeError("etl failed")
    records.set(n)
    success.set(1)
    last_ok.set_to_current_time()
except Exception:
    success.set(0)
finally:
    duration.set(time.time() - start)
    push_to_gateway("localhost:9091", job="etl", registry=registry)
    print("pushed")
PY
for i in 1 2 3 4 5; do ~/pca-lab/app/venv/bin/python ~/pca-lab/batch.py; sleep 3; done
```

## Exam tips

- Pushgateway = **cache for service-level batch jobs**. Prometheus still **scrapes** it. Port **9091**.
- **`honor_labels: true` is mandatory** on the Pushgateway scrape job. Without it you get `job="pushgateway"` plus `exported_job`.
- `honor_labels: true` means **scraped labels win**; `false` (the default) means **target labels win**.
- **PUT replaces the whole group. POST replaces only the named metrics. DELETE removes the group.**
- Grouping key = **job plus every label/value pair in the URL path**.
- **No TTL.** Metrics persist until deleted, and `--persistence.file` makes them survive restarts too.
- **You lose `up`.** Alert with `time() - push_time_seconds > X`, and use `absent()` for a job that never pushed.
- Batch job metrics should be **gauges**, and include a **last-success timestamp**.
- Push from a **dedicated registry**, not the default one.
- Python: `push_to_gateway` = PUT, `pushadd_to_gateway` = POST, `delete_from_gateway` = DELETE.
- Label values containing `/` use **`@base64`** with base64url; empty value is `=`.
- **Machine-level cron -> textfile collector. Service-level batch -> Pushgateway. Long-running service -> scrape it.**
- The Pushgateway is **not** a way to make Prometheus push-based. For central collection the answer is **agent mode plus remote write**.
- Agent mode: scrape and remote write only, WAL only, **no local queries, alerts, or rules**.
