# 01. Metrics And The Pillars Of Observability

**Domain:** Observability Concepts

## Concept Refresher

A **metric** is a numeric measurement of a system, recorded over time. In Prometheus a metric sample is:

```text
metric_name{label="value", ...}  <float64 value>  <int64 timestamp in milliseconds>
```

The three classic **pillars of observability**:

| Pillar | What it is | Cost profile | Cardinality tolerance | Good for |
| --- | --- | --- | --- | --- |
| Metrics | Aggregated numeric time series | Cheap, constant per series | Low. Bounded label values only | Alerting, dashboards, trends, SLOs |
| Logs | Discrete timestamped event records | Expensive, grows with volume | High. Arbitrary fields fine | Forensics, "what exactly happened to request X" |
| Traces | Causal chain of spans across services | Expensive, usually sampled | High | Latency attribution across services |

Some people add a fourth: **profiles** (continuous profiling, e.g. Pyroscope, Parca).

**Monitoring vs observability:**

- Monitoring watches known failure modes. "Is disk above 90%?"
- Observability lets you ask new questions about unknown failure modes without shipping new code. "Why are only Android users in Frankfurt slow?"

Prometheus is a **metrics** system. It is very good at the metrics pillar and deliberately does not try to be a log or trace store.

## Question

**Q1.** Which statement best describes what Prometheus stores?

- A. Individual request records with full request context
- B. Aggregated numeric time series identified by a metric name and label set
- C. Structured JSON log lines indexed by field
- D. Distributed traces composed of parent and child spans

**Q2.** Which of the following is the *least* appropriate use of a Prometheus metric label?

- A. `method="GET"`
- B. `status_code="500"`
- C. `user_id="8823f0a1-4c9d-4a2e-9df8-0c1e5b6f7a21"`
- D. `datacenter="eu-west-1"`

**Q3.** What uniquely identifies a time series in Prometheus?

- A. The metric name only
- B. The metric name plus the `instance` label
- C. The metric name plus the complete set of label name and value pairs
- D. The metric name plus the `job` label plus the timestamp

**Q4.** A team wants to answer "which exact user request caused this 500 error, and what was in the payload?" Which tool is the right fit?

- A. Prometheus counters with a `user_id` label
- B. A logging system such as Loki or Elasticsearch
- C. A Prometheus histogram of request durations
- D. A Grafana dashboard of error rate

**Q5.** Prometheus samples are stored as which numeric type?

- A. int32
- B. int64
- C. float64
- D. decimal with arbitrary precision

**Q6.** Which of these is *not* a pillar of observability as commonly defined?

- A. Metrics
- B. Logs
- C. Traces
- D. Backups

**Q7.** You have a metric `http_requests_total` with labels `method` (5 values), `status` (8 values), `handler` (20 values), and `instance` (50 values). How many time series does this produce at most?

- A. 83
- B. 4,000
- C. 40,000
- D. 400

**Q8.** Which statement about metric cardinality is correct?

- A. Cardinality only affects disk usage, not query performance
- B. Every unique label value combination creates a separate time series, driving memory and query cost
- C. Prometheus automatically drops high-cardinality labels
- D. Cardinality is only a concern for histograms

**Q9.** Which is the best description of an *event* as opposed to a metric?

- A. A pre-aggregated counter increment
- B. A discrete record of something that happened at a point in time, with context
- C. A time series with exactly one sample
- D. A gauge that changes rarely

**Q10.** Which of the following would you most likely track as a metric rather than a log?

- A. A stack trace from a panic
- B. The body of a rejected webhook payload
- C. The number of requests currently in flight
- D. The full SQL text of a slow query

## Answers

**Q1: B.** Prometheus stores aggregated numeric time series. Each series is a metric name plus labels, holding `(timestamp, value)` samples.

- A is a logging or tracing concern. Prometheus deliberately discards per-request identity.
- C describes a log store.
- D describes a tracing backend such as Jaeger or Tempo.

**Q2: C.** A UUID user ID is unbounded cardinality. Each distinct value creates a new time series, which explodes memory usage. Method, status code, and datacenter all have small bounded value sets.

**Q3: C.** Metric name plus the full label set. Internally the metric name is itself just the `__name__` label, so a series is really identified by its complete label set. Timestamps identify samples within a series, not the series itself.

**Q4: B.** Per-request forensic detail with payloads is a logging problem. Putting `user_id` into Prometheus would cause a cardinality explosion, and Prometheus does not store payloads.

**Q5: C.** float64 values with int64 millisecond timestamps. Native histograms are a distinct sample type but the bucket counts are still numeric.

**Q6: D.** Backups are an operational practice, not an observability signal.

**Q7: C.** 5 x 8 x 20 x 50 = 40,000 series. Cardinality multiplies, it does not add. This is the single most important arithmetic in metric design.

**Q8: B.** Every unique combination is a separate series consuming memory in the head block, index space, and query time. Prometheus does not automatically drop labels, though you can use `metric_relabel_configs` to drop them yourself.

**Q9: B.** An event is a discrete record of an occurrence, typically with rich context. Metrics are aggregations. Prometheus is not an event store.

**Q10: C.** In-flight request count is a numeric measurement, a natural gauge. The other three are unbounded text detail, which belongs in logs.

## Hands-on

Look at the raw shape of a metric:

```bash
curl -s http://localhost:9100/metrics | grep -A3 '^# HELP node_cpu_seconds_total'
```

Count how many series a single metric name produces:

```promql
count(node_cpu_seconds_total)
```

Break it down by dimension to see where cardinality comes from:

```promql
count by (mode) (node_cpu_seconds_total)
count by (cpu) (node_cpu_seconds_total)
```

Find your top cardinality metric names in the whole TSDB:

```promql
topk(10, count by (__name__) ({__name__=~".+"}))
```

Or use the built-in report:

```bash
curl -s http://localhost:9090/api/v1/status/tsdb | jq '.data.seriesCountByMetricName'
```

Total series in the head block:

```promql
prometheus_tsdb_head_series
```

Inspect the label set of one series:

```bash
curl -sG http://localhost:9090/api/v1/series --data-urlencode 'match[]=up' | jq
```

## Exam tips

- A series identity = metric name + all labels. Say it out loud until it sticks.
- The metric name lives in the reserved label `__name__`.
- Cardinality **multiplies** across labels. Never put IDs, emails, URLs with parameters, or full paths in labels.
- Metrics answer "how many, how fast, how full". Logs answer "what exactly happened". Traces answer "where did the time go".
- Prometheus samples are float64 with millisecond int64 timestamps.
- Prometheus is a metrics system, not a log or trace store. Any answer claiming otherwise is wrong.
