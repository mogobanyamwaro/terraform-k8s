# 05. Service Discovery

**Domain:** Observability Concepts

## Concept Refresher

**Service discovery (SD)** is how Prometheus learns which targets exist, without you hand-editing a list.

```text
                     ┌─────────────────────────────┐
                     │  Service Discovery source   │
                     │  (Kubernetes API, Consul,   │
                     │   EC2, DNS, files, ...)     │
                     └──────────────┬──────────────┘
                                    │ returns targets +
                                    │ __meta_* metadata labels
                                    ▼
                     ┌─────────────────────────────┐
                     │      relabel_configs        │  keep / drop / rewrite
                     └──────────────┬──────────────┘
                                    ▼
                     ┌─────────────────────────────┐
                     │   Final target label set    │  job, instance, your labels
                     │   __address__ decides where  │
                     └──────────────┬──────────────┘
                                    ▼
                              HTTP GET /metrics
```

The three-step mental model: **discover, relabel, scrape.**

### SD mechanisms you should recognise

| Config block | Discovers |
| --- | --- |
| `static_configs` | Hard-coded target list. Not really discovery |
| `file_sd_configs` | Targets from JSON or YAML files on disk, hot-reloaded |
| `kubernetes_sd_configs` | Pods, services, endpoints, nodes, ingresses via the K8s API |
| `consul_sd_configs` | Consul catalog services |
| `dns_sd_configs` | DNS SRV, A, or AAAA records |
| `ec2_sd_configs` | AWS EC2 instances |
| `azure_sd_configs` | Azure VMs and scale sets |
| `gce_sd_configs` | Google Compute Engine instances |
| `digitalocean_sd_configs` | DigitalOcean droplets |
| `docker_sd_configs` / `dockerswarm_sd_configs` | Docker containers / Swarm tasks |
| `openstack_sd_configs` | OpenStack instances |
| `nomad_sd_configs` | HashiCorp Nomad allocations |
| `eureka_sd_configs` | Netflix Eureka registry |
| `marathon_sd_configs` | Mesos Marathon apps |
| `triton_sd_configs` | Joyent Triton |
| `hetzner_sd_configs`, `linode_sd_configs`, `scaleway_sd_configs`, `ovhcloud_sd_configs`, `ionos_sd_configs`, `vultr_sd_configs` | Respective cloud providers |
| `http_sd_configs` | A generic HTTP endpoint returning JSON targets |
| `puppetdb_sd_configs` | PuppetDB queries |
| `serverset_sd_configs`, `nerve_sd_configs` | ZooKeeper-based (legacy) |
| `kuma_sd_configs` | Kuma service mesh |
| `uyuni_sd_configs` | Uyuni / SUSE Manager |
| `ovhcloud_sd_configs` | OVHcloud |

You will not be asked to recite all of them. You **will** be asked about `static`, `file`, `kubernetes`, `consul`, `dns`, `ec2`, and `http` SD.

### file_sd: the universal escape hatch

`prometheus.yml`:

```yaml
scrape_configs:
  - job_name: file-discovered
    file_sd_configs:
      - files:
          - /etc/prometheus/targets/*.json
          - /etc/prometheus/targets/*.yml
        refresh_interval: 5m
```

`/etc/prometheus/targets/web.json`:

```json
[
  {
    "targets": ["web1:9100", "web2:9100"],
    "labels": { "env": "production", "team": "platform" }
  },
  {
    "targets": ["web3:9100"],
    "labels": { "env": "staging", "team": "platform" }
  }
]
```

Key facts:

- Files are watched via inotify **and** re-read on `refresh_interval` (default `5m`).
- **No Prometheus reload is needed** when the file content changes. This is the classic exam question.
- `file_sd` sets `__meta_filepath` to the source file.
- If a file is malformed, Prometheus keeps the previous targets and increments `prometheus_sd_file_read_errors_total`.

### http_sd

```yaml
scrape_configs:
  - job_name: http-discovered
    http_sd_configs:
      - url: http://sd-service.internal/targets
        refresh_interval: 60s
```

The endpoint must return the same JSON shape as `file_sd`, with `Content-Type: application/json`. Metadata label `__meta_url` is set.

### dns_sd

```yaml
scrape_configs:
  - job_name: dns-srv
    dns_sd_configs:
      - names:
          - _prometheus._tcp.example.com
        type: SRV
        refresh_interval: 30s

  - job_name: dns-a
    dns_sd_configs:
      - names:
          - app.example.com
        type: A
        port: 9100        # required for A / AAAA, since they carry no port
        refresh_interval: 30s
```

- `SRV` records carry host **and** port, so `port` is optional.
- `A`, `AAAA`, and `MX` do not carry a port, so `port` is **required**.
- Meta labels: `__meta_dns_name`, `__meta_dns_srv_record_target`, `__meta_dns_srv_record_port`.

### consul_sd

```yaml
scrape_configs:
  - job_name: consul
    consul_sd_configs:
      - server: consul.service.consul:8500
        services: []          # empty means all services
        tags: ["prometheus"]
    relabel_configs:
      - source_labels: [__meta_consul_service]
        target_label: job
      - source_labels: [__meta_consul_dc]
        target_label: datacenter
```

Meta labels: `__meta_consul_service`, `__meta_consul_service_id`, `__meta_consul_dc`, `__meta_consul_tags`, `__meta_consul_node`, `__meta_consul_address`, `__meta_consul_health`, `__meta_consul_metadata_<key>`.

### kubernetes_sd roles

| Role | Discovers one target per | Typical use |
| --- | --- | --- |
| `node` | Cluster node (kubelet address) | node metrics, cAdvisor |
| `pod` | Pod, one per declared container port | Annotation-based pod scraping |
| `service` | Service port | Blackbox probing of services |
| `endpoints` | Endpoint address + port of a Service | The most common app scraping role |
| `endpointslice` | EndpointSlice address + port | Modern replacement for `endpoints` |
| `ingress` | Ingress path | Blackbox probing of ingress URLs |

Detail lives in `ServiceDiscovery.md` and `Kubernetes.md`.

### ec2_sd

```yaml
scrape_configs:
  - job_name: ec2
    ec2_sd_configs:
      - region: eu-west-1
        port: 9100
        filters:
          - name: tag:Monitoring
            values: ["enabled"]
    relabel_configs:
      - source_labels: [__meta_ec2_tag_Name]
        target_label: instance_name
      - source_labels: [__meta_ec2_private_ip]
        target_label: __address__
        replacement: "${1}:9100"
```

Meta labels: `__meta_ec2_instance_id`, `__meta_ec2_private_ip`, `__meta_ec2_public_ip`, `__meta_ec2_availability_zone`, `__meta_ec2_instance_type`, `__meta_ec2_instance_state`, `__meta_ec2_tag_<TagKey>`, `__meta_ec2_vpc_id`.

### Debugging SD

```bash
promtool check service-discovery prometheus.yml <job_name>
curl -s http://localhost:9090/api/v1/targets | jq '.data.activeTargets[] | {labels, health, lastError}'
curl -s http://localhost:9090/api/v1/targets?state=dropped | jq
```

The `/service-discovery` page in the web UI shows **discovered labels before relabeling** and **target labels after relabeling** side by side. That page is the single best SD debugging tool.

Useful meta-metrics:

```promql
prometheus_sd_discovered_targets
prometheus_sd_failed_configs
prometheus_sd_file_read_errors_total
prometheus_sd_kubernetes_events_total
prometheus_target_scrape_pool_targets
```

## Answers

**Q1: B.** SD dynamically produces the target list. Metric filtering after scraping is `metric_relabel_configs`, and alert routing is Alertmanager's job.

**Q2: B.** `__address__` is the connection endpoint. Rewriting it in `relabel_configs` is how you redirect scrapes, for example to point at the blackbox exporter.

**Q3: C.** `file_sd` watches the files with inotify and also polls on `refresh_interval`. No reload required. Note the contrast: changing `prometheus.yml` itself **does** need a reload.

**Q4: B.** `A` and `AAAA` records return only addresses, so you must supply `port`.

**Q5: B.** SRV records carry host and port, so Prometheus can build `__address__` directly.

**Q6: B.** `__meta_` is the SD metadata prefix.

**Q7: B.** All labels beginning with `__` are dropped after relabeling. `__name__` is the notable survivor because it holds the metric name.

**Q8: C.** `endpoints` (or `endpointslice`) gives you one target per backing pod address and port of a Service. `service` role gives one target per Service port, which is a load-balanced address and normally used for blackbox probing rather than scraping.

**Q9: C.** Prometheus is defensive here. It keeps the last good target set and increments `prometheus_sd_file_read_errors_total`. Alert on that counter.

**Q10: B.** `/service-discovery`. `/targets` shows only the final state and health.

**Q11: B.** Same JSON schema as `file_sd`, served as `application/json`.

**Q12: B.** `static_configs` is a hard-coded list, not discovery.

**Q13: B.** Either an SD-level `filters` block (which reduces API load) or a `keep` relabel rule on the tag meta label. `metric_relabel_configs` runs after the scrape, far too late to avoid scraping.

**Q14: C.** `5m`.

**Q15: B.** If no `instance` label is set, Prometheus sets it to the post-relabeling `__address__`. You can override it with a relabel rule.

## Hands-on

Add a `file_sd` job to your lab config:

```bash
mkdir -p ~/pca-lab/targets
cat > ~/pca-lab/targets/extra.json <<'EOF'
[
  { "targets": ["node-exporter:9100"], "labels": { "env": "lab", "team": "platform" } }
]
EOF
```

Add to `prometheus.yml`:

```yaml
  - job_name: file-sd
    file_sd_configs:
      - files:
          - /etc/prometheus/targets/*.json
        refresh_interval: 30s
```

Mount the directory in compose, then reload once:

```bash
curl -X POST http://localhost:9090/-/reload
```

Now prove no reload is needed for content changes:

```bash
cat > ~/pca-lab/targets/extra.json <<'EOF'
[
  { "targets": ["node-exporter:9100"], "labels": { "env": "lab", "team": "sre" } },
  { "targets": ["pushgateway:9091"],   "labels": { "env": "lab", "team": "sre" } }
]
EOF

sleep 35
curl -s http://localhost:9090/api/v1/targets | jq -r '.data.activeTargets[] | select(.scrapePool=="file-sd") | .labels'
```

The new target appears with no reload.

Break the file deliberately:

```bash
echo '{ this is not json' > ~/pca-lab/targets/extra.json
sleep 35
```

```promql
prometheus_sd_file_read_errors_total
```

Targets stay in place. Fix the file afterwards.

Inspect dropped targets and discovery metadata:

```bash
curl -s 'http://localhost:9090/api/v1/targets?state=dropped' | jq '.data.droppedTargets | length'
promtool check service-discovery ~/pca-lab/prometheus/prometheus.yml demo
```

Test DNS SD:

```yaml
  - job_name: dns-lab
    dns_sd_configs:
      - names: ["node-exporter"]
        type: A
        port: 9100
```

Query SD health:

```promql
prometheus_sd_discovered_targets
prometheus_target_scrape_pool_targets
prometheus_sd_failed_configs
```

## Exam tips

- Order is always: **discover, relabel, scrape**.
- `__address__` is where Prometheus connects. Rewrite it to redirect scrapes.
- `__meta_*` labels exist only during relabeling. All `__`-prefixed labels are dropped afterwards, except `__name__`.
- `file_sd` and `http_sd` pick up changes **without a Prometheus reload**. Changing `prometheus.yml` needs a reload.
- `file_sd` default `refresh_interval` is `5m`.
- DNS `A`/`AAAA` needs `port`. DNS `SRV` does not.
- Kubernetes roles: `node`, `pod`, `service`, `endpoints`, `endpointslice`, `ingress`. Use `endpoints`/`endpointslice` for app pods.
- `static_configs` is not service discovery.
- `instance` defaults to `__address__`.
- The `/service-discovery` UI page is your SD debugger. Filter SD-level where possible instead of relabel-dropping, to reduce API load.
