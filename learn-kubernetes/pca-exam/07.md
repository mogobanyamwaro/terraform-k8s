## Answers

**Q1: B.** The canonical division of labour. Metrics detect, traces localise, logs explain.

**Q2: B.** Session IDs are unbounded. Each distinct value produces another time series, blowing up head memory and index size.

**Q3: B.** `up` is the defining advantage of pull. Pull still requires knowing the target list, which is what service discovery is for, so A is wrong.

**Q4: B.** Only service-level batch job metrics. The Prometheus docs are explicit that Pushgateway is not a general-purpose ingest path.

**Q5: B.** Labels beginning with `__` are dropped after relabeling. `__name__` survives because it carries the metric name.

**Q6: B.** Label-only index, compressed chunk storage for bodies.

**Q7: B.** An exemplar. It requires OpenMetrics exposition and `--enable-feature=exemplar-storage`.

**Q8: B.** `traceparent`. B3 is Zipkin's older scheme.

**Q9: C.** The SLO must be tighter than the SLA. 99.95% gives you margin.

**Q10: B.** 30 days = 43,200 minutes. 0.05% = 21.6 minutes.

**Q11: B.** Utilisation, Saturation, Errors.

**Q12: B.** `file_sd_configs` files are watched and re-read. Everything that lives inside `prometheus.yml` needs a reload.

**Q13: B.** `A`/`AAAA` records carry no port, so you must specify it.

**Q14: B.** Prometheus explicitly documents that it is not suitable where 100% accuracy is required, such as per-request billing. Use a log/event pipeline for that.

**Q15: B.** Head sampling decides upfront at the root, cheaply, without knowing whether the request will fail.

**Q16: B.** A good SLI is a ratio of good to valid events from the user's point of view. CPU and pod count are causes, not user experience.

**Q17: B.** 2%. That is precisely why 14.4 is the chosen fast-burn threshold: 14.4 = 0.02 x 30 x 24.

**Q18: B.** OpenTracing and OpenCensus.

**Q19: C.** 4 x 10 x 25 x 20 = 20,000.

**Q20: B.** Prometheus deliberately drops per-event identity. That is the trade that makes it cheap. Sample values are float64 only, never strings.

## Hands-on Consolidation Drill

Run each of these and be able to explain the output in one sentence.

```promql
# 1. Liveness: which targets are down?
up == 0

# 2. Cardinality: top 10 metric names by series count
topk(10, count by (__name__) ({__name__=~".+"}))

# 3. Total head series
prometheus_tsdb_head_series

# 4. Scrape health: any target taking longer than its timeout budget?
scrape_duration_seconds > 1

# 5. How many samples each target exposes
scrape_samples_scraped

# 6. Series dropped by metric_relabel_configs
scrape_samples_scraped - scrape_samples_post_metric_relabeling

# 7. Discovery: how many targets each SD found
prometheus_sd_discovered_targets

# 8. Availability SLI
sum(rate(demo_api_request_duration_seconds_count{status!~"5.."}[5m]))
  / sum(rate(demo_api_request_duration_seconds_count[5m]))

# 9. Burn rate against 99.9%
(sum(rate(demo_api_request_duration_seconds_count{status=~"5.."}[1h]))
  / sum(rate(demo_api_request_duration_seconds_count[1h]))) / 0.001

# 10. Golden signal: latency p99
histogram_quantile(0.99, sum by (le) (rate(demo_api_request_duration_seconds_bucket[5m])))
```

## Exam tips

- The Observability Concepts domain is conceptual, not syntactic. Expect "which is the best tool for X" and "which statement is true" phrasing.
- Learn the three-signal division of labour as a sentence: metrics detect, traces localise, logs explain.
- Cardinality arithmetic is multiplication. Practice it until it is instant.
- Memorise the 99.9% / 30 day = 43.2 minutes anchor and derive the rest.
- Golden signals = LETS. RED for services. USE for resources.
- Pull gives `up`. That single fact answers many push-vs-pull questions.
- Pushgateway = batch jobs only, `honor_labels: true`, delete when done.
- `file_sd` and `http_sd` reload themselves. `prometheus.yml` does not.
