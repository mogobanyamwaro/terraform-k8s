# 36. Silences, Inhibition, And Notification Templates

**Domain:** Alerting and Dashboarding

## Concept Refresher

Three different mechanisms suppress or shape notifications. Confusing them is a guaranteed lost mark.

| Mechanism | Configured where | Driven by | Purpose |
| --- | --- | --- | --- |
| **Silence** | Runtime, via UI / API / `amtool` | A human, with a time window | "I know, I am working on it" or planned maintenance |
| **Inhibition** | `alertmanager.yml`, static | Another **alert** firing | Suppress redundant downstream alerts |
| **Mute time interval** | `alertmanager.yml`, static | Wall-clock time | Do not page for warnings at 3am |

All three suppress **notifications**. None of them stop Prometheus from evaluating the rule, and none of them remove the alert from the `ALERTS` metric.

### Silences

A silence is a set of matchers plus a start and end time. Any alert matching **all** matchers during the window is suppressed.

```bash
amtool silence add alertname=InstanceDown --duration=2h --comment="node replacement" --author=douglas

amtool silence add 'alertname=~"High.*"' instance=node1 \
  --duration=30m --comment="known noisy" --author=douglas

amtool silence query
amtool silence query --expired
amtool silence expire <id>
amtool silence expire $(amtool silence query -q)   # expire all
```

Via the API:

```bash
curl -s -XPOST http://localhost:9093/api/v2/silences \
  -H 'Content-Type: application/json' -d '{
  "matchers": [
    {"name": "alertname", "value": "InstanceDown", "isRegex": false, "isEqual": true},
    {"name": "instance",  "value": "node.*",       "isRegex": true,  "isEqual": true}
  ],
  "startsAt": "2026-08-18T10:00:00Z",
  "endsAt":   "2026-08-18T12:00:00Z",
  "createdBy": "douglas",
  "comment": "planned maintenance"
}'
```

Facts:

- Silences are stored in Alertmanager's `--storage.path` and **gossiped across the cluster**, so creating one on any node applies everywhere.
- A silence has states: **`pending`** (start time in the future), **`active`**, **`expired`**.
- Silences **expire**, they are not deleted. `amtool silence expire` sets the end time to now.
- Matchers require **all** to match, using the same `=`, `!=`, `=~`, `!~` semantics.
- A silenced alert appears in `alertmanager_alerts{state="suppressed"}` and shows as `suppressed` in the API.
- Silences survive Alertmanager restarts because of the storage path.

### Inhibition

Inhibition suppresses **target** alerts while a **source** alert is firing, but only when the labels in `equal` have **identical values** on both.

```yaml
inhibit_rules:
  - source_matchers:
      - severity = "critical"
    target_matchers:
      - severity = "warning"
    equal: ['alertname', 'cluster', 'service']
```

Reading it in English: "while a `critical` alert is firing, suppress `warning` alerts that have the **same** `alertname`, `cluster`, and `service`."

The classic real-world rule: a whole node being down should suppress every alert about services on that node.

```yaml
  - source_matchers:
      - alertname = "InstanceDown"
    target_matchers:
      - severity =~ "warning|critical"
    equal: ['instance']
```

And a cluster-level outage suppressing instance-level noise:

```yaml
  - source_matchers:
      - alertname = "ClusterUnreachable"
    target_matchers:
      - alertname =~ ".+"
    equal: ['cluster']
```

Rules you must know:

- The source alert must be **firing** for inhibition to apply.
- `equal` labels must be present **and equal** on both alerts. If the label is **missing on both**, that counts as equal (both empty).
- An alert matching **both** source and target matchers does **not** inhibit itself.
- Inhibition is evaluated **before** notification, so an inhibited alert never notifies.
- Inhibition is **not** transitive in a useful sense; each rule is evaluated independently against currently firing alerts.
- Omitting `equal` means the source inhibits **every** matching target globally, which is almost always a mistake.

Common mistake to recognise in a question: forgetting `equal`, so a critical alert in one cluster silences warnings everywhere.

### Notification templates

Alertmanager renders notifications with Go templates. The data available:

| Field | Meaning |
| --- | --- |
| `.Status` | `firing` or `resolved` |
| `.Receiver` | Receiver name |
| `.Alerts` | All alerts in the group |
| `.Alerts.Firing` | Just the firing ones |
| `.Alerts.Resolved` | Just the resolved ones |
| `.GroupLabels` | The `group_by` labels and values |
| `.CommonLabels` | Labels identical across all alerts in the group |
| `.CommonAnnotations` | Annotations identical across all alerts |
| `.ExternalURL` | Alertmanager's external URL |

Per alert, inside `range .Alerts`:

| Field | Meaning |
| --- | --- |
| `.Status` | `firing` / `resolved` |
| `.Labels` | Alert labels |
| `.Annotations` | Alert annotations |
| `.StartsAt`, `.EndsAt` | Timestamps |
| `.GeneratorURL` | Link back to the Prometheus expression |
| `.Fingerprint` | Alert fingerprint |

Template functions: `title`, `toUpper`, `toLower`, `join`, `match`, `reReplaceAll`, `safeHtml`, `stringSlice`, `date`, `tz`, and the standard Go template builtins.

```yaml
templates:
  - '/etc/alertmanager/templates/*.tmpl'
```

`custom.tmpl`:

```
{{ define "slack.title" }}
[{{ .Status | toUpper }}{{ if eq .Status "firing" }}:{{ .Alerts.Firing | len }}{{ end }}] {{ .GroupLabels.alertname }} ({{ .GroupLabels.cluster }})
{{ end }}

{{ define "slack.text" }}
{{ range .Alerts }}
*{{ .Labels.severity | toUpper }}* {{ .Annotations.summary }}
  instance: {{ .Labels.instance }}
  started : {{ .StartsAt.Format "2006-01-02 15:04:05" }}
  {{ if .Annotations.runbook_url }}runbook: {{ .Annotations.runbook_url }}{{ end }}
  graph  : {{ .GeneratorURL }}
{{ end }}
{{ end }}

{{ define "email.subject" }}
{{ .Status | toUpper }} {{ .CommonLabels.alertname }} on {{ .CommonLabels.cluster }} ({{ .Alerts | len }} alerts)
{{ end }}
```

Reference them:

```yaml
receivers:
  - name: slack
    slack_configs:
      - channel: '#alerts'
        title: '{{ template "slack.title" . }}'
        text: '{{ template "slack.text" . }}'
        send_resolved: true
```

The **default** templates live in `default.tmpl` inside Alertmanager and define `__subject`, `__text_alert_list`, `slack.default.title`, `email.default.html`, etc. You override by defining templates with the same names or by pointing the config at your own.

### Where templating happens: two different systems

This trips people up.

| | Prometheus alert rule templating | Alertmanager notification templating |
| --- | --- | --- |
| Where | `labels:` and `annotations:` in the rule | Receiver config and `.tmpl` files |
| Scope | **One alert instance** | **A whole group** of alerts |
| Variables | `$labels`, `$value`, `$externalLabels` | `.Alerts`, `.GroupLabels`, `.CommonLabels`, `.Status` |
| Has `$value` | Yes | **No.** The value is not passed to Alertmanager |

That last row matters. Alertmanager **never sees the metric value**. If you want the value in a notification, you must render it into an **annotation** in the Prometheus rule with `{{ $value }}`.

### Testing templates

```bash
amtool template render \
  --template.glob='/etc/alertmanager/templates/*.tmpl' \
  --template.text='{{ template "slack.title" . }}' \
  --template.data=alerts.json
```

Or just point a receiver at a webhook sink and read the JSON, which is what the webhook payload actually looks like:

```json
{
  "version": "4",
  "groupKey": "{}:{alertname=\"InstanceDown\", cluster=\"prod\"}",
  "truncatedAlerts": 0,
  "status": "firing",
  "receiver": "pager",
  "groupLabels": {"alertname": "InstanceDown", "cluster": "prod"},
  "commonLabels": {"alertname": "InstanceDown", "severity": "critical", "cluster": "prod"},
  "commonAnnotations": {"summary": "..."},
  "externalURL": "http://alertmanager:9093",
  "alerts": [
    {
      "status": "firing",
      "labels": {"alertname": "InstanceDown", "instance": "node1", "severity": "critical"},
      "annotations": {"summary": "node1 is down"},
      "startsAt": "2026-08-18T10:00:00Z",
      "endsAt": "0001-01-01T00:00:00Z",
      "generatorURL": "http://prometheus:9090/graph?g0.expr=up+%3D%3D+0",
      "fingerprint": "a1b2c3d4"
    }
  ]
}
```

Webhook payload facts worth remembering: `version` is `"4"`, `endsAt` for a firing alert is the zero time, and `truncatedAlerts` is non-zero when the group exceeded a receiver's size limit.

### Choosing the right suppression tool

```text
"We are doing planned maintenance on node3 tonight"
   -> SILENCE with matchers on instance=node3, scheduled window

"When the node is down, do not also page me about every service on it"
   -> INHIBITION, source InstanceDown, equal: [instance]

"Never page for warnings outside business hours"
   -> mute_time_intervals / active_time_intervals

"This alert is chronically noisy and we accept it"
   -> Fix the ALERT, not the notification. Failing that, a long silence with an owner and expiry
```

### Silences

Fire an alert first:

```bash
docker stop demo-b
sleep 90
amtool_cmd() { docker exec alertmanager amtool --alertmanager.url=http://localhost:9093 "$@"; }
amtool_cmd alert query
```

Now silence it and watch notifications stop:

```bash
amtool_cmd silence add alertname=InstanceDown \
  --duration=10m --comment="lab test" --author=douglas
amtool_cmd silence query
```

```bash
curl -s http://localhost:9093/api/v2/alerts | jq -r '.[] | "\(.labels.alertname) state=\(.status.state) silencedBy=\(.status.silencedBy)"'
```

The state is `suppressed` and `silencedBy` lists the silence ID. Confirm in Prometheus that the alert is **still firing**:

```promql
ALERTS{alertname="InstanceDown"}
```

It is. Silencing does not touch Prometheus. That contrast is the exam point.

```promql
alertmanager_alerts
alertmanager_alerts{state="suppressed"}
alertmanager_silences
```

Now expire it and watch notifications resume:

```bash
SID=$(amtool_cmd silence query -q | head -1)
amtool_cmd silence expire "$SID"
amtool_cmd silence query
amtool_cmd silence query --expired
```

Note the silence still exists, as `expired`. It was not deleted.

Create a **pending** silence, scheduled for the future:

```bash
curl -s -XPOST http://localhost:9093/api/v2/silences \
  -H 'Content-Type: application/json' -d '{
  "matchers": [{"name":"alertname","value":"InstanceDown","isRegex":false,"isEqual":true}],
  "startsAt": "'$(date -u -d '+5 min' +%Y-%m-%dT%H:%M:%SZ)'",
  "endsAt":   "'$(date -u -d '+35 min' +%Y-%m-%dT%H:%M:%SZ)'",
  "createdBy": "douglas",
  "comment": "scheduled maintenance window"
}' | jq .
```

```bash
curl -s http://localhost:9093/api/v2/silences | jq -r '.[] | "\(.id) \(.status.state) \(.startsAt) -> \(.endsAt)"'
```

State is `pending`. This is how you schedule maintenance in advance.

Test a **regex** silence, and note the anchoring:

```bash
amtool_cmd silence add 'alertname=~"Instance.*"' --duration=5m --comment="regex test"
amtool_cmd silence query

# This will NOT match, because regexes are fully anchored
amtool_cmd silence add 'alertname=~"stance"' --duration=1m --comment="anchoring demo"
```

The second silence matches nothing, because `stance` must match the **whole** value.

Clean up:

```bash
for s in $(amtool_cmd silence query -q); do amtool_cmd silence expire "$s"; done
```

### Inhibition

Now prove inhibition works, which requires two alerts. Add both to `~/pca-lab/rules/inhibit-demo.yml`:

```yaml
groups:
  - name: inhibit_demo
    rules:
      - alert: NodeDown
        expr: up{job="demo"} == 0
        for: 0m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} is down"

      - alert: NodeHighLatency
        expr: up{job="demo"} == 0
        for: 0m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} latency degraded"
```

Both fire on the same condition, deliberately, so you can watch one suppress the other.

Configure the inhibition rule scoped by `instance`:

```yaml
inhibit_rules:
  - source_matchers:
      - severity = "critical"
    target_matchers:
      - severity = "warning"
    equal: ['instance']
```

```bash
promtool check rules ~/pca-lab/rules/inhibit-demo.yml
docker exec alertmanager amtool check-config /etc/alertmanager/alertmanager.yml
curl -X POST http://localhost:9090/-/reload
curl -X POST http://localhost:9093/-/reload
docker stop demo-b
sleep 30
```

```bash
curl -s http://localhost:9093/api/v2/alerts \
  | jq -r '.[] | "\(.labels.alertname) sev=\(.labels.severity) inst=\(.labels.instance) state=\(.status.state) inhibitedBy=\(.status.inhibitedBy)"'
```

`NodeHighLatency` shows `state: suppressed` with `inhibitedBy` pointing at the `NodeDown` fingerprint. Only the critical alert notifies. Check the sink: you get one notification, not two.

```promql
alertmanager_alerts{state="suppressed"}
```

Now demonstrate the **`equal` scoping bug**. Remove `equal`:

```yaml
inhibit_rules:
  - source_matchers:
      - severity = "critical"
    target_matchers:
      - severity = "warning"
```

```bash
curl -X POST http://localhost:9093/-/reload
```

Inject an unrelated warning from a completely different service:

```bash
curl -s -XPOST http://localhost:9093/api/v2/alerts -H 'Content-Type: application/json' -d '[{
  "labels": {"alertname":"UnrelatedThing","severity":"warning","cluster":"other","instance":"totally-different"},
  "annotations": {"summary":"nothing to do with demo-b"},
  "startsAt": "'$(date -u +%Y-%m-%dT%H:%M:%SZ)'"
}]'
sleep 5
curl -s http://localhost:9093/api/v2/alerts \
  | jq -r '.[] | "\(.labels.alertname) sev=\(.labels.severity) state=\(.status.state)"'
```

`UnrelatedThing` is **suppressed** even though it has nothing to do with the down node. That is the failure mode. Restore `equal: ['instance']` and reload; now it notifies normally.

Add the realistic "node down suppresses everything on that node" rule and test it:

```yaml
inhibit_rules:
  - source_matchers:
      - alertname = "NodeDown"
    target_matchers:
      - alertname =~ ".+"
    equal: ['instance']
```

```bash
curl -X POST http://localhost:9093/-/reload
curl -s -XPOST http://localhost:9093/api/v2/alerts -H 'Content-Type: application/json' -d '[{
  "labels": {"alertname":"ServiceErrors","severity":"warning","instance":"demo-b:8080"},
  "startsAt": "'$(date -u +%Y-%m-%dT%H:%M:%SZ)'"
}]'
sleep 5
curl -s http://localhost:9093/api/v2/alerts | jq -r '.[] | "\(.labels.alertname) \(.labels.instance) \(.status.state)"'
```

Note `NodeDown` itself is **not** suppressed, even though `alertname =~ ".+"` matches it. Self-inhibition is prevented.

### Templates

Write a real template file. `~/pca-lab/alertmanager/templates/custom.tmpl`:

```
{{ define "custom.title" }}[{{ .Status | toUpper }}{{ if eq .Status "firing" }}:{{ .Alerts.Firing | len }}{{ end }}] {{ .GroupLabels.alertname }}{{ if .GroupLabels.cluster }} @ {{ .GroupLabels.cluster }}{{ end }}{{ end }}

{{ define "custom.text" }}
Status      : {{ .Status }}
Receiver    : {{ .Receiver }}
GroupLabels : {{ range $k, $v := .GroupLabels }}{{ $k }}={{ $v }} {{ end }}
CommonLabels: {{ range $k, $v := .CommonLabels }}{{ $k }}={{ $v }} {{ end }}
Firing      : {{ .Alerts.Firing | len }}
Resolved    : {{ .Alerts.Resolved | len }}

{{ range .Alerts.Firing }}
[FIRING] {{ .Labels.alertname }} / {{ .Labels.instance }}
  severity : {{ .Labels.severity }}
  summary  : {{ .Annotations.summary }}
  {{ if .Annotations.runbook_url }}runbook  : {{ .Annotations.runbook_url }}{{ end }}
  started  : {{ .StartsAt.Format "2006-01-02 15:04:05 MST" }}
  duration : {{ .StartsAt | since | humanizeDuration }}
  expr     : {{ .GeneratorURL }}
  finger   : {{ .Fingerprint }}
{{ end }}

{{ range .Alerts.Resolved }}
[RESOLVED] {{ .Labels.alertname }} / {{ .Labels.instance }}
  ended: {{ .EndsAt.Format "2006-01-02 15:04:05 MST" }}
{{ end }}
{{ end }}
```

Register it and use it in an email-style receiver, plus mount the directory:

```yaml
  alertmanager:
```

## Exam tips

- **Silence = human, runtime, time-bounded. Inhibition = static config, driven by another firing alert. Mute time interval = wall-clock schedule.** Know which one a scenario needs.
- All three suppress **notifications only**. Prometheus keeps firing and `ALERTS` still shows the alert. Prometheus has **no** `suppressed` state.
- Silence states: **`pending`, `active`, `expired`**. Silences are **expired**, never deleted, and are **persisted and gossiped**.
- **All** silence matchers must match. Regexes are **fully anchored**.
- Inhibition needs the source alert **firing**, and **`equal` labels equal on both**. Missing on both counts as equal.
- **Omitting `equal` inhibits globally.** That is the classic misconfiguration to spot.
- **Self-inhibition is prevented.**
- `.GroupLabels` = the `group_by` labels. `.CommonLabels` = labels identical across the group. Not the same thing.
- `.Alerts`, `.Alerts.Firing`, `.Alerts.Resolved`, `.Status`, `.Receiver`, `.ExternalURL`, and per-alert `.Labels`, `.Annotations`, `.StartsAt`, `.EndsAt`, `.GeneratorURL`, `.Fingerprint`.
- **Alertmanager never receives the metric value.** Use `{{ $value }}` in a Prometheus **annotation** if you need it in a notification.
- Register templates in the top-level **`templates:`** glob, then reference by name.
- Webhook payload: `version` is `"4"`, firing alerts have `endsAt` as the **zero time**, `truncatedAlerts` counts omitted alerts.
- `amtool silence add/query/expire`, `amtool template render`, `amtool check-config`, `amtool config routes test`.
- Alert on **`alertmanager_notifications_failed_total`**; a broken receiver is silent failure otherwise.
