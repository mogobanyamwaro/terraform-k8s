# 04. Push vs Pull

**Domain:** Observability Concepts

## Concept Refresher

Prometheus is a **pull** system. It reaches out to targets over HTTP and scrapes `/metrics`.

```text
PULL (Prometheus)                          PUSH (StatsD, Graphite, InfluxDB/Telegraf)

  Prometheus                                  App ──push──►
      │  GET /metrics                          App ──push──► Collector ──► Storage
      ├──────────────► App A                   App ──push──►
      ├──────────────► App B
      └──────────────► App C                   Collector must be discoverable
                                               and must absorb the arrival rate
  Prometheus owns the schedule
  Targets are discovered
```

### Why Prometheus chose pull

| Benefit | Explanation |
| --- | --- |
| Target liveness for free | A failed scrape sets `up == 0`. With push, silence is ambiguous: dead app or dead network or app just quiet? |
| Central control of scrape rate | You change `scrape_interval` in one place, no app redeploy |
| No target-side backpressure risk | A slow Prometheus cannot overload the app. The app never blocks on metric delivery |
| Easy manual debugging | `curl http://app:8080/metrics` shows exactly what Prometheus sees |
| Trivially runnable multiple times | Run a second Prometheus, or a laptop instance, against the same targets. No app config change |
| Natural service discovery fit | The list of things to scrape comes from the orchestrator |
| Detects half-broken targets | Scrape duration and failure are themselves metrics |

### Honest downsides of pull

| Problem | Prometheus answer |
| --- | --- |
| Short-lived batch jobs die before being scraped | Pushgateway |
| Targets behind NAT or firewall that Prometheus cannot reach | Push proxy, PushProx, or an agent-mode Prometheus inside the network doing remote_write out |
| Event-driven or serverless workloads | Pushgateway or OTel Collector, accept the caveats |
| Very large fleets | Sharding with `hashmod`, or hierarchical federation |

### Pushgateway: the narrow exception

Pushgateway is a **cache**, not a receiver-for-everything.

```bash
echo "backup_last_success_timestamp_seconds $(date +%s)" \
  | curl --data-binary @- http://localhost:9091/metrics/job/nightly_backup/instance/db01
```

Prometheus then **pulls** the Pushgateway. So the model stays pull end-to-end.

Rules and gotchas:

- Use `honor_labels: true` on the Pushgateway scrape job, otherwise Prometheus overwrites the pushed `job` and `instance` labels with the Pushgateway's own.
- Metrics persist **until explicitly deleted** or Pushgateway restarts. A deleted batch job keeps reporting stale values forever.
- Pushgateway does **not** expose `up` per pushed job. You lose liveness detection, so alert on timestamp freshness instead.
- Pushgateway is not for monitoring individual instances of a long-lived service. Use pull for those.
- `POST` merges into the group, `PUT` replaces the whole group, `DELETE` removes it.

The official guidance: **only** use Pushgateway for service-level batch jobs.

### Prometheus agent mode

Since 2.32, `--enable-feature=agent` (or `--agent`) runs Prometheus as a scrape-and-forward agent: it scrapes locally, keeps a WAL, and does `remote_write` outward. No local querying, no rules. This is the standard answer for "targets in a network Prometheus cannot reach" and for edge collection.

### Where OTel fits

The OpenTelemetry Collector can receive pushed OTLP metrics and then **expose** a `/metrics` endpoint that Prometheus pulls (`prometheus` exporter), or push directly to a remote_write endpoint (`prometheusremotewrite` exporter). This is the standard bridge for push-native apps.

## Answers

**Q1: B.** A failed scrape sets `up` to 0 for that target. In a push system, absence of data is ambiguous. Pull gives you a positive health signal on every interval.

**Q2: B.** Short-lived service-level batch jobs are the documented use case. Options A and C invert the model, and Pushgateway becomes a single point of failure and bottleneck.

**Q3: B.** By default Prometheus applies the scrape job's `job` and `instance` labels, clobbering the pushed ones. `honor_labels: true` makes the exposed labels win.

**Q4: B.** Pushgateway is a persistent cache with no TTL. You must `DELETE` the group. This is the classic Pushgateway trap.

**Q5: B.** `PUT` replaces the group. `POST` merges into it. `DELETE` removes it.

**Q6: B.** Agent mode scrapes locally and remote_writes outward, so only outbound connectivity is needed. This preserves pull semantics inside the network.

**Q7: B.** The collector is exposed to whatever rate clients push, which is a genuine overload risk. StatsD does support tags in many implementations, so C is wrong.

**Q8: B.** Prometheus always pulls, including from Pushgateway. Pushgateway only receives pushes from the batch jobs.

**Q9: C.** Values do not degrade in accuracy over time. The other three are real, documented trade-offs.

**Q10: B.** Push the last success timestamp and alert when it becomes stale. This is the standard batch job pattern. Option A fails because there is no `up` for a pushed job.

**Q11: B.** Pull means the target is oblivious to how many Prometheus servers scrape it. No app-side change needed.

**Q12: B.** The `prometheus` exporter exposes a scrape endpoint. The `prometheusremotewrite` exporter is the one that pushes.

## Hands-on

Push a batch job metric and inspect the label handling:

```bash
echo "batch_last_success_timestamp_seconds $(date +%s)" \
  | curl --data-binary @- http://localhost:9091/metrics/job/nightly_backup/instance/db01

echo -e "batch_records_processed_total 42\nbatch_duration_seconds 18.7" \
  | curl --data-binary @- http://localhost:9091/metrics/job/nightly_backup/instance/db01
```

See it in the Pushgateway:

```bash
curl -s http://localhost:9091/metrics | grep -E '^batch_'
```

Query in Prometheus and confirm `honor_labels` kept your job label:

```promql
batch_last_success_timestamp_seconds
```

Now prove the staleness trap. Delete the job's source but not the Pushgateway group:

```promql
time() - batch_last_success_timestamp_seconds
```

Watch that number climb forever. That is why you need the freshness alert.

Clean up properly:

```bash
curl -X DELETE http://localhost:9091/metrics/job/nightly_backup/instance/db01
curl -s http://localhost:9091/metrics | grep -c '^batch_' || echo "gone"
```

Compare `PUT` vs `POST`:

```bash
# POST merges
echo "metric_a 1" | curl --data-binary @- http://localhost:9091/metrics/job/demo
echo "metric_b 2" | curl --data-binary @- http://localhost:9091/metrics/job/demo
curl -s http://localhost:9091/metrics | grep -E '^metric_'   # both present

# PUT replaces the whole group
echo "metric_c 3" | curl -X PUT --data-binary @- http://localhost:9091/metrics/job/demo
curl -s http://localhost:9091/metrics | grep -E '^metric_'   # only metric_c
```

Prove pull liveness:

```bash
docker stop demo-b
sleep 20
```

```promql
up{job="demo"}
```

You get an explicit `0`, not silence.

Try agent mode:

```bash
prometheus --config.file=prometheus.yml --agent --storage.agent.path=/tmp/agent
# Note: the UI has no /graph, and rule files are rejected
```

## Exam tips

- Prometheus **pulls**. Always. Pushgateway is still pulled by Prometheus.
- Pull's killer feature is `up`. Push cannot give you unambiguous liveness.
- Pushgateway is only for **service-level batch jobs**. Not for microservices, not to reduce load.
- `honor_labels: true` is mandatory on the Pushgateway job.
- Pushgateway metrics live forever until `DELETE`. `POST` merges, `PUT` replaces, `DELETE` removes.
- No `up` for pushed jobs, so alert on `time() - *_last_success_timestamp_seconds`.
- Agent mode = scrape locally, `remote_write` outward, no querying, no rules. The answer for firewalled or edge networks.
- OTel Collector `prometheus` exporter is pulled, `prometheusremotewrite` exporter pushes.
