# 34. Alerting Rules

**Domain:** Alerting and Dashboarding

## Concept Refresher

Prometheus decides **when** an alert fires. Alertmanager decides **who gets told and how**. Keep that split clear, because half the questions in this domain test it.

```yaml
groups:
  - name: availability
    rules:
      - alert: InstanceDown
        expr: up == 0
        for: 5m
        keep_firing_for: 0s
        labels:
          severity: critical
          team: platform
        annotations:
          summary: "{{ $labels.instance }} is down"
          description: "{{ $labels.instance }} of job {{ $labels.job }} has been down for more than 5 minutes."
          runbook_url: "https://runbooks.example.com/InstanceDown"
```

### Fields

| Field | Required | Meaning |
| --- | --- | --- |
| `alert` | yes | Alert name. Becomes the `alertname` label |
| `expr` | yes | PromQL. **Every returned series becomes an alert instance** |
| `for` | no | How long the expression must be continuously true before firing. Default `0s` |
| `keep_firing_for` | no | Keep firing this long after the expression stops returning the series. Default `0s` |
| `labels` | no | Extra labels added to the alert. Used for routing |
| `annotations` | no | Human-readable text. **Not** used for identity or routing |

### The alert lifecycle

```text
expression returns nothing         -> inactive
expression returns a series        -> PENDING   (if for > 0)
still true after `for` elapses     -> FIRING    (sent to Alertmanager)
expression stops returning it      -> resolved  (resolve notification sent)
```

Critical details:

- On the **first** evaluation where the expression matches, the state is **`pending`**, not `firing`, whenever `for > 0`.
- With `for: 0` (or omitted), the alert goes straight to **`firing`** on the first matching evaluation.
- If the expression stops matching **during** the pending period, the timer **resets to zero**. It does not resume.
- The `for` duration is measured in wall-clock time across evaluations, so a `for: 5m` with `evaluation_interval: 1m` needs roughly 5 consecutive successful evaluations.
- Alertmanager receives firing alerts **repeatedly**, roughly every evaluation cycle, as a re-send/keepalive. If Prometheus stops sending, Alertmanager expires the alert after `resolve_timeout` (default `5m`).

### The `ALERTS` metric

Prometheus writes a synthetic series for every pending and firing alert:

```promql
ALERTS{alertname="InstanceDown", alertstate="firing", severity="critical", instance="..."}
```

- Value is always `1`.
- `alertstate` is `pending` or `firing`. Resolved alerts do not appear.
- `ALERTS_FOR_STATE` holds the Unix timestamp when the alert instance **started** being active, which is how Prometheus restores pending state across restarts.

```promql
ALERTS
ALERTS{alertstate="firing"}
count by (alertname) (ALERTS{alertstate="firing"})
ALERTS_FOR_STATE
time() - ALERTS_FOR_STATE          # how long this instance has been active
count_over_time(ALERTS{alertname="X", alertstate="firing"}[7d])   # flapping detection
```

`--rules.alert.for-outage-tolerance` (default `1h`) and `--rules.alert.for-grace-period` (default `10m`) govern how pending state survives a Prometheus restart.

### Templating

Annotations and labels support Go templating.

| Variable | Meaning |
| --- | --- |
| `{{ $labels.<name> }}` | A label from the alert's series |
| `{{ $value }}` | The value of the expression for this series |
| `{{ $externalLabels.<name> }}` | Prometheus `external_labels` |
| `{{ $externalURL }}` | Prometheus external URL |

Formatting functions:

| Function | Example output |
| --- | --- |
| `humanize` | `1.234k` |
| `humanize1024` | `1.234Ki` |
| `humanizePercentage` | takes a **ratio** 0-1, prints `4.2%` |
| `humanizeDuration` | `1h 5m 3s` |
| `humanizeTimestamp` | RFC3339-ish time |
| `printf "%.2f"` | `0.04` |
| `title`, `toUpper`, `toLower` | text case |
| `match`, `reReplaceAll` | regex on strings |
| `query`, `first`, `label`, `value` | run a PromQL query inside a template |

```yaml
        annotations:
          summary: "Error rate is {{ $value | humanizePercentage }} on {{ $labels.job }}"
          detail: "Memory: {{ $value | humanize1024 }}B, running for {{ $value | humanizeDuration }}"
          hosts: "{{ range query \"up == 0\" }}{{ .Labels.instance }} {{ end }}"
```

`humanizePercentage` expects a **ratio**, so `0.042` renders as `4.2%`. If your expression is already in percent, do not pipe through it.

### Labels versus annotations

| | Labels | Annotations |
| --- | --- | --- |
| Part of alert identity | **Yes** | No |
| Used for routing/grouping/inhibition | Yes | No |
| Changing the value creates a new alert | Yes | No |
| Should hold free text | No | Yes |
| Cardinality risk | Yes | No |

This is a very common question. **Never** put `$value` in a label, because the label changes on every evaluation and Alertmanager sees a stream of new alerts that never group or resolve properly.

### Writing good alerts

The canonical guidance ("My Philosophy on Alerting", reflected in the Prometheus docs):

- **Alert on symptoms, not causes.** Alert that users are seeing errors, not that a disk is 80% full.
- Every page must be **actionable** and **urgent**. If nobody must act now, it is a ticket or a dashboard, not a page.
- Alert on **user-visible** behaviour at the highest sensible level, and use dashboards and lower-severity alerts for the causes.
- Prefer few, high-quality alerts over many noisy ones.
- Use `for` to suppress transient blips.
- Include a **runbook link** in annotations.

Cause-based alerts are still useful as **warnings** or tickets, especially for slow-burning capacity problems where prediction is possible.

### Standard alert patterns

Target down:

```yaml
      - alert: InstanceDown
        expr: up == 0
        for: 5m
```

A whole job gone (better than per-instance in some cases):

```yaml
      - alert: JobDown
        expr: count by (job) (up == 1) == 0
        for: 5m
```

A metric or target that vanished entirely, which `up == 0` cannot catch:

```yaml
      - alert: TargetMissing
        expr: absent(up{job="critical-api"})
        for: 10m

      - alert: MetricMissing
        expr: absent_over_time(myapp_http_requests_total[30m])
        for: 5m
```

Error ratio:

```yaml
      - alert: HighErrorRate
        expr: |
          sum by (job) (rate(http_requests_total{code=~"5.."}[5m]))
            /
          sum by (job) (rate(http_requests_total[5m]))
            > 0.05
        for: 10m
```

Latency from a histogram:

```yaml
      - alert: HighLatency
        expr: |
          histogram_quantile(0.99,
            sum by (job, le) (rate(http_request_duration_seconds_bucket[5m]))
          ) > 1
        for: 10m
```

Disk filling, using prediction:

```yaml
      - alert: DiskWillFillIn4Hours
        expr: |
          predict_linear(node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}[6h], 4 * 3600) < 0
            and
          node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes{fstype!~"tmpfs|overlay"} < 0.2
        for: 30m
```

The `and` guard prevents alerting on a huge disk that is technically trending down but nowhere near full.

Crash looping:

```yaml
      - alert: ProcessRestartingRepeatedly
        expr: changes(process_start_time_seconds[15m]) > 3
        for: 0m
```

Certificate expiry:

```yaml
      - alert: CertExpiringSoon
        expr: (probe_ssl_earliest_cert_expiry - time()) / 86400 < 14
        for: 1h
        labels:
          severity: warning
```

Batch job staleness:

```yaml
      - alert: BatchJobStale
        expr: time() - push_time_seconds > 86400 * 1.5
        for: 10m
```

Clock skew:

```yaml
      - alert: ClockSkew
        expr: abs(node_timex_offset_seconds) > 0.05
        for: 10m
```

Monitoring the monitoring:

```yaml
      - alert: PrometheusRuleFailures
        expr: increase(prometheus_rule_evaluation_failures_total[10m]) > 0

      - alert: PrometheusNotConnectedToAlertmanager
        expr: prometheus_notifications_alertmanagers_discovered < 1
        for: 5m

      - alert: PrometheusNotificationsFailing
        expr: rate(prometheus_notifications_errors_total[5m]) > 0
        for: 5m

      - alert: PrometheusTSDBReloadsFailing
        expr: increase(prometheus_tsdb_reloads_failures_total[3h]) > 0

      - alert: PrometheusTargetScrapesExceedingLimit
        expr: increase(prometheus_target_scrapes_exceeded_sample_limit_total[10m]) > 0
```

The **Watchdog** / DeadMansSwitch alert, which is a standard practice:

```yaml
      - alert: Watchdog
        expr: vector(1)
        labels:
          severity: none
        annotations:
          summary: "This alert always fires to prove the alerting pipeline works end to end."
```

Route it to something that pages you when it **stops** arriving. `vector(1)` always returns a value, so the alert is permanently firing.

### `keep_firing_for`

Added to suppress flapping on the resolve side.

```yaml
      - alert: FlappyThing
        expr: rate(errors_total[5m]) > 0
        for: 2m
        keep_firing_for: 10m
```

The alert stays firing for 10 minutes after the expression stops matching. Without it, a flapping expression produces a firing/resolved/firing storm.

| Setting | Suppresses |
| --- | --- |
| `for` | Flapping **into** firing |
| `keep_firing_for` | Flapping **out of** firing |
| Alertmanager `group_interval` | Notification frequency for a group |
| Alertmanager `repeat_interval` | Re-notification of an unchanged firing group |

### Alerting configuration in prometheus.yml

```yaml
global:
  evaluation_interval: 15s
  external_labels:
    cluster: prod
    replica: A

rule_files:
  - /etc/prometheus/rules/*.yml

alerting:
  alert_relabel_configs:
    # Drop the replica label so HA pairs deduplicate in Alertmanager
    - regex: replica
      action: labeldrop
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager-1:9093", "alertmanager-2:9093"]
      timeout: 10s
      api_version: v2
      path_prefix: /
```

Key points:

- `external_labels` are added to **every alert** sent to Alertmanager (and to federated and remote-written samples). They are how Alertmanager knows which cluster an alert came from.
- **Prometheus sends every alert to every configured Alertmanager.** Alertmanagers then deduplicate among themselves via gossip. You do **not** load-balance across them.
- `alert_relabel_configs` runs on alerts on their way out. Dropping the `replica` label is the standard HA pattern.

### Notification pipeline metrics

| Metric | Meaning |
| --- | --- |
| `prometheus_notifications_alertmanagers_discovered` | How many Alertmanagers Prometheus knows about |
| `prometheus_notifications_sent_total` | Notifications sent |
| `prometheus_notifications_errors_total` | Send failures |
| `prometheus_notifications_dropped_total` | Alerts dropped because the queue was full |
| `prometheus_notifications_queue_length` | Current queue depth |
| `prometheus_notifications_queue_capacity` | Queue size |

### Validation

```bash
promtool check rules rules/alerts.yml

```

Alert unit test:

```yaml
rule_files:
  - ../rules/alerts.yml

evaluation_interval: 1m

tests:
  - interval: 1m
    input_series:
      - series: 'up{job="api", instance="a:80"}'
        values: '1 1 0 0 0 0 0 0'
    alert_rule_test:
      - eval_time: 3m
        alertname: InstanceDown
        exp_alerts: []            # still pending
      - eval_time: 7m
        alertname: InstanceDown
        exp_alerts:
          - exp_labels:
              severity: critical
              job: api
              instance: a:80
            exp_annotations:
              summary: "a:80 is down"
```

Note `exp_labels` must **not** include `alertname`, and pending alerts count as no alerts in `exp_alerts`.

## Answers

**Q1: B.** Prometheus evaluates rules and decides firing. Alertmanager only handles what happens next.

**Q2: B.** `pending`. This is a favourite exam question.

**Q3: B.** Straight to firing, because `for` defaults to `0s`.

**Q4: B.** It resets. `for` requires **continuous** truth.

**Q5: B.** Seven. Every returned series is an independent alert instance.

**Q6: B.** Labels. Annotations are informational only.

**Q7: B.** Identity churn. Every value change creates a "new" alert.

**Q8: A.** `ALERTS`, value always 1.

**Q9: B.** Only `pending` and `firing`. Resolved alerts have no series.

**Q10: B.** The activation timestamp, used to restore pending state after a restart.

**Q11: B.** A ratio. `0.042` becomes `4.2%`.

**Q12: B.** `{{ $value }}`.

**Q13: B.** Symptom-based alerting on user-visible impact.

**Q14: B.** `absent()`.

**Q15: B.** No series means no result, so the comparison never matches. This is the reason `absent()` exists.

**Q16: B.** `absent_over_time()` for a range, `absent()` for the instant case.

**Q17: B.** Resolve-side flap suppression.

**Q18: B.** `for`.

**Q19: B.** Fan-out to all, dedup in Alertmanager. Do not put a load balancer in front for this purpose.

**Q20: B.** `labeldrop` on `replica`, so both HA Prometheus servers emit byte-identical alerts that Alertmanager collapses into one.

**Q21: B.** Source identification, applied to alerts, federation, and remote write.

**Q22: B.** Always-firing canary whose disappearance is the signal.

**Q23: B.** Absolute-usage sanity guard against noisy predictions.

**Q24: B.** `prometheus_notifications_alertmanagers_discovered`.

**Q25: B.** Pending alerts are not listed, so an empty `exp_alerts: []` is how you assert "still pending".

**Q26: B.** No. Including it causes a mismatch.

**Q27: B.** `resolve_timeout`, default `5m`. Prometheus re-sends firing alerts as a keepalive.

**Q28: B.** Counting healthy instances catches total outage without paging per instance. Note that if **all** targets vanish this also returns nothing, so pair it with `absent()`.

**Q29: B.** An annotation, typically `runbook_url`.

**Q30: A.** Outage tolerance and grace period.

## Hands-on

Write a full alert file. `~/pca-lab/rules/alerts.yml`:

```yaml
groups:
  - name: availability
    rules:
      - alert: InstanceDown
        expr: up == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} ({{ $labels.job }}) is down"
          description: "Target has been unreachable for over 1 minute."
          runbook_url: "https://runbooks.example.com/InstanceDown"

      - alert: JobCompletelyDown
        expr: count by (job) (up == 1) == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Every instance of job {{ $labels.job }} is down"

      - alert: TargetMissing
        expr: absent(up{job="myapp"})
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "The myapp job has no targets at all"

      - alert: Watchdog
        expr: vector(1)
        labels:
          severity: none
        annotations:
          summary: "Alerting pipeline canary. Page if this STOPS arriving."

  - name: symptoms
    rules:
      - alert: HighErrorRate
        expr: |
          sum by (job) (rate(myapp_http_requests_total{code=~"5.."}[5m]))
            /
          sum by (job) (rate(myapp_http_requests_total[5m]))
            > 0.05
        for: 2m
        keep_firing_for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Error rate on {{ $labels.job }} is {{ $value | humanizePercentage }}"
          description: "Above the 5% threshold for 2 minutes."

      - alert: HighLatencyP99
        expr: |
          histogram_quantile(0.99,
            sum by (job, le) (rate(myapp_http_request_duration_seconds_bucket[5m]))
          ) > 0.5
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "p99 latency on {{ $labels.job }} is {{ $value | humanizeDuration }}"

  - name: causes
    rules:
      - alert: HighCPU
        expr: instance:node_cpu_utilisation:rate5m > 0.85
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "CPU on {{ $labels.instance }} is {{ $value | humanizePercentage }}"

      - alert: LowMemory
        expr: |
          node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes < 0.10
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Only {{ $value | humanizePercentage }} memory available on {{ $labels.instance }}"
          detail: "{{ with printf \"node_memory_MemAvailable_bytes{instance='%s'}\" $labels.instance | query }}{{ . | first | value | humanize1024 }}B free{{ end }}"

      - alert: DiskWillFillIn4Hours
        expr: |
          predict_linear(node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"}[1h], 4 * 3600) < 0
            and
          node_filesystem_avail_bytes{fstype!~"tmpfs|overlay|squashfs"}
            / node_filesystem_size_bytes{fstype!~"tmpfs|overlay|squashfs"} < 0.30
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.mountpoint }} on {{ $labels.instance }} will fill within 4 hours"

      - alert: ProcessRestarting
        expr: changes(process_start_time_seconds[15m]) > 2
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.job }} on {{ $labels.instance }} restarted {{ $value }} times in 15m"

  - name: meta
    rules:
      - alert: PrometheusNoAlertmanager
        expr: prometheus_notifications_alertmanagers_discovered < 1
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Prometheus has no Alertmanager"

      - alert: PrometheusNotificationsFailing
        expr: rate(prometheus_notifications_errors_total[5m]) > 0
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Failing to deliver notifications"

      - alert: PrometheusRuleFailures
        expr: increase(prometheus_rule_evaluation_failures_total[10m]) > 0
        labels:
          severity: warning
        annotations:
          summary: "Rule evaluation failures in group {{ $labels.rule_group }}"

      - alert: RuleGroupOverrunning
        expr: |
          prometheus_rule_group_last_duration_seconds
            > prometheus_rule_group_interval_seconds
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Rule group {{ $labels.rule_group }} takes {{ $value | humanizeDuration }}"
```

Watch it move through the states:

```bash
for i in $(seq 1 12); do
  echo -n "$(date +%T)  "
  curl -s -G http://localhost:9090/api/v1/query \
    --data-urlencode 'query=ALERTS{alertname="InstanceDown"}' \

  echo
  sleep 10
done
```

You will see `pending` for roughly 60 seconds, then `firing`. This is the single most important thing to have watched with your own eyes.

```promql
ALERTS_FOR_STATE{alertname="InstanceDown"}
```

## Exam tips

- **Prometheus decides when. Alertmanager decides who and how.**
- First matching evaluation with `for > 0` gives **`pending`**. Never `firing`.
- `for` defaults to **`0s`**, meaning immediate firing.
- The `for` timer **resets** if the expression stops matching. It requires **continuous** truth.
- **Every series returned becomes one alert instance.**
- **Labels are identity and routing. Annotations are text.** Never put `$value` in a label.
- `ALERTS{alertstate="pending"|"firing"}`, value always 1. `ALERTS_FOR_STATE` is the activation timestamp.
- `humanizePercentage` takes a **ratio 0-1**. `humanize1024` for bytes, `humanizeDuration` for seconds.
- **Alert on symptoms, not causes.** Every page must be urgent and actionable, with a runbook link.
- `up == 0` cannot detect a **vanished** target. Use **`absent()`** or `absent_over_time()`.
- `for` suppresses flapping **into** firing; **`keep_firing_for`** suppresses flapping **out of** firing.
- Prometheus sends alerts to **all** configured Alertmanagers; they deduplicate by gossip. Do not load-balance.
- HA dedup: **`labeldrop` the `replica` label** in `alert_relabel_configs`.
- `external_labels` go on every alert, federated sample, and remote-written sample.
- **Watchdog** alert = `vector(1)`, always firing, page when it stops.
- Guard `predict_linear()` alerts with an absolute-usage `and` clause.
- Alertmanager expires an unrefreshed firing alert after **`resolve_timeout` (5m)**.
- `promtool check rules` for syntax, `promtool test rules` for logic. In alert tests, pending equals `exp_alerts: []`, and **do not** put `alertname` in `exp_labels`.
