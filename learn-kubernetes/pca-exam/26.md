# 26. Evaluation Semantics: Staleness, Lookback, And Query Cost

**Domain:** PromQL

This file covers the "why does my query behave strangely" layer. It is the difference between knowing PromQL syntax and understanding what Prometheus actually does when it evaluates it.

## Concept Refresher

### How an instant query is evaluated

```text
Query at time T:  up

For each series matching the selector:
   Look BACKWARD from T for the most recent sample
   within the LOOKBACK DELTA window (default 5m)

   Found a sample?          -> return it, timestamped T (not the sample's own time)
   Found a staleness marker? -> series absent from the result
   Found nothing?            -> series absent from the result
```

Two consequences that surprise people:

1. The returned timestamp is **T**, the evaluation time, not the sample's own timestamp. Use `timestamp(v)` if you need the real one.
2. A series with a sample 4 minutes old still appears. A series with a sample 6 minutes old does not.

### Lookback delta

```bash
--query.lookback-delta=5m     # default
```

Rules:

- Applies to **instant vector selectors** only. Range vectors use their explicit window.
- If your `scrape_interval` approaches 5 minutes, instant queries develop gaps. **Keep `scrape_interval` well under the lookback delta**, ideally under 2 minutes.
- Raising it hides genuine outages, because a dead target keeps returning its last value for longer.
- Pushgateway data can appear "fresh" long after the job stopped, because Pushgateway keeps re-serving it on every scrape. That is a Pushgateway property, not a lookback property.

### Staleness markers

When Prometheus knows a series has ended, it appends a special **stale marker** sample instead of relying on the lookback window to expire.

Staleness markers are written when:

| Event | Effect |
| --- | --- |
| A target disappears from service discovery | All its series get markers |
| A target's scrape fails | Its metric series get markers, `up` becomes 0 |
| A previously exposed series is no longer in the exposition | That series gets a marker |
| A recording rule stops producing a series | That series gets a marker |

Effect: the series disappears from queries **immediately at the next evaluation**, not after 5 minutes. This is why deleting a target cleans up dashboards promptly.

Exception: `honor_timestamps: true` with an exporter that supplies its own timestamps suppresses staleness handling for those series. This is why Pushgateway data behaves differently.

### Range vector evaluation

```text
rate(x[5m]) at time T uses samples in the interval (T-5m, T]
```

The window is **left-open, right-closed**. A sample exactly at `T-5m` is excluded; a sample exactly at `T` is included.

Consequences:

- A range of exactly `2 * scrape_interval` can yield only one sample depending on alignment, so `rate()` returns nothing.
- With `scrape_interval: 15s` and `[1m]`, you get 4 samples typically, 3 if one scrape was late. This is why 4x is the minimum and 5m is the safe default.

### Rate extrapolation, precisely

`rate()` and `increase()` do not simply divide "last minus first" by the window. They:

1. Take the first and last samples in the window.
2. Detect and correct resets by summing the positive deltas.
3. **Extrapolate** to the window edges:
   - If the nearest sample is within 110% of the average sample interval of the boundary, extrapolate fully to the boundary.
   - Otherwise extrapolate only halfway to the boundary.
4. For a counter that cannot go below zero, if extrapolating backwards would produce a negative value, the extrapolation is clipped to the counter reaching zero.

That is why `increase()` returns fractional numbers, and why the value changes slightly as samples shift within the window.

### Alignment and the step

For a range query, evaluation timestamps are `start`, `start+step`, `start+2*step`, ... They are **not** aligned to scrape times. Each step independently looks back for samples.

If `step` is smaller than `scrape_interval`, consecutive steps return the **same sample value**, producing visible stairsteps. If `step` is much larger, you get aliasing and miss spikes.

Rule of thumb: `step >= scrape_interval`, and for `rate()` graphs, `step <= range/2`.

### Rule evaluation timing

Rules evaluate every `evaluation_interval` (default `1m`). Within a group, rules run **sequentially in file order**, so a later rule can use an earlier rule's output from the **same** evaluation cycle. Across groups, evaluation is concurrent and order is not guaranteed.

Groups are staggered by a hash of the group name so they do not all fire simultaneously.

If a group takes longer than its interval to evaluate, evaluations are skipped and you fall behind:

```promql
prometheus_rule_group_last_duration_seconds
  > on(rule_group) prometheus_rule_group_interval_seconds
```

### Query cost model

Cost is driven by **samples touched**, roughly:

```text
samples ≈ (number of matching series) x (samples per series in the range)
        = series x (range / scrape_interval)
```

For a range query, multiply by the number of steps.

| Guard | Default | Error when exceeded |
| --- | --- | --- |
| `--query.max-samples` | 50,000,000 | "query processing would load too many samples into memory" |
| `--query.timeout` | `2m` | `errorType: timeout` |
| Points per series in a range query | 11,000 | "exceeded maximum resolution of 11,000 points per timeseries" |
| `--query.max-concurrency` | 20 | Queries queue |

Expensive patterns to recognise:

```promql
{__name__=~".+"}                                    # every series
count_over_time({__name__=~".+"}[30d])              # every series, 30 days
rate(some_huge_metric[30d])                          # huge range on a huge metric
max_over_time(rate(x[5m])[30d:15s])                  # 172,800 inner evaluations
histogram_quantile(0.99, rate(x_bucket[5m]))         # fine, unless x has 40 buckets x 5,000 pods
topk(10, count by (__name__) ({__name__=~".+"}))     # useful but slow; run sparingly
```

Cheap equivalents:

```promql
# Precompute with a recording rule, then aggregate cheaply
max_over_time(job:error_ratio:rate5m[30d])

# Narrow the selector
rate(http_requests_total{job="api", status=~"5.."}[5m])

# Use the TSDB status API instead of a cardinality query
curl -s localhost:9090/api/v1/status/tsdb | jq
```

### Why recording rules solve cost

A recording rule evaluates the expensive expression **once per evaluation interval** and stores a small result series. Queries then read a handful of samples instead of millions.

```yaml
groups:
  - name: expensive
    interval: 30s
    rules:
      - record: job:http_error_ratio:rate5m
        expr: |
          sum by (job) (rate(http_requests_total{status=~"5.."}[5m]))
            / sum by (job) (rate(http_requests_total[5m]))
```

Then `max_over_time(job:http_error_ratio:rate5m[30d])` is trivially cheap, while the equivalent subquery would be prohibitive.

### Counter reset edge cases

| Situation | Behaviour |
| --- | --- |
| Process restarts, counter goes to 0 | `rate()` corrects. `resets()` counts it |
| Counter wraps at a maximum | Treated as a reset. Prometheus counters are float64, so real wrapping is essentially impossible |
| A target is replaced by a new pod with the same labels | Looks like a reset. Handled |
| A target is replaced with **different** labels | New series. Old series gets a staleness marker. `rate()` on the new one needs 2 samples first |
| Only one sample in the window | Series omitted from the `rate()` result |
| Counter decreases due to an exporter bug | Silently treated as a reset, inflating the rate |

### NaN propagation

```text
NaN in arithmetic  -> NaN
NaN in comparison  -> false (the series is filtered out)
NaN with bool      -> 0
sum() over a group containing NaN -> NaN
```

That last one bites: a single `NaN` in a group poisons the whole aggregation. Guard divisions with `clamp_min()`.

### Extended range selectors and anchored modifiers, quick reference

```promql
x[5m]                        # range vector
x offset 5m                  # shifted back
x offset -5m                 # shifted forward (needs the negative-offset feature on older versions)
x @ 1687000000               # pinned to an absolute timestamp
x @ start()                  # pinned to the query range start
x @ end()                    # pinned to the query range end
x[5m] @ end()                # a range vector ending at the query range end
x[5m] offset 1h @ end()      # combinable, order flexible
rate(x[5m] offset 1h)        # offset belongs INSIDE
expr[1h:1m]                  # subquery
expr[1h:]                    # subquery with default resolution
```

## Answers

**Q1: C.** `5m`.

**Q2: B.** Beyond the lookback delta, the series is treated as absent.

**Q3: B.** The evaluation timestamp T. All series in an instant query result share it, which is what makes cross-metric arithmetic align.

**Q4: B.** `timestamp(v)`.

**Q5: B.** Samples older than the lookback window vanish from instant queries. A `scrape_interval` near or above 5 minutes therefore produces intermittent empty results.

**Q6: B.** An explicit end-of-series marker sample.

**Q7: B.** Target removal from SD, failed scrape, and series disappearing from the exposition are the three main triggers. Recording rules that stop producing output also generate them.

**Q8: C.** Promptly. Staleness markers exist precisely so you do not wait out the lookback window.

**Q9: B.** Left-open, right-closed: `(T-5m, T]`.

**Q10: B.** Boundary extrapolation. Documented and expected.

**Q11: B.** Steps are computed from `start` and `step` and are unrelated to scrape timing. Each step independently looks back.

**Q12: B.** Stairsteps, since multiple steps resolve to the same underlying sample.

**Q13: B.** Sequential within a group, which is what makes rule chaining work.

**Q14: B.** Concurrent across groups, so never rely on cross-group ordering. If rule B depends on rule A, put them in the same group with A first.

**Q15: B.** Compare the group's last duration against its interval.

**Q16: B.** Samples touched.

**Q17: C.** 50,000,000.

**Q18: B.** A 30 day subquery at 15 second resolution means 172,800 evaluations of the inner `rate()`. That is catastrophically expensive.

**Q19: B.** Recording rules.

**Q20: B.** Prometheus cannot distinguish a bug from a restart. It applies reset correction, which inflates the rate. This is why exporters must guarantee monotonicity.

**Q21: B.** `NaN` fails every comparison, so filtering comparisons drop it. With `bool` you get 0.

**Q22: B.** `NaN` propagates through the aggregation. One poisoned sample ruins the group, which is why you guard denominators with `clamp_min()`.

**Q23: B.** Inside, attached to the range vector.

**Q24: B.** A valid range vector pinned to the range end. This is how you build "the last 5 minutes of the graph window" expressions.

**Q25: B.** Fewer than two samples. New series and missed scrapes are the usual reasons, and widening the range fixes it.

## Hands-on

Prove that instant queries return the evaluation timestamp, not the sample timestamp:

```bash
curl -sG http://localhost:9090/api/v1/query --data-urlencode 'query=up{job="node"}' \
  | jq '.data.result[0].value[0]'

curl -sG http://localhost:9090/api/v1/query --data-urlencode 'query=timestamp(up{job="node"})' \
  | jq '.data.result[0].value[1]'
```

The two differ by up to one scrape interval.

Measure sample age:

```promql

max(time() - timestamp(up))
```

Demonstrate the lookback delta. Add a job with a very long interval:

```yaml
  - job_name: slow-scrape
    scrape_interval: 6m
    static_configs:
      - targets: ["node-exporter:9100"]
```

```bash
curl -X POST http://localhost:9090/-/reload
```

Wait 15 minutes, then repeatedly run:

```promql
up{job="slow-scrape"}
time() - timestamp(up{job="slow-scrape"})
```

The series blinks in and out, because at many evaluation instants the newest sample is older than 5 minutes. Remove that job afterwards.

Demonstrate staleness markers. Stop a target and time the disappearance:

```bash

for i in $(seq 1 8); do
```

The application series disappear within one or two evaluation intervals, not after 5 minutes. Note `up{instance="demo-c:8080"}` remains at 0, because the target is still configured and still being scraped unsuccessfully.

## Exam tips

- **Lookback delta = `5m`**, applies to instant vector selectors. Keep `scrape_interval` well below it.
- An instant query returns the **evaluation timestamp**, not the sample's. Use `timestamp(v)` for the real one.
- **Staleness markers** make ended series disappear **promptly**, not after the lookback window. Written on SD removal, failed scrape, and series vanishing from the exposition.
- Range windows are **left-open, right-closed**: `(T-range, T]`.
- `rate()`/`increase()` **extrapolate to the window boundaries**, which is why results are fractional.
- Range query steps are `start + n*step` and are **not** aligned to scrapes. `step < scrape_interval` gives stairsteps; a very large `step` hides spikes.
- Within a rule group, rules run **sequentially in file order**, enabling chaining. **Across groups, concurrently and unordered.**
- Cost ≈ **series x samples per series x steps**. Defaults: `max-samples 50,000,000`, `timeout 2m`, `11,000 points per series`, `max-concurrency 20`.
- Subqueries with fine resolution over long ranges are the most expensive thing you can write. **Replace with recording rules.**
- A decreasing counter is always interpreted as a reset, so exporter bugs silently inflate rates.
- `NaN` fails all comparisons and **poisons aggregations**. Guard denominators with `clamp_min()`.
- `offset` goes **inside** the parentheses. `@` can be combined with `offset` in either order.
- Missing series in a `rate()` result = **fewer than two samples** in the window.
