# 05. Platform Architecture and Capabilities

**Domain:** Core Fundamentals (36%)

> **Prerequisite:** `01.md`–`04.md`. This chapter answers: *what does a platform actually **look like** architecturally — and how do you think in **capabilities** instead of tool names?*

## Concept Refresher

### Platform architecture in plain English

A **platform architecture** is how you **organise** everything the platform provides — runtime, infra APIs, security, observability, CI/CD, portal — into **layers** with clear **interfaces**, so developers get a **coherent product** instead of a pile of disconnected tools.

```text
Wrong mental model:  "We bought Kubernetes, Backstage, and Argo — we're done"
Right mental model:  "We composed capabilities into golden paths with APIs and UX"
```

The platform is **not**:

- A single Jenkinsfile
- Only etcd or only Backstage
- A shared cluster with no product owner
- “We run Kubernetes” with no paved paths on top

It **is**: **composed capabilities** with **APIs and UX** that reduce cognitive load.

### The capability stack (top to bottom)

Developers mostly touch the **top**. Platform team builds and maintains **everything below**.

```text
┌─────────────────────────────────────────────────────────────┐
│  DEVELOPER EXPERIENCE                                       │
│  Portal (Backstage), docs, templates, service catalog       │
├─────────────────────────────────────────────────────────────┤
│  GOLDEN PATHS                                               │
│  CI templates, GitOps, app charts, "Create service" flows     │
├─────────────────────────────────────────────────────────────┤
│  GOVERNANCE & TENANCY                                       │
│  Policy (Kyverno/OPA), RBAC, quotas, NetworkPolicy, PSS     │
├─────────────────────────────────────────────────────────────┤
│  PLATFORM SERVICES                                          │
│  Observability (OTel), secrets, ingress, identity, mesh*    │
├─────────────────────────────────────────────────────────────┤
│  RUNTIME + INFRA APIs                                       │
│  Kubernetes, Crossplane, Cluster API, storage operators     │
├─────────────────────────────────────────────────────────────┤
│  CLOUD / DATACENTER                                         │
│  AWS, GCP, Azure, bare metal, VMs                           │
└─────────────────────────────────────────────────────────────┘
         * mesh = optional capability, not mandatory
```

**User-facing** (developers interact): portal, templates, CRDs, Git repos, docs.  
**Internal** (platform team operates): control-plane clusters, Crossplane providers, Argo CD instances, policy engines.

### Capability map — what each layer does

| Layer | Capability (exam language) | Tool examples (not the answer) | Developer experience |
| --- | --- | --- | --- |
| **Developer experience** | Find, discover, scaffold | Backstage, portal UI | “Create Java API” button |
| **Golden paths** | Paved delivery | CI templates, GitOps, Helm chart | PR → build → deploy without inventing pipeline |
| **Policy & tenancy** | Safe multi-tenant isolation | Kyverno, OPA, RBAC, quotas | Namespace appears with defaults enforced |
| **Observability** | Metrics, logs, traces by default | OTel, Prometheus, Loki, Tempo | Dashboards exist on day one |
| **Secrets & identity** | Workload identity, secret refs | ESO, Sealed Secrets, cert-manager | App gets cert without manual ACM clicks |
| **Service communication** | mTLS, traffic management | Istio, Linkerd, Cilium mesh | Secure pod-to-pod without app team wiring CNI |
| **Runtime** | Container orchestration | Kubernetes | Deployment runs; platform hid node/CNI setup |
| **Infra APIs** | Self-service cloud/cluster | Crossplane, Cluster API | `DatabaseClaim` → RDS appears |
| **Cost** | Showback/chargeback | Labels, Kubecost-style reports | Team sees cost of their env |

Exam rule: answer with the **capability** (“we need secure service communication”) not the **brand** (“we must buy Istio”).

### Capabilities vs tools — the CNPA mindset

Platforms solve **jobs-to-be-done**. Tools are **implementations** you can swap.

| Need (capability) | One way | Another way |
| --- | --- | --- |
| Secure service communication | Service mesh (Istio) | NetworkPolicy + mTLS at ingress |
| Metrics | Prometheus | Vendor APM |
| GitOps CD | Argo CD | Flux |
| Policy | Kyverno | OPA Gatekeeper |
| Developer portal | Backstage | Custom portal on top of same APIs |

**Modular architecture** means you can change the backend (e.g. tracing vendor) behind a **stable contract** (OTel SDK + collector config) without rewriting the portal or every app.

```text
App team declares:     "I need traces"     (capability)
Platform provides:     OTel sidecar/inject  (default on golden path)
Backend swap:          Tempo → vendor X     (platform team change, not 50 app rewrites)
```

### Architecture principles (expanded)

#### 1. Modular

Swap components without breaking the developer contract. Version APIs. Deprecate old template v1 when v2 ships.

#### 2. API-first

**Everything a human can click, a CR/API can do.**

| Surface | Same underlying API |
| --- | --- |
| Backstage “Create service” | Submits same template as CLI/CR |
| `kubectl apply TeamWorkspace` | Same controller as portal form |
| GitOps merge to env repo | Same desired state as UI deploy |

**API-first is not “UI only” or “no YAML.”** It means portal, CLI, and Git all drive the **same** platform APIs — no secret human-only paths.

#### 3. Secure and observable by default

Capabilities are **wired into the golden path**, not optional homework:

```text
Bad:  "Step 7 in the wiki: install Prometheus after launch"
Good: OTel + scrape + baseline alerts injected by template on create
```

#### 4. Least privilege between layers

| Layer | Principle |
| --- | --- |
| App team | RBAC scoped to their namespace/project |
| GitOps agent | Can sync allowed paths only — not cluster-admin |
| Crossplane provider | Cloud IAM scoped to compositions |
| Platform admin | Break-glass separate from daily app deploy |

Shared `cluster-admin` for all developers = exam wrong answer.

#### 5. Multi-cluster as a product (fleet)

When one cluster is not enough (isolation, scale, locality, blast radius), the platform offers **fleet** as a **capability** — not “random clusters nobody documents.”

```text
Management / control-plane cluster          Workload clusters
┌──────────────────────────┐               ┌─────────┐ ┌─────────┐
│ Argo CD (fleet)          │───syncs──────►│  dev    │ │  prod   │
│ Crossplane, portal backend│               └─────────┘ └─────────┘
│ Policy bundles           │
└──────────────────────────┘
```

Developers still use **one golden path**; platform routes to the right destination.

More: `04.md` (env isolation), `15.md`–`16.md` (multi-cluster GitOps).

#### 6. Control plane vs data plane

| Plane | What runs there | Examples |
| --- | --- | --- |
| **Control plane** | Platform **management** — does not serve app traffic | Argo CD, Crossplane, portal backend, fleet controllers |
| **Data plane** | **Workload** execution — app traffic flows here | App pods, ingress data path, worker nodes |

Putting GitOps (Argo CD) in a **management cluster** that syncs **workload clusters** is a **valid, common pattern** — not illegal, not “merging all etcds.”

```text
                    CONTROL PLANE (management cluster)
                    ┌─────────────────────┐
                    │ Argo CD, Crossplane │
                    └──────────┬──────────┘
                               │ reconciles desired state
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
         DATA PLANE       DATA PLANE       DATA PLANE
         (workload)       (workload)       (workload)
         team-a apps      team-b apps      shared services
```

### User-facing vs internal — who sees what

| User-facing (product surface) | Internal (platform ops) |
| --- | --- |
| Developer portal / Backstage | Crossplane provider credentials |
| `Create service` template | Cluster autoscaler / Karpenter config |
| Self-service CRDs (`DatabaseClaim`) | etcd backups, control-plane upgrades |
| Public docs + golden path guides | Incident runbooks for platform SLOs |
| Service catalog (owner, SLO, on-call) | Management cluster networking |

**Backstage is not the platform** — it is **one UX layer** on top of capabilities (`IDP.md`, `20.md`–`21.md`).

### Cognitive load — when architecture fails

Architecture succeeds when hello-world does **not** require a “CNCF landscape PhD.”

| Low cognitive load (good) | High cognitive load (leaky abstraction) |
| --- | --- |
| Template injects sidecar, NetworkPolicy, OTel | Dev wires CNI, certs, HPA before hello-world |
| `size: small` on a CR | Dev fills 40 AWS RDS fields |
| Docs: “merge this PR” | Docs: “ssh to node, run 12 commands” |
| Policy enforced automatically | Policy in PDF nobody reads |

**Cognitive load leaks** when developers must assemble infrastructure primitives the platform should have **productised** (`01.md`).

### Each capability — beginner examples

**Identity & access** — OIDC login to cluster, workload identity to S3, RBAC templates per team. App team does not hand-craft IAM JSON for every pod.

**Compute / runtime** — Kubernetes schedules pods; Karpenter or cluster autoscaler adds nodes. App team sets `resources.requests`, not picks EC2 instance types.

**Networking** — CNI, Ingress/Gateway, optional mesh. App team declares `host: api.example.com`, not configures iptables.

**Data** — Postgres operator or `DatabaseClaim` CR. App team requests `size: small`, not clicks RDS console.

**CI/CD** — Shared pipeline template (`06.md`). Build digest once; GitOps promotes (`07.md`).

**Observability** — OTel traces/metrics/logs on by default (`08.md`). Not “each team installs Prometheus from scratch.”

**Security / policy** — Kyverno blocks `:latest`, PSS baseline, image scan in CI (`11.md`–`12.md`).

**Tenancy** — Namespace + quota + NetworkPolicy bundle (`04.md`). Not “only CSS in Backstage.”

### Service mesh on the exam

A **service mesh** (Istio, Linkerd, Cilium mesh mode) is **one implementation** of:

- Secure service communication (mTLS)
- Traffic management (retries, splits)
- Observability (L7 metrics)

CNPA does **not** mandate mesh for every answer. Ask: *what capability is needed?* mTLS can also come from NetworkPolicy + ingress TLS + workload identity patterns.

### Thinnest viable platform applied to architecture

Do not build all layers on day one (`01.md` TVP). Typical evolution:

```text
Phase 1:  Runtime (K8s) + namespace tenancy + basic CI template
Phase 2:  GitOps + observability defaults + policy baseline
Phase 3:  Portal + self-service CRDs (DB, env)
Phase 4:  Fleet/multi-cluster + chargeback + advanced progressive delivery
```

Each phase adds **capabilities** proven by tickets and adoption metrics — not tools because a conference booth looked cool.

### Anti-patterns

| Scenario | Verdict |
| --- | --- |
| “Platform = Backstage only” | Portal without APIs/templates behind it |
| “Platform = Kubernetes only” | Runtime without golden paths |
| Every team installs own Prometheus | Observability not productised |
| UI-only workflows with no API/CR equivalent | Not API-first |
| Mesh in every answer regardless of question | Tool worship, not capability thinking |
| Developers need cluster-admin to deploy | Least privilege violated |
| 30 tools before one golden path works | Violates TVP |
| Control plane runs app traffic at scale | Confuses control vs data plane roles |

## Question

**Q1.** A platform architecture is best described as:

- A. A single Jenkinsfile
- B. Composed capabilities with APIs/UX for developers
- C. Only etcd
- D. Only Backstage

**Q2.** API-first means:

- A. UI only, no YAML
- B. Portal, CLI, and Git all drive the same APIs
- C. No RBAC
- D. No Git

**Q3.** Putting the GitOps engine in a management cluster:

- A. Illegal
- B. A valid control-plane pattern for many workload clusters
- C. Merges all etcds
- D. Replaces Kubernetes

**Q4.** Observability as a **capability**:

- A. Each team installs Prometheus from scratch
- B. Platform provides OTel/metrics/logs/traces by default on the path
- C. Only stdout on laptops

**Q5.** Modular architecture lets you:

- A. Never version APIs
- B. Change a backend (e.g. tracing vendor) behind a stable contract
- C. Skip SLOs
- D. Skip docs

**Q6.** Service mesh on the exam is usually:

- A. Mandatory for CNPA
- B. One implementation of secure service communication / traffic features
- C. A replacement for Git
- D. A DORA metric

**Q7.** Tenancy capability includes:

- A. Only CSS in Backstage
- B. Isolation, quotas, identity, network/policy boundaries
- C. Only Helm
- D. Only DORA

**Q8.** Cognitive load leaks when:

- A. The path injects sidecars/policies automatically
- B. Developers must wire CNI, certs, and HPA before hello-world
- C. Templates exist
- D. Docs exist

**Q9.** Fleet/multi-cluster is justified when:

- A. You like YAML
- B. Isolation, scale, or locality needs exceed one cluster — as a **product**
- C. Backstage requires it
- D. DORA forbids one cluster

**Q10.** The runtime layer in most CNPA answers is:

- A. Bare metal SSH only
- B. Kubernetes (or Kubernetes-like APIs)
- C. Only VMs with no API
- D. Only mainframes

## Answers

**Q1.** B — Architecture = composed capabilities + developer-facing APIs/UX, not one tool.  
**Q2.** B — API-first = portal, CLI, and Git share the same platform APIs — not UI-only.  
**Q3.** B — Management-cluster GitOps syncing workload clusters is standard control-plane pattern.  
**Q4.** B — Observability productised on the golden path (OTel defaults), not DIY per team.  
**Q5.** B — Modularity = swap backends behind stable contracts (e.g. OTel → different vendor).  
**Q6.** B — Mesh is **one** way to deliver secure comms/traffic — not mandatory for CNPA.  
**Q7.** B — Tenancy = isolation + quotas + identity + network/policy — real guardrails.  
**Q8.** B — Leaky abstraction forces infra assembly before hello-world — cognitive load failure.  
**Q9.** B — Fleet when isolation/scale/locality exceed one cluster — offered as platform product.  
**Q10.** B — Kubernetes (or K8s-like APIs) is the usual runtime layer in CNPA scenarios.

## Exam tips

- **Capability first, tool second** — “secure service comms” not “Istio required.”
- **Backstage ≠ platform** — portal is UX; capabilities are APIs + paths + policy.
- **Management cluster** = control plane for GitOps/fleet — valid pattern.
- **API-first** = portal + CLI + Git → same APIs — not “no YAML.”
- **Observability/ security on the path** — not DIY per team.
- **Cognitive load** — hello-world must not need a landscape PhD.
- **Multi-cluster** = product choice when isolation/scale/locality demand it.
- **Runtime** — Kubernetes is the default CNPA answer layer.

## Memorise

```text
Architecture   → composed capabilities + APIs/UX, not one tool
Stack (top)    → DX → golden paths → policy/tenancy → obs/secrets → runtime/infra APIs → cloud
Capability     → job-to-be-done ("traces", "tenancy", "secure comms")
Tool           → implementation (swappable if modular)
API-first      → portal, CLI, Git drive SAME platform APIs
Control plane  → Argo, Crossplane, portal backend (management cluster)
Data plane     → app workloads and traffic
Modular        → stable contract, swap backend (OTel vendor, GitOps engine)
Mesh           → ONE option for secure comms — not mandatory
Backstage      → UX layer — NOT the whole platform
```
