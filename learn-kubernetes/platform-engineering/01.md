# 01. Goals, Objectives, and Approaches

**Domain:** Core Fundamentals (36%)

> **New to platform engineering?** Start here. This chapter is the vocabulary for everything else (`02.md`–`22.md`). For extra depth read `WhichLayer.md` and `PlatformsWhitepaper.md` first or right after this file.

## Concept Refresher

### What platform engineering actually is

**Platform engineering** is building an **internal product** that lets many application teams ship software **themselves** — on a shared, safe, consistent foundation — without opening a ticket for every namespace, pipeline, or database.

Think of it like an **internal AWS**: developers do not call Amazon to create an EC2 instance; they use a self-service API. Your platform team does the same job inside the company.

The platform is **not** “we run Kubernetes.” It is the **integrated experience** on top: templates, APIs, docs, defaults for security and observability, and a clear paved way to deploy.

### The problem it solves

Without a platform, every product team repeats the same hard work:

| Pain | What developers experience |
| --- | --- |
| **Toil** | Same ticket every week: “create namespace,” “wire CI,” “add monitoring” |
| **Cognitive load** | Learn 20 CNCF tools, 12 YAML files, and three runbooks before hello-world ships |
| **Inconsistency** | Team A has GitOps + OTel; Team B has manual kubectl and no alerts |
| **Slow delivery** | 5-day wait for infra while the feature is ready in an hour |
| **Risk** | Security and observability are optional homework, not defaults |

Platform engineering moves that burden **off each app team** and into **one product** the platform team maintains.

### Goal (one sentence to memorise)

**Reduce cognitive load and toil** so product teams can deliver on a **shared, self-service** substrate — **faster, safer, cheaper** — without a human in every request.

- **Cognitive load** = mental effort to understand *how* to ship (tools, YAML, policy, networking). The platform hides incidental complexity.
- **Toil** = repetitive manual work that does not permanently improve the system (tickets, copy-paste, one-off scripts).

### Objectives (what “good” looks like)

| Objective | In practice |
| --- | --- |
| **Platform as a product** | Named users, docs, roadmap, versioning, feedback, SLOs — not a helpdesk |
| **Golden paths** | The easiest, recommended, secure way to ship — with an **escape hatch** for valid exceptions |
| **Thinnest viable platform (TVP)** | Smallest set of capabilities that cut the **biggest toil now** — not every CNCF project in year one |
| **Enable DevOps at scale** | App teams still **own** what they build and run; the platform owns the **path** |
| **Scale via APIs and automation** | CRDs, templates, GitOps, policy as code — not headcount on a ticket queue |

### Three operating models (exam filter)

Same Kubernetes cluster; three very different jobs:

| Model | How developers get stuff | Verdict |
| --- | --- | --- |
| **Ticket ops** | Jira ticket → wait → human runs `kubectl` | **Not a platform.** Does not scale |
| **DIY / wiki** | 40-page runbook; every team invents its own stack | High cognitive load; snowflake estates |
| **Platform as a product** | Self-service API, golden path template, docs, SLOs | **CNPA default answer** |

Exam trick: if the scenario describes a queue, pick **self-service** or **golden path**, not “hire more platform engineers.”

### Approaches (how you build it)

| Approach | Idea | Example |
| --- | --- | --- |
| Platform as product | Docs, versioning, feedback, product owner | Platform API has an SLO; quarterly DX survey |
| Golden path | Default easy, secure, observable way to ship | “Create service” template → repo + CI + namespace + OTel |
| Self-service | No wait; users drive via API/portal/CRD | `kubectl apply -f DatabaseClaim.yaml` → RDS appears |
| Guardrails | Safe defaults; policy as code | Kyverno blocks `:latest`, PSS enforced, quotas set |
| Canned infrastructure | Infra modules behind a higher-level API | Crossplane composition, Cluster API, Terraform module via portal |

### Golden path — walkthrough example

A developer wants a new microservice. **Without** a platform: clone 12 YAML files, ask for a namespace, configure CI by copy-paste, add Prometheus scrape config by hand, hope NetworkPolicy exists.

**With** a golden path:

```text
Developer clicks "Create Java REST service" in portal (or applies ServiceTemplate CR)
        │
        ▼
Platform provisions: Git repo, CI pipeline, K8s namespace, ingress, OTel, alerts, PSS baseline
        │
        ▼
Developer gets a working hello-world in hours, not weeks
        │
        ▼
Escape hatch: advanced team can still apply raw YAML — with extra review, not shadow IT
```

Golden path = **easiest recommended way**, not the **only legal way**.

### Thinnest viable platform (TVP)

Do **not** start with Backstage + Crossplane + Istio + Argo + Kyverno + 6 clusters because a blog post said so.

Start with the **one** capability that removes the most tickets today — often “create namespace + CI + observability defaults.” Add the next layer when adoption and metrics prove the need.

### Platform engineering vs neighbours

| Term | Role |
| --- | --- |
| **DevOps** | Culture: teams share build/run responsibility. Platform **enables** this at scale (`02.md`) |
| **SRE** | Reliability engineering — often applies to the platform product itself |
| **IDP** (Internal Developer Platform) | The **thing** platform engineering builds — portal + APIs + paths (`IDP.md`, `20.md`–`21.md`) |
| **GitOps / IaC** | **How** desired state is stored and reconciled — capabilities inside the platform (`03.md`, `07.md`) |

Platform engineering **does not** replace developers or deploy every app for them.

### What is **not** the goal

- Replace developers
- Own every microservice’s business logic
- Mandate one language or one framework with no exceptions
- Hide Kubernetes forever if users genuinely need it (abstraction level is a **product choice**)
- Success measured by **tools installed** or **Slack bots built**

### Anti-patterns (recognise these in scenarios)

| Anti-pattern | Why it fails |
| --- | --- |
| 5-day ticket for every namespace | Ticket ops, not self-service |
| Platform team deploys all apps | Ops silo; app teams lose ownership |
| Backstage with no templates/APIs behind it | Empty portal = wallpaper |
| 30-tool “platform” before anyone uses path 1 | Violates TVP |
| Golden path with zero escape hatch | Mandate → shadow IT |
| Platform team scales 1:1 with app teams | Self-service failed |

## Question

**Q1.** The primary customer of an internal platform is:

- A. The platform team itself
- B. Application / product teams using self-service capabilities
- C. The CNCF TOC

- A. A mature golden path
- B. Ticket-ops; replace with self-service
- C. GitOps

**Q3.** A golden path should be:

- A. The only legal way, with no exceptions
- B. The easiest recommended way, with an escape hatch
- C. A 40-page wiki only

**Q4.** Thinnest viable platform means:

- A. Install every CNCF project in year one
- B. Smallest capabilities that cut the biggest toil now

**Q5.** Platform engineering vs DevOps:

- A. Exact synonyms
- B. Platform engineering **enables** DevOps at scale; app teams still own delivery

- D. DevOps forbids platforms

**Q6.** “Platform as a product” implies:

- A. No SLOs
- B. Users, docs, roadmap, versioning, feedback
- C. Only Slack commands
- D. Only tickets

**Q7.** Reducing cognitive load means:

- A. Developers assemble 20 tools from the landscape
- B. The path hides incidental complexity (policy, obs, networking defaults)
- C. Removing all abstraction

**Q8.** Scaling the platform team 1:1 with app teams:

- A. The intended model
- B. A sign the platform is not self-service
- C. A DORA requirement
- D. Required by Kubernetes

**Q9.** An escape hatch exists so that:

- A. Policy never applies
- B. Valid exceptions are possible without shadow IT
- C. Golden paths are unused
- D. Git is optional always

**Q10.** Success of platform engineering is closest to:

- A. Number of tools installed
- B. Developers shipping on the path with less wait and fewer incidents
- C. Lines of Terraform in a monorepo
- D. Count of Slack bots

## Answers

**Q1.** B — Application teams are the **users** of the platform product.  
**Q2.** B — Queues do not scale; self-service absorbs repeatable work.  
**Q3.** B — Paved road, not a prison.  
**Q4.** B — TVP = minimum that removes maximum toil.  
**Q5.** B — Platform provides the path; app teams still own their services.  
**Q6.** B — Product discipline: users, docs, roadmap, feedback.  
**Q7.** B — Hide incidental complexity; do not dump the whole landscape on devs.  
**Q8.** B — Linear headcount = ticket ops failure.  
**Q9.** B — Exceptions with governance beat shadow IT.  
**Q10.** B — Outcomes for developers, not tool count.

## Exam tips

- **Product, not helpdesk.** Users = app teams; success = they ship without waiting on you.
- **Golden path = easiest default, not a prison.** Escape hatch beats shadow IT.
- **Ticket queue → self-service.** Never “hire more people on the queue.”
- **TVP beats tool museum.** Smallest fix for biggest toil wins.
- Headcount scaling 1:1 with app teams = failed platform.
- When stuck, ask: *“Who is the customer, and does this reduce cognitive load?”*

## Memorise

```text
Goal     → less cognitive load + toil, self-service substrate
Customer → application / product teams

Measure  → devs ship faster/safer, fewer tickets — not tool count
```
