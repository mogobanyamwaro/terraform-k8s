# 10. Policy Engines for Platform Governance

**Domain:** Observability, Security, and Conformance (20%)

## Concept Refresher

**Policy as code** enforces platform **guardrails** continuously: admission (validate/mutate/generate) and sometimes audit.

| Engine | Flavour |
| --- | --- |
| **Kyverno** | Kubernetes-native YAML policies; mutate/generate/validate |
| **OPA Gatekeeper** | ConstraintTemplate + Constraint (Rego) |
| **OPA** (standalone) | General policy (API, Envoy, CI) |
| ValidatingAdmissionPolicy | Built-in CEL (newer K8s) |

**What to encode:** PSS-like rules, required labels, image registry allowlist, no `:latest`, resource requests, NetworkPolicy presence, encryption, tenancy.

**Mutate/generate** = secure-by-default (inject `runAsNonRoot`, add NetworkPolicy). **Validate** = block non-compliant.

Policies should be **exceptions-capable** (escape hatch with annotation + audit) or developers will bypass the platform.

CI can run the same policy (`conftest`, Kyverno CLI) **shift left**; cluster admission is still the last gate.

- Same policies in CI + cluster.
- Exceptions are a product feature.
