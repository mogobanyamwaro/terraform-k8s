# 04. Application Environments and Infrastructure

**Domain:** Core Fundamentals (36%)

> **Prerequisite:** `03.md` (declarative management, Git as desired state). This chapter answers: *how does a platform slice dev/staging/prod, isolate teams, and promote releases safely?*

## Concept Refresher

### What is an “environment”? (plain English)

An **environment** is a **place on the platform** where a specific **revision** of your app runs — with its own **config**, **data**, **policy**, and **access rules**.

Typical names: `dev`, `test`, `staging`, `prod`. They are not just folders in Git; they are **operational slices** of the platform.

Each environment should answer:

| Question | Example answer |
| --- | --- |
| Where does it run? | `dev` namespace on shared cluster vs dedicated prod cluster |
| What config? | 1 replica, fake payment URL in dev; 10 replicas, real URL in prod |
| What data? | Synthetic test data in dev; real customer data in prod (isolated) |
| Who can deploy? | Any dev to dev; only platform + release mgr PR to prod |
| What policy? | Relaxed PSS in dev; restricted + NetworkPolicy in prod |

**Platform product mindset:** environments are a **capability you offer** — not “every team inventing their own Minikube laptop.”

### The golden rule: promote artifacts, not rebuilds

One of the most tested CNPA ideas:

```text
Build ONCE  →  test artifact  →  promote SAME artifact  →  change CONFIG per env
```

| Good (platform golden path) | Bad (snowflake anti-pattern) |
| --- | --- |
| CI builds image `sha256:abc…` once | Rebuild image for staging with different Dockerfile |
| Staging runs digest `abc…` | Prod runs `:latest` nobody tested |
| Prod PR only changes **overlay/values** (replicas, URLs) | “Prod is special” untested Terraform fork |
| Same pipeline template for all envs | Dev uses Docker Compose; prod uses different stack |

**Why it matters:** if prod runs a **different binary** than staging, your staging tests lied. **Environment is config**, not a new build.

```text
         ┌─────────────┐
CI ─────►│ image digest │─────► dev overlay    (replicas: 1, debug: on)
         │  sha256:abc  │─────► staging overlay (replicas: 2, real-ish URLs)
         └─────────────┘─────► prod overlay     (replicas: 10, real secrets)
```

Details in `07.md`, `15.md`, `16.md`.

### How platforms physically slice environments

There is no single “correct” layout — it is a **product choice** (blast radius vs cost):

| Pattern | What it looks like | Pros | Cons | Guardrails needed |
| --- | --- | --- | --- | --- |
| **Namespaces on shared cluster** | `team-a-dev`, `team-a-prod` namespaces | Cheap, fast to provision | Weaker isolation; noisy neighbour risk | RBAC, ResourceQuota, NetworkPolicy, PSS |
| **Separate clusters per env** | `dev-cluster`, `prod-cluster` | Strong blast-radius isolation | More cost and ops | Fleet GitOps, Cluster API |
| **Separate clusters per team** | `payments-prod`, `checkout-prod` | Hard multi-tenant boundaries | Highest cost | Same as above + chargeback |
| **vClusters / virtual clusters** | Logical cluster inside physical cluster | Middle ground isolation | Extra complexity | Platform maintains vCluster CRs |
| **Ephemeral PR previews** | Temp env per pull request, TTL delete | Fast feedback, low lead time | Not for long-lived prod | ApplicationSet, TTL controller |

**Exam:** neither “shared cluster” nor “separate cluster” is always wrong. Pick the answer that describes a **product trade-off** with **guardrails**, not absolutes.

```text
Shared cluster (cheap)          Separate prod cluster (safer blast radius)
┌────────────────────────┐      ┌──────────┐    ┌──────────┐
│ ns:dev  ns:staging     │      │ dev/stg  │    │   prod   │
│ ns:prod (with quotas)  │      │ cluster  │    │ cluster  │
└────────────────────────┘      └──────────┘    └──────────┘
```

### Tenancy on a shared cluster — guardrails are not optional

When many teams share one cluster, the platform **must** productise isolation:

| Guardrail | What it prevents |
| --- | --- |
| **RBAC** | Team A reading Team B's secrets |
| **ResourceQuota / LimitRange** | One team consuming all CPU/RAM |
| **NetworkPolicy** | Lateral movement between namespaces |
| **Pod Security Standards (PSS)** | Privileged pods in shared tenant |
| **Audit logging** | “Who deleted prod?” |

**Wrong answers on the exam:** no quotas, shared `cluster-admin` for all developers, disabled audit.

The platform offers **tenancy as a product** — app teams request a slice; platform applies guardrails by default.

### Dev/prod parity — same path, different scale

**Parity** does **not** mean identical node counts or identical secrets. It means:

| Same across envs | Different per env (config) |
| --- | --- |
| Golden CI/CD pipeline | Replica count |
| Same Deployment/Helm chart structure | Resource limits (smaller in dev) |
| Same observability hooks (OTel, alerts) | Alert thresholds / on-call routing |
| Same policy engine (Kyverno/OPA) | Strictness (audit vs enforce) |
| Same ingress/mesh **pattern** | URLs, TLS certs, external integrations |

```text
Parity YES:  dev and prod both deploy via GitOps PR + same chart + same scan stages
Parity NO:   dev = laptop Minikube; prod = bespoke ClickOps terraform snowflake
```

**Weak contract:** “test env is a random laptop Minikube” — prefer a **platform-provided dev slice** or **ephemeral preview** on the real path.

### Ephemeral / preview environments

**Ephemeral env** = short-lived environment spun up for a **PR** or feature branch, destroyed by **TTL** when merged or abandoned.

```text
Developer opens PR #42
        │
        ▼
ApplicationSet / pipeline creates preview env (unique URL)
        │
        ▼
Reviewer tests feature on real platform path
        │
        ▼
PR merged or closed → TTL deletes env (no zombie cost)
```

Benefits:

- **Lower lead time** — feedback before merge to main
- **Real path** — not “works on my machine”
- **Cost control** — TTL prevents orphan namespaces

Not a replacement for Git or DORA — a **platform capability** that improves them.

More: `15.md` (GitOps env workflows).

### Environment-specific config — where it lives

Config that changes per env should **not** require a **new image build**:

| Config type | Where it belongs | Not here |
| --- | --- | --- |
| Replica count, CPU limits | Kustomize overlay / Helm values | Baked into Dockerfile |
| Service URLs, feature flags | ConfigMap / values file | Hard-coded in source only |
| Secrets | Sealed Secrets / SOPS / external secret ref | Plaintext in Git |
| Ingress hostname | Overlay per env | Manual console edit |

**Pattern (Kustomize-style):**

```text
base/
  deployment.yaml          # image: myapp@sha256:abc (same digest everywhere)
overlays/dev/
  kustomization.yaml       # replicas: 1, smaller limits
  config.env               # PAYMENT_URL=https://sandbox...
overlays/prod/
  kustomization.yaml       # replicas: 10
  sealed-secret.yaml       # prod credentials
```

Promotion = PR that updates **prod overlay** to point at the **same digest** staging already validated.

### Infrastructure the platform hides vs what app teams own

Beginners confuse “we use Kubernetes” with “every team manages the whole stack.”

| App team owns (golden path) | Platform owns / productises |
| --- | --- |
| Application code & tests | CNI, cluster lifecycle, node pools |
| Deployment spec / chart values for **their** app | etcd, control plane, cloud IAM glue |
| Business config (within guardrails) | Ingress controller, DNS platform, identity integration |
| Their service SLOs | Shared observability backend, policy engine |
| On-call for **their** service bugs | On-call for **cluster/path** outages |

**Exam:** app teams should **not** hand-assemble CNI + etcd + cloud IAM glue on the golden path — the platform already **products** that.

They **should** own their Deployment spec, tests, and README.

### Key infrastructure concepts (vocabulary)

The platform **hides or exposes** these as self-service APIs:

| Concept | Platform examples | Why app teams care |
| --- | --- | --- |
| **Compute** | Nodes, Karpenter autoscaling, Cluster API | Apps need CPU/RAM; don't pick instance types by hand |
| **Networking** | CNI, Ingress/Gateway API, optional mesh | Reachability + TLS without bespoke nginx |
| **Identity** | OIDC, workload identity, RBAC templates | Apps authenticate to cloud APIs safely |
| **Data** | Postgres operators, storage classes, backups | Databases as declarative claims, not manual RDS clicks |
| **Tenancy** | Namespaces, projects, vClusters | Team gets an isolated slice |
| **Chargeback / showback** | Cost labels, reports per team/env | Treat infra as a consumed product |

**Cluster API** = declarative **cluster** provisioning (Kubernetes managing Kubernetes clusters) — a platform capability, not a developer portal or DORA dashboard.

Architecture map of how these stack: `05.md`.

### Chargeback and showback

Platforms at scale treat infra like a **billable internal product**:

| Model | Meaning |
| --- | --- |
| **Showback** | Report who consumed what (visibility, no invoice) |
| **Chargeback** | Actually allocate cost to teams/budgets |

Why CNPA cares: environments + tenancy + labels enable **product thinking** — teams see cost of long-lived preview envs, oversized prod replicas, etc.

Not a replacement for RBAC or NetworkPolicy — a **complementary** capability.

### Multi-cluster and fleet thinking (intro)

When one cluster is not enough:

```text
Git repo family (or app-of-apps)
        │
        ├── Argo CD → dev cluster
        ├── Argo CD → staging cluster
        └── Argo CD → prod cluster
```

Same **GitOps engine**, different **destinations**. Still declarative (`03.md`). Still promote **artifact**, change **overlay** per destination.

Deep dive: `15.md`, `16.md`.

### Anti-patterns

| Scenario | Verdict |
| --- | --- |
| Rebuild image for prod after staging passed | Violates immutability; untested binary in prod |
| Prod Terraform completely different from dev | Snowflake; weak dev/prod parity |
| All developers have cluster-admin | Fails tenancy guardrails |
| Config only in Slack / etcd edits | Not declarative; no audit |
| Preview envs never deleted | Cost waste; not ephemeral |
| “Prod is ClickOps only” | Fails platform CD model |
| Identical prod/dev node counts required for “parity” | Wrong — parity is **path**, not identical scale |

## Answers

**Q1.** B — Same digest = tested artifact; env differences are **config overlays**, not new builds.  
**Q2.** B — Shared cluster multi-tenancy requires RBAC, quotas, NetworkPolicy, PSS — not cluster-admin for everyone.  
**Q3.** B — PR previews are temporary, fast-feedback envs — not prod, not a Git replacement.  
**Q4.** B — Parity = same **golden path** and contracts; scale, secrets, and strictness differ.  
**Q5.** B — Platform products boring infra (CNI, IAM glue); apps own Deployment, tests, README.  
**Q6.** B — Isolation model is a deliberate product trade-off — neither choice is universally wrong.  
**Q7.** B — Per-env config in overlays/values/sealed secrets — never rebuild untested binaries per env.  
**Q8.** B — Cluster API declaratively provisions **clusters** — platform infra layer.  
**Q9.** B — Laptop Minikube ≠ platform contract; use dev slice or ephemeral preview on real path.  
**Q10.** B — Cost visibility supports infra-as-product; does not replace security guardrails.

## Exam tips

- **Promote artifacts, not rebuilds** — digest travels; config changes in overlay.
- **Env = config + policy + isolation**, not a new untested binary.
- **Isolation is a product choice** — always with guardrails on shared clusters.
- **Dev/prod parity** = same **path**, not identical **scale**.
- **Platform owns boring infra**; apps own app spec, tests, business config.
- **Ephemeral previews** = short-lived, PR-driven, TTL — improves lead time.
- **Cluster API** = declarative clusters; not Backstage, not Ingress.
- **Chargeback/showback** = product/cost thinking; doesn't replace RBAC.

## Memorise

```text
Environment  → slice where a revision runs (config, data, policy, access)
Promotion      → SAME artifact digest + DIFFERENT overlay/values per env
Never          → rebuild image for prod after staging passed
Shared cluster → MUST have RBAC + quotas + NetworkPolicy + PSS
Parity         → same golden path; scale/secrets/strictness differ
Preview envs   → ephemeral, PR-triggered, TTL delete
Platform owns  → CNI, cluster lifecycle, IAM glue, shared controllers
App owns       → code, Deployment spec, tests, env-specific values (in Git)
```
