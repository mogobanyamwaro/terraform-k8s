# 02. DevOps Practices in Platform Engineering

**Domain:** Core Fundamentals (36%)

> **Prerequisite:** `01.md` (goals, golden paths, platform-as-product). This chapter answers: *how does a platform turn DevOps culture into something 50 teams can actually use?*

## Concept Refresher

### DevOps in one paragraph (for beginners)

**DevOps** is not a job title or a tool. It is a **culture** where the people who **build** software also share responsibility for **running** it and **learning** from production feedback — instead of throwing code “over the wall” to a separate Ops team.

Before DevOps, the classic failure mode looked like this:

```text
Developers write code  →  throw over wall  →  Ops deploys blindly  →  outage  →  blame game
```

DevOps tries to collapse that wall:

```text
One team (or closely paired teams) owns: build + test + deploy + monitor + fix + improve
```

The hard part at scale: **50 product teams** cannot each invent their own Jenkins, kubectl runbooks, monitoring stack, and security checks. That is where **platform engineering** enters.

### Platform engineering vs DevOps — the relationship

| | DevOps | Platform engineering |
| --- | --- | --- |
| **What it is** | Culture and shared responsibility | Internal **product** that makes DevOps practicable at scale |
| **Who owns the app** | The application / product team | Still the application team |
| **Who owns the path** | Everyone improvising | Platform team productises CI, CD, obs, security defaults |
| **Analogy** | “We cook and serve our own food” | “We provide a well-equipped kitchen + recipes; you still cook your dish” |

Platform engineering **enables** DevOps. It does **not** replace application ownership or deploy every microservice for app teams.

### “You build it, you run it” — who is on-call for what?

This Amazon phrase confuses beginners. With a platform, ownership splits cleanly:

| Layer | Owner | On-call for |
| --- | --- | --- |
| **Application code & business logic** | App / stream-aligned team | Their service bugs, their SLOs, their feature outages |
| **Golden path** (CI template, cluster, GitOps, defaults) | Platform team | Pipeline broken, cluster down, portal API failing |
| **Shared infra** (DNS, identity, mesh control plane) | Platform or infra team | Platform SLOs |

```text
App team:     "Our checkout API is slow"        → app team debugs their code
Platform team: "Every team's deploy failed at 3am" → platform fixes the CI runner / cluster
```

**Wrong model:** platform team on-call for every app bug → they become a bottleneck and app teams stop learning production.

**Wrong model:** platform team deploys all apps → recreates the old Ops silo with extra steps.

### How the platform “productises” DevOps practices

DevOps practices that work for one team must become **defaults in the golden path** for all teams:

| DevOps practice | Without a platform | Platform product shape |
| --- | --- | --- |
| **CI** | Each team copy-pastes a broken pipeline | Shared versioned templates, caches, runners (`06.md`, `13.md`) |
| **CD / GitOps** | Laptop `kubectl apply` to prod | Env promotion via Git PR; agent reconciles cluster (`07.md`, `15.md`) |
| **IaC / CaC** | Terraform on one engineer’s laptop | Modules/compositions/CRDs exposed as **self-service API** (`03.md`, `17.md`–`19.md`) |
| **Feedback** | “Add monitoring when you have time” | OTel, dashboards, alerts wired in the template (`08.md`) |
| **Security shift-left** | Security review at the end | Linters, SAST, image scan, PSS defaults in CI (`12.md`) |
| **You build it, you run it** | Wiki says “ask Ops” | App team runs their service on a paved, observable path |
| **Blameless learning** | Hero fixes fire; nothing changes | Post-incident → platform adds guardrail, template fix, or docs |

**Key idea:** the platform turns “good practice we preach in a wiki” into “good practice that happens automatically unless you opt out.”

### CALMS — DevOps values the platform must scale

CALMS is a DevOps mnemonic. On CNPA, you need to know what each letter means **in a platform context**:

| Letter | Meaning | Platform example |
| --- | --- | --- |
| **C** — Culture | Collaboration, shared responsibility, blameless postmortems | App teams own services; platform does not become a ticket queue |
| **A** — Automation | Repeatable pipelines, GitOps, policy as code | Self-service CRD instead of Jira ticket for a namespace |
| **L** — Lean | Remove waste: waiting, handoffs, duplicate work | Kill 5-day namespace tickets; one template family for all repos |
| **M** — Measurement | Data-driven improvement | DORA metrics, path adoption, platform SLOs (`22.md`, `DORA.md`) |
| **S** — Sharing | Inner-source templates, docs, modules | One golden CI template PR’d by any team; not 40 secret runbooks |

Exam pattern: if a scenario adds **more meetings, more tickets, or more copy-paste**, it violates **Lean**. If nobody measures adoption, it violates **Measurement**. If every team has a snowflake cluster, it violates **Sharing**.

### Team topologies (who does what)

From *Team Topologies* — simplified for CNPA:

| Team type | Job | Platform exam note |
| --- | --- | --- |
| **Stream-aligned** | Builds and runs a product feature end-to-end | Primary **users** of the platform |
| **Platform** | Builds internal products (APIs, templates, clusters) that stream teams consume | Must not become the **only** people who can deploy |
| **Enabling** | Coaches teams onto the path; temporary help | Teaches golden path; does **not** permanently do app work |
| **Complicated-subsystem** | Deep specialists (e.g. legacy mainframe bridge) | Platform team should **not** become this bottleneck |

```text
Enabling team:  "Let me pair with you for two sprints to migrate onto the golden path"
Platform team:  "Here is the self-service API + docs; we maintain it as a product"
Ops silo:       "Send us a ticket; we deploy your app for you every time"  ← anti-pattern
```

### Before and after — one team’s journey

**Before platform productisation:**

1. Developer writes feature  
2. Opens ticket for namespace (3 days)  
3. Copy-pastes CI YAML from another repo (wrong secrets)  
4. Manually adds Prometheus scrape config (forgets)  
5. Deploys with laptop kubectl  
6. Prod outage; nobody knows who changed what  

**After platform productisation:**

1. Developer applies `ServiceTemplate` or clicks portal  
2. Gets repo + CI + namespace + OTel + PSS baseline in one flow  
3. PR triggers golden CI (lint, test, scan, build digest)  
4. Merge to main → GitOps PR to staging → promote to prod via Git  
5. App team on-call for their service; dashboards exist by default  
6. Incident → blameless review → platform adds missing guardrail to template  

Same DevOps **intent**; the platform removes the repeated toil.

### CI vs CD vs GitOps — don’t mix them up

Beginners often lump everything into “DevOps pipeline.” CNPA separates them:

| Stage | Job | Platform owns |
| --- | --- | --- |
| **CI** | Build, test, scan → **immutable artifact** | Pipeline template, runners |
| **CD** | Move proven artifact to an environment | Promotion rules, approvals |
| **GitOps** | Desired cluster state in Git; agent **pulls** and reconciles | Argo CD/Flux as platform capability |

**Anti-pattern:** CI job runs `kubectl apply` to production with cluster-admin. That is push deploy + brittle credentials — not a platform golden path.

Details in `06.md` (CI), `07.md` (CD/GitOps), `13.md`–`16.md` (delivery domain deep dive).

### IaC only for central Ops — incomplete DevOps

Infrastructure as Code (Terraform, Crossplane, Cluster API) is a DevOps practice. But if **only** a central ops team runs it and app teams still open tickets, you have automation **without** self-service.

The platform exposes IaC as:

- A **CRD** (`DatabaseClaim`, `Environment`)
- A **portal form** that renders to a composition
- A **GitOps repo** app teams can PR into (with guardrails)

App teams consume; platform team maintains the modules and policy.

### Anti-patterns (DevOps edition)

| Scenario | Verdict |
| --- | --- |
| Platform deploys every microservice for app teams | Ops silo / bottleneck |
| “DevOps engineer” = person who runs all kubectl | Ticket ops in disguise |
| Wiki says “run these 12 commands” with no template | DIY / high cognitive load |
| Mandatory Change Advisory Board for every hello-world | Violates Lean |
| Post-incident → fire someone, no template fix | Violates Culture |
| 40 unique CI pipelines, no shared template | Violates Sharing |
| No metrics on path adoption | Violates Measurement |
| Enabling team permanently owns app delivery | Enabling became ops silo |

- A. Full DevOps
- B. Incomplete; the platform should expose **self-service** of that IaC

- D. The only CNCF pattern

## Answers

**Q1.** B — DevOps is culture + shared ownership; the platform provides self-service paths so that culture scales.  
**Q2.** B — Split ownership: app teams run **their** services; platform runs **the path**.  
**Q3.** B — Shift-left security and quality as **defaults** in the golden CI template.  
**Q4.** B — Centralised deploys recreate the old Ops silo; app teams lose ownership.  
**Q5.** B — Measurement = DORA, adoption, platform SLOs — not vanity counts.  
**Q6.** B — Blameless learning → fix the **system** (guardrail, template, docs).  
**Q7.** B — Sharing = inner-source templates and docs, not snowflake clusters.  
**Q8.** B — Lean = remove wait, tickets, duplicate pipelines, snowflakes.  
**Q9.** B — Enabling **coaches**; platform **builds and maintains** the product.  
**Q10.** B — IaC without self-service is incomplete; expose it via API/template/CRD.

## Exam tips

- Platform **enables** DevOps; it does **not** do all the deploys or own all on-call.
- **Defaults in the path** beat wiki sermons — linters, scans, OTel wired in the template.
- **CALMS:** tickets and snowflakes = bad Lean/Sharing; no metrics = bad Measurement.
- **Enabling ≠ platform:** coaches vs builds the product.
- **IaC + tickets only** = incomplete; need **self-service** exposure.
- CI `kubectl` to prod = classic anti-pattern (push, brittle creds).

## Memorise

```text
DevOps        → culture: build + run + feedback, shared ownership
Platform role → productise the path so 50 teams don't reinvent tooling
On-call       → app team: their service | platform team: the path
CALMS         → Culture, Automation, Lean, Measurement, Sharing
Enabling      → coaches onto path (temporary)
Platform team → builds & maintains path (ongoing product)
Anti-pattern  → platform deploys all apps = ops silo
```
