# 06. Continuous Integration Fundamentals

**Domain:** Core Fundamentals (36%)

> **Prerequisite:** `02.md` (DevOps), `04.md` (artifact promotion), `05.md` (golden paths layer). This chapter answers: *what does CI do on a platform — and where does it **stop** before CD/GitOps begins?*

## Concept Refresher

### What is Continuous Integration? (plain English)

**Continuous Integration (CI)** means: on **every code change** (usually every commit or PR), the platform **automatically**:

1. **Builds** the application  
2. **Tests** it (unit, lint, security scans)  
3. **Produces evidence** that the change is safe to integrate  
4. **Outputs an immutable artifact** (container image digest, package, SBOM)

The goal is **fast feedback to the author** — find bugs in minutes, not after a weekly “integration day.”

```text
Developer pushes code / opens PR
        │
        ▼
CI runs automatically (no human clicks "build")
        │
        ├── lint, unit tests, security scans
        ├── build container → push registry with DIGEST
        └── report pass/fail back to PR
        │
        ▼
Author fixes or merges when green
```

**CI does not deploy to production.** It **proves** a revision is worth deploying. That separation is one of the most tested CNPA ideas.

### CI vs CD vs GitOps — know where each stops

Beginners merge these into one “pipeline.” On the exam, keep them separate:

| Stage | Job | Who/what runs it | Output |
| --- | --- | --- | --- |
| **CI** | Verify & build | Pipeline on PR/commit | Immutable artifact + test evidence |
| **CD** | Deliver proven artifact to an env | GitOps agent or CD system | Running workload in dev/staging/prod |
| **GitOps** | Keep cluster = Git desired state | Pull-based reconciler (Argo CD, Flux) | Cluster matches config repo |

```text
  CI (prove)                    CD/GitOps (deploy)
┌─────────────────┐            ┌──────────────────────────┐
│ test → build    │  digest    │ update Git overlay/PR    │
│ scan → sign     │ ────────►  │ agent pulls + reconciles │
│ push digest     │            │ cluster runs digest      │
└─────────────────┘            └──────────────────────────┘
        │                                   │
   NO kubectl to prod                  NO rebuild for prod
```

| Anti-pattern | Why it fails |
| --- | --- |
| CI job `kubectl apply` to prod | Push deploy; prod creds in CI; blurs CI/CD boundary |
| CI rebuilds different image for prod | Violates build-once-promote (`04.md`) |
| No CI — manual “it works on my laptop” | No repeatable verification |

Deep CD/GitOps: `07.md`. Pipeline operations: `13.md`.

### Platform CI is a product — not “every team copy-pastes YAML”

On a platform, CI is a **golden-path capability** from `05.md`:

| Ad-hoc CI (DIY) | Platform CI product |
| --- | --- |
| 40 teams, 40 broken pipeline copies | One **versioned template family** |
| Security scan “when someone remembers” | SAST + SCA + secret scan **on by default** |
| `:latest` tags everywhere | **Digest** + SBOM + optional signing |
| Slow builds, no cache | Shared **runners** with autoscaling + caching |
| Platform team kubectl deploys for you | App team merges PR; CD/GitOps deploys |

**Platform CI product includes:**

- Reusable pipeline templates (GitHub Actions reusable workflows, GitLab `include`, Tekton `Pipeline`, Argo Workflows)
- Shared runners with caching and queue SLOs
- Required status checks on app repos
- Language packs (Java, Go, Node) as variants of the **same product family**
- Output: **digest + provenance**, never `:latest` as the contract

App teams still write **their** unit/integration tests and app code. Platform owns the **template**, runners, and default quality gates.

### Typical golden-path CI stages

Order matters — **fail fast** means cheap checks before expensive ones:

```text
1. Lint / format          ← seconds
2. Unit tests             ← seconds–minutes
3. Security               ← SAST, SCA, secret scan
4. Build image            ← minutes
5. SBOM + sign (optional) ← supply chain
6. Integration / contract ← heavier, later
7. Publish artifact       ← push digest to registry
8. (Optional) open GitOps config PR with digest — NOT kubectl apply
```

| Stage | Purpose | Platform default? |
| --- | --- | --- |
| Lint / unit | Catch logic/style bugs fast | Yes — in template |
| SAST / SCA / secret scan | Shift-left security (`12.md`) | Yes — golden path |
| Build + push | Produce immutable artifact | Yes |
| SBOM + sign | Supply chain evidence | Increasingly default |
| Integration / contract | Service boundary checks | Often in template |
| kubectl to prod | **No** — that is CD, wrongly placed | **Anti-pattern** |

`13.md` goes deeper on template versioning, runner queues, monorepos, and pipeline SLOs.

### Immutable artifacts — digest, not `:latest`

CI’s main output for a container app is an **immutable image identified by digest**:

```text
Bad:   myapp:latest          ← moves every build; prod may not match staging
Good:  myapp@sha256:abc123…  ← exact bytes; promotable through all envs
```

| Concept | Meaning |
| --- | --- |
| **Immutable artifact** | Built once; content-addressed; never “replaced in place” |
| **Digest** | SHA256 of image layers — unique fingerprint |
| **SBOM** | Software Bill of Materials — what is inside the image |
| **Provenance / signing** | Evidence of who built what, when (Sigstore, cosign) |

**Build once, promote many** (`04.md`): staging validates digest `abc…`; prod overlay points at the **same** digest — not a rebuild, not `:latest` in prod only.

### CI fundamentals — platform encoding

| CI principle | What it means | Platform encoding |
| --- | --- | --- |
| **Every commit is a candidate** | Any change can be integrated if green | PR pipelines on every push |
| **Fail fast** | Cheap tests before expensive e2e | Lint/unit before 3-hour integration |
| **Hermetic / repeatable** | Same inputs → same outputs | Pinned actions, lockfiles, pinned base images |
| **Trunk-based / small batches** | Small frequent merges | Enables DORA deployment frequency |
| **Artifact promotion** | Build once, deploy many times | Digest travels; env config changes |
| **Shift-left security** | Scan before merge, not after breach | SAST/SCA in template by default |

### Fail-fast — why order matters

```text
WRONG order:  3-hour e2e  →  unit tests  →  author waits hours for typo
RIGHT order:  lint (30s)  →  unit (2m)  →  build  →  e2e (optional, parallel)
```

Runner **queue time** also affects DORA **lead time for changes** — if CI waits 45 minutes in queue, your “fast feedback” product failed (`13.md`, `22.md`).

### Prod kubeconfig in CI — classic anti-pattern

```text
BAD CI job:
  - checkout code
  - docker build
  - kubectl apply -f prod/     ← cluster-admin creds in CI
```

Why CNPA marks this wrong:

| Problem | Better approach |
| --- | --- |
| CI has prod credentials | GitOps **agent** holds cluster creds |
| Push deploy from CI | **Pull** reconcile from Git (`07.md`) |
| Git and cluster drift | Git is desired state; CI only updates Git (optional PR) |
| Blast radius of compromised CI | CI compromise ≠ direct prod mutation |

CI **verifies**. CD **deploys**. GitOps **reconciles**.

### Required status checks — guardrails that preserve self-service

**Required checks** on PRs = branch protection rules: merge blocked until CI is green.

```text
Self-service preserved:  dev merges own PR when checks pass
NOT ticket ops:          dev opens ticket for platform to merge
```

Checks enforce quality **without** a human gatekeeper for every commit — aligns with platform-as-product (`01.md`).

Typical required checks: unit tests, lint, SAST, image scan, contract tests.

### Caching — speed without breaking trust

Shared runners cache dependencies (Maven, npm, Go modules) to shorten feedback loops.

| Good caching | Bad caching |
| --- | --- |
| Keyed by lockfile hash | Stale cache hides broken deps |
| Speeds feedback | Replaces tests (never) |
| Platform SLO on queue + duration | Ignored until devs complain |

Caching **speeds** CI; it does not replace hermeticity if keys are correct.

### Tekton / Argo Workflows — CI engines, not GitOps CD

On Kubernetes platforms, CI may run **on-cluster**:

| Tool | Role on platform | Not this |
| --- | --- | --- |
| **Tekton** `Pipeline`/`Task` | K8s-native CI workflow engine | GitOps CD engine |
| **Argo Workflows** | DAG/batch CI, ML pipelines | Argo **CD** (different product) |
| **GitHub Actions / GitLab CI** | Hosted/reusable pipeline templates | Policy engine or mesh |

Exam: structure and ownership matter — **versioned template with default stages** — not memorising brand-specific YAML.

### Shift-left security in CI (intro)

Platform templates embed security **before** merge:

| Scan | Catches |
| --- | --- |
| **SAST** | Code vulnerabilities |
| **SCA** | Vulnerable dependencies |
| **Secret scan** | Keys committed to Git |
| **Container image scan** | CVEs in base image / layers |

Policy in prod (Kyverno) is a **second line**; CI is the **first** (`12.md`).

### What app teams vs platform team own

| App team | Platform team |
| --- | --- |
| Application source code | Pipeline **template** (versioned) |
| Unit & integration tests for **their** logic | Default stages: lint, SAST, build, push |
| Choosing when to merge PR | Runners, cache, queue SLO |
| Business-specific test cases | Signing, SBOM infrastructure |
| README, CODEOWNERS | Docs: “how to use template v2” |

### Anti-patterns

| Scenario | Verdict |
| --- | --- |
| CI output = live prod mutation | Wrong — CI verifies, not deploys |
| `:latest` as artifact contract | Weak immutability |
| Every team copies pipeline YAML | Violates Sharing; unique bugs |
| Prod kubeconfig in every CI job | Push deploy + cred leak risk |
| 3-hour e2e before unit tests | Violates fail-fast |
| Rebuild different image for prod | Violates build-once-promote |
| Jenkins UI clicks as source of truth | Not declarative/repeatable |
| Monthly integration only | Not continuous integration |
| No artifacts produced | CI must output provable build |

## Question

**Q1.** CI’s main output for a container app is:

- A. A live prod mutation
- B. An immutable image (digest) plus test evidence

- B. Weak immutability; prefer digest

- A. Every team copies YAML with unique bugs

**Q4.** Prod kubeconfig in every CI job:

- A. Least privilege

- A. GitOps CD engines
- B. Kubernetes-native **CI/workflow** engines (examples)
- C. Policy engines
- D. Service meshes

**Q8.** Required status checks on PRs:

- A. Against DevOps
- B. Guardrails that still keep self-service (merge when green)
- C. Ticket ops
- D. ClickOps

**Q9.** Caching CI dependencies:

- A. Breaks hermeticity always
- B. Speeds feedback if keys are correct
- C. Replaces tests
- D. Replaces Git

**Q10.** CI fundamentals on CNPA emphasise:

- A. Jenkins UI clicks as source of truth
- B. Automated, repeatable verification of every change
- C. Monthly integration only
- D. No artifacts

## Answers

**Q1.** B — CI produces verified **immutable artifact** (digest) + test evidence — not prod mutations.  
**Q2.** B — `:latest` moves; digest gives provenance and safe promotion.  
**Q3.** B — Templates encode security scans and tests as **defaults** on the golden path.  
**Q4.** B — Prod creds in CI = push anti-pattern; GitOps/CD agent should reconcile.  
**Q5.** B — Fail-fast = cheap tests first, expensive tests later.  
**Q6.** B — Same digest through dev/staging/prod; env differs in **config** only.  
**Q7.** B — Tekton/Argo Workflows = CI/workflow **examples** — not GitOps CD engines.  
**Q8.** B — Required checks = automated guardrails; dev merges when green (self-service).  
**Q9.** B — Cache speeds feedback when keyed correctly; does not replace tests.  
**Q10.** B — CI = automated, repeatable verification on every change + artifacts.

## Exam tips

- **CI verifies. CD deploys. GitOps reconciles.** Three different jobs.
- **Digest, not `:latest`** — artifact immutability for promotion.
- **Templates = golden path** for quality gates — not copy-paste per team.
- **No prod kubeconfig in CI** — agent pulls from Git.
- **Fail-fast** — cheap tests before expensive e2e.
- **Build once, promote many** — same digest, different overlays.
- **Tekton / Argo Workflows** = CI examples; Argo **CD** is different.
- **Required checks** = self-service with guardrails, not ticket ops.

## Memorise

```text
CI job        → build + test + scan → immutable artifact (digest + evidence)
CI output     → NOT a live prod deploy
CD/GitOps     → takes proven digest → updates env config → agent reconciles
Templates     → versioned platform product; security scans ON by default
Fail-fast     → lint/unit first, heavy e2e later
Promotion     → SAME digest through envs (04.md)
Anti-pattern  → kubectl in CI, :latest contract, rebuild for prod
Tekton/Workflows → CI engines (examples) — not GitOps CD
```
