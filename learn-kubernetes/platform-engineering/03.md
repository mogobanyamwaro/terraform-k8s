# 03. Declarative Resource Management

**Domain:** Core Fundamentals (36%)

> **Prerequisite:** `01.md` (platform-as-product), `02.md` (DevOps + GitOps intro). This chapter answers: *how does a platform store “what we want” and make reality match — without humans clicking consoles or running one-off scripts?*

## Concept Refresher

### Imperative vs declarative — the core idea

Two ways to change infrastructure:

| Style | You say | Example |
| --- | --- | --- |
| **Imperative** | *How* to do it — steps, commands, API calls | “Run `kubectl scale deploy api --replicas=5`, then `aws rds create-db-instance ...`” |
| **Declarative** | *What* you want — desired end state | “`replicas: 5`” in a Deployment; `DatabaseClaim` with `size: small` |

**Declarative** configuration describes **desired state**. A **controller / reconciler** continuously compares **actual state** (what exists now) to **desired state** (what you declared) and acts to close the gap.

```text
Desired state (Git / CR spec)     Actual state (live cluster / cloud)
         │                                    │
         └──────────► Reconciler ◄────────────┘
                         │
                         ▼
              Create / update / delete until they match
```

**Platform exam mantra:** *What, not how.*

### Three terms you must not confuse

| Term | Meaning | Example |
| --- | --- | --- |
| **Desired state** | Configuration sufficient to recreate the system | Deployment YAML with `replicas: 3`, image digest `sha256:abc…` |
| **Actual state** | What really exists right now | Cluster currently has 2 pods because someone scaled manually |
| **Drift** | Actual ≠ desired | Console change bumped replicas to 2; Git still says 3 |

On a platform, **Git** (or another versioned store) should hold desired state. Drift becomes **visible** (GitOps diff, audit) and **fixable** (reconcile or revert commit).

**Not in desired state:** database row contents, user uploads, runtime logs. **Often in desired state:** app config, infra size, policy rules, secret *references* (Sealed Secrets, SOPS paths).

### Why platforms insist on declarative management

Without it, every team operates differently:

| Without declarative platform | With declarative platform |
| --- | --- |
| “SSH and run these 12 commands” wiki | One `TeamWorkspace` CR or Git PR |
| Snowflake staging cluster nobody can reproduce | Same overlay pattern: dev → staging → prod |
| Nobody knows who changed prod in the AWS console | Git history + PR review |
| Rollback = panic and guess | Rollback = revert commit; reconciler converges |
| Self-service = impossible (too many steps) | Self-service = apply a CR; controller does the toil |

Declarative management is how the platform delivers **repeatability**, **GitOps**, **self-service CRDs**, and **policy as code** — all from the same idea.

### The reconciliation loop (beginner version)

Kubernetes built this pattern. Platforms extend it.

```text
1. User merges YAML to Git (or kubectl apply a CR)
2. Controller watches the object
3. Controller reads spec (desired)
4. Controller inspects cluster/cloud (actual)
5. If different → create/update/delete resources
6. Controller writes status (observed, conditions, errors)
7. Repeat forever (or on every change)
```

| Built-in example | Desired | Reconciler |
| --- | --- | --- |
| Deployment | `spec.replicas: 3` | Deployment controller creates/deletes Pods |
| Service | `spec.ports`, selectors | Endpoints updated as Pods change |
| Crossplane `RDS` claim | `size: small`, `engine: postgres` | Crossplane provider creates AWS RDS |

**Exam:** the reconciler for Kubernetes built-ins is **controllers** (Deployment controller, etc.) — not Backstage, not DORA.

Deep dive on CRDs and operators: `17.md`, `Operators.md`.

### Declarative layers on a platform

A real platform stacks declarative config at several levels. App teams usually touch the top; platform team owns lower layers.

| Layer | Who edits | Examples | Purpose |
| --- | --- | --- | --- |
| **App runtime** | App team | Deployment, Helm chart, Kustomize overlay | How the app runs |
| **Cluster / tenancy** | App or platform | Namespace, ResourceQuota, vCluster, `Project` CR | Isolation, quotas |
| **Infra** | Platform (exposed via API) | Crossplane XR, Cluster API `Cluster`, Terraform module (if reconciled) | Cloud resources behind self-service |
| **Policy** | Platform / security | Kyverno `ClusterPolicy`, OPA `Constraint` | Guardrails enforced continuously |

```text
App team declares:     Application CR  →  Deployment + Service + Ingress
Platform declares:     ClusterPolicy     →  "no :latest", PSS baseline
Platform exposes:      DatabaseClaim CR  →  Crossplane creates RDS
```

Higher-level CRDs are **still declarative** — users declare `size: small`, not 40 AWS API fields.

### Git as the source of truth (state store)

On a platform, desired state should live in a **versioned, reviewable** store:

- Git repo (most common for CNPA)
- OCI registry for some policies/charts
- Internal config service (less common in exam scenarios)

**Workflow developers experience:**

```text
Edit manifest in Git  →  PR + review  →  merge  →  GitOps agent pulls  →  cluster converges
```

Benefits the exam cares about:

- **Audit trail** — who changed prod and when
- **Rollback** — revert commit; don't improvise
- **Same path for 50 teams** — not 50 unique kubectl habits
- **Credentials** — cluster/cloud creds stay with the **agent**, not every developer laptop

CNPA will not grade OpenGitOps pillar order like CGOA, but **pull + reconcile** beats **CI `kubectl apply`** every time.

Details: `07.md` (CD/GitOps), `gitops/` folder for GitOps cert depth.

### ClickOps — the usual wrong answer

**ClickOps** = making changes in the AWS/GCP/Azure **console** (or one-off CLI) with **no reviewed desired state** in Git.

| ClickOps | Declarative platform |
| --- | --- |
| Fast for one hero | Scales for many teams |
| No PR, no rollback story | Git history + revert |
| Drift invisible until outage | Drift visible in GitOps diff |
| Self-service impossible | CR + GitOps = self-service |

Exam: console as **real source of truth** → **wrong**.

### Immutability and versioning

Declarative platforms depend on **knowing exactly what was deployed**:

| Good | Bad |
| --- | --- |
| Image digest `sha256:…` | Tag `:latest` |
| Chart version `2.4.1` | “Whatever Helm finds today” |
| Pinned Terraform/Crossplane module version | Unversioned copy-paste module |
| Same artifact promoted dev → prod | Rebuild different image per environment |

**Immutable artifact + declarative config per environment** = reproducible environments (`04.md` covers env promotion).

### Policy as code is declarative too

Policy is not a PDF security checklist. On a platform:

```yaml
# Kyverno example (conceptual)
spec:
  rules:
    - validate:
        message: "Use an image digest, not :latest"
        pattern:
          spec:
            containers:
              - image: "!*:latest"
```

The **policy object** is desired state. The **policy engine** reconciles continuously — block bad creates, mutate defaults, audit violations.

Humans grep-ing clusters weekly = **not** policy as code.

More: `11.md`, `12.md`.

### Crossplane compositions — why they exist

Raw cloud APIs are too low-level for app teams. **Crossplane compositions** (and similar patterns) offer a **higher-level declarative API**:

```text
User applies:          DatabaseClaim { team: payments, size: small }
                              │
Composition + XRD:     platform team's opinionated template
                              │
Cloud actual:          RDS instance + subnet group + security group
```

User declares **job-to-be-done**. Platform hides **how** AWS fields are wired.

Same idea: Cluster API for clusters, cert-manager for certs, platform `Team` CR for namespace + quota + RBAC.

### Imperative habits that fail the platform test

| Habit | Why it fails |
| --- | --- |
| `helm upgrade` from laptop, no Git | Drift-prone; no review/rollback |
| CI job `kubectl apply` to prod | Push deploy; brittle creds; not GitOps |
| Wiki with 12 shell commands | Imperative source of truth |
| Edit etcd / kube-apiserver by hand | Breaks everything; not self-service |
| Ticket to human for every YAML apply | Ticket ops, not declarative self-service |

### Declarative + self-service together

These are **two sides of one coin**:

- **Declarative** = users say *what* they want (YAML/CR)
- **Self-service** = they can do it *without a ticket* (portal, CRD, template)

```text
Bad:  ticket → human writes YAML → human kubectl applies
Good: developer merges CR or clicks portal → controller/GitOps reconciles
```

That is the platform golden path from `01.md`.

### Anti-patterns

| Scenario | Verdict |
| --- | --- |
| Source of truth is the cloud console | Fails declarative management |
| Every team maintains unique snowflake scripts | High cognitive load |
| `:latest` everywhere | Weak immutability |
| Leaky CRD with 200 cloud fields | Bad self-service API; use higher-level spec |
| Policy only in PDF | Not policy as code |
| No reconciler — CRD with no controller | Broken platform API (`17.md`) |

- A. Backstage
- B. Controllers (Deployment controller, etc.)

- A. etcd directly
- B. Their declarative app/env manifests (or a CR), not raw cloud consoles

- D. Container runtime CRI sockets

- A. Tickets for every YAML

## Answers

**Q1.** B — Contract is desired state; platform/controllers converge actual toward it.  
**Q2.** B — Spec describes *what* (replicas, image); controller figures out *how*.  
**Q3.** B — Console changes lack reviewed, versioned desired state → drift and audit gaps.  
**Q4.** B — Compositions wrap cloud complexity in a simpler declarative API for users.  
**Q5.** B — Policy objects continuously enforced — not manual weekly grep or PDF rules.  
**Q6.** B — Laptop Helm with no Git = drift-prone imperative ops, not golden path.  
**Q7.** B — Pinning versions enables reproduce, review, and rollback.  
**Q8.** B — Built-in controllers (Deployment, etc.) run the reconciliation loop.  
**Q9.** B — App teams work through manifests/CRs/Git — not etcd, consoles, or API server flags.  
**Q10.** B — Self-service without tickets; automation reconciles after merge/apply.

## Exam tips

- **What, not how** — declarative = desired state, not command lists.
- **Console ClickOps** as source of truth = usual wrong answer.
- **Higher-level CRDs** are still declarative — `size: small` beats 200 cloud fields.
- **Pull + reconcile** (GitOps agent) beats **CI kubectl apply** (push).
- **Policy as code** = policy **objects** enforced continuously.
- **`:latest` / unversioned modules** weaken immutability — exam flags them.
- **Controllers** reconcile built-ins; **operators** reconcile custom CRs.

## Memorise

```text
Declarative  → describe WHAT you want (spec), not HOW (commands)
Actual vs desired → drift = mismatch; reconciler fixes or GitOps shows diff
State store  → Git (versioned, reviewed) — not the cloud console
Reconciler   → controller loop: spec → act → status → repeat
Self-service → user merges CR / PR; automation converges — no ticket
Immutability → digests + pinned versions, not :latest
Policy       → declarative objects (Kyverno/OPA), not PDF grep
```
