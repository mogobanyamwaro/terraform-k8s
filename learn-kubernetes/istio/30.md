# 30. istioctl proxy-status and xDS Sync State

## Concept Refresher

`istioctl proxy-status` (alias `ps`) is the **control plane health of every proxy**. It answers: did this Envoy ACK the latest config?

```bash
istioctl proxy-status
istioctl ps
istioctl proxy-status deploy/httpbin.demo
istioctl proxy-status --revision 1-26-0
```

Columns (names vary slightly by version):

| Column | xDS | STALE means |
| --- | --- | --- |
| CDS | clusters | DestinationRule / Service / ServiceEntry not pushed or not ACKed |
| LDS | listeners | Gateway / Sidecar ingress / inbound ports |
| EDS | endpoints | Endpoints / WorkloadEntry |
| RDS | routes | VirtualService |

`ISTIOD` / `VERSION` / `CLUSTER` columns tell you which control plane the proxy is attached to — critical during **canary upgrades** (`07.md`).

### States

| State | Meaning |
| --- | --- |
| `SYNCED` | ACK received, config matches |
| `STALE` | istiod sent an update, proxy has not ACKed (or NACK) |
| `NOT SENT` | istiod did not send this type (normal for some) |
| `NOT FOUND` / missing row | Proxy is not connected to istiod |

A missing row: pod has no sidecar, wrong revision label, CNI not injecting, or proxy cannot reach `istiod:15012`.

### What STALE is not

STALE does not mean "your YAML is wrong". Analyze is for YAML. STALE means **delivery**. Common causes:

- istiod overloaded or restarting
- Proxy cannot keep the xDS stream (NetworkPolicy, Sidecar that dropped `istio-system/*`)
- NACK: Envoy rejected config (bad EnvoyFilter, huge config)
- You looked during a push; wait 2 seconds and rerun

```bash
istioctl proxy-status
istioctl bug-report                    # too heavy for exam
kubectl -n istio-system logs deploy/istiod --tail=100
```

## Tasks

1. List all proxies and confirm every Bookinfo pod is `SYNCED`.
2. Identify which istiod revision `httpbin` is connected to.
3. Break xDS: apply a Sidecar in `demo` that omits `istio-system/*`, wait, show STALE or disconnect, then fix.
4. After a canary install of a second revision, show old and new proxies attached to different istiod pods.

## Solutions

### 1. Mesh dump

```bash
istioctl proxy-status | grep -E 'NAME|bookinfo'
istioctl proxy-status | awk '$2 != "SYNCED" && $3 != "SYNCED" {print}'
```

Read the header to know which column is which on **this** version.

### 2. One workload

```bash
istioctl proxy-status deploy/httpbin.demo
kubectl -n demo get pod -l app=httpbin -o jsonpath='{.items[0].metadata.labels}{"\n"}'
```

Look for `istio.io/rev` if revisions are in use.

### 3. Sidecar footgun

```yaml
apiVersion: networking.istio.io/v1
kind: Sidecar
metadata:
  name: broken
  namespace: demo
spec:
  workloadSelector:
    labels:
      app: httpbin
  egress:
    - hosts:
        - "demo/*"
```

Restart or wait. `proxy-status` for httpbin goes bad. Fix by adding `istio-system/*` or deleting the Sidecar.

### 4. Canary

If you have `istiod-1-26-0` and `istiod-1-27-0`:

```bash
istioctl proxy-status | grep httpbin
kubectl -n istio-system get pod -l app=istiod --show-labels
```

The ISTIOD column should match the namespace revision label.

## Verify

```bash
istioctl version
istioctl proxy-status
kubectl -n istio-system get endpoints istiod
```

All proxies should list. Zero proxies = you ran the command against a cluster without a mesh, or kubeconfig context is wrong.

## Exam Tips

- **First command on a troubleshooting task:** `istioctl proxy-status`. Then `analyze`. Then `proxy-config`.
- Filter: `istioctl ps | grep STALE`.
- `kubectl get pod -n istio-system` if **every** proxy is missing: istiod is down.
- Docs: [proxy-status](https://istio.io/docs/ops/diagnostic-tools/proxy-cmd/).
