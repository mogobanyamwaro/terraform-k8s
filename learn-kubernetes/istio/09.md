# 09. VirtualService Fundamentals

## Concept Refresher

The VirtualService answers one question: **where does this request go?** Everything about destination selection lives here. How you then talk to that destination lives in the DestinationRule, which is `11.md`.

### The shape

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
  namespace: bookinfo
spec:
  hosts:            # which destinations this applies to
    - reviews
  gateways:         # where the traffic comes from; defaults to [mesh]
    - mesh
  http:             # ordered list of routing rules
    - match: [...]  # optional conditions
      route: [...]  # where to send it
  tcp: [...]        # for TCP traffic
  tls: [...]        # for TLS passthrough by SNI
  exportTo: ["."]   # visibility scope
```

### `hosts` is the trigger, not the destination

This is the concept people get wrong most often. `spec.hosts` says **"when a client tries to reach this address, apply these rules"**. It does not say where traffic ends up. The destination is `http[].route[].destination.host`.

```yaml
spec:
  hosts:
    - reviews          # intercept traffic addressed to "reviews"
  http:
    - route:
        - destination:
            host: reviews-canary   # send it somewhere else entirely
```

That is a perfectly valid VirtualService that transparently redirects `reviews` to `reviews-canary`.

Host names resolve like Kubernetes DNS, relative to the VirtualService's namespace:

| In `hosts` | Resolves to |
| --- | --- |
| `reviews` | `reviews.<vs-namespace>.svc.cluster.local` |
| `reviews.bookinfo` | `reviews.bookinfo.svc.cluster.local` |
| `reviews.bookinfo.svc.cluster.local` | itself |
| `reviews.example.com` | an external host, needs a ServiceEntry |
| `*` | any host, only meaningful with a gateway |

**Use the fully qualified name when a VirtualService and its target Service are in different namespaces.** A short name silently resolves in the wrong namespace, producing a route to a service that does not exist.

### Rules are ordered, first match wins

```yaml
  http:
    - match:                        # rule 1: checked first
        - headers:
            end-user:
              exact: jason
      route:
        - destination:
            host: reviews
            subset: v2
    - route:                        # rule 2: catch-all, checked last
        - destination:
            host: reviews
            subset: v1
```

Evaluation stops at the first rule whose `match` succeeds. A rule with **no `match` matches everything**, so it must go last. Put a catch-all first and everything below it is unreachable dead configuration, with no error and no warning.

The last rule should almost always be an unconditional catch-all. Without one, requests matching nothing get `404`.

### Match is OR across entries, AND within one

```yaml
      match:
        - uri:
            prefix: /api           # entry 1
          headers:
            x-version:
              exact: v2            # AND within entry 1
        - uri:
            prefix: /v2            # entry 2, OR with entry 1
```

Each list item is a separate condition set; conditions inside one item must all hold. This is a frequently tested subtlety, so read it as: **list items are alternatives, fields within an item are requirements.**

### Route actions

Exactly one of these per rule:

| Action | Purpose |
| --- | --- |
| `route` | Send to one or more destinations, optionally weighted |
| `redirect` | Return a 3xx to the client |
| `directResponse` | Return a fixed status and body without contacting any upstream |
| `delegate` | Hand off to another VirtualService |

And these modifiers can accompany a `route`:

| Modifier | Purpose |
| --- | --- |
| `rewrite` | Change the URI or `Host` before forwarding |
| `timeout` | Give up after a duration |
| `retries` | Retry policy |
| `fault` | Inject a delay or an abort |
| `mirror` / `mirrors` | Shadow a copy of the traffic |
| `headers` | Add, set, or remove request and response headers |
| `corsPolicy` | CORS handling |

### `exportTo`

Controls which namespaces can see this VirtualService.

```yaml
  exportTo:
    - "."        # this namespace only
    - "*"        # all namespaces (the default)
    - "shop"     # a specific namespace
```

Useful for keeping a namespace's internal routing from affecting the rest of the mesh.

## Tasks

Use the `bookinfo` namespace with `destination-rule-all.yaml` applied, plus `demo` with `httpbin` and `sleep`.

1. Route all `reviews` traffic to subset `v1`. Verify by refreshing the product page.
2. Send requests carrying header `end-user: jason` to `reviews` v2, and everyone else to v1.
3. Route requests with prefix `/status` on `httpbin` to a fixed 418 response without contacting the service.
4. Redirect `/legacy` to `/get` with a 301.
5. Rewrite the URI so that requests to `/api/v1/get` reach `httpbin` at `/get`.
6. Add a request header `x-mesh: istio` on the way to `httpbin`, and a response header `x-served-by: mesh` on the way back.
7. Create a VirtualService in `demo` that routes to a service in `bookinfo`.
8. Demonstrate the ordering trap: write a VirtualService where the second rule is unreachable, prove it, then fix it.
9. Make a VirtualService visible only within its own namespace.
10. Use `delegate` to split routing across two VirtualService resources.
11. Configure a CORS policy on `httpbin` allowing only `https://app.example.com`.
12. Two VirtualServices both claim the host `reviews`. Determine what happens and fix it.

## Solutions

### 1. All traffic to one subset

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
  namespace: bookinfo
spec:
  hosts:
    - reviews
  http:
    - route:
        - destination:
            host: reviews
            subset: v1
EOF
```

Verify. Refresh the product page several times and the star ratings never appear, because v1 has no ratings:

```bash
for i in $(seq 1 10); do
  curl -s "http://localhost/productpage" | grep -o 'reviews-v[0-9]' | head -1
done
```

The authoritative check is the Envoy route on the caller's sidecar:

```bash
istioctl proxy-config route deploy/productpage-v1.bookinfo \
  --name 9080 -o json \
  | jq '.[].virtualHosts[] | select(.name|test("reviews")) | .routes[].route.cluster'
```

```text
"outbound|9080|v1|reviews.bookinfo.svc.cluster.local"
```

The `v1` in the cluster name is the proof. Note there is no `gateways` field, so it defaults to `mesh` and applies to all sidecars, which is what east-west routing needs.

**This only works because a DestinationRule defines subset `v1`.** Remove it and you get 503s:

```bash
kubectl -n bookinfo delete destinationrule reviews
curl -s -o /dev/null -w "%{http_code}\n" http://localhost/productpage
istioctl proxy-config cluster deploy/productpage-v1.bookinfo --fqdn reviews.bookinfo.svc.cluster.local
# no subset clusters

kubectl -n bookinfo apply -f ~/istio-1.26.0/samples/bookinfo/networking/destination-rule-all.yaml
```

### 2. Header-based routing with a fallback

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
  namespace: bookinfo
spec:
  hosts:
    - reviews
  http:
    - match:
        - headers:
            end-user:
              exact: jason
      route:
        - destination:
            host: reviews
            subset: v2
    - route:
        - destination:
            host: reviews
            subset: v1
EOF
```

Verify with the Bookinfo login. Logging in as `jason` in the browser sends the `end-user` header and black stars appear. From the command line:

```bash
kubectl -n bookinfo exec deploy/ratings-v1 -c ratings -- \
  curl -sS -H "end-user: jason" http://reviews:9080/reviews/0 | jq -r '.reviews[0].rating // "no rating"'

kubectl -n bookinfo exec deploy/ratings-v1 -c ratings -- \
  curl -sS http://reviews:9080/reviews/0 | jq -r '.reviews[0].rating // "no rating"'
```

The first shows a rating (v2), the second does not (v1).

Both routes on the sidecar:

```bash
istioctl proxy-config route deploy/productpage-v1.bookinfo --name 9080 -o json \
  | jq '.[].virtualHosts[] | select(.name|test("reviews"))
        | .routes[] | {match: .match, cluster: .route.cluster}'
```

```json
{"match": {"prefix": "/", "headers": [{"name": "end-user", "stringMatch": {"exact": "jason"}}]},
 "cluster": "outbound|9080|v2|reviews.bookinfo.svc.cluster.local"}
{"match": {"prefix": "/"},
 "cluster": "outbound|9080|v1|reviews.bookinfo.svc.cluster.local"}
```

Order is preserved from your YAML, and the specific rule is first. That is what makes it work.

### 3. Direct response

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - uri:
            prefix: /status
      directResponse:
        status: 418
        body:
          string: "I am a teapot, handled by Envoy\n"
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
EOF
```

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -w "\ncode: %{http_code}\n" http://httpbin:8000/status/200
```

```text
I am a teapot, handled by Envoy
code: 418
```

The request never reaches `httpbin`. Envoy answers it. Prove that by watching the application's access log:

```bash
kubectl -n demo logs deploy/httpbin -c istio-proxy --tail=5
# nothing new for /status
```

`directResponse` is genuinely useful for maintenance pages, for blocking a path, and for health endpoints that must answer even when the backend is down. Note the mutual exclusivity: a rule has `route`, `redirect`, `directResponse`, or `delegate`, never two.

### 4. Redirect

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - uri:
            prefix: /legacy
      redirect:
        uri: /get
        redirectCode: 301
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
EOF
```

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{http_code} -> %{redirect_url}\n" http://httpbin:8000/legacy

# Follow it
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sSL -o /dev/null -w "final: %{http_code}\n" http://httpbin:8000/legacy
```

```text
301 -> http://httpbin:8000/get
final: 200
```

`redirectCode` defaults to `301`. Other fields:

```yaml
      redirect:
        uri: /new              # replace the path
        authority: new.example.com   # replace the Host
        scheme: https
        port: 443
        redirectCode: 302
```

`uri` replaces the whole path. To keep the rest of the path, use `rewrite` instead, or `redirect` with a prefix rewrite semantics as in task 5.

### 5. URI rewrite

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - uri:
            prefix: /api/v1
      rewrite:
        uri: /
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
EOF
```

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{http_code}\n" http://httpbin:8000/api/v1/get
# 200
```

Prove the rewrite by asking httpbin what path it saw:

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS http://httpbin:8000/api/v1/headers | jq -r '.headers["X-Envoy-Original-Path"] // "not set"'
```

The rewrite semantics with a `prefix` match: the matched prefix is **replaced** by the `rewrite.uri`. So `/api/v1` + `/get` becomes `/` + `get` = `/get`. Get this wrong and you end up with `//get` or `/get` doubled, which produces a `404` from the application rather than from Envoy, and that distinction is the debugging clue.

Rewriting the `Host` header, which is needed when routing to an external service that validates it:

```yaml
      rewrite:
        uri: /
        authority: httpbin.org
```

### 6. Header manipulation

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        request:
          set:
            x-mesh: istio
          add:
            x-extra: appended
          remove:
            - user-agent
        response:
          add:
            x-served-by: mesh
          remove:
            - server
EOF
```

Verify the request headers, echoed by httpbin:

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS http://httpbin:8000/headers | jq '.headers | {"X-Mesh", "X-Extra", "User-Agent"}'
```

```json
{"X-Mesh": "istio", "X-Extra": "appended", "User-Agent": null}
```

And the response headers:

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -D- -o /dev/null http://httpbin:8000/get | grep -iE 'x-served-by|server'
```

`set` versus `add` is the distinction to remember:

| Operation | Behaviour |
| --- | --- |
| `set` | Replace the header, discarding any existing value |
| `add` | Append; if the header exists you get multiple values |
| `remove` | Delete, takes a list of names |

Headers can also be set per destination, which is how you tag traffic by version:

```yaml
      route:
        - destination:
            host: httpbin
            subset: v1
          headers:
            request:
              set:
                x-version: v1
          weight: 50
```

### 7. Cross-namespace routing

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: remote-reviews
  namespace: demo
spec:
  hosts:
    - reviews.bookinfo.svc.cluster.local
  http:
    - route:
        - destination:
            host: reviews.bookinfo.svc.cluster.local
            subset: v2
            port:
              number: 9080
EOF
```

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS http://reviews.bookinfo:9080/reviews/0 | jq -r '.reviews[0].rating.stars // "none"'
```

Two things are essential here:

- **Fully qualified host names.** Writing `reviews` in a VirtualService in `demo` resolves to `reviews.demo.svc.cluster.local`, which does not exist. There is no error; traffic just does not route as intended.
- **The subset must be defined by a DestinationRule that is visible.** The DestinationRule in `bookinfo` is exported to all namespaces by default, so `subset: v2` resolves. If it had `exportTo: ["."]`, this would fail with a 503.

Check visibility:

```bash
kubectl -n bookinfo get destinationrule reviews -o jsonpath='{.spec.exportTo}{"\n"}'
istioctl proxy-config cluster deploy/sleep.demo --fqdn reviews.bookinfo.svc.cluster.local
```

### 8. The ordering trap

The broken version:

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - route:                          # catch-all FIRST - wrong
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-rule: catch-all
    - match:                          # never reached
        - uri:
            prefix: /status
      directResponse:
        status: 418
EOF
```

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -D- -o /dev/null http://httpbin:8000/status/200 | grep -iE 'HTTP/|x-rule'
```

```text
HTTP/1.1 200 OK
x-rule: catch-all
```

The 418 rule never fires. Envoy shows only one usable route:

```bash
istioctl proxy-config route deploy/sleep.demo --name 8000 -o json \
  | jq '.[].virtualHosts[] | select(.name|test("httpbin")) | [.routes[].match]'
```

The first route matches `prefix: /`, which matches everything, so evaluation always stops there.

The fix is simply to reverse the order:

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - uri:
            prefix: /status
      directResponse:
        status: 418
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-rule: catch-all
EOF

kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "/status: %{http_code}\n" http://httpbin:8000/status/200
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "/get:    %{http_code}\n" http://httpbin:8000/get
```

```text
/status: 418
/get:    200
```

Note that `istioctl analyze` does **not** flag this. Unreachable routes are valid configuration. Ordering is on you, which is exactly why it makes a good exam trap: nothing tells you it is wrong except the behaviour.

### 9. Namespace-scoped visibility

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  exportTo:
    - "."
  http:
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-private: "true"
EOF
```

In-namespace clients see the rules:

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -D- -o /dev/null http://httpbin:8000/get | grep -i x-private
# x-private: true
```

Out-of-namespace clients do not:

```bash
kubectl -n bookinfo exec deploy/ratings-v1 -c ratings -- \
  curl -sS -D- -o /dev/null http://httpbin.demo:8000/get | grep -i x-private
# nothing
```

Traffic still reaches `httpbin` because the Kubernetes Service is still there; the VirtualService rules just are not applied for that caller. That distinction matters: `exportTo` controls **rule visibility**, not reachability. To control reachability you need an `AuthorizationPolicy` or a `Sidecar` resource.

Confirm from the config:

```bash
istioctl proxy-config route deploy/ratings-v1.bookinfo -o json \
  | jq '.[].virtualHosts[]? | select(.name|test("httpbin"))'
```

### 10. Delegation

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: root
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - uri:
            prefix: /api
      delegate:
        name: api-routes
        namespace: demo
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: api-routes
  namespace: demo
spec:
  # NOTE: no hosts, and no gateways. A delegate must not set them.
  http:
    - match:
        - uri:
            prefix: /api/get
      rewrite:
        uri: /get
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
    - match:
        - uri:
            prefix: /api/headers
      rewrite:
        uri: /headers
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
EOF
```

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "/api/get:     %{http_code}\n" http://httpbin:8000/api/get
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "/api/headers: %{http_code}\n" http://httpbin:8000/api/headers
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "/get:         %{http_code}\n" http://httpbin:8000/get
```

The rules for delegation, all of which are easy to get wrong:

- The delegate VirtualService must **not** specify `hosts`.
- The delegate must **not** specify `gateways`.
- Only one level of delegation is allowed; a delegate cannot delegate again.
- A delegating rule can only use `delegate`, not `route` alongside it.
- The delegate's `match` conditions must be **a subset of** the parent's, or they never fire.

Delegation exists so that a platform team can own the root VirtualService with its gateway binding and host, while application teams own their own path trees without being able to hijack the host. That rationale is worth being able to state.

### 11. CORS

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      corsPolicy:
        allowOrigins:
          - exact: https://app.example.com
        allowMethods:
          - GET
          - POST
        allowHeaders:
          - authorization
          - content-type
        exposeHeaders:
          - x-request-id
        maxAge: 24h
        allowCredentials: true
EOF
```

Verify a preflight from the allowed origin:

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -D- -o /dev/null -X OPTIONS \
  -H "Origin: https://app.example.com" \
  -H "Access-Control-Request-Method: GET" \
  http://httpbin:8000/get | grep -i access-control
```

```text
access-control-allow-origin: https://app.example.com
access-control-allow-methods: GET,POST
access-control-allow-headers: authorization,content-type
access-control-max-age: 86400
access-control-allow-credentials: true
```

And from a disallowed origin:

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -D- -o /dev/null -X OPTIONS \
  -H "Origin: https://evil.example.com" \
  -H "Access-Control-Request-Method: GET" \
  http://httpbin:8000/get | grep -i access-control-allow-origin || echo "no CORS headers"
```

Origin matching supports `exact`, `prefix`, and `regex`:

```yaml
        allowOrigins:
          - exact: https://app.example.com
          - prefix: https://staging-
          - regex: "https://.*\\.example\\.com"
```

An important caveat: **CORS is advisory.** Envoy adds the headers and answers preflights, but a non-browser client that ignores CORS headers still gets through. CORS is not a security control. If a task wants actual enforcement, that is an `AuthorizationPolicy`.

### 12. Two VirtualServices claiming one host

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: vs-one
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-from: vs-one
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: vs-two
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-from: vs-two
EOF
```

Detect it:

```bash
istioctl analyze -n demo
```

```text
Warning [IST0108] (VirtualService vs-two.demo) The VirtualServices vs-one, vs-two associated with
  mesh gateway define the same host httpbin which can lead to undefined behavior.
```

What actually happens:

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -D- -o /dev/null http://httpbin:8000/get | grep -i x-from
```

Istio **merges** them when the rules do not conflict, and when they do conflict the older resource wins by creation timestamp. That is not something to build on. Confirm what Envoy ended up with:

```bash
istioctl proxy-config route deploy/sleep.demo --name 8000 -o json \
  | jq '.[].virtualHosts[] | select(.name|test("httpbin")) | .routes | length'
```

The fix is to have exactly one VirtualService per host, with all rules in order:

```bash
kubectl -n demo delete virtualservice vs-two

kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: vs-one
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - uri:
            prefix: /special
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-from: special
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-from: default
EOF

istioctl analyze -n demo
```

The one legitimate exception is splitting by gateway: two VirtualServices can share a host if one binds to `mesh` and the other to a specific gateway, because they apply to disjoint sets of proxies. Even then, one resource with both gateways listed is clearer.

## Exam Tips

**`spec.hosts` is what you intercept, `route.destination.host` is where it goes.** Say it to yourself before writing any VirtualService. Confusing the two produces resources that look right and do nothing.

**Order your rules specific-first, catch-all-last.** First match wins, and a rule with no `match` matches everything. `istioctl analyze` will not warn you about an unreachable rule, so this is entirely on your discipline.

**Always end with an unconditional catch-all** unless the task genuinely wants unmatched requests to 404.

**Match semantics: list entries are OR, fields within an entry are AND.** Expect a task that hinges on this.

**Use fully qualified host names across namespaces.** `reviews.bookinfo.svc.cluster.local`, not `reviews`. A short name resolves in the VirtualService's own namespace and fails silently.

**A `subset` reference requires a DestinationRule.** If a task asks you to route to `v1`, check whether the DestinationRule exists. If not, creating it is part of the answer. Missing subsets are the number one cause of 503 in Istio.

**One VirtualService per host.** Two claiming the same host gets you `IST0108` and merge behaviour you should not depend on.

**`istioctl proxy-config route <workload> --name <port> -o json` is the verification command.** It shows the routes in evaluation order with the resolved cluster names. When behaviour and YAML disagree, this tells you which one Envoy believes.

**`route`, `redirect`, `directResponse`, and `delegate` are mutually exclusive per rule.** Combining them is a validation error, which at least fails loudly.

**Delegate VirtualServices must omit `hosts` and `gateways`**, and their matches must be a subset of the parent's. One level only.

**`exportTo` limits rule visibility, not reachability.** A task asking to "prevent other namespaces from reaching this service" wants an `AuthorizationPolicy` or a `Sidecar`, not `exportTo`.
