# 13. Traffic Mirroring (Shadowing)

## Concept Refresher

Mirroring **copies** a request to a second destination and discards that copy's response. The original request still goes to the primary destination, and **the client sees only the primary response**.

Use it to soak a new version with production traffic without affecting users.

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - route:
        - destination:
            host: httpbin
            subset: v1
      mirror:
        host: httpbin
        subset: v2
      mirrorPercentage:
        value: 100.0
```

### Behaviour that surprises people

- The mirrored request is fire-and-forget. Failures, slowness, and 5xx on the mirror **do not** change the client response.
- Envoy rewrites the `Host` / `:authority` header to the **mirrored** service. The shadow workload must accept that host. If you mirror to a different Service, that Service sees its own hostname, not the original.
- `mirrorPercentage.value` is 0-100. Omit it and Istio mirrors **100%**.
- You can combine weight-based routing and mirroring: 90/10 split on the primary route, plus a 10% mirror to a third subset.
- Mirroring is HTTP only. There is no TCP mirror field on the VirtualService.
- In ambient mode, mirroring is L7. It does nothing without a waypoint in the path.

### Mirroring vs shifting

| | Shifting (`weight`) | Mirroring (`mirror`) |
| --- | --- | --- |
| Client sees | The chosen subset's response | Always the primary route's response |
| Shadow load | N/A | Extra copies of requests |
| Good for | Canary that users hit | Soak test, dark launch |
| Failure of new version | Users feel it | Users do not |

## Tasks

Namespace `demo` has `httpbin` with two versions labelled `version=v1` and `version=v2`, a DestinationRule with those subsets, and `sleep` as the client.

1. Send all traffic to `v1`. Mirror **100%** to `v2`.
2. Keep primary on `v1`. Mirror only **10%** to `v2`.
3. Mirror only requests whose path starts with `/status` to `v2`. Other paths go to `v1` with no mirror.
4. Prove that a 500 from the mirror does not reach the client.

## Solutions

Prerequisite subsets:

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: httpbin
  namespace: demo
spec:
  host: httpbin
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
EOF
```

If you only have one httpbin Deployment, clone it:

```bash
kubectl -n demo get deploy httpbin -o yaml \
  | sed 's/name: httpbin/name: httpbin-v2/' \
  | sed 's/version: v1/version: v2/' \
  | kubectl apply -f -
# Keep the Service selector on app=httpbin so both versions are endpoints.
```

### 1. Full mirror

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - route:
        - destination:
            host: httpbin
            subset: v1
      mirror:
        host: httpbin
        subset: v2
      mirrorPercentage:
        value: 100.0
```

### 2. Partial mirror

Same YAML, `value: 10.0`.

### 3. Path-scoped mirror

```yaml
  http:
    - match:
        - uri:
            prefix: /status
      route:
        - destination:
            host: httpbin
            subset: v1
      mirror:
        host: httpbin
        subset: v2
      mirrorPercentage:
        value: 100.0
    - route:
        - destination:
            host: httpbin
            subset: v1
```

### 4. Mirror failures are silent to the client

Generate a 500 on v2 only (fault injection on that subset, `20.md`), then:

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{http_code}\n" http://httpbin:8000/get
```

You still get `200` from v1. Access logs on the v2 sidecar show the extra request.

## Verify

```bash
# Access logs: v1 and v2 should both see the request
kubectl -n demo logs deploy/httpbin -c istio-proxy --tail=20
kubectl -n demo logs deploy/httpbin-v2 -c istio-proxy --tail=20

# Route dump shows a requestMirrorPolicy
istioctl proxy-config route deploy/sleep.demo --name 8000 -o json \
  | jq '.. | .requestMirrorPolicy? // empty'
```

Watch logs in two terminals, then send one curl from sleep. One request in, two access-log lines.

## Exam Tips

- Field name is `mirror`, percentage is **`mirrorPercentage.value`** as a float. `mirror_percent` is the old deprecated name. Use the current one from the docs.
- If v2 logs are empty, the subset has no endpoints or the VS is not attached to the client proxy. Check `istioctl proxy-config endpoint deploy/sleep.demo --cluster "outbound|8000|v2|httpbin.demo.svc.cluster.local"`.
- Mirroring doubles load on shared dependencies (databases). That is a design warning, not an exam trick, but if a task says "do not affect the user-facing response", mirroring is the answer, not shifting.
- Docs: [Mirroring](https://istio.io/docs/tasks/traffic-management/mirroring/).
