# 08. Ingress Gateways and the Gateway Resource

## Concept Refresher

Getting traffic **into** the mesh takes two resources working together, and understanding the division of labour is the whole topic.

```text
   External client
        |
        v
  +-------------------------+
  | istio-ingressgateway    |  <- a Deployment + Service (an Envoy)
  |  the WORKLOAD           |
  +-------------------------+
        ^
        |  configured by
        |
  +-------------------------+
  | Gateway resource        |  <- WHICH ports, protocols, hostnames to accept
  |  "open the door"        |
  +-------------------------+
        +
  +-------------------------+
  | VirtualService          |  <- WHERE accepted requests go
  |  "route the request"    |
  +-------------------------+
```

**A Gateway on its own does nothing but open a port.** It accepts connections and then has nowhere to send them, so requests get `404`. You always need a VirtualService bound to it. That pairing is the most common source of "my gateway returns 404" and is worth internalising immediately.

### The Gateway resource

```yaml
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: shop-gateway
  namespace: shop
spec:
  selector:
    istio: ingressgateway        # matches the gateway POD's labels
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "shop.example.com"
```

Three parts, each with a trap:

**`selector`** matches labels on the gateway **pod**, not on a Service or namespace. The default install labels the ingress gateway pod `istio=ingressgateway`. Verify rather than assume:

```bash
kubectl -n istio-system get pod -l istio=ingressgateway
kubectl -n istio-system get deploy istio-ingressgateway -o jsonpath='{.spec.template.metadata.labels}' | jq
```

**`port.name`** must be prefixed with the protocol for Istio to infer handling. Valid prefixes: `http`, `http2`, `https`, `grpc`, `tcp`, `tls`, `mongo`, `redis`, `mysql`. A port named `foo` on an HTTP service will be treated as opaque TCP, and all your HTTP routing silently stops working. This is a classic silent failure.

**`hosts`** is a filter. Only requests whose `Host` header matches are accepted. `"*"` accepts anything.

### Binding a VirtualService to a Gateway

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: shop
  namespace: shop
spec:
  hosts:
    - "shop.example.com"       # MUST intersect the Gateway's hosts
  gateways:
    - shop-gateway             # the Gateway to attach to
  http:
    - route:
        - destination:
            host: frontend
            port:
              number: 80
```

Two rules govern the binding:

1. **`spec.gateways` must name the Gateway.** Omit it and the VirtualService defaults to `gateways: [mesh]`, meaning east-west only, and ingress traffic ignores it.
2. **`spec.hosts` must intersect the Gateway's `hosts`.** If the Gateway accepts `shop.example.com` and the VirtualService declares `api.example.com`, there is no overlap and the route never attaches.

To handle both ingress and in-mesh traffic with one VirtualService:

```yaml
  gateways:
    - mesh              # the reserved name for all sidecars
    - shop-gateway
```

### Cross-namespace references

A VirtualService in namespace `shop` referring to a Gateway in `istio-system` must qualify it:

```yaml
  gateways:
    - istio-system/shop-gateway
```

The format is `<namespace>/<gateway-name>`. Unqualified names resolve in the VirtualService's own namespace. Forgetting the prefix when the Gateway lives with the gateway deployment is extremely common.

### Where should the Gateway resource live?

Both work, and the choice has consequences:

| Placement | Pros | Cons |
| --- | --- | --- |
| Same namespace as the app | App team owns its routing, no cross-namespace refs | Multiple Gateways may conflict on the same port/host |
| `istio-system` with the gateway pod | Central control | VirtualServices need `istio-system/` prefixes |

Same-namespace-as-the-app is the pattern the Istio docs increasingly favour, and it is what the Bookinfo sample does.

## Solutions

### 1. Basic HTTP exposure

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: httpbin-gateway
  namespace: demo
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "httpbin.example.com"
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - "httpbin.example.com"
  gateways:
    - httpbin-gateway
  http:
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
EOF
```

Verify. The `Host` header is what the Gateway matches on, so you must send it:

```bash
curl -sS -o /dev/null -w "%{http_code}\n" -H "Host: httpbin.example.com" http://localhost/get
# 200
```

Without the header, the Gateway rejects it:

```bash
curl -sS -o /dev/null -w "%{http_code}\n" http://localhost/get
# 404
```

That `404` is not a bug. The gateway has no listener configured for the host `localhost`, so there is no route. Understanding this distinction saves a lot of confused debugging.

Using the resolve trick, which is closer to how a real client behaves:

```bash
curl -sS -o /dev/null -w "%{http_code}\n" \
  --resolve httpbin.example.com:80:127.0.0.1 \
  http://httpbin.example.com/get
```

Confirm the gateway actually got the config:

```bash
istioctl proxy-config route deploy/istio-ingressgateway.istio-system
```

```text
NAME     VHOST NAME                      DOMAINS                  MATCH   VIRTUAL SERVICE
http.80  httpbin.example.com:80          httpbin.example.com      /*      httpbin.demo
```

That single line proves everything: the listener exists on port 80, the vhost matches the domain, and the route resolves to your VirtualService.

### 2. Path-based routing on any host

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: api-gateway
  namespace: demo
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "*"
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: api
  namespace: demo
spec:
  hosts:
    - "*"
  gateways:
    - api-gateway
  http:
    - match:
        - uri:
            prefix: /api
      rewrite:
        uri: /
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
EOF
```

```bash
curl -sS -o /dev/null -w "%{http_code}\n" http://localhost/api/get
# 200

curl -sS -o /dev/null -w "%{http_code}\n" http://localhost/other
# 404 - no matching route
```

The `rewrite` matters: without it, `httpbin` receives `/api/get`, which it does not serve, and you get a `404` from the application rather than the gateway. Prove the rewrite happened:

```bash
curl -sS -H "Host: anything" http://localhost/api/headers | head -20
```

Note that `hosts: ["*"]` on a Gateway plus `hosts: ["*"]` on a VirtualService is a wildcard catch-all. It is convenient in a lab and a bad idea in production, where it collides with every other Gateway on port 80.

### 3. Two hosts on one gateway

```bash
kubectl -n demo apply -f ~/istio-1.26.0/samples/sleep/sleep.yaml 2>/dev/null

kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: multi-gateway
  namespace: demo
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "httpbin.example.com"
        - "admin.example.com"
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin-vs
  namespace: demo
spec:
  hosts:
    - "httpbin.example.com"
  gateways:
    - multi-gateway
  http:
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: admin-vs
  namespace: demo
spec:
  hosts:
    - "admin.example.com"
  gateways:
    - multi-gateway
  http:
    - route:
        - destination:
            host: httpbin      # pretend this is a different service
            port:
              number: 8000
      headers:
        response:
          add:
            x-served-by: admin
EOF
```

```bash
curl -sS -o /dev/null -w "%{http_code}\n" -H "Host: httpbin.example.com" http://localhost/get
curl -sS -D- -o /dev/null -H "Host: admin.example.com" http://localhost/get | grep -i x-served-by
```

One Gateway can carry many hosts, and each gets its own VirtualService. Alternatively, one Gateway server block per host lets you give each host different TLS settings, which is what you need in `27.md`.

Inspect both vhosts:

```bash
istioctl proxy-config route deploy/istio-ingressgateway.istio-system --name http.80
```

### 4. Non-standard port

Two changes are needed, and forgetting the second is the trap. The Gateway must declare the port **and** the gateway Service must actually expose it.

```bash
# Add the port to the gateway Service
kubectl -n istio-system patch svc istio-ingressgateway --type=json -p='[
  {"op":"add","path":"/spec/ports/-","value":{"name":"http-8080","port":8080,"targetPort":8080,"nodePort":30880,"protocol":"TCP"}}
]'

kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: port8080-gateway
  namespace: demo
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 8080
        name: http-8080
        protocol: HTTP
      hosts:
        - "*"
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: port8080-vs
  namespace: demo
spec:
  hosts:
    - "*"
  gateways:
    - port8080-gateway
  http:
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
EOF
```

Verify the listener exists on the gateway:

```bash
istioctl proxy-config listener deploy/istio-ingressgateway.istio-system --port 8080
```

```text
ADDRESS   PORT   MATCH   DESTINATION
0.0.0.0   8080   ALL     Route: http.8080
```

Then reach it:

```bash
kubectl -n istio-system port-forward svc/istio-ingressgateway 8080:8080 &
curl -sS -o /dev/null -w "%{http_code}\n" http://localhost:8080/get
kill %1
```

**Envoy in the gateway binds the port the Gateway resource declares.** If the Kubernetes Service does not forward to it, external traffic never arrives, even though `proxy-config listener` shows the listener happily. Checking both halves is the lesson.

### 5. Gateway in istio-system, VirtualService in demo

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: shared-gateway
  namespace: istio-system
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "*.example.com"
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin-shared
  namespace: demo
spec:
  hosts:
    - "httpbin.example.com"
  gateways:
    - istio-system/shared-gateway     # namespace-qualified
  http:
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
EOF
```

```bash
curl -sS -o /dev/null -w "%{http_code}\n" -H "Host: httpbin.example.com" http://localhost/get
```

Note two things. The Gateway's `hosts` uses the wildcard `*.example.com`, and the VirtualService's specific `httpbin.example.com` falls inside it, so they intersect. And the reference is `istio-system/shared-gateway`.

Drop the namespace prefix and it breaks:

```bash
kubectl -n demo patch virtualservice httpbin-shared --type=json \
  -p='[{"op":"replace","path":"/spec/gateways/0","value":"shared-gateway"}]'

curl -sS -o /dev/null -w "%{http_code}\n" -H "Host: httpbin.example.com" http://localhost/get
# 404

istioctl analyze -n demo
```

```text
Error [IST0101] (VirtualService httpbin-shared.demo) Referenced gateway not found: "shared-gateway"
```

`istioctl analyze` names it directly. Put it back:

```bash
kubectl -n demo patch virtualservice httpbin-shared --type=json \
  -p='[{"op":"replace","path":"/spec/gateways/0","value":"istio-system/shared-gateway"}]'
```

### 6. Raw TCP through the gateway

```bash
kubectl -n istio-system patch svc istio-ingressgateway --type=json -p='[
  {"op":"add","path":"/spec/ports/-","value":{"name":"tcp-3306","port":3306,"targetPort":3306,"protocol":"TCP"}}
]'

kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: tcp-gateway
  namespace: demo
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 3306
        name: tcp-mysql
        protocol: TCP
      hosts:
        - "*"
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: tcp-vs
  namespace: demo
spec:
  hosts:
    - "*"
  gateways:
    - tcp-gateway
  tcp:
    - match:
        - port: 3306
      route:
        - destination:
            host: mysql
            port:
              number: 3306
EOF
```

Three differences from the HTTP case, all of them examinable:

- `protocol: TCP` on the Gateway server.
- **`tcp:` instead of `http:`** in the VirtualService.
- **A `match` on `port` is required**, because there are no hosts or paths to match on. TCP has no `Host` header, so `hosts: ["*"]` is the only sensible value and port is the only discriminator.

TCP routing loses everything L7: no path matching, no header manipulation, no retries, no HTTP metrics. You keep mTLS, load balancing, and L4 authorization.

```bash
istioctl proxy-config listener deploy/istio-ingressgateway.istio-system --port 3306
```

### 7. HTTP to HTTPS redirect

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: tls-gateway
  namespace: demo
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "httpbin.example.com"
      tls:
        httpsRedirect: true       # <- 301 everything to https
    - port:
        number: 443
        name: https
        protocol: HTTPS
      hosts:
        - "httpbin.example.com"
      tls:
        mode: SIMPLE
        credentialName: httpbin-tls
EOF
```

```bash
curl -sS -o /dev/null -w "%{http_code} -> %{redirect_url}\n" \
  -H "Host: httpbin.example.com" http://localhost/get
# 301 -> https://httpbin.example.com/get
```

`tls.httpsRedirect: true` on the **HTTP** server block is the idiom. It is a slightly odd place for it, since the block has no TLS otherwise, but that is where it lives. Creating the certificate secret is `27.md`.

The alternative, redirecting from a VirtualService, gives you finer control:

```yaml
  http:
    - match:
        - uri:
            prefix: /old
      redirect:
        uri: /new
        authority: newhost.example.com
        redirectCode: 301
```

### 8. One VirtualService for ingress and mesh

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin-both
  namespace: demo
spec:
  hosts:
    - "httpbin.example.com"        # for external clients
    - httpbin                      # for in-mesh clients (short name)
  gateways:
    - mesh                         # all sidecars
    - httpbin-gateway              # the ingress gateway
  http:
    - match:
        - uri:
            prefix: /status
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-route: default
EOF
```

```bash
# External
curl -sS -D- -o /dev/null -H "Host: httpbin.example.com" http://localhost/get | grep -i x-route

# In-mesh
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -D- -o /dev/null http://httpbin:8000/get | grep -i x-route
```

Both hit the same rules. The essentials:

- **`mesh` is a reserved gateway name** meaning every sidecar. It is the implicit default when `gateways` is omitted.
- The `hosts` list needs an entry for each way the service is addressed: the external FQDN for gateway traffic and the Kubernetes name for in-mesh traffic.
- Once you list `gateways` explicitly, you must include `mesh` if you still want in-mesh traffic. Adding a gateway name and forgetting `mesh` silently removes the east-west routing you previously had. That is a real regression pattern.

### 9. Gateway returns 404: full checklist

Work down this list; it is ordered by how often each cause occurs.

```bash
# 1. Is the Host header right? Most common by a wide margin.
curl -sS -o /dev/null -w "%{http_code}\n" -H "Host: httpbin.example.com" http://localhost/get
```

```bash
# 2. Does the VirtualService bind to the Gateway?
kubectl -n demo get virtualservice httpbin -o jsonpath='{.spec.gateways}{"\n"}'
# empty or missing => defaults to "mesh", ingress ignores it
```

```bash
# 3. Do the hosts intersect?
kubectl -n demo get gateway httpbin-gateway -o jsonpath='{.spec.servers[*].hosts}{"\n"}'
kubectl -n demo get virtualservice httpbin -o jsonpath='{.spec.hosts}{"\n"}'
```

```bash
# 4. Cross-namespace reference missing the prefix?
istioctl analyze -n demo
```

```bash
# 5. Does the Gateway selector match a real gateway pod?
kubectl -n demo get gateway httpbin-gateway -o jsonpath='{.spec.selector}{"\n"}'
kubectl -n istio-system get pods -l istio=ingressgateway
```

```bash
# 6. Is the port name correctly prefixed?
kubectl -n demo get gateway httpbin-gateway -o jsonpath='{.spec.servers[*].port}{"\n"}'
# name must start with http/http2/https/grpc/tcp/tls
```

```bash
# 7. What does the gateway Envoy actually have? The authoritative check.
istioctl proxy-config route deploy/istio-ingressgateway.istio-system
istioctl proxy-config listener deploy/istio-ingressgateway.istio-system
```

If `proxy-config route` shows no vhost for your host, the config never reached Envoy and the problem is in the resources. If it shows the vhost but you still get `404`, the problem is downstream: the destination service, its port, or the path.

```bash
# 8. Does the destination exist and have endpoints?
kubectl -n demo get svc httpbin
istioctl proxy-config endpoint deploy/istio-ingressgateway.istio-system --cluster \
  "outbound|8000||httpbin.demo.svc.cluster.local"
```

```bash
# 9. Read the gateway's own logs while you send the request
kubectl -n istio-system logs deploy/istio-ingressgateway -f &
curl -sS -o /dev/null -H "Host: httpbin.example.com" http://localhost/get
kill %1
```

A `404` with response flag `NR` means **no route** was found, which points back at causes 1 to 6.

```bash
# 10. The umbrella
istioctl analyze -A
```

A compact mental model of gateway `404`s:

| Symptom | Likely cause |
| --- | --- |
| `404` with `NR` flag | No route matched. Host mismatch or missing gateway binding |
| `404` from the app, not Envoy | Route worked; the app does not serve that path. Check `rewrite` |
| `503` with `UF` | Route worked, upstream unreachable. Service or endpoints problem |
| `503` with `NC` | No cluster. The destination host does not resolve in the registry |
| Connection refused | The port is not on the gateway Service, or no listener exists |

### 10. Conflicting Gateways

Create the conflict:

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: gw-a
  namespace: demo
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "*"
---
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: gw-b
  namespace: demo
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "shop.example.com"
EOF
```

Detect it:

```bash
istioctl analyze -n demo
```

```text
Warning [IST0109] (Gateway gw-b.demo) The gateways gw-a and gw-b associated with the same port 80 and selector
  have conflicting hosts, which may cause unexpected behaviour
```

```bash
# Find every Gateway on port 80 with the same selector
kubectl get gateway -A -o json | jq -r '
  .items[]
  | . as $g
  | .spec.servers[]
  | select(.port.number==80)
  | "\($g.metadata.namespace)/\($g.metadata.name)\tselector=\($g.spec.selector)\thosts=\(.hosts)"' \
  | column -t
```

Resolve it by making the hosts disjoint:

```bash
kubectl -n demo patch gateway gw-a --type=json \
  -p='[{"op":"replace","path":"/spec/servers/0/hosts/0","value":"api.example.com"}]'
istioctl analyze -n demo
```

Or consolidate into one Gateway with multiple hosts, which is generally better. The rule to remember: **for a given gateway workload and port, hosts must not overlap across Gateway resources.** When they do, which one wins is not something you should rely on.

### 11. Which pod serves a Gateway, and what listener resulted

```bash
# The selector on the Gateway
kubectl -n demo get gateway httpbin-gateway -o jsonpath='{.spec.selector}{"\n"}'

# Pods matching it
kubectl get pods -A -l istio=ingressgateway
```

```bash
# The listeners that Gateway produced
istioctl proxy-config listener deploy/istio-ingressgateway.istio-system

# Full detail for port 80
istioctl proxy-config listener deploy/istio-ingressgateway.istio-system --port 80 -o json \
  | jq '.[0] | {name, address: .address.socketAddress, filterChains: [.filterChains[].name]}'

# The routes attached
istioctl proxy-config route deploy/istio-ingressgateway.istio-system --name http.80 -o json \
  | jq '.[].virtualHosts[] | {name, domains, routes: [.routes[].match]}'
```

The name `http.80` follows the pattern `<port-name-prefix>.<port-number>`. Recognising these generated names makes `proxy-config` output far easier to navigate.

The reverse lookup, from a listener back to the Gateway that created it:

```bash
istioctl proxy-config route deploy/istio-ingressgateway.istio-system -o json \
  | jq -r '.[].virtualHosts[]? | "\(.name)\t\(.domains)"'
```

And the workload-oriented summary:

```bash
istioctl x describe pod -n istio-system \
  $(kubectl -n istio-system get pod -l istio=ingressgateway -o jsonpath='{.items[0].metadata.name}')
```

### 12. Kubernetes Ingress instead of a Gateway

Istio can act as an Ingress controller, which is useful for compatibility.

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: httpbin-ingress
  namespace: demo
spec:
  ingressClassName: istio
  rules:
    - host: httpbin.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: httpbin
                port:
                  number: 8000
EOF
```

```bash
kubectl -n demo get ingress
curl -sS -o /dev/null -w "%{http_code}\n" -H "Host: httpbin.example.com" http://localhost/
```

`ingressClassName: istio` is what tells Istio to handle it. Which gateway serves Ingress resources is set by `meshConfig.ingressSelector`, defaulting to `ingressgateway`.

The limits, and why Gateway plus VirtualService is preferred: Ingress cannot express weighted traffic shifting, header matching, retries, timeouts, mirroring, or fault injection. It is a lowest-common-denominator API. The Kubernetes **Gateway API** is the modern successor and is covered in `20.md`.

istioctl proxy-config listener deploy/istio-ingressgateway.istio-system

## Exam Tips

**A Gateway alone always gives `404`.** Gateway opens the port, VirtualService routes the request. If a task says "expose service X externally", you write two resources. Writing only the Gateway is the single most common incomplete answer in this domain.

**`spec.gateways` on the VirtualService is mandatory for ingress.** Omitted, it defaults to `mesh` and ingress traffic is unaffected. And once you list a gateway explicitly, add `mesh` back if in-mesh clients also need the rules.

**Hosts must intersect.** Gateway `hosts` and VirtualService `hosts` need overlap, with wildcards counting as overlap. No intersection means no attachment and no error until you curl.

**Cross-namespace Gateway references need `namespace/name`.** `istio-system/my-gateway`. `istioctl analyze` reports `IST0101` when you forget, so run it.

**Port names must be protocol-prefixed.** `name: http`, `name: https`, `name: tcp-mysql`. A name like `web` makes Istio treat the port as opaque TCP, and every HTTP feature silently stops working. This is a favourite sabotage.

**`istioctl proxy-config route deploy/istio-ingressgateway.istio-system` is the fastest gateway debug command.** One line of output tells you whether the vhost exists, which domains it matches, and which VirtualService produced it. Reach for it before reading YAML.

**Two changes for a non-standard port.** The Gateway declares it and the gateway Kubernetes Service must expose it. `proxy-config listener` showing your port does not mean traffic can reach it.

**TCP routing uses `tcp:` with a `port` match, not `http:`.** And accept that you lose all L7 features. If a task involves a database or a non-HTTP protocol, that is the shape.

**`tls.httpsRedirect: true` goes on the HTTP server block**, not the HTTPS one.

**Send the `Host` header in every test curl.** Half of all "my gateway is broken" moments are a missing `-H "Host: ..."`.
