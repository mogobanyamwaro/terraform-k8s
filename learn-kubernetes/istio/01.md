# 01. Istio Architecture, Components, and Mesh Inspection

## Concept Refresher

Istio splits into two halves, and almost every troubleshooting question in the exam reduces to working out which half is at fault.

**Control plane: `istiod`.** One binary, one Deployment, in `istio-system`. It does four jobs:

1. Watches the Kubernetes API for Services, Endpoints, Pods, and Istio CRs.
2. Translates all of that into Envoy configuration and pushes it over **xDS**.
3. Acts as the mesh **certificate authority**, issuing workload identities.
4. Runs the **sidecar injection webhook** and the **validation webhook**.

**Data plane: Envoy.** One Envoy per workload in sidecar mode, or the shared `ztunnel` plus optional waypoints in ambient mode. Envoy is what actually moves bytes. It enforces every routing rule, every retry, every mTLS handshake, and every authorization decision.

The critical consequence: **istiod never sits in the request path.** If istiod dies, existing traffic keeps flowing on the last config Envoy received. New config stops propagating, new workloads cannot get certificates, but the mesh does not go down. This is a favourite exam concept.

### The xDS push cycle

```text
You apply a VirtualService
        |
        v
istiod watches the API server, sees the change
        |
        v
istiod recomputes config for every affected proxy
        |
        v
istiod pushes over xDS (port 15012, mTLS)
        |
        v
Envoy applies it, ACKs
        |
        v
istioctl proxy-status shows SYNCED
```

The xDS resource types map onto `istioctl proxy-config` subcommands, and knowing the mapping is how you debug quickly:

| xDS type | Full name | What it holds | Inspect with |
| --- | --- | --- | --- |
| **CDS** | Cluster Discovery Service | Upstream clusters, one per service+subset. Load balancing, connection pools, outlier detection | `istioctl proxy-config cluster` |
| **EDS** | Endpoint Discovery Service | The actual pod IPs behind each cluster | `istioctl proxy-config endpoint` |
| **LDS** | Listener Discovery Service | Ports Envoy listens on, and the filter chains on them | `istioctl proxy-config listener` |
| **RDS** | Route Discovery Service | HTTP routing rules, from VirtualServices | `istioctl proxy-config route` |
| **SDS** | Secret Discovery Service | TLS certificates and keys | `istioctl proxy-config secret` |

Read it as a sentence: a **listener** accepts the connection, a **route** picks the destination, a **cluster** describes how to talk to it, and **endpoints** are the addresses.

### Ports you must know

The `15xxx` range is Istio's. Memorise these; they appear in troubleshooting tasks and in `NetworkPolicy` and firewall questions.

| Port | Owner | Purpose |
| --- | --- | --- |
| `15000` | Envoy | Admin interface (localhost only) |
| `15001` | Envoy | Outbound traffic capture |
| `15006` | Envoy | Inbound traffic capture |
| `15008` | Envoy / ztunnel | HBONE tunnel (ambient, and sidecar-to-waypoint) |
| `15020` | pilot-agent | Merged Prometheus metrics, at `/stats/prometheus` |
| `15021` | pilot-agent | Health checks, at `/healthz/ready` |
| `15053` | Envoy | DNS proxy, when enabled |
| `15090` | Envoy | Raw Envoy Prometheus telemetry |
| `15010` | istiod | xDS over plaintext (not recommended, often disabled) |
| `15012` | istiod | xDS and CA over mTLS. **The important one** |
| `15014` | istiod | istiod's own control plane metrics |
| `15017` | istiod | Webhook (injection and validation), served over HTTPS |

A memory hook: **21 is ready, 20 is metrics, 12 is the control channel, 06 is in, 01 is out, 00 is admin.**

### Sidecar traffic interception

In sidecar mode, an init container (`istio-init`) writes iptables rules in the pod's network namespace so that all traffic detours through Envoy. When `istio-cni` is installed, the CNI plugin does this instead and no privileged init container is needed.

```text
Outbound from app                    Inbound to app
-----------------                    --------------
app -> iptables REDIRECT             pod IP:port
    -> Envoy :15001                      -> iptables REDIRECT
    -> pick cluster/endpoint             -> Envoy :15006
    -> mTLS to remote Envoy              -> policy checks (authn, authz)
                                         -> app on real port
```

This is why a workload can be reached on its normal port even though Envoy is really listening on `15006`, and why `istioctl proxy-config listener` shows a `virtualInbound` listener on `15006` rather than one listener per port.

### What gets installed

| Component | Kind | Namespace | Required? |
| --- | --- | --- | --- |
| `istiod` | Deployment | `istio-system` | Yes |
| `istio-ingressgateway` | Deployment + Service | `istio-system` | Optional, in `default` and `demo` profiles |
| `istio-egressgateway` | Deployment + Service | `istio-system` | Optional, only in `demo` |
| `ztunnel` | DaemonSet | `istio-system` | Ambient mode only |
| `istio-cni-node` | DaemonSet | `istio-system` | Ambient mode, or optional in sidecar mode |
| CRDs | CustomResourceDefinition | cluster-scoped | Yes |
| `istio-sidecar-injector` | MutatingWebhookConfiguration | cluster-scoped | Sidecar mode |
| `istio-validator` | ValidatingWebhookConfiguration | cluster-scoped | Yes |

### The API groups

Getting these wrong wastes time, so know them cold for 1.26:

| Group | Version | Kinds |
| --- | --- | --- |
| `networking.istio.io` | `v1` | VirtualService, DestinationRule, Gateway, ServiceEntry, Sidecar, WorkloadEntry, WorkloadGroup, ProxyConfig |
| `networking.istio.io` | `v1alpha3` | EnvoyFilter (still alpha, deliberately) |
| `security.istio.io` | `v1` | PeerAuthentication, RequestAuthentication, AuthorizationPolicy |
| `telemetry.istio.io` | `v1` | Telemetry |
| `extensions.istio.io` | `v1alpha1` | WasmPlugin |
| `gateway.networking.k8s.io` | `v1` | Gateway, HTTPRoute, GRPCRoute (Kubernetes Gateway API) |

`v1beta1` still works for the networking and security groups, and older docs use it. Prefer `v1`. **EnvoyFilter is the one that is still `v1alpha3`.**

## Solutions

### 1. Versions in one command

```bash
istioctl version
```

Output has three sections:

```text
client version: 1.26.0
control plane version: 1.26.0
data plane version: 1.26.0 (14 proxies)
```

All three should match. A mismatch between control plane and data plane means some proxies were injected by an older istiod and have not been restarted, which is exactly the state you are in mid-upgrade.

For detail on each proxy:

```bash
istioctl version -o json | jq '.dataPlaneVersion'
```

If `istioctl version` hangs or reports no control plane, `istiod` is unreachable and everything else you try will be misleading. Check it first:

```bash
kubectl -n istio-system get pods -l app=istiod
```

### 2. List the CRDs

```bash
kubectl get crd | grep istio.io
kubectl get crd | grep -c istio.io
```

Cleaner:

```bash
kubectl get crd -o custom-columns='NAME:.metadata.name,GROUP:.spec.group' \
  | grep istio.io
```

Group them to see the shape of the API surface:

```bash
kubectl get crd -o jsonpath='{range .items[*]}{.spec.group}{"\n"}{end}' \
  | grep istio.io | sort | uniq -c
```

```text
  1 extensions.istio.io
  9 networking.istio.io
  3 security.istio.io
  1 telemetry.istio.io
```

### 3. Which namespaces are in the mesh

There are three enrolment mechanisms and you must check all three.

```bash
kubectl get ns -L istio-injection -L istio.io/rev -L istio.io/dataplane-mode
```

```text
NAME            STATUS   AGE   ISTIO-INJECTION   REV       DATAPLANE-MODE
bookinfo        Active   1h    enabled
demo            Active   1h    enabled
nomesh          Active   1h
istio-system    Active   1h
```

Interpretation:

| Label | Meaning |
| --- | --- |
| `istio-injection=enabled` | Sidecar injection from the **default** revision |
| `istio.io/rev=<rev>` | Sidecar injection from a **specific** revision or tag |
| `istio.io/dataplane-mode=ambient` | **Ambient** mode, no sidecar |
| none of the above | Not in the mesh |

`istio-injection=enabled` and `istio.io/rev` are mutually exclusive. If both are present, **`istio-injection=enabled` wins** and the revision label is ignored. That is a classic upgrade trap covered in `07.md`.

Also check for pod-level overrides, which beat the namespace label:

```bash
kubectl get pods -A -o json | jq -r '
  .items[]
  | select(.metadata.annotations["sidecar.istio.io/inject"] != null
        or .metadata.labels["sidecar.istio.io/inject"] != null)
  | "\(.metadata.namespace)/\(.metadata.name): \(.metadata.labels["sidecar.istio.io/inject"] // .metadata.annotations["sidecar.istio.io/inject"])"'
```

And confirm reality rather than intent, by counting containers:

```bash
kubectl get pods -A -o json | jq -r '
  .items[]
  | "\(.metadata.namespace)/\(.metadata.name): \([.spec.containers[].name] | join(","))"' \
  | grep istio-proxy
```

### 4. istiod and the xDS port

```bash
kubectl -n istio-system get svc istiod
```

```text
NAME     TYPE        CLUSTER-IP     PORT(S)
istiod   ClusterIP   10.96.148.32   15010/TCP,15012/TCP,443/TCP,15014/TCP
```

| Port | Purpose |
| --- | --- |
| `15010` | xDS, **plaintext**. Debugging only |
| `15012` | xDS and CA, **mTLS**. What proxies actually use |
| `443` | Webhook, forwarded to container port `15017` |
| `15014` | istiod's own monitoring endpoint |

Confirm proxies are connected to it:

```bash
kubectl -n istio-system exec deploy/istiod -- \
  curl -sS localhost:15014/debug/endpointz | head

# Number of connected proxies
kubectl -n istio-system exec deploy/istiod -- \
  curl -sS localhost:15014/metrics | grep pilot_xds_pushes | head
```

The address a proxy dials lives in its bootstrap config:

```bash
istioctl proxy-config bootstrap deploy/productpage-v1.bookinfo -o json \
  | jq '.bootstrap.dynamicResources.adsConfig.grpcServices'
```

You will see `istiod.istio-system.svc:15012`.

### 5. Confirm xDS sync for one workload

```bash
istioctl proxy-status
```

```text
NAME                                    CLUSTER      CDS        LDS        EDS        RDS          ECDS         ISTIOD           VERSION
productpage-v1-...bookinfo              Kubernetes   SYNCED     SYNCED     SYNCED     SYNCED       NOT SENT     istiod-...       1.26.0
```

Filter to one workload:

```bash
istioctl proxy-status | grep productpage
```

Status meanings, which you will need in `30.md`:

| Status | Meaning |
| --- | --- |
| `SYNCED` | Envoy acknowledged the latest config. Healthy |
| `NOT SENT` | istiod had nothing to send for this type. Usually fine |
| `STALE` | istiod pushed, Envoy has not ACKed. Push problem, or overloaded proxy |
| `SYNCED (100%)` | Partial, seen with delta xDS |

`ECDS: NOT SENT` is normal. It is for Wasm extension configs, and you have none.

### 6. Clusters known to productpage

```bash
istioctl proxy-config cluster deploy/productpage-v1.bookinfo
```

```text
SERVICE FQDN                     PORT   SUBSET   DIRECTION   TYPE
reviews.bookinfo.svc.cluster.local  9080  -       outbound    EDS
reviews.bookinfo.svc.cluster.local  9080  v1      outbound    EDS
reviews.bookinfo.svc.cluster.local  9080  v2      outbound    EDS
reviews.bookinfo.svc.cluster.local  9080  v3      outbound    EDS
```

Narrow it:

```bash
istioctl proxy-config cluster deploy/productpage-v1.bookinfo \
  --fqdn reviews.bookinfo.svc.cluster.local --subset v2
```

Get the full Envoy cluster object, which is where you verify connection pools and outlier detection later:

```bash
istioctl proxy-config cluster deploy/productpage-v1.bookinfo \
  --fqdn reviews.bookinfo.svc.cluster.local --subset v2 -o json
```

**The subset clusters only exist because a DestinationRule defines them.** Delete `destination-rule-all.yaml` and the `v1`/`v2`/`v3` rows disappear, which is the root cause of the most common 503 in Istio. Prove it:

```bash
kubectl -n bookinfo delete destinationrule reviews
istioctl proxy-config cluster deploy/productpage-v1.bookinfo --fqdn reviews.bookinfo.svc.cluster.local
# subsets are gone

kubectl -n bookinfo apply -f ~/istio-1.26.0/samples/bookinfo/networking/destination-rule-all.yaml
```

### 7. Inbound capture port for httpbin

```bash
istioctl proxy-config listener deploy/httpbin.demo
```

```text
ADDRESS      PORT  MATCH                                        DESTINATION
0.0.0.0      15006 Addr: *:15006                                Inline Route: ...
0.0.0.0      15001 ALL                                          PassthroughCluster
0.0.0.0      8000  Trans: raw_buffer; App: http/1.1,h2c         Route: 8000
```

Port **`15006`** is `virtualInbound`, the single listener that receives all captured inbound traffic. Port `15001` is `virtualOutbound`.

See the filter chains on it, which is where mTLS and authorization actually live:

```bash
istioctl proxy-config listener deploy/httpbin.demo --port 15006 -o json \
  | jq '.[0].filterChains[] | {name: .name, transportProtocol: .filterChainMatch.transportProtocol, appProtocols: .filterChainMatch.applicationProtocols}'
```

You will see chains for `raw_buffer` (plaintext) and `tls` (mTLS). With `PERMISSIVE` mode both exist. Under `STRICT`, the plaintext chain is gone, which is exactly how you verify `STRICT` took effect in `23.md`.

### 8. Certificate and SPIFFE identity

```bash
istioctl proxy-config secret deploy/httpbin.demo
```

```text
RESOURCE NAME     TYPE           STATUS     VALID CERT     SERIAL NUMBER   NOT AFTER              NOT BEFORE
default           Cert Chain     ACTIVE     true           1a2b3c...       2026-08-20T10:00:00Z   2026-08-19T10:00:00Z
ROOTCA            CA             ACTIVE     true           4d5e6f...       2036-08-17T09:00:00Z   2026-08-19T09:00:00Z
```

`default` is the workload's own 24-hour cert. `ROOTCA` is the mesh root, valid 10 years.

Extract the identity:

```bash
istioctl proxy-config secret deploy/httpbin.demo -o json \
  | jq -r '.dynamicActiveSecrets[] | select(.name=="default")
           | .secret.tlsCertificate.certificateChain.inlineBytes' \
  | base64 -d \
  | openssl x509 -noout -text \
  | grep -A1 'Subject Alternative Name'
```

```text
X509v3 Subject Alternative Name: critical
    URI:spiffe://cluster.local/ns/demo/sa/httpbin
```

Decompose that URI, because `AuthorizationPolicy` in `25.md` matches on exactly this string:

```text
spiffe://cluster.local/ns/demo/sa/httpbin
        |             |       |
        trust domain  ns      Kubernetes ServiceAccount
```

The identity comes from the **ServiceAccount**, not the pod name, not the Deployment, not the label. Workloads that share a ServiceAccount share an identity and are indistinguishable to authorization policy. That is a real design trap and a likely exam distinction.

### 9. Sidecar mode, ambient mode, or both

```bash
# ztunnel present means ambient is installed
kubectl -n istio-system get daemonset ztunnel 2>/dev/null \
  && echo "ambient installed" || echo "no ambient"

# Injection webhook present means sidecar is available
kubectl get mutatingwebhookconfiguration | grep sidecar-injector \
  && echo "sidecar injection available"

# Which namespaces use which
kubectl get ns -L istio-injection -L istio.io/dataplane-mode
```

Both can be installed simultaneously. Enrolment is per namespace (or per pod), so a single cluster can run some namespaces in ambient and others with sidecars.

Check the profile that was used:

```bash
kubectl -n istio-system get iop -o yaml 2>/dev/null | grep -i profile
# or, if installed with istioctl without IstioOperator persisted:
kubectl -n istio-system get cm istio -o yaml
```

### 10. Effective MeshConfig

```bash
kubectl -n istio-system get configmap istio -o jsonpath='{.data.mesh}'
```

Readable:

```bash
kubectl -n istio-system get configmap istio -o jsonpath='{.data.mesh}' | less
```

A trimmed example:

```yaml
defaultConfig:
  discoveryAddress: istiod.istio-system.svc:15012
  proxyMetadata: {}
  tracing:
    zipkin:
      address: zipkin.istio-system:9411
defaultProviders:
  metrics:
    - prometheus
enablePrometheusMerge: true
rootNamespace: istio-system
trustDomain: cluster.local
```

`rootNamespace` matters enormously: policies created in it apply **mesh-wide**. It defaults to `istio-system`.

To see the whole thing including defaults you did not set:

```bash
istioctl x mesh-config 2>/dev/null || kubectl -n istio-system get cm istio -o yaml
```

You can also read what a specific proxy believes:

```bash
istioctl proxy-config bootstrap deploy/httpbin.demo -o json | jq '.bootstrap.node.metadata'
```

### 11. The injection webhook and its revision

```bash
kubectl get mutatingwebhookconfiguration
```

```text
NAME                         WEBHOOKS   AGE
istio-sidecar-injector       4          1h
```

Which revision and which namespaces it selects:

```bash
kubectl get mutatingwebhookconfiguration istio-sidecar-injector \
  -o jsonpath='{range .webhooks[*]}{.name}{"\t"}{.namespaceSelector}{"\n"}{end}'
```

For a revisioned install the object is named `istio-sidecar-injector-<revision>`:

```bash
kubectl get mutatingwebhookconfiguration -l app=sidecar-injector \
  -o custom-columns='NAME:.metadata.name,REV:.metadata.labels.istio\.io/rev'
```

The service the webhook calls:

```bash
kubectl get mutatingwebhookconfiguration istio-sidecar-injector \
  -o jsonpath='{.webhooks[0].clientConfig.service}'
```

```json
{"name":"istiod","namespace":"istio-system","path":"/inject","port":443}
```

`failurePolicy` decides what happens if istiod is unreachable during pod creation:

```bash
kubectl get mutatingwebhookconfiguration istio-sidecar-injector \
  -o jsonpath='{range .webhooks[*]}{.name}: {.failurePolicy}{"\n"}{end}'
```

`Fail` blocks pod creation when istiod is down. `Ignore` lets pods start with no sidecar, which is quieter but produces workloads silently outside the mesh.

### 12. Summarise one workload's mesh status

The single most useful command in the whole exam:

```bash
istioctl x describe pod -n bookinfo \
  $(kubectl -n bookinfo get pod -l app=reviews,version=v2 -o jsonpath='{.items[0].metadata.name}')
```

```text
Pod: reviews-v2-...
   Pod Revision: default
   Pod Ports: 9080 (reviews), 15090 (istio-proxy)
--------------------
Service: reviews
   Port: http 9080/HTTP targets pod port 9080
DestinationRule: reviews for "reviews"
   Matching subsets: v2
      (Non-matching subsets v1,v3)
   No Traffic Policy
VirtualService: reviews
   Weight 50%
--------------------
Effective PeerAuthentication:
   Workload mTLS mode: PERMISSIVE
```

This one command tells you the revision, the matching subsets, the VirtualService weight, and the effective mTLS mode. When a task says "why is this workload not receiving traffic", start here.

There is also a service-oriented view:

```bash
istioctl x describe service reviews -n bookinfo
```

## Exam Tips

**`istioctl x describe pod` is your highest-leverage command.** It collapses five separate lookups into one. `x` is short for `experimental`; both `istioctl x describe` and `istioctl experimental describe` work.

**Learn the four-word chain: listener, route, cluster, endpoint.** When traffic misbehaves, walk it in that order. A missing route means the VirtualService did not attach. A missing cluster means the subset or Service does not exist. Empty endpoints mean the pods are not ready or the selector is wrong.

**`proxy-status` before `proxy-config`.** If a proxy is `STALE`, the config you are about to read is not the config you just wrote, and you will chase a ghost.

**The target syntax `deploy/name.namespace` saves keystrokes.** These are equivalent:

```bash
istioctl proxy-config route deploy/httpbin.demo
istioctl proxy-config route -n demo deploy/httpbin
istioctl proxy-config route httpbin-7f5c9b8d4-xk2ml.demo
```

Using `deploy/` means you never have to copy a pod hash.

**Do not confuse `istioctl proxy-config` with `kubectl get`.** `kubectl get virtualservice` shows what you *asked for*. `istioctl proxy-config route` shows what Envoy *received*. When they disagree, believe Envoy and go find out why istiod did not push what you expected. That gap is the whole of `29.md` through `31.md`.

**Know that istiod is not in the data path.** If a task says "istiod was down for ten minutes, why did traffic keep working", the answer is that Envoy runs on cached config, and the visible symptoms are stale endpoints and failed cert rotation, not an outage.

**`istio-system` is special.** It is the `rootNamespace`. A `PeerAuthentication` or `AuthorizationPolicy` created there without a `selector` applies to the entire mesh. Creating a `DENY` policy there is how candidates accidentally break their own cluster mid-exam.
