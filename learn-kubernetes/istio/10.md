# 10. Request Matching: URI, Headers, Method, Query, Source

## Concept Refresher

`match` is how a routing rule decides whether it applies. The exam will give you a scenario in prose ("only requests from the frontend, with a beta header, on POST") and expect the YAML.

### The full match vocabulary

```yaml
      match:
        - uri:                    # path
            exact: /api/v1/users
            prefix: /api
            regex: "^/api/v[0-9]+/.*"
          scheme:
            exact: https
          method:
            exact: POST
          authority:              # the Host header
            prefix: api.
          headers:
            x-version:
              exact: v2
            user-agent:
              regex: ".*Chrome.*"
          withoutHeaders:         # negative match
            x-internal:
              exact: "true"
          queryParams:
            version:
              exact: v2
          port: 8000
          sourceLabels:           # WHO is calling
            app: frontend
          sourceNamespace: shop
          gateways:
            - my-gateway
          statPrefix: my-metric
          ignoreUriCase: true
```

### The three string match types

Every string field takes exactly one of these:

| Type | Meaning | Example |
| --- | --- | --- |
| `exact` | Full equality | `exact: /api/users` matches only that path |
| `prefix` | Starts with | `prefix: /api` matches `/api`, `/api/x`, `/apixyz` |
| `regex` | RE2 regular expression | `regex: "^/api/v[0-9]+$"` |

Two traps worth committing to memory:

**`prefix` is a plain string prefix, not a path-segment prefix.** `prefix: /api` matches `/apifoo`. If you need segment semantics, use `prefix: /api/` or a regex.

**The regex flavour is RE2**, which has no backreferences and no lookahead. `(?=...)` and `\1` are rejected. Keep expressions simple.

### AND versus OR, again

This is the most-tested subtlety in the whole matching topic:

```yaml
      match:
        - uri:
            prefix: /api
          headers:
            x-beta:
              exact: "true"
        # ^ ONE entry: path AND header must both hold

        - uri:
            prefix: /beta
        # ^ SECOND entry: OR'd with the first
```

Read the list as alternatives, and the fields inside one item as requirements. So the above means: "(`/api` **and** `x-beta: true`) **or** (`/beta`)".

### Header names are case-insensitive, values are not

HTTP header names normalise to lowercase, so `X-Version` and `x-version` are the same key. Values are matched literally, so `exact: V2` does not match `v2`. When a task specifies a header value, copy it exactly.

### `sourceLabels` is about the caller

```yaml
          sourceLabels:
            app: frontend
            version: v2
```

This matches on labels of the **client workload's pod**, and it only works because the client has a sidecar that knows its own identity. Two consequences to remember:

- It does **not** work for traffic arriving through a gateway, because the gateway is the client and its labels are the gateway's. For gateway traffic, match on headers instead.
- All listed labels must match, so it is an AND.

`sourceNamespace` is the namespace equivalent and is often what you actually want.

## Tasks

Use `demo` (with `httpbin`, `sleep`) and `bookinfo`.

1. Route `GET /get` on `httpbin` to a 200 with an added header, and `POST /post` to a different rule.
2. Route requests whose path matches the regex `^/status/[45][0-9][0-9]$` to a fixed 503 response.
3. Route on a query parameter: `?version=v2` goes to `reviews` v2.
4. Route on `authority` (the Host header) so `api.example.com` and `www.example.com` behave differently through one gateway.
5. Match on the absence of a header: requests **without** `x-internal: true` should be rejected with 403.
6. Route requests from workloads labelled `app: sleep` in `demo` to a distinct destination.
7. Route requests from any workload in the `bookinfo` namespace differently from all others.
8. Combine conditions: `POST` to `/api` with header `x-beta: true`, otherwise fall through.
9. Write a rule that fires for either of two completely different condition sets.
10. Make a path match case-insensitive.
11. Match on a header with a prefix and demonstrate that `prefix` on a URI is not segment-aware.
12. A `sourceLabels` match works east-west but not through the gateway. Explain and provide a working alternative.

## Solutions

### 1. Method and path matching

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - method:
            exact: GET
          uri:
            exact: /get
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: get-exact
    - match:
        - method:
            exact: POST
          uri:
            prefix: /post
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: post-prefix
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: fallback
EOF
```

```bash
C="kubectl -n demo exec deploy/sleep -c sleep -- curl -sS -D- -o /dev/null"

$C http://httpbin:8000/get               | grep -i x-matched
$C -X POST http://httpbin:8000/post      | grep -i x-matched
$C http://httpbin:8000/headers           | grep -i x-matched
$C -X POST http://httpbin:8000/get       | grep -i x-matched
```

```text
x-matched: get-exact
x-matched: post-prefix
x-matched: fallback
x-matched: fallback
```

The last one is the interesting case: `POST /get` matches neither of the first two rules, because rule 1 requires `GET` and rule 2 requires the `/post` prefix. Method and path are AND'd inside a single match entry.

### 2. Regex path match

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - uri:
            regex: "^/status/[45][0-9][0-9]$"
      directResponse:
        status: 503
        body:
          string: "error paths are blocked\n"
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
EOF
```

```bash
C="kubectl -n demo exec deploy/sleep -c sleep -- curl -sS -o /dev/null -w"

$C "404 path: %{http_code}\n" http://httpbin:8000/status/404
$C "500 path: %{http_code}\n" http://httpbin:8000/status/500
$C "200 path: %{http_code}\n" http://httpbin:8000/status/200
$C "/get:     %{http_code}\n" http://httpbin:8000/get
```

```text
404 path: 503
500 path: 503
200 path: 200
/get:     200
```

`/status/200` and `/get` fall through to the real service. The two error ranges are intercepted.

Two notes on regex. Anchors matter: without `^` and `$`, `[45][0-9][0-9]` would match anywhere in the path. And RE2 has no lookahead, so a "match anything except" expression has to be written with `withoutHeaders` or restructured rather than with `(?!...)`.

Verify Envoy received a regex matcher, not a prefix:

```bash
istioctl proxy-config route deploy/sleep.demo --name 8000 -o json \
  | jq '.[].virtualHosts[] | select(.name|test("httpbin")) | .routes[0].match'
```

```json
{"safeRegex": {"regex": "^/status/[45][0-9][0-9]$"}}
```

`safeRegex` confirms it compiled as RE2.

### 3. Query parameter matching

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
  namespace: bookinfo
spec:
  hosts:
    - reviews
  http:
    - match:
        - queryParams:
            version:
              exact: v2
      route:
        - destination:
            host: reviews
            subset: v2
    - route:
        - destination:
            host: reviews
            subset: v1
EOF
```

```bash
kubectl -n bookinfo exec deploy/ratings-v1 -c ratings -- \
  curl -sS "http://reviews:9080/reviews/0?version=v2" | jq -r '.reviews[0].rating.stars // "no stars (v1)"'

kubectl -n bookinfo exec deploy/ratings-v1 -c ratings -- \
  curl -sS "http://reviews:9080/reviews/0" | jq -r '.reviews[0].rating.stars // "no stars (v1)"'
```

`queryParams` supports `exact` and `regex`, but **not `prefix`**. That asymmetry with `uri` and `headers` is worth remembering, because writing `prefix` there is a validation error.

### 4. Authority (Host) matching

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: multi-host
  namespace: demo
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "*.example.com"
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: by-authority
  namespace: demo
spec:
  hosts:
    - "*.example.com"
  gateways:
    - multi-host
  http:
    - match:
        - authority:
            exact: api.example.com
      rewrite:
        uri: /get
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-site: api
    - match:
        - authority:
            prefix: www.
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-site: www
    - directResponse:
        status: 404
        body:
          string: "unknown host\n"
EOF
```

```bash
curl -sS -D- -o /dev/null -H "Host: api.example.com" http://localhost/anything | grep -iE 'x-site'
curl -sS -D- -o /dev/null -H "Host: www.example.com" http://localhost/anything | grep -iE 'x-site'
curl -sS -o /dev/null -w "%{http_code}\n" -H "Host: other.example.com" http://localhost/anything
```

```text
x-site: api
x-site: www
404
```

`authority` matches the `Host`/`:authority` header. It is how you do virtual hosting inside a single VirtualService rather than creating one per host. The Gateway's wildcard `*.example.com` is what allows all three to arrive in the first place.

### 5. Negative header matching

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - withoutHeaders:
            x-internal:
              exact: "true"
      directResponse:
        status: 403
        body:
          string: "internal header required\n"
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
EOF
```

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "no header:   %{http_code}\n" http://httpbin:8000/get

kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "with header: %{http_code}\n" -H "x-internal: true" http://httpbin:8000/get
```

```text
no header:   403
with header: 200
```

`withoutHeaders` matches when the header is **absent, or present with a different value**. To match purely on absence regardless of value, use a regex that matches anything:

```yaml
          withoutHeaders:
            x-internal:
              regex: ".*"
```

An important caveat for the exam: this is routing, not security. A client can trivially set `x-internal: true` itself. If the task says "only internal clients may access this", the correct tool is an `AuthorizationPolicy` keyed on workload identity, not a header check. Being able to make that distinction is worth more than the YAML.

### 6. sourceLabels

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - sourceLabels:
            app: sleep
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-caller: sleep-workload
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-caller: other
EOF
```

```bash
# From sleep, which has app=sleep
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -D- -o /dev/null http://httpbin:8000/get | grep -i x-caller
# x-caller: sleep-workload

# From a different workload
kubectl -n bookinfo exec deploy/ratings-v1 -c ratings -- \
  curl -sS -D- -o /dev/null http://httpbin.demo:8000/get | grep -i x-caller
# x-caller: other
```

How this works mechanically, and why it matters: the match is evaluated on the **client's** sidecar, not the server's. istiod generates a different route table for each workload, so the `sleep` sidecar gets a route table where rule 1 is unconditional, while other workloads get one where rule 1 is absent. Confirm that:

```bash
istioctl proxy-config route deploy/sleep.demo --name 8000 -o json \
  | jq '.[].virtualHosts[] | select(.name|test("httpbin")) | .routes | length'

istioctl proxy-config route deploy/ratings-v1.bookinfo -o json \
  | jq '.[].virtualHosts[]? | select(.name|test("httpbin")) | .routes | length'
```

Different route counts for different callers. That is `sourceLabels` in action, and it explains why it cannot work for gateway traffic.

### 7. sourceNamespace

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - sourceNamespace: bookinfo
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-from-ns: bookinfo
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-from-ns: other
EOF
```

```bash
kubectl -n bookinfo exec deploy/ratings-v1 -c ratings -- \
  curl -sS -D- -o /dev/null http://httpbin.demo:8000/get | grep -i x-from-ns
# x-from-ns: bookinfo

kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -D- -o /dev/null http://httpbin:8000/get | grep -i x-from-ns
# x-from-ns: other
```

`sourceNamespace` is usually more robust than `sourceLabels`, because it does not depend on a labelling convention that someone might change.

### 8. Combined AND conditions

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - method:
            exact: POST
          uri:
            prefix: /api
          headers:
            x-beta:
              exact: "true"
      rewrite:
        uri: /post
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: beta-post
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: fallback
EOF
```

Test every combination, which is the discipline that catches AND/OR mistakes:

```bash
C="kubectl -n demo exec deploy/sleep -c sleep -- curl -sS -D- -o /dev/null"

echo -n "POST /api  +beta : "; $C -X POST -H "x-beta: true"  http://httpbin:8000/api/x | grep -io 'x-matched:.*'
echo -n "POST /api  -beta : "; $C -X POST                    http://httpbin:8000/api/x | grep -io 'x-matched:.*'
echo -n "GET  /api  +beta : "; $C        -H "x-beta: true"    http://httpbin:8000/api/x | grep -io 'x-matched:.*'
echo -n "POST /other +beta: "; $C -X POST -H "x-beta: true"   http://httpbin:8000/other | grep -io 'x-matched:.*'
```

```text
POST /api  +beta : x-matched: beta-post
POST /api  -beta : x-matched: fallback
GET  /api  +beta : x-matched: fallback
POST /other +beta: x-matched: fallback
```

Only the case where all three conditions hold matches. Three fields in one entry means three requirements.

### 9. Two alternative condition sets

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - uri:
            prefix: /api
          headers:
            x-beta:
              exact: "true"
        - headers:
            x-force-beta:
              exact: "yes"
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: beta
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: normal
EOF
```

```bash
C="kubectl -n demo exec deploy/sleep -c sleep -- curl -sS -D- -o /dev/null"

echo -n "/api + x-beta       : "; $C -H "x-beta: true" http://httpbin:8000/api/x | grep -io 'x-matched:.*'
echo -n "/get + x-force-beta : "; $C -H "x-force-beta: yes" http://httpbin:8000/get | grep -io 'x-matched:.*'
echo -n "/get, no headers    : "; $C http://httpbin:8000/get | grep -io 'x-matched:.*'
```

```text
/api + x-beta       : x-matched: beta
/get + x-force-beta : x-matched: beta
/get, no headers    : x-matched: normal
```

Two match entries, either sufficient. This is how you express OR, and it is the structure to reach for whenever a task says "or".

### 10. Case-insensitive path

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - uri:
            prefix: /Get
          ignoreUriCase: true
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: case-insensitive
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: fallback
EOF
```

```bash
C="kubectl -n demo exec deploy/sleep -c sleep -- curl -sS -D- -o /dev/null"
$C http://httpbin:8000/get | grep -io 'x-matched:.*'
$C http://httpbin:8000/GET | grep -io 'x-matched:.*'
```

Both match. `ignoreUriCase` sits inside the match entry alongside `uri`, not inside `uri` itself, which is easy to get wrong.

### 11. Header prefix, and the URI prefix trap

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - match:
        - headers:
            x-client:
              prefix: mobile-
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: mobile
    - match:
        - uri:
            prefix: /api
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: api-prefix
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: fallback
EOF
```

Header prefix:

```bash
C="kubectl -n demo exec deploy/sleep -c sleep -- curl -sS -D- -o /dev/null"
$C -H "x-client: mobile-ios" http://httpbin:8000/get | grep -io 'x-matched:.*'
$C -H "x-client: desktop"    http://httpbin:8000/get | grep -io 'x-matched:.*'
```

Now the trap. `prefix: /api` also matches `/apifoo`, because it is a raw string prefix:

```bash
$C http://httpbin:8000/api/x   | grep -io 'x-matched:.*'   # api-prefix, expected
$C http://httpbin:8000/apifoo  | grep -io 'x-matched:.*'   # api-prefix, SURPRISING
```

If you want path-segment semantics, use a trailing slash or a regex:

```yaml
        - uri:
            prefix: /api/
```

```yaml
        - uri:
            regex: "^/api(/.*)?$"
```

This bites in real deployments where `/api` and `/apidocs` are different services, and it is a plausible exam trap because the YAML looks obviously correct.

### 12. sourceLabels does not work through a gateway

Set up the failing case:

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: httpbin-gw
  namespace: demo
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "httpbin.example.com"
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - "httpbin.example.com"
  gateways:
    - httpbin-gw
  http:
    - match:
        - sourceLabels:
            app: sleep
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: from-sleep
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
      headers:
        response:
          add:
            x-matched: fallback
EOF
```

```bash
curl -sS -D- -o /dev/null -H "Host: httpbin.example.com" http://localhost/get | grep -i x-matched
# x-matched: fallback  -- always
```

Why: for gateway-bound traffic the client is the **ingress gateway pod**, whose labels are `istio=ingressgateway`, `app=istio-ingressgateway`. External clients have no workload identity at all, and the gateway cannot invent one for them. So `sourceLabels: {app: sleep}` can never match at the gateway.

Check the gateway's labels to see what would match:

```bash
kubectl -n istio-system get pod -l istio=ingressgateway \
  -o jsonpath='{.items[0].metadata.labels}' | jq
```

The workable alternatives, in order of preference:

**Match on a header, which is what external clients can actually carry:**

```yaml
      match:
        - headers:
            x-client-type:
              exact: mobile
```

**Match on a JWT claim, if the traffic is authenticated (see `24.md`):**

```yaml
      match:
        - headers:
            "@request.auth.claims.groups":
              exact: beta-testers
```

**Use two VirtualServices, splitting by gateway:**

```yaml
# One for mesh traffic, where sourceLabels works
spec:
  hosts: [httpbin]
  gateways: [mesh]
  http:
    - match:
        - sourceLabels:
            app: sleep
      ...
---
# One for gateway traffic, matching on headers instead
spec:
  hosts: ["httpbin.example.com"]
  gateways: [httpbin-gw]
  http:
    - match:
        - headers:
            x-client-type:
              exact: mobile
      ...
```

**Or match on the gateway itself, when a rule should only apply to one entry point:**

```yaml
      match:
        - gateways:
            - httpbin-gw
          uri:
            prefix: /api
```

That `gateways` field inside `match` is distinct from `spec.gateways`: the former is a condition, the latter is the binding.

## Exam Tips

**List entries are OR, fields within an entry are AND.** If you remember one thing from this file, remember that. A task saying "requests that are POST **and** have header X" is one entry with two fields; "requests on `/api` **or** with header Y" is two entries.

**`prefix` is a string prefix, not a path prefix.** `/api` matches `/apifoo`. Use `/api/` or a regex when segments matter.

**Regex is RE2: no lookahead, no backreferences.** Anchor with `^` and `$`. If you find yourself wanting `(?!...)`, restructure with `withoutHeaders` instead.

**`queryParams` has no `prefix`.** Only `exact` and `regex`.

**`ignoreUriCase` is a sibling of `uri`, not a field inside it.**

**`sourceLabels` and `sourceNamespace` only work east-west.** They are evaluated on the caller's sidecar. For gateway traffic the caller is the gateway, so match on headers or JWT claims instead. This is a very likely exam discrimination question.

**Header matching is not access control.** Clients can set any header. If a task says "restrict access to", reach for `AuthorizationPolicy`. If it says "route differently based on", header matching is correct.

**Header names are case-insensitive; values are case-sensitive.** Copy the value from the task exactly.

**Test every combination when a rule has multiple conditions.** The four-way test in task 8 is the habit that catches an accidental OR where you wanted an AND, and it takes fifteen seconds.

**`match.gateways` and `spec.gateways` are different things.** `spec.gateways` binds the VirtualService; `match.gateways` is a condition restricting a single rule to traffic from a particular gateway.
