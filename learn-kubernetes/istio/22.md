# 22. Istio Identity, SPIFFE, and Certificate Plumbing

## Concept Refresher

Every meshed workload gets a strong identity, independent of IP:

```text
spiffe://<trust-domain>/ns/<namespace>/sa/<serviceaccount>
```

Default trust domain is **`cluster.local`**. A frontend in `shop` running as ServiceAccount `frontend` is:

```text
spiffe://cluster.local/ns/shop/sa/frontend
```

That string is the **principal** used by AuthorizationPolicy (`source.principals`) and the SAN on the workload certificate.

### Who issues the certs

`istiod` is the CA (unless you plug in cert-manager / an external CA, `28.md`). The sidecar agent (or ztunnel) uses SDS:

```text
pod starts
  -> agent requests cert from istiod :15012
  -> istiod authenticates the Kubernetes ServiceAccount token
  -> issues a short-lived X.509 cert (default TTL 24h, rotated at ~50%)
  -> Envoy uses it for mTLS
```

Root CA lives in `istio-system` Secret `istio-ca-secret` (self-signed) or is provided as `cacerts`.

### What identity is NOT

- It is not the Kubernetes user in `kubeconfig`.
- It is not the pod name. Pods of the same SA share identity.
- Changing labels on a pod does **not** change SPIFFE. Changing the **ServiceAccount** does (after restart / new cert).

### Peer vs request identity

| Kind | Carried how | Policy field |
| --- | --- | --- |
| Peer (workload) | mTLS client cert SAN | `source.principals`, `source.namespaces` |
| Request (user/jwt) | JWT `iss` + `sub` | `requestPrincipals` (`iss/sub`) |

Authorization can use both. JWT without mTLS still has `requestPrincipals` but `principals` will be empty or `cluster.local/ns/X/sa/Y` only if mTLS ran.

## Tasks

1. Print the SPIFFE identity of `demo/httpbin` and `demo/sleep`.
2. Run a second `sleep` as ServiceAccount `sleep-alt` and show its principal differs.
3. Find the root CA secret and the cert TTL on a workload cert.
4. Write the principal string you would put in an AuthorizationPolicy to allow only `bookinfo/productpage`.

## Solutions

### 1. Read the SAN

```bash
istioctl proxy-config secret deploy/httpbin.demo -o json \
  | jq -r '.dynamicActiveSecrets[] | select(.name=="default") | .secret.tlsCertificate.certificateChain.inlineBytes' \
  | base64 -d | openssl x509 -noout -text | grep -A1 'Subject Alternative Name'
```

Shorter:

```bash
istioctl x describe pod -n demo $(kubectl -n demo get pod -l app=httpbin -o jsonpath='{.items[0].metadata.name}')
```

Or from the cert files in the sidecar (older):

```bash
kubectl -n demo exec deploy/httpbin -c istio-proxy -- \
  openssl x509 -in /etc/certs/cert-chain.pem -noout -text 2>/dev/null | grep URI || \
kubectl -n demo exec deploy/httpbin -c istio-proxy -- ls /var/run/secrets/istio
```

Expected: `URI:spiffe://cluster.local/ns/demo/sa/httpbin` (SA name follows the sample; confirm with `kubectl -n demo get pod -o yaml | grep serviceAccount`).

### 2. Different SA

```bash
kubectl -n demo create sa sleep-alt
kubectl -n demo apply -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sleep-alt
spec:
  replicas: 1
  selector:
    matchLabels: { app: sleep-alt }
  template:
    metadata:
      labels: { app: sleep-alt }
    spec:
      serviceAccountName: sleep-alt
      containers:
        - name: sleep
          image: curlimages/curl
          command: ["sleep", "infinity"]
EOF
```

Identity: `spiffe://cluster.local/ns/demo/sa/sleep-alt`.

### 3. CA and TTL

```bash
kubectl -n istio-system get secret istio-ca-secret
# or cacerts if you installed a custom root

istioctl proxy-config secret deploy/httpbin.demo -o json \
  | jq -r '.dynamicActiveSecrets[] | select(.name=="default") | .secret.tlsCertificate.certificateChain.inlineBytes' \
  | base64 -d | openssl x509 -noout -dates -ext subjectAltName
```

NotAfter minus NotBefore is ~24h by default. MeshConfig `defaultExpirationDuration` changes this (`28.md`).

### 4. Principal for productpage

```text
cluster.local/ns/bookinfo/sa/bookinfo-productpage
```

Confirm the SA:

```bash
kubectl -n bookinfo get deploy productpage-v1 -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
```

AuthorizationPolicy uses the form **without** the `spiffe://` prefix, or with it; Istio accepts `cluster.local/ns/...` in `principals`. Docs examples use:

```yaml
    from:
      - source:
          principals:
            - cluster.local/ns/bookinfo/sa/bookinfo-productpage
```

Wildcards: `cluster.local/ns/bookinfo/sa/*` all SAs in that namespace.

## Verify

```bash
kubectl -n demo get pod -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.spec.serviceAccountName}{"\n"}{end}'
istioctl analyze -n demo
```

Call httpbin from sleep and check peer identity in the access log (`source_principal` if you enable the JSON format, `34.md`).

## Exam Tips

- **Namespace + SA, not Deployment name.** `productpage-v1` is not the identity.
- Trust domain changes in multi-cluster (`trustDomain`). If the exam set a custom domain, principals must use it.
- `source.namespaces: ["bookinfo"]` is the shorthand for "any SA in that namespace" under mTLS.
- Without mTLS (`PeerAuthentication DISABLE`), `principals` cannot be verified. ALLOW rules that match on principals will not match plaintext peers.
- Docs: [Istio identity](https://istio.io/docs/concepts/security/#istio-identity).
