# 11. DestinationRule and Subsets

## Concept Refresher

If the VirtualService answers **where**, the DestinationRule answers **how**. It configures what happens *after* a destination has been chosen: which pods count as a subset, how to load balance, whether to use TLS, connection pool limits, and outlier detection.

```yaml
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
  namespace: bookinfo
spec:
  host: reviews                 # which service this applies to
  trafficPolicy:                # defaults for ALL subsets
    loadBalancer:
      simple: LEAST_REQUEST
    connectionPool: {...}
    outlierDetection: {...}
    tls:
      mode: ISTIO_MUTUAL
  subsets:                      # named groups of pods
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
      trafficPolicy:            # per-subset override
        loadBalancer:
          simple: ROUND_ROBIN
```

### Subsets are the load-bearing concept

A **subset** is a named label selector over the pods behind a Service. It is the only way a VirtualService can address "version 2 of reviews".

```text
Service: reviews  (selector: app=reviews)
    |
    +-- pod reviews-v1-abc  labels: app=reviews, version=v1
    +-- pod reviews-v2-def  labels: app=reviews, version=v2
    +-- pod reviews-v3-ghi  labels: app=reviews, version=v3

DestinationRule subsets:
    v1 -> labels: {version: v1}   -> selects reviews-v1-abc
    v2 -> labels: {version: v2}   -> selects reviews-v2-def
    v3 -> labels: {version: v3}   -> selects reviews-v3-ghi
```

Each subset becomes a separate Envoy cluster:

```text
outbound|9080||reviews.bookinfo.svc.cluster.local     <- no subset, all pods
outbound|9080|v1|reviews.bookinfo.svc.cluster.local   <- subset v1
outbound|9080|v2|reviews.bookinfo.svc.cluster.local   <- subset v2
```

**A VirtualService referencing `subset: v2` when no DestinationRule defines `v2` produces `503`, not a validation error.** This is the single most common self-inflicted failure in Istio, and it is examined relentlessly. Internalise the pair: *route to a subset, define the subset.*

### `host` resolution

`spec.host` follows the same rules as VirtualService hosts: short names resolve in the DestinationRule's own namespace. Across namespaces, fully qualify.

```yaml
  host: reviews                                   # same namespace
  host: reviews.bookinfo.svc.cluster.local        # explicit
  host: api.external.com                          # needs a ServiceEntry
  host: "*.example.com"                           # wildcard, for external hosts
```

### trafficPolicy precedence

```text
subset trafficPolicy  >  port-level trafficPolicy  >  top-level trafficPolicy  >  mesh default
```

A subset's `trafficPolicy` **replaces** the top-level one for that subset rather than merging field by field. So if the top level sets both a load balancer and a connection pool, and a subset sets only a load balancer, that subset loses the connection pool settings. This is a genuine trap.

### Port-level policies

```yaml
  trafficPolicy:
    portLevelSettings:
      - port:
          number: 9080
        loadBalancer:
          simple: ROUND_ROBIN
      - port:
          number: 9443
        tls:
          mode: SIMPLE
```

Useful when one service exposes both an HTTP and a TLS port needing different handling.

## Solutions

### 1. Basic subsets

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
  namespace: bookinfo
spec:
  host: reviews
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
    - name: v3
      labels:
        version: v3
EOF
```

Verify the clusters exist on a caller's sidecar:

```bash
istioctl proxy-config cluster deploy/productpage-v1.bookinfo \
  --fqdn reviews.bookinfo.svc.cluster.local
```

```text
SERVICE FQDN                            PORT   SUBSET   DIRECTION   TYPE
reviews.bookinfo.svc.cluster.local      9080   -        outbound    EDS
reviews.bookinfo.svc.cluster.local      9080   v1       outbound    EDS
reviews.bookinfo.svc.cluster.local      9080   v2       outbound    EDS
reviews.bookinfo.svc.cluster.local      9080   v3       outbound    EDS
```

Confirm each subset resolves to the right pod:

```bash
for v in v1 v2 v3; do
  echo -n "$v -> "
  istioctl proxy-config endpoint deploy/productpage-v1.bookinfo \
    --cluster "outbound|9080|$v|reviews.bookinfo.svc.cluster.local" \
    -o json | jq -r '.[0].hostStatuses[].address.socketAddress.address'
done
```

Cross-check against the pod IPs:

```bash
kubectl -n bookinfo get pods -l app=reviews -o custom-columns='NAME:.metadata.name,IP:.status.podIP,VERSION:.metadata.labels.version'
```

The labels in the subset must match labels actually on the pods. Check what is available:

```bash
kubectl -n bookinfo get pods -l app=reviews --show-labels
```

### 2. The undefined subset 503

```bash
kubectl -n bookinfo delete destinationrule reviews

kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
  namespace: bookinfo
spec:
  hosts:
    - reviews
  http:
    - route:
        - destination:
            host: reviews
            subset: v1
EOF
```

```bash
curl -s -o /dev/null -w "productpage: %{http_code}\n" http://localhost/productpage
kubectl -n bookinfo exec deploy/productpage-v1 -c productpage -- \
  curl -sS -o /dev/null -w "reviews: %{http_code}\n" http://reviews:9080/reviews/0
```

```text
reviews: 503
```

Now diagnose it from the data plane alone, which is the skill being tested.

**Step 1: is the route present?**

```bash
istioctl proxy-config route deploy/productpage-v1.bookinfo --name 9080 -o json \
  | jq '.[].virtualHosts[] | select(.name|test("reviews")) | .routes[].route.cluster'
```

```text
"outbound|9080|v1|reviews.bookinfo.svc.cluster.local"
```

The route exists and names a `v1` cluster.

**Step 2: does that cluster exist?**

```bash
istioctl proxy-config cluster deploy/productpage-v1.bookinfo \
  --fqdn reviews.bookinfo.svc.cluster.local
```

```text
SERVICE FQDN                          PORT   SUBSET   DIRECTION   TYPE
reviews.bookinfo.svc.cluster.local    9080   -        outbound    EDS
```

**No `v1` row.** The route points at a cluster that does not exist. That is the diagnosis.

**Step 3: confirm from the access log.**

```bash
kubectl -n bookinfo logs deploy/productpage-v1 -c istio-proxy --tail=5
```

```text
[...] "GET /reviews/0 HTTP/1.1" 503 NC cluster_not_found - "-" 0 0 0 - ... outbound|9080|v1|reviews...
```

Response flag **`NC` means "no cluster"**. That flag is the fingerprint of a missing subset, and recognising it instantly is worth real time in the exam.

**Step 4: `analyze` names it outright.**

```bash
istioctl analyze -n bookinfo
```

```text
Error [IST0101] (VirtualService reviews.bookinfo) Referenced host+subset in destinationrule not found:
  "reviews+v1"
```

Fix by defining the subset:

```bash
kubectl -n bookinfo apply -f ~/istio-1.26.0/samples/bookinfo/networking/destination-rule-all.yaml
kubectl -n bookinfo exec deploy/productpage-v1 -c productpage -- \
  curl -sS -o /dev/null -w "reviews: %{http_code}\n" http://reviews:9080/reviews/0
# 200
```

The 503 flag vocabulary, which recurs in `33.md`:

| Flag | Meaning | Typical cause |
| --- | --- | --- |
| `NC` | No cluster | Subset undefined, or host not in registry |
| `UF` | Upstream connection failure | Pod unreachable, mTLS mismatch |
| `UH` | No healthy upstream | All endpoints failing health checks or ejected |
| `NR` | No route | VirtualService did not match |
| `UO` | Upstream overflow | Circuit breaker tripped |
| `URX` | Retry limit exceeded | Retries exhausted |

### 3. Per-subset load balancing

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
  namespace: bookinfo
spec:
  host: reviews
  trafficPolicy:
    loadBalancer:
      simple: LEAST_REQUEST
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
    - name: v3
      labels:
        version: v3
      trafficPolicy:
        loadBalancer:
          simple: ROUND_ROBIN
EOF
```

Verify each cluster's policy:

```bash
for s in "" v1 v2 v3; do
  echo -n "subset '${s:-none}': "
  istioctl proxy-config cluster deploy/productpage-v1.bookinfo \
    --fqdn reviews.bookinfo.svc.cluster.local ${s:+--subset $s} -o json \
    | jq -r '.[0].lbPolicy // "ROUND_ROBIN (default)"'
done
```

```text
subset 'none': LEAST_REQUEST
subset 'v1': LEAST_REQUEST
subset 'v2': LEAST_REQUEST
subset 'v3': ROUND_ROBIN
```

`v1` and `v2` inherit the top-level policy; `v3` overrides it. That is the intended behaviour and shows inheritance working.

### 4. Multi-label subsets

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
  namespace: bookinfo
spec:
  host: reviews
  subsets:
    - name: v2-canary
      labels:
        version: v2
        track: canary
    - name: v1
      labels:
        version: v1
EOF
```

All labels in a subset must match, so this is an AND. Label a pod to make it match:

```bash
kubectl -n bookinfo patch deployment reviews-v2 -p \
  '{"spec":{"template":{"metadata":{"labels":{"track":"canary"}}}}}'
kubectl -n bookinfo rollout status deployment reviews-v2

istioctl proxy-config endpoint deploy/productpage-v1.bookinfo \
  --cluster "outbound|9080|v2-canary|reviews.bookinfo.svc.cluster.local"
```

If the subset has no matching pods, the cluster exists but has **zero endpoints**. The symptom is a `503` with flag `UH` (no healthy upstream), not `NC`. That distinction is diagnostically important:

| Symptom | Meaning |
| --- | --- |
| Cluster missing entirely, `NC` | Subset not defined in any DestinationRule |
| Cluster present, no endpoints, `UH` | Subset defined, but its labels match no pods |

Check for the empty case:

```bash
istioctl proxy-config endpoint deploy/productpage-v1.bookinfo \
  --cluster "outbound|9080|v2-canary|reviews.bookinfo.svc.cluster.local" -o json \
  | jq '.[0].hostStatuses | length'
```

### 5. Connection pool limits

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: httpbin
  namespace: demo
spec:
  host: httpbin
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 10
        connectTimeout: 3s
      http:
        http1MaxPendingRequests: 10
        http2MaxRequests: 10
        maxRequestsPerConnection: 1
        maxRetries: 3
EOF
```

Verify:

```bash
istioctl proxy-config cluster deploy/sleep.demo --fqdn httpbin.demo.svc.cluster.local -o json \
  | jq '.[0] | {maxConnections: .circuitBreakers.thresholds[0].maxConnections,
                maxPendingRequests: .circuitBreakers.thresholds[0].maxPendingRequests,
                maxRequests: .circuitBreakers.thresholds[0].maxRequests,
                maxRetries: .circuitBreakers.thresholds[0].maxRetries,
                connectTimeout: .connectTimeout}'
```

The full behaviour of these settings, including how to trip them and observe `UO` flags, is `19.md`. What matters here is knowing they live on the DestinationRule, not the VirtualService.

### 6. Disable mTLS to one host

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: ServiceEntry
metadata:
  name: external-api
  namespace: demo
spec:
  hosts:
    - api.external.example.com
  ports:
    - number: 443
      name: https
      protocol: HTTPS
  resolution: DNS
  location: MESH_EXTERNAL
---
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: external-api-no-mtls
  namespace: demo
spec:
  host: api.external.example.com
  trafficPolicy:
    tls:
      mode: DISABLE
EOF
```

The TLS modes, which you must be able to distinguish:

| Mode | Meaning |
| --- | --- |
| `DISABLE` | Send plaintext. No Istio TLS |
| `SIMPLE` | Envoy originates TLS to the upstream, validating the server |
| `MUTUAL` | Envoy originates mTLS with certs you supply |
| `ISTIO_MUTUAL` | Istio mTLS with automatically provisioned certs. The mesh default |

For an external service that already terminates its own TLS, `SIMPLE` with `insecureSkipVerify: false` is usual. For an external service where the application already does TLS itself, `DISABLE` prevents double encryption:

```yaml
  trafficPolicy:
    tls:
      mode: SIMPLE
      caCertificates: /etc/ssl/certs/ca-certificates.crt
      sni: api.external.example.com
```

Verify:

```bash
istioctl proxy-config cluster deploy/sleep.demo --fqdn api.external.example.com -o json \
  | jq '.[0].transportSocket // "no TLS (DISABLE)"'
```

A very common real-world use is turning off mTLS for a workload that Istio cannot mTLS with, such as a database with its own TLS or a workload outside the mesh:

```yaml
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: legacy-db
  namespace: demo
spec:
  host: legacy-db.legacy.svc.cluster.local
  trafficPolicy:
    tls:
      mode: DISABLE
```

Pair this with `PeerAuthentication` knowledge from `23.md`: `PeerAuthentication` controls what a workload **accepts**, `DestinationRule.trafficPolicy.tls` controls what a client **sends**. Both must agree, and mismatches are a classic 503 source.

### 7. Per-port TLS

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: multiport
  namespace: demo
spec:
  host: httpbin
  trafficPolicy:
    tls:
      mode: ISTIO_MUTUAL
    portLevelSettings:
      - port:
          number: 8000
        tls:
          mode: ISTIO_MUTUAL
        loadBalancer:
          simple: ROUND_ROBIN
      - port:
          number: 9000
        tls:
          mode: DISABLE
        connectionPool:
          tcp:
            maxConnections: 5
EOF
```

```bash
istioctl proxy-config cluster deploy/sleep.demo --fqdn httpbin.demo.svc.cluster.local -o json \
  | jq -r '.[] | "\(.name)\t\(.transportSocket.name // "plaintext")"'
```

`portLevelSettings` is the answer whenever a service exposes several ports needing different handling, for example an HTTP API port and a metrics port that should not be mTLS'd.

### 8. The subset trafficPolicy replacement trap

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
  namespace: bookinfo
spec:
  host: reviews
  trafficPolicy:
    loadBalancer:
      simple: LEAST_REQUEST
    connectionPool:
      tcp:
        maxConnections: 100
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 10s
      baseEjectionTime: 30s
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
      trafficPolicy:
        loadBalancer:
          simple: ROUND_ROBIN
EOF
```

Observe what `v2` lost:

```bash
echo "=== v1 (inherits everything) ==="
istioctl proxy-config cluster deploy/productpage-v1.bookinfo \
  --fqdn reviews.bookinfo.svc.cluster.local --subset v1 -o json \
  | jq '{lb: .[0].lbPolicy,
         maxConnections: .[0].circuitBreakers.thresholds[0].maxConnections,
         outlier: (.[0].outlierDetection // "none")}'

echo "=== v2 (overrode trafficPolicy) ==="
istioctl proxy-config cluster deploy/productpage-v1.bookinfo \
  --fqdn reviews.bookinfo.svc.cluster.local --subset v2 -o json \
  | jq '{lb: .[0].lbPolicy,
         maxConnections: .[0].circuitBreakers.thresholds[0].maxConnections,
         outlier: (.[0].outlierDetection // "none")}'
```

```text
=== v1 (inherits everything) ===
{"lb": "LEAST_REQUEST", "maxConnections": 100, "outlier": {...}}
=== v2 (overrode trafficPolicy) ===
{"lb": "ROUND_ROBIN", "maxConnections": null, "outlier": "none"}
```

**`v2` lost the connection pool and outlier detection entirely.** The subset `trafficPolicy` replaces the parent wholesale; it does not merge per field.

The workaround is to restate everything you want to keep:

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
  namespace: bookinfo
spec:
  host: reviews
  trafficPolicy:
    loadBalancer:
      simple: LEAST_REQUEST
    connectionPool:
      tcp:
        maxConnections: 100
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 10s
      baseEjectionTime: 30s
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
      trafficPolicy:
        loadBalancer:
          simple: ROUND_ROBIN
        connectionPool:            # restated
          tcp:
            maxConnections: 100
        outlierDetection:          # restated
          consecutive5xxErrors: 5
          interval: 10s
          baseEjectionTime: 30s
EOF
```

Verify `v2` now has all three. This trap is easy to miss because nothing errors and the load balancer change you asked for does work; it is the silent loss of the other settings that bites.

### 9. DestinationRule exists but subsets do not appear

```bash
# 1. Does the host resolve to a real service?
kubectl -n bookinfo get destinationrule reviews -o jsonpath='{.spec.host}{"\n"}'
kubectl -n bookinfo get svc reviews
```

A `host` that names no Service means the DestinationRule has nothing to attach to. Short names resolving to the wrong namespace is the usual cause:

```bash
istioctl analyze -n bookinfo
```

```text
Error [IST0101] (DestinationRule reviews.bookinfo) Referenced host not found: "reviws"
```

```bash
# 2. Do the subset labels match any pods?
kubectl -n bookinfo get destinationrule reviews -o jsonpath='{.spec.subsets}{"\n"}' | jq
kubectl -n bookinfo get pods -l app=reviews --show-labels
```

Remember the two distinct failures: no cluster at all versus a cluster with no endpoints.

```bash
# 3. Is exportTo hiding it from this caller?
kubectl -n bookinfo get destinationrule reviews -o jsonpath='{.spec.exportTo}{"\n"}'
```

```bash
# 4. Is the caller's config even up to date?
istioctl proxy-status | grep productpage
```

`STALE` means you are reading old config.

```bash
# 5. Is a Sidecar resource restricting what this proxy receives?
kubectl -n bookinfo get sidecar
kubectl get sidecar -n istio-system
```

A `Sidecar` with a narrow `egress.hosts` removes clusters for everything not listed. See `16.md`.

```bash
# 6. Is discoverySelectors excluding the namespace?
kubectl -n istio-system get cm istio -o jsonpath='{.data.mesh}' | grep -A3 discoverySelectors
kubectl get ns bookinfo --show-labels
```

```bash
# 7. Is another DestinationRule for the same host winning?
kubectl get destinationrule -A -o json \
  | jq -r '.items[] | "\(.metadata.namespace)/\(.metadata.name)\t\(.spec.host)"' \
  | sort -k2
```

### 10. Conflicting DestinationRules

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews-a
  namespace: bookinfo
spec:
  host: reviews
  trafficPolicy:
    loadBalancer:
      simple: ROUND_ROBIN
  subsets:
    - name: v1
      labels:
        version: v1
---
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews-b
  namespace: bookinfo
spec:
  host: reviews
  trafficPolicy:
    loadBalancer:
      simple: LEAST_REQUEST
  subsets:
    - name: v2
      labels:
        version: v2
EOF
```

```bash
istioctl analyze -n bookinfo
```

```text
Warning [IST0106] (DestinationRule reviews-b.bookinfo) DestinationRule reviews-a in namespace bookinfo
  has a conflicting subset/host with this rule
```

What actually happens is version-dependent and unreliable. Istio merges subsets from multiple rules in recent versions, but the `trafficPolicy` from only one takes effect, chosen by creation time. Check reality:

```bash
istioctl proxy-config cluster deploy/productpage-v1.bookinfo \
  --fqdn reviews.bookinfo.svc.cluster.local
istioctl proxy-config cluster deploy/productpage-v1.bookinfo \
  --fqdn reviews.bookinfo.svc.cluster.local -o json | jq -r '.[0].lbPolicy'
```

Fix by consolidating into one rule per host:

```bash
kubectl -n bookinfo delete destinationrule reviews-a reviews-b

kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
  namespace: bookinfo
spec:
  host: reviews
  trafficPolicy:
    loadBalancer:
      simple: LEAST_REQUEST
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
    - name: v3
      labels:
        version: v3
EOF

istioctl analyze -n bookinfo
```

**One DestinationRule per host** is the rule to follow, exactly as with VirtualServices.

### 11. exportTo on a DestinationRule

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
  namespace: bookinfo
spec:
  host: reviews
  exportTo:
    - "."
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
    - name: v3
      labels:
        version: v3
EOF
```

In-namespace callers see the subsets:

```bash
istioctl proxy-config cluster deploy/productpage-v1.bookinfo \
  --fqdn reviews.bookinfo.svc.cluster.local
# v1, v2, v3 present
```

Out-of-namespace callers do not:

```bash
istioctl proxy-config cluster deploy/sleep.demo \
  --fqdn reviews.bookinfo.svc.cluster.local
# only the no-subset cluster
```

So a VirtualService in `demo` routing to `reviews.bookinfo` with `subset: v2` gets a `503 NC`, even though the DestinationRule plainly exists. This is a nasty cross-namespace failure and a plausible troubleshooting task: the resource is right there, and the caller still cannot use it.

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: remote-reviews
  namespace: demo
spec:
  hosts:
    - reviews.bookinfo.svc.cluster.local
  http:
    - route:
        - destination:
            host: reviews.bookinfo.svc.cluster.local
            subset: v2
            port:
              number: 9080
EOF

kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{http_code}\n" http://reviews.bookinfo:9080/reviews/0
# 503

kubectl -n demo logs deploy/sleep -c istio-proxy --tail=3 | grep -o 'NC\|UH\|UF' 
```

Fix by exporting appropriately:

```bash
kubectl -n bookinfo patch destinationrule reviews --type merge \
  -p '{"spec":{"exportTo":["*"]}}'
# or just to the namespace that needs it
kubectl -n bookinfo patch destinationrule reviews --type merge \
  -p '{"spec":{"exportTo":[".","demo"]}}'
```

### 12. Audit subsets against references

Subsets referenced by VirtualServices:

```bash
kubectl get virtualservice -A -o json | jq -r '
  .items[] as $vs
  | ($vs.spec.http // [])[]
  | (.route // [])[]
  | select(.destination.subset != null)
  | "\($vs.metadata.namespace)/\($vs.metadata.name)\tneeds\t\(.destination.host)+\(.destination.subset)"' \
  | sort -u | column -t
```

Subsets defined by DestinationRules:

```bash
kubectl get destinationrule -A -o json | jq -r '
  .items[] as $dr
  | ($dr.spec.subsets // [])[]
  | "\($dr.metadata.namespace)/\($dr.metadata.name)\tdefines\t\($dr.spec.host)+\(.name)"' \
  | sort -u | column -t
```

Compare them directly:

```bash
diff \
  <(kubectl get virtualservice -A -o json | jq -r '
      .items[] | ((.spec.http // [])[] | (.route // [])[] | select(.destination.subset)
      | "\(.destination.host)+\(.destination.subset)")' | sort -u) \
  <(kubectl get destinationrule -A -o json | jq -r '
      .items[] as $dr | ($dr.spec.subsets // [])[] | "\($dr.spec.host)+\(.name)"' | sort -u)
```

Lines prefixed `<` are **referenced but not defined**, which means 503s waiting to happen. Lines prefixed `>` are defined but unused, which is harmless clutter.

The much shorter version, and what you would actually do in the exam:

```bash
istioctl analyze -A
```

It reports `IST0101` for every dangling `host+subset` reference. Use the jq only when you want the full inventory.

Also worth checking: mirror destinations, which the jq above misses:

```bash
kubectl get virtualservice -A -o json | jq -r '
  .items[] as $vs
  | ($vs.spec.http // [])[]
  | select(.mirror != null or .mirrors != null)
  | "\($vs.metadata.namespace)/\($vs.metadata.name)\tmirror\t\(.mirror // .mirrors)"'
```

## Exam Tips

**VirtualService subset reference plus DestinationRule subset definition always travel together.** If a task asks you to route to `v1`, check that the DestinationRule exists. If it does not, creating it is part of the answer. This one pairing accounts for more Istio failures than anything else.

**`503` with flag `NC` means the subset or host does not exist. `503` with `UH` means it exists but has no healthy pods.** Learn to read that distinction from the access log; it splits the problem in half immediately.

**One DestinationRule per host.** Multiple rules for the same host produce `IST0106` and merge behaviour you should not depend on.

**A subset `trafficPolicy` replaces the top-level one, it does not merge.** If a task asks you to change one setting for one subset, restate the settings you want to keep. This is a quiet way to lose points because the change you asked for works while others silently vanish.

**Fully qualify `spec.host` across namespaces.** A short name resolves in the DestinationRule's own namespace, and `istioctl analyze` reports `IST0101` when it resolves to nothing.

**`exportTo: ["."]` on a DestinationRule breaks cross-namespace subset routing.** The resource exists and looks correct, and remote callers still get `503 NC`. Worth checking whenever a subset works locally but not from another namespace.

**Remember the division of labour.** VirtualService: routes, matches, weights, timeouts, retries, faults, mirroring, rewrites. DestinationRule: subsets, load balancing, connection pools, outlier detection, TLS to the upstream. When a task names a feature, that mapping tells you which resource to open.

**`DestinationRule.trafficPolicy.tls` is what the client sends; `PeerAuthentication` is what the server accepts.** A mismatch between them is a classic 503, and knowing which resource controls which direction is the key to fixing it fast.

**`istioctl proxy-config cluster ... --subset <name> -o json` is your verification.** If the subset cluster is not listed, nothing else you do will work.
