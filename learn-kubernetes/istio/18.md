# 18. Timeouts and Retries

## Concept Refresher

Timeouts and retries live on the **VirtualService** HTTP route. They are L7. TCP routes do not have them. Ambient needs a waypoint or they silently do nothing.

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - timeout: 2s
      retries:
        attempts: 3
        perTryTimeout: 1s
        retryOn: connect-failure,refused-stream,unavailable,cancelled,retriable-status-codes,5xx
        retryRemoteLocalities: true
      route:
        - destination:
            host: httpbin
```

### Defaults (memorise)

| Setting | Default |
| --- | --- |
| Route `timeout` | **Disabled** (0, wait forever) |
| `retries.attempts` | **2** |
| `retries.perTryTimeout` | Same as the route timeout, or none |
| `retries.retryOn` | `connect-failure,refused-stream,unavailable,cancelled,retriable-status-codes` |

Default retries do **not** include `5xx`. A 503 from the app is **not** retried unless you add `5xx` or `gateway-error` etc. Connection failures are.

### How the clocks nest

```text
timeout:            budget for the whole request including retries
perTryTimeout:      budget for a single attempt
attempts:           number of RETRIES after the first try

Total tries = 1 + attempts
```

If `timeout` is 2s and `perTryTimeout` is 1s with `attempts: 3`, you will **not** get four full tries. The parent timeout wins. Set `timeout >= (1 + attempts) * perTryTimeout` or leave `timeout` off while practising retries.

### `retryOn` tokens you will use

| Token | Meaning |
| --- | --- |
| `5xx` | HTTP 500-599 from upstream |
| `gateway-error` | 502, 503, 504 |
| `connect-failure` | Connection failed |
| `reset` | Upstream reset the stream |
| `retriable-4xx` | 409 Conflict |
| `retriable-status-codes` | Codes listed in `retriableStatusCodes` |
| `retriable-headers` | Matching response headers |

### Interaction with fault injection

A `delay` fault counts against the timeout. An `abort` of 500 is retried if `retryOn` includes `5xx`. Exam tasks love: "inject 50% abort 500, retry 3 times" and expect you to wire both VS fields.

## Tasks

1. Set a **2s** timeout on all `httpbin` calls from the mesh.
2. Retry `httpbin` **3** times, `perTryTimeout` 1s, on `5xx` and connect failures. Overall timeout 5s.
3. Time out **only** `GET /delay/*` at 1s; other paths stay unlimited.
4. Disable retries on `httpbin` (zero extra attempts).

## Solutions

### 1. Timeout only

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: demo
spec:
  hosts:
    - httpbin
  http:
    - timeout: 2s
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
```

```bash
kubectl -n demo exec deploy/sleep -c sleep -- curl -sS -o /dev/null -w "%{http_code}\n" http://httpbin:8000/delay/5
```

Expect `504` (or `504` from Envoy, sometimes seen as `504 Gateway Timeout`).

### 2. Retries + timeout

```yaml
  http:
    - timeout: 5s
      retries:
        attempts: 3
        perTryTimeout: 1s
        retryOn: connect-failure,refused-stream,5xx
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
```

### 3. Path-specific timeout

```yaml
  http:
    - match:
        - uri:
            prefix: /delay
      timeout: 1s
      route:
        - destination:
            host: httpbin
            port:
              number: 8000
    - route:
        - destination:
            host: httpbin
            port:
              number: 8000
```

### 4. Disable retries

```yaml
      retries:
        attempts: 0
```

Omitting `retries` keeps the **mesh default of 2**. You must set `attempts: 0` to turn them off.

## Verify

```bash
# 504 on slow endpoint
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{http_code} time=%{time_total}\n" http://httpbin:8000/delay/5

# Envoy route dump
istioctl proxy-config route deploy/sleep.demo --name 8000 -o json \
  | jq '.. | .route? | objects | {timeout: .timeout, retryPolicy: .retryPolicy} | select(.timeout or .retryPolicy)'

# Access log: look for multiple attempts on one client request (response flags like UT)
kubectl -n demo logs deploy/httpbin -c istio-proxy --tail=30
```

## Exam Tips

- Timeout/retry = **VirtualService**. Circuit breaking / pool = **DestinationRule**. Mixing them is the most common resilience mistake.
- `attempts: 3` means **3 retries**, 4 tries total.
- Default retry policy does not retry HTTP 500. If the task says "retry on 500", add `5xx`.
- `timeout: 0s` is "no timeout", not "fail immediately".
- Docs: [Request timeouts](https://istio.io/docs/tasks/traffic-management/request-timeouts/) and VirtualService `timeout` / `retries`.
