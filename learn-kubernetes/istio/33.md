# 33. Troubleshooting the Data Plane (Envoy, 503s, Response Flags)

## Concept Refresher

Data plane issues: traffic is wrong, slow, or failing **while istiod is healthy and proxies are SYNCED**. You debug **Envoy**.

### Access logs

Default format includes **response flags**. They are the fastest 503 decoder.

```bash
kubectl -n demo logs deploy/sleep -c istio-proxy --tail=50
kubectl -n demo logs deploy/httpbin -c istio-proxy --tail=50
```

Enable if off (`34.md` Telemetry API). `demo` profile already logs.

### Response flags (memorise these)

| Flag | Meaning | Typical cause |
| --- | --- | --- |
| `NR` | No route | VS not bound, wrong host, no catch-all |
| `UH` | No healthy upstream | 0 endpoints, all ejected, subset labels wrong |
| `UO` | Upstream overflow | Connection pool circuit breaker |
| `UT` | Upstream timeout | VS timeout, slow app, delay fault |
| `UF` | Upstream connection failure | mTLS mismatch, pod died, wrong port |
| `UC` | Upstream connection termination | App closed connection |
| `LR` | Connection local reset | Often protocol mismatch |
| `DC` | Downstream connection termination | Client went away |
| `SI` | Stream idle timeout | |
| `-` | No flag, HTTP code is from the app | App really returned that status |

**NR** = routing. **UH** = endpoints. **UO** = DestinationRule pool. **UF** = TLS or network. This table is worth more than rereading YAML.

### 503 decision tree

```text
istioctl analyze -A
istioctl proxy-status          # STALE? control plane (32.md)
istioctl pc route  <SOURCE>    # is there a route for this host?
istioctl pc cluster <SOURCE>   # is the subset cluster there?
istioctl pc endpoint <SOURCE>  # any IPs? healthy?
curl from sleep, read FLAGS on both sidecars
PeerAuthentication vs DestinationRule tls
```

Always inspect the **source** proxy for outbound (VS, DR, clusters) and the **destination** proxy for inbound (authz, mTLS).

### Protocol issues

Service `port.name` must start with `http`, `http2`, `grpc`, `tls`, `tcp`, ... or set `appProtocol`. Named `foo` → TCP → HTTP VirtualService never matches → NR or bytes mishandled.

```bash
kubectl -n demo get svc httpbin -o yaml | grep -A6 'ports:'
```

### Direct pod vs Service

`curl podIP:8000` bypasses some outbound VS matching (depends on capture). Exam tasks want you to curl the **Service DNS**.

## Tasks

1. Create 503 NR by routing to subset `ghost`. Diagnose from flags + `pc`, then fix.
2. Create 503 UH by DestinationRule subset labels that match no pods.
3. Create 503 UO with `maxConnections: 1` and parallel `/delay/3`.
4. STRICT mTLS + unmeshed client → show UF / connection fail, then PERMISSIVE.
5. Rename Service port to `web` without `http` prefix and show HTTP routing breaking; restore.

## Solutions

### 1. NR

Apply VS to `subset: ghost`. Curl. Log flag `NR`. `pc cluster` has no `ghost`. Add DR subset or remove subset from VS.

### 2. UH

```yaml
  subsets:
    - name: v1
      labels:
        version: does-not-exist
```

VS routes to `v1`. Endpoints empty. Fix labels to `version: v1`.

### 3. UO

See `19.md`. Flag `UO`.

### 4. UF / mTLS

`23.md` STRICT + `nomesh` sleep. Destination proxy logs TLS errors; client `UF` or timeout.

### 5. Port name

```bash
kubectl -n demo patch svc httpbin --type json -p '[
  {"op":"replace","path":"/spec/ports/0/name","value":"web"}
]'
# HTTP VS stops working properly
kubectl -n demo patch svc httpbin --type json -p '[
  {"op":"replace","path":"/spec/ports/0/name","value":"http"}
]'
```

## Verify

```bash
kubectl -n demo exec deploy/sleep -c sleep -- \
  curl -sS -o /dev/null -w "%{http_code}\n" http://httpbin:8000/get
kubectl -n demo logs deploy/sleep -c istio-proxy --tail=5
istioctl pc ep deploy/sleep.demo --cluster "outbound|8000||httpbin.demo.svc.cluster.local"
```

## Exam Tips

- **Read the flag before editing YAML.** Randomly adding DestinationRules wastes time.
- Look at **both** proxies. Authz 403 appears on the **inbound** sidecar; NR on the **outbound**.
- `curl -v` from sleep shows connection errors; `-o /dev/null -w` shows codes. Use both.
- Docs: [Envoy response flags](https://www.envoyproxy.io/docs/envoy/latest/configuration/observability/access_log/usage#config-access-log-format-response-flags) and Istio [troubleshooting FAQ](https://istio.io/docs/ops/common-problems/network-issues/).
