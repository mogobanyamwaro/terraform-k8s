# 03. Installing Istio with Helm

## Concept Refresher

The exam objective says "Installing Istio with `istioctl` **or** Helm", so both are fair game. Helm is the production-preferred path because it fits existing GitOps and release tooling, and because upgrades are ordinary Helm upgrades.

The key structural difference: **`istioctl install` is one command that installs everything. Helm is several charts you install in a required order.**

### The charts

| Chart | Installs | Namespace | Order |
| --- | --- | --- | --- |
| `istio/base` | CRDs and cluster-scoped RBAC | `istio-system` | **1st, mandatory** |
| `istio/istiod` | The control plane | `istio-system` | **2nd, mandatory** |
| `istio/cni` | CNI node agent | `istio-system` | 3rd, ambient or optional |
| `istio/ztunnel` | ztunnel DaemonSet | `istio-system` | 4th, ambient only |
| `istio/gateway` | An ingress or egress gateway | any | last, optional, repeatable |

`istio/base` **must** come first, because everything else creates custom resources that need the CRDs to exist. Getting the order wrong produces `no matches for kind` errors.

The `istio/gateway` chart is deliberately separate and installable many times, once per gateway, in whichever namespace the gateway belongs to. That is a deliberate design improvement over the old bundled gateways: gateways are workloads, and workloads belong with their teams.

### Adding the repository

```bash
helm repo add istio https://istio-release.storage.googleapis.com/charts
helm repo update

helm search repo istio
helm search repo istio --versions | head
```

```text
NAME                CHART VERSION   APP VERSION     DESCRIPTION
istio/base          1.26.0          1.26.0          Helm chart for deploying Istio cluster resources
istio/cni           1.26.0          1.26.0          Helm chart for istio-cni components
istio/gateway       1.26.0          1.26.0          Helm chart for deploying Istio gateways
istio/istiod        1.26.0          1.26.0          Helm chart for istio control plane
istio/ztunnel       1.26.0          1.26.0          Helm chart for istio ztunnel
```

### Mapping IstioOperator concepts onto Helm values

This mapping is the part people find confusing, so it is worth internalising. Helm values are flatter than the `IstioOperator` tree.

| Concept | `istioctl` / IstioOperator | Helm |
| --- | --- | --- |
| Profile | `spec.profile=demo` | `--set profile=demo` |
| Mesh config | `spec.meshConfig.accessLogFile` | `--set meshConfig.accessLogFile` |
| Revision | `spec.revision=1-26-0` | `--set revision=1-26-0` |
| istiod resources | `spec.components.pilot.k8s.resources` | `--set pilot.resources` |
| Trust domain | `spec.meshConfig.trustDomain` | `--set meshConfig.trustDomain` |
| Gateway service type | `spec.components.ingressGateways[0].k8s.service.type` | `--set service.type` on the `gateway` chart |
| Pilot env var | `spec.values.pilot.env.FOO` | `--set env.FOO` on the `istiod` chart |

`meshConfig` is spelled the same in both, which is the one piece of good news.

## Tasks

Use a clean cluster. If Istio is already installed via `istioctl`, remove it first with `istioctl uninstall --purge -y && kubectl delete ns istio-system`.

1. Add the Istio Helm repository and confirm that version 1.26.0 charts are available.
2. Install the CRDs and cluster resources only, nothing else.
3. Install the control plane, pinned to 1.26.0, into `istio-system`.
4. Install an ingress gateway named `my-ingress` into a new namespace called `gateways`, exposed as a `NodePort`.
5. Install an egress gateway using the same chart.
6. Install the control plane with access logging to stdout and tracing disabled, using a values file rather than `--set`.
7. Show the values that are actually in effect for the installed `istiod` release, including chart defaults.
8. Upgrade the `istiod` release to change istiod's memory request to 3Gi, without changing anything else.
9. Install a second control plane as revision `1-26-1` alongside the existing one.
10. Roll the `istiod` release back to its previous revision.
11. List every Istio Helm release across all namespaces, with their chart versions.
12. Uninstall everything installed by Helm, in the correct order.

## Solutions

### 1. Add the repo

```bash
helm repo add istio https://istio-release.storage.googleapis.com/charts
helm repo update istio

helm search repo istio/ --version 1.26.0
```

```text
NAME            CHART VERSION   APP VERSION     DESCRIPTION
istio/base      1.26.0          1.26.0          Helm chart for deploying Istio cluster resources
istio/cni       1.26.0          1.26.0          Helm chart for istio-cni components
istio/gateway   1.26.0          1.26.0          Helm chart for deploying Istio gateways
istio/istiod    1.26.0          1.26.0          Helm chart for istio control plane
istio/ztunnel   1.26.0          1.26.0          Helm chart for istio ztunnel
```

If the repo is unreachable, the charts also ship inside the release tarball:

```bash
ls ~/istio-1.26.0/manifests/charts/
# base  gateway  gateways  istio-cni  istio-control  istiod-remote  ztunnel
helm install istio-base ~/istio-1.26.0/manifests/charts/base -n istio-system --create-namespace
```

Worth knowing, because the exam environment may not have internet access to arbitrary hosts.

### 2. CRDs and cluster resources only

```bash
helm install istio-base istio/base \
  -n istio-system \
  --create-namespace \
  --version 1.26.0 \
  --wait
```

Verify:

```bash
kubectl get crd | grep istio.io | wc -l
kubectl get crd | grep istio.io
```

```text
authorizationpolicies.security.istio.io
destinationrules.networking.istio.io
envoyfilters.networking.istio.io
gateways.networking.istio.io
peerauthentications.security.istio.io
proxyconfigs.networking.istio.io
requestauthentications.security.istio.io
serviceentries.networking.istio.io
sidecars.networking.istio.io
telemetries.telemetry.istio.io
virtualservices.networking.istio.io
wasmplugins.extensions.istio.io
workloadentries.networking.istio.io
workloadgroups.networking.istio.io
```

At this point the CRDs exist but nothing is running. `kubectl get pods -n istio-system` is empty. You can create a VirtualService and it will be stored, but nothing will act on it.

The `base` chart also creates the `ValidatingWebhookConfiguration`, so if you install `base` and then never install `istiod`, **creating any Istio resource fails** because the validation webhook has no backend. That is a nasty state and a plausible troubleshooting scenario. Recovery is either installing `istiod` or deleting the webhook config.

### 3. Install the control plane

```bash
helm install istiod istio/istiod \
  -n istio-system \
  --version 1.26.0 \
  --wait
```

Verify:

```bash
kubectl -n istio-system get pods
kubectl -n istio-system get deploy istiod
istioctl version
```

```text
NAME                     READY   STATUS    RESTARTS   AGE
istiod-7d8f9c5b4-x2klm   1/1     Running   0          45s
```

At this stage sidecar injection works. Label a namespace and it takes effect:

```bash
kubectl create namespace demo
kubectl label namespace demo istio-injection=enabled
kubectl -n demo apply -f ~/istio-1.26.0/samples/httpbin/httpbin.yaml
kubectl -n demo get pods   # 2/2
```

There is still **no ingress gateway**. Unlike the `default` profile with `istioctl`, the Helm path never gives you one implicitly.

### 4. Ingress gateway in its own namespace

```bash
kubectl create namespace gateways
kubectl label namespace gateways istio-injection=enabled

helm install my-ingress istio/gateway \
  -n gateways \
  --version 1.26.0 \
  --set service.type=NodePort \
  --set 'service.ports[0].name=status-port' \
  --set 'service.ports[0].port=15021' \
  --set 'service.ports[0].targetPort=15021' \
  --set 'service.ports[0].nodePort=30021' \
  --set 'service.ports[1].name=http2' \
  --set 'service.ports[1].port=80' \
  --set 'service.ports[1].targetPort=80' \
  --set 'service.ports[1].nodePort=30080' \
  --wait
```

**The gateway namespace must have injection enabled.** The `gateway` chart deploys a plain pod and relies on the injection webhook to turn it into an Envoy gateway. Forget the label and you get a pod that starts and does nothing, with no obvious error. This is the single most common Helm gateway mistake.

Verify:

```bash
kubectl -n gateways get pods
kubectl -n gateways get svc my-ingress
kubectl -n gateways get deploy my-ingress -o jsonpath='{.spec.template.spec.containers[*].name}'
```

```text
istio-proxy
```

One container named `istio-proxy`, injected by the webhook. That is what a working gateway looks like.

A values file is much more readable here:

```yaml
# my-ingress-values.yaml
service:
  type: NodePort
  ports:
    - name: status-port
      port: 15021
      targetPort: 15021
      nodePort: 30021
    - name: http2
      port: 80
      targetPort: 80
      nodePort: 30080
    - name: https
      port: 443
      targetPort: 443
      nodePort: 30443
autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 5
```

```bash
helm install my-ingress istio/gateway -n gateways -f my-ingress-values.yaml --wait
```

Then reference it from a `Gateway` resource by its labels:

```yaml
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: my-gw
  namespace: gateways
spec:
  selector:
    istio: my-ingress     # the gateway chart sets istio=<release name>
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "*"
```

Confirm the selector label before relying on it:

```bash
kubectl -n gateways get pod -l istio=my-ingress
kubectl -n gateways get deploy my-ingress -o jsonpath='{.spec.template.metadata.labels}' | jq
```

### 5. Egress gateway from the same chart

The `gateway` chart makes no distinction; an egress gateway is just a gateway with no external Service and a different name.

```bash
helm install my-egress istio/gateway \
  -n gateways \
  --version 1.26.0 \
  --set service.type=ClusterIP \
  --wait
```

```bash
kubectl -n gateways get svc my-egress
kubectl -n gateways get pods -l istio=my-egress
```

`ClusterIP` is right for egress: only in-mesh workloads need to reach it. The direction is decided entirely by the `Gateway` and `VirtualService` resources you point at it, covered in `15.md`.

### 6. Values file with logging and tracing settings

```yaml
# istiod-values.yaml
meshConfig:
  accessLogFile: /dev/stdout
  accessLogEncoding: JSON
  enableTracing: false
pilot:
  resources:
    requests:
      cpu: 500m
      memory: 2048Mi
  autoscaleMin: 2
  autoscaleMax: 5
global:
  logAsJson: true
```

```bash
helm install istiod istio/istiod \
  -n istio-system \
  --version 1.26.0 \
  -f istiod-values.yaml \
  --wait
```

Verify:

```bash
kubectl -n istio-system get cm istio -o jsonpath='{.data.mesh}' \
  | grep -E 'accessLog|enableTracing'
kubectl -n istio-system get hpa istiod
```

Note the Helm-specific naming: it is `pilot.autoscaleMin`, not `components.pilot.k8s.hpaSpec.minReplicas`. Same outcome, different key, and this is exactly the sort of detail that costs time if you have only ever used one install path.

### 7. Effective values including defaults

```bash
# Only what you supplied
helm get values istiod -n istio-system

# Everything, defaults merged in
helm get values istiod -n istio-system --all

# The chart's defaults alone
helm show values istio/istiod --version 1.26.0
```

The `--all` form is the one that answers "what is actually configured", and it is long, so filter:

```bash
helm get values istiod -n istio-system --all -o yaml | grep -A20 meshConfig
```

To see the rendered Kubernetes objects:

```bash
helm get manifest istiod -n istio-system | grep '^kind:' | sort | uniq -c
```

And to preview without installing, the Helm equivalent of `istioctl manifest generate`:

```bash
helm template istiod istio/istiod -n istio-system --version 1.26.0 -f istiod-values.yaml
```

### 8. Change one value without losing the others

```bash
helm upgrade istiod istio/istiod \
  -n istio-system \
  --version 1.26.0 \
  --reuse-values \
  --set pilot.resources.requests.memory=3Gi \
  --wait
```

**`--reuse-values` is the critical flag.** Without it, Helm resets everything you are not currently passing back to chart defaults, exactly like the `istioctl install` trap in `02.md`. With it, your previous values are carried forward and only the new key changes.

Verify:

```bash
kubectl -n istio-system get deploy istiod \
  -o jsonpath='{.spec.template.spec.containers[0].resources.requests}'
helm get values istiod -n istio-system
```

```json
{"cpu":"500m","memory":"3Gi"}
```

The more robust approach, and the one to prefer in real life, is to keep the values file authoritative and always pass it:

```bash
# edit istiod-values.yaml, then
helm upgrade istiod istio/istiod -n istio-system -f istiod-values.yaml --wait
```

That way there is no hidden state and no `--reuse-values` to forget.

### 9. A second control plane as a revision

Canary upgrades are `07.md`, but the Helm mechanics belong here. A revisioned install gets a **different release name** and a `revision` value:

```bash
helm install istiod-1-26-1 istio/istiod \
  -n istio-system \
  --version 1.26.1 \
  --set revision=1-26-1 \
  --wait
```

Now both control planes run side by side:

```bash
kubectl -n istio-system get pods
```

```text
NAME                              READY   STATUS
istiod-7d8f9c5b4-x2klm            1/1     Running
istiod-1-26-1-6c9d8f7a5-mn3pq     1/1     Running
```

```bash
kubectl -n istio-system get deploy
istioctl tag list
kubectl get mutatingwebhookconfiguration | grep sidecar
```

```text
istio-sidecar-injector
istio-sidecar-injector-1-26-1
```

Two webhooks, each selecting different namespaces. Workloads follow whichever revision their namespace label names:

```bash
kubectl label namespace demo istio-injection- --overwrite
kubectl label namespace demo istio.io/rev=1-26-1 --overwrite
kubectl -n demo rollout restart deploy/httpbin
istioctl proxy-status | grep httpbin
```

The `revision` value must be a valid DNS label, so use `1-26-1`, not `1.26.1`. Dots are rejected and the error message is not especially clear.

### 10. Roll back

```bash
helm history istiod -n istio-system
```

```text
REVISION  UPDATED       STATUS      CHART          APP VERSION  DESCRIPTION
1         Mon Aug 19..  superseded  istiod-1.26.0  1.26.0       Install complete
2         Mon Aug 19..  deployed    istiod-1.26.0  1.26.0       Upgrade complete
```

```bash
helm rollback istiod 1 -n istio-system --wait
helm history istiod -n istio-system
kubectl -n istio-system get deploy istiod \
  -o jsonpath='{.spec.template.spec.containers[0].resources.requests}'
```

Rollback creates a **new** revision that reproduces the old state; it does not delete history. So revision 3 appears, describing "Rollback to 1".

Note the terminology clash that trips people up: a **Helm revision** is a release version number, while an **Istio revision** is a control plane instance name. They are unrelated concepts that share a word.

### 11. List all Istio releases

```bash
helm list -A
```

```text
NAME            NAMESPACE       REVISION  CHART           APP VERSION
istio-base      istio-system    1         base-1.26.0     1.26.0
istiod          istio-system    2         istiod-1.26.0   1.26.0
my-egress       gateways        1         gateway-1.26.0  1.26.0
my-ingress      gateways        1         gateway-1.26.0  1.26.0
```

Filtered and formatted:

```bash
helm list -A -o json | jq -r '.[] | select(.chart | startswith("base") or startswith("istiod") or startswith("gateway") or startswith("cni") or startswith("ztunnel")) | "\(.namespace)/\(.name)\t\(.chart)\t\(.status)"'
```

### 12. Uninstall in the right order

Reverse of installation. Gateways first, control plane next, base last.

```bash
# 1. Gateways
helm uninstall my-ingress -n gateways
helm uninstall my-egress -n gateways

# 2. ztunnel and CNI, if installed
helm uninstall ztunnel -n istio-system 2>/dev/null
helm uninstall istio-cni -n istio-system 2>/dev/null

# 3. Control plane, all revisions
helm uninstall istiod-1-26-1 -n istio-system 2>/dev/null
helm uninstall istiod -n istio-system

# 4. Base, last
helm uninstall istio-base -n istio-system

# 5. Namespaces
kubectl delete namespace istio-system gateways
```

**`helm uninstall istio-base` does not delete the CRDs.** Helm deliberately leaves CRDs behind to avoid destroying data, so remove them explicitly if you want a truly clean slate:

```bash
kubectl get crd -o name | grep istio.io | xargs -r kubectl delete
```

Confirm:

```bash
helm list -A | grep -i istio
kubectl get crd | grep istio.io
kubectl get ns | grep istio
```

All empty.

## Exam Tips

**Order is mandatory: `base`, then `istiod`, then gateways.** If you see `no matches for kind "VirtualService"` or `unable to recognize`, you skipped `base`.

**The gateway namespace needs `istio-injection=enabled`.** The `gateway` chart produces an uninjected pod otherwise, and it fails silently. Whenever a Helm-installed gateway "does nothing", check that label first, then confirm the pod has an `istio-proxy` container.

**`--reuse-values` on every `helm upgrade`, or pass the full values file.** Same failure mode as re-running `istioctl install` with partial flags: everything you omit silently reverts.

**Pin `--version 1.26.0` on every command.** Without it Helm installs the newest chart in the repo, which will not match the exam's control plane and can produce a version-skew mess.

**`--wait` saves you from checking twice.** It blocks until pods are ready, so a failure surfaces immediately rather than three commands later.

**The Helm value names are flatter than IstioOperator's.** `pilot.resources` not `components.pilot.k8s.resources`. `pilot.autoscaleMin` not `hpaSpec.minReplicas`. When a `--set` seems to do nothing, check with `helm show values istio/istiod` rather than guessing.

**`meshConfig` is spelled identically in both worlds.** So anything to do with mesh behaviour transfers between install methods unchanged, which is a useful anchor.

**`helm template` is the Helm answer to "render without applying".** The `istioctl` equivalent is `istioctl manifest generate`.

**Uninstalling `base` leaves the CRDs.** Deliberate, and the opposite of `istioctl uninstall --purge`. Know both behaviours, because a task saying "remove Istio completely" needs the extra CRD deletion step on the Helm path.
