# 20. Fix Privilege Escalation And Writable Root Filesystem

**Domain:** Minimize Microservice Vulnerabilities

## Question

A Deployment named `worker` in namespace `cks-20` is allowed to escalate privileges and writes to the root filesystem. Harden it while preserving writable `/tmp`.

## Answer

Export:

```bash
kubectl get deployment worker -n cks-20 -o yaml > worker.yaml
```

Edit the pod template:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: worker
  namespace: cks-20
spec:
  template:
    spec:
      volumes:
      - name: tmp
        emptyDir: {}
      containers:
      - name: worker
        volumeMounts:
        - name: tmp
          mountPath: /tmp
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          capabilities:
            drop:
            - ALL
          seccompProfile:
            type: RuntimeDefault
```

Apply:

```bash
kubectl apply -f worker.yaml
kubectl rollout status deployment/worker -n cks-20
```

## Verify

```bash
kubectl get deployment worker -n cks-20 -o jsonpath='{.spec.template.spec.containers[0].securityContext}'; echo
kubectl get deployment worker -n cks-20 -o jsonpath='{.spec.template.spec.volumes}'; echo
```

Test writable `/tmp`:

```bash
POD=$(kubectl get pod -n cks-20 -l app=worker -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n cks-20 $POD -- sh -c 'touch /tmp/ok && echo ok'
```

## Exam tips

- `allowPrivilegeEscalation: false` blocks setuid-style escalation.
- `readOnlyRootFilesystem: true` is safer, but many apps need `/tmp`.
- `emptyDir` is a common quick fix for writable temporary storage.
