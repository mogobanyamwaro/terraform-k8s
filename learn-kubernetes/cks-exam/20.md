# 20. Fix Privilege Escalation And Writable Root Filesystem

**Domain:** Minimize Microservice Vulnerabilities

## Question

A Deployment named `worker` in namespace `cks-20` is allowed to escalate privileges and writes to the root filesystem. Harden it while preserving writable `/tmp`.

## Answer

Export:

```bash
kubectl get deployment worker -n cks-20 -o yaml > worker.yaml
```

Edit the pod template:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: worker
  namespace: cks-20
spec:
  template:
    spec:
      volumes:
      - name: tmp
        emptyDir: {}
      containers:
      - name: worker
        volumeMounts:
        - name: tmp
          mountPath: /tmp
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          capabilities:
            drop:
            - ALL
          seccompProfile:
            type: RuntimeDefault
```

Apply:

```bash
kubectl apply -f worker.yaml
kubectl rollout status deployment/worker -n cks-20
```

## Verify

```bash
kubectl get deployment worker -n cks-20 -o jsonpath='{.spec.template.spec.containers[0].securityContext}'; echo
kubectl get deployment worker -n cks-20 -o jsonpath='{.spec.template.spec.volumes}'; echo
```

Test writable `/tmp`:

```bash
POD=$(kubectl get pod -n cks-20 -l app=worker -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n cks-20 $POD -- sh -c 'touch /tmp/ok && echo ok'
```

## Exam tips

- `allowPrivilegeEscalation: false` blocks setuid-style escalation.
- `readOnlyRootFilesystem: true` is safer, but many apps need `/tmp`.
- `emptyDir` is a common quick fix for writable temporary storage.

---
This is a classic **Kubernetes container hardening** question. It is asking you to fix **two security problems** while making sure `/tmp` remains writable.

### The two problems

The existing Deployment probably has something like:

```yaml
securityContext:
  allowPrivilegeEscalation: true
```

and:

```yaml
securityContext:
  readOnlyRootFilesystem: false
```

The question says:

> **"is allowed to escalate privileges"**

So you need:

```yaml
allowPrivilegeEscalation: false
```

This prevents a process inside the container from gaining additional Linux privileges through mechanisms such as setuid/setgid binaries.

---

### 2. Make the root filesystem read-only

The question says:

> **"writes to the root filesystem"**

You need:

```yaml
readOnlyRootFilesystem: true
```

Now:

```text
Container filesystem
       |
       +── /etc      ❌
       +── /usr      ❌
       +── /var      ❌
       +── /app      ❌
       |
       +── /tmp      ✅
```

But there's a problem:

**`readOnlyRootFilesystem: true` also makes `/tmp` read-only.**

That's why the question explicitly says:

> **"while preserving writable `/tmp`."**

---

# How do you keep `/tmp` writable?

You mount an **`emptyDir` volume** at `/tmp`.

```yaml
volumes:
- name: tmp
  emptyDir: {}
```

Then mount it:

```yaml
volumeMounts:
- name: tmp
  mountPath: /tmp
```

Now you get:

```text
Container
│
├── Root filesystem
│     └── 🔒 Read-only
│
└── /tmp
      └── ✍️ Writable
          (emptyDir)
```

---

# The resulting security configuration

You might end up with something like:

```yaml
spec:
  containers:
  - name: worker
    image: ...

    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true

    volumeMounts:
    - name: tmp
      mountPath: /tmp

  volumes:
  - name: tmp
    emptyDir: {}
```

### Notice where things go

`securityContext`:

```text
container
└── securityContext
    ├── allowPrivilegeEscalation
    └── readOnlyRootFilesystem
```

`volumeMounts`:

```text
container
└── volumeMounts
    └── /tmp
```

`volumes`:

```text
Pod spec
└── volumes
    └── emptyDir
```

---

## What is the security improvement?

Before:

```text
Worker container
│
├── Can escalate privileges ❌
└── Can write to root filesystem ❌
```

After:

```text
Worker container
│
├── Privilege escalation → ❌
│
├── Root filesystem → 🔒 READ ONLY
│
└── /tmp → ✍️ WRITABLE
```

This is a very common CKS pattern:

> **`allowPrivilegeEscalation: false` + `readOnlyRootFilesystem: true` + `emptyDir` for directories the application legitimately needs to write to.**

One subtle point: `readOnlyRootFilesystem` is a **container-level** setting, so put it under the container's `securityContext`, not the Pod-level `securityContext`.
