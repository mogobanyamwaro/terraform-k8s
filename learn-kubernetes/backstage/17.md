# 17. Frontend vs Backend Plugins

**Domain:** Customizing Backstage (32%)

## Concept Refresher

A **plugin** extends the portal. Most features are a **pair**:

| Side | Package (typical) | Runs in | May hold |
| --- | --- | --- | --- |
| **Frontend** | `@backstage/plugin-foo` | Browser (React) | Routes, entity cards/tabs, pages |
| **Backend** | `@backstage/plugin-foo-backend` | Node (`packages/backend`) | Tokens, GitHub/k8s API, DB |

Frontend plugins **must not** embed production secrets. They call `/api/...` on the backend.

Some plugins are UI-only (a static page). Some are backend-only (a processor/provider). CBA: **know which side you install and register.**

Core plugins shipped with create-app: catalog, scaffolder, techdocs, search, auth, permission, kubernetes (often added), GitHub Actions, etc.

Writing a **new** plugin package from zero is **out of exam scope**. Installing and wiring **is** in scope.

## Exam tips

- Empty plugin tab → missing backend or annotation, not “React is broken”.
