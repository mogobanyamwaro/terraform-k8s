# Section 2 (Deep Dive): The TCP/IP Stack & Encapsulation

You cannot troubleshoot what you cannot see. Every network problem in cloud/K8s is really an **encapsulation** or **decapsulation** problem.

## 2.1 The 5 Layers (Not 7—for cloud/K8s, 5 is enough)

| Layer | Name        | What lives here            | Example          | Your pain point                   |
| ----- | ----------- | -------------------------- | ---------------- | --------------------------------- |
| 5     | Application | Your data                  | HTTP, gRPC, DNS  | Misconfigured endpoints           |
| 4     | Transport   | Ports, reliability         | TCP, UDP         | `Connection refused` vs `Timeout` |
| 3     | Network     | Routing, IPs               | IPv4, IPv6, ICMP | Wrong routes, missing NAT         |
| 2     | Data Link   | MAC addresses, same subnet | Ethernet, ARP    | Can't reach same subnet hosts     |
| 1     | Physical    | Cables, wifi               | Fiber, radio     | Rarely your fault in cloud        |

**Golden rule for debugging:**

> "Work your way down. If Layer 3 fails, check Layer 2. If Layer 4 fails, check Layer 3."

## 2.2 Encapsulation (The Russian Doll Model)

When you `curl http://10.244.1.23:8080/api`:

```
[ETHERNET header | IP header | TCP header | HTTP header | "GET /api" ]
     ↑              ↑            ↑            ↑           ↑
   Layer 2        Layer 3      Layer 4      Layer 5      Payload
```

**Why this matters in Kubernetes:**

- **CNI plugins** add **overlay headers** (VXLAN, IPIP) between Layer 2 and 3
- **Service Mesh** (Istio) adds another Layer 5 proxy between apps
- **Network Policy** (Calico/Cilium) looks at all layers to allow/deny

**Real K8s example** (pod-to-pod across nodes with Flannel VXLAN):

```
Original:   [Pod-ETH | Pod-IP | TCP | App-Data]
After VXLAN: [Node-ETH | Node-IP | UDP | VXLAN-hdr | Pod-ETH | Pod-IP | TCP | App-Data]
                      ↑                              ↑
                 Outer (underlay)              Inner (overlay)
```

If you don't understand encapsulation, you'll never debug `Connection timed out` vs `No route to host`.

## 2.3 TCP Deep Dive (Your cloud apps rely on this)

### The Three-Way Handshake (Every connection)

```
Client (10.0.1.5:54321) --- SYN (seq=100) ----------> Server (10.0.2.10:80)
Client <--- SYN-ACK (seq=200, ack=101) --- Server
Client --- ACK (ack=201) -------------------> Server
# Now data flows
```

**What this means for you:**

- `Connection refused` → Server got SYN, no process listening on that port (Layer 4)
- `Connection timed out` → SYN never reached server or SYN-ACK never returned (Layer 3 routing, firewall, or overloaded server)
- `Connection reset` → Established connection got RST packet (process crashed, firewall enforced policy)

### TCP Socket States You WILL See (via `ss` or `netstat`)

| State         | Meaning                                   | Why you care                                              |
| ------------- | ----------------------------------------- | --------------------------------------------------------- |
| `LISTEN`      | Process waiting for incoming              | Your K8s Service is working                               |
| `ESTABLISHED` | Active conversation                       | Normal traffic flow                                       |
| `TIME_WAIT`   | Closed locally, waiting for stray packets | Too many = exhausted ports (tune `net.ipv4.tcp_tw_reuse`) |
| `CLOSE_WAIT`  | Remote closed, local hasn't closed        | App bug (not closing sockets)                             |
| `SYN_RECV`    | Received SYN, waiting for ACK             | Backlog full or DDoS                                      |

**Run this NOW on any Linux server:**

```bash
ss -tan | awk '{print $1}' | sort | uniq -c
```

## 2.4 UDP (DNS, VPN, VXLAN, Media Streaming)

No handshake. No guarantee. No retransmit.

**Why cloud/K8s uses UDP heavily:**

- **DNS** (port 53) - one query, one response
- **VXLAN** (port 8472) - pod overlay networks
- **WireGuard/IPsec VPNs** - faster than TCP-over-TCP
- **NodePort health checks** - some cloud LBs use UDP probes

**Debugging UDP is hard** because `telnet` doesn't work. Use:

```bash
# Send test UDP packet
echo "test" | nc -u 10.0.0.5 53

# Capture response (if any)
sudo tcpdump -i eth0 udp port 53
```

# Section 3: ARP & MAC Addresses (The Layer 2 You Ignore at Your Peril)

Most cloud engineers skip this. Then they can't debug "same subnet ping fails, but different subnet works."

## 3.1 The Truth About IP Addresses

**IP addresses are just labels. You cannot send a packet to an IP without knowing its MAC address.**

- **MAC address** = factory-burned hardware ID (e.g., `aa:bb:cc:11:22:33`)
- **IP address** = logical location

## 3.2 ARP (Address Resolution Protocol) - "Who has this IP?"

When computer A (10.0.0.5) wants to talk to computer B (10.0.0.10) on the **same subnet**:

```
A: "Who has 10.0.0.10? Tell 10.0.0.5 (MAC aa:aa:aa:aa:aa:aa)"
   [Broadcast to all on subnet]

B: "I have 10.0.0.10. My MAC is bb:bb:bb:bb:bb:bb"

A: [Stores in ARP cache: 10.0.0.10 = bb:bb:bb:bb:bb:bb]
A: Now sends real packet to MAC bb:bb:bb:bb:bb:bb
```

## 3.3 ARP in Linux (Check this NOW)

```bash
# View ARP cache
ip neigh show
# or
arp -n

# Sample output:
# 192.168.1.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE
# 192.168.1.10 dev eth0 lladdr 11:22:33:44:55:66 STALE
```

**States:**

- `REACHABLE` - recently confirmed alive
- `STALE` - expired, need to re-ARP
- `FAILED` - no response, unreachable

## 3.4 The Kubernetes ARP Horror Story

**Problem:** Pods on same node can't ping each other, but pods across nodes work.

**Diagnosis:**

```bash
# Inside pod1
ip neigh show
# Shows pod2's IP with FAILED state
```

**Root cause:** CNI plugin didn't program the Linux bridge properly. The bridge had no ARP entry for pod2.

**Fix:** Restart CNI or check bridge config:

```bash
brctl show
bridge fdb show br0
```

## 3.5 Proxy ARP (Cloud & K8s use this)

Normally, ARP only answers for IPs on the same subnet. **Proxy ARP** answers for IPs on **different subnets**.

**Used in:**

- **AWS VPC** - Instances respond to ARP for their own IPs only, not the whole subnet
- **Flannel host-gw** - Nodes proxy ARP for pod IPs
- **kube-ipvs** - Load balancer IPs answered via ARP

# Section 4: NAT (Network Address Translation) - The Cloud's Dirty Secret

Without NAT, we'd have run out of IPv4 addresses years ago. **Every cloud private subnet uses NAT.**

## 4.1 Types of NAT You Must Know

| Type            | Abbr | Direction                               | Example                                        | Cloud use              |
| --------------- | ---- | --------------------------------------- | ---------------------------------------------- | ---------------------- |
| Source NAT      | SNAT | Private → Public changes source IP      | Home router                                    | Private EC2 → Internet |
| Destination NAT | DNAT | Public → Private changes destination IP | Port forwarding                                | K8s NodePort           |
| Masquerade      | MASQ | Dynamic SNAT (IP not fixed)             | `iptables -t nat -A POSTROUTING -j MASQUERADE` | K8s pods → outside     |

## 4.2 How NAT Works (The Table You Never See)

When your laptop (192.168.1.5:54321) talks to Google (8.8.8.8:443):

1. **Before NAT (inside your network):** SRC=192.168.1.5:54321, DST=8.8.8.8:443
2. **NAT Router creates entry:** `192.168.1.5:54321` ↔ `1.2.3.4:12345` (your public IP:random port)
3. **After NAT (on internet):** SRC=1.2.3.4:12345, DST=8.8.8.8:443
4. **Google replies:** SRC=8.8.8.8:443, DST=1.2.3.4:12345
5. **NAT Router looks up table:** `1.2.3.4:12345` maps back to `192.168.1.5:54321`
6. **Forward to your laptop**

## 4.3 The Kubernetes NAT Explosion

**Problem:** Every pod-to-service connection creates a NAT entry. 10,000 pods = 10,000 conntrack entries.

**Symptoms:**

- `nf_conntrack: table full, dropping packet`
- Intermittent connection failures
- High CPU on `kube-proxy` nodes

**Fix options:**

```bash
# Increase conntrack table size
sysctl -w net.netfilter.nf_conntrack_max=524288

# Or switch kube-proxy to IPVS mode (no per-connection NAT)
kubectl edit configmap -n kube-system kube-proxy
# Change mode: "ipvs"
```

## 4.4 View NAT Table on Linux (Conntrack)

```bash
# See all NAT entries (need root)
sudo conntrack -L

# Count established connections
sudo conntrack -L | wc -l

# Watch real-time NAT table changes
sudo conntrack -E
```

# Section 5: Routes & The Default Gateway (Traffic Direction)

## 5.1 The Routing Decision Logic

For every packet, Linux does this:

```
If destination IP is on same subnet (check routing table):
    Send directly via ARP (Layer 2)
Else:
    Send to default gateway (or matching route)
```

## 5.2 Reading Routing Tables (Critical Skill)

```bash
ip route show
# or
route -n
```

Example:

```
default via 10.0.1.1 dev eth0
10.0.1.0/24 dev eth0 proto kernel scope link src 10.0.1.5
172.17.0.0/16 dev docker0 proto kernel scope link src 172.17.0.1
```

**Interpretation:**

1. `default via 10.0.1.1` = Any IP not matching below, send to 10.0.1.1 (your router)
2. `10.0.1.0/24 dev eth0` = If destination IP starts with 10.0.1.x, send directly out eth0
3. `172.17.0.0/16 dev docker0` = Docker containers route via docker0 bridge

## 5.3 Policy-Based Routing (Advanced, but used in K8s)

Sometimes you need **different routes for different source IPs**.

```bash
# Create a new routing table (table 100)
echo "100 mytable" >> /etc/iproute2/rt_tables

# Add route: traffic from 10.0.1.100 uses 192.168.1.1 as gateway
ip rule add from 10.0.1.100 table mytable
ip route add default via 192.168.1.1 dev eth1 table mytable
```

**Used in K8s for:**

- **Calico BGP peering** - different routes for pod traffic vs node traffic
- **Multus (multiple interfaces)** - pod has separate routing table per NIC

# Section 6: Bridge & VETH Pairs (Container Networking)

This is **the missing link** between Linux networking and Kubernetes.

## 6.1 What is a Linux Bridge?

A **software switch**. Same as a physical network switch but in the kernel.

```bash
# See bridges
brctl show
# or
bridge link show
```

## 6.2 VETH Pairs (Virtual Ethernet Cable)

A **veth pair** is like a tube: anything sent in one end comes out the other.

```
Namespace A (pod)          Host (node)
   eth0@if15  ----------  veth12345@if16 (plugged into bridge)
```

**Creating one manually (do this now to understand pods):**

```bash
# Create veth pair
sudo ip link add veth-host type veth peer name veth-pod

# Move one end to a new network namespace (like a pod)
sudo ip netns add pod-ns
sudo ip link set veth-pod netns pod-ns

# Give IP to pod end
sudo ip netns exec pod-ns ip addr add 10.244.1.10/24 dev veth-pod
sudo ip netns exec pod-ns ip link set veth-pod up

# Plug host end into bridge
sudo ip link set veth-host master cni-bridge
sudo ip link set veth-host up
```

**Now that veth pair acts exactly like a pod attached to a bridge.**

## 6.3 How a Kubernetes Pod Gets Its Network

1. kubelet calls CNI plugin (Calico/Flannel/Weave)
2. CNI creates **veth pair**
3. One end in pod's network namespace (becomes `eth0`)
4. Other end plugged into `cni-bridge` on node
5. CNI assigns pod IP from cluster CIDR
6. CNI adds routes on node: `10.244.x.x/32 via bridge`

# Section 7: Overlay Networks (How Pods Span Nodes)

Without overlays, pods on different nodes couldn't talk unless:

- All nodes share same L2 subnet (impossible in cloud)
- You run BGP (Calico can do this)

**Overlay solution:** Encapsulate pod packet inside node packet.

## 7.1 VXLAN (Most common in K8s)

- Outer header: Node IPs (routable in your VPC)
- Inner header: Pod IPs (cluster-private)
- UDP port 8472

```
[Node-ETH | Node-IP | UDP:8472 | VXLAN-hdr | Pod-ETH | Pod-IP | TCP | App]
     ↑                      ↑                                ↑
  Underlay              Tunnel                          Overlay
```

**View VXLAN interface:**

```bash
ip -d link show flannel.1
# or
bridge vxlan show
```

## 7.2 IPIP (Simpler, less overhead)

No UDP. Just wrap pod IP in node IP with IP protocol 4.

```
[Node-IP | IPIP-hdr | Pod-IP | TCP | App]
```

**Used by:** Calico (in IPIP mode), older Flannel

## 7.3 Host Gateway (No overlay, fastest)

```
Node A (10.240.0.5) ------ route added -----> Node B (10.240.0.6)
Pod10.244.1.5                              Pod10.244.2.8
```

Node A has route: `10.244.2.0/24 via 10.240.0.6 dev eth0`

**Limitation:** All nodes must be on same L2 subnet (rare in cloud multi-AZ).

# Section 8: Network Policies (K8s Firewall)

**Security Groups for pods.** But `kubectl apply -f networkpolicy.yaml` doesn't create iptables rules on your node directly—the CNI does.

## 8.1 Simple NetworkPolicy Example

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-nginx
spec:
  podSelector:
    matchLabels:
      app: nginx
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: api
      ports:
        - protocol: TCP
          port: 80
```

**What this means:** Only pods with label `app:api` can talk to nginx pods on port 80. All other traffic denied.

## 8.2 How Different CNIs Implement NetworkPolicy

| CNI     | Implementation                                | Debug command                 |
| ------- | --------------------------------------------- | ----------------------------- |
| Calico  | eBPF or iptables (Felix agent)                | `calicoctl get networkpolicy` |
| Cilium  | eBPF (kernel bytecode)                        | `cilium endpoint list`        |
| Weave   | iptables + userspace                          | `weave status`                |
| Flannel | No network policy (needs Calico/Cilium addon) | N/A                           |

## 8.3 Debugging NetworkPolicy (Critical Skill)

When policy blocks traffic:

```bash
# Check if policy exists
kubectl get networkpolicy -A

# Describe the policy
kubectl describe networkpolicy allow-nginx

# On the node hosting the pod, check iptables (Calico)
sudo iptables -L -n | grep -i calico

# Check cilium (if using Cilium)
cilium policy get
```

**Most common mistake:** `podSelector` without `namespaceSelector` when pods are in different namespaces.

# Section 9: Your Daily Debugging Workflow (For Cloud, Linux, K8s)

When something doesn't connect, follow this **exact order**:

## Phase 1: Is it Layer 4 (Port) or Layer 3 (Routing)?

```bash
# Test port connectivity (TCP)
nc -zv 10.244.1.23 8080

# Test ICMP (Layer 3)
ping -c 3 10.244.1.23

# If ping works but nc fails → Layer 4 problem (firewall, not listening)
# If ping fails → Layer 3 problem (routing, CNI, overlay)
```

## Phase 2: Check local routing table

```bash
ip route get 10.244.1.23
# Shows which interface and gateway it would use
```

## Phase 3: Check ARP (if same subnet)

```bash
ip neigh show 10.244.1.23
# If FAILED or INCOMPLETE, L2 is broken
```

## Phase 4: Trace the path

```bash
traceroute -n 10.244.1.23
# See where packets stop
```

## Phase 5: Capture actual packets

```bash
sudo tcpdump -i any -n host 10.244.1.23
# Then reproduce the failure
```

## Phase 6: Check conntrack (if NAT involved)

```bash
sudo conntrack -L | grep 10.244.1.23
```

## Phase 7 (K8s specific): Check if kube-proxy rules exist

```bash
# On any node
sudo iptables -t nat -L KUBE-SERVICES -n | grep <service-ip>
```

# Section 10: IPv6 in Cloud & K8s (The Future You Can't Ignore)

IPv6 is not optional anymore. AWS EKS, GKE, and AKS all support IPv6-only or dual-stack.

## 10.1 IPv6 Simplified

- **128 bits** (vs 32 bits in IPv4)
- Written as 8 groups of 4 hex digits: `2001:0db8:85a3:0000:0000:8a2e:0370:7334`
- Leading zeros omitted: `2001:db8:85a3::8a2e:370:7334`
- `::` = one or more groups of zeros

## 10.2 Important IPv6 Addresses

| IPv6 address | Meaning                     | IPv4 equivalent  |
| ------------ | --------------------------- | ---------------- |
| `::1`        | localhost                   | `127.0.0.1`      |
| `::`         | Unspecified (listen all)    | `0.0.0.0`        |
| `fe80::/10`  | Link-local (autoconfigured) | `169.254.x.x`    |
| `fd00::/8`   | Unique Local (private)      | `10.0.0.0/8` etc |
| `2000::/3`   | Global unicast (public)     | Public IPv4      |

## 10.3 K8s IPv6 Example

```yaml
# Pod with IPv6 address
apiVersion: v1
kind: Pod
metadata:
  name: ipv6-pod
spec:
  containers:
    - name: app
      command: ["sleep", "3600"]
      image: busybox
```

After creation:

```bash
kubectl exec ipv6-pod -- ip -6 addr show
# Likely see fd00:xxxx or 2001:xxxx
```

**Key difference in K8s:** Services get both IPv4 ClusterIP and IPv6 ClusterIP if dual-stack.
