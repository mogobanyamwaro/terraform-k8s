# Section 1: The Absolute Basics (No fluff)

Before CIDR and Kubernetes, you must understand **what an IP address actually is**.

### 1.1 Every computer is a house.

- **IP Address** = Street address of the house (e.g., `192.168.1.10`)
- **Port** = Specific door/window of the house (e.g., door #80 for web, door #22 for SSH)
- **Protocol** = Language used (TCP = reliable, certified mail; UDP = shouting, no confirmation)

### 1.2 IPv4 Addresses are just 32-bit numbers.

Humans write them as **dotted decimal** (`192.168.0.1`), but computers see 32 binary bits:

`192.168.0.1` in binary = `11000000.10101000.00000000.00000001`

**Memorize this table (it will save you):**
| Bit position | 8 | 7 | 6 | 5 | 4 | 3 | 2 | 1 |
|---|---|---|---|---|---|---|---|---|
| Value if bit=1 | 128 | 64 | 32 | 16 | 8 | 4 | 2 | 1 |

Practice: `192` = `128+64` → bits 8 and 7 are 1.

### 1.3 Two types of IPs you must know today:

| Concept        | What it means                                  | Example                              |
| -------------- | ---------------------------------------------- | ------------------------------------ |
| **Public IP**  | Unique on the entire internet                  | 8.8.8.8 (Google DNS)                 |
| **Private IP** | Only valid inside your home/cloud/office       | 192.168.x.x, 10.x.x.x, 172.16-31.x.x |
| **localhost**  | This current computer only                     | 127.0.0.1 (IPv4) or ::1 (IPv6)       |
| **0.0.0.0**    | "Listen on every available IP on this machine" | Used in servers                      |

### 1.4 Ports you will see daily in cloud/k8s/Linux:

| Port        | Service        | What you do with it            |
| ----------- | -------------- | ------------------------------ |
| 22          | SSH            | Remotely control Linux servers |
| 53          | DNS            | Convert `google.com` to IP     |
| 80          | HTTP           | Unencrypted web traffic        |
| 443         | HTTPS          | Encrypted web traffic          |
| 2379-2380   | etcd           | Kubernetes brain               |
| 6443        | kube-apiserver | Talk to Kubernetes             |
| 30000-32767 | NodePorts      | Kubernetes exposes apps        |

# Section 2: CIDR (Classless Inter-Domain Routing) — Your main pain point

CIDR is simple but poorly explained. Let me fix that.

### 2.1 The problem CIDR solves

Imagine you own 256 houses. Without CIDR, you'd write:
`192.168.1.0`, `192.168.1.1`, `192.168.1.2` ... up to `192.168.1.255`. That's tiring.

CIDR says: _Just tell me the starting address and how many houses._

### 2.2 The CIDR formula: `IP/PREFIX`

Example: `192.168.1.0/24`

- `/24` means: **The first 24 bits are fixed (network part). The rest (8 bits) are for hosts.**
- 8 free bits → 2^8 = 256 addresses.

So `192.168.1.0/24` = `192.168.1.0` to `192.168.1.255`.

### 2.3 The most important CIDR table (save this):

| CIDR | Subnet Mask     | Total IPs  | Usable IPs\* | For                       |
| ---- | --------------- | ---------- | ------------ | ------------------------- |
| /32  | 255.255.255.255 | 1          | 1            | A single specific machine |
| /30  | 255.255.255.252 | 4          | 2            | Point-to-point links      |
| /29  | 255.255.255.248 | 8          | 6            | Small cloud subnets       |
| /24  | 255.255.255.0   | 256        | 254          | Typical home/office LAN   |
| /16  | 255.255.0.0     | 65,536     | 65,534       | Cloud VPC (AWS/GCP)       |
| /12  | 255.240.0.0     | 1,048,576  | ~1M          | Large private networks    |
| /8   | 255.0.0.0       | 16,777,216 | ~16M         | Huge orgs (rare)          |

_\*Usable = total minus Network address (first) and Broadcast address (last)_

### 2.4 Network Address, Broadcast, and Default Gateway — demystified

Given `10.0.0.0/24`:

- **Network address** = `10.0.0.0` (identifies the subnet itself)
- **Default Gateway** = Usually `10.0.0.1` (the router that leaves the subnet)
- **Broadcast** = `10.0.0.255` (send to every host on subnet)

You cannot assign `.0` or `.255` to a real computer.

### 2.5 Cloud + Kubernetes examples you WILL see:

- **AWS VPC**: `10.0.0.0/16` (gives you 65k IPs)
- **Subnet for public web**: `10.0.1.0/24`
- **Subnet for databases**: `10.0.2.0/24`
- **K8s Pod CIDR**: `192.168.0.0/16` (each pod gets a real IP)
- **K8s Service CIDR**: `10.96.0.0/12` (virtual IPs for internal load balancing)

3. Can `10.0.0.0/8` and `10.1.0.0/16` exist in the same network? Why/why not?

# Section 3: The Linux Networking Toolbelt (Hands-on)

You must run these commands on a Linux VM (or WSL2, or Mac terminal with `brew install iproute2`).

### 3.1 See IPs & interfaces

```bash
ip addr show
# or the old way
ifconfig -a
```

Look for `eth0`, `ens5`, or `wlan0`. See `inet 192.168.1.5/24` → That's your IP + CIDR.

### 3.2 See routing table (how traffic leaves)

```bash
ip route show
```

Output like:

```
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.5
```

- `default via` = Your default gateway (where unknown traffic goes)
- `192.168.1.0/24 dev eth0` = Any IP in that range goes out eth0 directly

### 3.3 See what ports are listening (critical for k8s debugging)

```bash
ss -tlnp
# t = TCP, l = listening, n = numeric no DNS, p = process
```

Example output:

```
LISTEN 0.128  0.0.0.0:22    0.0.0.0:*    users:(("sshd",pid=123))
```

Means: SSH listening on all IPv4 addresses (0.0.0.0) port 22.

### 3.4 See active connections

```bash
ss -tnp | grep ESTAB
```

### 3.5 Trace the path packets take

```bash
traceroute google.com   # uses UDP by default
tracepath google.com    # better without root
```

### 3.6 Capture packets (huge for k8s debugging)

```bash
sudo tcpdump -i eth0 -n port 53
# Captures DNS traffic only
```

# Section 4: Cloud VPC Networking (Simplified)

You cannot understand K8s without cloud VPC (Virtual Private Cloud).

### The core cloud network stack:

| Layer                | What it does                                                    | Example (AWS)                   |
| -------------------- | --------------------------------------------------------------- | ------------------------------- |
| **VPC**              | Isolated virtual network                                        | 10.0.0.0/16                     |
| **Subnet**           | Partition of VPC (1 per AZ)                                     | public-subnet: 10.0.1.0/24      |
| **Route Table**      | Where traffic goes next                                         | local routes + internet gateway |
| **Internet Gateway** | Exit to public internet                                         | IGW-xxxx                        |
| **NAT Gateway**      | Private instances reach internet, but internet can't reach them | NAT-GW                          |
| **Security Group**   | Stateful firewall (allow/deny by IP/port)                       | Allow 0.0.0.0/0:443             |
| **Network ACL**      | Stateless firewall (subnet-level)                               | Ephemeral ports matter here     |

### Your cloud mental model:

1. **Public subnet** → Route table has `0.0.0.0/0 -> IGW`
2. **Private subnet** → Route table has `0.0.0.0/0 -> NAT Gateway`
3. **DB subnet** → No internet route, only VPC internal

### 🔥 Key confusion: Security Groups vs NACL

- **Security Group** (instance firewall): "Who can talk to my EC2/pod?"
  - Only _allow_ rules. Stateful (reply allowed automatically).
- **Network ACL** (subnet firewall): "What traffic is allowed in/out of this subnet?"
  - Allow AND Deny rules. Stateless (must allow both directions explicitly).

# Section 5: Kubernetes Networking (The real test)

Kubernetes assumes **every pod can talk to every other pod directly without NAT**. That's the "flat network" rule.

### 5.1 The 4 K8s network problems & solutions

| Problem                          | Solution                                                   |
| -------------------------------- | ---------------------------------------------------------- |
| 1. Pod-to-Pod on same node       | Linux bridge (`cbr0`) or `veth` pairs                      |
| 2. Pod-to-Pod on different nodes | CNI plugin (Calico, Cilium, Flannel) — uses overlay or BGP |
| 3. Pod-to-Service (ClusterIP)    | `kube-proxy` (iptables or IPVS)                            |
| 4. External-to-Service           | NodePort → LoadBalancer → Ingress                          |

### 5.2 The three CIDRs you must memorize for any k8s cluster:

```yaml
clusterCIDR: 10.244.0.0/16 # Each pod gets IP from here
serviceCIDR: 10.96.0.0/12 # Virtual Service IPs
clusterIPRange: 10.240.0.0/16 # Nodes themselves (cloud VPC subnet)
```

Example:

- Node = `10.240.0.5`
- Pod on that node = `10.244.1.23`
- Service in front of that pod = `10.100.45.67`

### 5.3 How kube-proxy works (simplified):

When you create a Service:

```bash
kubectl expose deployment nginx --port=80 --target-port=8080
```

kube-proxy adds iptables rules:

```bash
# On every node, see:
sudo iptables -t nat -L KUBE-SERVICES
```

It says: _"If destination is Service IP (10.100.45.67:80), change destination to actual pod IP (10.244.1.23:8080)"_ — this is DNAT.

### 5.4 Ingress vs LoadBalancer (cloud confusion cleared):

- `LoadBalancer` → Creates an actual cloud LB (AWS NLB/ALB) with a public IP. Expensive per service.
- `Ingress` → One cloud LB (Layer 7) that routes to multiple services based on host/path. Cheaper.

Example:

```
Internet -> Ingress (host: shop.com) -> Service A : checkout service
                       (host: blog.com)  -> Service B : wordpress
```

# Section 6: Your Daily Commands Cheatsheet

Save this. Run these daily until they're instinct.

```bash
# Linux networking
ip a                     # IP addresses + CIDR
ip r                     # Routing table
ss -tlnp                 # What's listening
ss -tunp                 # Active connections (no resolve)
ping -c 3 8.8.8.8        # Basic reachability
tracepath google.com     # Path + MTU
sudo tcpdump -i eth0 -n  # Live packets

# Cloud VPC (conceptual)
# List subnets (AWS CLI)
aws ec2 describe-subnets --filters "Name=vpc-id,Values=vpc-xxx"

# Kubernetes networking
kubectl get pods -o wide            # See pod IPs
kubectl get svc                     # See ClusterIP, NodePort
kubectl run debug --rm -it --image=nicolaka/netshoot -- /bin/bash
```

When a pod can't reach another pod, what do you check in order?

1. `kubectl get pods -o wide` (are IPs assigned?)
2. `kubectl exec pod1 -- ping <pod2-ip>` (does ICMP work?)
3. `ip route show` inside pod1 (does it have route to pod2 CIDR?)
4. `kubectl get networkpolicies` (is there a deny rule?)
5. `kubectl logs -n kube-system <cni-pod>` (is CNI plugin healthy?)
