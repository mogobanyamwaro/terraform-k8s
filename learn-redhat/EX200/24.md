# 24. Network Configuration With nmcli

**Objective:** Configure IPv4 and IPv6 addresses. Configure network services to start automatically at boot.

**This is one of the highest-risk objectives on the exam.** A mistake here can disconnect you from the machine you are being graded on. Read the "how not to lock yourself out" section before you touch anything.

## Concept Refresher

### The RHEL networking stack

```text
   ┌──────────────────────────────────────────────────────┐
   │  nmcli / nmtui / nm-connection-editor                │  ← you
   └────────────────────────┬─────────────────────────────┘
                            │  D-Bus
   ┌────────────────────────▼─────────────────────────────┐
   │  NetworkManager  (NetworkManager.service)            │  ← the manager
   │    reads/writes connection profiles under            │
   │    /etc/NetworkManager/system-connections/           │
   └────────────────────────┬─────────────────────────────┘
                            │  netlink
   ┌────────────────────────▼─────────────────────────────┐
   │  kernel: interfaces, addresses, routes               │  ← the live state
   │    visible with `ip addr`, `ip route`                │
   └──────────────────────────────────────────────────────┘
```

Two ideas you must keep separate:

| | **Device** (interface) | **Connection** (profile) |
| --- | --- | --- |
| What it is | Physical or virtual hardware: `ens160`, `eth0` | A **named set of settings** applied to a device |
| Listed by | `nmcli device status` | `nmcli connection show` |
| Count | One per NIC | **Zero, one, or many per NIC** |
| Stored where | Nowhere; it is hardware | **`/etc/NetworkManager/system-connections/*.nmconnection`** |
| Persists | n/a | **Yes** |

A device can have several connection profiles defined and only one active. This is why `nmcli con mod` changes a file, and `nmcli con up` applies it.

**`ip addr add` changes the kernel only and is lost on reboot. `nmcli con mod` writes a file and persists.** That sentence is worth more marks than anything else on this page.

### Interface naming

RHEL uses predictable names derived from firmware and topology, not `eth0`:

| Prefix | Meaning |
| --- | --- |
| `en` | Ethernet |
| `wl` | Wireless LAN |
| `ens160`, `ens192` | Ethernet, **s**lot 160 |
| `enp0s3` | Ethernet, **p**CI bus 0, **s**lot 3 |
| `eno1` | Ethernet, **o**nboard index 1 |
| `lo` | Loopback |

**Always check the actual name first** — do not assume `eth0`:

```bash
nmcli device status
ip -brief link show
```

### Inspecting current state

```bash
# Devices and their connection state
nmcli device status
nmcli device show
nmcli device show ens160

# Connection profiles
nmcli connection show                       # all profiles
nmcli connection show --active              # only active ones
nmcli connection show "Wired connection 1"  # full detail of one profile
nmcli -f ipv4.method,ipv4.addresses,ipv4.gateway connection show ens160

# Kernel state
ip addr show
ip -4 addr show
ip -brief addr show                          # compact, very readable
ip route show
ip -6 route show
ip link show
```

`nmcli` accepts abbreviations, so `nmcli c s`, `nmcli con show`, and `nmcli connection show` are the same. `nmcli d` is `device`, `nmcli c` is `connection`, `nmcli g` is `general`.

**`ip -brief addr` is the fastest way to see all addresses**, and `nmcli device status` the fastest way to see which profile is active where.

### Creating a connection profile

```bash
sudo nmcli connection add \
  type ethernet \
  con-name static-ens160 \
  ifname ens160 \
  ipv4.method manual \
  ipv4.addresses 192.168.56.11/24 \
  ipv4.gateway 192.168.56.1 \
  ipv4.dns "192.168.56.1 8.8.8.8" \
  ipv4.dns-search example.com \
  autoconnect yes
```

| Field | Meaning |
| --- | --- |
| `type ethernet` | Connection type |
| `con-name` | **The profile name** you will refer to later |
| `ifname` | The device it binds to |
| `ipv4.method manual` | **Static.** The alternative is `auto` for DHCP |
| `ipv4.addresses` | **Address with prefix.** `/24`, not a separate netmask |
| `ipv4.gateway` | Default gateway |
| `ipv4.dns` | **Space-separated, quoted** if more than one |
| `autoconnect yes` | **Activate at boot.** This is the persistence flag |

Then activate it:

```bash
sudo nmcli connection up static-ens160
```

**`ipv4.method manual` is mandatory for a static address.** If you set `ipv4.addresses` but leave the method as `auto`, DHCP still runs and your address may be ignored or supplemented. This is the classic silent failure.

### Modifying an existing profile

```bash
sudo nmcli connection modify ens160 ipv4.method manual
sudo nmcli connection modify ens160 ipv4.addresses 192.168.56.11/24
sudo nmcli connection modify ens160 ipv4.gateway 192.168.56.1
sudo nmcli connection modify ens160 ipv4.dns "192.168.56.1"
sudo nmcli connection modify ens160 connection.autoconnect yes

# Apply the changes — modify alone does NOT apply them
sudo nmcli connection up ens160
```

**`nmcli con mod` writes the file but does not touch the running system.** You must follow it with `nmcli con up <profile>` (or `nmcli device reapply`). Forgetting this is why "I configured it and it did not work" happens.

Adding versus replacing values:

```bash
sudo nmcli con mod ens160 ipv4.addresses 10.0.0.5/24        # REPLACES all addresses
sudo nmcli con mod ens160 +ipv4.addresses 10.0.0.6/24       # ADDS a second address
sudo nmcli con mod ens160 -ipv4.addresses 10.0.0.6/24       # REMOVES that address
sudo nmcli con mod ens160 +ipv4.dns 8.8.4.4                 # ADDS a DNS server
```

**The `+` and `-` prefixes are important.** Without `+`, you overwrite the whole list — which for `ipv4.dns` means you silently drop the existing resolver.

### Switching to DHCP

```bash
sudo nmcli con mod ens160 ipv4.method auto
sudo nmcli con mod ens160 -ipv4.addresses 192.168.56.11/24
sudo nmcli con mod ens160 ipv4.gateway ""
sudo nmcli con mod ens160 ipv4.dns ""
sudo nmcli con up ens160
```

Setting a property to `""` clears it. **Leaving a stale static gateway while switching to DHCP causes routing confusion**, so clear it.

### Activating, deactivating, deleting

```bash
sudo nmcli connection up static-ens160
sudo nmcli connection down static-ens160
sudo nmcli connection reload                  # re-read files from disk
sudo nmcli connection delete old-profile
sudo nmcli device reapply ens160              # apply changes without down/up
sudo nmcli device connect ens160
sudo nmcli device disconnect ens160
```

**`nmcli con down` then `up` briefly drops the link.** Over SSH, that disconnects you. See the lockout section.

### IPv6

Identical syntax with the `ipv6.` prefix:

```bash
sudo nmcli con mod ens160 ipv6.method manual
sudo nmcli con mod ens160 ipv6.addresses 2001:db8::11/64
sudo nmcli con mod ens160 ipv6.gateway 2001:db8::1
sudo nmcli con mod ens160 ipv6.dns 2001:4860:4860::8888
sudo nmcli con up ens160
```

IPv6 methods:

| Method | Behaviour |
| --- | --- |
| `auto` | SLAAC / router advertisements |
| `dhcp` | DHCPv6 only |
| `manual` | **Static** |
| `link-local` | Only a `fe80::` address |
| `ignore` | No IPv6 at all |
| `disabled` | IPv6 off for this connection |

Verify:

```bash
ip -6 addr show ens160
ip -6 route show
ping6 -c2 2001:db8::1
ping -6 -c2 2001:db8::1
```

**Every `fe80::` address is link-local and automatic** — it is not the address a task asks you to configure.

### nmtui

A curses interface. Slower than `nmcli` but hard to get wrong, and a fine fallback if the exact `nmcli` property name escapes you.

```bash
sudo nmtui
sudo nmtui-edit
sudo nmtui-connect
sudo nmtui-hostname
```

**Remember to Activate the connection after editing in nmtui** — like `nmcli con mod`, editing alone does not apply.

### The profile files

```bash
sudo ls -l /etc/NetworkManager/system-connections/
sudo cat /etc/NetworkManager/system-connections/static-ens160.nmconnection
```

```ini
[connection]
id=static-ens160
uuid=...
type=ethernet
interface-name=ens160
autoconnect=true

[ipv4]
method=manual
address1=192.168.56.11/24,192.168.56.1
dns=192.168.56.1;

[ipv6]
method=auto
```

**Permissions must be `600`**, since the file can contain secrets. NetworkManager refuses to load a world-readable profile. If you hand-edit a file, run `nmcli con reload` afterwards.

RHEL 8 used `/etc/sysconfig/network-scripts/ifcfg-*`. **RHEL 9 and 10 use keyfiles in `/etc/NetworkManager/system-connections/`.** The old `ifcfg` format is deprecated and the `network-scripts` package is gone.

### NetworkManager service

```bash
systemctl status NetworkManager
sudo systemctl enable --now NetworkManager
nmcli general status
nmcli networking on
nmcli networking off
nmcli general permissions
```

`nmcli general status` should show `STATE: connected`. If it shows `asleep` or `disconnected`, networking is off:

```bash
nmcli networking on
```

### How not to lock yourself out

**You are working over SSH. A network mistake ends your session and possibly your exam.**

Habits that protect you:

1. **Never `nmcli con down` your management interface** unless you have console access.
2. **Prefer `nmcli device reapply`** where possible — it applies changes with less disruption than a down/up cycle.
3. **Use a second interface for practice** if the VM has one.
4. **Test with a timed rollback** when making a risky change from a console-less machine:

```bash
# Schedule an undo before making the change
echo "nmcli con up ens160" | sudo at now + 5 minutes
```

5. **Keep the console open** in your hypervisor, so a lost SSH session is recoverable.
6. **Write the change, verify the file, then apply**:

```bash
sudo nmcli con mod ens160 ipv4.addresses 192.168.56.11/24
sudo nmcli -f ipv4 con show ens160        # read it back BEFORE applying
sudo nmcli con up ens160
```

If you do get disconnected, the fix is on the console: `nmcli con up <profile>` or, in the worst case, `ip addr add` temporarily to restore access and then repair the profile properly.

### Troubleshooting flow

```bash
# 1. Is the device present and up?
nmcli device status
ip link show ens160

# 2. Does it have the address you expect?
ip -brief addr show ens160

# 3. Is there a default route?
ip route show | grep default

# 4. Can you reach the gateway?
ping -c2 192.168.56.1

# 5. Can you reach outside?
ping -c2 8.8.8.8

# 6. Does DNS work? (see 25.md)
getent hosts server2.lab.example.com

# 7. What does NetworkManager think?
nmcli general status
sudo journalctl -u NetworkManager -n 30
```

**Working through those seven steps in order localises almost any network fault**: no address means a profile problem, address but no route means a gateway problem, route but no ping means a firewall or upstream problem, ping to an IP working but names failing means DNS.

**Task 3.**

```bash
sudo nmcli connection add \
  type ethernet \
  con-name static-lab \
  ifname ens192 \
  ipv4.method manual \
  ipv4.addresses 192.168.100.50/24 \
  ipv4.gateway 192.168.100.1 \
  ipv4.dns "192.168.100.1 8.8.8.8" \
  ipv4.dns-search lab.example.com \
  connection.autoconnect yes
```

Read it back before doing anything else:

```bash
nmcli connection show static-lab | grep -E '^ipv4|autoconnect'
```

```text
connection.autoconnect:                 yes
ipv4.method:                            manual
ipv4.dns:                               192.168.100.1,8.8.8.8
ipv4.dns-search:                        lab.example.com
ipv4.addresses:                         192.168.100.50/24
ipv4.gateway:                           192.168.100.1
```

Four things must be right:

- **`ipv4.method manual`** — without it, DHCP still runs and the task fails.
- **The prefix is part of the address**: `192.168.100.50/24`, not a separate netmask parameter.
- **Multiple DNS servers are space-separated inside quotes.**
- **`connection.autoconnect yes`** is what makes it come up at boot. This is the persistence requirement.

`nmcli con add` creates the profile and, unless `autoconnect no` is set, usually activates it immediately.

**Task 5.**

```bash
sudo nmcli connection modify static-lab +ipv4.addresses 192.168.100.51/24
sudo nmcli connection up static-lab
ip -brief addr show ens192
```

```text
ens192  UP  192.168.100.50/24 192.168.100.51/24 fe80::.../64
```

**The `+` is the whole point.** Without it:

```bash
sudo nmcli con mod static-lab ipv4.addresses 192.168.100.51/24   # DESTROYS the .50 address
```

`ipv4.addresses` is a list property, and assignment replaces the entire list. `+` appends, `-` removes:

```bash
sudo nmcli con mod static-lab -ipv4.addresses 192.168.100.51/24
sudo nmcli con up static-lab
```

**Task 6.**

```bash
nmcli -f ipv4.dns con show static-lab              # before
sudo nmcli connection modify static-lab +ipv4.dns 8.8.4.4
nmcli -f ipv4.dns con show static-lab              # after
sudo nmcli connection up static-lab
cat /etc/resolv.conf
```

```text
ipv4.dns:    192.168.100.1,8.8.8.8,8.8.4.4
```

Remove it:

```bash
sudo nmcli connection modify static-lab -ipv4.dns 8.8.4.4
sudo nmcli connection up static-lab
nmcli -f ipv4.dns con show static-lab
```

```bash
sudo nmcli con mod static-lab ipv4.dns ""
```

**Task 7.**

```bash
sudo nmcli connection modify static-lab ipv6.method manual
sudo nmcli connection modify static-lab ipv6.addresses 2001:db8:100::50/64
sudo nmcli connection modify static-lab ipv6.gateway 2001:db8:100::1
sudo nmcli connection up static-lab
```

Verify:

```bash
ip -6 addr show ens192
ip -6 route show dev ens192
nmcli -f ipv6.method,ipv6.addresses,ipv6.gateway con show static-lab
```

```text
$ ip -6 addr show ens192
inet6 2001:db8:100::50/64 scope global
inet6 fe80::20c:29ff:feaa:bbdd/64 scope link
```

```bash
ping -6 -c2 2001:db8:100::50
ping6 -c2 2001:db8:100::1
```

**The syntax is identical to IPv4 with an `ipv6.` prefix**, and `ipv6.method manual` is just as mandatory as its IPv4 counterpart. **The `fe80::` address is link-local and always present automatically** — it is never what a task means by "configure an IPv6 address". Look for `scope global`.

**Task 8.**

```bash
sudo nmcli connection modify static-lab ipv4.method auto
sudo nmcli connection modify static-lab ipv4.addresses ""
sudo nmcli connection modify static-lab ipv4.gateway ""
sudo nmcli connection modify static-lab ipv4.dns ""
sudo nmcli connection up static-lab
```

Verify:

```bash
nmcli -f ipv4.method,ipv4.addresses,ipv4.gateway con show static-lab
ip -brief addr show ens192
cat /etc/resolv.conf
```

```text
ipv4.method:      auto
ipv4.addresses:   --
ipv4.gateway:     --
```

**Order matters slightly**: NetworkManager will refuse to set `ipv4.method auto` while a gateway is configured in some versions, so if you get an error, clear the gateway first:

```bash
sudo nmcli con mod static-lab ipv4.gateway ""
sudo nmcli con mod static-lab ipv4.method auto
```

**Clearing the stale static values matters.** A leftover gateway from the manual configuration can override what DHCP offers and produce baffling routing behaviour.

**Task 9.**

```bash
sudo ls -l /etc/NetworkManager/system-connections/
```

```text
-rw-------. 1 root root 337 Aug 18 14:22 static-lab.nmconnection
-rw-------. 1 root root 291 Aug 18 09:10 ens160.nmconnection
```

```bash
sudo cat /etc/NetworkManager/system-connections/static-lab.nmconnection
```

```ini
[connection]
id=static-lab
uuid=4f8a2b91-...
type=ethernet
interface-name=ens192
autoconnect=true

[ipv4]
address1=192.168.100.50/24,192.168.100.1
dns=192.168.100.1;8.8.8.8;
dns-search=lab.example.com;
method=manual

[ipv6]
addr-gen-mode=default
method=auto
```

**`-rw-------` (0600) is required.** NetworkManager refuses to load a profile with looser permissions because it may contain WiFi passwords or 802.1X secrets:

```bash
sudo chmod 600 /etc/NetworkManager/system-connections/static-lab.nmconnection
sudo nmcli connection reload
```

If you hand-edit any of these files, **`nmcli connection reload` is required** for NetworkManager to notice, then `nmcli con up` to apply.

**This file is the persistence.** If it exists, is 0600, and has `autoconnect=true`, the configuration survives a reboot.

**Task 10.**

```bash
sudo nmcli connection modify static-lab connection.autoconnect no
nmcli -f connection.autoconnect connection show static-lab
```

```text
connection.autoconnect:    no
```

**After a reboot, this profile will not be activated.** The device stays down with no address, even though the profile file exists and is perfectly valid. The configuration is present but not applied.

This is one of the exam's cleanest traps: a candidate configures everything correctly, verifies with `ip addr`, and loses the marks because `autoconnect` was off and the grader checks after a reboot.

Turn it back on:

```bash
sudo nmcli connection modify static-lab connection.autoconnect yes
nmcli -f connection.autoconnect connection show static-lab
```

Check every profile at once:

```bash
nmcli -f NAME,AUTOCONNECT connection show
```

```text
NAME        AUTOCONNECT
ens160      yes
static-lab  yes
lo          yes
```

**`connection.autoconnect yes` is the `systemctl enable` of networking.** Make checking it part of your pre-reboot routine.

**Task 12.**

Break it:

```bash
sudo nmcli con mod static-lab ipv4.gateway 192.168.100.99   # nothing at .99
sudo nmcli con up static-lab
```

The symptom:

```bash
ip -brief addr show ens192          # address is fine
ip route show | grep default        # a default route exists, via the wrong host
ping -c2 192.168.100.50             # own address: works
ping -c2 192.168.100.1              # local network: works
ping -c2 8.8.8.8                    # anything remote: fails
```

```text
connect: Network is unreachable
```

**Read the pattern.** The address is present, the local network is reachable, and everything beyond it fails. That is a gateway fault, not an address fault and not DNS. Contrast:

| Symptom | Likely cause |
| --- | --- |
| No address at all | Profile wrong, or `ipv4.method` still `auto` with no DHCP |
| Address present, local pings fail | Link down, wrong subnet, or firewall |
| Local works, remote fails | **Gateway wrong or missing** |
| IP pings work, names fail | **DNS** (see `25.md`) |

Confirm the gateway is unreachable:

```bash
ip route get 8.8.8.8
ping -c2 192.168.100.99
arp -n
ip neigh show
```

An `INCOMPLETE` entry in `ip neigh` for the gateway means nothing is answering at that address.

Repair:

```bash
sudo nmcli con mod static-lab ipv4.gateway 192.168.100.1
sudo nmcli con up static-lab
ip route show | grep default
ping -c2 8.8.8.8
```

**Task 13.**

The non-persistent way:

```bash
sudo ip addr add 192.168.100.99/24 dev ens192
ip -brief addr show ens192
```

```text
ens192  UP  192.168.100.50/24 192.168.100.99/24 ...
```

It works. It pings. And it is **entirely in kernel memory**:

```bash
grep -r 192.168.100.99 /etc/NetworkManager/system-connections/ 2>/dev/null
# no output — nothing on disk
```

Prove the point:

```bash
sudo reboot
# after reboot:
ip -brief addr show ens192        # .99 is gone
```

sudo nmcli con up static-lab      # NetworkManager reasserts the profile

| Command | Effect | Survives reboot |
| --- | --- | --- |
| `ip addr add` | Kernel only | **No** |
| `ip route add` | Kernel only | **No** |
| `ip link set up` | Kernel only | **No** |
| `hostname foo` | Kernel only | **No** |
| `nmcli con mod` | **Writes a keyfile** | **Yes** |
| `nmcli con add` | **Writes a keyfile** | **Yes** |
| `hostnamectl set-hostname` | **Writes `/etc/hostname`** | **Yes** |

**`ip` is for looking, `nmcli` is for changing.** That is the safest rule to carry into the exam. `ip addr add` is legitimate for one purpose only: restoring temporary access after you have locked yourself out, so that you can then fix the profile properly.

## Persistence Check

| Change | Persistent artifact | Also required |
| --- | --- | --- |
| Static address | `nmcli con mod ... ipv4.addresses` → keyfile | **`ipv4.method manual`** + `nmcli con up` |
| Gateway | keyfile `address1=...,<gw>` | `nmcli con up` |
| DNS | keyfile `dns=` | `nmcli con up` |
| Static route | keyfile `route1=` | `nmcli con up` |
| Activation at boot | **`connection.autoconnect yes`** | — |
| NetworkManager running | `systemctl enable --now NetworkManager` | — |
| Profile readable | **file mode `0600`** | `nmcli con reload` if hand-edited |

**Four things must all be true**, and the exam separates candidates on the last two:

1. The keyfile exists in `/etc/NetworkManager/system-connections/` with mode 0600.
2. `ipv4.method` is `manual` if you configured a static address.
3. **`connection.autoconnect` is `yes`.**
4. NetworkManager is enabled.

```bash
# The five-second pre-reboot network check
nmcli -f NAME,AUTOCONNECT connection show
systemctl is-enabled NetworkManager
ip -brief addr show
```

## Exam Tips

- **`ip` is for looking; `nmcli` is for changing.** `ip addr add` never persists.
- **`nmcli con mod` writes the file; `nmcli con up` applies it.** Both are needed.
- **`ipv4.method manual` is mandatory for a static address.** Setting only `ipv4.addresses` leaves DHCP running.
- **`connection.autoconnect yes` is the persistence flag.** Without it the profile exists but never activates at boot.
- **The prefix goes with the address**: `192.168.56.11/24`. There is no separate netmask parameter.
- **Use `+` to append to list properties**: `+ipv4.addresses`, `+ipv4.dns`, `+ipv4.routes`. Plain assignment **replaces the whole list**.
- **Multiple DNS servers are space-separated inside quotes**: `ipv4.dns "192.168.1.1 8.8.8.8"`.
- **IPv6 is the same syntax with an `ipv6.` prefix.** `fe80::` addresses are automatic link-local, never what a task means.
- **Check the interface name.** It is `ens160` or `enp0s3`, not `eth0`.
- **Keyfiles live in `/etc/NetworkManager/system-connections/` and must be 0600.** The old `ifcfg-*` scripts are gone in RHEL 9 and 10. Hand-edits need `nmcli con reload`.
- **Never `nmcli con down` your SSH interface.** Prefer `nmcli device reapply`, and keep the hypervisor console available.
- **Verify with `ip addr`, not `nmcli con show`.** The profile shows intent; `ip` shows reality.
- **One profile per interface.** Duplicate profiles with `autoconnect=true` fight over the device at boot.
- **Diagnose in order**: address, then route, then gateway ping, then remote ping, then name resolution.
- **`nmtui` is allowed** and is a good fallback if you cannot recall a property name — but you still have to activate the connection.
- **Reboot and re-check.** Networking is graded after a reboot, and `autoconnect` is where marks are lost.
