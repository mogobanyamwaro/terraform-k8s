# 27. SELinux

**Objectives:**
- Set enforcing and permissive modes for SELinux
- List and identify SELinux file and process context
- Restore default file contexts
- Manage SELinux port labels
- Use boolean settings to modify system SELinux settings
- Diagnose and address routine SELinux policy violations

**Six sub-objectives, more than any other single topic.** SELinux is also the thing most likely to make an otherwise-correct configuration fail. Every "the service is running but does not work" problem on this exam is either the firewall or SELinux.

**Never disable SELinux to make a task pass.** It is graded, and disabling it fails other tasks too.

## Concept Refresher

### What SELinux adds

Standard permissions ask "does this *user* have access to this file?" SELinux asks "does this *process*, in its security context, have permission to perform this *action* on this object, in its security context?"

```text
   process wants to open a file
             │
   ┌─────────▼──────────────────────────┐
   │  1. Standard permissions (DAC)     │   ugo/rwx, ACLs
   │     Denied?  ──► EACCES            │
   └─────────┬──────────────────────────┘
             │ allowed
   ┌─────────▼──────────────────────────┐
   │  2. SELinux policy (MAC)           │   context vs context
   │     Denied?  ──► EACCES + AVC log  │
   └─────────┬──────────────────────────┘
             │ allowed
        ┌────▼─────┐
        │  access  │
        └──────────┘
```

**Both must allow.** So `chmod 777` does not defeat SELinux, and a correct SELinux context does not defeat a missing execute bit. When troubleshooting, check both — see `12.md` for the DAC side.

### Contexts

Every process and every file has a context, written as four colon-separated fields:

```text
    system_u : object_r : httpd_sys_content_t : s0
       │          │              │              │
      user       role          TYPE           level
                                │
                    ◄── this is the one that matters ──►
```

| Field | Purpose | RHCSA relevance |
| --- | --- | --- |
| user | SELinux user, e.g. `system_u`, `unconfined_u` | Rarely |
| role | `object_r` for files, `system_r` for processes | Rarely |
| **type** | **The label that policy rules act on** | **This is 95% of the exam** |
| level | MLS/MCS sensitivity, `s0` | Only for containers |

**Type Enforcement is the mechanism you are being tested on.** A rule says "a process of type `httpd_t` may read a file of type `httpd_sys_content_t`". If the file is labelled `user_home_t` instead, the read is denied.

```bash
ls -Z /var/www/html/index.html
ps -eZ | grep httpd
id -Z
ls -Zd /var/www/html
netstat -Z 2>/dev/null || ss -Z
```

```text
$ ls -Z /var/www/html/index.html
unconfined_u:object_r:httpd_sys_content_t:s0 /var/www/html/index.html

$ ps -eZ | grep httpd
system_u:system_r:httpd_t:s0     1234 ?  00:00:00 httpd
```

**`-Z` is the universal SELinux flag**: `ls -Z`, `ps -Z`, `id -Z`, `cp -Z`, `mkdir -Z`, `ss -Z`, `netstat -Z`.

### Modes

| Mode | Enforces policy | Logs denials |
| --- | --- | --- |
| **`enforcing`** | **Yes** | Yes |
| **`permissive`** | No | **Yes** |
| `disabled` | No | No |

```bash
getenforce                       # current mode
sestatus                         # full status
sestatus -v                      # plus context of key files/processes
sudo setenforce 0                # Permissive — RUNTIME ONLY
sudo setenforce 1                # Enforcing — RUNTIME ONLY
```

```text
$ sestatus
SELinux status:                 enabled
SELinuxfs mount:                /sys/fs/selinux
SELinux root directory:         /etc/selinux
Loaded policy name:             targeted
Current mode:                   enforcing
Mode from config file:          enforcing
Policy MLS status:              enabled
Policy deny_unknown status:     allowed
Memory protection checking:     actual (secure)
Max kernel policy version:      33
```

**Two lines to read: `Current mode` and `Mode from config file`. If they differ, someone used `setenforce` and the setting will revert on reboot.**

**`setenforce` does not persist.** The persistent setting is in `/etc/selinux/config`:

```bash
sudo vim /etc/selinux/config
```

```ini
SELINUX=enforcing
SELINUXTYPE=targeted
```

```bash
grep '^SELINUX=' /etc/selinux/config
```

Or non-interactively:

```bash
sudo sed -i 's/^SELINUX=.*/SELINUX=enforcing/' /etc/selinux/config
grep '^SELINUX=' /etc/selinux/config
```

**Permissive mode is a diagnostic tool, not a solution.** Set permissive, reproduce the problem, collect the AVC denials, then go back to enforcing and fix the labels properly. A task that says "SELinux must be in enforcing mode" is checking `getenforce` **and** the config file after a reboot.

### Going from disabled to enforcing

You cannot simply flip the config from `disabled` to `enforcing` and reboot — the whole filesystem is unlabelled and the system will not boot properly. You must relabel:

```bash
sudo sed -i 's/^SELINUX=.*/SELINUX=permissive/' /etc/selinux/config
sudo touch /.autorelabel
sudo reboot
# the system relabels everything and reboots again — this takes a while
# then, once it is up and you have confirmed no denials:
sudo sed -i 's/^SELINUX=.*/SELINUX=enforcing/' /etc/selinux/config
sudo reboot
```

**Going `disabled` → `permissive` → relabel → `enforcing` is the safe route.** Jumping straight to `enforcing` on an unlabelled filesystem can leave you with an unbootable machine — a spectacular way to fail an exam.

### Changing file contexts

Two commands, and choosing the wrong one costs marks:

```bash
# TEMPORARY: changes the label now, LOST on relabel
sudo chcon -t httpd_sys_content_t /web/index.html
sudo chcon -R -t httpd_sys_content_t /web
sudo chcon --reference=/var/www/html /web        # copy context from elsewhere

# PERMANENT: adds a policy rule, then apply it
sudo semanage fcontext -a -t httpd_sys_content_t "/web(/.*)?"
sudo restorecon -Rv /web
```

| | `chcon` | `semanage fcontext` + `restorecon` |
| --- | --- | --- |
| Effect | **Changes the label directly** | **Adds a rule to the policy database** |
| Immediate | Yes | Only after `restorecon` |
| Survives `restorecon` | **No** | **Yes** |
| Survives `touch /.autorelabel` | **No** | **Yes** |
| Survives a reboot | Yes, usually | **Yes** |
| Exam answer | **Almost never** | **Almost always** |

**`chcon` is graffiti; `semanage fcontext` changes the map.** A `chcon` label survives an ordinary reboot but is wiped by any relabel — and, more importantly, it is the wrong answer to "ensure the correct context is set permanently". **Use `semanage fcontext -a` followed by `restorecon`.**

The regular expression matters:

```bash
sudo semanage fcontext -a -t httpd_sys_content_t "/web(/.*)?"
```

| Pattern | Matches |
| --- | --- |
| `"/web(/.*)?"` | **`/web` itself and everything beneath it.** The standard idiom |
| `"/web/.*"` | Contents only, not the directory itself |
| `"/web"` | Only the directory itself |
| `"/web(/.*)?\.html"` | Only `.html` files under `/web` |

**`"(/.*)?"` is the pattern to memorise.** Quote it, or the shell expands the glob characters.

Managing the rules:

```bash
sudo semanage fcontext -l                        # all rules (long)
sudo semanage fcontext -l -C                     # only LOCAL customisations
sudo semanage fcontext -l | grep '^/web'
sudo semanage fcontext -m -t httpd_sys_content_t "/web(/.*)?"    # modify existing
sudo semanage fcontext -d "/web(/.*)?"           # delete the rule
sudo restorecon -Rv /web                         # then reapply
```

**`semanage fcontext -l -C` shows only your local additions**, which is the fast way to verify your own work against the thousands of default rules.

### restorecon

```bash
sudo restorecon -v /path/to/file          # verbose
sudo restorecon -Rv /path                 # recursive
sudo restorecon -RFv /path                # -F forces even user/role changes
sudo restorecon -Rvn /path                # -n = dry run, change nothing
```

```text
$ sudo restorecon -Rv /web
Relabeled /web from unconfined_u:object_r:default_t:s0 to unconfined_u:object_r:httpd_sys_content_t:s0
Relabeled /web/index.html from unconfined_u:object_r:default_t:s0 to unconfined_u:object_r:httpd_sys_content_t:s0
```

**`restorecon` sets the label the policy says it should be** — it does not guess and it does not take a type argument. So `restorecon` alone fixes a *wrong* label on a *standard* path, but for a non-standard path you must first tell the policy what the label should be with `semanage fcontext -a`.

The whole filesystem:

```bash
sudo restorecon -Rv /                     # long
sudo touch /.autorelabel && sudo reboot   # relabel during boot
sudo fixfiles relabel
sudo fixfiles -R httpd restore            # only files owned by a package
```

**`restorecon -Rvn` is the safest diagnostic in the toolkit** — it reports every mislabelled file without changing anything:

```bash
sudo restorecon -Rvn /var/www/           # what WOULD change?
```

Empty output means every label matches the policy.

### Why labels go wrong

| Action | Resulting label | Why |
| --- | --- | --- |
| `cp file /var/www/html/` | **Inherits the destination's type** | New file created in the directory |
| `cp -a file /var/www/html/` | **Keeps the source label** | `-a` preserves context |
| `mv file /var/www/html/` | **Keeps the original label** | The inode is not recreated |
| `tar xf` | Inherits from the directory | Unless `--selinux --xattrs` |
| `tar --selinux -xf` | Restores the archived labels | |
| Creating a new directory | Inherits from the parent | |
| `useradd` | Correct by policy | |

**`mv` preserving the old label is the number one cause of SELinux failures on this exam.** You move a file from your home directory to `/var/www/html`, it arrives labelled `user_home_t`, and httpd cannot read it:

```bash
mv ~/index.html /var/www/html/
ls -Z /var/www/html/index.html
# unconfined_u:object_r:user_home_t:s0
sudo restorecon -v /var/www/html/index.html
# Relabeled ... to httpd_sys_content_t
```

**Rule: after `mv`, `tar x`, or `cp -a` into a service directory, always `restorecon`.** The habit costs nothing.

### Booleans

Booleans toggle optional parts of the policy without writing rules.

```bash
getsebool -a                                     # every boolean
getsebool -a | grep httpd
getsebool httpd_enable_homedirs
semanage boolean -l                              # with descriptions
semanage boolean -l -C                           # only ones you changed
```

```text
$ semanage boolean -l | grep httpd_enable_homedirs
httpd_enable_homedirs   (off  ,  off)  Allow httpd to enable homedirs
```

The two values in parentheses are **(current, permanent)**. If they differ, someone set the boolean without `-P`.

```bash
sudo setsebool httpd_enable_homedirs on          # RUNTIME ONLY
sudo setsebool -P httpd_enable_homedirs on       # PERMANENT
```

**`-P` is the `--permanent` of SELinux.** Without it the boolean reverts at the next reboot. `-P` takes a few seconds because it rebuilds the policy — that pause is how you know it worked.

Booleans worth recognising:

| Boolean | Enables |
| --- | --- |
| `httpd_enable_homedirs` | httpd serving `~/public_html` |
| `httpd_can_network_connect` | httpd making outbound connections (proxying) |
| `httpd_can_network_connect_db` | httpd connecting to a remote database |
| `httpd_use_nfs` | httpd serving content from an NFS mount |
| `httpd_anon_write` | httpd writing to `public_content_rw_t` |
| `ftpd_full_access` | vsftpd full filesystem access |
| `ftp_home_dir` | FTP access to home directories |
| `nfs_export_all_rw` | Exporting any directory read-write over NFS |
| `samba_enable_home_dirs` | Samba sharing home directories |
| `ssh_sysadm_login` | ssh login to the sysadm role |
| `use_nfs_home_dirs` | Home directories on NFS |
| `selinuxuser_execmod` | Certain memory operations |

**Find the right boolean by keyword rather than memorising the list:**

```bash
getsebool -a | grep -i nfs
semanage boolean -l | grep -i home
semanage boolean -l | grep -i httpd | grep -i network
```

And `sealert` output usually names the boolean for you.

### Port labels

SELinux labels network ports too, which is why moving a service to a non-standard port fails.

```bash
semanage port -l                                 # everything
semanage port -l | grep http
semanage port -l -C                              # only local changes
semanage port -l | grep 8080
```

```text
$ semanage port -l | grep '^http_port_t'
http_port_t     tcp   80, 81, 443, 488, 8008, 8009, 8443, 9000
```

```bash
sudo semanage port -a -t http_port_t -p tcp 8090      # ADD a new port
sudo semanage port -m -t http_port_t -p tcp 8090      # MODIFY an existing entry
sudo semanage port -d -t http_port_t -p tcp 8090      # DELETE
```

**`-a` adds, `-m` modifies, `-d` deletes.** If `-a` fails with "port already defined", the port is already labelled with some other type and you need `-m`:

```bash
$ sudo semanage port -a -t http_port_t -p tcp 82
ValueError: Port tcp/82 already defined
$ semanage port -l | grep '\b82\b'
$ sudo semanage port -m -t http_port_t -p tcp 82
```

The classic sequence for moving sshd to port 2222:

```bash
sudo semanage port -a -t ssh_port_t -p tcp 2222
sudo firewall-cmd --permanent --add-port=2222/tcp
sudo firewall-cmd --reload
sudo sed -i 's/^#\?Port .*/Port 2222/' /etc/ssh/sshd_config
sudo systemctl restart sshd
ss -tlnp | grep 2222
```

**Three things are needed for a non-standard port: the service configuration, the SELinux port label, and the firewall rule.** Miss any one and it fails. This is a favourite exam construction because it tests three objectives in one task.

**Port labels persist automatically** — `semanage` writes to the policy store, and there is no `-P` flag needed.

### Reading AVC denials

An AVC (Access Vector Cache) denial is SELinux's log entry for a blocked action.

```bash
sudo ausearch -m AVC -ts recent
sudo ausearch -m AVC,USER_AVC -ts today
sudo ausearch -m AVC -ts recent -i              # -i interprets numbers into names
sudo journalctl -t setroubleshoot
sudo grep -i denied /var/log/audit/audit.log | tail
sudo journalctl -b | grep -i avc
```

```text
type=AVC msg=audit(1692364800.123:456): avc:  denied  { read } for
  pid=1234 comm="httpd" name="index.html" dev="dm-0" ino=12345
  scontext=system_u:system_r:httpd_t:s0
  tcontext=unconfined_u:object_r:default_t:s0
  tclass=file permissive=0
```

Read it in this order:

| Field | Value here | Meaning |
| --- | --- | --- |
| `denied { read }` | read | **The action that was blocked** |
| `comm=` | httpd | **Which program** |
| `name=` | index.html | **Which object** |
| **`scontext=`** | `httpd_t` | **The source type — the process** |
| **`tcontext=`** | **`default_t`** | **The target type — the file** |
| `tclass=` | file | The kind of object |
| `permissive=0` | 0 | 0 = it was blocked; 1 = permissive, logged only |

**`tcontext=...:default_t` immediately tells you the file has the wrong label** — httpd content should be `httpd_sys_content_t`. That is the whole diagnosis, from one line.

The friendlier tool:

```bash
sudo dnf install -y setroubleshoot-server
sudo sealert -a /var/log/audit/audit.log
sudo journalctl -t setroubleshoot --since today
```

```text
SELinux is preventing /usr/sbin/httpd from read access on the file index.html.

*****  Plugin restorecon (99.5 confidence) suggests   ************************
If you want to fix the label.
/var/www/html/index.html default label should be httpd_sys_content_t.
Then you can run restorecon. The access attempt may have been stopped due to
insufficient permissions to access a parent directory.
Do
# /sbin/restorecon -v /var/www/html/index.html
```

**`sealert` names the fix and gives you the command.** Install `setroubleshoot-server` in your lab and check whether it is present on the exam — if it is, it turns SELinux troubleshooting into reading a paragraph.

The audit service must be running for any of this to work:

```bash
systemctl status auditd
```

### The troubleshooting decision tree

```text
   Service is running but does not work
              │
   ┌──────────▼─────────────────────────────────────┐
   │ Are there AVC denials?                         │
   │   sudo ausearch -m AVC -ts recent              │
   └──────────┬─────────────────────────────────────┘
              │
       ┌──────┴───────┐
       │ no           │ yes
       ▼              ▼
  Not SELinux.   Read tcontext / scontext
  Check the      and what was denied
  firewall,             │
  the service    ┌──────┴─────────────────────────┐
  config,        │                                │
  and DAC        ▼                                ▼
  permissions   Wrong FILE label?          Wrong PORT label?
                 │                                │
                 ▼                                ▼
        semanage fcontext -a          semanage port -a -t X -p tcp N
        restorecon -Rv                        │
                 │                            │
                 └─────────┬──────────────────┘
                           │
                    still denied?
                           │
                           ▼
                 Is there a BOOLEAN for it?
                   semanage boolean -l | grep <keyword>
                   setsebool -P <boolean> on
                           │
                    still denied?
                           │
                           ▼
                 Generate a policy module
                   ausearch -m AVC -ts recent | audit2allow -M mymod
                   semodule -i mymod.pp
```

**Confirm SELinux is even the culprit before spending time on it:**

```bash
sudo setenforce 0
# retry the operation
```

If it now works, SELinux was the cause. **Then put it straight back:**

```bash
sudo setenforce 1
```

Never leave it permissive as your answer.

### audit2allow

The last resort, for when no boolean and no label fixes the denial:

```bash
sudo ausearch -m AVC -ts recent | audit2allow           # show the rules
sudo ausearch -m AVC -ts recent | audit2allow -w        # explain in words
sudo ausearch -m AVC -ts recent | audit2allow -M mypol  # build a module
sudo semodule -i mypol.pp                               # install it
semodule -l | grep mypol
sudo semodule -r mypol                                  # remove it
```

**Use `audit2allow` only after ruling out a label or boolean fix.** It is a legitimate tool but it grants whatever was attempted, including things you did not intend, and on the exam a correct label or boolean is nearly always the expected answer. Read `audit2allow -w` output before installing anything.

### Everything that persists, and how

| Setting | Non-persistent | **Persistent** |
| --- | --- | --- |
| Mode | `setenforce 0/1` | **`/etc/selinux/config`** |
| File context | `chcon` | **`semanage fcontext -a` + `restorecon`** |
| Boolean | `setsebool X on` | **`setsebool -P X on`** |
| Port label | — | **`semanage port -a`** (always persistent) |
| Policy module | — | **`semodule -i`** (always persistent) |

**Three flags to memorise: `-P` for booleans, `semanage fcontext` instead of `chcon`, and `/etc/selinux/config` instead of `setenforce`.**

### The packages you need

```bash
sudo dnf install -y policycoreutils-python-utils setroubleshoot-server
```

**`semanage` lives in `policycoreutils-python-utils`** and is not always installed. If `semanage: command not found` appears mid-exam, this is the fix. Check in your lab so you recognise it instantly.

## Solutions

**Task 1.**

```bash
getenforce
sestatus
```

```text
$ getenforce
Enforcing

$ sestatus
SELinux status:                 enabled
SELinuxfs mount:                /sys/fs/selinux
SELinux root directory:         /etc/selinux
Loaded policy name:             targeted
Current mode:                   enforcing
Mode from config file:          enforcing
Policy MLS status:              enabled
Policy deny_unknown status:     allowed
Memory protection checking:     actual (secure)
Max kernel policy version:      33
```

Three lines answer the question:

- **`Current mode`** — now.
- **`Mode from config file`** — after the next reboot.
- **`Loaded policy name: targeted`** — the standard policy, which confines listed services and leaves everything else `unconfined_t`.

```bash
grep '^SELINUX' /etc/selinux/config
sestatus -v            # also shows contexts of key files and processes
```

**If `Current mode` and `Mode from config file` disagree, someone ran `setenforce` and the setting will revert.** Reconciling those two lines is the first thing to check on any SELinux task.

**Task 2.**

```bash
getenforce                       # Enforcing
sudo setenforce 0
getenforce                       # Permissive
```

The config file is untouched:

```bash
grep '^SELINUX=' /etc/selinux/config
```

```text
SELINUX=enforcing
```

```bash
sestatus | grep -i mode
```

```text
Current mode:                   permissive
Mode from config file:          enforcing
```

**Those two lines disagreeing is the signature of `setenforce`.** Restore:

```bash
sudo setenforce 1
getenforce
```

`setenforce` accepts either form:

```bash
sudo setenforce 0        # or: sudo setenforce Permissive
sudo setenforce 1        # or: sudo setenforce Enforcing
```

**`setenforce` cannot reach `disabled`** — that requires a config change and a reboot, by design.

**Use permissive deliberately and briefly**: switch to permissive, reproduce the failure, collect the denials with `ausearch`, switch back to enforcing, fix the labels. **Never leave a system permissive as your answer to a task.**

**Task 3.**

```bash
sudo sed -i 's/^SELINUX=.*/SELINUX=enforcing/' /etc/selinux/config
grep '^SELINUX=' /etc/selinux/config
```

```text
SELINUX=enforcing
```

Make it active now as well:

```bash
sudo setenforce 1
getenforce
sestatus | grep -i mode
```

```text
Current mode:                   enforcing
Mode from config file:          enforcing
```

**Both are required.** `setenforce 1` alone reverts at the reboot; the config change alone does not take effect until the reboot. **This is exactly the runtime-versus-permanent split you saw with firewalld.**

Careful with the file — the wrong value produces a machine that boots without SELinux, and other tasks will fail:

```bash
grep -v '^#' /etc/selinux/config | grep -v '^$'
```

```text
SELINUX=enforcing
SELINUXTYPE=targeted
```

**Valid values are `enforcing`, `permissive`, `disabled`.** A typo such as `SELINUX=enforcng` is treated as disabled. Always read the file back.

**Task 4.**

```bash
ls -Zd /var/www/html
ls -Z /var/www/html/
ps -eZ | grep httpd
id -Z
```

```text
$ ls -Zd /var/www/html
system_u:object_r:httpd_sys_content_t:s0 /var/www/html

$ ps -eZ | grep httpd
system_u:system_r:httpd_t:s0    1234 ?  00:00:01 httpd
system_u:system_r:httpd_t:s0    1235 ?  00:00:00 httpd

$ id -Z
unconfined_u:unconfined_r:unconfined_t:s0
```

Reading these:

- The directory is `httpd_sys_content_t` — the type httpd is permitted to read.
- The process is `httpd_t` — a confined domain.
- **Your shell is `unconfined_t`** — under the targeted policy, interactive user sessions are not confined, which is why you can do as you please while httpd cannot.

The relationship being enforced is a policy rule of the form "allow `httpd_t` read on `httpd_sys_content_t`":

```bash
sesearch -A -s httpd_t -t httpd_sys_content_t -c file 2>/dev/null | head
```

More context-aware commands:

```bash
ps -eZ
ps -axZ | grep -v unconfined
ss -tlnpZ | grep :80
find /var/www -printf '%Z %p\n' 2>/dev/null | head
```

**Task 5.**

```bash
sudo dnf install -y httpd
```

**Task 6.**

Do it the wrong way first:

```bash
ls -Zd /web
curl http://localhost/           # works
```

It works. It even survives a plain reboot. But the policy database has no record of it:

```bash
sudo semanage fcontext -l -C | grep web        # nothing

```

```text
Would relabel /web from unconfined_u:object_r:httpd_sys_content_t:s0 to unconfined_u:object_r:default_t:s0
```

```bash
sudo restorecon -Rv /web

curl -s -o /dev/null -w '%{http_code}\n' http://localhost/
```

```text
403
```

**Broken.** Anything triggers this: a `restorecon` on a parent path, `fixfiles`, an RPM update, `touch /.autorelabel`, or a package `%post` script.

| | `chcon` | `semanage fcontext` + `restorecon` |
| --- | --- | --- |
| Immediate | Yes | After `restorecon` |
| In the policy database | **No** | **Yes** |
| Survives `restorecon` | **No** | **Yes** |
| Survives `/.autorelabel` | **No** | **Yes** |
| Correct exam answer | **No** | **Yes** |

Restore the correct approach:

```bash
sudo semanage fcontext -a -t httpd_sys_content_t "/web(/.*)?"
sudo restorecon -Rv /web

```

**`chcon` has exactly one legitimate use on the exam: a quick test to confirm that the label is the problem.** Then do it properly with `semanage`.


```bash

```

```text
403
```


```text
Relabeled /var/www/html/moved.html from unconfined_u:object_r:user_home_t:s0 to unconfined_u:object_r:httpd_sys_content_t:s0
moved file
```

**No `semanage` needed here**, because `/var/www/html` is a standard path with a correct default rule. Only the label on this one file was wrong, and `restorecon` restores what the policy already specifies.

Contrast with `cp`:

```bash
echo "copied" > ~/copied.html
sudo cp ~/copied.html /var/www/html/
ls -Z /var/www/html/copied.html
```

```text
unconfined_u:object_r:httpd_sys_content_t:s0 /var/www/html/copied.html
```

**`cp` creates a new file, which inherits the destination directory's type. Correct by default.**

| Operation | Label | Needs `restorecon` |
| --- | --- | --- |
| `cp src dst/` | **Inherits from `dst`** | No |
| **`cp -a src dst/`** | **Keeps the source label** | **Yes** |
| `cp -p src dst/` | Inherits from `dst` | No |
| **`mv src dst/`** | **Keeps the source label** | **Yes** |
| `tar xf` | Inherits from the directory | Usually no |
| **`tar --selinux -xf`** | Restores archived labels | Check |
| `rsync -a` | Inherits, unless `-X` | Usually no |
| **`rsync -aX`** | Preserves xattrs, i.e. labels | **Yes** |

**Habit: after any `mv`, `cp -a`, `tar x`, or `rsync -aX` into a service directory, run `restorecon -Rv`.** It costs a second and prevents the most common SELinux failure on the exam.

Three separate layers block this. Configure httpd first:

```bash
sudo sed -i 's/^Listen 80/Listen 8090/' /etc/httpd/conf/httpd.conf
grep '^Listen' /etc/httpd/conf/httpd.conf

```

```text

```

```bash

sudo journalctl -xeu httpd | tail -20
```

```text
(13)Permission denied: AH00072: make_sock: could not bind to address [::]:8090
```

**"Permission denied" on a bind is the signature of an SELinux port label problem.** Confirm:

```bash
sudo ausearch -m AVC -ts recent | tail -5
```

```text
avc: denied { name_bind } for pid=... comm="httpd" src=8090
  scontext=system_u:system_r:httpd_t:s0
  tcontext=system_u:object_r:unreserved_port_t:s0 tclass=tcp_socket
```

`8090` is `unreserved_port_t`; `httpd_t` may only bind `http_port_t`. Check and fix:

```bash
semanage port -l | grep '^http_port_t'
```

```text
http_port_t     tcp   80, 81, 443, 488, 8008, 8009, 8443, 9000
```

```bash
sudo semanage port -a -t http_port_t -p tcp 8090
semanage port -l | grep '^http_port_t'
```

```text
http_port_t     tcp   8090, 80, 81, 443, 488, 8008, 8009, 8443, 9000
```

Now it starts:

```bash
sudo systemctl restart httpd
systemctl is-active httpd
ss -tlnp | grep 8090
```

Third layer, the firewall:

```bash
sudo firewall-cmd --permanent --add-port=8090/tcp
sudo firewall-cmd --reload
firewall-cmd --list-ports
```

Verify locally and remotely:

```bash
curl http://localhost:8090/
# from server2:
curl http://192.168.56.11:8090/
```

**Every non-standard port task has these three layers:**

| Layer | Symptom if missed | Fix |
| --- | --- | --- |
| Service config | Listens on the old port | Edit the config, restart |
| **SELinux port label** | **Service fails to start, "Permission denied" on bind** | **`semanage port -a -t TYPE -p tcp N`** |
| **Firewall** | **Starts fine; unreachable from other hosts** | **`firewall-cmd --permanent --add-port=`** |

**Distinguish the two failure modes carefully.** SELinux prevents the service from *starting*; the firewall lets it start and blocks the *traffic*. So "will not start" points at SELinux, and "runs but unreachable" points at the firewall.

If `-a` reports the port is already defined, use `-m`:

```bash
sudo semanage port -a -t http_port_t -p tcp 8090
# ValueError: Port tcp/8090 already defined
semanage port -l | grep 8090          # find out what owns it
sudo semanage port -m -t http_port_t -p tcp 8090
```

Revert:

```bash
sudo semanage port -d -t http_port_t -p tcp 8090
sudo sed -i 's/^Listen 8090/Listen 80/' /etc/httpd/conf/httpd.conf
sudo systemctl restart httpd
```

**Task 13.**

Four steps, and missing any one locks you out or fails the task.

```bash
# 1. SELinux port label FIRST — before restarting sshd
sudo semanage port -a -t ssh_port_t -p tcp 2222
semanage port -l | grep ssh_port_t

# 2. Firewall — before restarting sshd
sudo firewall-cmd --permanent --add-port=2222/tcp
sudo firewall-cmd --reload

# 3. sshd configuration
sudo sed -i 's/^#\?Port .*/Port 2222/' /etc/ssh/sshd_config

sudo sshd -t                              # ALWAYS validate before restarting

# 4. Restart
sudo systemctl restart sshd
ss -tlnp | grep 2222
```

**Order matters enormously.** Restart sshd before labelling the port and it fails to start — and if your only access is SSH, you are locked out with no way back except the console.

```text
$ semanage port -l | grep ssh_port_t
ssh_port_t     tcp   2222, 22
```

Test from another terminal **before closing the one you have**:

```bash

```

**Keep the working session open until the new one succeeds.** This is the same discipline as the networking chapter.

To allow both ports during the transition:

```bash
sudo tee -a /etc/ssh/sshd_config >/dev/null <<'EOF'

Port 2222
EOF

ss -tlnp | grep sshd
```


```text
403
```

Find it:

```bash
sudo ausearch -m AVC -ts recent
```

```text
type=AVC msg=audit(1692364800.123:456): avc:  denied  { getattr } for
  pid=2345 comm="httpd" path="/badweb/index.html" dev="dm-0" ino=67890
  scontext=system_u:system_r:httpd_t:s0
  tcontext=unconfined_u:object_r:default_t:s0
  tclass=file permissive=0
```

Field by field:

| Field | Value | What it tells you |
| --- | --- | --- |
| `avc: denied { getattr }` | getattr | **The operation blocked** — stat, read, write, name_bind, etc. |
| `comm="httpd"` | httpd | **The program** |
| `path=` | `/badweb/index.html` | **The object** |
| `pid=` | 2345 | The process |
| **`scontext=`** | **`httpd_t`** | **The subject's type — a confined httpd** |
| **`tcontext=`** | **`default_t`** | **The object's type — WRONG for web content** |
| `tclass=file` | file | Object class: `file`, `dir`, `tcp_socket`, `process` |
| **`permissive=0`** | **0** | **Actually blocked.** `1` would mean permissive mode |

**Diagnosis: `httpd_t` is not permitted `getattr` on `default_t`. The file has the wrong label.** The expected label is `httpd_sys_content_t`.

Compare against a known-good path:

```bash
ls -Zd /var/www/html /badweb
```

Fix, permanently:

```bash
sudo semanage fcontext -a -t httpd_sys_content_t "/badweb(/.*)?"
sudo restorecon -Rv /badweb
ls -Zd /badweb
curl http://localhost/
```

More ways to reach the same log:

```bash
sudo ausearch -m AVC -ts today -i               # -i resolves numbers to names
sudo ausearch -m AVC -c httpd
sudo ausearch -m AVC -ts recent | audit2allow -w
sudo journalctl -t setroubleshoot --since today
sudo grep denied /var/log/audit/audit.log | tail -3
```

**Read `scontext` and `tcontext` first.** Those two types plus the denied operation are the entire diagnosis, and they tell you whether the answer is a label, a port, or a boolean:

| `tcontext` type | Likely fix |
| --- | --- |
| `default_t`, `user_home_t`, `admin_home_t` on a file | **Wrong file label** → `semanage fcontext` + `restorecon` |
| `unreserved_port_t`, `*_port_t` with `name_bind` | **Wrong port label** → `semanage port -a` |
| A correct-looking type, operation still denied | **A boolean** → `semanage boolean -l \| grep` |

**Task 16.**

`httpd` is active, `curl localhost` returns 403. Work through the layers in order.

```bash
# 1. Is httpd really running and listening?
systemctl is-active httpd
ss -tlnp | grep :80
```

```bash
# 2. What is the error, in httpd's own words?
sudo tail -5 /var/log/httpd/error_log
```

```text
[core:error] [client ::1:41234] AH00035: access to / denied (filesystem path
'/web/index.html') because search permissions are missing on a component of the path
```

**Note that httpd's log distinguishes the two causes.** "Search permissions are missing on a component of the path" is a DAC problem; an SELinux denial says "Permission denied" and appears in the audit log.

```bash
# 3. Is it SELinux? Check for denials
sudo ausearch -m AVC -ts recent
```

If there are denials, follow Task 14. If there are none, SELinux is not the cause.

```bash
# 4. Confirm by testing in permissive mode
sudo setenforce 0
curl -s -o /dev/null -w '%{http_code}\n' http://localhost/
sudo setenforce 1              # PUT IT BACK IMMEDIATELY
```

**200 in permissive means SELinux. Still 403 means it is not SELinux.**

```bash
# 5. Standard permissions on every component of the path
namei -l /web/index.html
```

```text
f: /web/index.html
 dr-xr-xr-x root root /
 drwx------ root root web          <-- no execute for others
 -rw-r--r-- root root index.html
```

**There it is.** `/web` is `700`, so the `apache` user cannot traverse it. See `12.md` for why `namei -l` is the right tool.

```bash
sudo chmod 755 /web
sudo chmod 644 /web/index.html
curl http://localhost/
```

```bash
# 6. httpd configuration
grep -i '^DocumentRoot' /etc/httpd/conf/httpd.conf
grep -rn 'Require' /etc/httpd/conf.d/ /etc/httpd/conf/httpd.conf
sudo httpd -t                  # validate the config
```

A missing `Require all granted` for a non-default DocumentRoot also produces 403.

**The full 403 checklist:**

| Cause | Detect with | Fix |
| --- | --- | --- |
| **Wrong SELinux label** | `ausearch -m AVC`, `ls -Zd` | `semanage fcontext` + `restorecon` |
| **Missing execute on a parent directory** | **`namei -l`** | `chmod 755` |
| Missing read on the file | `ls -l` | `chmod 644` |
| No `Require all granted` | `grep -r Require /etc/httpd` | Add a `<Directory>` block |
| Missing index file | `ls DocumentRoot` | Create `index.html` |
| Wrong DocumentRoot | `grep DocumentRoot` | Correct it |

**Both DAC and SELinux must allow.** A perfect label with `chmod 700` on the parent fails, and `chmod 777` with a wrong label fails too. Check `namei -l` and `ls -Z` together.

Policy modules are **persistent automatically** — they are installed into the policy store, so no `-P` and no config file.

Remove:

```bash
sudo semodule -r mycustompol
sudo semodule -l | grep mycustompol
rm -f /tmp/mycustompol.*
```

| Fix | Preference | When |
| --- | --- | --- |
| **`semanage fcontext` + `restorecon`** | **1st** | Wrong file label — most denials |
| **`semanage port -a`** | **1st** | Wrong port label |
| **`setsebool -P`** | **2nd** | A boolean exists for the behaviour |
| `semodule -i` from `audit2allow` | **Last** | Nothing above applies |
| `setenforce 0` | **Never** | — |

**On the exam, a label or boolean is nearly always the intended answer.** Reach for `audit2allow` only when you have checked `restorecon -Rvn`, `semanage fcontext -l`, and `semanage boolean -l | grep` and none of them apply.

**Task 18.**

```bash
sudo touch /.autorelabel
sudo reboot
```

The system relabels every file during boot and reboots again. **On a large filesystem this takes many minutes, and there is no meaningful progress output** — do not interrupt it.

Alternatives:

```bash
sudo restorecon -Rv /                 # relabel now, no reboot
sudo fixfiles relabel                 # same, via the wrapper
sudo fixfiles -f relabel              # also empties /tmp
sudo fixfiles restore                 # restore contexts
sudo fixfiles -R httpd restore        # only files owned by the httpd package
```

**When you need a relabel:**

- After changing `SELINUX=disabled` to `permissive` or `enforcing`.
- **After changing the root password via `rd.break`** — see `16.md`. This is the exam-critical case.
- After restoring files from a backup that lacked xattrs.
- When labels are widely wrong across the filesystem.

**When you do not:** a single mislabelled directory. Use `restorecon -Rv /path`, which takes a second instead of ten minutes.

The `rd.break` connection is worth repeating because it is an almost-certain exam task:

```bash
# In the rd.break shell, after passwd root:
touch /.autorelabel
```

**Without it, `/etc/shadow` is left labelled `unlabeled_t`** and the system will not let anyone log in — you have fixed the password and broken the login. See `16.md`.

Confirm the relabel happened:

```bash
ls -l /.autorelabel 2>/dev/null      # should be GONE after the reboot
sudo restorecon -Rvn /etc            # should be silent
ls -Z /etc/shadow
```

```text
system_u:object_r:shadow_t:s0 /etc/shadow
```

**Task 19.**

```bash
grep '^SELINUX=' /etc/selinux/config
getenforce
```

```text
SELINUX=disabled
Disabled
```

**Do not jump straight to `enforcing`.** With SELinux disabled, newly created files were never labelled, so an immediate `enforcing` boot denies critical access and can leave the system unbootable.

The safe route, in three stages:

```bash
# Stage 1: permissive, and request a full relabel
sudo sed -i 's/^SELINUX=.*/SELINUX=permissive/' /etc/selinux/config
grep '^SELINUX=' /etc/selinux/config
sudo touch /.autorelabel
sudo reboot
```

The machine relabels everything, then reboots again. Be patient.

```bash
# Stage 2: verify in permissive mode
getenforce                                  # Permissive
sestatus
sudo ausearch -m AVC -ts boot               # any denials logged?
sudo restorecon -Rvn / 2>/dev/null | head   # anything still mislabelled?
```

**Permissive mode logs denials without enforcing them, so this stage tells you exactly what would break** before it breaks. Fix anything that appears.

```bash
# Stage 3: enforcing
sudo sed -i 's/^SELINUX=.*/SELINUX=enforcing/' /etc/selinux/config
sudo setenforce 1
getenforce
sestatus | grep -i mode
sudo reboot
```

After the final reboot:

```bash
getenforce                    # Enforcing
sestatus
sudo ausearch -m AVC -ts boot
systemctl --failed
```

**The path is `disabled` → `permissive` + relabel → verify → `enforcing`.** Skipping the permissive stage is how people produce an unbootable machine, which on an exam means starting over.

If you do end up with an unbootable system, add `enforcing=0` or `selinux=0` to the kernel command line at the GRUB prompt (see `17.md`) to get in and repair it.

Everything must be true:

- **`getenforce` and `SELINUX=` in the config agree.**
- Your fcontext rules, port labels, and booleans appear in the `-C` output.
- **Booleans show `(on, on)`, not `(on, off)`.**
- **`restorecon -Rvn` is silent** on every path you configured.
- No unresolved AVC denials.


**`ausearch -m AVC -ts boot` is the single best post-reboot check.** Empty output means nothing SELinux-related broke during startup. Anything there needs attention before you move on.

The three things most likely to have evaporated:

| Symptom after reboot | Cause |
| --- | --- |
| `getenforce` says Permissive | **`setenforce` used; config not updated** |

## Persistence Check

| Change | Non-persistent | **Persistent** |
| --- | --- | --- |
| Mode | `setenforce 0/1` | **`/etc/selinux/config`** (`SELINUX=enforcing`) |
| File context | **`chcon -t TYPE path`** | **`semanage fcontext -a -t TYPE "path(/.*)?"` + `restorecon -Rv path`** |
| Boolean | **`setsebool BOOL on`** | **`setsebool -P BOOL on`** |
| Port label | — | **`semanage port -a -t TYPE -p tcp N`** — always persistent |
| Policy module | — | **`semodule -i mod.pp`** — always persistent |

**Three flags decide whether you score:**

1. **`/etc/selinux/config`**, not `setenforce`.
2. **`semanage fcontext` + `restorecon`**, not `chcon`.
3. **`setsebool -P`**, not `setsebool`.

```bash
# The four-command SELinux pre-reboot check
getenforce; grep '^SELINUX=' /etc/selinux/config
semanage boolean -l -C            # every entry must read (on, on)
sudo semanage fcontext -l -C
sudo restorecon -Rvn /path/you/changed    # must be silent
```

## Exam Tips

- **Never disable SELinux.** It is graded, and disabling it fails other tasks. `setenforce 0` is a diagnostic, used for seconds, then reversed.
- **`setenforce` does not persist. `/etc/selinux/config` does.** Set both, and check `sestatus` shows the same value on both mode lines.
- **`chcon` is the wrong answer.** Use **`semanage fcontext -a -t TYPE "/path(/.*)?"` then `restorecon -Rv /path`**. `restorecon` will silently undo a `chcon`.
- **Memorise the regex `"(/.*)?"`** and quote it. `"/web(/.*)?"` covers the directory and its contents.
- **`setsebool` needs `-P`** to persist. Verify with `semanage boolean -l`, which shows `(current, permanent)` — `getsebool` shows only the current value and hides the error.
- **`mv` preserves the old label; `cp` inherits the destination's.** After `mv`, `cp -a`, `tar x`, or `rsync -aX` into a service directory, run `restorecon -Rv`.
- **`restorecon -Rvn PATH`** is a risk-free dry run that reports every mislabelled file. Silence means correct.
- **Non-standard port = three fixes**: the service config, `semanage port -a`, and `firewall-cmd --permanent --add-port`. **SELinux stops the service starting; the firewall stops the traffic.**
- **`semanage port -a` fails if the port is already defined — use `-m`.**
- **Read AVC denials for `scontext`, `tcontext`, and the denied operation.** `tcontext=default_t` on a file means a label problem; `unreserved_port_t` with `name_bind` means a port problem.
- **`sudo ausearch -m AVC -ts recent`** is the command to have in your fingers. `-ts boot` after a reboot.
- **`sealert -a /var/log/audit/audit.log`** gives a plain-English fix if `setroubleshoot-server` is installed. Trust its `restorecon` suggestions, not its `audit2allow` ones.
- **Find booleans by searching**: `semanage boolean -l | grep -i <keyword>`. Do not try to memorise them.
- **`-C` shows only your customisations**: `semanage fcontext -l -C`, `semanage port -l -C`, `semanage boolean -l -C`. Your verification checklist.
- **`semanage` is in `policycoreutils-python-utils`.** Install it if the command is missing.
- **Both DAC and SELinux must allow.** For a 403, check `namei -l` as well as `ls -Z`.
- **`audit2allow` is the last resort**, after ruling out labels and booleans.
- **`touch /.autorelabel` after `rd.break`**, always. Otherwise `/etc/shadow` is left unlabelled and nobody can log in.
- **Going from disabled to enforcing: `permissive` + relabel first, then `enforcing`.** Never jump straight there.
- **After a reboot, run `ausearch -m AVC -ts boot`.** Empty output means SELinux broke nothing during startup.
