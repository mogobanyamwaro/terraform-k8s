# 25. Hostnames And Name Resolution

**Objective:** Configure hostname resolution.

A short objective with a small number of files, but it appears in almost every other task indirectly — NFS mounts, SSH targets, and chrony servers are all specified by name.

## Concept Refresher

### Setting the hostname

```bash
hostnamectl                                        # full status
hostnamectl status                                 # same thing
hostname                                           # just the name
hostnamectl hostname                               # RHEL 9+ syntax
sudo hostnamectl set-hostname server1.lab.example.com
```

```text
$ hostnamectl
 Static hostname: server1.lab.example.com
       Icon name: computer-vm
         Chassis: vm
      Machine ID: 8f3a...
         Boot ID: 4b2c...
  Virtualization: vmware
Operating System: Red Hat Enterprise Linux 10.0 (Coughlan)
     CPE OS Name: cpe:/o:redhat:enterprise_linux:10::baseos
          Kernel: Linux 6.12.0-55.el10.x86_64
    Architecture: x86-64
```

Three kinds of hostname exist:

| Kind | Meaning | Stored |
| --- | --- | --- |
| **Static** | The persistent, configured name | **`/etc/hostname`** |
| Transient | Set by DHCP or mDNS at runtime | Kernel only |
| Pretty | A free-form label, e.g. "Doug's Laptop" | `/etc/machine-info` |

```bash
sudo hostnamectl set-hostname server1.lab.example.com          # static (what you want)
sudo hostnamectl set-hostname "Lab Server 1" --pretty
sudo hostnamectl set-hostname server1 --transient
```

**`hostnamectl set-hostname` writes `/etc/hostname` and persists. The legacy `hostname foo` command changes the kernel only and is lost on reboot.** Same distinction as `ip addr add` versus `nmcli con mod`.

```bash
cat /etc/hostname
```

**Use the fully qualified name** when a task gives you one: `server1.lab.example.com`, not `server1`. And note that your shell prompt does not update until you start a new shell:

```bash
exec bash          # or just log out and back in
```

### Name resolution order

```text
   getaddrinfo("server2.lab.example.com")
              │
   ┌──────────▼───────────────────────────────┐
   │  /etc/nsswitch.conf                      │
   │     hosts: files dns myhostname          │
   └──────────┬───────────────────────────────┘
              │
      ┌───────▼────────┐   found?   ┌─────────┐
      │  1. files      │──────yes──►│ ANSWER  │
      │   /etc/hosts   │            └─────────┘
      └───────┬────────┘
              │ no
      ┌───────▼────────┐   found?   ┌─────────┐
      │  2. dns        │──────yes──►│ ANSWER  │
      │ /etc/resolv.conf│           └─────────┘
      └───────┬────────┘
              │ no
        ┌─────▼──────┐
        │ NXDOMAIN   │
        └────────────┘
```

**`/etc/hosts` is consulted before DNS.** That is what makes it a useful override, and also what makes a stale entry there so confusing to debug.

```bash
cat /etc/nsswitch.conf | grep '^hosts'
```

```text
hosts:      files dns myhostname
```

### /etc/hosts

```bash
sudo vim /etc/hosts
```

```text
127.0.0.1   localhost localhost.localdomain localhost4
::1         localhost localhost.localdomain localhost6
192.168.56.11  server1.lab.example.com server1
192.168.56.12  server2.lab.example.com server2
```

Format: **IP address, then the canonical FQDN, then any short aliases**, whitespace separated.

```bash
echo "192.168.56.12  server2.lab.example.com server2" | sudo tee -a /etc/hosts
```

**Put the FQDN first.** Some tools take the first name as canonical, and Kerberos and NFS in particular care. **Never remove the `127.0.0.1 localhost` line** — a great deal of software breaks without it.

### /etc/resolv.conf

```bash
cat /etc/resolv.conf
```

```text
# Generated by NetworkManager
search lab.example.com
nameserver 192.168.56.1
nameserver 8.8.8.8
```

| Directive | Meaning |
| --- | --- |
| `nameserver` | A DNS server to query. **Up to three are used** |
| `search` | Domains appended to unqualified names |
| `domain` | A single search domain; superseded by `search` |
| `options timeout:2` | Seconds before trying the next server |
| `options rotate` | Round-robin across the servers |

**This file is generated by NetworkManager. Editing it by hand is wrong — your changes will be overwritten.** Set DNS through the connection profile instead:

```bash
sudo nmcli con mod ens160 ipv4.dns "192.168.56.1 8.8.8.8"
sudo nmcli con mod ens160 ipv4.dns-search lab.example.com
sudo nmcli con up ens160
cat /etc/resolv.conf                    # now reflects the profile
```

If a task truly requires a hand-managed `resolv.conf`, tell NetworkManager to leave it alone:

```bash
sudo nmcli con mod ens160 ipv4.ignore-auto-dns yes
```

or globally, in `/etc/NetworkManager/conf.d/90-dns-none.conf`:

```ini
[main]
dns=none
```

then `systemctl reload NetworkManager`. **But the exam-correct answer is almost always to configure DNS via `nmcli`.**

### Query tools

```bash
# The RIGHT tool for the exam: it uses nsswitch, so it sees /etc/hosts
getent hosts server2.lab.example.com
getent ahosts server2.lab.example.com          # all addresses, both families

# DNS-only tools: they IGNORE /etc/hosts
host server2.lab.example.com
dig server2.lab.example.com
dig +short server2.lab.example.com
dig -x 192.168.56.12                           # reverse lookup
nslookup server2.lab.example.com

# Reverse lookups
getent hosts 192.168.56.12
host 192.168.56.12
```

**This distinction wins marks.** `getent hosts` follows `/etc/nsswitch.conf`, so it consults `/etc/hosts` and then DNS — exactly like a real application. `host` and `dig` talk to DNS servers directly and **never look at `/etc/hosts`**.

So if `ping server2` works but `dig server2.lab.example.com` returns nothing, the name is resolving from `/etc/hosts` and there is no DNS record. That is not a fault if the task asked you to add a hosts entry.

Install the tools if missing:

```bash
sudo dnf install -y bind-utils              # provides host, dig, nslookup
```

### Reading dig output

```bash
dig server2.lab.example.com
```

```text
;; QUESTION SECTION:
;server2.lab.example.com.	IN	A

;; ANSWER SECTION:
server2.lab.example.com. 3600 IN A	192.168.56.12

;; Query time: 1 msec
;; SERVER: 192.168.56.1#53(192.168.56.1) (UDP)
```

Things to notice: the **ANSWER SECTION** is the result, **SERVER** tells you which resolver replied, and `status: NXDOMAIN` in the header means the name does not exist. `dig +short` gives just the answer, which is what you want when checking quickly.

### Troubleshooting resolution

```bash
# 1. Is there a resolver configured at all?
cat /etc/resolv.conf

# 2. Is the name in /etc/hosts?
grep server2 /etc/hosts

# 3. What does the system-level resolver return?
getent hosts server2.lab.example.com

# 4. What does DNS alone return?
dig +short server2.lab.example.com

# 5. Is the DNS server reachable?
ping -c2 192.168.56.1
dig @192.168.56.1 server2.lab.example.com

# 6. Is the search domain being applied?
getent hosts server2
```

| Symptom | Cause |
| --- | --- |
| `getent` works, `dig` fails | Resolving from **`/etc/hosts`**; no DNS record |
| `dig` works, `getent` fails | `/etc/nsswitch.conf` broken, or a bad `/etc/hosts` entry shadowing it |
| Both fail, IP ping works | **No resolver, or the resolver is unreachable** |
| FQDN works, short name fails | **Missing `search` domain** |
| Slow lookups then success | The first `nameserver` is unreachable; it times out and falls through |

## Solutions

**Task 1.**

```bash
sudo hostnamectl set-hostname server1.lab.example.com
```

Verify:

```bash
hostnamectl
hostname
cat /etc/hostname
hostname -f              # FQDN
hostname -s              # short name
```

```text
$ cat /etc/hostname
server1.lab.example.com
$ hostname -s
server1
```

**Your prompt will not change until you start a new shell**, because bash captured the hostname at startup:

```bash
exec bash
```

Or log out and back in. **This confuses people into thinking the command failed** — check `hostname`, not the prompt.

**Use the FQDN when the task gives one.** `set-hostname server1` when the task said `server1.lab.example.com` is a wrong answer.

**Task 2.**

```bash
hostnamectl status
hostnamectl hostname                    # static
hostnamectl --static
hostnamectl --transient
hostnamectl --pretty
```

| Kind | Set with | Stored in | Persists |
| --- | --- | --- | --- |
| **Static** | `hostnamectl set-hostname NAME` | **`/etc/hostname`** | **Yes** |
| Transient | `hostnamectl set-hostname NAME --transient`, DHCP | Kernel | No |
| Pretty | `hostnamectl set-hostname "NAME" --pretty` | `/etc/machine-info` | Yes |

```bash
cat /etc/hostname
cat /etc/machine-info 2>/dev/null
```

**The static hostname in `/etc/hostname` is the one that matters.** A transient hostname can be pushed by a DHCP server and overrides the static one at runtime, which is worth knowing if a hostname mysteriously reverts — the fix is to stop NetworkManager from accepting it:

```bash
sudo nmcli con mod ens160 ipv4.dhcp-hostname ""
```

**Task 3.**

The legacy way:

```bash
sudo hostname temporary-name
hostname                          # temporary-name
cat /etc/hostname                 # STILL the old name — nothing written
```

```bash
sudo reboot
# after reboot:
hostname                          # back to the old name
```

The correct way:

```bash
sudo hostnamectl set-hostname server1.lab.example.com
cat /etc/hostname                 # server1.lab.example.com
```

| Command | Writes a file | Survives reboot |
| --- | --- | --- |
| `hostname NAME` | **No** | **No** |
| `sysctl kernel.hostname=NAME` | No | No |
| **`hostnamectl set-hostname NAME`** | **`/etc/hostname`** | **Yes** |
| Editing `/etc/hostname` directly | Yes | **Yes**, but not active until reboot |

If you do edit `/etc/hostname` by hand, apply it without rebooting:

```bash
sudo hostnamectl set-hostname "$(cat /etc/hostname)"
```

**Same pattern as everywhere else on this exam**: the quick command touches the kernel, the right command writes a file.

**Task 4.**

```bash
echo "192.168.56.12  server2.lab.example.com server2" | sudo tee -a /etc/hosts
```

Or with an editor:

```bash
sudo vim /etc/hosts
```

```text
127.0.0.1   localhost localhost.localdomain localhost4 localhost4.localdomain4
::1         localhost localhost.localdomain localhost6 localhost6.localdomain6
192.168.56.11  server1.lab.example.com server1
192.168.56.12  server2.lab.example.com server2
```

Three points:

- **`sudo tee -a`, not `sudo echo >>`.** The redirection happens in your unprivileged shell, so `sudo echo ... >> /etc/hosts` fails with "Permission denied". See `02.md`.
- **`-a` appends.** `tee` without `-a` truncates the file, which would delete your `localhost` lines.
- **FQDN first, aliases after.** `192.168.56.12 server2.lab.example.com server2` — the first name is canonical.

Verify:

```bash
cat /etc/hosts
getent hosts server2
getent hosts server2.lab.example.com
ping -c1 server2
```

**Task 5.**

The tool that consults `/etc/hosts`:

```bash
getent hosts server2.lab.example.com
```

```text
192.168.56.12   server2.lab.example.com server2
```

The tools that do not:

```bash
dig +short server2.lab.example.com
host server2.lab.example.com
```

```text
$ dig +short server2.lab.example.com
(no output)

$ host server2.lab.example.com
Host server2.lab.example.com not found: 3(NXDOMAIN)
```

**Both results are correct**, and understanding why is the point:

| Tool | Path | Sees `/etc/hosts` |
| --- | --- | --- |
| **`getent hosts`** | `nsswitch.conf` → files, dns | **Yes** |
| `ping`, `ssh`, `curl`, `mount` | Same as getent | **Yes** |
| `dig`, `host`, `nslookup` | **Straight to a DNS server** | **No** |

So `dig` returning NXDOMAIN while `ping` works means the name is coming from `/etc/hosts`. **This is not a fault** — it is exactly what a task asking you to add a hosts entry wants.

**On the exam, verify with `getent hosts`**, because it takes the same path a real application takes. Use `dig` only when you specifically want to test DNS itself.

**Task 6.**

```bash
sudo nmcli connection modify ens160 ipv4.dns "192.168.56.1 8.8.8.8"
sudo nmcli connection modify ens160 ipv4.dns-search lab.example.com
sudo nmcli connection up ens160
```

Verify at both levels:

```bash
nmcli -f ipv4.dns,ipv4.dns-search connection show ens160
cat /etc/resolv.conf
```

```text
ipv4.dns:          192.168.56.1,8.8.8.8
ipv4.dns-search:   lab.example.com
```

```text
# Generated by NetworkManager
search lab.example.com
nameserver 192.168.56.1
nameserver 8.8.8.8
```

**Configure DNS through the connection profile, never by editing `/etc/resolv.conf`.** The profile is the persistent source of truth; `resolv.conf` is generated output.

To append rather than replace:

```bash
sudo nmcli con mod ens160 +ipv4.dns 1.1.1.1
```

**Without the `+` you replace the entire list**, which is how a working resolver quietly disappears.

**Task 7.**

```bash
head -1 /etc/resolv.conf
```

```text
# Generated by NetworkManager
```

**That first line is the warning.** NetworkManager rewrites this file whenever a connection activates, on reboot, or on a DHCP lease renewal. Prove it:

```bash
echo "nameserver 1.2.3.4" | sudo tee -a /etc/resolv.conf
cat /etc/resolv.conf                     # your line is there
sudo nmcli con up ens160
cat /etc/resolv.conf                     # your line is GONE
```

This is a real exam trap. A candidate adds a nameserver to `resolv.conf`, verifies it with `dig`, and loses the marks because the grader reboots and NetworkManager regenerates the file.

| Approach | Persists |
| --- | --- |
| Edit `/etc/resolv.conf` | **No — overwritten** |
| **`nmcli con mod ... ipv4.dns`** | **Yes** |
| `nmcli con mod ... ipv4.ignore-auto-dns yes` + hand-edit | Yes, but convoluted |
| `dns=none` in `/etc/NetworkManager/conf.d/` + hand-edit | Yes, but rarely what is wanted |

**Task 8.**

```bash
getent hosts server2                     # unqualified
ping -c1 server2
```

With `search lab.example.com` in effect, resolving `server2` causes the resolver to try `server2.lab.example.com`. Watch it happen:

```bash
dig +search +short server2
dig +short server2.lab.example.com
```

Note that in this lab the answer comes from `/etc/hosts` because we added the `server2` alias there. To test the DNS search path specifically you need a real DNS zone. The mechanism is the same:

```bash
grep search /etc/resolv.conf
```

Multiple search domains:

```bash
sudo nmcli con mod ens160 ipv4.dns-search "lab.example.com,example.com"
sudo nmcli con up ens160
grep search /etc/resolv.conf
```

```text
search lab.example.com example.com
```

**A missing search domain is the cause of "the FQDN works but the short name does not".** See Task 13.

**Task 9.**

```bash
getent hosts 192.168.56.12
```

```text
192.168.56.12   server2.lab.example.com server2
```

```bash
dig -x 192.168.56.12
dig +short -x 192.168.56.12
host 192.168.56.12
nslookup 192.168.56.12
```

**`getent hosts <ip>` reads `/etc/hosts` backwards**, so it succeeds for anything you added there. `dig -x` performs a real PTR lookup in `in-addr.arpa` and needs a reverse DNS zone, which a lab usually lacks:

```text
$ dig +short -x 192.168.56.12
(no output — no PTR record)
```

Again, both answers are correct. **Reverse lookups matter for NFS and Kerberos**, so if a service complains about a name mismatch, check `getent hosts <ip>` first.

**Task 10.**

```bash
dig @192.168.56.1 server2.lab.example.com
dig @8.8.8.8 redhat.com
dig @8.8.8.8 +short redhat.com
host server2.lab.example.com 192.168.56.1
nslookup server2.lab.example.com 192.168.56.1
```

**`@server` bypasses `/etc/resolv.conf` entirely**, which is how you separate "my resolver is broken" from "the record does not exist":

```bash
dig +short redhat.com                 # via configured resolver: fails
dig @8.8.8.8 +short redhat.com        # via a known-good resolver: works
```

Those two results together tell you the problem is your configured resolver, not DNS in general. If both fail, the record genuinely does not exist or you have no network path at all.

Useful extras:

```bash
dig +trace redhat.com                 # walk the delegation from the root
dig MX redhat.com
dig NS example.com
dig ANY example.com
```

**Task 11.**

```bash
grep '^hosts' /etc/nsswitch.conf
```

```text
hosts:      files dns myhostname
```

Read left to right — **the first source that answers wins**:

| Source | Consults |
| --- | --- |
| `files` | **`/etc/hosts`** |
| `dns` | The `nameserver` entries in `/etc/resolv.conf` |
| `myhostname` | systemd's built-in resolution of the local hostname |
| `mdns4_minimal` | Avahi / `.local` names, if installed |
| `resolve` | `systemd-resolved`, if in use |

Consequences worth remembering:

- **`/etc/hosts` beats DNS.** A stale entry there silently overrides a correct DNS record — always `grep /etc/hosts` when a name resolves to the wrong address.
- Reordering to `dns files` would make DNS authoritative, but there is rarely a reason.
- `myhostname` is why your own hostname resolves even with no DNS and no hosts entry.

The whole file governs more than hostnames:

```bash
grep -Ev '^\s*#|^\s*$' /etc/nsswitch.conf
```

```text
passwd:     files sss
group:      files sss
shadow:     files sss
hosts:      files dns myhostname
```

That is the same mechanism that makes `getent passwd` show both local and directory users.

**Task 12.**

Symptom: routing works, name resolution does not.

```bash
ping -c2 8.8.8.8              # OK — network and routing are fine
ping -c2 google.com           # ping: google.com: Name or service not known
```

**"Name or service not known" is a resolver failure, not a network failure.** Diagnose:

```bash
cat /etc/resolv.conf
```

```text
# Generated by NetworkManager
(empty — no nameserver at all)
```

That is the fault. Other possibilities in order of likelihood:

```bash
# a. No nameserver configured
cat /etc/resolv.conf

# b. Nameserver configured but unreachable
grep nameserver /etc/resolv.conf
ping -c2 <that address>
dig @<that address> redhat.com

# c. nsswitch.conf missing 'dns'
grep '^hosts' /etc/nsswitch.conf

# d. A known-good resolver works, proving it is yours that is broken
dig @8.8.8.8 +short redhat.com
```

Fix, persistently:

```bash
sudo nmcli con mod ens160 ipv4.dns "192.168.56.1 8.8.8.8"
sudo nmcli con up ens160
cat /etc/resolv.conf
getent hosts redhat.com
ping -c2 redhat.com
```

**The `ping IP` works but `ping name` fails pattern always means DNS.** Do not go looking at routes or the firewall.

**Task 13.**

```bash
ping -c1 server2.lab.example.com      # works
ping -c1 server2                      # ping: server2: Name or service not known
```

The FQDN resolves, the short name does not. **That is a missing search domain.**

```bash
grep search /etc/resolv.conf          # nothing
nmcli -f ipv4.dns-search con show ens160
```

Fix:

```bash
sudo nmcli con mod ens160 ipv4.dns-search lab.example.com
sudo nmcli con up ens160
grep search /etc/resolv.conf
getent hosts server2
ping -c1 server2
```

The alternative fix — add the short name as an alias in `/etc/hosts`:

```bash
sudo sed -i 's/^192.168.56.12.*/192.168.56.12  server2.lab.example.com server2/' /etc/hosts
getent hosts server2
```

| Fault | Fix |
| --- | --- |
| Short name fails, FQDN works | **`ipv4.dns-search`**, or an alias in `/etc/hosts` |
| FQDN fails, short name works | An `/etc/hosts` entry missing the FQDN |
| Both fail | No resolver, or no hosts entry at all |

**Which fix to use depends on the task.** "Configure the search domain" means `nmcli`. "Ensure server2 resolves" is satisfied by either, and the hosts entry is more robust in a lab with no DNS.

**Task 14.**

Per-connection:

```bash
sudo nmcli con mod ens160 ipv4.ignore-auto-dns yes
sudo nmcli con up ens160
```

That only ignores DHCP-supplied DNS. To stop NetworkManager writing the file at all:

```bash
sudo mkdir -p /etc/NetworkManager/conf.d
sudo tee /etc/NetworkManager/conf.d/90-dns-none.conf >/dev/null <<'EOF'
[main]
dns=none
EOF

sudo systemctl reload NetworkManager
```

Now `/etc/resolv.conf` is yours:

```bash
sudo tee /etc/resolv.conf >/dev/null <<'EOF'
search lab.example.com
nameserver 192.168.56.1
nameserver 8.8.8.8
EOF

sudo nmcli con up ens160
cat /etc/resolv.conf                  # your content survives
getent hosts redhat.com
```

Revert:

```bash
sudo rm /etc/NetworkManager/conf.d/90-dns-none.conf
sudo nmcli con mod ens160 ipv4.ignore-auto-dns no
sudo systemctl reload NetworkManager
sudo nmcli con up ens160
cat /etc/resolv.conf                  # regenerated header is back
```

**Know this exists, but do not reach for it.** On the exam, "configure DNS" means `nmcli con mod ipv4.dns`. `dns=none` is for the rare case where a task explicitly requires a hand-maintained `resolv.conf`.

**Task 15.**

Before the reboot:

```bash
cat /etc/hostname
grep -v '^#' /etc/hosts | grep -v '^$'
nmcli -f ipv4.dns,ipv4.dns-search connection show ens160
nmcli -f NAME,AUTOCONNECT connection show
cat /etc/resolv.conf
getent hosts server2.lab.example.com
```

Then:

```bash
sudo reboot
```

After the reboot:

```bash
hostname
hostname -f
hostnamectl
cat /etc/resolv.conf
getent hosts server2
getent hosts server2.lab.example.com
ping -c1 server2
```

**`/etc/hostname` and `/etc/hosts` are plain files and always persist.** The fragile piece is DNS: `/etc/resolv.conf` is regenerated at boot from the connection profile, so if you configured DNS by editing `resolv.conf`, it is gone now.

```bash
# The one thing to check after a reboot
cat /etc/resolv.conf                  # do your nameservers reappear?
```

If they are missing, the profile does not have them:

```bash
nmcli -f ipv4.dns con show ens160
```

| Hostname | **`hostnamectl set-hostname`** → `/etc/hostname` | New shell to update the prompt |
| Hosts entry | **`/etc/hosts`** | Nothing; always persistent |
| DNS servers | **`nmcli con mod ipv4.dns`** → keyfile | `nmcli con up`; **`autoconnect yes`** |
| Search domain | **`nmcli con mod ipv4.dns-search`** | `nmcli con up` |
| Lookup order | `/etc/nsswitch.conf` | Nothing |

**Two traps:**

1. **`hostname foo` does not persist.** Use `hostnamectl set-hostname`.
2. **Editing `/etc/resolv.conf` does not persist.** NetworkManager regenerates it. Use `nmcli con mod ipv4.dns`.

Post-reboot check:

```bash
hostname -f                     # correct FQDN?
cat /etc/resolv.conf            # nameservers still present?
getent hosts <name>             # resolution still works?
```

## Exam Tips

- **`hostnamectl set-hostname NAME` persists; `hostname NAME` does not.**
- **Use the FQDN** when a task supplies one: `server1.lab.example.com`.
- **Your prompt will not update** until a new shell. Check with `hostname`, not the prompt.
- **`/etc/hosts` format: IP, then FQDN, then short aliases.** FQDN first.
- **Use `sudo tee -a` to append to `/etc/hosts`**, never `sudo echo >>`. And do not forget `-a`, or you truncate the file.
- **Never delete the `127.0.0.1 localhost` line.**
- **`getent hosts` is the right verification tool** — it follows `nsswitch.conf`, so it sees `/etc/hosts` exactly as `ping`, `ssh`, and `mount` do.
- **`dig` and `host` ignore `/etc/hosts`.** NXDOMAIN from `dig` while `ping` works is normal when the name is in `/etc/hosts`.
- **Never edit `/etc/resolv.conf`.** It says "Generated by NetworkManager" at the top for a reason. Use `nmcli con mod ipv4.dns`.
- **Use `+ipv4.dns` to append.** Plain assignment replaces the entire list.
- **`ipv4.dns-search`** fixes "the FQDN works but the short name does not".
- **`/etc/hosts` beats DNS** in the default `hosts: files dns` order. Grep it when a name resolves to the wrong address.
- **`dig @8.8.8.8 name`** bypasses your resolver — the fastest way to prove whether the fault is local.
- **`ping IP` works but `ping name` fails means DNS.** Do not investigate routes.
- **`getent hosts <ip>`** does a reverse lookup from `/etc/hosts`; `dig -x` needs a real PTR record.
- **Install `bind-utils`** if `dig` and `host` are missing.
- **After a reboot, check `/etc/resolv.conf` first.** It is the piece most likely to have evaporated.
