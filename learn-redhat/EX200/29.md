# 29. Logical Volume Management (LVM)

**Objectives:** Create and remove physical volumes. Assign physical volumes to volume groups. Create and delete logical volumes. Extend existing logical volumes.

**"Extend an existing logical volume" is one of the most reliably-appearing tasks on the exam**, and it is worth practising until it is automatic. LVM is also easier than raw partitions for anything involving resizing, which is why Red Hat uses it by default.

## Concept Refresher

### The three layers

```text
   ┌────────────────────────────────────────────────────────────┐
   │  /data          mount point                                │
   ├────────────────────────────────────────────────────────────┤
   │  XFS            filesystem                                 │
   ├────────────────────────────────────────────────────────────┤
   │  LV: lv_data    LOGICAL VOLUME     "the usable device"     │
   │       /dev/vg01/lv_data  =  /dev/mapper/vg01-lv_data       │
   ├────────────────────────────────────────────────────────────┤
   │  VG: vg01       VOLUME GROUP       "the pool of space"     │
   │       carved into Physical Extents (PE), default 4 MiB     │
   ├────────────────────────────────────────────────────────────┤
   │  PV: /dev/sdb1  /dev/sdc1          PHYSICAL VOLUMES        │
   ├────────────────────────────────────────────────────────────┤
   │  /dev/sdb  /dev/sdc                disks                   │
   └────────────────────────────────────────────────────────────┘
```

| Layer | What it is | Created with | Inspected with |
| --- | --- | --- | --- |
| **PV** | A disk or partition prepared for LVM | **`pvcreate`** | `pvs`, `pvdisplay` |
| **VG** | A pool of space made of one or more PVs | **`vgcreate`** | `vgs`, `vgdisplay` |
| **LV** | A slice of the VG, used like a partition | **`lvcreate`** | `lvs`, `lvdisplay` |

**The command prefixes are completely regular:** `pv*`, `vg*`, `lv*`, each with `create`, `remove`, `display`, `s`, `extend`, `reduce`, `rename`, `scan`.

### Why LVM

| | Plain partition | **LVM** |
| --- | --- | --- |
| Grow it | Only if free space follows it | **Any free space in the VG** |
| Span multiple disks | No | **Yes** |
| Snapshot | No | Yes |
| Shrink | ext4 only, awkward | ext4 yes; XFS still no |
| Rename | No | **Yes** |

**Growing is the point.** A plain partition can only grow into contiguous free space; an LV can grow using extents from anywhere in the VG, including a disk added later.

### Physical extents

A VG divides its space into fixed-size **physical extents**, 4 MiB by default. Every LV is a whole number of extents.

```bash
sudo vgdisplay vg01 | grep -E 'PE Size|Total PE|Free.*PE'
```

```text
  PE Size               4.00 MiB
  Total PE              511
  Free  PE / Size       255 / 1020.00 MiB
```

```bash
sudo vgcreate -s 8M vg01 /dev/sdb1        # non-default extent size
sudo vgcreate --physicalextentsize 16M vg01 /dev/sdb1
```

**Extent size matters for two exam reasons.** First, a task may specify it: "create a volume group with a 16 MiB extent size" means `vgcreate -s 16M`. Second, **LV sizes are rounded up to a whole number of extents**, so asking for a 100 MiB LV with 8 MiB extents gives you 104 MiB. That is expected, not an error.

### Physical volumes

```bash
sudo pvcreate /dev/sdb1
sudo pvcreate /dev/sdb1 /dev/sdc1         # several at once
sudo pvcreate /dev/sdb                    # a whole disk, no partition table

sudo pvs                                  # summary
sudo pvs -o +pv_used
sudo pvdisplay                            # detail
sudo pvdisplay /dev/sdb1
sudo pvscan
sudo pvremove /dev/sdb1                   # must not be in a VG
sudo pvmove /dev/sdb1                     # migrate extents off it first
```

```text
$ sudo pvs
  PV         VG    Fmt  Attr PSize   PFree
  /dev/sda2  rhel  lvm2 a--  <19.00g      0
  /dev/sdb1  vg01  lvm2 a--  1020.00m 508.00m
  /dev/sdc1        lvm2 ---     1.00g   1.00g
```

**An empty `VG` column means the PV is not yet in a volume group.** `PFree` is the unallocated space on that PV.

### Volume groups

```bash
sudo vgcreate vg01 /dev/sdb1
sudo vgcreate vg01 /dev/sdb1 /dev/sdc1
sudo vgcreate -s 16M vg01 /dev/sdb1

sudo vgs
sudo vgdisplay
sudo vgdisplay vg01
sudo vgscan

sudo vgextend vg01 /dev/sdc1              # ADD a PV to the VG
sudo vgreduce vg01 /dev/sdc1              # REMOVE a PV from the VG
sudo vgrename vg01 vgdata
sudo vgremove vg01                        # must contain no LVs
sudo vgchange -an vg01                    # deactivate
sudo vgchange -ay vg01                    # activate
```

```text
$ sudo vgs
  VG    #PV #LV #SN Attr   VSize   VFree
  rhel    1   2   0 wz--n- <19.00g      0
  vg01    1   1   0 wz--n- 1020.00m 508.00m
```

**`VFree` is the space available for new or extended LVs.** If it is zero, you must `vgextend` before you can `lvextend`.

**`vgcreate` runs `pvcreate` implicitly** if the device is not already a PV. Doing it explicitly is clearer and is what tasks expect.

### Logical volumes

```bash
# By size
sudo lvcreate -n lv_data -L 500M vg01
sudo lvcreate -n lv_data -L 1G vg01

# By extent count
sudo lvcreate -n lv_data -l 50 vg01

# By percentage
sudo lvcreate -n lv_data -l 50%FREE vg01
sudo lvcreate -n lv_data -l 100%FREE vg01        # all remaining space
sudo lvcreate -n lv_data -l 100%VG vg01

sudo lvs
sudo lvs -o +devices
sudo lvdisplay
sudo lvdisplay /dev/vg01/lv_data
sudo lvrename vg01 lv_old lv_new
sudo lvremove /dev/vg01/lv_data
```

```text
$ sudo lvs
  LV      VG   Attr       LSize   Pool Origin Data%
  root    rhel -wi-ao---- <17.00g
  swap    rhel -wi-ao----   2.00g
  lv_data vg01 -wi-a-----  512.00m
```

**Case matters: `-L` is a size, `-l` is extents or a percentage.** Mixing them up is a classic slip:

| Flag | Meaning | Example |
| --- | --- | --- |
| **`-L`** | **Size** | `-L 500M`, `-L 1G`, `-L +200M` |
| **`-l`** | **Extents or percentage** | `-l 50`, `-l 100%FREE`, `-l +50` |
| `-n` | Name | `-n lv_data` |

Two device paths refer to the same LV:

```bash
ls -l /dev/vg01/lv_data
ls -l /dev/mapper/vg01-lv_data
```

**Both work everywhere.** `/dev/vg01/lv_data` is easier to type; `/dev/mapper/vg01-lv_data` is what `lsblk` and `df` display. **Note the hyphen in the mapper name** — a VG or LV name containing a hyphen is doubled there, which is a good reason to use underscores.

### Extending — the exam-critical operation

```text
   Need more space in /data?
              │
   ┌──────────▼──────────────────────────────┐
   │  Does the VG have free space?           │
   │     sudo vgs                            │
   └──────────┬──────────────────────────────┘
              │
       ┌──────┴───────┐
       │ yes          │ no
       │              ▼
       │      Add a PV first:
       │        fdisk /dev/sdc      (28.md)
       │        pvcreate /dev/sdc1
       │        vgextend vg01 /dev/sdc1
       │              │
       └──────┬───────┘
              ▼
     lvextend -r -L +500M /dev/vg01/lv_data
              │
              ▼
       df -h /data     ← the size must have changed
```

```bash
# The one command to remember
sudo lvextend -r -L +500M /dev/vg01/lv_data

# Variations
sudo lvextend -r -L 2G /dev/vg01/lv_data          # to an absolute 2 GiB
sudo lvextend -r -l +100%FREE /dev/vg01/lv_data   # use all remaining VG space
sudo lvextend -r -l +50 /dev/vg01/lv_data         # 50 more extents
```

**`-r` (`--resizefs`) grows the filesystem at the same time.** Without it you have a bigger LV and a filesystem that still believes it is the old size:

```bash
sudo lvextend -L +500M /dev/vg01/lv_data          # no -r
sudo lvs                                          # LV is bigger
df -h /data                                       # filesystem is NOT
```

Then you must do it by hand:

```bash
sudo xfs_growfs /data              # XFS: takes the MOUNT POINT, must be mounted
sudo resize2fs /dev/vg01/lv_data   # ext4: takes the DEVICE
```

**`-r` is worth memorising because it removes an entire class of mistake.** It calls the right tool for whichever filesystem is there.

**The `+` matters:**

| Command | Result |
| --- | --- |
| `-L +500M` | **Adds** 500 MiB |
| `-L 500M` | Sets the total size **to** 500 MiB — a shrink if it was bigger |

Asking for a smaller absolute size on XFS fails outright, which is a lucky escape. On ext4 without care it destroys data. **Use `+` when a task says "add" or "increase by".**

### Shrinking

```bash
# ext4 only, and unmount first
sudo umount /data
sudo e2fsck -f /dev/vg01/lv_data
sudo resize2fs /dev/vg01/lv_data 500M
sudo lvreduce -L 500M /dev/vg01/lv_data
sudo mount /data

# or, with -r doing the filesystem part
sudo lvreduce -r -L 500M /dev/vg01/lv_data
```

**XFS cannot shrink. At all. Ever.** The only route is backup, `lvreduce`, `mkfs.xfs`, restore.

```text
$ sudo lvreduce -r -L 500M /dev/vg01/lv_data
fsadm: Xfs filesystem shrinking is not supported
```

**On the exam, "shrink" implies ext4 or a fresh filesystem.** Since RHEL's default is XFS, a shrink task is unusual — but recognise the constraint immediately so you do not waste time.

**Shrinking below the used data destroys it.** Check first:

```bash
df -h /data
```

### Removing, in the right order

```bash
# 1. Unmount and remove the fstab entry FIRST
sudo umount /data
sudo vim /etc/fstab                       # delete the line
sudo findmnt --verify

# 2. Then work down the stack
sudo lvremove /dev/vg01/lv_data
sudo vgremove vg01
sudo pvremove /dev/sdb1
```

**Removal is strictly bottom-up-blocked**: you cannot remove a VG containing LVs, or a PV belonging to a VG. LVM refuses with a clear message, which is helpful.

**And the `/etc/fstab` entry must go first**, or the next boot drops to emergency mode looking for a device that no longer exists. Same rule as `28.md`.

To take a PV out of a VG that still has other PVs:

```bash
sudo pvs -o +pv_used                      # is anything on it?
sudo pvmove /dev/sdc1                     # migrate extents elsewhere
sudo vgreduce vg01 /dev/sdc1
sudo pvremove /dev/sdc1
```

**`pvmove` before `vgreduce`** if the PV holds any extents, or you lose the data on it.

### Inspecting everything

```bash
sudo pvs; sudo vgs; sudo lvs              # the three-command summary
sudo lvs -o +devices                      # which PVs each LV uses
sudo vgs -o +vg_free_count                # free extents
sudo pvdisplay; sudo vgdisplay; sudo lvdisplay
sudo lvmdiskscan
lsblk
sudo dmsetup ls
sudo dmsetup info
```

```bash
# One-liner overview
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
```

```text
NAME            SIZE TYPE FSTYPE      MOUNTPOINTS
sda              20G disk
├─sda1            1G part xfs         /boot
└─sda2           19G part LVM2_member
  ├─rhel-root    17G lvm  xfs         /
  └─rhel-swap     2G lvm  swap        [SWAP]
sdb               2G disk
└─sdb1         1020M part LVM2_member
  └─vg01-lv_data 512M lvm  xfs        /data
```

**`lsblk` shows the whole stack in one view**, which is why it is the fastest sanity check.

### The complete workflow, start to finish

```bash
# 1. Partition a disk with type lvm (28.md)
lsblk
sudo fdisk /dev/sdb          # n, Enter, Enter, +1G, t, lvm, w
sudo partprobe /dev/sdb
lsblk /dev/sdb

# 2. PV
sudo pvcreate /dev/sdb1
sudo pvs

# 3. VG
sudo vgcreate vg01 /dev/sdb1
sudo vgs

# 4. LV
sudo lvcreate -n lv_data -L 500M vg01
sudo lvs

# 5. Filesystem
sudo mkfs.xfs /dev/vg01/lv_data

# 6. Mount point and mount
sudo mkdir -p /data
sudo mount /dev/vg01/lv_data /data

# 7. PERSIST — the step that scores
sudo blkid /dev/vg01/lv_data
echo "UUID=$(sudo blkid -s UUID -o value /dev/vg01/lv_data)  /data  xfs  defaults  0 0" | sudo tee -a /etc/fstab
sudo findmnt --verify
sudo mount -a

# 8. Verify
df -hT /data
lsblk
```

**Eight steps. Step 7 is the one people forget, and it is where the marks are.**

### Snapshots

Not a listed objective, but easy and occasionally useful:

```bash
sudo lvcreate -s -n lv_data_snap -L 200M /dev/vg01/lv_data
sudo lvs
sudo mount -o ro /dev/vg01/lv_data_snap /mnt
sudo umount /mnt
sudo lvconvert --merge /dev/vg01/lv_data_snap     # roll back to the snapshot
sudo lvremove /dev/vg01/lv_data_snap
```

**A snapshot fills up as the origin changes, and becomes invalid when full.** Size it for the expected rate of change.

```text
$ sudo lvs
  LV   VG   Attr       LSize   Pool Origin
  root rhel -wi-ao---- <17.00g

```

```text
$ lsblk
NAME          SIZE TYPE FSTYPE      MOUNTPOINTS
sda            20G disk
├─sda1          1G part xfs         /boot
└─sda2         19G part LVM2_member
  ├─rhel-root  17G lvm  xfs         /
  └─rhel-swap   2G lvm  swap        [SWAP]
sdb             2G disk
sdc             2G disk
```

Reading the default RHEL layout:

- **`/boot` is a plain partition** (`sda1`), because GRUB reads it before LVM is available.
- **`sda2` is a single PV** holding the `rhel` VG.
- **`/` and swap are logical volumes** inside that VG, which is why `/` can be grown later.
- **`VFree 0`** means the installer used all the space. To grow `/` you would need to add a PV first.

The `Attr` field on an LV, `-wi-ao----`:

| Position | Value | Meaning |
| --- | --- | --- |
| 1 | `-` | Volume type: `-` linear, `s` snapshot, `t` thin pool |
| 2 | `w` | **Writable** |
| 3 | `i` | Allocation policy: inherited |
| 5 | **`a`** | **Active** |
| 6 | `o` | **Open, i.e. mounted** |

**`a` in position 5 means active; if it is missing, the LV is not usable.** Activate with `vgchange -ay vg01`.

More detail when you need it:

```bash

sudo vgdisplay rhel
sudo lvdisplay /dev/rhel/root
sudo lvs -o +devices
```

**Now persist it — this is the step that scores:**

```bash
sudo blkid /dev/vg01/lv_data
echo "UUID=$(sudo blkid -s UUID -o value /dev/vg01/lv_data)  /data  xfs  defaults  0 0" | sudo tee -a /etc/fstab
```

```bash
echo "/dev/vg01/lv_data  /data  xfs  defaults  0 0" | sudo tee -a /etc/fstab
```

**Validate before trusting it:**

```bash
sudo findmnt --verify
sudo umount /data
sudo mount -a
df -hT /data
```

```text
Success, no errors or warnings detected
```

**Unmounting and then running `mount -a` is the real test** — it proves the `/etc/fstab` line works rather than just that the manual mount worked.

Two notes:

- **`-L 500M` gives exactly 500 MiB** here because 500 is divisible by the 4 MiB extent size. A size that is not divisible is rounded up, with a message.
- **Device path or UUID both work for an LV.** Unlike `/dev/sdb1`, `/dev/vg01/lv_data` is stable across reboots because LVM assembles it by metadata. UUID is still the safer habit.

```text
$ findmnt /data
TARGET SOURCE                    FSTYPE OPTIONS
/data  /dev/mapper/vg01-lv_data  xfs    rw,relatime,seclabel,attr2,inode64
```

**If `/data` is not mounted after the reboot, the `/etc/fstab` entry is wrong or missing.** Check in this order:

```bash
grep data /etc/fstab                # is the line there?
sudo findmnt --verify               # is it valid?
sudo mount -a                       # does it mount, and what is the error?
sudo lvs                            # is the LV active?
sudo blkid /dev/vg01/lv_data        # does the UUID match the fstab line?
systemctl --failed                  # did the mount unit fail?
journalctl -b | grep -i data
```

**LVM volumes are activated automatically at boot** by udev and `lvm2-monitor`, so an inactive LV is unusual. If it happens:

```bash
sudo vgchange -ay vg01
sudo lvs                            # check for 'a' in the Attr field
```

| Filesystem | Grow command | Argument | Mounted? |
| --- | --- | --- | --- |
| **XFS** | **`xfs_growfs`** | **The mount point** | **Must be mounted** |
| ext4 | `resize2fs` | The device | Either |
| **Any** | **`lvextend -r`** | The LV | Handles it for you |

**Use `-r` and this whole table stops mattering.** Memorise `lvextend -r -L +SIZE /dev/vg/lv`.

**Note it is `-l`, lowercase, for a percentage — not `-L`:**

| Form | Meaning |
| --- | --- |
| **`-l +100%FREE`** | **Add all currently free space** |
| `-l 100%VG` | Set the LV to the whole VG size |
| `-l +50%FREE` | Add half the currently free space |
| `-L +100M` | Add 100 MiB |
| `-l +25` | Add 25 extents |

**`+100%FREE` versus `100%FREE`** — the `+` means "add all free space to what I already have", which is almost always what you want. Without it the LV is set to the size of the free space, which could shrink it.

`-l +100%FREE` is the right answer to "use all remaining space in the volume group" and saves you doing arithmetic under time pressure.

**Task 11.**

Create an ext4 LV:

```bash
sudo lvcreate -n lv_ext -L 800M vg01 2>/dev/null || sudo lvcreate -n lv_ext -l 100%FREE vg01
sudo mkfs.ext4 /dev/vg01/lv_ext
sudo mkdir -p /extdata
sudo mount /dev/vg01/lv_ext /extdata
df -hT /extdata
echo "test data" | sudo tee /extdata/file.txt
```

Shrink it. **The filesystem must shrink before the volume, and ext4 must be unmounted and checked first:**

```bash
sudo umount /extdata
sudo e2fsck -f /dev/vg01/lv_ext
sudo resize2fs /dev/vg01/lv_ext 300M
sudo lvreduce -L 300M /dev/vg01/lv_ext
sudo mount /extdata
df -hT /extdata
cat /extdata/file.txt
```

`lvreduce` warns, and the warning is justified:

```text
  WARNING: Reducing active logical volume to 300.00 MiB.
  THIS MAY DESTROY YOUR DATA (filesystem etc.)
Do you really want to reduce vg01/lv_ext? [y/n]: y
```

Or let `-r` orchestrate it:

```bash
sudo lvreduce -r -L 300M /dev/vg01/lv_ext
```

**The order is the opposite of extending:**

| Operation | Order |
| --- | --- |
| **Extend** | **LV first, then filesystem** (`lvextend -r`) |
| **Shrink** | **Filesystem first, then LV** (`lvreduce -r`) |

Reversing it destroys data — shrinking the LV under a full-size filesystem truncates it.

**Now XFS:**

```bash
sudo lvreduce -r -L 300M /dev/vg01/lv_data
```

```text
  fsadm: Xfs filesystem shrinking is not supported
```

```bash
sudo xfs_growfs -D 76800 /data
```

```text
  data size 76800 too small, old size is 230400
```

**XFS cannot shrink. There is no tool, no flag, and no workaround.** The only route is:

```bash
sudo tar -czf /root/data-backup.tar.gz -C /data .
sudo umount /data
sudo lvreduce -L 300M /dev/vg01/lv_data
sudo mkfs.xfs -f /dev/vg01/lv_data
sudo mount /data
sudo tar -xzf /root/data-backup.tar.gz -C /data
sudo restorecon -Rv /data
```

| | Grow | Shrink |
| --- | --- | --- |
| **XFS** | **Yes**, `xfs_growfs`, mounted | **NO. Never** |
| ext4 | Yes, `resize2fs`, online or offline | **Yes**, offline, after `e2fsck -f` |
| LVM LV | Yes, `lvextend` | Yes, `lvreduce` |

**RHEL's default is XFS, so on the exam a shrink task means ext4** — or it is testing whether you recognise the constraint. Note the `restorecon` after restoring from tar; see `27.md` for why.

| --- | --- | --- |

| `pvremove` | Erase the LVM label | The disk still looks like a PV |


**Two linear segments on two PVs. Confirmed.**

```bash
sudo mkfs.xfs /dev/vgspan/lv_big
sudo mkdir -p /bigdata
sudo mount /dev/vgspan/lv_big /bigdata
df -hT /bigdata
```

```text
/dev/mapper/vgspan-lv_big  xfs  3.0G  54M  2.9G   2% /bigdata
```

**A single 3 GiB filesystem built from two 1.5 GiB disks — impossible with plain partitions.** That is LVM's headline feature.

Two caveats:

- **Linear LVM gives no redundancy.** Lose either disk and the whole LV is lost. For redundancy you need RAID or `lvcreate --type raid1`, neither of which is an RHCSA objective.
- **`--type striped` interleaves for performance:**

```bash
sudo lvcreate --type striped -i 2 -n lv_striped -L 1G vgspan
```

`-i 2` stripes across two PVs. Also not an objective, but worth recognising.

Before the reboot:

```bash
df -hT

```

All of these must hold:

- The PVs, VGs, and LVs are as the tasks required.
- **Every LV that should be mounted has an `/etc/fstab` entry.**
- **`findmnt --verify` reports no errors.**
- **`mount -a` succeeds.**
- `df -hT` shows the expected sizes.

```bash
sudo reboot
```

After:

```bash
sudo pvs; sudo vgs; sudo lvs
lsblk
df -hT
findmnt /data
mount | grep data
systemctl --failed
```

**LVM metadata lives on the disks, so PVs, VGs, and LVs always persist** — there is no service to enable and no configuration file to write. LVs are activated automatically at boot.

**So the only persistence risk in LVM is `/etc/fstab`:**

| Symptom after reboot | Cause |
| --- | --- |
| LV exists, not mounted | **No `/etc/fstab` entry** |
| Emergency mode | **A stale `/etc/fstab` entry** for a removed LV, or a typo |
| Mounted but the wrong size | `lvextend` without `-r`, filesystem never grown |
| LV inactive | Rare; `vgchange -ay VG` |

```bash
# The pre-reboot storage check, in three lines
sudo findmnt --verify
sudo mount -a && echo OK || echo "*** DO NOT REBOOT — FIX FSTAB ***"
df -hT
```

**If `mount -a` fails, do not reboot.** Fix `/etc/fstab` first. That single habit prevents the worst outcome available on this exam.

## Persistence Check

| Change | Persistent because | Also required |
| --- | --- | --- |
| PV created | **LVM label on the disk** | — |
| VG created | **Metadata on the PVs** | — |
| LV created | **Metadata on the PVs** | — |
| LV extended | **Metadata on the PVs** | **`-r`, or grow the filesystem separately** |
| Filesystem | `mkfs` writes to the LV | — |
| **Mount** | **`/etc/fstab`** | **`findmnt --verify` + `mount -a`** |
| LV activation | Automatic at boot | `vgchange -ay VG` if ever needed |

**All LVM structures persist by themselves.** The two things that can still cost you marks:

1. **No `/etc/fstab` entry** — the LV exists but is not mounted after the reboot.
2. **`lvextend` without `-r`** — the LV is bigger but the filesystem is not, so `df` shows the old size and the task fails.

```bash
# The pre-reboot LVM check
sudo lvs                            # sizes as required?
df -hT                              # filesystems the SAME size as the LVs?
sudo findmnt --verify
sudo mount -a && echo OK
```

## Exam Tips

- **The stack is PV → VG → LV → filesystem → mount.** Create in that order, remove in reverse.
- **The full sequence to memorise:** `fdisk` → `partprobe` → `pvcreate` → `vgcreate`/`vgextend` → `lvcreate`/`lvextend -r` → `mkfs` → `mkdir` → `mount` → **`/etc/fstab`** → `findmnt --verify` → `mount -a`.
- **`lvextend -r -L +500M /dev/vg/lv` is the single most valuable command in this file.** `-r` grows the filesystem too.
- **`-L` is a size, `-l` is extents or a percentage.** `-L +500M`, `-l +100%FREE`.
- **The `+` means add.** `-L 500M` sets the total size and can shrink the volume.
- **Run `sudo vgs` before every `lvextend`.** "Insufficient free space" means `vgextend` first.
- **VG full? `fdisk` → `pvcreate` → `vgextend` → `lvextend -r`.** This is the classic exam task.
- **Without `-r`: `xfs_growfs /mountpoint`** (must be mounted) or **`resize2fs /dev/vg/lv`**. XFS takes the mount point, ext4 takes the device.
- **XFS cannot shrink.** Shrinking means ext4, unmounted, `e2fsck -f`, `resize2fs`, then `lvreduce`.
- **Extend: LV first, then filesystem. Shrink: filesystem first, then LV.**
- **A VG's usable size is slightly less than the disk** because of metadata. 1 GiB becomes 1020 MiB. Normal.
- **LV sizes round up to whole extents.** With `-s 16M`, a 100 MiB request gives 112 MiB.
- **`vgcreate -s 16M`** sets a non-default extent size when a task asks for one.
- **`/dev/vg01/lv_data` and `/dev/mapper/vg01-lv_data` are the same device.**
- **Use `UUID=` in `/etc/fstab`.** It survives renaming a VG or LV; a device path does not.
- **Remove the `/etc/fstab` entry before removing an LV.** Otherwise the next boot lands in emergency mode.
- **`pvmove` before `vgreduce`** if the PV holds extents. Never `vgreduce --force`.
- **`lvs -o +devices`** shows which PVs an LV occupies.
- **Verify a resize with `df -h`, not `lvs`.** Both numbers must change.
- **`findmnt --verify` and `mount -a` before every reboot.** If `mount -a` fails, fix `/etc/fstab` before rebooting.
